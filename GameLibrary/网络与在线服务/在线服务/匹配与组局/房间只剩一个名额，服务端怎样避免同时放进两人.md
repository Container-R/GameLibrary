# 房间只剩一个名额，服务端怎样避免同时放进两人

四人房已经连进三人。甲和乙都看到列表写着「3/4」，几乎同时点击加入。只要两个请求都按列表人数放行，服务器就可能承诺五个人能进四人房。哪怕列表从未缓存，也可能发生：两次读取都在第一笔预留落账之前。

列表回答「刚才看到几个人」，加入接口才回答「现在这一个名额给谁」。排查时还要分开**已入房的人数**与**已经占掉的名额数**。有人正在连接但已经拿到预留，列表可以仍显示三人已入房，实际已没有空位。

## 在承诺入房的那一步核对空位

若服务端收到请求就能完成入房，在同一次权威状态变更里检查房间可加入、还有名额，并登记成员即可。不要在一段代码读人数、走完异步步骤后又无条件加一。SQLite 小试件让两个请求都先读到 1 个空位：直接相信旧读数，最终计成 5/4；以当前状态作条件更新，只有一个成功，最后是 4/4。

实际项目可能要先返回地址、等客户端连到房间再确认。此时给先到的人留下一个带截止时间的预留：

```text
占用 = 已加入 + 未过期的预留
始终保证占用 ≤ 当前房间容量
```

对同一个房间实例，让会改变这笔账的操作按一个顺序提交。比如交给房间服务器的串行处理循环，或在数据库里让同房的操作竞争同一处锁或写入条件。**检查还有名额、记录这份预留、返回分配成功**要有同一个明确的生效点：先提交，成功后才答复。若用数据库，仅把各自的读取和写入包进一般事务，并不自动保证两笔写入检查到同一个最新状态；必须验证隔离或条件更新的实际行为。[3]

## 确认是在交接名额，不是再抢一次

为每次预留保存房间实例、服务端确认的玩家身份、不会混淆的新预留号及截止时间。复用的房间号要能区分旧房和新房；预留号也不能只写玩家名。这里采用服务端决定时刻严格早于截止才有效的规则，即「到点即过期」。这不是所有游戏都必须采用的处置。

| 操作 | 服务端该检查什么 | 对占用的影响 |
| --- | --- | --- |
| 首次预留 | 房间仍接纳、玩家符合条件、尚有空位 | 有效预留加 1 |
| 同一有效预留的回复丢失，玩家重试 | 先查原请求或预留，返回已有结果及当前状态，不替换截止时间 | 不变 |
| 连接完成后确认 | 还是该房该玩家的这份预留，状态仍为预留，且还有效 | 同一步将预留变为已加入，占用不变 |
| 预留到期 | 用服务端时间确认这份预留已到期且仍未转正 | 不再占位；清理不动已加入成员 |
| 已加入后离开 | 确认是当前成员的离开，不是旧预留的超时 | 释放这份成员占位 |

例如三名成员加甲的一份有效预留是 `3+1`；甲确认后变成 `4+0`，乙不应在交接中途挤进来。不要先释放预留，再等另一次写入加成员。反过来，超时任务晚到了，也不能按「甲」把他当时正持有的东西全删掉。**只让这次任务修改它对应的预留号，而且必须仍处于预留状态。** 旧 A1 的定时任务即使看到同一个玩家，也不能释放新预留 A2；已过期的 A1 更不能被迟到确认重新启用。过期资格的判断不依赖定时器有没有及时执行：决定接纳下一人时，也要按同一时钟处理已过期的记录。

GameLift Servers 的公开流程把创建玩家会话后的 `RESERVED` 和验证后的 `ACTIVE` 分开，超时会重新开放名额。Nakama 则把是否同意加入的 `MatchJoinAttempt`、成功加入后通知游戏逻辑、提供玩家连接记录的 `MatchJoin` 分开，列表标签可用于搜索。它们提供了观察这些阶段的例子。若自己的逻辑负责容量，不能等后面的加入回调才记住已批准但尚未连接的人。上述标识和清理规则是本文的设计，不是两套服务公开的内部实现。[1][2]

## 复现两个读数一样，不代表两个结果一样

SQLite 对照用同一临时数据库的两条连接，预设三人已加入。两条连接的列表读取都得到 3。甲先开启 `BEGIN IMMEDIATE` 并写预留；乙此时尝试同一写入口，收到 `SQLITE_BUSY`。甲提交后，乙从头重试，取得写入口并重算占用，才得到「已满」。**数据库忙表示这次没取得决定权，不代表当时确认没有名额。** 对前者可按产品规则给有上限的重试或短暂提示；后者则应更新大厅列表或让玩家另选房。[3]

另外，试件用可控时钟验证截止。A1 在时刻 0 建立，截止为 10：

- 甲在 9 确认，记录变成 `4+0`。A1 的清理在 11 才执行，改变 0 行；之后重复确认也不增加成员。
- 若甲没有确认，10 到点时不能再确认 A1；同一人新拿到 A2 后，A1 的旧清理不会改变 A2。若名额已改给乙，迟到的 A1 也不会抢走乙的预留。

项目回归可以把这些顺序做成自动化测试。日志至少要能串起房间实例、容量、请求号、预留号、服务端决定时间、状态变更前后的两种人数，以及结果是「忙」「已满」「已加入」还是「已失效」。同一请求丢回执后再试，也要校验它拿回的还是原结果或同一份资格的现状，而不是新开一张预留。测试中间的 `3+1 → 4+0` 比只看最后人数更有用。

这些试件使用本地文件和合成时钟，验证的是容量、状态转移和数据库写入条件。多节点房间还要单独确认主机故障、重连、持有时间与共同的授权状态如何交接；不能把只有某一节点看到的连接数当成全局账本。
