# 匹配确认超时后，迟到的接受该算给哪一场

玩家点了“接受”，界面一直等待。另一人没回应，这轮确认超时，已经同意的人回到队列。几秒后弹出新的对局，第一轮那个没收到回执的“接受”也自动重发了。如果服务端只看匹配票号，两轮可能还是同一张票，重发就会被当成接受了新对局。问题不是“要不要重试”，而是**玩家接受的是哪一份提案，决定在哪一步生效**。

下面用假想的匹配协调器讲解。目标是处理正常的延迟、重发、掉线恢复和分配竞态，不是描述任何托管服务的内部代码。

## 排队票可以继续，确认提案必须换

匹配票（ticket）是某个玩家或小队的一次排队请求。确认提案（proposal）是匹配器拿这批票组成的一份特定对局建议。一次提案失败后，项目可以让符合规则的整张票回到搜索；新的候选对局必须生成新的提案身份，即使碰巧还是同一批人。应由服务端确定票与提案的对应、参与成员和确认截止时间。客户端打开弹窗时保存提案身份；弹窗关闭也不会改变此前提交的请求所指向的提案。

以下事件的时间是模拟服务时钟。A 的排队票始终是 TA，P1 有 A、B，P2 有 A、C。P1 在 100 到期，P2 在 200 到期。

| 时间和动作 | 只查当前票号与玩家 | 按提案登记并保留回执 |
| --- | --- | --- |
| 90：A 接受 P1，但回复丢失 | P1 记录 A | P1 记录 A |
| 100：B 超时；110：A 的票进入 P2 | TA 仍有效 | P1 已关闭；TA 指向 P2 |
| 130：A 原样重发 P1 | 把 A 记为接受 P2 | 可重放 P1 的回执；不改变 P2 |
| 140：P1 的超时任务晚到 | 仍须避免旧超时动到 P2 | 检查提案已关闭，无变更 |
| 150：C 接受 P2；151 重发 | 错误地进入服分配 | P2 只数 C，继续等 A |
| 160：A 真正接受 P2；161 重发 | 已经错误地开始分配 | 此时才产生一次分配意图 |

这张表定义了两件独立的事。**提案身份**决定这条请求有没有资格写入当前候选对局；**请求身份**决定它是不是已经处理过的同一个操作。同一玩家对 P1 的旧请求若有已保存的回执，可以返回“P1 已接受”；若从未登记过，就拒绝写入当前提案。无论哪种情况，这个回执都不是“现在正处于 P1”，更不是对 P2 的接受。不能用会重建内容的通用重试逻辑，把请求上的提案 ID 换成当前页面所显示的提案。

## 在同一次权威写入里检查并计数

对于自己管理提案的服务，在收到决定后开启事务或使用支持等价前置条件的写入。先让涉及同一提案的有效写入串行化，例如锁提案记录再读状态，并让确认、超时、取消和会改变资格的票转移遵守同一规则；或者使用可串行隔离，在冲突后从头重试。仅把步骤放进普通事务还不够：若最后两个人各写一条，两个事务都看不到对方未提交的接受，就可能都判断没齐，最后反而没人触发分配。获得写入顺序后，按已鉴权的玩家、票和提案读取参与关系；新决定只在该票仍指向请求里的提案、提案正待确认、该玩家属于名单、且截至服务端定义的截止边界时生效。示例把截止定义为 `服务端判定时间 < deadline`，截止为 200 时，199 可收、200 和 201 不收。不依赖过期任务一定准点执行，也不让客户端倒计时决定最终结果。生产中要明确哪个权威时间点算立刻生效，以及排队/锁竞争如何计入截止；仅仅先读出状态、过一会再另发写请求，不构成这个保护。

按 `(proposal, player)` 约束玩家只计一次。若面向客户端承诺可重放旧回执，另存 `(proposal, ticket, player, operation)` 对应的决定与返回值，并验证同一请求键没有被改成不同内容。回执和请求内容的指纹应与决定原子提交；否则已接受但还没保存回执时进程退出，提案随后关闭，重发就无法得到承诺的原结果。重复接受不会再增人数。模拟只处理“接受”；拒绝是否可撤回或覆盖以前的接受，必须由游戏规则另定，不能让两台设备无条件“后写覆盖前写”。

最后一个接受（含承诺的回执）、提案从“等待确认”推进到“待分配”，以及插入分配意图，应在同一事务里提交。后台再读取已提交的意图去申请服务器；即使意图存储本身唯一，后台进程也可能在“外部服务已受理、还没来得及标记完成”之间退出。重试时给外部操作稳定的幂等键；若接口不提供这种能力，设计查单、对账与多余分配回收，不能把一条本地记录等同于外部只执行一次。[1][2]

实际 SQLite 3.53.1 试件用两条连接和 `BEGIN IMMEDIATE`。P1 的旧提交不计入 P2；C 的重复只写一条。A 的最后接受、回执和待分配记录一同回滚时，状态与回执仍只保留 C；持有写事务时第二条连接得到 `SQLITE_BUSY`，释放后完整重试，留下 A、C 和恰好一条 P2 分配意图，随后可重放 A 的 P2 回执。SQLite 在这个试件里串行化写入，其他数据库不能因此省掉提案级并发控制。这证明所测事务边界，不证明分布式服务或外部分配恰好一次。[3]

## 重连时别让旧通知把界面倒回去

服务器写入正确，界面仍可能被迟到消息改错。假设同一张票，完整状态修订 42 表示 P1 已过期，修订 43 表示 P2 待确认。若到达顺序是 43、42、43、42，按最后到达者覆盖会显示旧局已结束；按这张票的状态修订只接纳更新版本，则保持当前 P2。提案 ID 用于动作作用域，票的状态修订用于判断哪份状态更新鲜，两者不能互换。

重连先查当前权威快照，再决定是否恢复确认弹窗。完整快照可替换旧状态；如果服务发的是增量，发现缺版本不应盲目跳过，得补取缺失变化或重新拉完整状态。换新票时切换身份，不能把两个不同票的编号比大小。收到旧回执可以结束旧按钮的“正发送”状态，但不能拿回执覆盖新弹窗，也不要自动替玩家接受它。如果已进入“待分配”，还要等分配及连接信息；发出取消请求不等于取消已生效，最终以服务端状态为准。若允许分配期间取消，分配结果回来时仍要确认同一提案还可接入；已取消的不挂接，并按分配接口的规则清理多余资源。

## 托管接口公开了提案事件，不一定能按提案写

AWS GameLift FlexMatch 的公开文档给出一个近似业务流程：提案要求全员接受，失败后已经全员接受的一张票可以重新搜索；票内有人拒绝或不回应，API 文档说整票退出处理。提案、接受和确认完成事件中都有 `detail.matchId`，但确认结束也可能是拒绝或超时，不等于已分配服务器。API 的接受请求只有票号、玩家和决定，没有可传的提案身份；查票也没有公开可用的待确认提案比较字段。[4][5][6]

应用可以用事件里的 ID 对照自己的弹窗，避免主动转发**已知**过时的请求；但“先查票、再提交”并不提供一个公开文档承诺的上游原子条件。这里不推断 AWS 会错误接收重发，也不推断它的内部保护。若业务要求调用方能保证“只接受这份指定提案”，要按公开契约确认上游支持这种条件，或由自己持有确认状态、在确认后才启动可独立调用的分配流程。不要把客户端加字段写成托管服务也知道并检查那个字段。也不要把通知当成完整状态库，托管通知可能丢失，应准备按服务限制对账。若只查到票在待确认，却拿不到可验证的提案标识，就不要用旧弹窗或票号猜身份；保持不可提交，等可核对的状态或按产品规则提示玩家恢复。[7]

排查一例提前进房，至少串起票、提案、玩家、操作号、服务端判定时间、状态修订和分配操作。先判断是**旧确认被记给新提案**，还是**状态没错但到达晚的消息把 UI 改回去**；若提案和修订都对，再查最后确认到服分配这段有没有落下或重复触发。三种症状相似，修复层不同。
