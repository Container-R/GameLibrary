# 实时排行榜用游标翻页，为什么还是会重复或漏人

赛季榜第一页刚看到 A、B，点下一页却又出现 B；原本应该在后面的 C 消失了。把 `OFFSET` 换成游标并不一定能修好。游标回答「从哪条排序边界往后读」，不能让正在改动的分数停在原位。另外，即使所有玩家都出现一次，同分两人的名次也可能算错。榜单需要分别约定**名次、翻页顺序和数据版本**。

## 游标固定的是位置条件，不是数据

假设榜上 A=100、B=90、C=80、D=70，每页两人，按分数从高到低、同分按玩家 ID 升序。第一页给 A、B，游标记下旧边界 (90, B)。两次请求之间 C 升到 110，B 降到 65：

| 读法 | 第二页 | 前两页合看 |
| --- | --- | --- |
| 在当前榜单跳过前两行 | D(70)、B(65) | B 重复、C 漏掉 |
| 从旧游标 (90, B) 查当前榜 | D(70)、B(65) | 同样重复、漏掉 |
| 在第一页的冻结版本查游标 | C(80)、D(70) | 旧版完整且无重复 |

第二行里，B 降到游标之后，所以又符合查询；C 升到游标之前，所以不会再被追加。分数没有动时，键集游标可以避免把一个行号当位置，也便于使用匹配索引；但它不能解决排序键自己跨过边界。在客户端按玩家 ID 去重能遮住重复的 B，找不回漏掉的 C。冻结只是要求浏览过程读同一版本；它不承诺看到最新分数。

## 同分的座次与同分的名次是两件事

再用一个冻结例：A=100，B=C=90，D=E=80。约定同分并列，后一名跳号，则显示 1、2、2、4、4；若产品需要稠密名次（1、2、2、3、3），是另一个规则。分页必须稳定区分 B/C 和 D/E，所以总序仍用分数降序、玩家 ID 升序。榜单身份使用唯一、不可空且排序规则固定的 ID；不能用可改的昵称代替，也不能让两套存储用不同的大小写或字节序解释游标。

以 C、D 为第二页，按并列规则应是 C(2)、D(4)。若先在游标后过滤，再在留下的行里做窗口排名，C、D 会变成 1、2；若窗口排序也塞进唯一 ID，同分不再是同一组，得到 3、4，而不是并列。PostgreSQL 的窗口函数看到的是本层 `WHERE` 等过滤之后的集合，`rank()` 给同一组排序同伴相同名次。[1] 因此先按排行榜**参与资格**确定完整的排序人群，再求名次，最后才给游标划页。若产品另有不改「全服排名」的界面筛选，应放在算名次之后，不能把显示筛选误写成名次范围。

以下是固定版本、固定排名范围的下一页查询；分数非空，每个版本内每个玩家只有一行，比较谓词和排序使用同一套能区分各 ID 的规则。符号参数只表达绑定含义，实际按数据库驱动写法替换。首页省略外层的游标条件。

```sql
WITH ranked AS (
  SELECT player_id, score,
         RANK() OVER (ORDER BY score DESC) AS display_rank
  FROM board_rows
  WHERE board_id = :board AND version_id = :version
)
SELECT player_id, score, display_rank
FROM ranked
WHERE score < :last_score
   OR (score = :last_score AND player_id > :last_id)
ORDER BY score DESC, player_id ASC
LIMIT :page_size;
```

从本页第一条往回翻时，边界改为 `score > first_score OR (score = first_score AND player_id < first_id)`。先按 `score ASC, player_id DESC` 取最近的前 N 条，再按显示总序排回来；若直接按显示总序取 N 条，会跳回榜首而不是上一页。对实际高频榜，可以在生成不可变版本时预计算显示名次，再按版本、分数和 ID 建索引。PostgreSQL 多列 B-tree 可以声明混合排序方向，但查询是否使用索引、成本如何，要看实际规模和计划。[2] 不要把全榜跑窗口的示例直接当每次翻页的性能承诺。

Redis 也不是透明替换：`ZRANGE ... REV` 分数从高到低，等分成员按逆字典序，不是上面 SQL 的 ID 升序。[3] 如果浏览跨后端，先让双方对同一个稳定 ID 比较规则达成一致；不能把旧游标原样迁到另一种总序，也不要把 Redis 有序集合的位置当作产品并列名次。

## 冻结版本要一路带到前端

榜首希望实时更新，长列表却希望继续滑动而不跳人。可以让用户进入界面时拿到当前已发布版本，随后所有续页都读这份不可变数据；用户主动刷新或者点「查看新榜单」时，用新版本首页**替换**旧列表。（若产品选择每页都追最新，则应明确它是实时浏览，不承诺完整遍历。） PostgreSQL 默认 Read Committed 下，即使两条查询位于同一事务中，也可能各看不同快照；普通无状态 HTTP 翻页并不会天然共用一个数据库事务。不可变版本是应用层方案，不要求把一个事务跨用户停留时间长期挂住。[4]

一条续页游标至少绑定榜单、排名范围与显示筛选、排序规则版本、数据版本和最后的分数/ID。服务端验证这些值属于这次浏览，不能默默拿旧边界去查最新数据。快照用多久要考虑榜单刷新频率、玩家浏览时长和保留成本；已回收时返回明确的「须刷新」，不返回可拼接的新版本页。客户端也要把请求和本次列表代次关联：开始新刷新时递增代次。首页响应要匹配当前代次和首页请求，通过后一次性安装新列表与新版本；不用旧版本号拒绝新的首页。只有续页需要同时匹配已安装的版本、当前代次和预期游标，随后才允许追加。即使重新打开的版本号没变，旧请求也不能接进新列表。同一游标的并行请求或重试也应去重，或限制同时只有一个续页在途。

例如版本 17 的第二页尚在路上，版本 18 首页已替换成 X、A。旧的 C、D 到达时应丢弃；只在服务端固定版本、却在客户端直接追加，仍会得到不存在于任何一版的 X、A、C、D。

## 验收不只核对玩家 ID

用 SQLite 3.53.1 逐一执行本篇的查询对照：实时换版的偏移和键集第二页均为 D、B；固定旧版是 C、D。在五人并列试件中，三个页面依次是 A(1)、B(2)；C(2)、D(4)；E(4)。两种错误排名查询都返回正确的第二页 ID；从 C 向前翻则先取 B、A，再还原显示顺序 A、B。另用 Python 模拟响应顺序，拒绝了旧版本的续页与同版本旧代次的续页。SQL 没有测试数据库并发、Redis 或 PostgreSQL，响应模型也没有调用实际前端。

接入前另外要现场测试：版本回收后是否只返回刷新指令，错误页能否被误追加；同分跨页、倒序翻回、同时完成两次续页是否符合协议；以及查询计划在预期榜单规模下的开销。别只断言列表没有重复，还要核对覆盖了哪一版人群、同分是否共享名次。
