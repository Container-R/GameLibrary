# 玩家重连后，怎样防止旧会话覆盖新存档

玩家掉线重连，新会话已接管角色，上一轮会话迟到的一次自动保存却把进度写回了旧数值。旧会话开始计算存档时可能确实有权写；出错的是提交那一刻，存储端仍把这份内容当成现任提交的。对持久化服务来说，要定义的不是「何时通知旧会话停手」，而是**接管提交后，存储从哪一步起拒绝旧会话写入**。

本文约定接管以权威数据库的事务提交为准。它不会撤销之前已成功提交的写入；继任者也不需要先存一次档，保护才生效。

## 先测新会话接管、但尚未保存的间隔

我用 SQLite 3.53.1 的两条连接控制以下顺序。初始存档由 A 持有，写入代次为 17，内容是 `before`。A 先读到自己的写入权，结束这次读取，再继续计算。

| 时点 | 只按存档 ID 写 | 写入同时核对写入者和代次 |
| --- | --- | --- |
| B 提交接管到 18，还没写内容 | B / 18 / before | B / 18 / before |
| A 的旧请求到达 | 命中 1 行，内容变成 late-A | 命中 0 行，仍是 before |
| B 正常保存 | 内容变成 current-B | 内容变成 current-B |

最后一行解释了为什么只查最终快照会漏报：两条路径的存档正文最终相同。回归要在 B 接管后暂缓它的第一次保存，放行旧请求后立即读存档。取消 B 的接管事务作为另一项对照，此时独立连接应仍读到 A / 17。SQLite 的写事务串行化和这里使用的 `BEGIN IMMEDIATE` 也决定了试件中的并发写者会遇到 `SQLITE_BUSY`；锁忙与写入守卫未命中是两种结果。[1]

## 让存档写入本身核对授权

给每轮写入权一个不会重用的编号，称为**写入代次**。服务先按自己的规则确定谁能接管，再在权威事务中比较既有代次、修改写入者并推进代次。下面两段 SQL 用绑定参数；`save_id` 是唯一键。

```sql
UPDATE saves
SET writer = :new_writer, epoch = epoch + 1
WHERE save_id = :id AND epoch = :expected_epoch AND epoch < :max_epoch;
```

代次存为能强制类型的整数，`max_epoch` 固定为该类型可表示的上限（例如 SQLite 有符号 64 位整数的最大值）；耗尽时拒绝接管，绝不回绕或转换为浮点近似。只有命中一行且接管提交成功，才公布新的写入权。随后每份存档携带**这份内容开始计算时所属的代次**。写入者和代次来自可信的服务端授权上下文，不接受客户端自行声称；每条存档写路径都由实际更新检查，而不是只信入口缓存：

```sql
UPDATE saves SET body = :body
WHERE save_id = :id AND writer = :writer AND epoch = :epoch;
```

命中一行只是通过守卫，仍要等待事务提交才算保存成功；零行不写成功回执，它也可能意味着目标已不存在。核对驱动报告的是命中行还是内容实际变化的行：一次内容相同的有效写入不应被判成失权，必要时按后端支持用 `RETURNING`。提交应答丢失或锁忙也不能冒充零行；应按数据库错误和请求回执查证。重试旧请求时不要替它查最新代次再投递，它仍是上一轮计算出来的数据。

只有写入者名字还不够。将接管链再推进为 A17 → B18 → A19，试件里只比名字的 A17 旧写命中一行；比较代次后，A17 命中零行，A19 命中一行。恢复备份或删除重建存档时，也不能让旧请求曾经持有的标记与当前资源再次相等。可用不随存档回档而复用的资源世代参与匹配；代次计数本身不能循环使用。

## 多表事务还要回答：谁与接管争同一把锁

如果写入权和正文在同一条记录上，接管与条件更新争的是同一个目标。装备、进度和成功回执涉及多张表时，让守卫、其余同库写入和回执位于同一事务。未命中就整笔回滚，命中也要等提交。试件故意在守卫之前插入旧回执；条件更新返回零行并回滚后，另一连接看到正文仍是 `before`，也看不到旧回执。合法 B18 的正文和回执则一起出现。实际实现通常先做守卫，避免提前做无谓工作。已经发送给其他服务的消息不会随本库回滚；需要派发时可先在同一事务写待发送记录，提交后再派发，下游仍需去重。

**如果写入权本身也拆到了另一张表，光把普通查询放在同一个事务里还不够。** 以 PostgreSQL 18 的 Read Committed 为例：A 在事务里普通读取权限行，B 可以在 A 写正文之前更新那条权限行并提交；A 接着更新的是另一张表，两者并不争同一行。PostgreSQL 会在等待并发更新后重验同一目标行的条件，但这个规则不会顺带刷新条件中对其他行的普通读取。[2]

同一 PostgreSQL 数据库里，可以让保存事务先按稳定主键对**已存在的权限行**做 `SELECT … FOR UPDATE`，比较实际返回的名字和代次，缺行或不符便拒绝。接管也更新这同一行；保存要一直持锁到正文与回执提交或回滚，不能用自动提交的锁定读。[3] 若 B 先提交，等待中的 A 拿到新代次便拒绝。若 A 先锁住并正常提交，B 的接管会在其后完成，那是合法的接管前保存。锁应该只包数据库提交所需的短步骤，不要持锁等网络或执行长时间的玩法计算。这里是依据 PostgreSQL 文档推导的分表方案，不是以上 SQLite 实验测过的行锁行为。

当授权服务与持久化端分开，问题仍是持久化端何时开始拒收。Chubby 的 sequencer 把锁代次交给实际使用资源的接收端来检查。[4] 如果接收端仅比较「已见过的最大代次」，继任者拿到新代次但存储还没见过它的间隔仍可能接受旧请求。需要在宣布接管前让存储确认新门槛，而不是仅让签发方记住它。

## 在项目里怎样验收

1. 暂停一份已通过早期检查的 A17 请求。接管提交 B18，暂不写新档，再放行 A17。立即从另一连接检查正文和成功回执，不能等下一次正常保存盖掉痕迹。
2. 再由同一个逻辑写入者 A 接管到 19，然后分别投递 A17 和 A19。前者不改正文，后者能提交。把 B 的接管改为回滚再跑一遍，确认未提交的接管不会变成新写入权。
3. 如果权限和正文分表，安排 B 持锁、A 等待，再安排相反顺序各跑一次。观察哪个事务实际取得权限行，以及提交后旧代次、正文和成功回执的状态。若 A 先取得锁但保存失败，要检查其余表也被回滚。记录请求 ID、存档标识、代次和提交结果即可，无须记录存档正文。

代次只能回答这轮有没有写入权。同一轮里两份存档的先后和丢失回包后的去重，仍需分别用内容版本、请求键或持久化回执来处理。
