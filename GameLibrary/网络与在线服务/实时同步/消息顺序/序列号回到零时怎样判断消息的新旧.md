# 序列号回到零时怎样判断消息的新旧

服务器刚处理过编号 65535 的输入，下一条编号却是 0。若接收端用普通整数比较，认为 `0 < 65535` 所以必然是旧消息，就会丢掉本来应该继续处理的输入。反过来，看到一个很大的编号就认作新消息，也可能把回绕前的迟到包重新接进来。

这里说的**回绕**，是计数到字段能够表示的最大值后，从零继续。本文面向设计游戏消息格式的网络与玩法程序员：我们要解决的不是怎样让整数永不溢出，而是怎样让有限编号在约定的历史范围内仍有用。以下数字是教学构造；没有发送网络数据包，也没有验证某个游戏协议。

## 把编号看成一圈，而不是无限长的尺子

先用很小的4位字段，数值只有0到15。假设发送者每次加一，顺序会经过：

`12 → 13 → 14 → 15 → 0 → 1 → 2`

因此，相对于14，1可能是向前走了三步。但字段只保存圆周上的位置，没有记录已经绕了几圈。单看两个数，不能知道这个1来自最近的三步之后，还是更早的另一轮。

RFC 1982为DNS序列号定义了一套有限域运算，并允许其他用途明确引用这套规则。[1] 它不是所有游戏协议必须遵守的规范。下面借用它的比较关系说明一种设计选择；项目仍须规定字段含义、有效历史和异常处理。

设字段有 `b` 位，一圈大小为 `M = 2^b`。令候选编号为 `a`、当前参考为 `r`，用普通数学整数计算：

`d = (a - r) mod M`

其中 `d` 取0到 `M-1`。按这套比较关系：

| 正向距离 | 两个字段的比较结果 |
|---|---|
| `d = 0` | 相等 |
| `0 < d < M/2` | 沿正向距参考不足半圈，可称为“向前” |
| `d = M/2` | 恰好半圈，大小关系未定义 |
| `M/2 < d < M` | 候选在另一侧，可称为“向后” |

4位例中，参考14、候选1，距离是3；参考1、候选14，距离是13。它们的方向相反，解决了普通整数比较跨零失效的问题。参考0、候选8却恰好隔着半圈：选哪边都一样远，不能假装字段自己提供了唯一答案。

本文的教学比较器把半圈情况显式返回为“无法判定”。这是方便调用者处理异常的选择，不是声称RFC要求所有实现必须返回同一个错误码。也不要用“不是向前”合并相等、向后和无法判定：三者需要的处理可能不同。

## 这个比较仍然需要有效历史

即使结果是“向前”，也没有证明消息实际上来自未来。假设参考是14，线上收到1：它既可以是向前3步，也可以是向后13步，甚至来自更早的一整圈。选择正向较短的一侧，依赖的是协议另外建立的历史范围，不是模运算恢复了已经丢失的信息。

所以，不能只说“我们每次都加一，不会跨半圈”。许多小增量累积后，旧副本与当前参考仍可能隔得很远。项目需要限制仍可参与比较的历史跨度，并规定断连、长时间停顿、历史耗尽或切换会话时怎样失效、重建基线。具体期限还取决于编号增长速度、突发量和允许保留的消息，不存在仅由位宽决定的通用超时。

相等也不自动表示同一事件。同一个线上的编号用完一圈后会再次出现；若旧消息仍可能被误认为当前消息，单靠这个字段无法区分。会话身份、实体代次与有效窗口解决的是额外问题，不能用序号比较函数替代。反过来，有了代次，也还要检查本代内的顺序与业务资格。

这与[客户端移动预测中的连续确认](../移动预测/客户端移动预测与服务器纠正.md)是两层设计：那篇解释“已经最终处理到哪条输入”；本文解释把编号装入有限字段后，比较前还缺什么前提。不要把传输层的可靠序号、应用输入编号和服务器模拟时刻当成同一个数。

## 不要把圆周关系当作任意历史的排序器

还有一个容易忽略的后果。仍用4位编号，比较0、6、12：

- 从0到6，正向距离6，小于半圈8。
- 从6到12，正向距离仍是6。
- 从12回到0，正向距离4，也小于8。

于是三次局部比较可以得到一个环：“6向前于0，12向前于6，0又向前于12”。每一对都避开了半圈歧义，合在一起却不是普通数字那样的全局顺序。

因此，不能把这个函数直接交给要求传递性顺序的通用排序算法，再指望它排列任意年代的记录。若确实需要整理一个有限窗口，应先选定共同参考、确认所有记录属于允许的窗口，再按相对这个参考的合法距离处理；窗口之外的记录先按协议处置，而不是偷偷混入排序。一种足够但非唯一的约束，是让参与排序的记录在已知的实际发送历史中，编号跨度严格小于半圈，并先排除不属于这个连续区间的旧记录；不是收到字段后仅凭模距离就能证明这一前提。本段说明的是设计条件，不提供一个能自动恢复真实历史的排序实现。

## ENet的接收窗口还要多检查一层

真实库不会只问“模距离是否小于半圈”。ENet `v1.3.18` 的固定源码就是一个具体例子。[2] 在其可靠接收命令排队路径中，窗口大小为4096，整圈有16个窗口；候选数值小于当前数值时，代码会调整候选窗口所在的圈，再检查窗口范围。后面还存在重复、内存和分片等条件。

只看这一道窗口筛选，可手算两个案例：

| 当前可靠编号 | 候选编号 | 这一道窗口筛选的结果 |
|---:|---:|---|
| 0 | 28672 | 候选在窗口7，达到排除上界，因此被拒绝。虽然28672小于16位半圈32768，也不能据此放行。 |
| 65534 | 1 | 候选窗口经回绕调整后为16，当前窗口15，这一关不拒绝；并不表示已经成功分发。 |

第二例仍须通过后续路径，可靠分发还会检查连续序号和分片是否完整。本文没有调用ENet，也没有证明这两个参数在所有其他状态下都会产生同样的最终结果；表格只核对指定筛选条件。

这正是三个问题的区别：**数学上怎样比较，协议允许接收什么，以及消息何时可以交给应用。** 不能把RFC的半圈关系称为ENet的完整接收规则，也不能把通过窗口检查当作角色操作已经执行。需要了解交付与应用就绪的区别，可接着读[可靠通道与实体就绪](../../../../管理档案/研究记录/source-notes/reliable-channel-entity-readiness.md)。

## 在项目里先决定什么

落到游戏消息格式，可以先从实际风险反推：最旧的有效记录可能比当前参考落后多少？最多允许积压多少未处理输入？重连后旧消息如何退出当前历史？达到比较范围之外时，是拒绝、停止预测还是请求重新同步？这些选择应与输入确认、缓冲容量和恢复流程一致。

随后才选择位宽和比较实现。扩大位宽能推迟回绕，却不会把有限字段变成永久身份。采用现成网络库时，先确认应用到底看到了哪一层序号及其窗口约束，不要绕过库的接收规则自行“修正”迟到包。

本文只给数学整数下的教学关系。移植到C或C++时，整数提升、无符号运算和有符号转换需要按语言与类型另行审查；不要把这里的式子直接当作任意强转写法的正确性证明。序号判断也不验证发送者权限、内容合法性或跨会话防重放。

## 配套模型检查到哪里

[配套的 Python 教学模型与测试](../../../../管理档案/支持资料/序列号回绕/README.md)把上面的模差比较写成可运行函数，并用另一份按RFC条件分支写出的判据核对4位、8位的全部有序对。半圈歧义、环形比较、输入越域及选定的ENet窗口边界也有测试。16位只检查选定情况，没有穷举全部组合。

这些检查针对的是数学模型和简化窗口条件，不是发送数据包、调用原生ENet或测试客户端与服务器互通。模型返回“窗口未拒绝”，不会替项目补上排队、分片、应用就绪和授权检查；通过测试也不能证明真实消息处于约定的历史范围。
