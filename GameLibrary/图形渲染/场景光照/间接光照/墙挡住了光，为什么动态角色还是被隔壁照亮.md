# 墙挡住了光，为什么动态角色还是被隔壁照亮

角色走近一堵薄墙，背光侧的衣服突然染上隔壁房间的橙色。实时阴影看起来没破，静态墙面也正常。先别把所有探针加密：可能是**暗室的探针已经存进了不该有的亮光**，也可能是**两边的探针都对，角色取样时混进了墙另一侧的数据**。前者要追烘焙，后者要追取样。本文用 Unity 6.0 URP 的 Adaptive Probe Volumes（APV，自适应探针体积）说明怎样把两者分开。

## 墙能挡住一条光路，不会自动切断插值

探针在空间位置上烘焙来自不同方向的光照，受光表面按位置、法线等信息读取这些数据。墙对实时光投出的阴影，与动态物体如何读取烘焙漫反射，是两条不同的路径。APV 在局部用规则网格布点；网格单元可能跨墙。如果表面点附近有四个探针在暗室、四个在亮室，“距离近”并不意味着“光照可以共享”。两侧各自烘焙正确，混起来仍会让暗侧亮、亮侧暗。[1]

数据也可能在读取前就错了。比如一个探针的标称位置在薄墙的暗侧邻近处，Virtual Offset（虚拟偏移）为避开几何而移动了它的**烘焙捕获点**，但搜索范围太大，实际捕获点到了亮侧。另一个情形是探针仍无效，Dilation（用邻近有效探针填补无效探针的数据）找得过远，写进了不同光照区域的数据。此时即使运行时只接受本房标签，拿到的记录也不一定代表本房。注意区分标称位置、捕获位置和像素的取样位置：它们会被不同选项改变。[2][3]

## 同样亮了 0.25，为什么不能用同一种修法

取一个归一化的网格单元，墙在 x = 0.5；x = 0 的四角属暗室，x = 1 的四角属亮室。在暗侧点 (0.25, 0.5, 0.5) 用普通三线性权重，把同侧四角的权重分别加起来，暗侧是 0.75，亮侧是 0.25。法线固定，只用一个线性光照量代表每个探针；这里不模拟 APV 的球谐求值、有效性或过滤器。

| 故障 | 暗、亮两侧分别存什么 | 接受哪些探针 | 基线 | 只排除亮侧探针 | 只把暗侧存值修到 0 |
| --- | --- | --- | ---: | ---: | ---: |
| 跨墙插值 | 暗 0，亮 1 | 两侧 | 0.25 | 0 | 0.25 |
| 本房数据偏亮 | 暗 0.25，亮 1 | 只接受暗侧 | 0.25 | 0.25 | 0 |

第一行是 0.75 × 0 + 0.25 × 1；排除亮侧后，只剩的暗侧权重归一化到 1。第二行的权重已经归一为暗侧 1，读出来仍是 0.25。两种症状靠一张截图区分不了。这个试件另测了两种负对照：同房常值 0.10 去掉亮侧后仍为 0.10；若所有候选都被拒绝，模型报告“无样本”，不把它冒充黑色或引擎规定的回退结果。[7]

真实场景可以同时出现两种故障。在同一试件把暗侧存值设为 0.25 且仍接受两侧，基线是 0.75 × 0.25 + 0.25 × 1 = 0.4375。单独排除对面或单独修好暗侧存值，都还剩 0.25；两个都修才归零。在现场，如果排除对面后暗侧还偏亮，就保留这个对照继续查本房探针，不要把改善当成已经找全原因。

## 在 Unity 6.0 URP 先取两份证据

1. **先隔离 APV 的贡献。** 在能影响当前相机的 Volume 中加 Adaptive Probe Volumes Options。固定同一个角色姿态、表面点、材质、相机和曝光，把该 Override 的 Intensity Multiplier 从原值暂改为 0，再恢复，对比同一处。这个值为 0 时不使用 APV 光照数据；它不是所有光源、阴影、反射和自发光的总开关。若异常仍在，先用无反光、无自发光的漫反射测试件和单独的实时灯检查阴影、墙缝及其他分量。消失只说明 APV 参与了异常，不能判断是哪一类。[1][4]
2. **先看“存了什么”，再看“谁参与”。** 打开 Rendering Debugger → Probe Volumes，开启 Display Probes，看墙两侧的探针位置和烘焙光照；把暗侧近墙探针与暗室深处的参考探针对照，按相近法线方向比较，不把探针调试球的任意朝向当成角色像素的值。再用 Debug Probe Sampling 选中问题表面，查看附近探针的贡献权重，记录哪几个在墙另一侧；Rendering Layer Masks 着色可另查层的归属。用同一份烘焙数据先检查这些证据，再决定改捕获还是改取样。[5][6]

例如，暗侧探针显示正确的低亮度，选中肩部却看到亮室探针有明显权重，下一步是做**同份数据下的取样对照**。反过来，如果可疑的暗侧探针本身发橙，肩部主要读的是它们，则先追这些探针烘焙时看到了什么；肉眼看不到越墙候选也不证明真实场景没有间接反弹，特别是门缝、天花板或相邻开口未封闭时。

## 把修法用在发生问题的那一步

| 得到的证据 | 先改什么 | 怎么知道没修偏 |
| --- | --- | --- |
| 本房值正常，隔壁探针有贡献 | 在测试副本中为暗、亮两边配置 APV Rendering Layer Masks；或在适用的几何上，用 Volume 比较小幅 Normal Bias 和 Leak Reduction Mode | 看权重是否离开隔壁，不只看变暗多少；同时看另一个视角、薄件的两面和穿过门洞的角色 |
| 标称暗侧，烘焙捕获点落错位置 | 查看 Virtual Offset 的预览，核对碰撞几何和偏移方向；只改本处的偏移或搜索范围，再重烘 | 捕获点应回到本室，存值恢复；偏移太小也可能让探针留在几何内 |
| 探针无效，被远处有效数据填补 | 在同一烘焙副本只改 Dilation 的搜索半径，或先单独禁用作对照；有证据时局部调整有效性 | 附近仍有同室数据可用才算修好；半径太小可能不再有合适的填补来源，黑斑不是成功 |

设置区域掩码时，先在 URP Asset 启用 Use Rendering Layers，在 Lighting 的 Adaptive Probe Volumes 面板配置 Baking Set 的 Rendering Layer Masks，给相关场景几何与接收光照的 renderer 分配对应层，再 Generate Lighting。一个 Baking Set 最多配置四个 APV 掩码，不是每间房都能独占一个。用调试器核对实际烘焙出的掩码后，可在**同一份已启用掩码的烘焙数据上**对测试接收件切换为“只匹配暗室 APV 掩码的专用层”与“接收件不匹配 Baking Set 中任何 APV 掩码的层”。后者会使用所有有效候选；这与附近恰好没有匹配探针不是同一个条件。若同一层还影响灯光或贴花，先隔离那些影响，否则不能把差异只归因于 APV；可用只有 APV 漫反射的测试材质做这组对照。渲染层不是逐点的墙体可见性；移动角色和横跨门槛的大物体要另验渐变或边界跳变。[1][6]

Normal Bias 移动的是沿表面法线的**运行时查询点**，不是探针捕获点；View Bias 则把查询点向相机推，可能随观察方向改变结果。偏得太远可能越过另一处真正的边界。Performance 与 Quality 应在目标设备按相同画面比较：Unity 文档说明 Performance 尝试用一次 APV 取样避开无效探针，Quality 按情况取样一至三次；该选项不是修复烘焙值，也不能把一份已经污染的数据恢复成正确照明。[4] 如果两边一直共享同一组候选、又没有足够的同侧探针供筛选，才优先考虑局部加密；验收时一起记录烘焙与数据占用，不用全场加密代替定位。

交付前至少沿一条实际通行路线复查：暗室深处、贴墙、经过敞开的门、进入亮室。固定曝光对照，保留贴墙点的探针值与权重，确认暗处不再借到隔壁光，门洞的合理亮度过渡也没有被切断。
