# D3D12临时渲染目标的别名复用

一帧渲染会产生多张中间纹理，其中有些结果在后续结果开始生成之前就不再使用。把这些纹理各自分配到独立存储，管理起来直接，却可能让已经失去用途的空间一直占到帧末。D3D12 的 placed resource 允许多个资源对象放在同一 heap 的重叠区间上，以别名复用（aliasing）安排先后使用。[1]

真正的困难是同时回答三个问题：**旧结果什么时候可以丢弃，这段存储能否容纳新资源，以及 GPU 怎样从旧资源交接到新资源。** 只比较纹理大小，或只把新资源转换到渲染目标状态，都不足以完成这项工作。本文从资源描述和全部使用次序出发，构造一份包括分配、首次激活、初始化、采样和最终回收的完整计划。

读者应已能创建 D3D12 设备、颜色纹理及匹配的 RTV/SRV，并录制、提交 direct 命令列表。本文采用传统 `ResourceBarrier` 和 placed-resource **简单模型**：单适配器、单 direct 队列，一份普通命令列表、一次 `ExecuteCommandLists`；纹理均为单采样二维颜色 RT，只有一个 mip、一个数组层和一个颜色平面，不使用 simultaneous-access、tight-alignment、shared 或 reserved 路径，也不继承重叠资源的旧内容。下文的“阶段”是应用安排的渲染工作，不是 `BeginRenderPass`/`EndRenderPass` API 区间。

## 先找出结果必须保留多久

复用的对象是存储，应用真正需要保护的是存储里的结果。将一张纹理称为“临时纹理”，不会缩短它的内容保留期。后处理、调试预览、复制读回和下一帧的历史采样都可能延长这段时间。

可以先为每个候选填写下表。表中所有使用都应来自实际渲染流程；遗漏一位读者，会直接改变哪些纹理能够重叠放置。

| 输入 | 要记录的内容 | 用于哪项判断 |
|---|---|---|
| 资源描述与视图 | 资源 ID、完整 `D3D12_RESOURCE_DESC`、匹配 RTV/SRV、清理颜色 | 创建何种资源；清理和读取究竟覆盖哪个子资源 |
| 设备分配要求 | 对该描述单独查询得到的 `SizeInBytes`、`Alignment`，以及适配器和驱动身份 | heap 容量、起点对齐和放置区间 |
| 全部读写 | 每次 Clear、draw、采样、copy 等使用，所属队列和提交位置 | 第一次建立内容到最后一次需要内容的范围 |
| 内容需求 | 局部还是完整写入，是否依赖原值，是否跨帧保留 | 初始化方式，以及能否放弃旧结果 |
| 状态与持有者 | 创建时和当前子资源状态；录制、提交期间的对象持有者；最后使用对应的 fence | 正确的 transition，以及 CPU 何时可以回收 |

“最后一次写入”通常早于“最后一次使用”。如果 A 在 P0 写完，P2 还要采样，那么 P0 到 P2 之间，A 即使没有任何写操作，其内容仍必须保留。别名规划应保护这整段时间。

下面用三个资源贯穿全文。阶段顺序和分配数字都是原创假定输入，用来推导布局；数字并非由某组宽高、格式或真实设备查询得到。实际接入时必须用自己的描述、查询结果和使用表替换。

| 资源 | 假定 `SizeInBytes` | 假定 `Alignment` | 建立内容 | 最后需要内容 | 写入要求 |
|---|---:|---:|---|---|---|
| A | 8 MiB | 64 KiB | P0 完整清理，再局部绘制 | P2 像素着色器采样 A | 未绘制位置保持指定背景色 |
| B | 6 MiB | 64 KiB | P3 完整清理，再局部绘制 | P5 像素着色器采样 B | 未绘制位置保持指定背景色 |
| C | 4 MiB | 64 KiB | P1 完整清理，再局部绘制 | P4 像素着色器采样 C | 未绘制位置保持指定背景色 |

这些是 A、B、C 的全部使用。各阶段需要的其他输入和输出均放在不与这三者冲突的存储中，也没有跨帧读取。1 MiB 为 1,048,576 字节，1 KiB 为 1,024 字节。

```text
          P0      P1      P2      P3      P4      P5
A         W===============R
B                                 W===============R
C                 W=======================R

W：清理并写入，开始保留内容；R：最后读取；横线：期间仍需保留。
可复用：A 的最后读取 → 交接 → B 的首次初始化。
不可复用：A 与 C、B 与 C 的内容保留期分别相交。
```

因此可以为 A、B 选择同一起点，而 C 必须另占不重叠区间。这个图表示**需要满足的使用关系**，不是 GPU 的毫秒时间线。D3D12 可以流水化执行命令，应用随后还要用屏障表达依赖，不能仅凭 CPU 已记录完 P2，就认定 GPU 已停止读取 A。[5][12]

若输入缺少末次采样位置、另一队列的使用或历史保留要求，应先保留独立存储，补齐缺失事实，再决定是否复用。

## 用设备给出的大小构造 heap 布局

placed resource 的 heap 是承载资源数据的内存分配，和保存 RTV/SRV 描述的 descriptor heap 不同。创建两个视图不会创造两个独立的图像存储，两个资源对象也可以指向重叠的 heap 区域。[1]

### 资源描述先固定，分配结果再查询

真实实现应保留完整描述，而不只记“1080p RT”。对于本文范围，需要明确：

- `Dimension = TEXTURE2D`；`Width`、`Height` 和 `Format` 取目标效果实际需要的值，格式须满足所选 RTV 和 SRV 的使用要求。
- `DepthOrArraySize = 1`、`MipLevels = 1`、`SampleDesc.Count = 1`、`SampleDesc.Quality = 0`，并选择单颜色平面格式。
- 使用 `D3D12_TEXTURE_LAYOUT_UNKNOWN`，按常规放置路径设置描述的 `Alignment`；本例可用 `0` 请求默认要求。
- `Flags` 包含 `ALLOW_RENDER_TARGET`，且不能用禁止 SRV 的标志与后续采样需求冲突。本文不启用前述特殊资源路径。
- 选择与 RTV 格式兼容的 optimized clear value，并准备实际 Clear 使用的颜色。这个创建参数用于清理优化，**不会代替一次清理操作**。[1]

对每个资源分别调用 `GetResourceAllocationInfo`，参数 `numResourceDescs` 取 1；单 GPU 查询的 `visibleMask` 取 0。若返回的 `SizeInBytes == UINT64_MAX`，这是查询错误，应停止为该描述规划放置。有效返回值属于具体适配器和驱动版本；换设备、驱动或资源描述后，不能把旧结果直接作为新布局的依据。[2]

纹理可能有额外存储开销，不能用宽 × 高 × 每像素字节数推算 `HeapOffset` 所需的资源大小。一次给 API 传入 A、B、C 三个描述，得到的则是它们组合排列的分配要求，还可能受数组次序影响；它不是“这三者共用一个别名槽”的答案。[2] 本文先取得各资源的独立要求，再由应用计算重叠和不重叠区间。

### 逐个检查起点与尾端

设资源 i 的分配大小为 Sᵢ、分配对齐为 Aᵢ，放置起点为 Oᵢ，heap 大小为 H。`CreatePlacedResource` 要求起点是该资源对齐的倍数，并且整个资源落在 heap 内。[1] 可写成：

```text
Oᵢ mod Aᵢ = 0
Oᵢ ≤ H
Sᵢ ≤ H − Oᵢ
```

最后两项有意不直接写成程序里的 `Oᵢ + Sᵢ <= H`，以免无符号加法溢出后误判。下面只是原创的整数检查示意，不是已运行的 SDK 实现：

```cpp
bool Fits(uint64_t offset, uint64_t size,
          uint64_t alignment, uint64_t heapSize) {
    if (size == UINT64_MAX || alignment == 0) return false;
    if (offset % alignment != 0) return false;
    if (offset > heapSize) return false;
    return size <= heapSize - offset;
}
```

若 A、B 共用起点 O，必须分别检查 O 对 A、B 都满足要求。起点为 0 时，两者都能对齐，共用区域至少需要 `max(S_A, S_B)` 的容量。对于一般的非零起点，不能只检查其中一张纹理的对齐。

本文使用 `D3D12_HEAP_TYPE_DEFAULT`，heap flags 选择 `D3D12_HEAP_FLAG_ALLOW_ONLY_RT_DS_TEXTURES`。这个选项由排除 buffer 和非 RT/DS 纹理的标志组合而成，适合本例全部带 `ALLOW_RENDER_TARGET` 的资源，也避免把 heap tier 1 的类别限制扩展成混合资源分配问题。[4] 它不替代资源描述、格式和创建结果的检查。

在这个不含 MSAA 的常规 heap 中，选择 `D3D12_DEFAULT_RESOURCE_PLACEMENT_ALIGNMENT`，即 64 KiB。heap 的对齐与每个资源的放置对齐仍是不同字段，都要满足。官方建议 heap 大小为有效 heap 对齐的倍数，也允许非整倍数大小；本文采用向上取整的大小以方便管理，并非将非整倍数一律判为非法。[3]

将示例数值代入，可以选取以下布局：

| 资源 | `HeapOffset` | 占用区间，左闭右开 | 对齐与容量检查 |
|---|---:|---|---|
| A | 0 | [0, 8 MiB) | 0 满足 64 KiB 对齐；尾端不超过 12 MiB |
| B | 0 | [0, 6 MiB) | 同一起点；6 MiB 不超过共用区间容量 |
| C | 8 MiB | [8 MiB, 12 MiB) | 8 MiB 为 64 KiB 的整数倍；尾端恰好落在 heap 末端 |

A、B 共用的区域预留 8 MiB，C 再使用 4 MiB，H 取 12 MiB。A 结束于 8 MiB，C 从该位置开始，两个左闭右开区间不相交。若按同样输入顺排、完全不别名，A、B、C 共需 18 MiB，且各起点也满足给定对齐。

**12 MiB 和 18 MiB 是这两个布局的覆盖容量。** 它们不是 DXGI 的实测使用量，也不表示帧时或显存预算风险按同样比例下降。此方法只构造一个满足给定输入的简单布局，不求解任意渲染图的最优分配。

接下来才用 H、heap 属性和 flags 创建 heap，并为各描述在表中起点调用 `CreatePlacedResource`。本例三个资源都显式以 `D3D12_RESOURCE_STATE_RENDER_TARGET` 创建。逐项检查 `CreateHeap`、`CreatePlacedResource` 的返回并确认得到对象；任一失败都不能继续向命令列表写入该对象的使用。容量计算成立只是放置的一部分条件，不保证资源创建必然成功。[1][10]

## 为对象分别记录活动状态、用途状态和内容

Microsoft 的简单模型规定：placed resource 创建后处于非活动状态，GPU 不能读写；在 aliasing barrier 的 `pResourceAfter` 指定某个资源，才使它活动，同时使所有与它重叠的资源失活。即使是放在独立区间里的 C，在本文统一采用的简单模型下也要有首次激活步骤。[1]

实现中至少要分开保存三类信息：

| 信息 | 本例怎样改变 | 它不回答什么 |
|---|---|---|
| 活动资源 | `alias(A, B)` 激活 B，使重叠的 A 失活 | B 是否处于可清理的用途状态 |
| 每个子资源的用途状态 | `transition(A, RT, PSR)` 将 A 从渲染目标变为像素着色器可读 | A 是否活动、内容是否已建立 |
| 内容有效性及保留需求 | 完整 Clear 建立确定初值；绘制产生结果；交给重叠资源后不再保留旧结果 | 对象是否已经可以销毁 |

这里 `RT` 表示 `D3D12_RESOURCE_STATE_RENDER_TARGET`，`PSR` 表示 `D3D12_RESOURCE_STATE_PIXEL_SHADER_RESOURCE`。它们是后文的缩写，不是额外的 D3D12 状态。

创建后的 B 具有 RT 初始状态，但仍非活动、没有本轮有效内容。命令序列执行到 `alias(A, B)` 后，B 变为活动，状态仍是它自己的 RT，接着才能以完整 Clear 建立内容。没有必要为这个 B 凭空补一条 RT 到 RT 的 transition。

A 的状态则沿另一条记录变化：创建时 RT，绘制后转换到 PSR，末次采样后被 B 的激活操作置为非活动；这不把 A 的用途状态自动重置为 RT。D3D12 要求 transition 的前后状态与该子资源已有状态相符，aliasing barrier 的职责是重叠资源之间的交接，二者不能互相代替。[5]

首次激活可写作 `alias(nullptr, A)`，其中 `pResourceBefore` 留空，`pResourceAfter` 明确指定 A。后续已知从 A 交给 B 时写 `alias(A, B)`。API 允许 before、after 为空来表达更宽的别名关系，但本文的简单模型用 after 指明要激活的资源。[1][6] 也不需要额外加入 UAV barrier：本例没有 UAV 访问，UAV barrier 不能替代这次 aliasing 或用途转换。[5]

## 从首次清理到末次采样，组织完整命令链

先确定初始化方式。本例三张纹理都只画局部，而且之后会读取未绘制位置，因此选完整 Clear，使所有位置先具有已知背景色。对每张纹理的唯一子资源建立完整 RTV，再使用 `ClearRenderTargetView(rtv, color, 0, nullptr)` 清理整个视图。该调用要求视图引用的子资源处于 RT 状态；由于本例只有一个子资源，且 RTV 覆盖它的全部范围，这一次全视图 Clear 才足以覆盖所需内容。[7]

带 RT 或 DS 标志的别名资源在激活后还需要初始化；使用 aliasing barrier 交接时，初始化要位于该屏障之后。[1] 本例的顺序因此如下。表中 `draw X` 表示绑定 X 的 RTV 并局部绘制，`read X` 表示绑定其 SRV，由像素着色器采样；各自的管线、视图和其他资源绑定按该阶段正常设置。末列描述 GPU 执行相应命令后的语义，不表示 CPU 录制时已经观察到这些结果。

| 阶段 | 在普通 direct 命令列表中依次记录 | 这一段结束时的相关信息 |
|---|---|---|
| P0 | `alias(nullptr, A)`；完整 Clear A；draw A | A 活动、RT，A 内容开始保留 |
| P1 | `alias(nullptr, C)`；完整 Clear C；draw C | C 活动、RT；C 不与 A 重叠，A 仍活动 |
| P2 | `transition(A, RT, PSR)`；read A | A 活动、PSR；这是 A 内容的最后一次需要 |
| P3 | `alias(A, B)`；完整 Clear B；draw B | A 失活；B 活动、RT，B 内容开始保留；C 不受该交接影响 |
| P4 | `transition(C, RT, PSR)`；read C | C 活动、PSR；这是 C 内容的最后一次需要 |
| P5 | `transition(B, RT, PSR)`；read B | B 活动、PSR；这是 B 内容的最后一次需要 |

表中的 `alias`、`transition` 是便于阅读的记法。实际 aliasing barrier 的类型为 `D3D12_RESOURCE_BARRIER_TYPE_ALIASING`，标志取 `NONE`，before/after 字段按表填写；transition 的类型为 `TRANSITION`，同样不使用 split flags，`pResource` 指向表中的对象，`Subresource` 取唯一子资源 0，`StateBefore`、`StateAfter` 取对应的完整枚举值，再交给 `ResourceBarrier`。每记录一次 transition，都同步更新应用对该对象的状态记录。[5][6]

P2 的最后读取与 P3 的 Clear 之间有 `alias(A, B)`，是这次共享存储的关键交接。不能把它挪到 Clear B 之后，因为那会先访问尚未激活的 B；也不能把 Clear B 挪到 A 的最后读取之前，因为 B 会改写 A 仍需读取的存储。CPU 可以连续录制这整份命令列表，无须在 P2 与 P3 之间等待 fence。这里建立的是 GPU 命令之间的关系，CPU 回收的完成条件将在后面单独处理。

这个状态方案不依赖隐式 promotion 或 decay：资源在 direct 队列上以 RT 创建，随后显式转为 PSR，不是从 COMMON 隐式提升到只读状态，也没有 simultaneous-access 标志。在本文路径中，不能把“最后是读状态”当成自动回到 COMMON 的理由。更换资源或队列路径时，应重新核对官方的 promotion/decay 条件，而不是无条件套用这份状态记录。[5]

如果以后还要用 A **生成一份新结果**，且 B 的全部使用已经结束，可以在后续交接处执行 `alias(B, A)`，按 A 仍为 PSR 的记录转换为 RT，再完整 Clear 并绘制。重新激活不恢复初始状态，也不恢复 P0 产生的旧图像。若此时想要的仍是那份旧图像，就不能采用这个重新初始化分支。[1][5][9]

## 根据内容需求选择 Clear、Discard 或 Copy

Clear 是本例的完整实施路径，并非所有别名资源唯一允许的初始化。官方列出的选项还包括 `DiscardResource` 和符合覆盖要求的 Copy。[1]

| 之后怎样使用目标 | 可选择的初始化 | 必须满足的内容条件 |
|---|---|---|
| 局部绘制，未写位置需要确定背景 | 完整子资源 Clear | 清理覆盖所需子资源，随后部分写入保留正确初值 |
| 后续运算会产生全部需要的内容，且不先读旧值 | 完整子资源 Discard 后写入 | Discard 不提供背景色；后续覆盖与读依赖要由应用确认 |
| 目标内容应来自另一份已有图像 | 符合资源和格式约束的完整子资源 Copy | 来源内容有效，源和目标用途状态满足所选 copy API，复制覆盖需要初始化的全部子资源 |

在 direct 列表上，对带 `ALLOW_RENDER_TARGET` 的区域调用 `DiscardResource` 时，被丢弃区域需处于 RT 状态。Discard 表示原内容无需保留，某些情况下还会重新初始化资源元数据，但不会把目标填成指定颜色。[8] 因而本例不能将 Clear 换成 Discard 后仍只绘制一角，再假定其余区域保持背景色。

“画了一个全屏三角形”也不是完整覆盖的全部证明。视口和 scissor、深度或模板测试、着色器中的 discard、颜色写入掩码，以及依赖目标原值的混合，都可能影响哪些值实际产生、哪些值仍会被读取。选择 Discard 时应从真实管线核对：所有将被消费的值在读取之前都已建立，且建立过程本身不依赖被丢弃的内容。若难以保证，完整 Clear 是更直接的内容定义。

Copy 分支同样不意味着 A、B 地址相同就已经完成复制。数据继承另有涉及 heap 属性、资源描述、布局和兼容状态的规则；本文采用的简单模型不使用它。[1][9] 要保留一份结果，最直接的办法是让原存储继续有效，或在交出原存储前，把结果按合法复制流程保存在另一段不冲突的存储中。

## 输入一旦改变，重新决定能否重叠

可以用两种变化检查前面的计划是否仍适用。

**变化一：P3 改为采样 A 并写入 B。** 现在 P3 的操作同时需要 A 的旧结果和 B 的目标存储。即使数学上写成 `B = f(A)`，它们也不能按本文方案重叠放置。

```text
          P0      P1      P2      P3
A         W=======================R
B                                 W======...

P3 同时需要读取 A、写入 B，两个内容保留期在这里相交。
```

在 P3 前激活 B，会使 A 失活；P3 后才交接，又不能先把 B 当活动目标使用。调整这条屏障的位置无法满足两者同时有效。可行的直接方案是让 B 使用独立区间，并保留正常的 A 读取和 B 写入状态转换。另一种方案是改变算法，把必要输入先保存在另一个资源中，但需要重新计算那份资源的保留期和空间成本。

**变化二：下一帧还要读取 A。** A 的内容保留期延长到了 B 使用之后，原先的 A→B 交接不再成立。应取消此次重叠，或提前将所需历史结果保存到独立历史资源，再重新安排原区间。B 用完后重新激活 A，只能重新建立内容，不能从对象仍然存在推得旧图像仍被保留。

C 也是同一个判断：它最后写入在 P1，但 P4 才最后读取。不能在 P2 看见“C 已经画完”，就把其存储交给 B。对于内容保留期相交的资源，独立存储是可实施的基线；它多占空间，但允许结果同时存在，也省去两者之间的别名交接安排。两种路径仍都需要正确的用途状态、内容初始化和对象寿命管理。

## 最后一次 GPU 使用之后，才由 CPU 回收

别名切换使同一块存储能在 GPU 工作内部先后复用；释放资源对象、释放 heap 和重置 command allocator，是另一层寿命问题。计划在 P3 使 A 失活，不表示 CPU 录制完 P3 就可以销毁 A，因为 GPU 可能尚未执行到 P2，已录制的命令也仍然引用 A。

D3D12 graphics command list 的 API 不替调用者持有所传对象的引用；应用必须保证引用对象在提交及执行期间存在。placed resource 自身持有其 heap 引用，但 heap 最后一个引用释放前，仍须确保 GPU 不再读写它。[10][11] 本例采用容易实现的保守策略：从录制开始，由一个批次持有 A、B、C 和 heap，在覆盖整个批次的 GPU 完成点之后统一退役。项目中其他 GPU 使用的对象和描述符存储也要遵守各自寿命要求。

对这份单队列、一次提交的计划，可按下面的正常路径处理：

1. 录制 P0 到 P5，检查命令列表 `Close` 成功。不要将未关闭或包含已知错误的命令列表提交。
2. 保持批次引用，用该 direct 队列调用一次 `ExecuteCommandLists`。它不是返回 HRESULT 的提交确认接口，不能以“CPU 调用返回”推断 GPU 已完成。[13]
3. 在同一队列随后调用 `ID3D12CommandQueue::Signal(fence, retirementValue)`，检查其 HRESULT。该值取自这条队列专用的递增序列，并为 `UINT64_MAX` 保留异常含义，不将其分配为正常退役值。Signal 成功后，把这份批次与 **fence 对象身份及该值** 关联。[12][14]
4. 稍后在 CPU 查询这个 fence。先判断 `GetCompletedValue()` 是否为 `UINT64_MAX`；若是，进入设备移除处理，不能因数值足够大就走正常完成分支。[15]
5. 在设备正常、有效完成值达到 `retirementValue`，并且没有其他在途、尚未提交或未来已安排的使用时，释放本批次的对象引用。若这是 heap 的最后使用者，才能释放最后的 heap 引用。若 allocator 也只服务于该批次，且没有相关命令仍在录制或执行，再按 allocator 的使用约束重置。[10][11]

队列的 Signal 在此前队列工作完成后更新 fence；`ID3D12Fence::Signal` 则是 CPU 立即更新。用后者把值抬高，不能证明 GPU 已完成 P5。也不要让无关队列或 CPU 用同一个 fence 随意写入值，否则“值已达到”不再可靠地代表本文批次完成。[12]

Signal 失败时，保留已提交批次的引用，不把它加入已有可靠完成点的正常退役队列，转交项目的提交或设备错误处理。对于需要立即退出或回收的情况，CPU 可以等待该完成点；对于正常连续渲染，保留待退役批次并在后续查询即可。无需为了 A→B 的每次 GPU 内交接都让 CPU 阻塞。

同样，command list 的 `Reset` 与 command allocator 的 `Reset` 不具有相同限制。前者可以在先前执行仍在进行时用于重新录制；后者回收命令存储之前，必须保证 GPU 不再执行任何关联命令列表。[11] 不应因为“命令列表已经 reset”，就提前回收本批次资源或 allocator 存储。

## 接入时检查真实输入，而不是增加无关屏障

将这份方法用于项目时，先保留一个不重叠的基线，再接入选定的一组别名资源。检查应沿着同一条因果链进行：

- 保存实际资源描述、适配器与驱动身份、单资源 allocation info，以及最终 heap 大小和 offset。先用整数检查排除错位、越界和无效查询结果，再检查真实创建返回。
- 对照渲染阶段的全部使用，确认 A 的末次读取确实在交接之前，没有遗漏预览、复制、另一队列或下一帧消费者。若有重排，重新求内容保留期。
- 检查每个对象的首次激活、逐对象状态记录和初始化覆盖范围。特别检查 B 是否只是“状态正确”而未激活，或将 optimized clear value 当作实际 Clear。
- 在目标设备中启用项目已有的调试层，检查创建、命令列表关闭和提交相关错误；用可辨认的背景色配合局部绘制，比较独立存储与别名路径的目标结果。官方明确指出状态验证是保守且不穷尽的，零诊断不能证明使用表完整或所有依赖正确。[5]
- 单独核对退役队列：Signal 属于哪条队列、绑定哪个 fence、设备移除是否先于正常数值比较处理，以及是否仍有人持有后续使用计划。

这些是目标项目的接入检查，不是本文已经取得的 GPU 观察。本文的数值只作布局推导，小代码只表达整数条件；没有原生资源创建、画面或性能测试结果。是否值得采用别名，还要在代表性负载中测量实际内存使用、初始化工作和同步成本，不能用纸面容量差替代这些结果。

两处范围变化尤其需要重新设计。首先，D3D12 render-pass API 不允许在其区间内加入 aliasing barrier，本例的交接及完整 Clear 都在普通命令列表环境中；接入 `BeginRenderPass` 时，应将交接安排到 render pass 外，并按该 API 重组工作。[16] 其次，官方高级模型允许同一队列两次 `ExecuteCommandLists` 调用边界提供等效别名同步，但一次调用传入两份命令列表不具有相同边界，仍可由驱动合并执行。这也不是跨队列顺序保证，初始化要求仍然存在。[1][13] 本文不通过拆分提交来消除显式屏障，也不由此推断性能改善。

最终得到的应是一份可以从头顺读的计划：描述决定设备分配要求，全部使用决定内容保留期，两者共同决定布局；首次激活和 aliasing barrier 决定哪个重叠资源可用，每个对象自己的 transition 决定用途，初始化建立需要的内容；最后由正确的队列 fence 将 GPU 完成转换成 CPU 可回收的事实。这些条件在同一份计划里相互吻合，临时存储复用才有明确的实施依据。
