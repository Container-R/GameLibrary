# 用 RenderDoc 定位角色变形：一帧能证明什么

角色挥剑时手腕翻了一下。动画师在编辑器里停到附近，看到的姿势却没问题。此时抓一帧可以回答：**这一次绘制吃进了哪些顶点和变换，它们在哪一步开始不对？** 这跟“把这段挥剑动画恢复成可编辑资产”是两件事。本文用自有项目中的角色变形举例，给出一条能把问题交回动画、蒙皮或渲染环节的排查路线。

## 抓对对象：屏幕上一个角色，事件里可能有几份

先让问题能重现，记录角色实例、网格部件、动画采样时刻和镜头。多线程渲染可能画的是更早交给渲染线程的姿态，不能拿“抓帧时编辑器面板显示的时间”直接和顶点对。能改项目时，在姿态提交处加编号，并把编号和角色名放进绘制标记或同时记录到日志；有两个捕获文件时，用这些应用侧标识对齐，不拿各自的 EID 当跨文件帧号。

启动自有项目后抓到出问题的帧，在 RenderDoc 的 **Event Browser** 选一个符合目标用途的 draw。在 **Pipeline State** 核实它写到哪个深度/颜色目标，以及网格、索引范围、实例和绑定的着色器。要查可见角色的形变，就选实际贡献给该视图的通道；不要把相同角色的 shadow draw 当成主视图 draw。捕获一份正常帧，尽量固定视角、LOD、网格部件和渲染通道，再找其中对应的 draw。做不到完全固定时，把变化写下来，别把换模型或换镜头误认为动作变了。[1]

## 从顶点第一次不同的地方往回追

在 **Mesh Viewer** 选对实例，找手腕附近几个易识别的顶点。对照时用索引和相同网格部件确认是同一批点，不只认表格行号。先看 **VS Input**（顶点着色器接收的输入），再看 **VS Output**；如果还有细分、几何等后续阶段，另核对真正交给光栅器的输出。使用 mesh shader 的项目应选它的实际输出，不照搬这条 VS 检查顺序。两份捕获应对照数值及其空间，不能只比预览外观：对常见投影路径，最终位置可能是含 `w` 的齐次裁剪坐标，而预览为显示立体网格会尝试反投影，默认参数可能不准。[2]

| 观察结果 | 接下来查什么 |
| --- | --- |
| 输入位置没变，着色器里读到的当帧关节数据变了 | 在 **Pipeline State** 打开实际绑定的常量或缓冲，按着色器的关节索引和布局核对矩阵。先和动画提交日志比较；日志正确而绑定值错误，再查调色板上传、偏移或缓冲版本。输入位置相同并不说明没有蒙皮。 |
| VS Input 的位置已经变形 | 先查输入绑定、着色器读取位置的方式，并和源网格空间对齐。有些路径把 CPU 蒙皮结果上传，有些先由 compute shader 写出变形缓冲。对后者，从实际读取资源的用法回查捕获内更早的写入，再核对候选 dispatch 的输入、写入字节范围和同步顺序。复用缓冲或异步 compute 时，仅凭 EID 先后不能断定哪个写入供应了这个 draw；如果生产者不在本次捕获内，看初始内容或补抓/补记录，别仅凭输入形状猜生产者。若顶点着色器从存储缓冲自行取点，还要查着色器读取的资源，不只看 VS Input 的顶点属性。[1][3][4] |
| 输入和预期的变形数据正确，但输出位置不对 | 核对着色器是否多乘了模型矩阵、错误套了实例偏移，或用了另一台相机的视图投影矩阵。固定变形输入，只换已确认的模型或相机参数，对一个点手算对比。 |
| 代表顶点在目标几何阶段都符合预期，只有最终图像看起来错 | 给同一姿势做一次无动态模糊、无时间累积的对照；检查问题是否只出现在速度缓冲、遮挡或后处理。这一步不能凭几个顶点就宣布整个几何通道无错。 |

例如，在普通列向量约定中，如果着色器用 `clip = P × V × M × p_pose`，用项目记录的 `p_pose` 和实际绑定的矩阵算出预期 `clip`，再与输出中的齐次坐标比较，而不是用截图里的二维像素反猜关节。若这些矩阵确实已知且组合可逆，逆变换可以还原这条公式中的 `p_pose`。它没把混合后的网格拆回每根骨骼，更没把该帧的姿势拆回多段动画。不同引擎的蒙皮位置可能已在世界空间，核对实际代码后才能决定式子里是否还要乘 `M`。[2]

## 同一姿势甚至可以来自相反方向的动作

做一个可重复的小例子：固定相机和画法，一根长 2 的线段由一个旋转关节驱动。A 每秒增加 120°，B 每秒减少 60°；在 0.50 秒，两条轨迹都是 30°。把每次关节矩阵交给同一个 OpenGL 顶点着色器，用变换反馈读回旋转后的顶点，再读回 128×128 的颜色缓冲。得到：

| 动画采样时间 | A 角度 | B 角度 | 两份颜色缓冲的不同像素数 |
| --- | ---: | ---: | ---: |
| 0.45 秒 | 24° | 33° | 82 |
| 0.50 秒 | 30° | 30° | 0 |
| 0.55 秒 | 36° | 27° | 82 |

0.50 秒两份顶点输出相同，末端都是约 `(1.732051, 1.000000)`，两份颜色缓冲逐字节相同。即使知道这帧完整的关节矩阵，也分不清它是抬上来的还是降下来的。这个对照用 Mesa llvmpipe 执行 OpenGL 着色器和光栅化，不是 RenderDoc 捕获；像素计数只属于这里的分辨率和画法。本例也刻意没给着色器传上一帧的关节数据。如果项目使用蒙皮运动矢量，而捕获里有上帧数据，同一个捕获文件也可能提供两个时刻的线索；那仍不等于完整时间线。

## 如果需要的是动作，而不是这张姿势

先定交付物，再决定去哪找数据：

- **验证这个时刻的画面。** 对同一实例、通道和坐标空间的代表顶点做数值对照。报告“该 draw 的关节缓冲和对应采样不同”或“关节数据正确，位置偏差在该着色阶段输出已可见”，比报告“动画不对”更容易交接。要进一步定位到着色器中的某次矩阵乘法，先在自有调试构建里额外记录或输出该步的输入和结果。
- **重做一段看起来接近的运动。** 对固定镜头下的多个采样做比较，记录实际模拟时间，尤其要覆盖接触、反向和切换。以本例为例，`(36−24)/0.10` 和 `(27−33)/0.10` 得到 A、B 两条轨迹间隔内的平均角速度，方向相反。实际 3D 旋转还要先统一坐标系、匹配局部/全局变换、处理角度跨界；用采样重建出来的是一条满足观测的运动，不是唯一原曲线。RenderDoc 的 `TriggerMultiFrameCapture` 会独立捕获随后呈现的各帧，并分别存档。[5]
- **诊断转场或恢复可编辑的原动作。** 回到动画侧：保存实际采样的片段和时间、过渡/混合权重、IK 目标及权重、以及送给角色控制器和实际应用的根运动。只记录项目确实走到的环节。查源文件时，关键时间、插值和值应从资产或编辑工程读取，不靠顶点反推。有动画资产也不一定有运行时播放逻辑：例如 glTF 的片段定义关键帧和插值，但不决定什么时候播放、切换或循环。[6]

一个实用的交接是，把异常帧与至少一个前后采样的编号、同一 draw 的绑定和局部点值、动画侧对应姿态日志一起留给接手人。若角色在第 120 帧姿势正确，却在第 121 帧反向，从第 120 帧重建一个静态姿势不能验证修复；要看变化方向在哪一级开始错。
