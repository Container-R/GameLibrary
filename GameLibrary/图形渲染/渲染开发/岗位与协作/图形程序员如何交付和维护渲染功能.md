# 图形程序员如何交付和维护渲染功能

新阴影在演示镜头里更柔和，负责它的那一步图形处理器（GPU）运算也变快了。可换到低画质，建筑墙角开始漏光；回到正常玩法，整帧反而更慢。这时，能说这项功能已经做好了吗？

这是一个虚构的功能改版，不是本文测得的故障。它适合说明图形程序的工作：不仅把某种画面算出来，还要让它在项目需要的内容、设备和制作流程中成立。本文面向准备进入图形开发的人，以及需要与他们协作的美术、技术美术和制作人员，不提供完整阴影算法或性能测量教程。

## 先说明希望改变什么，而不是先选算法

“阴影更好”可以指边缘柔和、远处更稳定、接触处更清楚，也可能是让玩家更容易辨认物体与地面的关系。这些目标不必由同一种技术解决，彼此之间还可能有取舍。

图形程序应先与美术和玩法同事选出代表场景，说明哪里不能出现怎样的错误。我们的阴影改版可以先固定一个室外镜头和一处狭窄墙角，讨论远处轮廓、近处接触及移动时的稳定性。这里只提出观察对象，不预定所有游戏通用的误差阈值。

随后才讨论实现需要什么：哪些物体投影、哪些物体接收，能否处理动态物体，需要额外的纹理或计算，低画质如何减少成本。**着色器（shader）**是由图形处理器执行、参与生成画面的程序；它只是功能的一部分。引擎还要准备输入、安排执行、管理资源，内容作者也要能按约定制作资产。

Capcom 的渲染岗位说明同时涉及游戏团队的图形功能需求、发布支持、中央处理器（CPU）与 GPU 的优化以及资产压缩与过滤；Techland 则把自研引擎渲染系统的设计、实现和维护放在一起。[1][2] 这些职责样本说明，图形开发不只等于独立写一段好看的 shader，但不能据此推定各团队的岗位权限相同。

## 让美术能使用，而不必猜实现内部

假设新阴影提供“距离”和“柔和度”两个参数。距离是阴影有效范围、光源到物体的距离，还是屏幕上某种采样范围？柔和度改大后会增加计算，还是只是改变已经算出的结果？作者不该靠逐个尝试才能知道这些含义。

图形程序与技术美术应一起决定可编辑的参数、默认值和允许组合，把不适用情况说明白。例如某项简化只适用于静态物体，就不能只在程序里默默跳过动态角色，然后让美术排查一整天。反过来，也不必把底层所有参数直接暴露给内容作者。

接入时还要确认资源由谁创建、何时可以读取、什么时候释放，以及功能关闭后旧资源怎样处理。渲染过程中的一个 **pass** 可以理解为完成某一步处理的工作阶段；仅仅拥有一张纹理，不说明它已经在本次 pass 需要的时间准备好。

数据也可能“字节能读，意思却不对”。矩阵的存放次序与乘法约定就是常见例子，详见[《CPU与着色器之间的矩阵布局和乘法约定》](../../着色器开发/数据传递/CPU与着色器之间的矩阵布局和乘法约定.md)。岗位协作的重点是把这些约定交给实际产生和消费数据的人，而不是要求所有美术都理解接口内部。

## 能编译、画面正确和成本合适，是三件事

阴影代码能编译，只说明通过了相应语言与接口检查；它可能使用了错误的变换，或者在某些内容上产生漏影。画面看起来符合目标，也不意味着它能满足项目的运行预算。

先在约定场景中检查新旧画面，保持相机、内容、曝光与输出设置一致。再换到声明支持的质量档与边界内容，看看低画质减少了什么、是否仍保留必要信息。若某档不支持这项功能，应提前作出产品选择，而不是看到错误以后才把它排除出承诺。

美术判断画面是否符合意图，程序解释实现和失败原因，测试人员帮助重现不同配置的问题，制作与相关负责人作范围和交付取舍。一个人可以兼任其中几项，但“性能通过”不应自动替代视觉判断，“美术喜欢”也不自动替代平台约束。

Ubisoft Montreal 的一份高级 3D 程序岗位说明，明确提到渲染与整帧诊断、预算、回归和跨内容团队协作。[3] 它是特定高级岗位的责任范围，不意味着每位新人都独自承担预算审批或发布决定。

## 某一步更快，为什么游戏仍可能更慢

回到开头，新阴影的 GPU pass 缩短了，整帧却变慢。下一步不是立刻让美术删模型，而是查清成本去了哪里：CPU 是否增加了准备工作，是否多了一次资源处理，其他渲染阶段是否改变，比较时是否其实换了内容或设置。

CPU 和 GPU 的工作会有执行与等待关系，不能把两个测得的时间简单相加就当作帧时。单个 pass 的变化也不能替代整帧观察。正式测量需要规定设备、构建、场景、相机、分辨率、画质、采集方法和运行条件；采集本身的开销也要考虑。本篇没有规定通用预热次数或声称某工具读数天然准确。

优化还可能交换不同资源：减少一次处理，却多占一些显存；减少绘制准备，却扩大需要处理的区域。纹理文件大小也不能直接代替 GPU 资源成本，相关计算见[纹理 mip 预算](../../../技术美术/环境管线/纹理与材质/计算BC压缩纹理和Mip链的数据量.md)。是否接受这种交换，要回到目标设备和实际场景，而不只挑一个下降的数字。

使用分析工具的价值，是缩小原因范围并让别人能够复查。Capcom 列举 PIX、NsightGraphics 和 RadeonProfiler，Techland 提到 RenderDoc。[1][2] 本文没有运行这些工具；工具名不是分析已经完成的证明，也不是所有团队必须采用的清单。

## 第一次出现时，也要看到正确的画面

反复观察同一处阴影，可能看不到第一次使用时才发生的准备工作。因此，还应分别检查“已经显示过”与“第一次需要显示”的情况，而不是把稳定运行后的流畅直接当作初次体验。

Unreal Engine 5.6 的 PSO 预缓存文档提供了一个具体边界。**PSO（管线状态对象）**描述绘制所需的一组状态；着色器相同，不等于完整状态相同。文档的 shader-only（仅着色器）统计不检查其他状态，full（完整状态）统计才包含接收绘制结果的渲染目标信息。

统计范围之外，还要检查实际显示时机。在文档所述为组件建立渲染侧表示（代理）的流程中，准备不足时可涉及暂不绘制、使用默认材质或阻塞等待等处理，具体可用方式仍取决于组件支持，不能统一套用；而已经预缓存，也不保证首次从驱动缓存取回没有成本。[6] 这说明要分开检查“是否准备到正确组合”“是否及时完成”和“第一次使用是否满足要求”，不是说某种策略能普遍消除卡顿。

对我们的阴影改版，接入人员可以先确认新增绘制阶段及输出目标有没有进入准备范围，再与美术、玩法确定未就绪时允许看到什么。若墙角阴影暂时缺席会改变空间判断，就不能只因少了一次等待便接收；若选择等待，也要检查时间代价。这是本书提出的接收建议，不是已经观察到的玩家影响。需要进一步核对组件、状态与记录时，可选读[PSO 首次显示的检查范围](../../../../管理档案/研究记录/source-notes/pso-precache-first-use-acceptance.md)。本文没有运行 UE 或比较驱动缓存，不能据此给某个项目判定缺失原因。

## 一个真实例子：更省的资源布局也会改变美术结果

Wube 在 2018 年的 Factorio 开发日志中描述过树与阴影的拆分：两者合在一个图像里虽然减少了图像精灵（sprite）的数量，却留下许多空白区域；拆分后，阴影合并方式也发生变化，原来叠得很黑的部分不再那样显示，团队需要重新调整树的美术。[4]

这里有用的不是把某种拆法当作优化秘诀，而是看到技术变化与内容接收连在一起。原素材在旧系统中合适，并不表示新系统里仍然合适。日志还提醒同一优化可能在不同机器上产生不同结果，因此当时提供可切换选项。这是当时的制作进展，不是本文验证的最终上线收益，也不说明今天的版本仍有同样问题。

对我们的阴影改版，如果外观变化要求重新制作内容，就应把这部分工作放进交付范围。不能先宣布程序完成，再把所有后果都视为美术的额外修补；也不能因为有美术调整，就认定技术方案必然不值得采用。

## 维护时，先查原来的假设变了什么

功能交付后，内容扩充、画质档变化、平台或引擎升级，都可能使原来的假设不再成立。保存一个可复现的代表场景、配置和已知限制，比只保留“某版看起来正常”的截图更有用。

Godot 4.3 的反向 Z 迁移是一个具体的历史例子：它改变了深度约定，直接写常量或比较原始深度的效果，与通过相应投影矩阵转换后比较位置的效果，不应一律用同一种修改。[5] 这并不是本篇阴影功能采用 Godot，而是说明维护者要知道参数和输入究竟代表什么。

旧资料中的[深度效果选择例](../../../../管理档案/历史正文/roles/rendering/graphics-programmer.md#维护中的具体选择深度效果究竟比较什么量)保留了前后判断、沿视轴的间隔与实际长度的区别，以及 Godot 4.6 两类渲染器的重建条件。需要处理这种迁移时再读；这些来源分析没有编译 shader 或验证水面效果，不能当作通用修补代码。

准备切换新功能时，还应明确哪些资产或参数需要迁移，出现问题怎样退回，谁会接手维护。回退如果只恢复代码，却无法使用已经改过的内容，就不是一个已建立的恢复办法；没有实际检查过的步骤应保持待验证，而不写成保证。

## 把交付说明写给下一位要处理问题的人

这项阴影工作结束时，最有用的说明可以很短：改进了哪个可见问题，支持哪些内容和质量档，参数怎样使用，在哪些场景与设备检查过，仍有什么限制，以及改动与恢复由谁接手。

若开头那三个观察真的发生，结论应分别说明参考画面的改善、低画质的漏影和整帧成本的问题，而不是压成一句“新阴影更快”。团队据此决定继续修改、缩小范围或暂不启用。图形程序交付的不是一句胜负结论，而是一项能被使用、能解释问题，也能继续维护的功能。
