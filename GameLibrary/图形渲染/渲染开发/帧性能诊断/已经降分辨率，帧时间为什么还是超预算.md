# 已经降分辨率，帧时间为什么还是超预算

要稳定在每秒 60 帧，留给相邻帧推进的间隔约为 16.67 毫秒。重场景掉帧，动态分辨率已经把内部比例压到 70%，画面明显更糊，卡顿却没消失。这时不该继续盲降：先弄清哪些渲染步骤实际上变小了，再看省下的 GPU 时间有没有落在决定帧节奏的那条链路上。

## 哪些步骤真的少画了像素

先区分玩家看到的输出尺寸和场景内部渲染尺寸。假设输出固定 1280×720，主渲染宽高都用 70%，内部就是 896×504，像素数变为原来的 49%。但不必跟着变的步骤可以仍在 1280×720 工作，例如放大后的全屏合成或独立绘制的界面；阴影图、计算工作和场景提交也可能用各自的尺寸或成本尺度。是否如此要看所用管线、功能和实际目标，不是凭步骤名字猜。Unity 的动态分辨率说明也将调整对象描述为选定的渲染目标，不等于把最终窗口一起改小。[1]

我们用 Mesa llvmpipe 的离屏 OpenGL 在两种尺寸合同下画满渲染目标，用单采样的 `GL_SAMPLES_PASSED` 读通过样本数。100% 时主目标与固定输出各 921,600；70% 时主目标降到 451,584，输出仍是 921,600。这个实验只验证覆盖量及目标尺寸，没测 GPU 时间。实机即使覆盖量减半，时间也未必减半：状态设置、几何、缓存、带宽和不跟比例变化的步骤都可能留下开销。[2]

## 时间省在哪里，谁还在挡住下一帧

先用一个理想流水线理解三种结果。假定 CPU 和 GPU 可并行处理不同帧，没有同步等待、锁帧或其它限速，稳定吞吐由较慢阶段决定，不是两项相加。下面是用“GPU 固定时间 + 随像素数缩放的时间”代入的例子；数值不是某个游戏或引擎的基准。

| 100% → 70% 的情形 | CPU（ms） | GPU（ms） | 稳定帧间隔（ms） | 下一步 |
| --- | ---: | ---: | ---: | --- |
| 像素部分决定时间 | 8 → 8 | 22 → 14.35 | 22 → 14.35 | 在画质可接受处留余量，继续查重场景 |
| 换成 CPU 限制吞吐 | 18 → 18 | 22 → 14.35 | 22 → 18 | 查 CPU 的活跃段与等待来源，再决定保留多少像素 |
| 固定 GPU 工作仍重 | 8 → 8 | 22 → 19.40 | 22 → 19.40 | 检查不随内部比例变小的高开销 GPU 工作 |

不要从两档数据反推一个普适的“固定时间”。两点总能凑出一条直线，不能证明每个渲染步骤都照像素数增长；共享内存带宽、缓存命中、绘制条件与频率都可能同时变化。即使 CPU 和 GPU 的总表显示 18 和 14，CPU 那 18 毫秒也可能在等 GPU 或 Present，不能按哪一列较大就指定优化对象。要在剖析时间线上找让后续工作晚开始的那段：主线程是自己忙、等渲染线程、等 GPU 完成，还是受帧率上限约束？如果低比例下 GPU 更早完成但活跃 CPU 段仍让下一帧迟到，再去优化 CPU；如果 CPU 并没卡住 GPU，而固定输出步骤占据显著的关键段，就单独量那个步骤。显存带宽共享的平台还可能同时影响两侧，别把表格当成硬件定律。[3][4]

异步计算也不能把各行毫秒直接相加。例如图形队列占 0–8 ms、计算队列占 4–10 ms，两行相加是 14 ms，但这两段的时间覆盖并集是 10 ms。并集还不等于完整帧间隔：等待、跨队列 fence 和显示提交都可能改变关键链路。在支持的平台上用 PIX Timing Capture 查实际队列重叠、CPU 活动和依赖；GPU Capture 的计时来自重放，可能串行化队列，适合检查选定步骤的开销，不用它替代运行现场的并发时间线。[4]

## 先固定两档，再查动态控制

1. **固定输入。** 用同一平台、同一构建和可重放的镜头/事件段落，固定输出尺寸、画质档、放大方法与帧率策略。先停用自动调比例，分别强制 100% 与 70%，在两档预热后对照同一段内容。记录是否有 VSync 或帧率限制；若目标是找吞吐上限，可在可控环境做一组无锁帧对照，并与实际交付模式分开解释。比较分布而不拿一帧定输赢，例如看中位数与 95 分位，分清持续超预算与偶发峰值。
2. **先验尺寸，再验耗时。** 用抓帧或渲染统计核对附件和实际工作范围：光栅看视口和裁剪，计算看派发和有效区域。附件分配尺寸不变也可能只画了其中一部分；Unity 6000.3 的文档就描述了这种做法。若本来应该缩的步骤实际上没有缩，先修测试。先选清楚要解释的是应用出帧间隔还是显示节奏，两个量分开记录。[1]将主要步骤的耗时、CPU 活跃/等待段、GPU 时间线及最终帧间隔放在一起。若该缩的步骤变小却没省时，先找它还在做什么工作。若节省确实出现但帧间隔未按比例变化，按上节找下一处限制。如果波动或方法切换改变了结果，再加中间一档检查变动，别把两档的差额直接外推到最小比例。
3. **开启动态控制，核对时间归属。** 记录请求的比例、实际执行的比例、计时属于哪个渲染帧以及读数何时到达；无对应尺寸的旧样本不要塞进新一档。合成试件把比例在第 4 帧从 100% 改为 70%，同时让读数晚四帧到：第 4 帧读到的 22 ms 实际上仍来自第 0 帧、100%；第 8 帧才收到第 4 帧、70% 的 14.35 ms。把到达时比例补给旧计时，会把已经有效的降档看成没用。Unity 6000.0 的 FrameTimingManager 文档说明结果延后四帧且不一定有效，并提供同条 FrameTiming 的帧起始时间和宽高比例，应与计时一起记录；示例只是解释错配，不是 Unity 实时执行数据。[3][5]

如果固定低档可以稳定达标，动态打开后却长期达不到，才去查比例的实际生效时刻、历史长度、过滤与上下限。历史很短会受噪声干扰，太长又会拖慢响应；Unreal 5.9 的动态分辨率文档还区分连续超预算后的快速调整和可见到的异步响应，具体策略以实际运行配置为准。[6] 反过来，如果固定低档下还是因为 CPU 或固定 GPU 工作超预算，继续下调画质不会把那个瓶颈一起变小。优先找出挡住下一帧的工作，再保留那些确实换来时间的降档空间。
