# CPU与着色器之间的矩阵布局和乘法约定

主处理器（CPU）算出的变换看起来正确，传给着色器后，模型的位置或朝向却不对。程序检查了缓冲区大小：够用；检查了每个数的类型：也是浮点数。接着有人建议“转置一下试试”，画面似乎好了，但没人能说清为什么。

这种试改容易留下下一次故障。矩阵交接至少包含三个不同问题：**这些数代表什么变换，按什么顺序存进内存，着色器怎样拿它们做乘法。** 本文面向渲染程序和需要检查上传数据的技术美术，用一个可以手算的小矩阵把三者拆开。例子不是某个模型的真实变换，也不是图形处理器（GPU）的运行结果。

## 先把矩阵当作计算规则，而不是一串字节

矩阵可以用来表达缩放、旋转等线性变换。这里先只看三维向量，不涉及透视投影或用四维齐次坐标表达平移。

假设我们希望计算下面的矩阵 M 与向量 v：

```text
        [ 1  2   3 ]          [ 1 ]
M   =   [ 4  5   6 ]    v =   [ 2 ]
        [ 7  8  10 ]          [ 3 ]
```

横着看，第一行是 1、2、3；竖着看，第一列是 1、4、7。现在规定向量写在右边，计算 `M × v`。结果的第一个分量由第一行与向量对应分量相乘后相加：

```text
第一分量：1×1 + 2×2 + 3×3  = 14
第二分量：4×1 + 5×2 + 6×3  = 32
第三分量：7×1 + 8×2 + 10×3 = 53
```

因此，我们想得到的是 `(14, 32, 53)`。到这里还没有决定内存布局，只规定了九个数在矩阵中的位置，以及怎样计算。

向量放在哪一边不是排版习惯。在 GLSL 着色语言中，矩阵右边的向量按列向量参与乘法，左边的向量按行向量参与乘法。[1] 对同一组矩阵元素，换成 `v × M` 一般不会得到原结果。CPU 数学库采用什么约定，应与着色器的表达式一起核对，不能只凭“我们用行向量”决定内存必须按行存。

## 行优先和列优先，回答的是先存哪些数

要把矩阵放进缓冲区，必须把二维排列变成内存中的一维顺序。

**行优先存储**先放第一行，再放第二行、第三行；**列优先存储**则先放第一列，再放后面的列。两种存法都能表达上面同一个 M，前提是读取方知道采用哪一种。

GLSL 的 `row_major` 和 `column_major` 限定符控制矩阵在缓冲区中的布局，不改变变量的代数使用规则。[2] 所以，把声明改成 `row_major`，不会自动将 `M × v` 改成 `v × M`，也不会替项目修正坐标系或变换组合顺序。

还要区分**CPU 数学对象本身的布局**与**上传时写出的布局**。一个库内部按行保存矩阵，不妨碍上传代码逐列取数并写成列优先记录。真正要检查的是交给着色器的那份数据，而不是数学库的名称或结构体注释。若所用上传接口还提供转换选项，也必须核对它实际做了什么，不能假定一次普通缓冲区复制会替你转置。

## 为什么九个浮点数会用到48字节？

继续使用原矩阵，限定为一个 `std140` 布局下的 3×3、32 位浮点矩阵。`std140` 是一种缓冲区布局规则，不是矩阵乘法规则。在本例中，每一行或列记录的起点相隔 16 字节；这个起点间距称为**步长**。三个 32 位浮点数占 12 字节，其余 4 字节是填充，不是第四个矩阵元素。[3]

下面两份记录都正确。括号内的 99 是为了显眼而放入的填充值，不参与矩阵计算：

```text
行优先：1,2,3,(99),   4,5,6,(99),   7,8,10,(99)
列优先：1,4,7,(99),   2,5,8,(99),   3,6,10,(99)
```

每份都有三个 16 字节记录，共 48 字节。若矩阵位于缓冲区开头，成员偏移就是 0；偏移表示从块起点到该成员的距离，步长表示从一行或列记录起点到下一条记录起点的距离。两者不是同一个数。

把第一份交给行优先读取，把第二份交给列优先读取，都能还原 M，得到前面手算的 `(14, 32, 53)`。

现在故意错配：上传第一份，却让着色器按列优先理解。它会把 1、2、3 当成第一列，把 4、5、6 当成第二列，于是还原成：

```text
[ 1  4   7 ]
[ 2  5   8 ]
[ 3  6  10 ]
```

这正是原矩阵的转置，也就是行和列互换。仍然与右侧向量 `(1, 2, 3)` 相乘，结果变成 `(30, 36, 45)`。没有读取越界，没有改变记录大小，填充也没被用到，结果却错了。

这就是为什么只检查“48 字节、步长 16”不够。单位矩阵或其他对称矩阵转置后不变，更容易掩盖这种错误；排查时应选像本例这样不对称、能逐项核算的数据。

48 字节只是这里的矩阵记录大小，不是 GPU 实际分配量，也不是所有接口的绑定范围或动态偏移对齐要求。换成数组、其他维度、其他标量类型或其他布局规则时，必须重新确认。Vulkan 的规范还根据启用特性和存储类别区分对齐要求，不能把这个例子套到所有缓冲区。[3]

## 按数据经过的顺序查，而不是反复试转置

先在纸面上固定想表达的矩阵、输入向量和乘法方向。本例的目标是 M、`(1,2,3)` 与 `M × v`，而不只是“一个 3×3 矩阵”。如果还涉及多个变换的组合，也应另外写清先应用哪个变换；存储限定符不会替你决定这一点。

接着看最终着色器产物中，真正被使用的那个成员。它属于哪个缓冲区、哪个绑定位置？行列数、数值类型、行列存储方向、成员偏移和步长分别是什么？不能因为模块里恰好出现一个步长 16，就认定它属于正在排查的矩阵。不同编译参数或变体也可能需要分别检查。

再按这些信息检查上传字节。以本例为准，先确认每个记录起点，再逐个读回三个数，跳过填充，重新排成纸面矩阵。这样可以判断错误发生在 CPU 数学计算、序列化排列，还是着色器消费方式，而不是靠一次转置同时掩盖多个不一致。

最后才是目标设备上的实际验证：确认绑定到正确资源、范围正确、同步满足要求，并比较实际计算结果与预期。前面的纸面和字节检查不能代替这一步。修改数学库、上传路径、成员排列、数值类型或编译配置后，也应重新核对相关部分，而不是永久相信一次修好的截图。

这是排查建议，不要求为每个简单矩阵都建一套通用工具。重要的是找到错误的那一层；没有证据表明本例中行优先或列优先哪一种更快。

如果矩阵上传和乘法都正确，模型非均匀缩放后法线方向仍可能不对；选读[非均匀缩放后的法线与切线](../../../../管理档案/来源笔记/tangent-handedness-normal-transform.md)，可以用一个手算例理解为什么恢复单位长度还不够。

## 字节没错，也不能提前覆写上一帧的数据

还有一种问题与行列布局无关：CPU 已经准备好新矩阵，GPU 却还在读取同一块存储中的旧矩阵。此时，即使每个偏移和数值都正确，直接覆盖也破坏了读写之间的安排。**轮流选用几块存储，只是在分配位置；确认旧使用结束，才是在安排复用时机。**

用一个未执行的两槽例子说明。假设由同一个 CPU 线程写入并提交，只使用一条 GPU 队列，设备正常；U0、U1 是两个独立、不重叠、可由 CPU 写入的矩阵存储区域。这里特意选用 Vulkan 的 host-coherent 内存，即主机写入不需要另做显式缓存刷新；绑定、范围等其他条件都合法，且各区域的全部旧 GPU 使用都归入对应提交，没有其他读者。

CPU 写好 U0，提交读取它的工作；下一次写 U1，再提交读取 U1 的工作。第三次按帧号取模又选中 U0，却不能因此立即改写它：CPU 走完两轮，不代表 GPU 已经读完第一轮。Vulkan 1.3.296 的规范明确区分提交与完成，提交调用把控制权交回应用时，并不等待队列工作结束。[4]

一种做法是让 U0 的那次提交关联一个 **fence（完成同步对象）**。在这个限定例子中，CPU 成功等待到该次关联的 fence 发出完成信号，并确认它覆盖 U0 的全部旧使用、没有新的使用插入，才继续覆写 U0。[5] fence 不是唯一可用的完成确认方式，但无论采用什么办法，都需要对应到真正会读取这块区域的工作；不能用另一槽的完成或一个从未关联本次工作的初始信号来替代。

这条正常路径还应接完整：**确认旧使用完成 → CPU 普通写入新的 coherent 矩阵数据 → 再提交读取新矩阵的工作。** 主机写入发生在下一次提交之前；规范规定的提交操作提供相关的主机到设备内存域操作。对这里限定的路径，不需要凭空再加一次 flush 或通用屏障。[6] 旧使用的完成与新数据的可见性是两项责任，只是本例选择的内存属性和提交顺序让后者较简单。

如果等待超时或返回错误，就不能沿用这条成功分支。fence 的重置和再次使用也须合法，并保留它当前对应哪次工作的关系；本例不提供失败恢复流程。若改用非 coherent 内存，还须处理主机写入的刷新及 `nonCoherentAtomSize` 所规定的粒度：两个逻辑记录不重叠，并不自动排除它们共用同一同步／刷新粒度。[6]

这里的槽号不是交换链图像索引，提交完成也不是图像已经显示。帧槽与呈现信号量的复用区别，可选读[交换链与呈现队列说明](../../画面呈现/输入延迟/交换链和呈现队列怎样影响输入延迟.md)。例子没有运行 Vulkan、测量等待时间或证明旧矩阵实验已经进入 GPU 执行；它只是把“同步满足要求”落实到一次 CPU 更新的具体前提。

## 旧验证记录证明了什么

旧稿记录过两个只改变布局限定的 GLSL 编译案例。编译产物使用相同的 3×3 浮点逻辑类型，目标成员分别带行优先和列优先标记，偏移均为 0、步长均为 16。旧检查还追踪了该成员被读取、参与矩阵乘向量并写出结果的关系，而不只是查找某个指令名称。

这些是既有离线编译与 CPU 字节解释证据。旧稿另有同一编译库的复跑及有限错误输入检查，但不是不同编译器的全面比较。后续图形接口能力尝试没有成功进入着色器执行，因此本文中的两个数值结果仍不是 GPU 读回。

本次改写只读取旧正文并重新核对规范，没有重跑编译、读取原始执行档案或运行着色器。读者可以手算本文例子；要确认自己的驱动、上传路径和着色器，仍需在自己的目标环境完成集成验证。

需要追查旧工具检查方法时，可选读[编译消费链、启动负例与能力门](https://github.com/Container-R/GameLibrary/blob/1a7bf18b24ba56395892c4c0cdb3b2acecc16985/solutions/rendering/matrix-major-interface-contract.md#3-实际编译证据到哪里为止)和[原C接口及释放范围](https://github.com/Container-R/GameLibrary/blob/1a7bf18b24ba56395892c4c0cdb3b2acecc16985/solutions/rendering/matrix-major-interface-contract.md#5-来源身份与可复现范围)。它们保留当时的失败与限制，不是当前环境认证；本文的矩阵算式不依赖读者先复现这些工具。
