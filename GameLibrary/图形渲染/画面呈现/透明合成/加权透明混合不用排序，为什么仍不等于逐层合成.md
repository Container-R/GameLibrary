# 加权透明混合不用排序，为什么仍不等于逐层合成

两片半透明面相互穿过时，按前后顺序绘制可能让颜色突然切换。改成加权混合后，提交顺序不再决定这个像素的结果，却又可能出现另一种现象：前面的红色像被后面的蓝色稀释了。消除了排序依赖，为什么仍没有得到原来的遮挡？

这篇文章面向渲染程序与参与材质接入的技术美术。我们用两个颜色片段说明 **Weighted Blended Order-Independent Transparency，简称 WBOIT** 保留什么、近似什么，以及接入时哪几份数据不能混用。它不是折射玻璃、全部透明算法或性能测试的教程。

## 改的是合成规则，不是找到了隐藏的正确顺序

普通 source-over 把前景颜色加到剩余背景上。用未预乘颜色 U 和 alpha 表示，盖上一层就是 `U×alpha + 原颜色×(1−alpha)`。交换两层，通常会改变结果；已有[透明网格优化与顺序语义](../../../技术美术/环境管线/模型导入/优化半透明网格时，怎样保留三角形顺序语义.md)展示了这一点。

McGuire 与 Bavoil 的方法不保存完整的逐层覆盖链，而是分别累计颜色贡献、归一化所需的权重和背景保留比例，再统一合成。[1] 所以它不是“照样执行 source-over，只是省掉排序”，而是换成一种可交换的近似规则。下文以排序后的 OVER 作比较基准，也不将它称作所有真实透明现象的物理真值。

为避免把不同问题混在一起，以下只讨论同一线性 RGB 空间、非发光、非折射的片段，以及不透明背景 B。alpha 在0到1之间，使用标量覆盖模型，不表示红、绿、蓝各有不同的透射率。片段集合、着色结果与测试条件固定。

## 一个像素只留下哪些量

第 i 个片段有未预乘颜色 Uᵢ、覆盖值 αᵢ，以及由自身深度和 alpha 等信息算出的权重 wᵢ。权重不能依赖提交先后；对参与贡献的片段，这里要求有限正值。预乘颜色是 Cᵢ=αᵢUᵢ，不能把已预乘的 RGB 再乘一次 alpha。[1] 若要先分清两种表示，可读[预乘透明度与普通透明度的混用问题](../../../技术美术/环境管线/纹理与材质/预乘透明度与普通透明度的混用问题.md)。

把三个累计量分开命名：

```text
A = Σ(Cᵢ × wᵢ)       三个颜色通道的累计值
S = Σ(αᵢ × wᵢ)       归一化的分母，不是最终透明度
R = Π(1 − αᵢ)        背景保留比例，常称 revealage
```

初始 A 为零向量，S=0，R=1。若 S>0，先求平均颜色 M=A/S，再得到：

```text
最终 RGB = M × (1 − R) + B × R
```

没有片段，或本例的片段全部 α=0 时，应直接保留背景，避免0/0。透明层自身的合成 alpha 是1−R；盖到这里的不透明背景后，最终画面 alpha 仍为1。

在理想实数算术中，求和与乘积允许交换次序。因此，只交换这些相同片段的**提交顺序**，不会改变 A、S、R。但移动物体、交换空间深度可能改变 wᵢ，那是改变输入，不是检验同一输入是否与提交顺序无关。实际浮点加法也不满足任意重新分组后逐位相同，本篇不承诺 GPU 像素的位级一致。

## 两个半透明颜色，先用等权重看清损失

设背景为黑色，红面与蓝面的 alpha 都是1/2，权重都为1。等权重是论文公式6退回公式5的合法简化，用于解释，不是生产调参建议。[1]

此时 A=(1/2,0,1/2)，S=1，R=1/4，所以加权结果为 `(3/8,0,3/8)`。与两种空间前后关系比较：

| 合成约定 | 最终 RGB |
|---|---|
| 红在前，按正确前后顺序做 OVER | `(1/2,0,1/4)` |
| 蓝在前，按正确前后顺序做 OVER | `(1/4,0,1/2)` |
| 等权重 WBOIT | `(3/8,0,3/8)` |

三个结果都给黑色背景留下1/4的比例，但透明颜色分配不同。WBOIT 的这个设置只保留了两层的平均贡献，没有保留“红面盖住多少蓝面”与“蓝面盖住多少红面”的区别。把两层都变成预乘颜色也不能补回这一关系，因为预乘解决的是数值表示，不是前后遮挡。

## 给近处更大权重，也只是增加线索

现在红面在前、蓝面在后，alpha 都改为3/4。为了独立手算，给近层权重2、远层权重1。例如相机空间深度为−1、−2时，教学函数 `w=2/|z|` 会得到这两个值；它不是论文或作者推荐的生产参数。

按同一套公式：

```text
A = (3/2, 0, 3/4)
S = 9/4
R = 1/16
M = (2/3, 0, 1/3)
WBOIT = (5/8, 0, 5/16)
```

逐层 OVER 则为 `(3/4,0,3/16)`。近层确实占了更大比例，但蓝色仍比这个 OVER 基准多。两种规则给背景留下的比例依然都是1/16：**背景保留量相同，并不表示每层颜色的可见贡献也相同。**

再看一个更尖锐的边界：若红色前层 alpha=1，蓝色后层 alpha=1/2，仍用2:1权重，并明确把两片都送入透明累积路径，加权结果是 `(4/5,0,1/5)`，OVER 则只剩红色 `(1,0,0)`。如果实际管线把前层划进不透明阶段并写深度，后层可能不再进入同一片段集合，便不能把那次结果当成这个算例的反驳。

这些是本库原创分数例。权重提供了与深度有关的遮挡线索，却没有保存每层前方所有片段逐一遮掉它多少的信息。某一组权重偶然吻合某一对颜色，不意味着对另一组 alpha 仍能吻合。

## 接入时，先把累积与合成分开

作者2015年的实现说明采用三个阶段：先画不透明内容，再累计透明片段，最后把透明层合到原背景。透明阶段保留原深度用于测试，但不写入或清除它。[2] 对应前面的量，可以按下面顺序检查自己的实现：

1. 把颜色累计 A 与分母 S 清零，把 R 清为1。R 若也清零，背景保留量从一开始就错了。
2. 每个通过测试的透明片段，将预乘颜色乘权重后加到 A，将 alpha 乘权重后加到 S；R 乘上 `1−alpha`。不要把权重乘进这个背景保留因子。
3. 片段累计结束后，再用 A/S、R 和原背景合成。检查空输入、零分母及有限精度保护，而不是把 S 当成输出 alpha。

这些步骤是依据公式整理的接入检查，不是可直接复制的完整渲染器。若透明片段写入深度，使后提交片段被先提交片段剔除，输入集合可能随提交顺序变化；此时累计公式的可交换性不能保证整条管线也无关顺序。深度格式、采样方式、缓冲区精度与实际混合状态仍需目标 API 验证。

## 合成阶段的 alpha，有两种配套约定

论文 Listing 3/4 把 R 放进输出 alpha，并配上“源颜色乘1−源alpha，背景乘源alpha”；作者2015年博客则输出1−R，使用相反的两项颜色混合因子。[1][2] 两套都能得到 `M(1−R)+BR`。

危险在于只复制其中一半：输出了 R，却使用后一套因子，就会得到 `MR+B(1−R)`，把前景和背景的保留量调换。排查时先把最终 RGB 展开写一遍，比只问“alpha 是不是0到1”更容易发现问题。这一比较只说明颜色合成约定，不替代中间纹理或目标 alpha 通道的单独设置。

## 权重调节不能用来保证完全遮挡

原论文给出了多种深度／覆盖权重，作者后来的实现说明又提供了不同调参。论文2014年的勘误修正过公式7–10与 Listing 4；引用时应核对修正版。[1] 本篇没有把论文、博客正文和代码里的常数拼成一套参数。

真正接入时，要先确认深度是什么：线性相机空间距离、普通窗口深度或 reversed-Z 并非同一个数。直接照抄对某种深度单调下降的函数，换一种编码后可能把远近偏好反过来。随后检查数值范围、饱和、下溢和精度；分母上的 epsilon 或夹取是实现保护，不是让近似突然变成精确遮挡的证明。[1][2]

对于相近深度、高不透明度且颜色差异明显的层，先看项目是否接受这种颜色混合，再决定是否采用该方法。若需求是严格保留指定的逐层 OVER 结果，就应评估保留层序信息的其他路径，而不是只不断放大近层权重。标量 R 也没有提供彩色透射、折射方向或真实光传输。

## 已复算的是什么，项目还应验证什么

[原创精确分数脚本](../../../../管理档案/实验/加权透明混合/proof_check.py)复算了上述两个主例、透明累积中的不透明前层边界、一个偶然相等例和一组不同 alpha 的例子，并检查交换提交顺序、空输入与全零覆盖。它只计算给定片段，没有运行着色器、绘制图像或测量性能。

接入项目后，可以先固定片段集合与颜色，交换提交顺序，再分别查看 A、S、R 及合成结果；之后才改变空间深度，观察权重是否按预期变化。把“顺序变化是否稳定”“与目标 OVER 相差多少”“有限精度是否可接受”分开记录。它们回答三个不同问题，不应只用一张看起来顺眼的截图代替。

WBOIT 的取舍，是用少量累计量换掉完整层序信息。理解这个取舍以后，才知道应该修正混合状态、调整权重，还是换一种保留更多遮挡信息的方法。
