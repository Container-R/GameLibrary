# SQLite 存档已经提交，为什么只复制数据库文件还会漏掉进度

游戏刚把一件道具的数量 7 保存进数据库，提交返回成功，随后查询也能读到 7。玩家点击“备份存档”，程序把 `save.db` 复制到另一个目录，文件复制没有报错。然而打开备份后，这件道具的记录却不见了。

这个情境不一定说明事务提交失败。接入备份的程序员还需要问：刚才复制的是**数据库的完整内容**，还是恰好叫作 `save.db` 的那一个文件？使用 SQLite 的 WAL 模式时，这两者不能直接画等号。

下文以一张道具表解释这个问题，再沿着取得一致内容、确认复制完成、读回候选这三个环节，说明数据库备份怎样接入游戏存档。Python 的整次连接备份与 C 接口的分步完成、取消会分别讨论。它不提供完整的云存档方案，也不把文件复制成功、数据库能打开或游戏能进主菜单当作恢复完成。

## 一次提交，不一定已经改写主文件

WAL 是预写式日志（Write-Ahead Logging）。在这种模式下，提交可以先记录在 WAL 文件中，而主数据库文件仍保留较早的页面；SQLite 读取数据时会按规则结合两者。**检查点**则负责把 WAL 中的相关内容转回主数据库文件。[1]

因此，假设主文件中已有一张空的 `save_item` 表，随后提交了 `id=1、qty=7`：通过数据库连接查询到这条记录，与主文件单独复制品里没有它，并不矛盾。查询走的是数据库读取路径，文件复制工具却只拿到了指定文件的字节。

这也解释了为什么“文件摘要与原文件完全一样”仍不够。它可以证明主文件复制准确，却不能证明备份已经包含 WAL 中的提交。此时缺的不是更精确的复制函数，而是选择了不完整的复制对象。

SQLite 官方把 WAL 视为数据库持久状态的一部分，警告将它与主文件分离可能丢失已提交事务，甚至造成损坏。[1] 这不是说每次单独复制都会得到空表；具体结果取决于主文件当时已经包含什么。

## 不要把补救办法写成“再复制一个 WAL 文件”

看到遗漏后，很容易给备份脚本增加一步：先复制主文件，再复制旁边的 WAL。问题是，如果数据库仍在活动，两次文件读取未必对应同一个状态。把所需文件名列齐，不能替代取得一致内容的方法；也不要手动删除源 WAL 来让目录看起来只剩一个文件。

同样，不能把“先要求做检查点”当成任何时刻都可复制主文件的通行证。检查点与应用后续写入、其他连接的使用需要一起考虑。本文不设计活动数据库的多文件复制协议，也不建议为了备份而在生产中关闭自动检查点。

对于正在使用的数据库，可以优先考察 SQLite 提供的数据库备份接口，而不是自行拼接活动文件。Online Backup API 在数据库层复制内容，并支持分步工作；Python 的 `Connection.backup` 则把源连接的指定数据库备份到目标连接。[2][3]

## 备份接口成功，与游戏存档完整，仍是两层判断

在 Python 中，`source.backup(destination)` 表达的是从源连接向目标连接备份，而不是把源主文件直接交给文件复制工具。`name` 参数选择连接中的哪一个数据库，默认是 `main`。[3] 接入时应使用单独的候选目标，按接口要求处理连接与错误；不要先覆盖唯一可恢复的旧备份，再检查新副本是否可用。

但接口并不知道“玩家这次保存”在业务上包括哪些内容。假设道具数量已提交，任务完成标志却还留在内存里，那么数据库备份不能替程序补上未提交的任务状态。若程序把两项变化分成不同事务，也需要明确允许备份落在哪个业务阶段。这些是接入方要定义的保存规则，不是 WAL 替游戏决定的事。

如果保存工作拆给多个辅助函数，还要先确认谁负责整次提交。可选读[辅助保存函数已经成功，为什么外层回滚仍会撤销它](../../../../管理档案/支持资料/辅助保存函数已经成功，为什么外层回滚仍会撤销它.md)，区分内层保存点释放与外层事务完成；这不改变本文已经提交成功后再检查备份的前提。

并发写入也不能用一句“在线备份”带过。官方说明，分步备份期间的源修改可能使备份重新开始，频繁重启可能使操作一直无法完成。[2] 因此，应为实际产品设计等待、取消和失败提示，不把开始调用时刻一概当成最终快照时刻，也不承诺任意写入负载下都能及时完成。本文后面的有限观察没有并发写入，不能回答这些调度问题。

如果一个存档还引用数据库外的截图、地图块文件或另一个数据库，本次备份也不自动把它们纳入同一个一致时刻。应先确定恢复需要哪些内容及其对应关系，再设计协调方式；不能把单库接口的成功扩大为整套存档包的成功。

## C 接口的完成和取消，要保留三个不同判断

前面使用的是 Python 的整次 `Connection.backup`。若程序自己调用 SQLite 的 C 备份接口，`sqlite3_backup_step` 返回 `SQLITE_OK` 表示这一步成功，但仍有页面待复制；返回 `SQLITE_DONE` 才表示复制完成。`sqlite3_backup_finish` 负责收尾，不能从名字或它返回的 OK 推断已经备份完。[4]

考虑玩家在分步复制中途按取消的情形。若尚未完成就调用 finish，目标上仍活动的写事务会回滚；即使复制没有完成，只要没有相应的备份错误，finish 仍可返回 OK。[4] 取消后旧内容仍在，与“本次新进度已备份”是两回事。finish 还会释放备份对象，之后不能拿同一个对象继续 step。因此，保留对象以待继续的暂停，与调用 finish 结束这次复制，需要不同的状态处理。

### 完整与取消两支，实际都得到过 finish OK

本库使用官方 SQLite 3.50.4 源码编译 C driver，直接观察了这一区别。[5] 两条分支各使用新的源和目标；开始前关闭创建连接并重新打开，确认源的唯一道具数量为 7，旧目标为 3。源含固定填充数据，数据库实际有 18 页，每次只请求复制 1 页。单线程构建、4096 字节页、DELETE 日志模式，执行期间没有并发写入。

| 接入选择 | 实际 step 结果 | finish 返回值 | finish、关闭连接后，新只读连接查到的目标数量 |
|---|---|---|---|
| 继续至完成 | 共 18 次；前 17 次 OK，末次 DONE，剩余 0 页 | OK（0） | 7 |
| 提前取消 | 仅 1 次，OK，仍剩 17 页 | OK（0） | 3 |

`SQLITE_DONE` 的数值为 101，`SQLITE_OK` 为 0。两次 finish 都返回 0，但只有完整分支先得到 DONE，且目标读回符合新进度。取消分支留下的是原先已提交的数量 3，不是一份“完成了十八分之一”的新存档。这个有限对照直接取得 C finish 的返回值；它与后文 Python/WAL 主文件复制观察使用不同输入和日志模式，不能混算成一次实验。

作者与另一操作者各执行一次，均在同一宿主使用新目录、新编译和相同固定输入。两轮编译与运行返回 0，27 行技术输出逐字一致；第二位操作者事先知道首轮结果，不是盲复现或跨机器验证。精确表结构、唯一行、blob 类型、长度和零字节内容也被检查。固定源码身份、协议、driver、两轮输出及复现要求见[分步完成与取消的有限观察](../../../../管理档案/支持资料/SQLite备份提前收尾/README.md)。它没有测试 BUSY/LOCKED 重试、并发修改、崩溃或断电；原输入使用有旧值的测试目标，也不是覆盖唯一可恢复备份的产品建议。

### 从接口状态到界面反馈

接入时应保存三个独立结果，而不是只保留最后一个返回码：

1. **复制是否到达终点。** 记录 step 是否真正返回 DONE。某一步 OK 或界面进度百分比都不能替代这个完成条件。
2. **收尾是否成功。** 对已成功初始化的备份对象执行对应 finish 并处理结果；finish OK 不能覆盖本次取消状态。若尚未 DONE 就取消，显示“已取消本次备份”，不把候选当作新备份发布。
3. **候选是否包含本次业务内容。** 正常完成复制并收尾后，再独立读回候选，对照这次承诺保存的道具、任务状态及版本。只有前两项通过，仍不能证明未提交的内存数据已进入数据库。

目标连接的生命周期也影响检查顺序。从成功初始化到对应 finish 之间，不能把目标连接传给其他 SQLite API，包括为了刷新界面而查询内容；即使 step 已返回 DONE，也先完成 finish，再读回。[4] 剩余页数和总页数是最近一次 step 更新的记录，不是持续实时查询，源变化后可能暂时过时。[2][4]

真实产品仍需处理初始化、分步复制和收尾错误，并决定等待与取消策略。本节交付完成、收尾和业务接受三个判据，没有提供通用重试循环或安全超时。任何一步失败都应保留原存档和此前可用备份；不要先覆盖唯一可恢复副本，再借一个 OK 掩盖候选尚未通过的检查。

## 怎样确认备份里确实有这次进度

回到数量 7 的例子，检查对象应当是**独立打开的备份目标**，不是仍然打开的源连接。程序可以先完成候选备份并结束目标写入，再通过新的连接读回目标中的道具记录，确认 `id=1` 对应数量 7；若本次保存还承诺某个任务状态或存档版本，也要对照相应预期。

这里的重点不是机械地增加一次查询，而是避免查错对象，以及把“可打开”误认为“有本次进度”。真实接入检查还应经过应用的读取路径，确认存档版本受支持、必要关联可解析。若还需要数据迁移，可继续阅读[迁移函数返回了数据为什么还不能直接保存](迁移函数返回了数据为什么还不能直接保存.md)；那解决的是数据如何被新版接受，不是怎样取得完整备份。

读回失败时，应保留原存档和此前可用备份，把新候选作为失败结果处理，而不是向玩家报告已经备份完成。即使读回成功，也只建立了所检查内容在正常读取下的证据；断电时的持久性、恢复替换过程以及跨设备兼容性，仍需要各自的验证。这些是本文提出的接入检查，不是一套已经运行过的完整游戏恢复流程。

如果源数据库里的数量就已经不符合本次保存意图，备份不能替你修正它；可选读[复用保存语句时，为什么上一件道具的数量会留到下一件](../../../../管理档案/支持资料/复用保存语句时，为什么上一件道具的数量会留到下一件.md)，区分 SQLite C 接口的执行重置与参数重绑，而不是把写入问题归给备份接口。

若数量正确，却少了装备的附加词条，也应先检查源中的关联数据。可选读[保存后装备编号还在，为什么附加词条却没了](../../../../管理档案/支持资料/保存后装备编号还在，为什么附加词条却没了.md)：它用一个原创背包例子说明 `INSERT OR REPLACE` 与冲突时更新的区别，以及启用外键级联时同编号重插为何不能保留从属行。

## WAL 主文件复制与连接备份的有限观察

本库完成了 1 次作者执行与 1 次独立执行，两轮在同一环境、同一夹具和相同条件下分别使用新目录：单线程、一个持续打开的源连接，使用 WAL，先让主文件具有空表，再提交唯一一行 `(1,7)`；提交后源内容保持不变。为让比较条件明确，该观察关闭了自动检查点，并在新提交之前完成空基线检查点。**这是实验控制条件，不是生产配置建议。**

实际记录如下：

| 读取对象 | 查询到的道具行 |
|---|---|
| 提交后的源数据库 | `(1,7)` |
| 仅复制主文件后，独立打开的复制品 | 空表 |
| 经 `Connection.backup` 完成后，关闭并重新打开的目标 | `(1,7)` |

记录还显示：源连接关闭前，主文件摘要一直与空基线相同；新提交后 WAL 非空。运行自报 Python 3.12.14、SQLite 3.53.1，这不是运行库来源认证。它说明该固定条件下两条复制路径取得了不同内容，不证明所有文件复制都会丢数据，也不是并发、崩溃、断电或跨文件恢复试验。

两轮结果均如上表，没有失败重试。独立执行者先读作者结果，再冻结接受条件并进行自己的执行，因此不是盲复现，也不是跨机器验证。输入、两轮原始输出及限制见[主文件复制与连接备份的有限观察](../../../../管理档案/研究记录/experiments/sqlite-wal-main-copy-backup/README.md)。
