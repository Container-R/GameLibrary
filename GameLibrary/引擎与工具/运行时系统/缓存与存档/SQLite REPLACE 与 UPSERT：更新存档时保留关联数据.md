# SQLite REPLACE 与 UPSERT：更新存档时保留关联数据

存档程序只想把背包中装备 41 的耐久从 8 改成 9。保存后装备仍叫 41，耐久也正确，附加词条却消失了。若源数据库已经如此，正确备份只会保留这个错误结果。值得先检查保存语句：`INSERT OR REPLACE` 并不等于“找到同编号记录，只改这几个字段”。

下文用装备与词条之间的外键级联，对照替换和冲突时更新的不同结果。读者需要了解基本 SQL 与父子表关系；本文关注本次写入是否保留既有关联，不把后续备份成功当成保存语义正确。

## 编号相同，不代表没有删除过

SQLite 的 REPLACE 遇到主键或唯一性冲突，会先删除造成冲突的旧行，再继续插入。[1] 因而，判断保存是否符合业务意图，不能只查询父表最后还有没有同一个编号。

以下原创教学结构先按文档作纸面推演，随后另做了同一结构的有限 SQL 观察，结果见文末；没有验证引擎包装器。只讨论普通表、单连接、无其他修改者、无用户定义触发器；除表中列出的约束外无其他约束，推导以所示语句均成功完成为前提：

```sql
CREATE TABLE inventory_item(
  item_id INTEGER PRIMARY KEY,
  durability INTEGER NOT NULL
);
CREATE TABLE item_affix(
  item_id INTEGER NOT NULL REFERENCES inventory_item(item_id) ON DELETE CASCADE,
  affix TEXT NOT NULL
);
```

`inventory_item` 保存装备，`item_affix` 保存属于它的附加词条。初始已保存装备 `(41,8)` 与词条 `(41,'frost')`。外键能力必须未被构建选项省略；当前连接在事务外启用 `PRAGMA foreign_keys=ON`，并查询确认为 1。不能凭默认值推断已经开启，也不能在活动事务里才切换这个设置。[3]

现在执行：

```sql
INSERT OR REPLACE INTO inventory_item(item_id,durability) VALUES(41,9);
```

根据 REPLACE 与 `ON DELETE CASCADE` 的规则推导：旧装备行先被删除，引用它的词条随之级联删除，随后插入装备 `(41,9)`。[1][3] 新插入同一个编号不会重建本例已经删除的词条。因此，“装备 41 仍在、耐久为 9”可以成立，同时“frost 还属于装备 41”已经不成立。这里不是声称整数编号必然变化，而是强调相同编号也掩盖不了删除产生的后果。

## 更新已有装备，要明确冲突时改什么

从相同初始数据重新考虑另一种保存选择，不要把下面语句接在已经删除词条的分支后，当成恢复方法：

```sql
INSERT INTO inventory_item(item_id,durability) VALUES(41,9)
ON CONFLICT(item_id) DO UPDATE SET durability=excluded.durability;
```

这个 UPSERT 指定由 `item_id` 的唯一性冲突转入更新；`excluded.durability` 是本次原想插入的 9。[2] 在上述限定结构中，它只更新旧行的耐久，不删除父行，也不修改父键，所以纸面结果是装备 `(41,9)`、词条 `(41,'frost')` 均保留。这是本例推导，不是保证任意 UPSERT 都没有其他效果。

该语法需要 SQLite 3.24.0 或更新版本；本文只用单个、有明确目标的冲突子句，不依赖 3.35.0 的扩展语法。UPSERT 只处理唯一性冲突，不能当作忽略所有约束失败的开关；`DO UPDATE` 自身违反约束会按 ABORT 终止并回退整条 INSERT。[2] 应检查实际嵌入的 SQLite 版本和最终 SQL，而不只看保存函数或 ORM 方法叫什么。

## 先查关联数据，再决定保存算不算正确

对这个背包，业务意图是“改耐久，保留词条”。接入检查至少应同时核对装备 41 的耐久和它的词条集合，不能只看执行成功或父表行数。若词条已在源中消失，先调查写入路径；若源中关系完整、备份中缺失，再回到[存档备份正文](SQLite%20存档已经提交，为什么只复制数据库文件还会漏掉进度.md)。

不要靠关闭外键来修补保存语义，也不要认为关闭 `recursive_triggers` 就关闭了级联操作。REPLACE 引发的删除是否执行用户定义 DELETE 触发器，受这个开关控制；外键动作不受它控制。[1][3] 本例没有用户定义触发器，接入真实表时若存在触发器，应另外核对其效果，不能直接继承上面的两行结果。

这份说明只帮助选择“替换”还是“更新”的含义，不提供生产迁移、错误恢复或并发协议。已有存档的事务和备份观察没有执行这里的结构；下面是另行执行的观察，不借用那些记录作为本例的证据。

## 同一父行结果，实际读回了不同的词条

2026-11-04，作者与独立执行者各完成一次有限执行：两个分支各自建立新的内存数据库，都从装备 `(41,8)` 和词条 `(41,'frost')` 开始，分别运行上面的 REPLACE 与 UPSERT。每个连接在事务外开启并读回外键为 1，同时将 `recursive_triggers` 关闭并读回为 0；没有用户定义触发器。

两轮中，两条保存语句都正常完成，直接查询父表都得到 `(41,9)`，但 REPLACE 分支查询词条表得到空集，UPSERT 分支仍得到 `(41,'frost')`。因此，仅凭装备编号与耐久正确，无法判断这次保存是否满足“保留词条”的意图。这次观察也没有把 UPSERT 接在已丢失词条的数据库上冒充恢复。
