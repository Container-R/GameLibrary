# 实体句柄什么时候能保存，什么时候需要映射

玩家点了一只箱子，工具把“稍后打开它”的命令存进队列。等命令真正执行时，箱子已经被销毁；更麻烦的是，程序可能已经切换到另一个世界。队列里留下的数字，还能说明玩家当时指的是谁吗？

这类问题不必先从整个 ECS 架构讲起。这里把**实体**理解为游戏中可以关联位置、库存等数据的对象，把**注册表（registry）**理解为管理一组实体及其数据的容器。**实体句柄**是程序用来在这个容器中指认实体的值，不是箱子的名称，也不必是内存地址。

本文面向玩法和工具程序员，沿着这一条延迟开箱命令，区分三件容易混淆的事：句柄在当前注册表中有效、恢复存档时保留句柄，以及把另一个世界的对象导入当前世界。随后用 EnTT v3.13.2 的固定源码说明这些区别。开箱例子是条件推演；其中映射与当前有效性的区别另有同一条件下的有限原生观察。它没有执行箱子业务，也没有验证下文的 `snapshot_loader` 恢复路径、组件引用迁移、版本绕回或网络行为。

## 只记住槽位，会丢掉箱子是哪一次创建的

一种常见的句柄设计，把值分成两部分：**索引**用于找到实体槽位，**版本**用于区分这个槽位的不同使用轮次。这里的版本不是游戏版本或存档格式版本。

假设箱子 A 当前的完整句柄是“索引 7、版本 0”，简写为 `(7,0)`。这个数字只是例子的前提，不表示某个库的下一次创建必定分配索引 7。

A 被销毁后，程序把这个槽位用于新箱子 B，并将版本推进为 1，于是 B 的句柄是 `(7,1)`。如果延迟命令只保存了索引 7，再把它解释成“这个槽位现在的对象”，它就可能打开 B。完整保留 `(7,0)`，才保留了判断“这不是原来那一代”的信息。

因此，延迟命令不能为了节省一个字段就丢掉版本。真正执行前，也要用当前注册表提供的有效性检查确认原句柄仍对应活跃实体。这个检查可以阻止一类误用，但它还没有解决换世界的问题。

## 在另一个注册表里有效，不代表仍是原来的箱子

假设世界甲有箱子 A，句柄是 `(7,0)`；独立的世界乙也有一个 `(7,0)`，但那里代表的是敌人 C。两个世界分别管理自己的实体，这种相同数值并不矛盾。

如果把开箱命令直接交给世界乙，然后问“`(7,0)` 在这里有效吗”，答案可以是有效。检查没有出错：它回答的只是世界乙里面有没有这个活跃实体，根本没有回答“它是不是玩家在世界甲点过的箱子”。

**有效性需要一个所属范围。** 一个不含世界身份的整数，不能单独证明跨世界的对象等价。给数字补上版本，也没有把世界身份补进去。

项目应先决定延迟命令能否跨越这次世界切换。若不能，就随原世界结束而取消；若确实需要跨越，就要有明确的对象对应关系。对应关系也许来自一个持久业务标识，也许来自受控的存档恢复或导入映射。它不必总是 GUID，但必须能解释“为什么现在找到的对象就是命令所指的对象”，而不是因为数值碰巧相同。

## 恢复同一个世界时，保留原句柄可以是正确做法

前面的例子并不意味着“实体句柄绝不能写进存档”。如果保存的是某个世界的配套快照，恢复时有意重建同样的实体标识，那么让箱子和引用它的数据继续使用原句柄，可以正是加载设计的一部分。

关键在于恢复方式的前提。调用方要知道归档保存了哪些实体和组件，读取使用什么格式与类型，以及按什么次序恢复；不能只从存档里取出一个整数，塞进任意已有世界便期待它自动找到原对象。这里的“快照”是成套保存的状态，不是一份只有对象编号的清单。

EnTT v3.13.2 的 `snapshot_loader` 就提供了这个正向例子：它要求目标注册表为空，并在恢复时保留原有标识。[3] 因此，“句柄可以随配套快照保存”和“句柄不是跨任意世界的永久身份”可以同时成立。

不过，源码中的空目标检查是断言。断言是开发时检查前提的一种机制，其启用方式可以由构建配置改变；不能据此承诺所有发布构建都会给非空目标返回一个可处理错误。应用仍须在调用前保证目标符合恢复要求，也不能把这个加载器当作已验证的跨内容版本迁移器。

## 导入已有世界时，先建立对应关系，再交出本地句柄

现在换一种需求：不是恢复世界甲，而是把甲的箱子导入已经运行的世界乙。乙里面的索引 7 可能已经被占用，继续强求原数值反而会混淆双方对象。

此时可以建立“来源对象→本地对象”的映射。比如来源甲的 `(7,0)` 被映射到乙中新建箱子的某个本地句柄。这里不需要预设本地分配结果；重要的是保存这条对应关系，而不是要求两边数字相等。

EnTT 的 `continuous_loader` 面向这种可非空的目标注册表：它维护远端标识与本地标识的对应，不承诺保留相同数值。[3] 这解释了为什么两个看似都在“加载快照”的接口，实际回答的是不同的问题：一个恢复原标识，一个建立对应关系。

映射表本身也有范围。如果来源甲和来源丙各有 `(7,0)`，一个裸整数不足以让应用知道它来自哪一方。使用一个加载器接收哪一个来源、切换来源时是否重建映射、怎样识别已经结束的来源会话，都要由集成约定。不能把连续加载器当成自动区分所有服务器和世界的身份服务。

而且，找到映射后仍要检查本地对象是否还有效。该版本的 `map` 查询会比对完整远端标识，未知映射返回空实体，但返回已有本地句柄时不会再次调用本地 `registry.valid`。例如本地箱子已经被其他逻辑删除，单凭映射非空就应用开箱命令仍然不够。应用还需确认目标存在、确实能被打开，以及这条命令仍然适用于当前情境。

我们用固定版本做了一个只含实体、没有组件的原生观察：目标注册表预先有一个实体，同一个 `continuous_loader` 先载入来源实体，再由加载器之外的逻辑删除映射得到的本地实体，最后重新载入完全相同的内存归档。[4] 每一步都重新查询映射，并用目标注册表检查返回句柄：

| 阶段 | `map` 返回非空句柄 | 返回句柄当前有效 |
|---|---|---|
| 首次载入前 | 否 | 否 |
| 首次载入后 | 是 | 是 |
| 本地实体被外部删除后 | 是 | 否 |
| 相同归档重新载入后 | 是 | 是 |

第三行说明，查询映射不会自动把被删除的实体恢复。第四行的有效对应来自重新载入时的恢复路径，而不是 `map` 查询；这次得到的完整本地句柄已改变，先前保存的旧句柄仍然无效。最初两个新副本在同一环境按相同配置各构建、执行一次，观察一致。之后发现运行目录准备不符合当时规范，修订协议后另用两个新副本重复了这个条件，输出仍一致；新执行不改变旧流程的缺口。四次调用仍是同一条件的重复，不是跨平台或不同操作者的复现，也没有验证“箱子重新出现后是否还应允许开箱”。

## 对象映射完成，不等于对象内部的引用也改好了

假如一个任务组件保存了“要打开的箱子”的实体句柄，导入箱子本身只是第一步。这个组件中的引用究竟保持源值，还是已经转换成本地值，也必须明确。

尤其不能只看接口注释中出现“成员映射”就认定整张对象关系网会自动修复。本文核对的 EnTT v3.13.2 固定实现中，`continuous_loader::get` 的组件读取路径没有调用文件内的私有 `update` 辅助函数。[3] 因而本篇不承诺该调用会自动改写组件中的实体字段或容器，更不承诺识别任意嵌套引用。

如果项目需要迁移这些引用，应为其定义并核查明确的转换步骤，再检查转换结果。暂时没有映射的引用，是拒绝导入、延后解析还是允许为空，也要按数据用途决定。否则箱子虽然已经导入成功，任务仍可能指着来源世界的旧编号。

## EnTT 的版本检查能保证到哪里

在本篇固定的 EnTT 实现中，`registry.valid` 检查的是本注册表实体池中的版本匹配和活跃状态。普通销毁会推进版本，普通创建可回收空闲槽位，因此前面的 `(7,0)` 与 `(7,1)` 能被区分。[1][2] 这里没有使用指定标识的创建提示，也没有使用显式指定销毁版本的重载；这些不同路径不能被默默并入同一个例子。

版本也不是无限增长的承诺。该版本默认配置使用 32 位标识，分配给实体索引与版本的位数分别是 20 和 12；保留版本会被跳过，有限版本空间最终可以绕回。[1] 这是固定源码的边界，不是已测得的复用周期，也不是所有 ECS 的位布局。不要以“带了版本”推导出永远不会重合，更不要把句柄当成无法伪造的权限凭据。

回到最初的开箱命令，可靠的判断顺序是：先确定它属于哪个世界或来源，再确定本次是恢复原身份还是查找映射，最后确认本地目标当前有效且业务上仍允许操作。存档是否能保留句柄，取决于这条恢复链如何建立，而不是取决于它的外形是不是一个整数。
