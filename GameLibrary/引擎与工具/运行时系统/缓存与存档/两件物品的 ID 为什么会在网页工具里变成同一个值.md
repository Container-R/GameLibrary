# 两件物品的 ID 为什么会在网页工具里变成同一个值

策划用网页工具选中一件库存物品，调整它的备注，再把对象 ID 交回后台。后台保存的是精确整数，导出的 JSON 也能正常打开，工具甚至能把数据保存后再读回来。这些条件仍不足以说明：回传的 ID 就是最初选中的那一件。

问题可能发生在“读取数字”这一步，而不是数据库查找时。本文面向接入网页工具的玩法、服务端和工具程序员，沿着“产生 ID→导出 JSON→JavaScript 接收→按 ID 查找”的过程，说明在哪里保留身份，以及怎样检查往返没有丢失区别。库存场景和检查方法是教学推演，不是真实事故，也不代表已经验收了库存服务。

## 两个不同 ID，怎样变成一个 Number

假设后台为两件物品保存了不同的持久业务 ID：

| 物品 | 后台精确 ID |
|---|---|
| A | `9007199254740992` |
| B | `9007199254740993` |

这里不是 EnTT 的默认实体句柄，也不预设某种分布式 ID 生成器。这两个整数都能装进 64 位整数；问题在于接收方是否仍使用能区分它们的表示。

这对数字来自 ECMAScript 规范已有的例子，不是本库发现的新反例。ECMA-262 第 16 版规定 Number 使用 binary64，并明确说明两者会得到同一个 Number 值 `9007199254740992`。该版普通 `JSON.parse` 将 JSON 数字解析为 Number。[1]

因此，如果导出的是以下数字字段，且网页按上述普通路径解析，没有另外保留数字原文，两项 `itemId` 就不再能用 Number 值区分：

```json
[
  {"itemId": 9007199254740992},
  {"itemId": 9007199254740993}
]
```

两行不一定从页面上消失。数组可以仍有两项，名称和备注也可能都在。真正危险的是后续若**只用这个数值指认对象**，便已经缺少区分 A、B 的信息。工具会覆盖某个条目、选中哪一行，还是主动拒绝操作，取决于具体实现；不能仅凭这个例子断言某个产品必然错发物品。

这也不是“JSON 不能保存大整数”。RFC 8259 允许实现限制数值范围和精度，并未要求所有接收器都采用 binary64。[2] 原始 JSON 中的数字字符可以完整；损失发生在本例所选的接收表示。

## 能表示这个整数，不等于能安全区分它

Number 的安全整数范围是绝对值不超过 `9007199254740991`，即 `2^53−1`。这里的“安全”针对不同整数不会因转换而共用同一个 Number 值，而不只是当前值有没有小数部分。[1]

A 的 `9007199254740992` 本身能精确表示，但 B 已会映射到它。因此，只检查“是整数”不够；也不能反过来说，所有超过安全范围的整数都无法精确表示。

项目如果明确把 ID 限制在安全整数范围内，可以把这个限制作为接口合同，并在产生端和接收端检查。本例却允许更大的 64 位 ID，不能靠一次 `Number.isInteger` 检查就放行。更不能在值已舍入后说“这是一个合法的 64 位整数”，便认定它仍是原来那个 ID。

## 最后转成字符串，为什么已经太晚

假如接收端已经把 B 读成 Number `9007199254740992`，此时再做 `String(value)`，转换的是这个现有值，不是 JSON 里原来的数字字符。对它做 `BigInt(value)` 也只会转换现有整数值，不会推断被舍掉的那一位。[1]

这不是否定所有恢复途径。若处理器还持有可靠的原始数字文本，或使用另行约定的无损解析路径，那是不同前提。本例只讨论**仅剩舍入后的 value，再对它转换**；不把结论推广成任何版本、任何 reviver 都无法保留精度。

正确的改动位置应在第一次有损转换之前。例如，后台从精确 ID 直接产生字符串字段：

```json
[
  {"itemId": "9007199254740992"},
  {"itemId": "9007199254740993"}
]
```

引号不是补救已经丢失的数字，而是让接收方从一开始就按文本保存这一标识。网页中的状态、表格选择值、查找键和回传字段也必须遵守同一约定；若其中一层为了方便又转 Number，问题会重新出现。

BigInt 可以参与精确整数处理，但不能把“改成 BigInt”当成完整传输设计。在本文固定规范中，如果序列化流程最终仍遇到 BigInt，且没有 `toJSON` 或 replacer 先将其转换，`JSON.stringify` 会抛出 TypeError。[1] 因此仍要明确传输表示，而不是依赖默认序列化替自己决定。

## 为什么“保存后再读回来相等”仍可能漏检

现在设工具接收 B 后，不修改 ID，直接保存，再次读取。限定对象是普通数据对象，ID 是上述有限 Number，没有修改值的 getter、`toJSON`、replacer 或 reviver。此时默认序列化写出的是现有 Number，后续解析又得到同一值。[1]

这条往返可以稳定，却稳定在错误的起点上：

| 比较的两端 | 本例能说明什么 |
|---|---|
| 第一次解析后的值 ↔ 保存后再次解析的值 | 已丢失区别的值没有继续变化 |
| 后台可信的原始 ID ↔ 工具回传的精确 ID | 才有机会发现 B 已变成 A 的数值 |
| 原始 A、B 两项 ↔ 工具中分别用于查找的标识 | 检查两个源对象是否仍能被分别指认 |

所以，验收基准不能来自第一次可能有损的解析。可以由后台保留可信的原始十进制 ID，逐项核对工具接收、选择及回传的值；对象关联也要保留，不能只比较一批 ID 的总数。

这里要求的是身份值和关联一致，不是整份 JSON 字节完全一致。字段顺序、空白等无关变化不必被误判为身份损坏；但也不能先把两边都转成 Number，再用相等来证明没有损失。

## 把字符串字段约定落实到入口和查找

对于本例，最小可用约定可以是：`itemId` 必须为规范化的十进制整数字符串，符号、前导零、范围及是否允许零由项目明确。它不是任意文本，也不是数量字段。

接收端先检查类型，再检查允许的文本形式和范围。不符合合同的数字字段应明确拒绝，而不是先 `String(value)` 后装作收到了无损 ID。需要数值范围判断时，也不能借助会丢精度的 Number 转换；应选择能精确处理该范围的方式。检查完成后，才将规范化结果用于对应命名空间内的对象查找。

建议接入时至少准备三项检查，下面只是待实施的检查设计，并非已通过的测试：

- **同一个对象保持身份。** 以源端精确 ID 为基准，核对导出、工具选择和回传，不以页面格式化后的显示值充当基准。
- **不同对象保持区别。** 使用上面的 A、B，分别选择和回传，确认没有在中间状态或查找键处合并。只有“两行都显示出来”还不够。
- **错误表示被识别。** 在约定字符串字段的入口提供数值字段，应看到明确拒绝，而不是自动转换后继续提交。

采用字符串会增加字段校验和跨层约定的工作；若现有接口使用数字字段，还需要明确迁移方式，不能静默把混合类型都接受下来。项目也可以选择其他无损表示，但必须对整条链负责，不能只看最终存储类型足够大。

最后，无损 ID 仍不是权限凭据。查到物品后，仍要确认它属于正确的玩家或存档范围、当前存在且允许这次操作。若问题是实体跨世界后的对应关系，应继续阅读[实体句柄什么时候能保存，什么时候需要映射](实体句柄什么时候能保存，什么时候需要映射.md)；本篇补的是在查找之前，输入有没有保留原来的身份值，不继承那篇的 EnTT 原生观察。

## 附：普通 JavaScript 接口的有限观察

在一个自报 `v24.22.1` 的 Node 运行时中，作者两次调用和独立审者另外两次同条件调用，均观察到上面的两个数字文本合成同一 Number，而字符串路径仍保留区别；对已解析 Number 再转 String 或 BigInt 没有找回差别。直接从原始文本得到的两个 BigInt 则不同，默认序列化第二个 BigInt 实际抛出 TypeError。

这些调用只检查固定数字和普通接口，没有运行网页、库存查找、字段拒绝或完整业务往返。四次重复不是四种覆盖，版本自报也不是二进制认证。[复现输入、实际输出和独立审查](../../../../管理档案/研究记录/experiments/json-integer-identity/README.md)单独保留；正文提出的接入检查仍需要在项目自己的工具链中实施。
