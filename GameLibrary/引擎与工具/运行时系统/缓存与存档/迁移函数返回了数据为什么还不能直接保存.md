# 迁移函数返回了数据为什么还不能直接保存

旧存档把角色生命值写在一个字段里，新代码准备把它放进一组新的角色属性。开发者接上迁移函数，调用没有中断，还拿回了一份数据，于是准备把版本号改成新版并保存。

真正需要确认的并不只是“函数有没有返回”，而是：返回的究竟是完成迁移的数据、没有处理的原数据，还是发生错误后保留下来的部分内容？如果把这些情况都当成成功，新版本号就可能比数据本身先走一步。

这个改字段场景是本文的原创设想，不是某款游戏的事故。下面借 Mojang 的 DataFixerUpper 固定源码说明为什么要作这种区分。本文面向负责存档读取、数据转换和版本升级的开发者；不提供完整的嵌套字段迁移实现，也不推断 Minecraft 怎样覆盖存档文件。

## 先知道自己正在解释哪一版数据

序列化，是把运行数据转换成可保存的形式。格式升级要解决的是：以前保存的结构，怎样按照新的结构和含义使用。它不同于加载后重新计算一个缓存。关于后者，可以另读[Factorio缓存失效与读档后的重算](Factorio缓存失效与读档后的重算.md)；重新算对派生值，并不能自动把旧磁盘字段转换成新版格式。

DataFixerUpper 的 README 将两件事分开：**Schema** 描述系统关心的类型及其关系，**DataFix** 描述类型之间的重写规则；构建器把已登记的 schema 和规则组织起来。[1] 可以把它理解为：不仅要知道数据放在哪个字段，还要知道这一版的字段应该怎样解释，以及下一步怎样改写。

库的 `update` 接口由调用者提供数据类型、输入数据、源版本和目标版本。[2] 这些参数不是由函数替应用从文件中鉴定出来的。因此，调用者要先确定文件属于哪个格式体系、版本号是否可用、这一版是否在应用支持范围内。不能因为未来版本读起来不顺，就把它标成一个较老版本，强迫旧规则处理它。

本文引用的是固定库提交，不是 Minecraft 的完整存档格式，也不是当前游戏版本的兼容性清单。一个版本数字只有放进应用约定的版本体系，才有意义。

## 第一种返回：根本没有进入升级

在本文固定的 DataFixerUpper 实现里，`update` 只有在**源版本小于目标版本**时才进入转换；否则直接返回输入。[2]

假设应用希望得到第2版结构，却传入源版本9、目标版本2。按这个分支，函数会原样返回数据。这个事实既不表示它已完成降级，也不表示第2版代码能理解第9版格式。若应用只检查“得到了对象”，接着把版本号写成2，就把未处理的数据重新贴了标签。

源版本等于目标版本也会直接返回。对于应用而言，这可能本来就不需要升级，但“不需要升级”和“已经验证内容完整”仍是两件事。版本号相等，不能代替对实际字段的检查。

反过来，也不能要求库里必须登记每一个整数版本才算正确。该实现会按请求版本选择相应的已登记 schema，而不只是要求版本键完全相等。[2] 正因如此，应用支持哪些源版本，应是明确的接收政策，不能靠“库没有报未知版本”来倒推。

## 第二种返回：选出的规则没有需要执行的重写

进入升级分支后，库会选择类型和规则，调用类型的 `readAndWrite`。这个方法有一个容易忽略的分支：若重写视图是 `nop`，也就是不做改变，它直接把输入作为成功结果返回，不继续执行后面的解码与写出。[3]

这不必然是错误。某个类型在这次版本跨越中可能确实没有变化。但它说明，不能仅凭调用经过了升级入口，就断言所有嵌套字段都按新版要求检查过。

回到角色属性例子：若团队打算移动生命值字段，需要确认实际登记的类型和规则确实覆盖这个变化。只登记了一个新版本、拿到一份不变数据，不能证明字段已经移动。这里没有公开一个可以直接照抄的完整迁移方案；应把“这次应当改变什么”作为应用自己的明确预期。

## 第三种返回：有错误，但仍有一份部分结果

DataFixerUpper 的这一层返回的是 `Dynamic`，即封装数据的对象，而不是一个供调用者直接判断的完整成功标志。其内部读写得到 `DataResult` 后，会取完整结果或部分结果；对于 `DataResult` 表示的错误，会调用日志报告；只有拿不到完整值或部分值时，才使用原输入值。[2][4]

因此，不能把所有错误说成“静默返回旧数据”。可能返回部分结果，也可能退回原值；某些查找或转换路径还可能抛异常。[6]反过来，没有异常也不够证明完整迁移成功。

官方序列化测试里有一个很小的例子，可以帮助理解“部分结果看起来仍像合法数据”。测试读取嵌套的字符串到整数映射，其中一组内容相当于：

```text
foo: 1
bar: "garbage"
baz: 3
```

测试选择允许部分结果的读取方式，期望留下 `foo: 1` 和 `baz: 3`，不保留那个不能读作整数的字符串项；外层的其他有效映射仍存在。[5]

得到的结果仍然是一份整齐的映射。只检查“不是空对象”或“可以继续编码”，就看不出它是否缺少应用必须保留的数据。不过，这里说的是**官方序列化测试的预期**，不是本地运行结果，也不是某个 DataFix 迁移导致游戏物品丢失的观察。它说明部分结果这个概念的具体含义，不能代替实际迁移规则的检查。

## 将“转换候选”和“接受新版存档”分成两步

对最初的角色属性修改，更可靠的思路不是围绕一个返回值猜测成功，而是先说明应用接受什么。

第一步是确定允许进入迁移的输入。已知旧版可以走对应转换；已经是目标版的数据可以走目标结构的检查；未支持的未来版则应按产品约定处理，例如停止载入并给出说明，而不是默默换成旧版本号。如何提示和保留用户数据属于应用选择，这里不替所有产品制定相同政策。

第二步是对转换候选建立具体预期。生命值应从哪个位置进入哪个位置，数值含义是否改变，哪些其他属性应保持，缺少必要数据时能否接受，都应该能说清楚。如果新版结构要求某项必须存在，就不能因为部分结果仍能解析，便把缺项当成完成。

目标结构解析可以帮助发现类型或必需字段问题，但它也不是全部答案。例如，生命值被错误地改成另一个仍然合法的整数，类型检查可能看不出来。还需要与这次迁移有关的业务约束和内容保留预期。反过来，某次升级本来就要移除废弃字段，也不应该用“所有字段必须原封不动”阻止合法转换。

最后才是决定是否接受为新版并保存。**版本标记应该描述已被应用接受的数据，而不是把一次调用尝试变成成功事实。** 本文不提供磁盘替换的完整实现，也没有执行任何文件写入；这里只讨论作出保存决定前，程序还欠缺哪些判断。

这也不是建议解析日志来补造一个成功标志。日志能帮助诊断，但本接口的返回形态不会因为团队约定了某个日志字符串，就变成可靠的迁移结果协议。具体应用怎样取得所需错误信息、调用严格检查或封装转换，仍需要单独设计和验证。

## 检查时，比较预期变化，不只比较能否载入

团队可以围绕同一个字段修改，准备少量有明确预期的候选输入：已知旧版、已经是目标版、未支持的未来版，以及必要字段损坏的旧版。它们不应该全部得到同一种“调用成功”的判断。

对已知旧版，应能逐项说明新字段的位置和内容，以及应保持的其他数据。对目标版，应确认内容符合接收规则，而不是重复不必要的修改。对未来版，应检查它没有被误贴旧标签。对损坏输入，应知道应用是拒绝、请求修复，还是按照明确政策接受有限恢复，而不是由偶然的部分结果决定。

这些是本文提出的检查思路，尚未实现或运行。现有官方测试主要展示序列化与往返行为，本文没有找到并复现一份完整的嵌套存档升级示例。因此，不能把上述设想说成已验证的 DataFixerUpper 集成方案。

这个来源案例能支持的结论很具体：迁移调用返回数据，只说明得到了一份返回值；是否真正执行了所需变化、是否保留了必要内容、是否能标成目标版本，是另外需要回答的问题。先把这些问题分开，才能避免用一个“有数据”判断替代整次升级的接受条件。
