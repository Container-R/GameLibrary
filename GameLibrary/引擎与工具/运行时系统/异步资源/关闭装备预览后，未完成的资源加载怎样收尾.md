# 关闭装备预览后，未完成的资源加载怎样收尾

玩家点开一把剑的预览，模型还在加载，又切到一张弓。弓先显示出来，随后剑的加载回调才到达。如果回调只做“加载成功就显示”，画面会跳回玩家已经放弃的剑。另一种修法也有问题：关窗时把所有记录清空，迟到结果虽然不再显示，却可能没人负责释放它。

这里有两件不能混为一谈的事：**玩家不再需要这次结果，与加载工作已经停止，不是同一个状态。** 前者由界面和玩法决定；后者取决于资源系统支持什么。即使底层不能取消，应用仍需拒绝旧结果，并把自己持有的资源引用收尾。

本文面向接入异步资源的界面与玩法程序。以下剑、弓与关闭重开的过程是原创设计示意，不是实测故障。具体 API 以 Unity Addressables 1.21.21 文档为例；提出的收尾安排尚未实现或在 Unity 中运行，不是一份可直接复制的加载器。

## 先把三种“取消”分开

关掉预览窗口，通常意味着“不再把这次结果交给玩家”。取消等待，只意味着某段等待流程不再继续。停止底层加载，则要求资源系统确实中止相应工作。不能因为一个按钮叫“取消”，就默认三件事同时发生。

Addressables 的异步操作手册明确说明，`LoadAssetsAsync` 启动后不能取消。完成前释放句柄会减少引用，并在加载完成时自动释放；这不是下载当场停止的保证。[1] 因此，给请求换一个编号、销毁窗口或停止等待，都不能据此宣布底层工作已经结束。

**句柄**是访问一次异步操作及其结果的凭证，也参与释放责任。它不是“玩家仍想看这件装备”的证明。一个有效的加载结果可能已经过时；反过来，玩家仍想看弓，也不表示弓已经加载成功。

## 每次打开都要有自己的请求身份

不要只用装备地址判断结果是否还有效。玩家可以依次打开剑、弓，再打开同一把剑。第一次剑请求与第三次请求虽然地址相同，却不一定属于同一个窗口状态；中间可能换过皮肤、预览参数或界面实例。

一种便于检查的应用设计，是为每次预览建立独立请求记录。它至少知道：这次请求是否仍被当前窗口接受、谁负责加载句柄、结果是否已交给实际使用者，以及本方引用是否已经释放。请求身份在仍有迟到结果时不能被复用。

切换装备或关闭窗口时，撤回旧请求的展示资格，不把旧记录直接丢掉。记录需要存活到它的责任结束；否则“忽略回调”可能只是把需要释放的引用一起忘了。这项规则是本文提出的应用安排，不是 Addressables 自动提供的界面状态管理。

## 选一种收尾路径，不要把两种释放办法叠加

为了便于追踪，下面只讨论一种策略：**不提前释放，由能够等到完成的资源管理方一直持有本方引用，再统一处理结果。** 它牺牲了尽早放弃引用的机会，但避免了“先释放，回调里又继续读同一句柄”的混乱。

讨论从成功取得操作句柄开始，不包括调用尚未建立操作就抛出异常的路径。这个管理方不能就是随窗口销毁而失去所有状态的临时对象。关闭窗口后，仍要有人保存请求记录并接收完成结果。项目必须明确这段生命周期；仅把代码从一个函数搬到另一个函数，并不会自动让负责人活得更久。

在这项设计中，完成后分成两条路径：

- 请求仍属于当前预览，整组加载成功，而且结果满足预览要求，才交给显示方。引用继续保留，直到显示方不再使用相关资源。
- 请求已过时，或者加载/接纳失败，就不显示，按本方仍持有的引用执行一次收尾。

“显示成功”不是立刻释放的理由。官方要求在使用加载结果期间保留句柄。[1] 若显示步骤只完成了一半就报错，应先撤下已经建立的使用关系，再结束相应持有；不能留下仍使用资源的预览，却按“失败”把引用先放掉。

也不要让关窗处理、完成回调和显示对象销毁各自无条件释放同一份引用。可以由一个所有者始终保留释放责任，显示方仅通知它“已不再使用”；如果确实要交接责任，交接前后谁能释放必须唯一明确。复制句柄变量本身不能作为多获得了一份拥有权的依据。

完成处理本身也只能结清同一记录一次。可以只选一个完成入口，或让入口先检查该记录是否已经处理；不能看见 `IsDone` 就收尾一次，随后又在 `Completed` 通知中无条件再收尾。该版本文档规定，对已经完成的操作订阅 `Completed`，回调会延至当前帧的 `LateUpdate`，并非订阅时必定立即调用。[5]

## 一组资产加载失败，不代表结果列表必定为空

假设完整装备预览需要一组资源，项目决定缺任何一项都不显示。这里明确选择 `LoadAssetsAsync` 的 `IList<IResourceLocation>, Action<TObject>, bool` 重载，并将 `releaseDependenciesOnFailure` 设为 `false`。这是为了限定讨论，不是在推荐所有项目都用这个选项。

该重载的参数说明指出：某项失败时，整体状态仍是 `Failed`，结果列表却可以保留成功项，并在失败位置留下空值；调用方仍需释放操作。[2][3] 因而，不能只看列表非空，也不能因为某个资源已经到了，就宣布整件装备可以显示。

本例不在逐资源回调中提前创建预览，而是在整次操作完成后检查整体结果。逐资源回调与整次操作的完成通知不是同一件事。[1] 若项目确实允许渐进显示，就还需要设计部分成功、后续失败和撤下已显示部分的规则，不能直接沿用这里“整组通过才接纳”的安排。

这个 `false` 条件不能丢掉。参数说明同时规定，设为 `true` 时，失败会释放已加载资源和操作，不要求调用方再释放失败句柄。[2][3] 同页通用 Remarks 没有保留这一区分，因此不要从一句“失败时释放”拼出适用于所有重载和参数的统一代码。本文采用具体参数说明与多资产加载手册相互印证的范围，没有用运行结果消除所有边缘时序疑问。

## 把迟到的剑沿着责任走完

下面是假定完成通知已被资源管理方接收的推演，不是 Unity 事件日志：

| 发生的事 | 展示资格 | 本方引用怎样处理 |
|---|---|---|
| 打开剑预览，请求 A 开始 | A 当前有效 | 管理方持有 A，等待完成 |
| 改看弓，请求 B 开始 | A 失效，B 当前有效 | 不丢弃 A 的待收尾记录；B 单独记录 |
| B 整组成功并被接纳 | 只显示 B | 保留 B 的持有，支持实际使用 |
| A 随后成功 | A 仍然过时 | 不改画面，结束 A 的本方持有 |
| 关闭已显示的 B | B 不再接受展示 | 显示方停止使用后，结束 B 的持有 |

如果 A 先失败，按本例 `false` 的政策，它仍有收尾责任；不是因为失败就忘掉它。过时失败也不能清空 B 的预览，或把 A 的错误写进 B 的界面。如果 B 失败而 A 随后成功，也不能擅自把 A 当作替代结果，除非产品明确选择了这样的回退并重新确认玩家意图。

请求身份比较、接纳决定与拥有权记录必须在项目定义的串行处理顺序中保持一致。有效性检查后不能跨过一次等待，再沿用之前的判断。显示逻辑若回调到界面并触发关闭或切换，也必须重新确认交接状态，不能把“都在同一线程”当作不会重入。若回调、关闭和显示逻辑在不同线程交错，还需要另外设计同步；一条 `if (request == current)` 不能证明整个流程安全。本文没有提供线程安全或重入安全的实现。

## 这项策略解决什么，付出什么

它解决的是旧结果误显示和本方引用无人收尾，不是节省所有被放弃加载的成本。连续快速浏览很多装备，仍可能产生许多等待结束的工作；限流、合并请求、缓存和底层取消是后续资源调度问题，不能从请求失效标记中自动得到。

释放本方引用也不等于资源立刻从内存消失。共享引用与 AssetBundle 生命周期会影响实际卸载；官方内存管理说明区分了引用释放和内存真正归还。[4] 因此，检查释放责任时看谁还持有，检查内存时看实际资源和包的状态，不以窗口关闭时刻替代两项判断。

接入项目时，至少逐项检查：剑比弓晚完成；关闭后再开同一装备；一组资源部分失败；显示建立到一半失败；已经显示的资源在关窗前仍被使用；窗口销毁后负责人仍能收尾。这些是待执行检查，不是本文已通过的测试。加载永不结束、管理方自身退出和进程终止也需要单独政策；“等完成再处理”不能假装覆盖永远没有完成的情况。

归根结底，取消按钮先改变的是玩家意图。可靠的资源接入还要把这个意图变化接到结果接纳和引用责任上，而不是让一个“取消”标签承担底层系统没有承诺的能力。
