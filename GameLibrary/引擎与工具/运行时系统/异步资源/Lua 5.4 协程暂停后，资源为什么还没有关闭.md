# Lua 5.4 协程暂停后，资源为什么还没有关闭

关卡脚本取得一个临时资源，等待剧情事件后再继续。玩家在等待期间离开场景，调度器不再恢复这段脚本，并把任务表里的记录删掉。资源是否也随之关闭？

对嵌入 Lua 的玩法与脚本程序，这不是单看“任务取消了没有”就能回答的问题。**停止恢复协程，不等于退出它暂停着的作用域；移除一个引用，也不等于执行关闭方法。** 以下使用 Lua 5.4 手册及固定5.4.8源码解释这一区别，场景与代码均为原创示意，未执行。[1–4]

## 等待把执行停在哪里

Lua 的协程可以保留执行位置，主动让出控制，之后再从那里继续。它虽然在 Lua 中具有 `thread` 类型，却不是这里新建的一条操作系统线程。`coroutine.create` 创建它，`coroutine.resume` 启动或恢复它，`coroutine.yield` 暂停它。[1]

先假定宿主引擎提供了 `acquire_scene_resource`：成功时返回一个资源包装对象，已定义 `__close`。这里的宿主就是嵌入 Lua、实际管理游戏资源的程序；这个函数不是 Lua 标准接口。

```lua
-- 未执行示意；假定宿主取得资源成功，返回可关闭的包装对象。
local co = coroutine.create(function()
    local resource <close> = acquire_scene_resource()
    coroutine.yield("等待剧情事件")
    -- 被恢复后，才会继续来到这里并最终退出函数。
end)

local ok, value = coroutine.resume(co)
```

`<close>` 把局部变量声明为待关闭变量。通常离开它的作用域时，Lua 调用值的 `__close` 方法；这是由该值的元表提供的关闭处理，不是 Lua 自动猜出引擎资源应该怎样释放。声明时初始化为 nil 或 false 的待关闭变量会被忽略；待关闭变量不能再被重新赋值。[1][3]

在这个例子里，假定第一次恢复顺利到达 `yield`，`ok` 为真，`value` 是等待说明。**这只是按语义推导的结果，不是运行日志。** 资源变量仍在暂停的函数作用域中，尚未因这次暂停而关闭。`resume` 的真值既可能对应暂停，也可能对应正常返回，不能单凭它宣布脚本已经做完。[1][2]

如果随后正常恢复，函数走到结尾，资源变量才随作用域结束进入关闭处理。若场景决定永远不再恢复它，这条自然退出的路径就不能被当作必然会发生。

## 不再持有协程，与关闭协程是两回事

把任务表条目删除，或把某个 `co` 变量设为 nil，只是移除了相应引用。其他回调或对象可能仍持有它；即使它最终不再可达，也不能把回收时刻当成场景卸载时刻。

尤其要分清两种名字相近的机制：`__close` 配合待关闭变量的作用域收尾；`__gc` 则是为合适的对象设置的垃圾收集终结器，执行时机不能由“刚删掉任务”来确定。固定源码的线程回收与显式关闭确实走不同路径：回收线程所做的关闭上值，不等于逐个调用待关闭变量的 `__close`。[3][4] 上值是闭包保留的外层局部变量，别把源码函数名里的“close”直接理解成业务资源释放。

这不表示带有适当终结器的资源永远不能回收，而是说：**“场景退出时已完成关闭”需要自己的依据，不能由丢引用或将来可能发生的垃圾收集代替。**

## 显式关闭，也需要读懂结果

对于暂停或已经死亡的协程，可以调用 `coroutine.close(co)`，关闭它尚待关闭的变量，并使它处于结束状态。正在运行、或者正在等待它所恢复的另一协程返回的 `normal` 状态，不是这个接口允许关闭的状态。[1][2]

关闭不是让暂停点之后的普通代码继续跑到末尾。因此，不要把必要收尾只写在 `yield` 后面，然后期望显式关闭替你执行那段代码。需要作用域收尾的工作，应由实际关闭处理承担；能否在那里安全调用宿主，仍要由项目确认。

该调用返回真，表示这次接口没有报告相应错误；返回假时还会给出错误对象。这里有一个容易误判的地方：**假值可能来自先前让协程停止的原始错误，并不意味着所有关闭方法都没有执行。** 关闭方法自身也可能出错，其他待关闭方法仍会继续被调用。固定实现会在受保护的关闭流程中保留原错误，或处理关闭时产生的新错误。[1][4][5]

反过来，返回真也不能证明宿主业务资源都已释放成功。包装对象的 `__close` 具体做了什么、外部接口的失败如何报告，必须有自己的约定。固定源码调用关闭方法时不接收它的普通返回值；如果包装方法只是返回一个 false，而没有将失败接入项目的错误处理，不能指望 `coroutine.close` 自动理解那个业务失败。[3] 不应把这一点变成“任何关闭失败都无限重试”的策略，重试是否安全需要资源自己的规则。

## 已经 dead，为什么仍可能需要关闭

普通 `coroutine.resume` 驱动的函数若发生未被内部保护调用处理的错误，会停止并向调用方返回失败。Lua 为保留调试信息，不在这条错误结束路径中自动展开整段协程栈；状态为 `dead`，因此不是“待关闭变量已全部处理”的证明。[1][2][5]

这里不能概括成“Lua 遇到错误都不收尾”。正常退出作用域有关闭规则，受保护错误有自己的展开过程；而 `coroutine.wrap` 创建的包装函数，在协程内部错误路径中会关闭协程再传播错误，与普通 `resume` 不同。[1][2] 改用 wrap 也不等于得到了场景取消方案：一个正常暂停、以后再也不调用的包装函数，不会仅因“以后不用了”而走这条错误关闭路径。

所以，调度器至少要分清正常结束、暂停待恢复和错误停止，而不是把“本次 resume 返回了”或“状态已经 dead”统一记成资源收尾完成。

## 场景退出时，把责任接到仍能收尾的人手里

回到开篇，实际接入首先要回答：**谁仍持有需要关闭的协程，谁能阻止它以后被迟到事件再次恢复？** 如果在建立关闭安排前就清空唯一记录，可能连显式收尾的入口也一起丢了。

然后要核对关闭处理依赖什么。假设包装对象的 `__close` 还要访问场景的资源管理器，那么先销毁管理器、再处理协程，可能已经不满足这段关闭代码的前提。这是要检查的依赖关系，不是本文给所有引擎规定的销毁顺序。关闭方法可能回调宿主或出错，不能假定收尾过程不会重入、不会失败。

最后，协程关闭与外部工作结束仍须分别判断。它不会自动取消一个下载、撤销别处的事件订阅，或关闭其他协程。若等待的是底层资源加载，应用仍要安排迟到结果和引用责任；同书架的[装备预览加载收尾](关闭装备预览后，未完成的资源加载怎样收尾.md)以 Addressables 解释另一种具体实现，不能把其中接口当作 Lua 的行为。

本文没有给出生产调度器、跨线程方案或完整的 C 调用边界处理，也不假定关闭方法可以随意再次 yield。可落实的第一步是沿一段脚本画出资源取得、暂停、继续或放弃、关闭处理及宿主依赖失效的位置，逐一确认谁能推动它们，而不是让“取消任务”这个名字代替整条收尾过程。
