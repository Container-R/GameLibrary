# 系统挂起前后的本地期限计时

玩家让设备睡眠十分钟，回来时，一个五分钟的本地确认窗口应该已经过期，角色的战斗冷却却不应该凭空走完。若两者都依靠上一帧到这一帧之间的差值，修好其中一个，可能会让另一个变错。

本文面向实现主循环或平台恢复的游戏程序员，讨论同一次系统启动内、进程仍能恢复既有状态的情况。目标是在恢复后判断本地期限、处理首帧模拟，并能从日志区分“恢复后发现到期”和“计时器唤醒了设备”。不讨论跨重启持久化、远端会话裁决或如何保证后台回调准时。

## 先把到期、推进和通知分开

先为本地期限选时钟。若设计要求睡眠也占用这五分钟，就用计入挂起的经过时间。在 Linux 上，单调时钟 `CLOCK_MONOTONIC` 不计系统挂起，`CLOCK_BOOTTIME` 计入；单调只说明读数不会倒退，不决定挂起是否算进去。[1] 在开始时，用选定时钟的读数加上时长得到期限；稍后必须用同一时钟比较。两个时钟的绝对读数不能互相替代。

战斗用的是另一项规则：冷却和状态只随已经执行的模拟步推进。设备恢复并不授权把整个停顿补成很多步。即便帧时钟本身不计设备挂起，仍可能跨过应用层暂停、恢复过程或其他未执行模拟的间隔，所以不要仅用“这个时钟不计挂起”来省掉恢复处理。

第三件事是计时器何时发信号、应用何时处理信号，或者设备是否因此唤醒。读时钟只得到经过时间，不能使程序在挂起中运行。实现时可以让计时器与恢复入口都触发同一个期限检查，但不把通知本身当作过期事实。主动唤醒不是此方案判过期的前提。

## 恢复入口怎样接到主循环

假设设计要求确认窗口跨挂起继续计时，战斗不补算挂起，也保留暂停前已经认可的模拟欠账。应用在同一次启动内持有期限值、窗口状态、帧时钟基准，以及固定步累加器。

1. 开始本地窗口时，用包含挂起的时钟保存 `deadline = now + duration`。处理确认、计时器通知和恢复时都重新读取同一时钟；若 `now >= deadline`，让仍待处理的窗口只转换一次为已过期。处理确认时先检查到期，再决定是否接受；到期与确认由同一个串行所有者处理。即使确认排在迟到通知之前，也不能接受已到期的请求。若窗口会重开，让旧通知只检查它所属的窗口实例，不向新窗口提交旧结果。
2. 主循环在首次普通帧入账和补步前，必须先处理已知的恢复边界。用帧时钟当前读数替换上一帧基准。这一帧不把中断间隔累加，也不补算；下一普通帧再从新基准取差。若保留了暂停前的正常欠账，可以从下一普通帧按既有补步预算处理，不能和中断间隔混在一起。这里的冷却只在真正执行模拟步时更新。
3. 记三组不同的观测：期限时钟的开始、期限和比较值；恢复时是否重设帧基准、向累加器加了多少、模拟步编号是否改变；通知的到达时间和已知的唤醒来源。没有可靠的唤醒来源记录，就标未知。若运行时没有可信的恢复边界，长帧差只能作为过载处理线索，不能凭它断定设备曾挂起。

如果设计要让菜单暂停也暂停本地期限，不能拿这套“继续计时”的窗口照搬；需要另行维护暂停规则，例如在暂停时保存剩余时长、恢复时用选定时钟重新建立期限。另一方面，也不是所有窗口都该在恢复后重建期限：需要跨挂起到期的窗口一旦重建就会被无意延长。

## 用同一段经历判三件事

纸面场景：打开五分钟窗口；设备运行一分钟后挂起，十分钟后由玩家手动唤醒，立即进入恢复处理。忽略恢复处理耗时。

| 观测项 | 在此场景应得到的结果 |
| --- | --- |
| 包含挂起的同源时钟差 | 11 分钟，本地窗口过期 |
| 如果误用了不计挂起的时钟 | 只记 1 分钟，错误地还剩 4 分钟 |
| 模拟步和累加器 | 恢复首帧不补算，不加中断差值；此前的欠账另计 |
| 通知与唤醒 | 已知是玩家唤醒。恢复后显示已过期，不能证明计时器曾唤醒设备或回调已在睡眠中运行 |

检查工程接入时，再安排两个对照：在到期前手动恢复，应仍可操作且不补算战斗；到期后，让恢复入口与迟到通知先后抵达，应只出现一次过期处理。这样能分别识别选错时钟、恢复时基线没重设、以及同一结果被通知重复触发。这里给的是验收输入和预期，不是设备实测。若目标恰好是定点唤醒，需要在相应平台另测实际唤醒和投递，而不是用上述手动恢复结果代替。

## 平台接口能承诺的是哪一件事

- Linux `timerfd_create` 的 `CLOCK_BOOTTIME` 以计入挂起的时钟设定期限；`CLOCK_BOOTTIME_ALARM` 另具在到期时唤醒系统的语义，设置这类定时器需要 `CAP_WAKE_ALARM`。[2] 应用不需要主动唤醒时，不必把它变成期限检查的依赖。
- Android `AlarmManager` 的 `ELAPSED_REALTIME` 与 `ELAPSED_REALTIME_WAKEUP` 使用同一计入睡眠的开机后时钟。前者不唤醒设备，睡眠中到期则等待后续唤醒投递；后者提供唤醒类型。[3] 类型只说明时间基准和唤醒语义，不承诺任意调度方式都准点投递。
- Windows 的 `SetWaitableTimer` 是另一个提醒：在 Windows 8 / Windows Server 2012 及以上，负值指定的相对到期不计低功耗时间；文档列出的旧版本相对到期规则不同。其 `fResume` 参数另行申请唤醒；不支持恢复时，调用可以成功，而文档说明此时 `GetLastError` 报 `ERROR_NOT_SUPPORTED`。[4] 不把定时器设定成功当作跨睡眠计时或唤醒成功，也不从这里推断其他 Windows 时钟。

同一个引擎函数也可能有不同口径。以 Godot 4.6.3 的源码为例，`Time.get_ticks_usec()` 转调平台实现：桌面 Linux 读 `CLOCK_MONOTONIC_RAW`，编译时未提供它则用 `CLOCK_MONOTONIC`，两者都不计挂起；Windows 读 `QueryPerformanceCounter`，微软文档说明该计数器计入睡眠时间。[1][5][6] 因此，若直接拿同一个接口去算上一节的本地窗口，按源码推导，Linux 会错误地还剩约四分钟，而 Windows 会判它过期。跨平台的期限接口应明确约定“计入挂起”，而不只是“读数单调”。这个例子是源码与平台文档推导，不是发行包或设备实测，也不能用来判断引擎计时器何时回调。
