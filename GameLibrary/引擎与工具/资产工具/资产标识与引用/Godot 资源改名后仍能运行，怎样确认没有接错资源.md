# Godot 资源改名后仍能运行，怎样确认没有接错资源

美术把一份红色的昼夜渐变从旧目录移到新目录，又在原路径放入另一份蓝色渐变。关卡打开不报致命错误，天空却变成了蓝色。看起来只是路径移了位置，实际上有两个问题：**引用有没有找到一个能读的文件，找到的是不是原来要用的那份资源。** 在 Godot 的文本资源里，这两个问题不能靠一次“场景能打开”同时验收。

这里讨论从版本控制重建的 Godot 项目，重点是 `.tres` / `.tscn` 的外部资源引用与写死的路径；不讨论导出包重映射、运行时资源分包或跨项目传送资源。

## 名字换了，资源身份未必换；名字没换，身份也可能换了

一个保存的外部资源引用可能同时带有 `uid` 和 `path`。路径是文件的位置，UID 用来识别当前项目里的资源。文件改名后，如果仍是同一份资源且保留 UID，编辑器扫描能把该 UID 登记到新位置。原引用的路径即使没一同修改，文本加载器仍可采用 UID 指向的位置。Godot 4.4 的官方说明解释了这一分工，也明确提示：UID 不可用时，保存的路径会回退为加载依据；旧路径复用就可能把两份资源接错。[1]

用于保存身份的信息不一定在同一个地方。原生场景与资源文件通常把 UID 写进自己的文件头；导入资源可以在相应的 `.import` 文件中保存身份；Godot 4.4 为脚本、着色器等不能方便地在内容里放原生文件头的资源引入了 `.uid` 伴随文件。[1] 因此，不论是用编辑器移动还是在版本控制中重排目录，都应先知道这项资产的身份由什么文件承担。外部移动脚本时，不要只移动 `.gd` 而把相应的 UID 文件留在原地。反过来，复制成一个以后独立维护的资产时，不应把原 UID 当成副本可共享的名字；应给副本分配自己的身份，并明确哪些调用方需要改指副本。

这套机制只保护用相应形式保存的引用。脚本直接写 `load("res://assets/old.tres")` 时，传进去的是旧路径，不是对某个已登记 UID 的引用。即使编辑器场景能正确跟着移动走，也要另查脚本字符串、外部配置和工具生成的数据。项目存档或跨引擎数据若需要在版本之间识别一种玩法对象，另定义稳定的业务键和迁移表；不要把本次导入的 UID、文件名或内容哈希直接当成同一概念。

## 一份红色资源，两种情况都可能“加载成功”

试件里的父资源是 `GradientTexture1D`，外部引用声明一个 `Gradient`：UID 指向红色渐变，文本路径写着 `res://assets/old.tres`。蓝色渐变也是 `Gradient`，但有另一个 UID。每个主要用例都在单独创建的 Godot 4.6.3 官方版项目中，先用 headless 编辑器导入，再在新进程读取；核对导入没有改写父资源的引用文本。结果记录了返回对象、实际资源路径和第一个色值，而不只是有没有加载异常。

| 资源变化 | 带 UID 和旧路径的外部引用 | 脚本直接按旧路径加载 |
| --- | --- | --- |
| 红资源和 UID 都在旧路径 | 读到红色 | 读到红色 |
| 保留 UID 搬去新路径，旧路径空着 | 读到新路径的红色 | 没有资源 |
| 红 UID 不再登记，旧路径也空着 | 加载失败，记录无效 UID 警告 | 没有资源 |
| 红 UID 不再登记，旧路径改为蓝资源 | **父资源成功加载，却读到蓝色**；仍有无效 UID 警告 | 读到蓝色 |
| 红 UID 仍能找到新路径，旧路径另有蓝资源 | 仍读到新路径的红色 | 读到蓝色 |

这里的蓝色不是模拟出的日志结论，而是实际返回的 `Gradient` 的颜色。类型检查只能保证它是 `Gradient`；这两个资源类型相同，类型通过并不能证明引用没换。官方发布标签的文本加载器在 `ext_resource` 分支中先读文本路径，如果 UID 已登记就替换成索引中的路径，否则保留文本路径并按条件发出警告；然后才尝试按选定路径加载。[2]

“UID 已登记”与“目标路径现在能打开”也是两件事。另一个受控反例在扫描登记后、启动读取进程前，只移除临时项目里的新路径红资源，让旧路径蓝资源留着。UID 索引还指向新路径，父资源加载失败；它没有因为新路径后来不存在就再去旧路径读蓝，也没产生“无效 UID，改用文本路径”那条警告。这个反例是故意制造的过期索引，不是说日常编辑器发现移动后不会重扫。它提醒维护工具：**既要验映射，也要验映射指到的资源能加载。** 不能只搜无效 UID 警告，更不能认定任何失败都会自动尝试旧路径。[2][3]

再做一组对照：扫描后不删除新路径，而是把那里原本的红资源替换成另一个 UID 的蓝资源。索引仍给出预期的新路径，父资源能打开、没有无效 UID 回退警告，最后却读到了蓝色。它不需要回退就能接错对象。因此，即使“映射正确、能加载、没有回退警告”三项都满足，迁移测试也还需要核对文件身份和实际依赖。

## 用清洁导入验收“同一份资产搬过去了”

先把目录变更做成有预期的迁移清单。对每个重要目标，记录是同一份资产改名、复制成新资产，还是有意替用另一份资产；然后明确哪些场景、资源和脚本应保留同一身份，哪些应改指。不要让回归测试运行后，拿“这次碰巧读到了谁”反写期望值。如果是搬迁，检查原 UID 和必要伴随文件仍在；如果是替换，检查你改的是目标引用，而不是把一个同名文件覆盖到旧路径，让回退碰巧成功。

从待验收提交建立一份真正没有旧导入缓存的工作副本，按你支持的 Godot 版本导入并另开进程读取。围绕关键场景做三层检查：

1. **映射。** 检查预期 UID 是否登记、它是否解析到期望路径、这个文件的身份信息是否仍符合搬迁清单。给重复身份留下明确诊断，不依赖在某一台机器上恰好扫到哪个副本。
2. **依赖。** 读取脚本或父资源实际使用的对象，确认其类型、有效路径和业务上能区分目标的一项特征；例如关卡配置的稳定键、预期子资源或者本例的标记色。同时记录路径回退警告。仅检查加载调用返回非空，会漏掉“蓝色替了红色”。
3. **路径型消费者。** 检查脚本、表格和工具输出中保存的旧文本路径。让原路径被同类型的虚构替代物复用作为反例，可以证实测试不会把“文件存在”当成“找对了”。本例的原始 fixture 就把两种读取方式分开记录。

旧提交可能已经有无害但待修的警告，不必不分范围一次封死整个项目。对本次迁移触及的资产和场景应明确哪些警告要阻断、哪些是已核实、有意保留的兼容路径；旧缓存里能运行不作为例外依据。如果仍需旧文件名供旧工具或旧数据访问，做有对象身份断言的迁移或明确兼容映射，不在同一路径悄悄换一个资源。让版本控制记录这一决定，便于重新导入时复现。
