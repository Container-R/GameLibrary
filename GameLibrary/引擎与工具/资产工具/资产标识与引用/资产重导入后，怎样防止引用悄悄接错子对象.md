# 资产重导入后，怎样防止引用悄悄接错子对象

一个模型文件导出三种材质。栏杆材质改了名字、窗玻璃没改，侧门扣件被删除；新做的窗扣却沿用了显示名“Latch”。重导入后，旧预制体的三个材质引用都没有丢失，但其中一扇门用上了窗扣的材质。非空只能说明找到东西，不能说明找到了原来那个对象。工具需要同时认得留下的、被删除的和新产生的对象。

这里讨论一个源资产被导入为多个可引用产物时的身份设计，不讨论单个资产改路径时怎样保住文件本身的身份。两者的区别是：源文件的资产身份没变，文件内的某个子对象仍可能改名、移动或消失。

## 把作者身份、导入键和序列化引用分开

**作者身份**是工具与制作人员承诺“这个对象仍然是它”的依据。可在资产内给材质、网格或语义槽持久分配 ID，并定义什么变更不换 ID。改名字、调参数和重排通常保留；新建、同文件内复制通常要新发。模型里的“可替换门扣槽”与“当前门扣材质”是两个对象；如果对方依赖槽而不是具体的材质，就应该引用槽的稳定身份，并令槽到材质的绑定可修改。内容一样的两个槽也仍可能不同，所以内容哈希适合查产物变化与缓存，不宜默认当身份。

**导入键**是导入器用来把本次生成的对象与上次匹配的标识。对于项目自管的 Unity ScriptedImporter，可从作者 ID 与产物角色生成如 `material/<source-id>` 的字符串，并在导入文件内保证唯一。Unity 6000.0 的 `AssetImportContext.AddObjectToAsset` 明确要求对应对象的 identifier 在重导入时可确定地重新生成。[1] 若一个作者对象能生产可分别引用的材质、遮罩、碰撞体，应给这些角色不同且稳定的派生标识；不能把可改名的显示标签写进前缀或把今日的输出列表顺序写进后缀。

**序列化引用**是引擎最后写进场景等资产的键。Unity 把包含资产的 GUID 和文件内 `localId` 一起用作引用；`TryGetGUIDAndLocalFileIdentifier` 可读两者，`localId` 用 C# `long`。[2] 若把它送到 JavaScript 报表，用能无损保存的十进制字符串，不要转成精度不足的普通数字。 别把传给导入器的字符串误当作 Unity 最终的数字 fileID，更不要自己猜计算方式。公开合同针对自定义导入器这一入口，不代表内置 FBX 或另一插件对改层级、改槽位的承诺。项目接入时应在实际编辑器和固定版本做一次存盘引用的重导入对照。

## 三个非空引用，可以三个都错

glTF 的数组下标可以连接本文件的对象，不能作为出下一版后仍相同的持久身份；规范也不要求名称唯一。[3] Blender 4.3 可把自定义属性输出到 glTF 的 `extras`。[4] 用 Blender 4.3.2 实际导出三个各带一个材质的三角片，然后改栏杆材质名、修改其颜色，将栏杆对象从集合解除链接再加回，并删除门扣、新建同名窗扣，得到以下数组。末列的短码是本试件 UUID 的尾号，不是 glTF 标准字段。

| 数组下标 | 初版导出 | 重导出 |
| ---: | --- | --- |
| 0 | Metal（外栏杆，01） | Glass（窗玻璃，02） |
| 1 | Glass（窗玻璃，02） | Latch（新窗扣，04） |
| 2 | Latch（旧侧门扣，03） | Exterior Metal（外栏杆，01） |

两次都开启自定义属性导出时，栏杆的 01 随它留存，旧侧门扣 03 消失，同名新对象的是 04；关掉该选项再导出，三条材质都没有本项目的 ID。这里只证明这组操作在这个版本的 JSON 中产生了上述变化，不保证所有导出器或所有 DCC 修改都以此顺序重排，导出后的消费者也得实际读取而不是默默忽略 `extras`。

将真实导出两次列表喂给一个抽象引用模型，旧三条引用按下标都能找到对象，却分别落到窗玻璃、窗扣和栏杆。按名字时，栏杆改名而找不到，窗玻璃不变，原来叫 Latch 的侧门扣还会悄悄连到新窗扣。按作者 ID，两个仍在的对象继续匹配，旧门扣变成显式缺失。用基于内容的键则让改色栏杆也丢身份；这一个分支用人工填入的版本字符串模拟内容变化，不是在算 glTF 文件哈希。Node 试件不执行 Unity 的本地 ID 算法，不意味着 Blender 的 glTF 默认消费者也实施了同一规则。

## 没有稳定 ID 时，不要悄悄用名字兜底

优先用作者工具能持久保存的元数据，或一份和源资产一起交付的标识清单。清单需要一个跨编辑仍能关联到作者对象的键；如果每次重新按名称或索引做配对，它只把错误挪到了文件外。还要明确 ID 的范围：复制整份资产后有新的文件身份，若约定子 ID 在每个文件内独立，一个别处的同样子 ID 不冲突；如果工具只接受项目级源 ID，整份复制也要重发或加命名空间。复制同文件中的一个对象时应立即让新副本有独立 ID；若从外部回传造成重复，在写产物前报告并停止自动匹配。缺 ID 或发现 ID 冲突时可让内容过审后补录，别为了能打开关卡临时拿第一个同名物顶上。

删除、替换或合并则要先看旧引用承诺什么。删除时停用旧 ID，将停用 ID 和旧用途保存在跟随源资产版本化的清单中，导入时拿新清单与它核对，不能让新物件重新登记为旧号。若外栏杆被拆成上横杆与底座，旧 ID 只有在其中一个产物仍完整承担旧合同，或能保留一个明确的兼容外栏杆槽时才应继续可用。否则列出旧消费者，由制作明确选择替换对象；存在多义时不要自动从一对多里挑第一个。换键规则是迁移，不是普通重导入。旧文件已经用索引或名字串接时，先把**旧版本**的标识、所指作者身份、引用它的预制体或场景存成基准，再对照新规则得到一对一、缺失、多义三组；确认后修改消费者并一并提交，难以决定的保留错误和待办。更换同名对象还可能是有意的内容替换，但这种语义变更应明示，不能靠名称重复碰碰运气。

## 用会变更的案例验收，而不只重导入两次相同的文件

做一份带三个独立消费者的场景或预制体，初始版本保存到磁盘，记录它们应指向的作者 ID 和引擎实际序列化身份。按改名、重排、编辑内容、复制、删除和同名替换做变更。不要只打印导入器刚创建的对象；重新加载原消费者，检查实际解到的目标身份和用途。如果消费者的序列化值变了，也检查是否是计划内迁移；如果数字没变，仍要核对背后所指对象，因为同一键可能刚好被错误复用。验收同时要求未删除的保持、已删除的可追踪失败、未授权的换对象不通过。再对干净导入和旧缓存重导入分别跑一遍，确定成功不靠编辑器内某个尚未释放的旧对象；刻意缺配置的导出版本应报身份缺失。

这种检查会把原本不报错的错绑变成一次能定位的制作问题。把“找不到旧门扣”留给有上下文的人，比让一个初次打开关卡时能显示出来的错误材质更好修。
