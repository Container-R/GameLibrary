# 构建日志里有着色器变体，为什么成品里还是用不上

测试包能显示武器的普通材质，一强化，冰霜效果却不见了。构建日志写着这个着色器留下一个片元变体，编译前的自定义日志也记过 `FROST`。这两份记录并不矛盾：计数不能告诉你留下的是哪一个；回调见过 `FROST` 也不能证明最终运行的是带它的成品。

以下以 Unity 6.0 的图形着色器为例。排查的目标不是尽可能多保留变体，而是找到**第一次看不到正确组合的地方**。先核对运行时真正请求了什么，再比较构建阶段。若两份证据来自不同包，先停止归因。

## 先把“这个变体”说清楚

同一着色器可以有多个 SubShader 和 Pass（绘制阶段），同一个 Pass 的顶点与片元阶段也不一定生成同一组变体。排查时，先记录候选包的唯一标识、平台、渲染管线及质量配置；选定一帧里真正出问题的物体和绘制 Pass，记录着色器资源身份、SubShader/Pass、着色器阶段、图形 API，以及该阶段所需的有效关键字组合。构建枚举另外保留编译器平台、图形级别等区分维度；不要把运行时 API 名称直接当构建枚举的字符串，要核实两边对应。[1]

从实际参与那次绘制的材质读状态，不要只看脚本中本来要改的材质。启用同名全局关键字也不一定覆盖局部定义，取决于关键字的作用域与可覆盖性。另一方面，材质上启用的所有关键字不等于某个阶段的变体键。阶段后缀能否缩小范围取决于后端：Unity 6.0 文档明确说明 OpenGL、OpenGL ES 和 Vulkan 不采用这些后缀的阶段限定。不能看到 `_fragment` 就自行删掉 Vulkan 顶点阶段的这个关键字；要按目标后端与实际编译记录统一适用范围，不要拿材质的长名单和某个阶段的短名单直接判“不匹配”。[1][2] 如果实际请求的就是普通外观组合，优先修材质归属或关键字设置，而不是先关闭剥离。

## 构建时，计数和成员名单是两种证据

Unity 的编辑器日志会给出设置过滤、内置剥离和脚本剥离等阶段的变体数。URP 可额外导出 `Temp/shader-stripping.json` 等报告，用于识别哪个着色器和片段减得最多；不要把这份文件名当作包内清单。[3] 在固定的 Unity Graphics 6.0 维护分支源码中，核心 `ShaderVariantStripper` 是顺序值为 0 的编译前回调。它先改候选列表，再把当时的前后数量交给报告。报告里的 `variantName` 对图形着色器实际上由 Pass、SubShader 与 ShaderType 等信息组成，并没有给出每个存活条目的关键字集合。[4]

比如候选 A 的 Forward 片元阶段只保留 `FROST`，候选 B 的同一阶段只保留空集合。两者输出数都是 1，冰霜效果却不一样。需要查成员时，可以在测试构建中加入两个**只读**的 `IPreprocessShaders` 记录器，分别安排在怀疑的剥离器之前和之后，按 `ShaderSnippetData` 与 `ShaderCompilerData` 逐条记录完整身份。Unity 按由小到大的顺序值调用同类回调；先核对项目与渲染管线使用的实际顺序，避免同序值，更不要假定给记录器一个很大的数就看到了包内数据。[1][5]

记录器可从 `ShaderSnippetData` 取得 Pass 和着色器阶段，从每条 `ShaderCompilerData` 取得 `shaderCompilerPlatform`、`graphicsTier` 与 `shaderKeywordSet`；输出时把关键字按固定次序排列，另保留该版本可见的平台条件，避免同一集合因枚举顺序不同被误判。它记录的是各编译候选，不是帧调试器里已经绑定的程序。[1]

每个观察点除记录候选成员，还要标明观察范围：例如“此次捕获完整记录了候选 B 的该着色器、Forward 片元、Vulkan 片段”。如果只筛 `FROST` 又没有记录该片段是否实际进入回调，没找到一行只能写成未知。整个片段没到达记录点、收集范围不对、捕获不完整和组合被删，不是同一个结论。

## 把两段构建观察与实际绘制对起来

开一个只用于诊断的 Player 构建，启用严格着色器变体匹配，在已记录的平台、图形 API 与画质上，用同一个候选包分别触发普通状态和冰霜状态。若还会加载内容包，记录本次运行**实际装载**的内容版本及资源来源，不能拿另一次构建的成员日志横向拼起来。画面和 Player 日志都要看。严格模式找不到精确组合时会使用错误着色器并报告；默认非严格模式可能采用相近组合。无报错不证明目标 Pass 已经执行，也不能证明效果正确。[6]

最小复现可只放一件可强化武器，让普通和冰霜状态各只触发一次。平台支持时把 Unity Frame Debugger 附到诊断 Player（官方要求包括 Development Build 与多线程渲染支持），选中目标绘制，通过 Pass、Original Shader 与 Used Shader 辨别实际调用和可能的回退；附不上就用该平台可用的抓帧或等效的项目级绘制记录。[7] 在 Player 日志中核对严格模式报告的着色器及有效组合；只从脚本读取的材质关键字是旁证，不能拿来替代这条运行时记录。若报告只给出组合、未能可靠对齐到出问题的绘制和编译阶段，就先隔离场景、标记状态切换并重跑，仍对不上则保留未知。诊断包和正式构建是不同候选，不能因为开发包通过就给正式包销案。

| 同一候选的观测 | 下一步 |
| --- | --- |
| 实际请求与预期不同 | 先核对绘制材质、局部关键字和可覆盖的全局状态。 |
| 精确请求确实失败，完整前表有、完整后表无 | 组合在两个观察点之间消失。收紧记录点，或仅改变一个剥离条件后重建对照；不能仅凭消失就指定罪魁祸首。 |
| 精确请求失败，前后两份完整表都无 | 去查更早的候选生成、目标设置和内置过滤；不能归咎于两个记录点之间的脚本。 |
| 精确请求失败，后表仍有 | 先确认资产实例、包版本、Pass、API 和质量配置确实匹配，再查后续编译、序列化或实际装载。后表是候选，不是成品。 |
| 记录不完整、包不同，或没有确认该状态确实触发 | 补证据，不判“已剥离”也不判“已经保留”。 |

做修复对照时，只改一项可重建的条件并另发候选标识，例如只给目标材质的运行时组合增加一个明确的构建保留来源；分别记录两个候选的阶段表和 Player 结果。关闭全部剥离可以作为宽泛的诊断对照，但构建时间、大小和加载都可能变，不能把它当作长期修复。反过来，即使一个候选修好，也只覆盖实际走通的效果、目标和 Pass。

[复现材料](../../../../管理档案/实验/shader-variant-runtime-evidence/README.md) 是一个可执行的诊断模型，验证相同计数、漏看阶段、跨包误配和日志静默等反例如何改变结论。它没有运行 Unity；实际引擎主张来自下列文档和固定源码，不用模型证明某个项目真的构建或绘制成功。
