# 构建工程师如何交付可用的游戏版本

下午的内部试玩要测试一把新武器。程序已经提交修改，自动构建页面也是绿色，测试人员下载安装包后，却发现武器仍按旧规则造成伤害。有人建议“删掉缓存再打一次”，有人说“我本机是好的”，还有人重新上传了一个同名压缩包。现在大家连刚才测的是哪一份都说不清了。

这是一个用于说明工作的假设场景，不是哪家公司的事故。它说明构建工程师的任务不只是让编译器成功退出，而是让团队拿到**来源清楚、内容符合本次目标、能够安装和验证的游戏版本**。

本文面向准备从事构建工程的程序员，以及需要与其协作的工具、内容和测试人员。下面沿着这把新武器，从输入到生成文件，再到试玩包，解释构建工程师怎样帮助团队找出问题并交付下一份可信的候选版本。文中的排查与交接办法是工程建议，不是对某家公司内部流程的复刻。

## 先说清楚这次要交付什么

“打最新版本”并不是充分的构建要求。最新代码可能仍引用旧资源；同一代码修订也可能构建出开发版、发行版或连接不同服务环境的包。

对这次试玩，更明确的目标是：在指定测试平台上运行一份包含新武器规则的内部候选包，进入指定关卡后能够装备、使用这把武器，并连接约定的测试服务。这里的“候选”表示它准备接受检查，不表示它已经适合公开发布。

构建工程师需要先和提出需求的人确定范围。玩法程序知道代码修改在哪里，策划知道哪份规则表才是预期输入，工具作者知道规则表如何变成游戏读取的文件，测试人员知道怎样识别新行为。构建工程师把这些信息变成可执行、可追踪的构建过程，而不是替每个人猜测“最新”的含义。

公开岗位能看到这种协作：Cygames 的构建工程岗位包含自动测试、二进制分发、开发支持与仓库管理；Bandai Namco Studios 的相关岗位覆盖共享引擎的构建、测试、包分发与流程改进。[1][2] 这些说明了工作范围，但不能推出每位构建工程师都拥有最终上线决定权。

## 游戏版本的输入不止源代码

构建可以理解为一系列转换：把源代码编译成程序，把美术和设计源文件转换成运行时资源，再按目标平台与配置组合成可交付文件。每个转换都可能依赖工具和配置。

假设新武器的数据链是：

**武器规则表 → 数据转换工具 → 游戏读取的数据文件 → 试玩安装包。**

即使规则表没有变化，转换工具修复了单位换算错误，生成的数据也可能需要改变。反过来，转换工具没变，规则表改了，也必须产生相应的新结果。编译游戏程序成功，并不能证明这一条资源链已经更新。

因此，不宜只留下代码分支名。对这个例子，至少要能找回实际使用的规则表版本、工具版本、构建配置和最终数据文件，并知道它们来自哪次构建。若包启动后还会读取远端规则或服务配置，这些包外输入也应在测试说明中单独指出。仅保存安装包不能固定运行时世界的全部条件。

自动化还可能产生后续工作的输入。Cygames 在 2020 年的一篇技术问答中说明，他们定期在持续集成（CI）环境运行 C++ 缩略图程序，再由 Python 通过资产系统把缩略图提交到 Perforce。[3] 这是开发环境里的生成链，不是新武器事故的证据，也不表示缩略图必然随游戏出货。它提醒我们：不能把所有自动任务的输出都当作流程终点。

## “工具先编好”与“数据应重做”是两件事

前面的失败可以先沿数据链检查：包里确实是旧数据吗？这次生成步骤有没有执行？如果没有，构建系统为什么认为旧输出仍能使用？

这里有一种常见的依赖区别。**执行顺序依赖**回答“生成数据之前，工具是否已经可用”；**重新生成的依赖**回答“哪个输入变了，现有数据就应失效”。只解决前一个问题，未必解决后一个。

CMake 3.31.12 的文档给出了具体例子：在生成命令中用完整的 `TARGET_FILE` 表达式引用项目内工具，会建立相应的目标构建顺序，但不会自动建立“工具重编后重新运行生成命令”的文件级依赖；把可执行目标列入 `DEPENDS` 才补上这类依赖。[4]

把它应用到我们的假设中：项目内的 `asset_packer` 把规则表生成一个文件，输出由同目录中实际参与构建的目标使用。若生成命令的 `DEPENDS` 只写了规则表，就不能仅凭工具已重编，保证数据也会重做。应同时表达表文件和工具的依赖。这里只说缺少该保证，不意味着在任何情况下都绝不会因其他原因重跑。

检查这类规则时，只做一次干净构建不够。因为输出原本不存在，生成成功可能掩盖增量依赖遗漏。更有针对性的做法是分别检查“仅改表”和“仅改工具”两种情况，观察相应数据是否重新生成，再检查新数据的内容。这是待执行的检查建议，本文没有运行 CMake，也不声称任何团队存在这个缺陷。

这个例子仅限同目录、单输出、本机可执行工具和明确输入。工具另外读取的配置、插件或脚本，不会因为加入一个目标名就自动全部成为依赖。它说明的是依赖设计，不是一份可直接覆盖所有项目的构建脚本。

实际修改 CMake 规则时，还要留意两种相似写法。这里的完整 `TARGET_FILE` 不能与只取目录或文件名的 `TARGET_FILE_DIR`、`TARGET_FILE_NAME` 混同：后者是否建立目标依赖受 CMP0112 政策影响，在 `NEW` 行为下不会自动建立。[8] 同样，把 `add_custom_target` 创建的自定义目标写进 `DEPENDS`，不能照搬可执行目标重编触发文件级失效的结论；还应明确它真正生成的文件如何参与依赖。[4]

## 缓存是节省工作，不是证明输出正确

缓存保存过去的结果，是为了在输入条件适合时复用它们。问题不在于“用了缓存就不可靠”，而在于复用判断有没有考虑会影响结果的输入。

如果新工具仍然命中了旧数据结果，清掉缓存可能让本次试玩恢复，但还没有回答下次为什么不会复发。应继续检查缓存采用什么身份区分输入，工具与配置变化是否能使旧结果失效，以及生成文件是否来自另一个遗留目录。

干净构建可以帮助比较，却也有成本：需要重新完成本来能够复用的工作，而且一次成功不能证明所有增量组合都正确。较稳妥的安排是保留这次失败的定位信息，用尽量小的变化复现依赖问题，修正规则后再进行针对性的增量检查与必要的干净构建比较。不要让“每次都全删”成为依赖错误永远不被修复的理由。

重试也要有明确输出归属。新任务失败时，分发页不能因为目录里还留着昨天的包，就把那个包展示成“本次成功结果”。如果确实要退回旧候选，应明确告诉接收者，而不是悄悄替换。

为避免把几次尝试拼成一次成功，每次构建调用都应能单独识别，并把生成、编译、打包和检查各阶段的日志、输出及最终状态关联到这一次。比如生成完成后构建被取消，应保留已产生数据的归属，同时明确后续打包没有执行；不能因为有生成文件就宣布整包成功。重试是新的调用，不能借用上一次的日志或结果来填补本次未执行的阶段。

### 开发机能临时补编，不等于发行包已经齐全

**着色器**是参与画面绘制的程序，不同选项组合可能需要不同的编译结果。假设美术改了一个材质选项，当前预编译文件却来自修改前，那么“找不到对应结果”未必说明构建规则漏掉了组合，也可能只是新产物还没有生成。这两种情况需要不同处理：前者要修正规则，后者要核对产物与输入修订是否一致。

Nexon 的 정희석 在 NDC 2013 介绍 Mabinogi2 项目时，就谈到类似困扰：着色器设置修改后，尚未更新的每日构建会造成缺失报告，干扰对真正漏列组合的判断。他描述的开发流程是，在相关改动后暂时让客户端本地编译，新的每日构建完成后再切回预编译结果。[9] 这是官方会议文字转录中的历史经验，不是本库复现，也不是当前引擎的通用配置方法。

这个办法能够帮助开发继续进行，却不能单凭“本机又能画出来了”批准发行包。对我们的交付检查，还应确认候选使用的是哪次输入生成的预编译产物，并在项目预定的发行配置下检查需要的组合；若本地补编掩盖了缺项，就保留这个缺口，不把它计成预编译覆盖已经通过。哪些改动会启用兜底、何时退出、退出后按什么条件验收，也应可追踪。这里提出的是接收建议，不是说原演讲已经公开了完整覆盖算法或证明所有组合都正确。

### 强化效果需要的变体，是否真的进入了包

沿用新武器的假设：强化后，材质要显示冰霜效果。在 Unity 中，脚本可以通过 `FROST` 这样的**关键字**选择着色器功能；不同静态选项组合对应的编译结果称为**变体**。以下依据 Unity 6000.0 版本路径的可变文档解释机制，不是已经运行的武器效果。[14]

先确认请求：脚本是否改了这把武器实际使用的材质？若关键字声明带 `_local`，仅启用同名全局关键字，不能代替修改材质的局部状态。[15] 再查保留：`shader_feature` 会依据构建所用材质的组合减少变体，运行时才启用的组合可能不在其中。Shader 资产存在、普通外观正常和构建成功，都不足以证明冰霜组合已保留。可以按所需组合配置随构建包含的变体集合等保留途径；改用 `multi_compile` 也不是免剥离承诺，构建回调仍可移除变体。[14][16]

若所请求的精确变体确实缺失，Unity 可能尝试相近变体，所以没有粉色错误也不能证明匹配正确。Player 的 Strict Shader Variant Matching（严格着色器变体匹配）设置可在找不到精确匹配时使用错误着色器并记录诊断；它检查的是局部状态及全局覆盖后实际生效的组合，不是设计意图，也不会补回缺项。[17] 若请求本就错了，单凭画面异常仍不能断定发生了剥离。

接收这份候选时，应限定平台、渲染管线、材质及 Shader pass（绘制阶段），核对所需状态的有效关键字与保留途径，再在目标 Player 中检查普通与强化状态。保留更多组合会增加构建负担，应按需求选择；一次走通也不覆盖未触发的状态或其他平台。这是未执行的检查建议。

## 测试人员拿到的必须是同一份候选

假设修正后生成了候选 B，而刚才测试的是候选 A。即使二者代码提交相同，也不应覆盖同一个下载对象，让旧测试报告失去指向。

可以给每份候选一个稳定标识，并让下载入口、安装包中的版本显示和测试记录能够对应起来。文件清单与摘要有助于确认拿到的文件是否匹配预期；摘要可以理解为按文件内容计算的指纹，但它本身不证明文件是谁构建的，更不证明游戏可玩。

接收说明也不必写成庞大的表。对新武器试玩，简洁地说明这份包面向哪个平台、包含哪项改动、使用哪个测试环境、如何进入测试关卡，以及哪些检查没有完成，就比单发一句“最新包好了”有用。

软件供应链标准 SLSA 的 v1.2 构建来源格式，将产物、构建定义和本次执行信息分开；验证还涉及摘要对应、签名、可信构建者和预期参数。[5][6] 这可作为来源记录的技术参照，但不是“有摘要就安全”，也不是游戏测试已经通过的凭据。本文没有实现该标准，更没有断言上述雇主采用它。

### 测试时崩溃了，同名符号文件还不够

候选 B 如果在新武器试玩时崩溃，接下来要交付的就不只是安装包。调查者可能需要当时加载的程序模块及其调试符号：在这里限定的 Windows 原生程序场景中，PDB 是保存调试信息的程序数据库文件，帮助调试器把编译后的指令与函数、源码位置等联系起来。它不是崩溃原因的说明书。[10]

应先确认崩溃时实际使用的 EXE 或 DLL 模块，再找该模块对应的 PDB。另拿一份“最新”的程序和与它匹配的符号，不能代替候选 B 的材料。Microsoft 的转储调试文档要求二进制和符号对应转储创建时的版本与构建；缺少某些信息时，能调查的范围也会受限。[11]

怎样区分两份同名的 `Game.pdb`？LLVM 8.0.0 的原生 PDB 格式文档说明，链接器会在 PDB 和可执行模块的 CodeView 调试记录中写入对应的 **Guid** 与 **Age**：前者是标识符，后者记录 PDB 的写入次数；增量链接可能沿用 Guid 并增加 Age。该关联需要核对两个字段，不是只核对文件名。[12]

继续作一个未执行的示意：已经确认 B 的模块要求标识 K、Age 4，归档里却有 K/3 与 K/4 两份同名 PDB。K 只是这里的抽象标签。K/3 不符合这个匹配条件；K/4 满足两字段，只说明这一步关联成立。它不能认证文件来源，也不保证私有变量信息齐全、调用栈完整或已经找到根因。公开符号与私有符号可以拥有相同的匹配身份，却提供不同程度的信息。[13]

因此，分发候选 B 时应让对应模块和符号都能被找回，而不是只保存源代码提交号，事后再编一份同名文件。调查记录也应区分“还没找到正确模块”“符号不匹配”和“匹配后仍缺信息”。这是交付建议，没有实际读取崩溃转储或运行调试器；上述格式规则不推广到 Portable PDB、DWARF 或其他平台。

## 绿色构建之后，还要验证交付给谁、用来做什么

持续集成页面的绿色通常反映已配置步骤的结果。如果只编译了程序，它不会凭空证明资源齐全；如果安装检查被跳过，它也不会证明接收者能正常安装。

对内部试玩，可以和测试团队约定一个小而明确的接收过程：从实际分发入口取得候选 B，在目标测试环境安装并启动，进入约定关卡，确认新武器资源可用，再执行能区分新旧规则的操作。具体期望行为由玩法和测试人员定义，不由构建工程师仅凭文件时间决定。

这是一段快速发现交付阻断问题的检查，不替代完整回归测试。若只完成启动而尚未验证武器行为，就如实交代；若服务无法连接，应区分是包本身问题还是测试环境受阻。跳过、受阻与通过不能混成一个结论。

如果 B 只改变包装或签名，能否沿用 A 的部分结果，要看受影响范围与原检查目的。既不必武断地每次全部重测，也不能凭“只是包装”自动继承全部结论。安装、升级和启动本身就可能是包装相关的检查。

同样，内部试玩包获准分发，不等于可直接提交商店或部署正式服务。Riot 的高级中央发布岗位明确涉及客户端、服务器、服务、内容、配置和跨团队发布协作。[7] 它表明产品交付可能横跨多个系统，但不意味着一个普通构建岗位必须包办所有系统，更不是职位名称赋予了公开发布权限。

## 把一次救火变成下一次能重复的交付

回到新武器场景，真正有价值的结束并不是“删缓存后绿了”。更完整的结果应是：团队知道旧数据为什么被复用，依赖规则已修正，新的候选可以明确识别，测试人员确实针对这份候选检查了预期行为，未完成的范围也有交代。这里描述的是理想的处置过程，不是本文已经取得的实验结果。

构建工程师在其中连接了工具作者、玩法程序和测试人员：工具作者说明真实输入，构建工程师让变化触发正确工作并可靠分发，测试人员判断交付对象是否符合需求。失败时，工程师既要能定位具体任务，也要能告诉接收者“哪里尚未完成、现在哪份包可以用”。工具选型和自动化技巧都服务于这个目标。

最后，要谨慎使用“可重复构建”这个承诺。能够再次运行流程、产出相同游戏内容、得到逐字节相同的文件，是不同层次。时间戳、签名或其他变化可能影响字节；相同代码也可能仍受外部输入影响。应明确想保证哪一层，再设计相应检查，不能凭一次成功宣布位级复现。

本文没有运行构建或发布实验，也没有测量速度与成本。它给出的是一个从依赖到接收的工作思路；供应链安全实现、商店认证、跨平台工具链、远端资源更新和完整服务部署仍需各自的专门方案。
