# Zstandard旧资源包为什么还需要配套的压缩字典

一份旧关卡包已经下载完整，加载器却还需要另一个文件才能解开它。资源打包程序员找到同名的 `assets.dict`，发现它刚被新版构建重新生成过：旧包还在，新字典也在，这算不算输入齐全？

不一定。对于**确实需要旧字典解码的包**，文件名相同不能代替字典配套关系。Zstandard 支持不使用字典的压缩，也支持使用字典；本文只讨论后一种资源交付问题，以固定的 Zstandard v1.5.7 文档和接口为依据，不讨论字典训练方法或压缩率。

## 字典是解码输入，不是可随时丢弃的缓存

压缩字典可以提供压缩数据之前的历史内容，供解码时的序列引用。格式化字典还可以携带熵编码表。因此，需要字典的帧不能只靠自己的压缩字节恢复内容；解码器还得拿到配套字典。官方解码接口也明确要求使用与压缩时相同的字典。[1][2]

这里的字典并不都来自训练工具。Zstandard 既支持带头部、字典 ID 和熵表的格式化字典，也支持直接使用一段内容的 raw-content 字典。后者没有那套字典头和 ID。不能把“没有训练器生成的字典文件”理解为“这份压缩数据没有外部字典依赖”。[2][3]

回到关卡包。假设旧包需要字典 D旧，后来打包工具生成 D新，并用它覆盖了同名文件。旧包下载成功只能说明包已经取得，不能说明 D旧 仍然可用。这个例子尚未制作成真实压缩文件，也不预言传入 D新 后一定报哪一种错；要指出的是：**交付了新字典，并没有交付旧包所需的旧字典。**

## 帧里的字典 ID 是线索，不是字典本身

一个自然的改法是让加载器先读帧里的字典 ID，再找对应字典。这比只猜文件名更有用，但仍要分清它能回答什么。

首先，帧可以不提供字典 ID。格式规定，ID 字段缺省或取值为 0 时，帧可能需要字典，也可能不需要；解码器必须通过其他途径知道该用哪份字典。读取帧 ID 的 API 返回 0 还可能意味着头部数据不足或输入不是 Zstandard 帧，不能把这一个返回值统一解释成“可以不传字典”。[1][2]

其次，非零 ID 不是字典所有字节的内容摘要。格式化字典的 ID 可以在生成时指定；固定版本的解码实现会比较非零帧 ID 与所用字典 ID，并拒绝这种编号不匹配，但这项比较并没有逐字证明两份字典内容相同。[3][4]

所以，ID 可以帮助加载器选择候选字典、发现部分错配，却不能替项目保存准确的包与字典关系。尤其不能认为：“ID 相同，所以把旧字典替换为新文件也没有关系。”

## 旧包仍可加载，就要保住它的解码输入

对这个游戏自有资源包，打包与加载双方需要约定：旧关卡包依赖哪份字典，以及客户端从哪里取得那份准确内容。可以让受控的包描述关联一个不可随同名文件覆盖而改变的字典版本或内容身份；如何表示和校验这种身份是项目自己的交付设计，不是 Zstandard 帧内置的下载协议。

重要的不是再加一个字段，而是让它实际约束选择：加载旧包时应取得 D旧，不能在找不到它时随手改用“最新的 `assets.dict`”。仍受支持的旧包若确实依赖 D旧，就不能只因为 D新 已生成而删除 D旧。具体何时允许淘汰旧包和字典，需要跟项目的内容保留政策一起决定。

如果加载器只看到了没有字典 ID 的帧，也应回到这份配套约定，而不是把缺少线索当作没有依赖。反过来，项目明确采用无字典压缩的资源，不需要为了这个例子强加字典文件。

## 解码完成之后，仍要认出这是哪份资产

字典配套、压缩数据解码、游戏接受资产，是相邻但不同的检查。拿到配套字典解决了解码输入问题；解码成功不代替关卡格式、资源版本以及“本次本应加载哪一份关卡”的检查。

Zstandard 帧还可以携带内容校验和，用于检测内容损坏。它是对解码内容计算的 xxHash64 的低 32 位，而且是可选字段，不是可信发布者认证。不能用“校验通过”代替项目所需的来源与资产身份判断。[2][5]

排查旧包的问题时，先确认包究竟是否需要字典，再追到它对应的准确字典内容，比反复替换同名文件更能定位责任。本文没有声称错误字典总会被拒绝，也没有声称它总会静默产生错误内容；具体结果不能只从“文件名相同”或“编号相同”推出。
