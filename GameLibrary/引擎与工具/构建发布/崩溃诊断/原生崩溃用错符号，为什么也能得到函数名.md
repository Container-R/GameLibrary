# 原生崩溃用错符号，为什么也能得到函数名

同一个 Android 版本号有两次补包，里面都叫 `libplay.so`，也都支持 arm64。QA 收到崩溃回溯，把地址交给手边的符号工具，得到了「商店购买按钮」和源码行。但那个地址实际来自开门任务。**能查到名字，只说明这份候选文件能解释这个地址，不说明玩家运行过这份库。**

本文面向游戏构建发布、QA 与客户端程序。定位原生栈帧要分别确定三件事：**是哪份模块、这个地址在哪个坐标里、符号包能提供到哪一级**。一个结果即使有函数和行号，也可能在第一步就不可信。

## 先配对这一帧和发给玩家的二进制

崩溃报告里可保留原始栈帧、ABI、模块路径、报告类型及 Build ID。分发环节则要从**同一次链接产物**归档未剥离的库或分离的调试文件，并登记发布渠道、包或模块摘要、ABI、模块名和 Build ID。这样补包、渠道变体、同版本回滚，都不靠文件名或市场版本号猜。定位哪个包发出去通常由发布系统完成，不要求 QA 收集与崩溃无关的用户数据。

GNU 工具链说明，同一份 ELF 的原始文件、去符号版本和分离调试文件可以保留同一个 Build ID。[1] 它适合连接这三份产物，但不是当前文件字节的通用校验和，链接后的修改可能不改它。[2] 需要确认实际发货字节时，查发布清单的摘要或签名。三种情况要分开记：

| 模块身份 | 处理 |
|---|---|
| 报告和候选都有 Build ID，而且冲突 | 拒绝这一份候选；即使它提供名字也不能用来归因 |
| 同 ABI、正确发布变体且身份配对得到确认 | 再查地址与符号覆盖；身份一致不等于相对地址换算正确 |
| 一侧缺 ID，只有同名库或一个漂亮的函数名 | 标为「未核实」，不把猜测写成故障归属。尝试从实际发布包、严格的部署清单或对应的原始二进制建立配对 |

Android NDK 固定提交的 `ndkstack.py` 说明了为什么需要第三档：它的直读 ELF 候选在双方都有 ID 时拒绝冲突；一侧缺少时，有调试信息且名称相符的文件仍可能被采用。[3] 这是特定候选查找路径，不是所有 NDK 版本的承诺，也不是缺 ID 就一定能匹配。工具是否输出名字，和团队是否拥有配对证据，仍是两个判断。

## APK 的偏移不是给 PC 再加一次的数

先看报告格式。进程寄存器读出的绝对 PC 是运行时虚拟地址；单独交给读取 ELF 的符号器，可能查不到东西，也可能碰巧命中。若手头只有进程绝对 PC，应保留事发时的模块映射，按匹配的 `PT_LOAD` 段及其文件偏移求该模块的加载偏差，再转换到符号工具需要的 ELF 地址。不能把任意一行可执行映射的起点当成整份库的加载偏差。举例，若某映射已确认从模块虚拟地址 `0x6000` 开始，运行时映射起点处的一条指令，模块地址是 `0x6000`，不是 0。

而本文核对的 AOSP 原生回溯格式已把 `rel_pc` 写在帧的 `pc` 位置。模块直接从 APK 等容器加载时，还可能另写 `(offset 0x…)`，表示 ELF 在容器中的起始偏移；Build ID 又是另一字段。[4] 例如一行已经打印 `pc 00006000`，并带 APK 的 `(offset 0x200000)`，应保留 `0x6000` 作为这行帧地址，不把它加成 `0x206000`。在本文核对的 NDK 源码里，APK 偏移只用于找到嵌入的 ZIP 条目，送给符号器的仍是独立的帧 PC。[3] 其他格式（比如只收绝对 PC 的 SDK）先查字段定义，不照搬这里的数字。

## 用错库照样能查到一行

在 GNU/Linux x86-64 做一个最小反例：两次编译均生成 `libplay.so`，把不同函数放在同一个 ELF 虚拟地址 `0x6000`。用 `addr2line -f -e 候选库 0x6000` 查文件。这个命令并没有收到原始帧的 Build ID，因此不能替你拒绝错误候选。

| 用来查同一地址的文件 | 身份判断 | 真实工具返回 |
|---|---|---|
| 发布 A 的完整库 | ID 与 A 匹配 | `award_room_key`，`quest_room.c:42` |
| 同名同 ABI 的补包 B | ID 与 A 不同，应拒绝 | `refresh_shop_badge`，`shop_ui.c:94` |
| 缺帧 ID，或缺候选 ID | 只凭现有材料未核实 | 仍可得到 B 的函数和行号 |
| A 去掉调试信息，保留函数符号 | ID 与 A 匹配 | `award_room_key`，无行号 |
| A 的独立调试文件 | ID 与 A 匹配 | 回到 `award_room_key` 和 `quest_room.c:42` |

该试件用编译/链接得到的 ELF 地址测试真实的 GNU 工具输出，没有触发原生崩溃，也没有运行 Android、APK 解包或 NDK 符号工具。匹配、拒绝、未核实是额外身份检查的结果，不是 `addr2line` 自己给的认证。两次使用不同临时目录构建时，最初没有规范化编译路径，具体 Build ID 发生了改变；规范化路径后，在本机固定工具链上两次结果一致。不要用「源码相同」替代「同一次发布构建」。

Android 发布也要分清层次。官方文档中 `SYMBOL_TABLE` 可恢复函数名，`FULL` 再提供文件和行号。[5] 已确认匹配却只剩函数，先查导出的符号级别或第三方库是否有调试材料；不要为找行号，拿另一次调试构建的库替换。即便完整符号也不是每一帧必有唯一源码行：构建优化、内联、或采集端没有正确展开堆栈，都需要分别排查。

## 把错误配对纳入发布验收

为每次发布做一条从真实发布包到符号包的抽查：挑一个已知库和 ABI，用发布包确认模块身份，再用同构建产物解析代表地址。把预期覆盖写清楚，只要求函数的包和要求文件行号的包不共用一个失败判据。接着拿同名的另一份库作负对照，它应因身份不符而被拒绝，而不能凭能解出名字混过去。没有可靠 ID 或发布凭据的样本应落在「未核实」，不是失败后偷偷选一份看起来最近的版本。

日常排查可以在每个栈帧旁记三列：身份结论及配对依据、地址类型及转换来源、符号覆盖。若只有 APK 偏移，先找对库；若有正确的库但没有行号，查符号级别；若身份还未知，先保留原始帧和可追溯线索，不派给看起来最像的功能组。这样能把「没有查到」与「查到了另一个项目的位置」分开处理。
