# Horizon如何避免两类植被争用同一个候选点

一片林地要混合两类树。第一层负责甲类，第二层负责乙类，各自都有密度设置。分别看，两层都分布得不错；合在一起，却有两棵树落到同一个候选位置。问题可能不在随机数“够不够随机”，而在于两层是否各自认领了同一批位置。

《Horizon Zero Dawn》2017年的程序化放置讲义提供了一个具体思路：对具有相同放置尺度、使用相应候选模式的层，不只给每层一个“低于它就生成”的阈值，而是给它一个接收区间。讲义称这种方法为 **Layered Dithering（分层阈值筛选）**，并以双阈值和保存两个数值的密度图表达。[1] 本文用原创小例子解释这个选择，面向环境技术美术与放置工具程序，不提供完整 Decima 实现。

## 同一个测试分别通过，不代表两层能共存

先把场景缩到三个候选点。每个点已有一个用于筛选的数值 `t`，分别为0.2、0.5、0.9；这里不讨论怎样生成点，只规定两层面对的是**同一组点和同一组数值**。

假设甲层采用 `t<0.3`，乙层采用 `t<0.4`。这是示意条件，不是游戏参数：

| 候选点的 t | 甲层是否选择 | 乙层是否选择 | 结果 |
|---:|---|---|---|
| 0.2 | 是 | 是 | 同一点生成两份对象 |
| 0.5 | 否 | 否 | 空 |
| 0.9 | 否 | 否 | 空 |

两个判断都正确执行了，但它们的接收范围重叠。继续增加候选点数量，并不会自动消除这个逻辑重叠；重新换种随机分布，也不等于建立了两层之间的互斥关系。

这和“点之间距离够不够远”是不同的问题。一套候选模式即使已经保证了自己的点彼此分开，两个层仍可能同时认领其中同一个点。

## 把独立上限改成互不重叠的区间

仍保留甲层0.3、乙层0.4的区间宽度，但让它们接收不同的一段：

```text
甲层：0.0 ≤ t < 0.3
乙层：0.3 ≤ t < 0.7
其余：不放置这两类对象
```

现在0.2归甲，0.5归乙，0.9留空。同一候选点不再同时被两层接收。

这里的数值、从左向右安排区间的顺序，以及左闭右开的端点约定，都是本文为了讲清机制自行规定的。讲义原图给出了相邻的颜色区间和双阈值测试，但没有公开足以确认所有端点、累加和超额处理分支的着色器代码，不能把这段示意写成它的逐行复现。[1]

互斥的理由也不神秘：甲要求 `t<0.3`，乙要求 `t≥0.3`，同一个数不可能同时满足。这个理由依赖共享候选及其筛选值；若两层使用不同候选位置、不同数值或不同空间尺度，上面的证明便没有直接覆盖它们。

另外，区间宽度0.3不意味着三个候选里一定有30%被选中。有限点的数值分布会影响实际数量。例子只证明这三个点怎样归属，不把它当作密度统计、面积覆盖率或森林观感的测量。

## 美术调的是分布意图，不必逐棵认领

Horizon 的讲义把手工制作资产、放置数据和放置逻辑留给美术控制，再把规则整理成层。运行处理分为密度求值、候选生成、对象放置：最后一步才生成对象所需的变换等信息。[1][2]

这个分工对理解前面的区间有帮助。密度图不是已经摆好的一棵棵树，而是参与决定哪些候选应被接受的数据。若一条道路需要少树，应先看道路相关数据怎样影响接收条件；不必一开始就把每棵树从场景里手动删除。

我们可以据此提出一个工具检查例：保持候选模式不变，只在道路附近收紧甲、乙的允许范围，然后分别查看“密度输入改变了哪里”“哪些候选改变归属”“最终对象发生了什么变化”。这只是建议的排查顺序，本文没有修改真实地图或验证更新范围。也不能因为系统以局部稳定为目标，就推断任意参数修改都不会改变远处结果。

## 同点互斥，不是所有碰撞都解决了

假设甲树和乙树不再占同一个点，它们仍可能位于相邻的两个点。树冠很大、资产缩放不同，或放置方向变化时，两个对象的几何形状是否相交，仍是另一个问题。候选点归属不等于三维碰撞检测，更不等于玩家一定走得过去。

讲义明确将 **footprint（用于放置模式的占地尺度）相同** 与不同的情况分开：相同尺度讨论分层阈值筛选，不同尺度则标出读回与依赖问题。[1] 因此，不能把两类树的例子直接扩成“大石头、小草、树冠、手工建筑全部互不相交”的通用保证。

若项目希望灌木可以长在树旁，却不允许两棵大树挤在一起，也应该先写清这两种关系，再决定哪些层共享互斥规则。把所有层都排斥，可能反而破坏所需的自然叠置；全部独立，又可能保留不想要的重叠。这是工具规则与美术意图需要共同确认的部分，不是提高随机质量就能代替的决定。

## 少等结果，有时要多算密度

这种安排也不是免费午餐。为了知道某层的接收区间，流水线可能需要先求其他层的密度，即使那些层这次不输出对象。作者在讲义里明确说明了这部分额外工作，以及用它减少相关处理间刷新等待的取舍。[1]

因此，不应只统计最后生成了多少棵树来估算处理成本。更合适的比较是：同一输入下，求了多少层密度，生成了哪些候选，在哪些阶段需要等待或传递结果。本文没有运行 GPU，也不引用旧项目时间当成其他硬件的预算。

回到开头，最先要问的不是“为什么两次随机都挑中了这里”，而是“这两个层是否允许挑中同一个候选”。把对象分布、候选归属和几何碰撞分别说清，再选择需要共享的规则，才能判断问题该修在数据、筛选还是后续放置上。
