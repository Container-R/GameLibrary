# 换一台电脑后如何保持资产导入结果一致

同一张图片，在美术的工程里大小正确，交给同事后却变小了。项目没有报错，场景也能打开。遇到这种问题，先不要反复复制文件或删除缓存：源图片可能没有变化，丢失的是导入时选择的设置。

这篇文章面向维护环境资产管线的技术美术和工具开发者。读完后，你可以整理一份完整的资产交付清单，并设计一次“不借用作者缓存”的检查。这里讨论的是资产进入工程时如何保留制作决定，不涉及运行时的资源复制或多线程加载。

## 一份资产，不只是一份源文件

图片、模型和音频通常要经过导入处理，才能供引擎使用。源文件回答“交来的是什么”，导入设置回答“要怎样处理它”。例如，同一个模型可以采用不同的缩放设置；同一张图片也可能采用不同的尺寸或压缩设置。它们不应仅凭文件名相同，就被当成同一个交付结果。

可以把导入过程理解为：

```text
源文件 + 导入设置 + 工具版本 → 引擎可用的资源
```

这只是帮助排查问题的示意，不是“输入齐全就一定逐字节一致”的保证。自定义工具、外部依赖和平台差异，也可能影响结果。

整理项目时，应区分三类内容：

| 内容 | 例子 | 为什么需要区分 |
|---|---|---|
| 制作输入 | 源图片、模型、场景，以及它们依赖的文件 | 丢失后，导入器没有完整材料可处理 |
| 制作决定 | 导入参数、资源身份信息、自定义导入工具的配置 | 文件仍可能打开，但得到的结果可能不再符合原先要求 |
| 生成结果 | 导入缓存和其他可重新生成的数据 | 可以帮助加快工作，却不能代替前两类内容 |

第二类最容易被误删。一个文件由编辑器自动生成，不代表里面没有需要保存的决定。例如，Godot 4.6 在源资产旁保存 `.import` 文件，官方明确要求将其纳入版本控制；Unity 6.0 的 `.meta` 文件也包含资产身份和导入设置。[1][2] 两种文件的格式和具体规则不同，不应互换，但它们都说明：**判断能否忽略一个文件，要看它保存什么，而不是看它是不是自动生成的。**

## 先写清楚“交付正确”是什么意思

假设一张环境标识贴图用于场景中的指示牌。交接时只说“图片已提交”，接收者无法判断导入后的尺寸变化是否有意为之。更有用的说明是：“这张贴图需要按约定尺寸导入，使用它的场景应仍引用该资源；若要降低尺寸，请先调整对应的资产预算。”

例如，交接一张标识贴图时，可以一起提供源图片、项目配置、该图片的导入设置、场景及其资源依赖、所需插件和工具版本，并注明预期导入宽高。接收者按这些材料建立独立副本，再读取纹理尺寸和场景引用，而不是只确认图片文件已经收到。

不必为每份资产建立厚重的报告。先选真正影响使用的几项检查就够了：

- **要得到什么？** 比如导入后的宽高，或场景应使用哪份资源。
- **由什么产生？** 源文件、导入设置，以及必须配套的工具或插件版本。
- **在哪里检查？** 不只看导入面板，还要读取导入后的资源；必要时再检查使用它的场景。

纹理尺寸是本文已经有实验记录的例子。模型尺度、材质效果和动画轨道可以采用类似思路，但检查方式应另行设计；不能因为贴图检查通过，就宣布这些内容也已验证。

## 做一次不带旧缓存的交接检查

下面是可用于团队的检查流程建议，不是已经接入某个项目的自动化系统。

### 1. 准备一个独立副本

从版本库取出项目到新目录，获取项目实际依赖的资产，再使用团队规定的工具版本打开或导入。不要把作者机器上的导入缓存复制过去。这样才能检查，版本库里保留的输入是否足以重建资源。

所有清理操作都只针对这个测试副本。没有必要为了验证交接，冒险删除正在制作的工程数据。

新目录用于排除旧工程缓存；要验证机器之间的差异，还需在另一台机器或隔离环境执行同样检查。

### 2. 先看导入过程，再看结果

导入失败时，先查缺失文件、插件和工具配置；导入成功后，继续读取前面约定的属性。两者回答的问题不同：没有报错，只能说明流程走完，不能说明尺寸、引用或其他属性符合制作要求。

如果导入后的资源正确，还要确认场景实际使用的就是它。有些问题发生在资源引用上，而不是导入参数上。

### 3. 留下足够定位问题的记录

一次交接检查至少应能回答：用的是哪个项目版本、哪些输入和工具，预期结果是什么，实际读到什么。详细命令和日志可以保存到验证附件，不必全部挤进资产说明。

| 观察到的现象 | 优先查什么 |
|---|---|
| 导入阶段直接失败 | 输入是否齐全，插件与工具版本是否正确 |
| 资源能加载，但尺寸等属性不符合要求 | 导入设置是否遗漏，默认值是否替代了原设置 |
| 单独加载资源正确，场景里的结果不对 | 场景引用和依赖是否指向预期资源 |
| 数据属性正确，画面仍不符合要求 | 另做渲染与视觉检查，不要用尺寸检查代替画面检查 |

### 4. 从少量关键资产开始，再扩大检查范围

完整重建大项目可能很慢。可以先挑选容易受设置影响、又能代表实际交付方式的资产，检查它们及其依赖；同时保留完整干净导入的检查机会，避免局部检查一直漏掉某项依赖。

检查频率和覆盖范围需要结合项目规模决定，本文没有提供性能测试数据。工具升级后，应重新确认关键结果，不要假定旧设置在新版本中一定得到相同产物。

## 为什么“能打开”和“身份相同”都还不够

本库已有一个小型对照实验：使用同一张 16×8 的 SVG 图片，只改变交接时是否保留导入设置。保留设置的一份得到 32×16 的纹理，遗漏设置的一份得到 16×8。两份场景都成功加载。[3]

这就是这一检查值得做的原因。导入器可以用默认值完成工作，而默认值未必是作者的选择。此次记录中，两份资源的 UID——引擎用于识别资源的标识——也相同。因此，身份检查不能代替尺寸等实际属性的检查。

这不是要求每次交接都比较缓存文件的全部字节。团队首先需要确认的是资产能否按约定使用。若项目另有可重复构建要求，再增加相应检查；不要把这两种目标混为一谈。

## 最后应留下什么

完成检查后，交付物应包括源资产、需要保留的导入设置和身份信息，以及必要的工具版本说明。接收者应能在独立副本里重建资源，并核对约定的关键属性。

如果检查失败，修改的是缺失输入或不符合要求的设置，而不是把作者缓存补过去让错误暂时消失。缓存可以用于加速，不能成为只有作者机器才保存的制作依据。

如果问题发生在加载之后——例如修改候选配置却连带改变了正在使用的资源——那是另一层的对象共享问题，可选读[《编辑候选资源前，先分清哪些对象仍然共享》](../../../../research/source-notes/runtime-resource-sharing-boundaries.md)。它讨论内存中的依赖与请求，不改变本章对离线导入输入的要求。

## 验证附录：Godot 中的一次导入设置丢失实验

下面解释上述例子的来源。使用其他引擎的读者可以停在正文，不必掌握这些 API。

实验使用原创 SVG 和最小场景。先让编辑器生成合法的 `.import` 文件，再将 `svg/scale` 从默认的 `1.0` 改为 `2.0`，重新导入并确认纹理为 32×16。Godot 4.6 文档说明该参数控制 SVG 的导入缩放。[4]

随后从完整输入创建两个不含旧缓存的副本。两者共同文件内容一致，唯一差别是其中一份没有 `asset.svg.import`。各自完成导入后，再启动新的进程读取纹理尺寸和场景引用：

| 交接内容 | 直接加载的纹理 | 场景中使用的纹理 | 场景加载 |
|---|---:|---:|---|
| 保留缩放为 2.0 的导入设置 | 32×16 | 32×16 | 成功 |
| 遗漏导入设置 | 16×8 | 16×8 | 成功 |

这些数值来自现有归档，本次改写没有重新运行实验。原实验及同机独立复核记录均保留在验证附件。[3] 被测程序自报 Godot 4.6.3，但其与官方发行包及固定源码的精确对应关系尚未确认。因此，这里报告的是该本地程序的有限观察，不是对所有 Godot 4.6.3 发行包的认证结果。

实验只检查资源尺寸、类型和引用，没有验证 GPU 画面、导出包、显存性能或跨机器结果。它支持“遗漏导入设置可能不报错却改变结果”，不支持“提交某种文件就能保证所有资产完全复现”。

Godot 文件规则还要按版本使用：4.6 文档建议忽略 `.godot/` 缓存；该页注明这套忽略规则适用于 4.1 及以后，不能直接套到 3.x 或 4.0。[5]
