# 素材没变，导入规则改了，为什么还拿到旧资产

移动端图标在编辑器里显示 256 像素宽。你新增一份目录覆盖规则，把它改成 1024；素材原文件和全局规则都没动。隔离目录里从头导入，宽度已经是 1024，原项目却一直看到 256。清掉所有导入结果可以让这次正确，却不能告诉你下一次改规则时哪些资产又会过期。

本文面向资产管线开发者。这里检查一次增量导入要过的三个关口：资产有没有被重新考虑、缓存是否选了正确的版本、导入器生成的字节是否使用了同一份输入。若同事从新工作区开始就导不出预期结果，先检查[换一台电脑后如何保持资产导入结果一致](换一台电脑后如何保持资产导入结果一致.md)；本文检查的是一个已经能正确导入的工作区改变规则后会怎样。

## 先确认旧尺寸是不该出现，还是规则本来就允许

给复现用的素材写下规则优先级。例如，目录覆盖高于全局设置，值指定最长边上限，源图本来是 1024×768，因此两条规则确实会产生不同尺寸；样本没有更高优先级的单资产设置。这意味着新增覆盖后，目标平台应该得到 **1024 像素**。不要只断言冷、热构建相同：如果两边都错误解析成 256，二者也会一致。

还要区分「新素材的默认值」「现有素材未固定时使用的默认值」与「强制覆盖现有值」。如果导入器第一次把默认 256 写进每个素材的配置，后续仍保留 256 可能是预期；要改既有资产，就需要明确迁移配置或把规则升级成强制项。若你在 Unity 6.0 的预处理器里只在 `importSettingsMissing` 为真时赋值，文档将此条件定义为素材没有随附 `.meta` 文件，并不等于每次重导入都重套默认。[1]

## 把发现变更和查缓存分开排查

**第一个关口：调度看见了什么。** 如果任务只依赖源图与全局规则，新增一份此前不存在的覆盖文件不会改动这两份输入。旧计划甚至不安排这张图，后面的缓存比较做得再对也无济于事。解决办法之一是把正确的规则搜索范围做成可追踪输入：例如在调度前重算负责该目录/平台的规则索引，让图标任务依赖相应的细分索引，并保证新增、删除、改名和优先级修改能更新该索引。也可用显式清单替代隐式搜索。清单必须由实际扫描或已声明的写入流程产生；只把一个从不更新的清单挂进图里没有用。

**第二个关口：这次请求查的是哪个缓存键。** 即使手动让导入任务跑起来，只对全局规则做摘要仍会把 1024 请求看成 256 请求。应先解析该资产在目标平台的实际规则，再把生成字节所需的输入放进键。例如源文件内容、规则的规范化有效值、会改变输出的平台参数、导入器行为/格式版本及相关工具版本。规则的来源路径可以记入诊断；只有当路径本身会影响产物（例如它决定相对引用的解析）时，才必须进入键或解析成已经包含的输入。若目录覆盖和全局规则恰好都给同一个有效值、导入过程也只消费这个值，覆盖新增可被发现而不必强制重生相同字节。全库哈希虽然简单，但规则一动连不消费它的音频也全失效；按资产类型、目录和平台缩小依赖可保留正常命中。

Unity 6.0 的 Asset Database 区分导入前已知的静态依赖与导入时识别的动态依赖。[2] 对自定义规则，一种接法是在导入之外解析并用 `AssetDatabase.RegisterCustomDependency` 注册变化的哈希，导入器内部通过 `AssetImportContext.DependsOnCustomDependency` 声明消费同一名称；更新后还需确保刷新或重新导入实际发生。配置本身若是导入产物，则评估 `DependsOnArtifact`；具体用哪个接口，取决于消费的是源文件、产物还是项目状态。[3] 这些接口不会替项目决定规则优先级，也不会自动知道任意目录里新增了什么覆盖。

**第三个关口：生成和键使用的是同一份输入吗。** 如果导入器先用 256 计算键，执行时却重新读取已变成 512 的规则，它可能把 512 的结果放在 256 的键下。下一次请求原本的 256，会命中错误的 512。可以让执行过程直接消费解析好的不可变设置；对源文件和其它输入也要使用同一快照，或检测到变化后丢弃这次输出并重试，不要发布到缓存。Bazel 5.4.1 的远程缓存文档同样提醒了构建期间输入改变所造成的错误结果风险。[4] 如果导入字节已正确而游戏仍显示 256，再检查打包清单是否取了这次产物的路径或摘要，不要重复调整导入规则。

## 用同一素材做一次冷、热对照

1. 只用 256 的基础规则预热。记录源图摘要、规则选择、调度状态、缓存键、命中与否和实际导入宽度；选一个不消费该规则的音频作为对照。
2. **只新增**优先级更高的 1024 覆盖。先原地构建，再用同版本、同平台、同配置与隔离缓存从头构建。直接读输出尺寸和摘要，不靠编辑器缩略图。断言两边都是 1024，且音频不因贴图规则变化重建。
3. 删掉覆盖复跑，预期回到 256。若有效规则重新成为先前的 256，命中以前正确的 256 产物也可以；关键在于任务先重新判断了适用规则。再试同名但无关的元数据，确保落在合理的失效范围以内。

另一个试件直接运行 GNU Make 4.4.1 和 Pillow 13.0.0。只依赖旧规则的构建图在新增覆盖后跳过精灵任务，热构建仍输出 256×192；同配置冷构建输出 1024×768。改为在每次启动 Make 前解析规则，仅当有效值变化才更新清单，让任务依赖并读取这份清单。此后新增覆盖产出 1024×768，移除后回到 256×192，中间的无变化构建跳过精灵任务，音频对照的文件内容和修改时间均不变。这是构建调度与真实图片尺寸的验证，不是内容寻址缓存。

在附录的缓存模型中，使用仅含全局规则的键时，新增覆盖后热跑命中旧 256，冷跑生成 1024；先解析实际规则则热跑和冷跑同为 1024，音频继续命中。冻结输入的独立对照也复现了「同一个 256 键」如何返回 512 或正确的 256。这里的模型独立验证缓存决策，不等同于 Unity 原生测试。
