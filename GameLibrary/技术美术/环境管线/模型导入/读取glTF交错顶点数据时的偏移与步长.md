# 读取glTF交错顶点数据时的偏移与步长

你写了一个模型处理工具，从 glTF 文件中读取顶点位置。文件能够打开，二进制数据也足够长，可读出的第二个顶点却成了 `(0,0,1)`，后面甚至出现了本不属于模型的数值 `99`。这不一定是美术导出损坏了文件：读取器可能从正确位置开始，却按错误的距离寻找下一个顶点。

本文面向编写模型检查、转换或导入工具的程序员，以及需要排查数据布局的技术美术。需要知道字节、数组下标和三维坐标；不要求已经熟悉 glTF。我们用四个顶点解释三个问题：从哪里开始读、每次向后走多远、读到哪里必须停。若你只负责模型外观制作，不必先掌握这些字段才能与导入工具的维护者合作。

## 先看想得到的模型，再看它怎样存储

例子是位于 `z=3` 平面的一个矩形。四个顶点的位置和法线如下。**法线**是描述表面朝向的向量，这里都指向 +Z。

| 顶点编号 | 位置 | 法线 |
|---:|---|---|
| 0 | (1,2,3) | (0,0,1) |
| 1 | (5,2,3) | (0,0,1) |
| 2 | (1,8,3) | (0,0,1) |
| 3 | (5,8,3) | (0,0,1) |

用索引 `(0,1,2)` 和 `(2,1,3)` 把它们连成两个三角形。索引不是新的坐标，而是“取第几个顶点”的编号。这样，两个三角形可以重复使用顶点1和2。

这个小模型采用一种**交错存储**：每个顶点的位置和法线放在同一条记录中，而不是先放完全部位置，再放全部法线。为了让误读容易识别，每条记录还故意加了一个值为99的填充项。

```text
一条顶点记录，共28字节：
[ 填充99：4字节 ][ 位置x/y/z：12字节 ][ 法线x/y/z：12字节 ]
```

其中每个数都按32位浮点数保存，占4字节。每个位置或法线由三个分量组成，合计12字节，但相邻两条位置之间相隔28字节。**元素大小**回答一次要读多少，**步长**回答下一个元素从哪里开始；交错布局里二者通常不同。

这是本库已有的小型教学输入，不是某个商业模型。本文重新讲解它的布局和地址计算，不提供通用 glTF 解析器。

## 三层描述各自回答一个问题

glTF 用 JSON 描述模型结构，实际数值通常存于二进制数据中。读者会遇到 `buffer`、`bufferView` 和 `accessor` 三个名称。先把它们理解为三层说明，而不是三份重复的数据。[1]

- **buffer：字节数据。** 告诉你模型引用了哪份二进制数据及其声明长度。它不直接说明某个数字是位置还是法线。
- **bufferView：数据中的一段。** 指定从 buffer 的哪一个字节开始，连续取多少字节。本文简称 view。
- **accessor：这一段数据的读法。** 指定元素类型、数量和在 view 内的起点，例如“从这里读取4个由三个浮点数组成的位置”。

一个 buffer 可以包含多个 view；一个存放交错顶点的 view 又可以供位置和法线两个 accessor 使用。注意这里有两种不同的偏移：view 的偏移从 buffer 起点算，accessor 的偏移从 view 起点算。

本例的 buffer 总长160字节，安排如下。所有区间都左含右不含，例如 `[16,128)` 包含字节16到127。

| buffer中的区间 | 用途 | 长度 |
|---|---|---:|
| [0,16) | 前缀，不是本例顶点数据 | 16字节 |
| [16,128) | 4条交错顶点记录 | 112字节 |
| [128,140) | 6个无符号16位索引 | 12字节 |
| [140,160) | 尾部，不属于上述两个view | 20字节 |

这不是 GLB 文件头的示意图；表里的位置都相对于已取得的 buffer 字节数据。不要把容器文件起点和 buffer 起点混为一谈。

## 把字段翻译成一次实际读取

本例顶点 view 的 `byteOffset=16`、`byteLength=112`、`byteStride=28`，分别表示起点、长度和相邻记录的步长。两个 accessor 的读法是：

| 字段 | 位置 accessor | 法线 accessor |
|---|---|---|
| 关联的view | 同一个顶点view | 同一个顶点view |
| `byteOffset` | 4 | 16 |
| `componentType` | FLOAT，数值标识5126 | FLOAT，数值标识5126 |
| `type` | VEC3，即三个分量 | VEC3 |
| `count` | 4个元素 | 4个元素 |

第0个位置从 buffer 字节 `16+4=20` 开始，读取12字节。下一次读取的起点比本次起点后移28字节，而不是只跳过刚读完的12字节。第 `i` 个元素的地址因此是：

```text
buffer内起点 = view.byteOffset + accessor.byteOffset + i × stride
```

`i`从0开始，小于 `count`。对本文有 view 的普通属性，`stride` 来自该 view 的 `byteStride`；没有这个字段时，按紧密排列的元素大小推进。[2]

将四个编号代入，可以得到完整的对照：

| 顶点编号 | 位置起点 | 位置读取区间 | 法线起点 | 法线读取区间 |
|---:|---:|---|---:|---|
| 0 | 20 | [20,32) | 32 | [32,44) |
| 1 | 48 | [48,60) | 60 | [60,72) |
| 2 | 76 | [76,88) | 88 | [88,100) |
| 3 | 104 | [104,116) | 116 | [116,128) |

glTF 的多字节分量采用小端序；本例要按小端32位浮点数解释每组12字节，而不是依赖程序运行机器的默认读法。[1] 从 buffer 中取对字节，再用正确类型解释，才会得到开头那张坐标表。

## 为什么没有越界，也会读错顶点

假设读取器知道第一个位置在20，却认为每个位置占12字节，所以后面依次从32、44、56读取。它会得到：

| 错误起点 | 被当成位置的三个数 | 实际来自哪里 |
|---:|---|---|
| 20 | (1,2,3) | 第0个位置，恰好正确 |
| 32 | (0,0,1) | 第0个法线 |
| 44 | (99,5,2) | 第1条记录的填充，以及位置的前两个分量 |
| 56 | (3,0,0) | 第1个位置的最后分量，以及法线的前两个分量 |

这四次读取都还在顶点 view 内，也都能解释成浮点数。因而“没有越界”“没有崩溃”“读取到了三个数”都无法证明拿到的是位置。

遇到这种情况，先打印每个元素的**绝对起点、类型和读出值**，与一份可辨认的小模型逐项比较。若只看最终画面，几个错误可能互相遮掩；若只看文件长度，又根本没有检查读取含义。这里应修复的是步长解释，不是让制作者反复导出同一个正确文件。

## 长度检查必须同时尊重view和buffer

另一种错误是声明的 view 太短。即便整个 buffer 还有剩余数据，也不能越过 view 去读取后面的内容。[2]

要计算一个 accessor 需要多长的 view，先找到最后一个元素的起点，再加上这个元素本身的大小：

```text
view内所需末端 = accessor.byteOffset
              + (count - 1) × stride
              + element_size
```

这里 `count` 为正数，末端仍按“不包含该字节”的方式计。最后一项是元素大小，不是步长；读完最后一个元素后，不必再额外要求一整条记录的余量。

本例中：

- 位置需要的末端是 `4 + 3×28 + 12 = 100`，所以它需要 view 内至少100字节。
- 法线需要的末端是 `16 + 3×28 + 12 = 112`，刚好到顶点 view 结束。

如果把顶点 view 的声明长度从112改为108，位置仍在范围内，最后一个法线却超出4字节。整个 buffer 仍有160字节并不能让这个声明变得正确。

读取前还要检查 view 自身是否落在 buffer 的声明范围内，以及实际取得的数据是否足够。对于本文这种普通数据，可以分别核对：

```text
view.byteOffset + view.byteLength <= buffer声明长度
accessor所需末端 <= view.byteLength
```

实现时先检查字段是否合法，再做地址运算；使用固定宽度整数的语言还要防止加法和乘法溢出。不能让一个溢出后变小的末端值蒙混通过范围检查。

范围正确也不是所有格式要求都满足。以本例4字节浮点分量为例，view 偏移与 accessor 偏移要**分别**满足4字节对齐，而非只检查二者相加的结果。顶点步长还受规范约束，例如它必须容得下一个元素；两个顶点属性共用 view 时，需要声明步长。本文28字节的布局满足这些条件，索引 view 则不使用顶点步长。[2][3]

## 读取位置以后，还要按索引恢复三角形

本例索引从 buffer 字节128开始，共6个无符号16位整数，每个占2字节，不交错。其元素起点依次是128、130、132、134、136、138，值为 `0,1,2,2,1,3`。

glTF 将同一个索引用于该图元的全部顶点属性。这里的**图元（primitive）**可以理解为按同一种连接方式组装的一组顶点；本例连接方式是三角形列表。因此索引2同时选择位置数组第2项和法线数组第2项，不能另给它一套独立法线编号。[4]

恢复两个三角形后，可以核对它们是否与预期矩形一致：坐标都在 `z=3`，X范围为1到5，Y范围为2到8；两个三角形的绕序都朝 +Z。**绕序**是三角形三个顶点的排列顺序，与读出三个坐标本身不是一回事。

还应检查索引是否在属性数量允许的范围内，以及各属性的数量是否一致。若两个角点位置相同但法线或UV不同，不能仅按位置合并记录；索引引用的是整组属性。[4] 本例没有这些接缝，只说明阅读和检查索引时应保留这种含义。

## 调试时，区分三类结论

完成上面的计算后，你可以把问题分得更清楚：

| 检查对象 | 本例中的问题 | 接下来查哪里 |
|---|---|---|
| 数据范围 | view只有108字节，法线需要112字节 | 文件声明、生成该声明的代码 |
| 数据解释 | view足够，却每12字节找一个位置 | accessor偏移、view步长、分量类型和字节序 |
| 几何用途 | 数据可读，但索引或属性不是预期模型 | 图元属性关联、索引顺序、模型预期 |

这三类不能都用“文件损坏”概括。尤其是格式正确并不等于内容符合制作意图：一个完全自洽的文件，也可能保存了你不想要的模型。

本库旧版研究曾用这个小输入进行有限CPU读取和独立数值对照。这里保留足以手算的布局与预期，不把有限读取器当成生产导入器，也不要求读者先看运行日志。本文没有重新执行实验。

## 遇到稀疏属性，先找基底，再做替换

前面的逐项地址计算针对有 bufferView、无稀疏替换的普通属性。稀疏 accessor 则先确定元素的基底来源，再替换其中指定的元素；不是把补丁数值加上去。[5]

用旧版研究的另一个小例子手算：基底为 `[10,20,30,40]`，从0开始编号，要替换的元素编号为1和3，对应新值为7和9。最终得到 `[10,7,30,9]`，而不是相加后的 `[10,27,30,49]`。这里的1和3是在 accessor 中选择待替换元素，不是前文用来连接三角形的索引流。

如果这个例子不使用扩展提供元素，也省略基底的 `bufferView` 和 `byteOffset`，就从四个零开始，替换后得到 `[0,7,0,9]`。即便 buffer 的其他位置仍保存10和30，也不能擅自把那些字节当作基底。[5]

稀疏索引和值分别来自自己的 view，各自有偏移、长度和对齐要求；索引还须严格递增且小于 accessor 的元素数量。整个 buffer 够长，不意味着其中某个 view 可以越界。[5] 这里仅解释替换含义，不把前文普通属性的读取公式变成完整稀疏解析器。这个标量例子也不是上面矩形的引擎导入结果，本次没有执行它。

关于详细规则和旧有限读取器的适用范围，可选读[稀疏 accessor 来源说明](../../../../管理档案/来源笔记/gltf-sparse-accessor.md)。矩阵、压缩扩展、外部资源加载、蒙皮和动画仍需另作处理。对暂未支持的合法形式，应明确报告“不支持”，而不是把它们一概称为非法文件。

## 导入之后，应按目标表示的规则比较

源 buffer 的布局不一定就是引擎或GPU最终使用的布局。某个引擎导入后可能重组数据或转换表示；那是下一层问题，不能由本文的28字节步长推出。

比较时应先确认目标表示的约定，再决定哪些值必须保持一致。例如，若目标采用不同的三角形正面绕序，就应按明确的转换规则核对索引与正面含义，不能只因索引数组不再逐项相等便判定模型损坏。属性精度或包围盒处理也要分别说明；一个小样例观察到的差异，不能自动成为所有网格的容差标准。

这是对导入结果的检查建议，不是本章已完成的引擎验证。既不能要求所有阶段逐字相等，也不能没有依据地把任何差异都归为“引擎优化”。先确认目标规则，再检查该规则是否被正确执行；本章的交错读取主线仍只解决：**按glTF声明读到正确的属性，并知道每一次读取为什么合法。**
