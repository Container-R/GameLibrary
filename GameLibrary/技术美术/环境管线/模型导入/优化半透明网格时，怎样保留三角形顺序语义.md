# 优化半透明网格时，怎样保留三角形顺序语义

一个带彩色半透明面片的模型经过构建工具后，顶点位置相同、三角形一片不少，重叠处却变了颜色。关闭整个“网格优化”可以恢复画面，但也放弃了本来可能保留的顶点存储整理。问题在于：不同优化改变的数据不同，渲染器保证的排序粒度也不同。

本文面向维护模型导入器、资产构建和渲染接入的技术美术与工具程序。假定读者知道顶点属性、索引三角形列表和 draw call。我们要完成的是：在保持既有 source-over 外观约定的条件下，为每个绘制范围选择优化步骤，正确重映射共享数据，并用结构与渲染两级测试验收。这里的“保留”以优化前的合法运行时输入为基线，不意味着原有面序已经适合所有视角。

## 先分清三个会被叫作“顺序”的东西

设索引列表是 `0,1,2 | 3,4,5`，每组三个索引构成一个三角形。

- **面序**：把它改成 `3,4,5 | 0,1,2`，交换了完整三角形的先后位置。
- **面内角序**：把第一面改成 `0,2,1`，翻转了绕序，可能改变正反面剔除。`1,2,0` 虽未翻转绕序，也可能改变平面插值所选的 provoking vertex，即为整个图元提供某些不插值属性的顶点。
- **顶点存储顺序**：移动顶点记录，并把每个索引改成记录的新地址。只要每个索引位置仍引用同一份原始顶点数据，面序和面内角序都可以保持不变。

还有第四个更上层的顺序：引擎先提交哪个 draw call。一次 draw 使用的一段索引称为 **draw range，绘制范围**；常见的记录是索引起点、索引个数、材质和顶点域。同一材质可以有多个范围，一个大索引缓冲区也可以被多个 draw 分段使用。它与“整个网格”不是同一单位。

因此，检查结果应保留“原始面是谁、三个角依次是谁、属于哪个范围”的对应关系。只比较无序三角形集合，会把第一种变化吞掉；只比较索引字节，又会把合法的第三种变化误报成损坏。

## 为什么重叠处会变色

固定同一采样点的片段集合、着色输出、覆盖和测试结果。用 U 表示未预乘 RGB，α 表示 alpha，C=αU 表示预乘颜色。普通 source-over 将当前片段放到已有背景前面：[1]

```text
新预乘颜色 = C当前 + C背景 × (1 − α当前)
新 alpha   = α当前 + α背景 × (1 − α当前)
```

若 A、B 都通过测试，先画 A 再画 B，与先画 B 再画 A 的颜色差为：

```text
C先A再B − C先B再A = αA × αB × (UB − UA)
```

这是把上式展开两次得到的结果，原背景项相消。两层同色或其中一层 alpha 为零时可能看不出差异；不同颜色的重叠面则能揭露问题。这个结论要求参与合成的片段固定，不能用来忽略深度写入造成的片段丢失。

例如不透明黑底上，A 为红色、α=1/4，B 为青色、α=3/4。先 A 后 B 得到 `(1/16,3/4,3/4)`，反过来得到 `(1/4,9/16,9/16)`，最终 alpha 都是1。正确使用预乘表示仍得到各自的结果；[预乘与普通透明度](../纹理与材质/预乘透明度与普通透明度的混用问题.md)解决表示和混合因子的配套，不会让 OVER 变成可交换运算。

索引顺序怎样走到合成，还要看实际 API。Vulkan 1.3.296 的普通索引绘制从低索引缓冲区地址向高地址确定图元序；在同一 render-pass 实例的同一 subpass 内，同一 `(x,y,layer,sample)` 的混合和颜色写入按 rasterization order 发生。默认严格顺序对应图元序；主动选择 AMD relaxed rasterization order 是需要另行处理的例外。[2] 这说的是固定功能结果的次序，不是各个 shader invocation 必须串行执行。OpenGL 4.6 也明确区分 framebuffer 输出顺序与 shader 自行向存储资源写入的顺序。[3]

本文由此限定普通索引 triangle-list、常规固定功能混合路径。几何着色器、细分、mesh shader 或自定义存储写入若重新生成图元与合成过程，必须追踪它们实际产生的序列，不能直接把源索引当最终顺序。

## “引擎已经排序”通常只回答了上层问题

three.js r170 的普通 WebGL Mesh 路径是一个具体例子。渲染器先建立 render item 列表，默认透明比较器按 groupOrder、renderOrder、投影深度 z、对象 id 排序。z 来自对象或几何包围球中心，不是每个三角形的深度。[4]

多材质 Mesh 的 `BufferGeometry.groups` 会形成多个 item，但这些 item 使用同一个对象中心 z；单材质 Mesh 则只入队一次，不因为存在 groups 就自动拆开。在普通索引填充路径中，最终使用的范围为：

```text
start = max(drawRange.start, group.start（若有）, 0)
end   = min(drawRange.start + drawRange.count,
            group.start + group.count（若有）, index.count)
count = end − start
drawElements(TRIANGLES, count, indexType, start × bytesPerIndex)
```

这里的 start/count 单位是索引元素，传给 GL 的最后一个参数才是字节偏移。该调用链没有默认逐帧按相机重排三角形索引的步骤。[4] 所以，对象整体已从远到近，不代表同一 item 内部的透明面序可以任意改变。`DoubleSide` 透明材质的背面、正面两个 pass 也不是逐面深度排序。

glTF 的 primitive、场景树中的 Group 和 `BufferGeometry.groups` 也不应混用：该版 GLTFLoader 为每个 primitive 建立 Mesh/SkinnedMesh，多个结果再装进场景 Group；BLEND 材质会开启 transparent 并关闭 depthWrite。[5] 导入后再把这些 Mesh 合并成单一绘制单元，可能连原有的排序粒度都改变。即使合并时保持了各段内部面序，也要重新验证段与其他对象之间的交错关系。

这些是固定版本的默认实现。自定义透明比较器、`onBeforeRender` 重写索引、批处理或另一渲染后端，需要按同样的数据流检查，而不是套用 three.js 的结论。

## 给每个范围选择优化链

meshoptimizer 0.25 将相关工作拆成三种操作：[6]

| 操作 | 实际改变 | 保留既有 OVER 面序时的处理 |
|---|---|---|
| Vertex cache optimization | 调整三角形次序，提高重复顶点引用的局部性 | 未证明可重排的范围跳过 |
| Overdraw optimization | 继续调整三角形次序，寻求降低重复绘制成本 | 同样跳过；不能靠它绕开 cache 限制 |
| Vertex fetch optimization | 按首次引用顺序搬移顶点，并同步改写索引编号 | 可单独评估，前提是全部属性和引用一起映射 |

源码中，`meshopt_optimizeVertexFetch` 按递增索引位置访问原列表，首次见到某顶点时复制完整顶点记录，再改写当前位置的编号；它不移动索引位置。多属性流对应 `meshopt_optimizeVertexFetchRemap` 加各流的 remap。[7] 这就是“可以保序地整理顶点存储”的依据，而非“透明网格都不能优化”。

cache 与 overdraw API 都要求不同 draw-call ranges 分别处理。overdraw 的输入还必须是 cache 优化后的索引，参数 `1.05` 表示允许的顶点缓存效率退化程度，不是5%的颜色误差或帧时间保证。[6] 分范围是必要的调用边界，却不能证明范围内部的 OVER 可交换。

实际构建可按下表审批。每个范围记录合成方式、深度测试/写入、运行时排序粒度、VertexID/PrimitiveID 依赖及边界是否会被合并。

先将输入整理为完整三角形列表，并校验范围落在已定义的面边界、没有截断三元组，索引在绑定顶点域内有效。若多个 draw 引用同一索引缓冲区的重叠片段，不能把它们当互不影响的范围分别原地重排：改动一段也会改变另一 draw 的输入。应为有不同要求的使用者保留独立索引副本，或按最严格的保序要求处理共享片段。带 baseVertex 等顶点偏移的 draw 还须先将引用解释到正确顶点域，再生成映射。

| 运行时用途 | 可采用的起点 | 会改变判断的条件 |
|---|---|---|
| 顺序敏感 OVER，运行时直接使用此面序 | 保留每个三元组及其序列，只评估 fetch remap | 多流漏映射、外部顶点表或编号驱动着色仍会破坏结果 |
| 运行时确实重建逐面顺序 | 可以研究离线重排，但先证明最终序列等价 | 深度并列时若沿用输入顺序，离线换序仍可能改变结果；面身份表也须跟随 |
| 已验证的普通不透明/alpha-mask 深度路径 | 各范围 cache → 可选 overdraw → fetch | 共面深度并列、模板操作、编号依赖或 shader 副作用可能使顺序仍有含义 |
| 累加或顺序无关透明路径 | 按该路径的实际约定验证后选择 | 数学上可交换不代表浮点逐位相同；深度写入也可能改变参与片段集合 |

overdraw 优化偏向减少不可见片段工作，而普通半透明 OVER 往往需要保留多层贡献。把透明面近的先画，并打开深度写入来“省 overdraw”，会让后层被深度测试排除，改变的是画面需求，不是等价优化。另一方面，关掉深度写入只避免透明层互相封死，仍应测试既有不透明深度，也仍需处理透明层之间的合成顺序。

只凭工具名称或材质标签也不够。gltfpack 0.25 即使在材质优化后仍保留 BLEND，普通非空三角形网格也不会因此跳过 cache；`optimizeMesh` 执行 cache（压缩优先设置下用 cacheStrip）和 fetch remap，不调用 overdraw。[8] 更早的处理还可能合并兼容、同材质的 primitive，改变后续优化和绘制的范围。无有效 alpha 的材质可能先被改成 OPAQUE，所以“输入带 BLEND”既不证明其输出材质不变，也不证明面序受保护。这里核实的是固定源码流程，不是宣称每个透明输入都会产生可见错误。

## 面重排按绘制范围，顶点 remap 按共享顶点域

这是最容易在修复中再引入错误的地方。假设范围 T 是透明层，范围 O 是不透明框架，两者共同引用一个顶点数组和若干平行属性流。T 保序，O 可重排，并不意味着可以分别调用两次原地 fetch，然后把结果塞回同一个顶点数组。两个范围都可能把自己首次见到的不同顶点编号为0，第二次搬移会覆盖第一次所依赖的内容。

应先完成各范围许可的面序处理，再对**共享顶点域的所有使用者**建立一个映射 M。M 的方向明确为“旧顶点编号 → 新顶点编号”。简化步骤如下：

```text
for each draw range:
    if 本范围已批准改变面序:
        cache(range)
        if 已批准且有必要: overdraw(range)

references = 按既定顺序连接所有共享该顶点域的最终索引
M, usedCount = fetchRemap(references, oldVertexCount)

for each vertex attribute stream S:
    newS[M[old]] = oldS[old]          # 对所有已映射顶点
for each index buffer I in this domain:
    newI[k] = M[oldI[k]]
for each external table containing vertex references:
    用 M 改写其顶点引用
```

连接 references 只是为了决定一次统一的首次引用编号，不要求把多个 draw 合并成一次提交。每个 range 的索引起点、个数和材质边界仍保留。共享同一顶点域的 LOD、阴影索引或其他备用索引，也必须使用同一个 M；只考虑当前可见范围，可能把其他用途需要的顶点当成“未使用”删掉。[6] 若各范围确实拥有独立顶点副本，则可分别 fetch，代价是复制和更大的存储范围。

“全部属性”至少包括位置、法线、切线、UV、颜色、蒙皮权重和关节属性、morph target 的逐顶点数据，以及项目自定义流。关节属性记录要随顶点搬走，但其中的关节编号属于骨骼域，不能把其数值也当顶点编号套 M。外部表还要区别“按顶点下标排列的属性表”和“表中含有顶点引用的关系表”：前者搬行，后者改引用，有些表两者都需要。

如果着色器直接用 VertexID 作为业务身份，单纯搬移流仍不够。可以把稳定原始身份保存为属性或间接表并修改读取，也可以禁止这项转换。PrimitiveID 对应的逐面表同理；允许 cache 变序时要同步面映射。仅用 position 查找身份也不可靠，UV缝、硬法线和重合表面经常有相同位置但不同记录。

fetch remap 会返回实际使用顶点数，未被所传索引引用的顶点没有正常的新编号。[7] 若外部消费者还需要它们，应把那些引用纳入保留策略或明确保留相关顶点，不能把无效映射直接写到外部表。

## 验收要比较语义，并覆盖最终解码结果

**先做结构检查。** 在去重、量化或简化之前隔离本次转换，保存原始顶点和面身份。对保序范围，令 `oldOfNew` 为 M 在保留顶点上的逆映射，检查每个索引位置 k：

```text
oldOfNew[newIndex[k]] == oldIndex[k]
```

同时检查每个属性流 `newS[M[v]] == oldS[v]`、范围边界、材质归属和外部引用。这样允许编号变化，却要求每个面、每个角仍对应同一输入。若阶段包含去重，M 不再一一对应，应保存面角到源记录的关联，并按该去重策略证明完整属性和身份用途等价；不能硬造一个唯一逆映射。

对允许面重排的范围，可以比较带材质与完整属性的三角形多重集合及合法面映射，但仍保留面内绕序约束。重复面必须计数，不能用去重后的集合掩盖丢面。那些使用 PrimitiveID、平面插值或角身份的路径需要更强条件。

检查应做到最终上传或解码后的输入，而不只检查优化函数刚返回的数组。meshoptimizer 的 triangle index codec 保留面序，却可以循环旋转每面的三个角以改善压缩；这可能改变 provoking vertex。需要保持精确角序时，应采用保留序列的编码路径，或明确证明该旋转对当前着色没有影响。[6]

**再做渲染对照。** 建立三个输入：原始基线、仅 fetch 的保序版本、故意交换重叠异色面的正对照。三者使用相同的视角、线性工作颜色、混合状态、深度/模板状态、剔除、采样和材质数据。先用无光照常量色隔离混合，再恢复实际材质。交换正对照必须在覆盖相同采样点、两片段都参与时显出预期差异，否则测试可能根本没有覆盖顺序风险。

典型排查顺序如下：

1. 仅 fetch 就变形或变色：先检查多流、外部表、VertexID 及范围映射，再查最终解码。此时不应把问题直接归咎于面序。
2. fetch 对照一致，开启 cache 后仅重叠区域变色：比较原始面身份序列和最终 draw 提交。这是强线索，再固定状态复现，而不是仅靠肉眼定案。
3. 深度写入开关改变了缺面和遮挡：检查哪个片段不再参与；不要拿不同片段集合套前面的交换公式。
4. 随相机旋转，优化前后都出现切换或穿插：检查运行时排序粒度及几何交叉，先把既有排序缺陷与构建回归分开。

本文的原生结构实验用18个三角形运行固定 meshoptimizer 0.25。纯 fetch 的索引数值改变，但还原原始身份后逐项一致；cache 的真实输出确实改变了面序。两个范围共用顶点数组的反例也显示，逐范围覆盖共享数组会损坏先前范围，统一 remap 则保留两者。完整输入、命令和输出见[复现材料](../../../../管理档案/实验/透明网格顺序/README.md)。这些结构观察不估计目标设备性能。

另一个离屏对照实际调用 `glDrawElements(GL_TRIANGLES, …)`，在软件 OpenGL 光栅的线性 RGBA8、16×16单样本 FBO 中绘制两个全屏三角形。两面都取 alpha=1/2，清为透明黑，关闭深度测试和写入；RGB 使用 SRC_ALPHA / ONE_MINUS_SRC_ALPHA，alpha 使用 ONE / ONE_MINUS_SRC_ALPHA。这与前面 α=1/4、3/4的不透明黑底算例是两个输入。采样点 `(8,8)` 的实际 RGBA8 为：

| 输入 | 实际读回 |
|---|---|
| 先红后青 | `[64,128,128,192]` |
| 显式交换为先青后红 | `[128,64,64,192]` |
| 原生 fetch 后，仍先红后青 | `[64,128,128,192]` |

fetch 前后的完整16×16 RGBA读回也逐字节相同。这里确实运行了光栅和混合；交换两面是显式正对照，不是 cache 对这两个面的输出。它验证这些输入与状态下的区别，不是目标引擎、真实资产或物理 GPU 的性能测试，8位读回也不代替无限精度公式。

## 保留基线以后，再决定是否需要另一种透明方案

资产优化器只能保持或改变给定序列，不能让一个固定列表自动适合所有相机。整物体排序不能处理物体内部的层次；用三角形中心排序也可能在相交面或循环遮挡处没有一个能满足每个像素的全局次序。需要严格逐层 OVER 时，应评估更细排序、必要的几何切分或保留逐像素层信息的方案，并计入运行时更新和存储成本。

如果项目接受近似，可另行评估[加权顺序无关透明](../../../图形渲染/画面呈现/透明合成/加权透明混合不用排序，为什么仍不等于逐层合成.md)。它改变合成规则，不能当作保留既有 OVER 外观的等价补丁。

最后把外观验收和性能验收分开。纯 fetch 可能改善读取局部性，但动态逐面排序会不断改变访问顺序；按材质拆得更细可能改善排序粒度，也可能增加 draw 和数据管理成本。只在目标设备与代表资产上比较构建耗时、顶点/片段工作和帧时间，记录多个视角及波动，再决定是否保留优化。没有收益测量时，能批准的是“这项转换满足保真约定”，而不是“它一定更快”。
