# 用cgltf完整展开glTF稀疏属性

一个模型处理工具能打开 glTF 文件，也能找到 accessor，逐项读取却返回 false。改成批量读取之后，另一个问题又出现了：两个四分量元素究竟需要两个还是八个输出位置，补丁中的64究竟应保留为64，还是转换成64/255？

这些问题来自不同阶段。解析成功只建立结构；稀疏属性还需要确定基底、替换指定元素，并按分量类型转换数值。本文面向维护模型读取工具的程序员，假定已懂数组、字节和基本的 buffer/view/accessor 关系。普通字节寻址可先读[交错属性的偏移与步长](读取glTF交错顶点数据时的偏移与步长.md)。这里以 cgltf 1.15 的固定实现为对象，说明怎样得到一个完整的浮点输出数组，以及哪些输入不能直接走这条路径。

贯穿全文的例子是紧密排列的 FLOAT SCALAR 和 UNSIGNED_BYTE VEC4，不使用扩展提供元素；它们分别揭示基底来源，以及元素、分量和数值转换的区别。例子没有 mesh、skin 或引擎对象，不能从一般 accessor 的数值正确推断它已经满足具体顶点属性或蒙皮语义。

## 稀疏数据给的是替换元素，不是加法增量

accessor 描述一组有限的元素。SCALAR 每项只有一个分量，VEC4 每项有四个。sparse 描述其中哪些元素需要替换：目的编号来自 sparse.indices，新元素来自 sparse.values。它与三角形连接索引不是同一套编号。[1]

先看四个标量。若密集基底为 `[10,20,30,40]`，稀疏编号为1和3，新值为7和9，那么最后数组是 `[10,7,30,9]`。索引从0开始；7替换第二项20，9替换第四项40，不是分别相加。文件用稀疏表示，不意味着工具取得的最终数组也必须是稀疏结构。

基底不能从“buffer里碰巧有数”推断。accessor 有 bufferView 时，从引用的区域取得基底；没有该来源、也没有扩展另行提供元素时，从零开始，再执行 sparse 替换。因此同样的1、3与7、9，作用在四个零上会得到 `[0,7,0,9]`。即使 buffer 其他位置还保存10和30，也不能擅自取用它们。[1]

可以把展开理解为两遍：

```text
建立 count 个基底元素；没有元素来源则清零
对每个补丁 j：
    i = sparse.indices[j]
    完整元素[i] = sparse.values[j]
```

这是语义模型。实际实现可以直接把基底和补丁都解码进目标 float 数组；它仍必须保持“先基底、后替换”以及完整元素对应关系。

## 两个VEC4是八个分量

第二个例子只有两个 VEC4，每个分量以无符号8位整数保存。buffer 共16字节：

| 字节区间 | 数据 | 用途 |
|---|---|---|
| [0,4) | `[255,0,0,0]` | 基底元素0 |
| [4,8) | `[0,255,0,0]` | 基底元素1 |
| [8,9) | `1` | 被替换的元素编号 |
| [9,12) | 三个零 | 填充，不作为属性读取 |
| [12,16) | `[64,191,0,0]` | 新的完整元素 |

目的编号1选择第二个四分量元素，所以补丁写入输出数组的第4至7项，不是只改第1项。这个区别也决定容量：两个 VEC4 需要 `2×4=8` 个 float。若每个 float 占4字节，输出占32字节；8是接口所需的分量数量，32是分配内存时的字节数量，不能互换。[2]

稀疏表示可以节省源文件中的数据，但完整展开要为全部元素分配输出，而不是只为补丁数量分配。对很大的数组，这个内存代价需要在决定是否展开时考虑；本文的方法服务于后续接口确实需要完整 float 数组的工具。

## normalized改变数值，不改变元素结构

对于 UNSIGNED_BYTE，normalized 为 true 时，每个分量按 `c/255` 转为浮点数；省略或 false 时，浮点输出保留该整数的数值。normalized 不是“把四个分量的总和归一到1”，也不会重新分配元素数量。[1][2]

上面的同一份字节可以形成三个不同配置：

| 配置 | 输出元素0 | 替换后的输出元素1 |
|---|---|---|
| 有基底，normalized=true | `[1,0,0,0]` | `[64/255,191/255,0,0]` |
| 无基底，normalized=true | `[0,0,0,0]` | `[64/255,191/255,0,0]` |
| 有基底，normalized=false | `[255,0,0,0]` | `[64,191,0,0]` |

转换规则同样作用于基底和补丁。若先把基底除以255，却把补丁64、191直接写进浮点数组，输出形式看似一致，数值含义却混了两种编码。相反，raw 配置仍然输出 float，只是数值没有被缩放。

无基底的全零元素在一般 accessor 中解释清楚，不等于它是一组有效蒙皮权重。具体属性的合法类型、关节映射、权重总和等属于使用这些数值的下一层规则。

## 四个阶段分别解决什么

cgltf 1.15 把解析、资源取得、附加检查和读取分开。排错时应保留每阶段结果，不要只记录一次“加载成功”。[2]

1. **cgltf_parse 建立结构。** 它把 glTF/GLB 声明转成 cgltf_data。成功不表示外部 buffer 已加载，也不表示 accessor 已解码。成功创建的数据最终需要 cgltf_free 释放，包括后续步骤失败的退出路径。
2. **cgltf_load_buffers 取得数据。** 本文两组示例使用内嵌 data URI。实际项目若用外部文件，应按自己的资源加载约定处理路径和错误。取得数据后，仍须核对声明长度、所引用的 view 和 accessor 范围。
3. **cgltf_validate 提供附加检查。** 它不是输出生成器，也不能替代调用者所需的所有格式和资源检查。下节列出与这条展开路径直接相关的条件。
4. **cgltf_accessor_unpack_floats 生成数组。** 它先转换基底或清零，再把 sparse 指定的完整元素写到目标位置。只有完整展开成功后，输出才可交给下游。

逐项函数 cgltf_accessor_read_float 在这个固定版本中一进入 sparse accessor 分支就返回 false。它没有代替你查找补丁，也没有把失败细分成“文件非法”。因此对于这里合法且受支持的稀疏输入，应选择批量展开路径，而不是继续使用失败调用留下的输出。[2]

## 调用前核对基底、目的编号与补丁三个区域

稀疏属性不是只有一个 view。基底、补丁目的编号和补丁值可能来自不同 view，甚至不同 buffer。每个 view 都先要落在对应已取得的 buffer 声明范围内；实际资源更长，不会放宽 view 边界。偏移省略时默认0，显式错误类型或负值应拒绝。[1]

对本例的非矩阵元素，令 `e` 为一个源元素占用字节数，`n` 为 accessor.count，`k` 为 sparse.count。需要确认：

- `1≤k≤n`。有基底时，按它的偏移、步长与元素大小检查全部 n 个元素；无基底时，不得声明 accessor.byteOffset。
- sparse.indices 使用无符号整数类型，紧密排列。若索引分量宽度为 `q`、其 view 内有效偏移为 `a`，需要的末端为 `a+k×q`。该偏移与其 view 的 buffer 内偏移分别按 q 对齐。
- sparse.values 的元素类型和分量数跟原 accessor 一致，紧密排列。若其 view 内有效偏移为 `v`，需要的末端为 `v+k×e`；两项偏移分别满足原分量宽度的对齐。
- indices 和 values 的 view 都不得声明 byteStride 或 target。目的编号必须严格递增、无重复且全部小于 n。编号选的是元素，不能把输出分量编号当作目的编号。

这些是 glTF 规范条件，不是由示例数量推出来的经验规则。计算末端时仍要先检查乘加是否可表示，不能依靠溢出后变小的数通过范围检查；可采用[普通读取文章](读取glTF交错顶点数据时的偏移与步长.md)解释的逐步范围算法。[1]

固定版本 cgltf_validate 的 sparse 检查包括类型、需要的区域长度，以及数据已加载时的最大目的编号；它没有检查目的编号严格递增或重复。它还会读取部分索引数据来求最大值。因此，不能先把完全未经资源边界核对的内容交给 validate，再把成功当作任意输入的安全证明。这里处理的是格式、资源边界和版本条件已明确的受控输入，不提供不可信文件的安全加载框架。[2]

## 分配完整容量，返回失败就不消费输出

令每个元素的分量数为 m，完整输出需要 `N=n×m` 个 float。先检查乘积和 `N×sizeof(cgltf_float)` 能在使用的整数类型中表示，且不超过工具的内存预算，再进行容量查询和分配。库的容量查询本身也会计算乘积，不能用查询结果倒过来替代溢出检查。[2]

调用次序可以表达为：

```text
确认输入与本版本读取路径相容，并完成字段/资源范围检查
确认 n×m 和输出字节数可表示且在预算内
N = n×m
要求 unpack_floats(accessor, NULL, 0) 返回 N
分配独立的 N 个 cgltf_float，不与源数据重叠；分配失败则停止
written = unpack_floats(accessor, output, N)
仅当 written == N 时，才把 output 作为完整属性交给下游
其他返回：丢弃此次输出，报告所在阶段，不继续消费
```

这里的 unpack_floats 指 cgltf_accessor_unpack_floats，不是另一套函数。空输出指针只查询数量，没有生成任何属性值。两元素 VEC4 的正确查询和完整返回都应是8；标量例子才恰好是4个元素、4个float。

尤其不要为了节省空间给 sparse accessor 一个“小容量数组”，期待函数安全截断。这个固定实现会按容量限制基底转换数量，但第二遍仍遍历全部稀疏补丁，按目的编号计算输出位置，没有按 float_count 截断这些写入。完整容量是本文调用路径的前提，不能把参数名称当作越界保护。[2] 此处是源码控制流核对，不是用错误容量执行了原生程序。

即使容量足够，函数也可能在取得基底或补丁数据时失败；此前已有部分输出被写入。失败返回后不能把数组中碰巧存在的数送入下游，也不应退回去忽略 sparse 只用基底。

## 固定版本的采用条件不能省略

前面的语义规则适用于 glTF；库接口能否正确实现当前输入，还要看具体版本。本文的 cgltf 1.15 路径采用紧密排列的基底，使 accessor.stride 等于元素字节数，并处理 FLOAT SCALAR 或 UNSIGNED_BYTE VEC4。FLOAT 的 normalized 不得为 true；字节元素则按前述标志决定是否除以255。[1][2]

该固定实现通过 C 指针读取分量，紧密 FLOAT 基底还使用直接内存复制。这里的调用路径要求小端数据解释、32位 cgltf_float，以及满足分量读取对齐的实际输入地址；仅有 JSON 中的偏移合法，不等于任意自定义数据指针都满足 C 读取条件。不能把本文数值观察当作不同字节序或浮点表示平台的移植证明。[2]

**交错基底需要另选处理路径。** 规范要求 sparse.values 的替换元素始终紧密排列；基底自身却可以是交错顶点属性。固定源码先从基底view得到 accessor.stride，再在 sparse 循环中也用该stride推进补丁值。如果基底stride大于元素大小且有后续补丁，这两个步长便不能混用。一个补丁的例子无法暴露推进到下一补丁的错误，因此不能凭本文 UINT8 示例批准所有交错稀疏输入。[1][2] 遇到这类输入，应采用已核对能分别处理两种步长的实现；不能仅修改stride字段，因为那又会改变基底读取。

**有符号 normalized 也不能从无符号示例外推。** 规范要求8位的−128和16位的−32768都解码为−1，相应公式为 `max(c,−127)/127` 与 `max(c,−32767)/32767`；这个固定版本的转换分支直接除以127或32767，没有对最小负数加这一步钳制。本文没有用 UINT8 的正确结果批准这些输入。[1][2] 如果管线需要它们，应先核对或修正所采用实现的该分支，并单独验证端点，不把值小于−1视为资产本来如此。

这两个限制影响的是所选库版本的采用决定，不改变“按完整元素替换”或 unsigned byte 除以255的规范含义。矩阵列填充、扩展提供的元素、压缩数据、实际网格和引擎导入也不在本例路径中；不能因为暂未实现便统称为非法文件。

## 两组已有观察能说明什么

已有有限 C 检查分别使用上述标量与四分量字节布局：

| 材料 | 配置与观察 | 能支持的结论 |
|---|---|---|
| FLOAT SCALAR | 有基底与无基底两配置，完整输出分别为 `[10,7,30,9]`、`[0,7,0,9]`，返回数量4；单元素接口均false | 在这两个紧密配置中，选择批量接口可以取得正确的基底与替换结果 |
| UNSIGNED_BYTE VEC4 | 有基底normalized、无基底normalized、有基底raw三配置，完整返回均8；归一化补丁输出约为0.250980407和0.749019623，raw保留64、191 | 输出容量按分量数计，基底与补丁都遵循normalized，缺少基底时从零开始 |

两组材料各执行过一轮及一次独立复跑，复跑仍是各自同一套输入，不增加到更多配置或跨平台覆盖。整数例子以预先规定的绝对误差1e−7比较64/255和191/255，其余预期值按记录检查。这些观察不证明部分输出安全、交错基底正确、所有normalized类型正确，也不是模型渲染或性能结果。[3][4]

实际接入时，先确定自己需要的是完整属性数组还是稀疏表示，再选接口。若采用这里的完整展开路径，重点不是“文件解析没有报错”，而是元素来源与替换关系清楚、源数据条件被核对、容量完整、返回数量匹配，且下游知道这些float数值所代表的属性含义。
