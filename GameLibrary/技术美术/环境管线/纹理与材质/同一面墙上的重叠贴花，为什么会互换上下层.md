# 同一面墙上的重叠贴花，为什么会互换上下层

墙上的警示标记应该盖在污渍上。两张贴花单独都能投到墙上，叠在一起也正常；到布景齐全的关卡里，镜头没动，标记却被污渍盖住了。此时先别再加大排序值。需要确认的是：排序值控制的是待处理列表，还是最终在墙上叠色的顺序？在有些实现里，这两件事不是一回事。

## 先确认两张贴花都参与了同一点的着色

固定机位、采样位置和渲染路径，在同一块不透明墙面上，把两张贴花换成容易区分的红、蓝基色，暂时不写法线、粗糙度或自发光。先只开红色，再只开蓝色，最后同时打开。两张分别打开时都该能改变目标点，且应避开投影盒边缘、距离淡出和法线淡出。若其中一张单独就不见，先排查[接收层和投影范围](地面贴花为什么投到了道具上.md)；排序无法让一个没参与的贴花出现在墙上。

然后只改变不覆盖目标点的贴花，别同时改镜头、投影盒或材质。若两张测试贴花的单独结果保持不变，叠起来却换了主色，说明该沿着实际着色顺序向回查，而不是继续改墙的接收设置。诊断时可用不透明红蓝清楚地标出最后一层，再恢复半透明确认混合：以黑色为底，各用 0.5 的权重，后混入的纯色分量是 0.50，先混入的只剩 0.25。

## Godot Forward+：先给记录排序，再按掩码读取

Godot 4.7.2 的这个 Forward+ 实现会把本次进入贴花缓冲区的记录按「相机到贴花原点的距离 − sorting_offset」升序排列。数组里位置靠前的记录先获得较小的索引。之后引擎将视图分成供渲染查询的空间簇，每个簇用位掩码标记相关的贴花索引，不把整份已排序的列表交给每个像素逐项读取。每 32 个索引占一个整数：索引 31 是第 0 个字的最高位，索引 32 是第 1 个字的最低位。[1][2]

片元着色器按字从小到大读取，**却在一个字内先取最高位**。相邻索引如果在同一个字里，就先读较大的；如果跨了字，就先读较小的。每次通过接收层和投影范围等检查后，基色直接混入当前结果。因此，两张贴花在 CPU 上维持同一个相对顺序，到叠色时仍可能互换先后。[3]

这是固定版本源码和可运行的位掩码模型给出的结果，不是 Godot 画面读回。关键不是场景里有 31 张贴花，而是**两条有效索引恰好落在不同的字**。在项目里做对照时，每张填充贴花都用有效基色贴图而不是空节点，让它们在同一视图成功登记，键排在两个目标前面，但投影不改变采样点。用只含目标和填充的试验镜头排除别的记录；如果看不到翻转，先核对列表成员和两个索引，别把场景节点数量当成排序后的索引。这一例不适用于 Mobile 的另一套路径。[4]

## 先定哪些层一定要分开，再选能保证顺序的做法

如果视觉上允许两道普通污渍任意互盖，就让它们共享一个语义层，不必每生成一张就永久递增优先级。若轮到警示编号必须可读，先在实际交付的材质通道和渲染路径上查清楚哪些优先级有明确规则。例如 Unreal Engine 5.5 的 DecalComponent 明确规定较大的 `sort_order` 后画。对同一渲染路径里需要明确上下关系的普通叠放，可先把污渍和标记分配给两个不同值，在对照镜头核验。不要把同值间的先后当作合同，也不要把这个设置当成 Godot 的距离偏移。[5]

优先级确有用，也不意味着应该给上百张贴花各一个等级。Epic 提醒大量不同排序值会妨碍按渲染状态归组，可能影响性能。先用同一镜头和相同素材、数量、覆盖面积做两组**固定**配置，一组只有少量语义层，一组分散排序值，比较目标机器上的相关渲染耗时。不要逐帧调用 `set_sort_order` 模拟第二组：该 setter 会让贴花重新挂接，测到的便不只是排序值分布差异。[5]

若目标路径不能可靠地维持该上下关系，最简单的是从允许投影的有效区域中避开标记。固定墙面也可以把标记和污渍按确定顺序合入同一贴图；如果污渍在运行时增减，而标记必须压住它，另一种做法是把两个遮罩交给同一个接收材质，明确在其中先合污渍、再合标记。这要求那些动态痕迹进入同一次合成，而不是最后仍作为独立投影叠上去。前者要多维护贴图变体，后者要考虑遮罩的存储、更新与采样成本。最终验收应在简化镜头和实际布景都做一次：移动镜头、加减不覆盖目标点的贴花，并检查原本允许相互覆盖的装饰没有被过度约束。
