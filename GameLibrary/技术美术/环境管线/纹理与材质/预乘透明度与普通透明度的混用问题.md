# 预乘透明度与普通透明度的混用问题

一张柔边图标在绘图工具里看起来正常，放进游戏后却多了一圈黑边。美术把边缘涂亮，黑边淡了，换到另一种材质又出现亮边。继续修图之前，值得先查一个问题：**这张图的 RGB 是否已经乘过透明度，而接收它的混合过程又乘了一次？**

这类误接会改变半透明部分的颜色贡献，却不一定改变图片尺寸、通道数，甚至最终画面的 alpha。只检查“是不是 RGBA”不够。本文面向 UI、特效美术和渲染协作者，用一个半透明边缘像素解释它为什么会发生，再说明从导出到混合该查哪里。以下计算是解释用的数值例子，不是某款游戏黑边的实测诊断。

## RGB 描述颜色，alpha 决定它怎样参与合成

先把通道值想成 0 到 1 之间的小数。RGB 是红、绿、蓝三个颜色分量；alpha 在本文的普通透明合成中表示不透明度：0 表示完全透明，1 表示完全不透明。半透明边缘处的 alpha 可以介于两者之间，表达边缘覆盖等效果。

同一份颜色信息有两种常见表示：

- **Straight alpha，未预乘表示**：RGB 仍保留原颜色，alpha 单独保存。本文标题里的“普通透明度”指这种表示，并不表示它天然优于另一种。
- **Premultiplied alpha，预乘表示**：RGB 已经乘以 alpha，保存的是参与合成的颜色贡献；alpha 本身仍单独保存，并没有跟着平方。

例如颜色 RGB 为 `(0.8, 0.4, 0.2)`，alpha 为 `0.5`。未预乘表示是 `(0.8, 0.4, 0.2, 0.5)`；预乘表示则是 `(0.4, 0.2, 0.1, 0.5)`。它们可以描述同一个半透明像素，但接收端必须知道自己拿到哪一种。W3C 的简单 alpha 合成说明正是通过这两种颜色表示来写公式。[1]

因此，预乘不是换一个名称或勾选一个标签。真正的转换会改变 RGB 数值。标签只是告诉后续环节这些数应该怎样解释；只改解释而不改数据，便可能接错。

## 同一条边缘为什么会变暗，也可能变亮

继续用这个半透明橙色像素，把它盖在不透明灰色背景 `(0.1, 0.1, 0.1)` 上。这里限定为普通的“前景覆盖背景”，也称 **source-over**，不是发光叠加等其他混合效果。所有颜色已经在同一个选定工作空间中；颜色空间本身稍后再讲。

前景遮住一半，背景就留下另一半。正确的颜色由两部分相加：

```text
前景贡献：(0.8, 0.4, 0.2) × 0.5 = (0.4, 0.2, 0.1)
背景贡献：(0.1, 0.1, 0.1) × 0.5 = (0.05, 0.05, 0.05)
输出颜色：(0.45, 0.25, 0.15)
```

如果输入是预乘值 `(0.4, 0.2, 0.1)`，第一行的乘法早已做完，接收端直接拿它加背景贡献即可，结果相同。

**暗边的一个来源是重复乘。** 把这份预乘值误当成 straight，再乘 `0.5`，前景只剩 `(0.2, 0.1, 0.05)`；加上背景后得到 `(0.25, 0.15, 0.10)`，比正确结果暗。alpha 越小，额外一次乘法对前景贡献的削弱比例越大，所以柔边尤其值得检查。

**反过来，漏乘也会过亮。** 如果把原始 straight RGB 当成已经预乘，直接与背景贡献相加，输出会变成 `(0.85, 0.45, 0.25)`。这里说的是同一计算条件下数值过大，不是承诺所有素材都一定呈现某种可见光晕。

不透明区域的 alpha 是 1，乘一次或乘两次都不改变数值，因此图标中心正常，并不能排除边缘的表示误接。背景在本例中不透明，三条路径的输出 alpha 也都是 1；只盯最终 alpha，同样发现不了 RGB 的问题。

## 找到哪一步乘过，比把边缘重新画亮更重要

排查时先保留原图，不要立刻用补偿色掩盖问题。让内容和渲染两端沿着同一个边缘像素，回答它在每一步是什么表示。

**先看导出文件。** 导出设置和文件格式说明的是文件保存了什么，不一定说明游戏最终拿到什么。PNG 第二版规范规定颜色不预乘 alpha。[2] 这不意味着导入工具不能在读取后生成预乘的工作纹理，也不意味着 PNG 文件会自动配置游戏的混合方式。

**再看导入和中间处理。** 确认是否有工具、材质准备步骤或着色器做了 RGB 乘 alpha。记录代表像素在转换前后的实际数值，而不是仅凭选项名猜测。Pillow 就明确区分 `RGBA` 和 `RGBa`，后者代表预乘；这种模式区分是该工具自己的接口约定，不能照搬成所有引擎的命名规则。[3]

**最后看送入混合器的值。** 对本例这种不透明背景上的 source-over，若着色器输出 straight RGB，前景颜色还需要乘一次源 alpha；若输出已预乘 RGB，前景颜色直接使用。背景贡献仍乘 `1 − 源 alpha`。渲染人员应核对实际着色器输出与颜色混合因子是否配套，不能只检查导入面板：纹理在导入时没预乘，也可能在着色器里才乘。

排查用的素材应同时包含不透明、半透明和全透明部分。先在简单背景下核对同一个半透明像素，再回到原界面或特效看实际表现。这里是建议的排查过程，本文没有执行目标引擎测试，也没有规定通用视觉合格阈值。

如果数值与表示都对得上，而异常只在缩放、远距离或图集边缘出现，就应转查过滤、缩小层级和相邻图块取样等环节，不能继续认定必然是预乘错误。这些过程怎样处理颜色需要单独分析，本书不把它们压成“换一种透明模式就能修好”。

## 转回 straight 不一定能恢复原图

当 alpha 大于零时，理想数学中可以把预乘 RGB 除以 alpha，得到 straight RGB。但实际文件往往使用有限精度，例如每通道 8 位整数；乘法和舍入可能已经丢掉信息，除法不能自动找回。

alpha 为零时更明显：无论原来的 RGB 是什么，乘零以后都是零。完全透明像素原本可能藏着颜色，预乘后再反向转换，不能指望恢复那些值，也不能对零做除法。另一方面，“直接合成时不贡献颜色”并不等于这些隐藏颜色在编辑或过滤过程中毫无作用，不能因此批量把所有透明区域都清黑。

已有离线 Pillow 数值例子采用 `(240,120,60,85)`，其中 alpha 恰为 `1/3`。显式预乘得到 `(80,40,20,85)`；正确路径盖到不透明黑色上得到 `(80,40,20,255)`，将预乘字节误解释为 straight 后再合成则得到 `(27,13,7,255)`。这些是旧资料记录的 CPU 字节域结果，不是 GPU 图像，也没有做 sRGB 解码。主例能精确往返，是特意选出的可整除数值，不能推广为所有 8 位颜色无损。

## 还有一个独立问题：在哪个颜色空间里乘？

“预乘还是未预乘”和“编码颜色还是线性颜色”是两个问题。前者问 RGB 有没有乘过 alpha；后者问这些 RGB 数值代表什么。

常见的 sRGB 编码不是光能的线性刻度。若目标是在与光能线性对应的 RGB 中合成，应先把编码 RGB 解码到该工作空间，在那里做颜色乘法与合成，再按输出需要编码。alpha 不是一个 RGB 颜色分量，不应跟着套用 RGB 的 sRGB 转换曲线。[2][4]

因此，不能看到“RGB 已乘 alpha”，就断定线性合成也做对了。把编码值直接乘 alpha，与解码后再乘、再编码，可能得到不同数值。也不能只靠把图像模式从 `RGBA` 改成 `RGBa`，就声称完成了颜色管理。

旧资料另有一项独立的 LittleCMS CPU 颜色转换实验，使用编码 sRGB `(128,64,192)/255`、alpha `128/255` 和不透明黑色背景。直接对编码值乘 alpha，约为 `(0.2520,0.1260,0.3779)`；经库转换到线性工作值、由主机代码乘 alpha、再编码，实际记录约为 `(0.3629,0.1746,0.5513)`。库负责颜色转换，主机代码负责合成算术。这组结果与前面的 Pillow 字节域实验不是同一条测试，也没有验证显示器、真实素材或引擎效果。

需要制定浮点误差和最终字节的检查条件时，可选读旧资料的[精度与量化说明](https://github.com/Container-R/GameLibrary/blob/1a7bf18b24ba56395892c4c0cdb3b2acecc16985/solutions/art2d/alpha-association-contract.md#double-buffer-不代表全程-double也不保证最终字节相同)。浮点结果接近，不一定意味着舍入后的字节相同；该支持小节保留具体反例与有限实验范围，不是对所有颜色转换的保证。

这不等于可以不经确认就批量改变现有资产的外观。SVG 2 的固定文档本身就区分 sRGB 与 linearRGB 运算，并将该属性的初始值设为 sRGB。[4] 对已有项目，要先问它希望维持哪条颜色流程，再检查导出、导入、着色器和目标缓冲区是否一致；若工作空间改变，应把它视为需要美术复核的外观变更，而非纯技术修复。

## 半透明背景要另算输出 alpha

前面的灰色与黑色背景都不透明，所以能直接用简化结果。若 UI 先画到透明的中间图层，再叠到其他画面上，就不能丢掉输出 alpha 或把结果误存成另一种表示。

用 `αs` 表示前景 alpha、`αb` 表示背景 alpha，`cs`、`cb` 表示双方已经预乘的 RGB，source-over 为：[1]

```text
输出 alpha：αo = αs + αb × (1 − αs)
输出预乘 RGB：co = cs + cb × (1 − αs)
```

这里的 `co` 仍然是预乘结果。只有在 `αo > 0` 且下一步确实要接收 straight 时，才计算 `Co = co / αo`。这也是为什么渲染侧不仅要核对颜色混合，还要核对输出 alpha 和中间图层的表示。颜色通道用对了公式，不代表 alpha 通道设置也自动正确。

回到最初的图标：先查清每一步 RGB 的表示、工作颜色空间以及谁负责乘除 alpha，再决定是否修改素材。预乘和 straight 都可以进入正确流程；真正需要避免的是两端各按不同约定工作，却用“都是四通道图片”掩盖差别。
