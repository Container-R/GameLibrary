# 计算BC压缩纹理和Mip链的数据量

一张纹理在下载包里很小，进游戏后却占用了更多内存；另一张纹理换成压缩格式后，预算表的数字下降了，性能工具显示的数字却没有按相同比例变化。这不一定是计算错了。下载文件、上传缓冲区和 GPU 纹理资源，存放的是不同阶段的数据，不能直接拿它们的大小互相替代。

这篇文章面向需要做纹理预算的技术美术（TA）和内容制作者。我们用一张 **60×40 的二维纹理**贯穿计算，说明尺寸、BC 格式和 mipmap 如何决定编码数据量，再说明哪些问题必须到目标设备上检查。无需先了解显卡内存分配接口，但需要知道项目导入后实际使用的纹理尺寸与格式。

## 先分清：下载了多少，与GPU需要多少

源图片经过导入后，可能被缩放、转换格式并生成多级小图。发行包还可能对这些数据作额外压缩。因此，源 PNG 的文件大小或下载包中的压缩大小，都不能直接作为 GPU 纹理预算。

**BC（Block Compression，块压缩）**是按固定大小的小块编码纹理的格式。以 BC1 和 BC7 为例，它们都覆盖 4×4 个纹素；“纹素”就是纹理中的一个像素位置。BC1 每块占 8 字节，BC7 每块占 16 字节。[1] 同样的尺寸和级数，选择哪种格式会直接改变编码数据量，但字节较少并不自动说明图像质量合适。

本文先算的是这些块紧密排列时的数据量，不包含文件头、上传时的额外间隔，也不是实际显存测量。这个数字可以帮助比较资产方案，却不能独自回答“某个场景峰值占用了多少显存”。

## 从一张60×40纹理开始

先假设导入后的顶层尺寸确实是 60×40，格式为 BC1。横向需要 `60÷4=15` 个块，纵向需要 `40÷4=10` 个块，所以顶层数据量为：

```text
15 × 10 × 8 = 1200 字节
```

这里没有根据图片内容估计压缩率：对给定尺寸，BC1 的块数与每块字节数已确定。换成 BC7，同样的 150 个块需要 2400 字节。选择哪种格式，还要检查目标平台支持、透明度需求以及实际内容的压缩效果，不能只看这两个数字。[1]

接下来加入 **mipmap**：它是一组逐级缩小的纹理图像，简称 mip 级。它们供采样时使用较低分辨率版本；预算时，不能只记原尺寸那一级。本文计算完整链，即一直缩小到 1×1，且所有级都保留。

60×40 的逻辑尺寸依次是：

```text
60×40 → 30×20 → 15×10 → 7×5 → 3×2 → 1×1
```

每次把宽和高分别除以二、向下取整，但最小保持为 1。计算块数时则向上取整，因为不足 4×4 的边缘仍要由完整块覆盖。缩小图像与计算块数是两步，不能混在一起。[2][3]

| mip级 | 逻辑尺寸 | 横向块数×纵向块数 | BC1数据量 |
|---|---|---|---:|
| 0 | 60×40 | 15×10 | 1200字节 |
| 1 | 30×20 | 8×5 | 320字节 |
| 2 | 15×10 | 4×3 | 96字节 |
| 3 | 7×5 | 2×2 | 32字节 |
| 4 | 3×2 | 1×1 | 8字节 |
| 5 | 1×1 | 1×1 | 8字节 |
| 合计 | 六级 | 208块 | **1664字节** |

例如，30 像素宽需要八个块，而不是七个半；1×1 也不能只保存一个块的十六分之一。最后两级各占 8 字节，正是小 mip 容易漏算的地方。

同一完整链若采用 BC7，每个块的字节数翻倍，总数据量为 **3328 字节**。这只是格式布局计算，没有进行 BC7 编码或质量比较。

## 把例子变成可复用的计算方法

对正整数宽高 `W、H`，先列出实际保存的各级尺寸。第 `i` 级的宽高与数据量可写为：

```text
w_i = max(1, floor(W / 2^i))
h_i = max(1, floor(H / 2^i))
该级字节数 = ceil(w_i / 4) × ceil(h_i / 4) × 每块字节数
总字节数 = 所有保存级的字节数相加
```

其中 `floor` 表示向下取整，`ceil` 表示向上取整，`max(1, …)` 表示不小于 1。BC1 的每块字节数为 8，BC7 为 16。Microsoft 的 DDS 指南给出相应块行计算；固定版本 DirectXTex 的正常块布局与二维 mip 累计路径也采用这类计算。[3][4]

最容易出错的是先把尺寸补齐，再用补齐后的尺寸生成下一层。15×10 需要四乘三个块覆盖，但下一层仍是 **7×5**，不是把覆盖范围当成 16×12 后得到 8×6。逻辑图像尺寸与编码块的覆盖范围必须分别保留。

此外，“能算出块数”不等于“目标 API 允许创建这个基础纹理”。例如 D3D10 文档要求 BC 基础资源尺寸满足四的倍数，同时解释较小 mip 的块补齐。[2] 上表中的 7×5 是链内小 mip，不能据此推导任意 7×5 基础 BC 资源在所有平台上都合法。

## 为什么“顶层乘4/3”只能作近似

常见估算认为，完整 mip 链比顶层多占约三分之一，即总量约为顶层乘 `4/3`。它来自面积级数：顶层为 1，后续为 `1/4、1/16……`，无限相加得到 `4/3`。当每级面积接近缩小到四分之一、块边缘影响较小时，这个近似容易使用。

但我们的例子用它得到 `1200×4/3=1600` 字节，比逐级计算的 1664 少 64 字节。原因不是 BC1 的压缩率发生了变化，而是每一级都要独立覆盖完整块，尾部也有最小块占用。

它也不是始终向同一方向偏差。离线计算一个 4×4 BC1 完整链，三层各占 8 字节，共 24 字节，远大于 `8×4/3`；17×17 的布局算术则得到 256 字节，低于顶层 200 字节乘 `4/3` 的约 266.67 字节。后一个只是布局反例，不表示已在某个 API 创建了该基础资源。

因此，草拟大纹理预算时可以知道这个近似从哪里来，但正式统计，尤其是大量小图与尾部 mip，应逐级相加。不要给一个不固定的误差方向起名叫“安全余量”。

## 1664字节为什么还不是文件大小或显存

把本例数据装入 DDS 文件，还要加入描述尺寸、格式等信息的文件头。采用基本 DDS 描述时，本例为 `1664+128=1792` 字节；带 DX10 扩展的描述长度则为 148 字节，不能把 128 写死到所有 DDS。[3] 如果再放进压缩发行包，下载大小还需要按实际包文件统计。

数据上传到 GPU 时，又可能需要按指定间隔排列每行。这个间隔称为 **row pitch（行跨度）**，可能大于一行有效数据的字节数。D3D12 的 `GetCopyableFootprints` 文档明确区分这两个数字；它提供的是可复制的上传布局，不是纹理永久占用量。[5]

纹理资源本身的分配要求要由目标 API 与资源描述确定。例如 Vulkan 的 `VkMemoryRequirements` 分别提供所需分配大小和对齐要求。[6] 而运行时实际驻留多少，还涉及场景和纹理流送状态——流送是按需要加载不同级别或部分资源的管理方式。减少磁盘中的数据、减少分配量和减少某一时刻的驻留量，不能视为同一个动作。

如果性能工具的数字与 1664 不一致，先确认它显示的是哪一层，而不是立即判定工具或引擎出错。也不要反过来用一份小 DDS 文件证明场景显存足够。

## 如何把计算用于一次资产调整

开始比较前，从目标平台的导入结果确认宽高、格式和实际 mip 级数，而不是只看源图片。然后写清目标：要减少下载体积，还是降低纹理数据量、上传峰值或运行时驻留？单位也要明确；若使用 MiB，1 MiB 等于 1,048,576 字节。

对于本例，BC1 完整链的 1664 字节可以作为一个明确基线。若提议换格式，就保持尺寸与级数一致，先比较编码数据量，再检查内容表现；若提议缩小尺寸，就按新的逻辑尺寸重新枚举各级，不能直接假定每次都恰好省四分之三。若提议只保留部分 mip，还要查引擎实际创建和加载了哪些级，而不是仅从预算表删除几行。

当离线计算正确、实机数值仍超预算时，应让渲染或平台侧核对资源分配及工具口径；当数据量下降但画面不可接受时，则回到内容、格式和分辨率的选择。省下若干字节本身不证明帧率提高，也不代替纹理质量检查。

本文的算术范围是单张、单层、单面二维 BC1／BC7 纹理。立方体、数组、三维纹理、其他压缩格式及稀疏资源需要额外规则，不能直接套用这里的总量。

## 这组数字经过了什么检查

旧版资料保存了有限 CPU 算术检查，以及本例 BC1 DDS 的文件长度与逐级数据检查。六个 mip 曾分别取出并包装成单级 DDS，由同一图像库解码检查尺寸和色标；这不是自动遍历完整 mip 链，也不是两个独立解码器的比较。

这些记录没有执行 GPU 资源创建、驻留测量或 BC7 解码。本次改写保留其结果范围，没有重跑实验；上面的计算可用于理解编码布局，不能冒充实机显存观察。
