# Unreal自动生成光照UV后，为什么仍要检查切缝与分辨率

同一块墙饰放进两个房间，使用同一个静态网格。它已经勾选“生成光照 UV”，一处烘焙后看起来正常，另一处却出现可疑接缝。再生成一次，是否就能解决？

先不要把“生成过”当作验收结果。应分别确认：**源 UV 是否适合重新排布，烘焙是否使用了生成的通道，以及问题实例的分辨率是否仍符合生成时的前提。** 这三项需要不同的修正，不能靠反复按同一个按钮替代。

本文面向模型美术和接收环境资产的技术美术，限定 Unreal Engine 5.6 文档中 Static Mesh Editor 的 LOD0 工作流程，以及使用预计算光照的静态模型。墙饰是虚构例子，未制作、导入或烘焙；下文提供排查方法，不报告已经修好的画面。

## 生成的是新排布，不是替你完成所有展开工作

UV 将模型表面对应到二维空间；展开后的一块连通区域常称为 chart，也叫 UV 岛。材质纹理可以有意重复使用同一片区域，光照贴图却需要为表面提供独立空间，并在区域之间留出间距。[2]

Epic 对自动生成工具的限制写得很明确：它需要已有源 UV，重排其中的 chart，**不会通过切开 chart 边缘来创建新的岛**。[1] 因此，“生成光照 UV”不能理解成“重新判断所有表面该在哪里切缝并完成展开”。

回到墙饰，假如作者检查源 UV 后，确认某块区域需要增加切缝，才能得到合适的光照展开，那么这一步仍应在 UV 编辑工具中完成，再交给重排流程。只提高光照分辨率，没有完成那次切分；重复生成，也没有提供新的源切缝。

但不要反过来说“只要有重叠，自动生成都无能为力”。已有独立岛之间的排布问题，与源 chart 本身还需要拆分，是不同问题。检查应落到实际 UV 区域，而不是仅根据一条重叠警告猜测原因。本文不推断引擎怎样识别任意网格的 chart，也不给所有几何统一规定切缝位置。

## 看到了UV1，不等于烘焙正在使用UV1

设墙饰从 UV0 生成 UV1。这里至少有三个设置要区分：[1]

- **Source Lightmap Index**：从哪个通道读取现有 UV。
- **Destination Lightmap Index**：把生成结果写到哪个通道。
- **Lightmap Coordinate Index**：烘焙实际使用哪个通道。

前两个属于生成设置，第三个决定生成结果是否真的被使用。它们在本例中应分别为0、1、1；这不是所有资产都必须采用的通道编号。

一个容易误判的检查过程是：作者显示 UV1，看到岛已排开，就认为烘焙设置也正确了。如果实际 Lightmap Coordinate Index 仍指向 UV0，漂亮的 UV1 并没有证明当前烘焙使用它。此时应先核对通道选择，而不是继续修改 UV1 的间距。

反过来，三项编号符合预期也只关闭了“读错通道”这个疑点，不证明 UV1 本身合格。检查时应记录具体通道及其内容，避免把“编号正确”和“内容正确”合成一次判断。

## 模型默认256，为什么还要检查实例？

现在假设墙饰的源 chart 已适合重排，三个通道设置也符合预期。生成时，**Min Lightmap Resolution 设为128**；模型的默认 Lightmap Resolution 为256。

Min Lightmap Resolution 参与决定生成时的 chart 间距，不是给所有实例强制设置实际分辨率的开关。[1] Epic 另说明，关卡中的 **Overridden Light Map Res** 可以覆盖模型默认值；实际分辨率低于生成时的 Min，会带来接缝及潜在漏光问题。[2]

沿用这个前提，比较两个虚构实例：

| 墙饰实例 | 实际采用的分辨率 | 这一项能得出的判断 |
|---|---:|---|
| 甲：沿用模型默认值 | 256 | 没有低于生成时的128，但其他问题仍需检查 |
| 乙：启用实例覆盖 | 32 | 已低于生成时采用的最低分辨率前提 |

因此，只打开模型资产看到256，不能解释乙实例的问题。读者应先找到乙实际生效的覆盖值，再决定修改方向。

**如果32是误设，修正的是实例设置。** 让它回到项目批准的分辨率，并重新检查结果；没有必要因此假定所有源 UV 都需要重做。

**如果32是有意的预算要求，原来的生成前提就需要重新考虑。** 应按最低预定使用分辨率调整并重新生成排布，或由作者重新设计 UV，再检查这份墙饰是否仍能满足质量要求。降低目标后，能否同时容纳足够间距和所需细节，需要检查，不能预先宣布成功。

这里不把 Min 与实际分辨率相等视为质量保证：生成指南要求模型默认分辨率高于 Min，而另一篇说明把 Min 称作最低预定分辨率。[1][2] 若预算确实要求32，应重新制定生成方案并检查结果，不能只凭两个字段都为32就批准资产。

仅修改 Min 字段，却没有应用生成修改，不等于已有 UV 已经重新排好。完成生成也不等于光照已重新烘焙，更不等于画面已经通过。这些是不同阶段的完成条件。

## 用一次有针对性的检查结束盲目重试

对开头的乙实例，可以按以下顺序收窄问题。这是未执行的建议流程，不是 Epic 的完整故障诊断程序。

1. **确认正在排查什么。** 找到问题实例、使用的静态网格和对应烘焙结果。若异常来自法线贴图、探针或动态照明，本流程不能直接解释它。
2. **对齐三个通道角色。** 查看源、目标及实际光照通道，别把编辑器当前显示的通道当作实际使用通道。
3. **检查展开是否需要作者修正。** 若源 chart 需要新增切缝，先完成展开修改；若只是已有岛的排布问题，再评估重新生成。不要把所有重叠归为同一种原因。
4. **检查问题实例的分辨率。** 将实际覆盖值与生成时的 Min 比较，分清误覆盖和有意降低预算，再选择修正对象。
5. **重新取得结果，再评价修改。** 在实际制作阶段应用必要修改、重新烘焙，保持其他相关条件稳定，检查乙及受同一资产修改影响的实例。尚未查看的用途不能自动继承通过结论。

Static Mesh Editor 的 UV overlay 可用于查看通道；光照错误颜色可帮助定位重叠或越界，文档要求使用 Preview 或 Medium 光照品质才能显示该诊断结果。[2] 这些工具帮助定位，不会单独证明最终质量合格。

若源 UV、通道与分辨率都符合预期，仍有异常，就应继续调查其他候选原因，而不是把每一条接缝都归罪于自动生成工具。尤其不要用法线烘焙的投射笼或高低模分组来替代这里的检查；那是在解决[取得哪些表面细节](法线烘焙串到附近零件时，为什么不能只加大投射笼.md)的另一类问题。

## 这次检查能交付什么

一份有用的结论可以是：“墙饰从UV0生成UV1，光照使用UV1；乙实例覆盖为32，低于生成时的128。接下来确认32是否为预算要求，再选择修正覆盖或重做排布。”这比“已经重新生成”更能让下一位协作者继续工作，因为它指出了尚待决定的具体条件。

本文不提供通用安全间距、最佳分辨率或必然无缝的保证，也不扩展到所有 LOD、Nanite、GPU Lightmass 或虚拟光照贴图。未运行引擎、检查资产或比较图像；所有操作解释限于所读版本文档。
