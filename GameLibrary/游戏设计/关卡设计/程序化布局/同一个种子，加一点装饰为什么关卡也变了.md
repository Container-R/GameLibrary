# 同一个种子，加一点装饰为什么关卡也变了

一张已验收的地下城地图，种子、地形规则和房间库都没改。美术只给地面植物多加一次随机选择，入口后第三间房却转了方向。另一次重启从地图右侧加载，结果左侧房间又变了。这不一定是种子失效。它可能一直产生相同的随机数，**变的是哪一步拿走了哪个数**。

这里要保证的是：同一生成规则与输入下，独立的装饰变化不改布局，分块加载顺序不改按块应得的结果。若树木真能堵门、道路必须接到新地形，那不是独立变动；后续内容可以按设计依赖改变。把这些真实依赖与共享随机状态分开，才有可验的边界。

## 种子给出序列，不给每个对象认领号码

设布局和装饰拿同一实例。第一间房先录一个方向，第二间房还未抽门型，美术增加的采样却先拿走了下一个值。入口种子并没变化，之后门型、候选选择和其他房间都可能换到不同的随机数。如果中间还有拒绝重抽，消耗数量也会随分支改变；不要把「同样调用一次高层抽样」想成固定走一步底层状态。

实际做一个小地图对照：三块地各生成「方向和高度编号」，中间一块在这两项之间额外抽一次。共享 Python 随机实例时，右块的编号从 (2,2) 变为 (3,1)。只把加载次序倒过来，最左和最右两块也拿到不同的编号；把输出排序后比较，它们仍不同，并非只是数组展示顺序。[复现实验](../../../../管理档案/实验/程序化随机流/README.md)

这也是全局方便接口不宜供多个生成步骤直接争用的原因。Unity 6000.0 的 `UnityEngine.Random` 文档明确它是全局共享的静态状态，与创建多个实例不同。[1] Godot 4.6 的 `RandomNumberGenerator` 支持分别设种子与保存内部状态，文档也提醒实现算法不属于跨版本约定，且相近种子不一定产生充分不同的序列。[2] 能直接读写一个状态不意味着各模块应该共同拥有它。将全局状态临时存下再恢复可以做孤立调试，但难以把随时执行的工具、异步任务或随机装饰都约束在同一套借用规则里。另用 Godot 4.6.3 实际运行整数抽取：共享时，插入一次装饰调用让后续布局序列从 149008 开头变成 865485 开头；分开两个实例后布局序列不变。把同一实例保存的状态放回，能精确重放接下来的五次抽取。这里没有生成地图，也没有测不同种子的统计性质。

## 先按职责分流，再给独立对象稳定的归属

一种便于逐步迁移的办法：

1. **把布局和装饰拆成各自的随机入口。** 由调用者把明确的流交给负责它的阶段，装饰代码不拿布局实例。让同样的装饰变化只改装饰。
2. **分块分别派生。** 若布局实例仍由所有可独立块共用，反过来加载依然会改变各块领到的序列。用世界种子、阶段、块坐标、决定用途等输入为每个块建立本地流；重载同一块时还用同一个标识，不按它排在加载表第几项取随机数。
3. **必要时拆到决定，而不是每个函数都盲拆。** 若同一个块中「房间朝向」和「装饰重试」也应互不影响，使用不同用途键；一个只在同阶段内部有顺序依赖的求解器可以继续独占一个有状态实例。为每点维护不同的状态比单流复杂，需标明哪些输出真需要隔离。

在上面的脚本里，布局和装饰分别用带用途的派生值初始化；给中间块增加三次装饰抽样，同时反转加载和候选数组，布局三块均不变。中间的植物由 lichen 变为 moss，其他块也不受这三次抽样影响。在共享流里，单独加入相同三次装饰采样就会改变布局。它只验证固定生成器和合成地图的操作，不表示跨引擎或任何种子都必然让某个具体植物变化。

派生时写下固定的数据格式。例如在一个只接收受限 ASCII 名称与整型坐标的项目内，用固定字段顺序的无空格数组编码 `[格式版本, 世界种子, 阶段名, 块X, 块Y, 用途名]`，明确字节编码、哈希和取多少位及字节序。试件使用 UTF-8 的该数组、SHA-256 前八字节按大端解释，用作种子；`["game-atlas-v1",20261119,"layout",-1,2,"turn-and-height"]` 得到十六进制 `d297cb622ab2effb`，可以存一条固定向量供别的实现对照。不要用某语言在不同进程会变化的对象哈希，也不能假设两种语言写出来的任意 JSON 永远相同；需要跨语言时，把负坐标、数字范围、名称转义和字节规则一并固定。有限位数的派生不保证任意键都不冲突，也不是安全或随机品质证明。

用稳定 ID 指向语义对象，而非当前容器序号。例如同一格的地砖、已命名的房间槽位可以跨加载维持；若把 `第 n 个遍历到的房间` 当作 ID，新增一个更早的房间就会让后续 ID 全换。随机值相同也不保证选中同一个资产：在「按编号选」之前先按稳定资源 ID 规定候选顺序与必要的同值决胜规则，不能让异步回调次序或资源目录枚举替你排序。候选本来就变了时，结果是否应保存则另由项目决定，不承诺靠分流使替换素材毫无影响。

## 按地址取随机值，不能代替处理真实依赖

有时规模更大，工作分派过程中无法约束采样顺序。计数器式伪随机生成器可以用键和计数直接得到指定元素，不必先生成此前所有值。Salmon 等人的 Random123 论文给出这种随机访问思路，并强调软件接口不能重新引入序号依赖。[3] 在游戏中，一个地址可以由对象 ID、决定名、一次本地重试的序号组成。重抽序号只影响该决定；如果仍用「哪个线程先拿到，下一个全局计数就给谁」，重排任务照样会改变结果。这里介绍地址分配，不要求项目换成该论文的实现。

独立随机流不会解决跨块共享的决策。两块都看到接壤的一处空地，各自随机生成一座塔，谁占地可能仍由加载顺序决定。要么让这条边归某个明确的所有者（例如以一对规范排序的块坐标给边命名），要么先收集两个候选，按规则和稳定 ID 仲裁，再让各块读取共享决定。另一种游戏允许已加载的地块优先，这也是明确设计，但就不应声称换加载顺序仍生成相同世界。把随机输入和合并顺序分别记录，才知道第一处差异来自哪里。

## 让旧地图、调试回放和新版各有明确合同

回归从小到大走三组：

- **不改任何输入再跑一次。** 按稳定 ID 比对结构摘要、决定发生的阶段、每阶段关键输入和抽样位置。保存随机实例状态只能重演这一实现的一个采样点，不等于保存地图。Godot 文档也要求将曾保存的状态用于恢复，而不是拿任意值当种子之外的状态。[2]
- **只改允许独立变化的条件。** 加一条装饰采样、改变分块载入顺序、故意打乱同一批候选的枚举次序；对不应改变的布局逐块比对，同时确认装饰路径确实做了新增抽样；单个种子碰巧选中相同装饰不等于没有扰动。可用一个已确认会改变装饰的测试向量作阳性对照。可把相邻所有权拿出来另测，不能只验几种顺序后宣称并行求解全面确定。
- **改规则或版本。** 保存需长期一致时，保存已生成的关键结果，或保存世界种子、规则、内容表与随机实现版本并保留对应复算能力；两者成本不同。早期还可允许旧地图按明确迁移规则再生成。换一个引擎或更新生成库后，“旧种子还能重造旧世界”需要测试向量和历史内容，不是默认承诺。

当结果不同，先找到第一个变掉的稳定对象：它的随机流输入是否真的相同、抽到的是不是相同的位置、相同索引选到的候选是否也相同、最后是否被跨块竞争覆盖。这样才能区分需要改种子派生、候选排序，还是整个生成过程的依赖顺序。
