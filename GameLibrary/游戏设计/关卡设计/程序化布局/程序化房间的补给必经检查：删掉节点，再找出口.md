# 程序化房间的补给必经检查：删掉节点，再找出口

生成器交出一条从入口到出口的路，补给房也放进去了。试玩时，玩家却能从侧门直接离开。如果设计要求是“进入下一段前必须经过补给位置”，检查出口可达、补给房存在，甚至检查补给房可达，都没有回答真正的问题：**是否还存在一条不经过补给位置的通关路线？**

本文面向配置房间生成工具的关卡作者和玩法程序，用一个静态有向图完成这项验收，并输出能定位错误的绕行路线。读者只需理解节点、单向边和可达性。这里的“必经”指所有成功到达出口的路线都经过指定位置，不保证玩家一定选择通关，也不保证经过后实际领取补给。

## 先把流程要求和房间选择分开

Sébastien Bénard 在《Dead Cells》的早期制作说明中，将手工世界框架、具有特定用途与出入口条件的房间、区域概念图，以及按图的要求挑选房间分开介绍。[1] 这给生成工具一个实用分工：上层决定某个位置为什么存在，下层选择能够承担它的内容。补给房与战斗房即使门口相同，也未必是可互换的候选。

这份资料支持制作分工，不提供本文的必经检查算法。以下图、判定和代码均为独立教学例子，不是《Dead Cells》的关卡或当前生成器实现。

先将设计要求写成可检查的输入：入口 S、出口 E、指定补给位置 R，以及最终生成结果的有向邻接表。S、E、R 必须是三个不同且存在的节点；每条边的终点也必须存在。边表示在本次检查条件下始终可走的连接，双向通道要明确登记为两条边。本例没有钥匙、开关、消耗、能力变化或随机通行条件。

应检查最终实例图，而不只检查生成前的概念图。布局阶段多接一扇门，就可能增加概念图中不存在的绕行。反过来，若实际存在传送或单向落差而邻接表漏记，检查通过也只是图的数据通过。

## 五个房间中，哪一条边破坏了要求

S 是入口，A 是战斗段，R 是补给室，T 是可选宝箱支路，E 是出口。基准图如下：

```text
S → A → R → E
    ↕
    T
```

它的边是 `S→A、A→R、A→T、T→A、R→E`。宝箱支路允许玩家来回，仍不破坏补给必经：只要最终从 S 到 E，就要经过 R。允许分支并不等于允许绕过必经位置，没有必要把整张图压成直线。

现在加入 `A→E`。补给室仍存在且可达，但 `S→A→E` 已是一条绕行。只查看搜索器第一次找到的路线也不可靠：某种遍历顺序可能先找到 `S→A→R→E`，只能证明“有一条路线经过 R”，不能证明“每条成功路线都经过 R”。

需要把问题反过来：暂时禁止访问 R，搜索能否从 S 到 E。若找到了路线，它就直接反驳必经要求。若找不到，再结合原图确实可通关，才可以报告 R 必经。

为什么这样成立？一条不经过 R 的原图路线，不使用 R 的任何关联边，删除 R 后仍然存在；删除 R 后找到的路线，也仍是原图中不经过 R 的路线。因此，“删 R 后能到出口”与“存在绕行”在这个静态图上等价。环路不影响这个论证：若存在绕行，删去路线中重复的绕圈部分，仍能留下一个绕行路径，所以搜索时可以按节点去重。

## 用三种结果代替一个通过按钮

检查器应区分下面三种结果，避免把堵死出口当作成功：

| 原图 S→E | 禁止 R 后 S→E | 结果及用途 |
| --- | --- | --- |
| 不可达 | 不必继续查 | `unreachable`：先修通关路线，不能报告补给必经合格 |
| 可达 | 可达 | `bypass`：返回一条绕行，定位是哪组连接允许跳过 R |
| 可达 | 不可达 | `mandatory`：在当前图中，R 是所有成功路线的必经位置 |

实现不必真的修改邻接表。搜索扩展邻居时跳过 R，就等价于删除它和关联边；原数据还能保留给诊断界面。下面是核心搜索，返回节点序列或 `None`：

```python
from collections import deque

def route(graph, start, end, blocked=None):
    if start == blocked or end == blocked:
        return None
    parents = {start: None}
    queue = deque([start])
    while queue:
        node = queue.popleft()
        if node == end:
            result = []
            while node is not None:
                result.append(node)
                node = parents[node]
            return result[::-1]
        for other in graph[node]:
            if other != blocked and other not in parents:
                parents[other] = node
                queue.append(other)
    return None
```

先校验上述输入条件，再调用 `route(graph, S, E)`；若返回 `None`，报 `unreachable`。否则调用 `route(graph, S, E, R)`，有返回值就报 `bypass` 并附路线，没有则报 `mandatory`。`parents` 同时防止在 A、T 之间无限搜索，并保存回溯路径所需的前驱。这里默认节点标识不是 `None`，示例使用字符串。

邻接表上的两次广度优先搜索，时间为 O(V+E)、额外空间为 O(V)，V 是节点数，E 在这个复杂度式中表示边数。返回的绕行具有最少边数，通常容易在编辑器中展示；它不是最快、最安全或玩家最可能选择的路线。诊断至少保留生成种子、图与房间模板版本、S/E/R 和这条见证路径，才能回到产生错误的实例。随机种子相同而模板库变了，不足以恢复同一结果。

本次用独立 Python 试件运行了以下小图：

| 修改 | 观察到的结果 | 排除的错误判断 |
| --- | --- | --- |
| 基准图不变 | `mandatory` | 可选宝箱环路并不自动破坏必经 |
| 加入 `A→E` | `bypass`，见证 `S→A→E` | 补给可达不代表补给必经 |
| 从基准图移除 `R→E` | `unreachable` | 没有绕行不代表关卡合格 |
| 只给基准图加入 `E→A` | `mandatory` | 不能把单向边当成双向连接 |
| 加入 `A→E`，同时移除 `R→E` | `bypass`，见证 `S→A→E` | 补给房可能可达，却只是一条死路 |

这些执行结果核对的是图模型与路径输出，不是游戏碰撞、实际模板连接或玩家行为。

## 拓扑通过后，还要问 R 被什么内容填上

如果生成器给 R 选了一间门口合适的普通战斗房，上面的搜索仍会报告 `mandatory`。这不是搜索错了：它检查的是位置，而位置的用途被另一个阶段丢掉了。

应把候选资格写成明确的合取条件，例如“属于指定区域、用途包含补给、出入口满足该节点要求”。门能接上只是其中一项。若满足全部条件的候选集为空，应报告无法实现这个节点，让作者补素材、调整连接或明确修改设计要求；不要悄悄去掉用途限制后把生成结果当成合格。

试件另设了“R 必经，但实际房间用途为 combat、要求为 supply”的反例。拓扑结果保持 `mandatory`，用途比较失败。这个简单比较说明两项验收彼此独立，不是完整的模板筛选器。实际项目还要检查标记与内容一致：标成补给的模板是否生成了补给对象，玩家进入房间时能否接近它。若可以从门口直接穿过而不碰到补给，房间级必经无法保证互动发生；要么将检查粒度细化到通行区域或互动事件，要么把设计承诺保留为“经过补给房”。

发现绕行时，见证路线能缩小修改范围，但不直接决定删哪扇门。可以取消绕行连接、把 R 移到分流之前，或承认补给本应可选。修图以后要重新检查通关与必经，不能只消除刚看到的一条路径：其他绕行可能仍存在，粗暴删边也可能把出口一起封死。

## 什么情况下需要换一种判定

本文针对指定的一个 R 和一个 E。如果关卡允许从多个出口结束，把所有合法出口用单向边接到一个虚拟终点，再对该终点检查，才能发现通往其他出口的绕路；只检查主出口会漏掉这些通关方式。

“R1、R2 至少经过一个”也不同于“R1 和 R2 各自必经”。前者应同时禁止集合中的全部节点，寻找完全避开这组位置的路线；后者才是逐个禁止、分别要求不可绕过。不能把逐节点检查直接用于“任一补给点即可”的设计。

一旦门锁或能力会改变可走的边，同一房间的不同游戏状态就不能合并。此时可参考[程序生成的关卡：地图连通，玩家为什么还过不了](程序生成的关卡：地图连通，玩家为什么还过不了.md)，先建立合法状态与动作的搜索模型。那篇解决“至少存在一条合法通关路线”；本文解决静态图中“所有成功路线是否经过指定位置”。这两个量词不同，不能用其中一个通过替代另一个。
