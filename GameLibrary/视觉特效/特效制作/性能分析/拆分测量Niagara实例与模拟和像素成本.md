# 拆分测量Niagara实例与模拟和像素成本

一团烟雾单独播放很流畅，战斗中同时出现很多团就开始卡顿。把粒子模拟切到图形处理器（GPU）后，情况没有明显改善；镜头一靠近烟雾，又变得更慢。下一步应该减粒子、合并发射器，还是简化材质？

这些动作针对的并不是同一种成本。本文用这段虚构战斗作为贯穿例，说明怎样安排有区分力的比较，而不是提供一个通用粒子数量上限。读者是实时特效、技术美术及协助定位性能的程序与测试人员。具体工具以 Niagara 为例，但先定位等待、分离变量、再检查整帧和视觉结果的思路也适用于其他特效系统。

以下安排尚未在 Unreal 项目中执行。主要机制依据 Unreal Engine（UE）5.6 官方文档；测量和 Effect Type API 的两项补充页面标识为5.8，不能据此假定5.6具有全部相同字段或界面。

## 先问是哪一份工作变多了

Niagara 的 **System** 是组织一组效果的系统资产，**Emitter** 是其中的发射器；同一系统在关卡里可以有多个运行实例。相同的总粒子数量，分布在少量大实例还是许多小实例上，组织成本与剔除粒度可能不同。

切换到 GPU Simulation 也不表示所有计算离开了中央处理器（CPU）。5.6文档说明，System 与 Emitter 脚本仍在 CPU 上，粒子阶段才随 Sim Target 改变。[1] 因而“GPU版还有CPU开销”本身不构成异常。

对烟雾例，先分别查看：

- **生成与管理**：是否同一帧激活了很多实例，第一次使用时是否还有资源准备？
- **模拟**：粒子运动、碰撞或数据读取花在哪里，相关任务是否让关键线程等待？
- **渲染组织**：绘制器、材质、网格和视图数量是否增加了组织工作？
- **像素工作**：近处烟雾覆盖更大屏幕范围，透明层是否反复绘制同一片像素？
- **内存与传输**：存活的资源、缓冲与峰值分配是否造成压力？

不要先把最后三项都称作“模拟慢”。GPU同时承担多种工作，将更多模拟搬上去，也可能使已经拥挤的阶段更拥挤。

## 做比较前，先固定能复现的战斗

用可重放的战斗片段、固定摄像机轨迹和随机种子，明确同时出现多少名角色、多少次爆炸，以及烟雾如何运动。峰值应来自游戏规则中真正可能发生的情况，而不是随意堆放一万个实例后替正常关卡作结论。

同一份比较应记录精确引擎与构建版本、目标硬件和驱动、地图、质量档、分辨率及渲染比例、渲染后端、动态分辨率、垂直同步与限帧设置。移动设备还要区分温度和电源状态。首次激活与稳定播放分别看，不能为了曲线平滑，就把玩家确实会遇到的初始化尖峰删掉。

目标60帧每秒对应约16.67毫秒一帧，但这不意味着把所有线程和 GPU 计时相加，就得到该帧总耗时。并行工作和等待需要从时间线上理解；特效单项在预算内，也不等于整帧已经达标。

先保存原资产和一个诊断副本，再逐步改动。每一步都记清修改了什么，以及最后拿什么结果作比较。预算需要的不仅是时间，还包括视觉底线：烟雾中的伤害轮廓、来袭方向和命中反馈，哪些不能丢？

## 第一组比较：多实例，还是大实例

先让所有烟雾都处于可见范围，尽量保持总粒子数、寿命、运动与屏幕覆盖一致，比较许多小实例与较少大实例。这样的安排较有利于观察实例与发射器组织成本。

接着必须回到真实关卡分布：有的烟雾在镜头里，有的在远处或墙后。合并可能减少管理，却让原本可以独立剔除的部分一起保留。官方文档也指出了实例数量与剔除粒度之间的取舍。[1] 第一步更快，不能自动说明整个关卡也更快。

同时启用、禁用目标效果，可以先观察它在当前场景中的边际影响。不过这个差值包含其他系统的交互，不是以后所有场景都能直接套用的“每团烟成本”。

## 第二组比较：先把模拟和绘制拆开

在诊断副本中临时关闭绘制器，可以帮助判断绘制部分的影响。但必须确认模拟仍按原条件运行：实例和粒子数没有减少，生命周期与包围范围没有因改动而改变。否则省下来的工作可能来自模拟或剔除，不能全部算到绘制。

再保持粒子数和绘制方式不变，只简化一个可疑的模拟模块，观察对应阶段和整帧是否变化。比如先比较碰撞逻辑的两个可解释版本，而不是同时改碰撞、寿命、粒子数量和材质。

CPU与GPU模拟的比较，也应先确认支持的功能、输入和生命周期能对应。不支持的模块需要替代时，实际比较的就不只是一个开关。结果应同时看 CPU关键路径、GPU余量、内存与响应，不仅选粒子阶段数字较小的版本。

## 第三组比较：为什么镜头靠近后变慢

保持模拟数量和运动轨迹，分别改变镜头距离、粒子尺寸、透明叠层或一个材质简化项。目的是区分“同样的粒子，覆盖了更多像素”与“粒子计算本身更多”。这些改动也会改变画面，所以比较后还要恢复真实摄像机和视觉要求。

降低分辨率后 GPU 变快，只能提示像素相关工作可能重要；其他全屏阶段也被一起改变了。应在 GPU 捕获中找到目标绘制阶段，再与正常渲染下的整帧结果对照。

UE 5.8 的测量文档介绍了 Shader Complexity 与 Quad Overdraw 视图，可辅助找复杂材质和透明叠加。[5] 它们的颜色不是毫秒刻度，不能只凭“红变绿”填写节省了多少时间。

Niagara Debugger 能确认实例、粒子和包围范围，FX Outliner 的性能视图则区分游戏线程（GT）与渲染线程（RT）。**RT不是GPU执行时间。** GPU粒子数据读回还会带来内存开销和数帧延迟。[2] 所以先用诊断显示找对象，再用合适的时间线与平台 GPU 工具测量，不把两种用途混在一起。

具名追踪也有额外成本。5.8测量文档建议用详细名称定位后，再关闭这种额外记录取得代表性计时。[5] 测量方式改变了结果时，要把这种影响说明白。

## 包围范围不能靠“看起来够大”决定

**Bounds** 是用于判断效果可能覆盖哪里的包围范围。它太小，烟雾或拖尾还可见时可能被错误剔除；这类“性能改善”其实丢了效果。它太大，则可能让本可剔除的工作继续存在。

固定范围减少了一类动态更新工作，但对长距离移动的效果，巨大固定盒又可能抵消这个好处。[1] 应检查实际坐标空间，以及初始爆发、附着物运动、旋转缩放、拖尾、后期大粒子和随机可达极值。镜头扫过边缘、效果离屏再回来、暂停恢复也需要看，防止突跳、重复爆发或不再恢复。

对于跨越大段场景的轨迹，可以比较适当的生命周期分段、坐标空间或动态策略；不要先用一个覆盖整条路线的大盒，便宣称固定范围一定更快。记录选择依据，关闭调试显示后再计时。

## 压力大时，先保住玩家需要读懂的东西

烟尘、余烬和装饰性光点可以考虑缩减；伤害范围与发生时刻则可能不能延后或消失。分类依据是玩法意义，不只是距离：远处的狙击预警，可能比近处的一团装饰烟雾更重要。

**Effect Type** 可以将一组系统的预算相关距离、实例数量等规则集中配置。[3] 这些设置负责执行缩减，并不替团队判断哪些信息可以丢。需要按平台质量档安排规则，也给关键效果准备本身就便宜的版本。

如果按相对重要性排序，要说明输入是什么，拥挤时是否反复剔除又恢复。可以提出滞回或最短保留时间一类设计，但须核对项目分支能怎样实现，不声称已有默认机制。5.8 API 文档中的 `SignificanceHandler` 仅说明其相对重要性用途，不是5.6所有字段兼容的证明。[6]

大量生成的尖峰也要拆开：首次资源准备、同帧激活、稳定更新分别处理。错峰是改变发生时间，不是免费的工作消失。伤害预警和爆炸首帧不能为了平滑数字而延迟，装饰层才适合在视觉允许时讨论错峰。池化、预热是否有益，同样要分别观察初始化与稳定成本。

## 怎样判断这次改动值得保留

回到固定战斗，在相同目标设备上多次交错运行旧版和候选，而不是只保留最好的一次。记录每帧样本、样本数量、冷热状态、运行顺序、异常事件和视觉问题，比较中位数与尾部尖峰。帧时间的第99百分位数（p99，用于观察较慢的一端）应从合适的帧样本汇总计算，不能直接平均几个运行各自的p99。

候选需要同时回答两件事：目标阶段或整帧是否确实改善，以及玩法信息与生命周期是否仍然正确。合并实例还要回到真实分布看剔除；改GPU模拟要看另一侧余量；减材质或粒子要看轮廓、亮度和时机；调整预算要看高压下关键提示及恢复；固定范围则要通过全寿命与边缘重入。

若变化小于重复测量的波动，就写“当前样本无法确认收益”。若CPU减少而整帧未变，可以报告释放了CPU余量，但不要改写成帧率提升。没有项目与目标硬件时，这篇文章只能帮助准备比较，不能替代真实的毫秒和视觉结果。
