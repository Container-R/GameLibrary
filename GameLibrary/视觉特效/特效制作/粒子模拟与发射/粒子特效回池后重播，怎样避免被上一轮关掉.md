# 粒子特效回池后重播，怎样避免被上一轮关掉

连续两次命中共用了一个火花实例。第二次命中时，火花混进了上一轮的烟；把旧粒子清掉以后，第二次火花又突然消失。前一个问题是粒子还留在模拟里，后一个可能是上一轮的结束回调归还了正在使用的实例。清掉粒子不会撤销已经排队的回调，给回调加校验也不会清掉烟。

## 停止发射，不等于这一份可以再借

停止发射只是停止补充新粒子，已经出生的烟仍可衰减；暂停则冻结模拟，继续等墙钟不一定会消散；清空则直接丢掉旧粒子。这三种操作对应不同的美术意图。Unity 6.0 的内置粒子系统把停止方式明确分成 `StopEmitting`（保留已发粒子）和 `StopEmittingAndClear`（移除已发粒子）；暂停不是其中一种。[1]

要保留原地的烟，实例应从“播放中”进入“收尾中”，保留它需要的渲染和模拟，不移动到停放点，也不放进空闲列表。资产要列清楚收尾还要等谁：主粒子、仍可能发粒子的子系统、拖尾、灯光或尾音。能独立收尾的尾音可以移交给音频系统，而不是让粒子实例一直占着池位。以 Unity 为例，`IsAlive(true)` 可以把层级内的子粒子系统纳入判定，但不会替你等待独立灯光、声音或将来才触发的外部任务。若允许已经出生的粒子在死亡时再发出尾部子粒子，就不能把“主发射停止”当成“再无新粒子”。先关闭新的外部触发，再按资产巡查仍在生效或已约定要触发的部分。[2]

要立即重播，则走抢占路径：先让旧租用失效，再解绑定或取消未完成任务，按资产清单清理旧粒子、尾迹和可变参数，设置新的变换、材质参数和种子策略，再启动新一轮。不要把“关闭后重新打开节点”当作重置合同。比如 Godot 4.5 的 `GPUParticles3D` 文档指出，一次性发射器在收到 `finished` 后短时间内把 `emitting` 设回 `true` 仍可能不重播；需要立即重新开始发射周期时用 `restart()`。这里说的是发射周期，不是保证画面在函数返回前已经更新，更不包括取消应用的回调。[3]

## 归还的不是节点，而是某一次租用

每次从池取出实例，给它一个新的租用编号，例如同一槽位先后使用 17、18。注册延迟操作时捕获当时的编号，不能在回调执行时才去读槽位当前编号，否则旧任务会拿着新号码被放行。对每个尾部组件的完成消息也做同样的校验，再从待收尾集合中移除对应组件，重复消息不得减掉别的组件。最后一项完成后才归还。下例假定池的状态只能在游戏主线程修改：

```text
beginDrain(slot):
    slot.state = DRAINING
    id = slot.lease
    // 预先记录所有仍需等待的组件；注册后重新检查已完成的组件。
    slot.pending = tailPartsToWaitFor(slot)
    subscribeCompletion(slot, eachPart, captured=id, callback=partDone)
    stopNewTriggersAndDrain(slot)
    // 把已完成组件和空集合一并处理，避免等一个不会再来的信号。
    recheckCompletedPartsAndTryReturn(slot, id)

partDone(slot, id, part):
    if slot.state != DRAINING or slot.lease != id: return
    slot.pending.removeIfPresent(part)
    if slot.pending.isEmpty(): tryReturn(slot, id)
```

`tryReturn` 要再次检查编号和收尾状态，在将实例放回空闲表前先进入“归还中”，再执行可能触发信号的清理，最后只入表一次。立即抢占时同样先标记“重置中”并换编号，再清理和启动；清理过程中同步到来的旧回调也不能归还。待收尾集合登记的是负责收尾的组件或已预约的任务，不是当前可见粒子的快照。如果某组件眼下没有粒子，却还有一次已预约的死亡触发或延迟发射，必须等触发和后续尾效完成，或明确取消该触发，才能移出集合。上面是流程示意：如果接口可能在 `subscribeCompletion` 或停止时同步报告完成，让这些回调先排队，等本次设置结束再由同一主线程处理，或者在设置阶段阻止最终归还。后台线程的结果也先带编号投到主线程，不能把“检查”和“归还”拆成两条并发路径。

有一种回调无法只靠编号补救：如果底层异步完成通知只有节点、没有旧播放标识，而且新监听器也会收到迟到的旧通知，新监听器捕获的恰好是新编号。此时需要底层按播放实例标识结果，或者隔离新旧节点，等旧通知可靠排空后再复用。编号能挡住**已绑定到旧租用**的回调，不能事后辨认来源不明的信号。

## 验收时，让旧通知真的撞上新播放

在 Godot 4.7.2 的无窗口实验中，真实 `CPUParticles2D` 自然播放时，第 20 个检查点第一次读到 `emitting=false`，到第 34 个检查点才收到 `finished`。另一组在检查点 6 显式停止发射，当场没有完成信号，到了 23 才收到。这个版本的连续模式在**显式停止后**也出现了完成信号，因此不把“一次性会自然结束”反推为“所有连续节点停止后必定没有信号”，也不把这里的结果当作跨引擎保证。单独重播的实例在检查点 10 调用 `restart()`，只在 42 收到一次完成。源码显示该 CPU 节点的重播会重置模拟时钟与粒子活动标记；实验只读节点状态和信号，没有数画面里的粒子。[4]

在同一实验里，真实的 `SceneTreeTimer` 在检查点 15 交回旧编号 17，而实例已经在检查点 10 借给 18。不验证租用的一侧立即被标记为不再使用；另一侧拒绝旧通知并保持有效。这个定时器是故意安排的旧业务回调，不是引擎错误地发出了两次 `finished`。在项目里验收时，可把两轮颜色设不同，在旧通知到达的同一帧记录槽位、收到的编号、当前编号、收尾集合和池状态：旧色残留先查重置；新色消失且收到了旧编号先查归还逻辑。再重复投递一次同编号完成消息，确认实例只入表一次。最后在目标渲染器验收首帧和尾迹，不能用这份无窗口日志证明画面已经清干净。

池满时不要被动混用两条路径。需要留下烟雾和拖尾，就给收尾实例预留容量，或者为此类尾部单独留池；硬上限下，对不重要的视觉效果可以丢弃新请求或按优先级抢占，而重要的玩法预警要保留最低可读性。收尾超时可用作报警或可接受的强制清理上限，不能把墙钟超时当作粒子、声音一定播完。暂停与不可见时是否仍推进模拟，应在目标引擎和资产上核对。
