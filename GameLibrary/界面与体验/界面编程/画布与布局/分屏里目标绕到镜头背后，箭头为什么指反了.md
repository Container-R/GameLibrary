# 分屏里目标绕到镜头背后，箭头为什么指反了

双人分屏时，队友从二号玩家的右侧跑到镜头后面，导航箭头却突然跳到左边。还有一种症状：方向对了，箭头却贴在两块画面的分界线上，而不是二号玩家自己的屏幕边缘。第一个问题要查投影的深度，第二个要查用的是哪块视口。调箭头旋转角或加大边距，都无法同时修好这两件事。

本文采用一种明确的界面规则：目标在镜头后面时，箭头仍提示目标位于相机的哪一侧。它不是罗盘，也不保证给出玩家的最短转向指令。

## 投影能算出坐标，不代表目标在那里

把世界中的目标先换到**该玩家的相机坐标**，记横向、向上和向前分量为 `x, y, d`。对于对称透视、UI 像素向下的例子，在镜头前时有：

```text
屏幕位置 = C + (fx × x, −fy × y) / d
```

`C` 是该视口的投影中心，`fx/fy` 是把相机方向换成像素的一对焦距。这个式子是透视除法在所定坐标下的写法：标准透视的齐次分量 `w` 与这里的前向深度同号。当除数接近 0，投影会突然跑得很远；除数变成负数，横向和纵向偏移都会反向。把这个坐标再限制到矩形内，只会把错的一侧固定下来。[1]

先判目标能不能当作前方投影点使用，再看投影是否落在允许画标记的区域。Unity 的 `Camera.WorldToViewportPoint` 返回相对于这个相机的归一化坐标，原点在左下，另带世界单位的相机深度；别只截取返回值的 XY。Godot 的 `unproject_position()` 返回视口坐标，文档提示用 `is_position_behind()` 避免为镜头后的物体画前方标签。Godot 4.7.2 的这个检查使用近裁剪面：在眼点前方、但还没到近裁面的点也会被标记为真。别把任何一个接口单独当成完整可见性检测：远裁面、视口边界和遮挡仍是不同问题。[2][3][4]

## 用相机方向求交，再放到自己的画布上

1. 为每个玩家拿相机和**实际显示矩形**。如果在窗口坐标算，先把显示矩形、需要避开的安全区和 HUD 保留区域换到同一坐标空间。本文以投影中心 `C` 为起点，把箭头中心允许落入的范围做成内缩矩形，并假设 `C` 在里面。边距要考虑图标本身（含旋转后可能伸出的部分），不是只给中心留 1 像素。
2. 若正深度通过近/远范围检查，而且投影点在允许矩形内，就用普通点标。其余目标若按设计仍需提示，用像素方向 `D = (fx×x, −fy×y)`。它在前方和正确投影平行，到了相机后面也不被负深度翻向。**这条射线是提示规则，不是让镜头后的物体重新参与渲染。**
3. 从 `C` 沿 `D` 取第一次碰到内缩矩形的位置。若内缩对称，半宽、半高为 `hx, hy`，则 `t = min(hx/abs(Dx), hy/abs(Dy))`，某分量为零时跳过对应的边，结果是 `C+tD`。若安全区不对称，就按分量正负取对应边与 `C` 的距离，再算正向的最小交点。不要分别钳住 X 和 Y：两轴同时越界时逐轴钳位经常把箭头挤到角上，改变指向。
4. 在同一 UI 坐标中用 `atan2(Dy,Dx)` 求方向，按图标原本的朝向调整角度。若 HUD 是玩家局部坐标，先在局部算，合成至窗口时只加一次起点；若 HUD 覆盖整窗，就按显示矩形转换为全局坐标后再映射到逻辑画布。[3]

正后方 `x=y=0`，此时没有唯一的侧向。可以暂时隐藏箭头，或在进入一个小角度范围时保留上一帧的稳定方向，离开更大范围后再恢复计算，避免跟着细微数值误差左右翻。若界面要求明确「往哪边转身」，应另选基于角色或相机水平朝向的角度政策，并单独做正后方的选边规则。偏轴、正交、立体投影也不要直接套本文的中心和焦距公式。

## 用同一目标检查投影，再移动视口检查归属

在 Godot 4.7.2 无窗口试件中，用左右两个 640×720 的 SubViewport，两个相机同姿态，竖直视野 90°，近面 0.1，UI 向下。世界目标只改深度、横向和高度不改；右视口合成起点是 `(640,0)`，留边 18 像素。相机 API 读数如下：

| 前向深度 | API 判「behind」 | 右侧视口局部投影 | 贸然加起点后的窗口坐标 |
| ---: | --- | --- | --- |
| +5 | 否 | (392,324) | (1032,324) |
| −5 | 是 | (248,396) | (888,396) |

两个窗口坐标都可能落在右玩家的画面里。只问「坐标是否在屏幕上」无法区分它们。改用相机横向、纵向分量和射线求交，后方目标在右玩家的箭头中心是 **(1262,209)**，在左玩家则是 **(622,209)**；两者相差恰好一个视口起点差。正后方的测试点无侧向，试件不生成边缘位置。试件还验证了眼点前方 0.05 的点被近裁检查挡住。这些是引擎投影 API 与几何求交的读数，没有实际绘制 HUD 或测玩家对箭头的理解。

在项目里先固定相机，扫过左前、右前、近裁面、左右后和正后，记录相机本地三分量、是否使用投影、箭头局部位置。然后固定点与相机相对关系，只改变分屏布局、玩家面板起点、宽高比或画布比例，重新对应实际显示矩形。若第一组翻向，查深度与方向政策；若第二组落到错误玩家或被切边，查坐标转换及图标占地。最后加回真实安全区、黑边和镜头转动，看箭头是否仍留在自己的视口里。
