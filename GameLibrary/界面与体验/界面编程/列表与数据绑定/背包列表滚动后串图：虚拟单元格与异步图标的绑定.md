# 背包列表滚动后串图：虚拟单元格与异步图标的绑定

背包快速向下滚动，药草名称已经出现，图标却短暂还是上一把剑；有时药草图标先正确显示，随后又变成剑。两种现象很像，修法却不相同：前一种可能是复用时没撤下旧图片，后一种可能是旧加载结果覆盖了新绑定。把贴图加载得更快，最多让问题更难碰到。

本文面向熟悉回调和 UI 数据绑定的界面程序员，以 Unity 6000.0 UI Toolkit 的 ListView 生命周期为接入背景，给出单元格复用、列表重排与异步图标交付的一套应用约定。加载器用可控替身复算；不涉及图集打包、纹理解码或 GPU 上传优化。

## 屏幕上的格子不是背包里的物品

虚拟列表只维护显示所需的视觉元素，滚动时重复使用它们，而不是为每件物品永久建立一个控件。Unity 的 ListView 示例在 `makeItem` 创建元素，在滚动复用时用 `bindItem(element, index)` 关联当时的数据项；`unbindItem` 解除这种关联，`destroyItem` 对应元素不再需要时的清理。官方还提醒，自定义绑定与解绑需要配套，不能无条件混用另一半的默认实现。[1][2]

设可视单元格 V 原先显示物品 A，滚动后改显 B。V 仍是同一个对象，A 的图标请求也可能还在路上。这里至少有四种身份：

| 身份 | 能回答什么 | 不能替代什么 |
| --- | --- | --- |
| 列表索引，例如第 7 项 | 当前排序里的位置 | 删除、筛选、排序后不一定还是同一物品 |
| 稳定物品 ID | 当前表示哪件业务物品 | 同一物品可以被解绑、重新绑定多次 |
| 图标资源键及版本 | 此次应显示哪份资源 | 不同物品可以共用图标；同一物品也可以换皮肤 |
| 本次绑定票据 | 哪一次绑定仍有权写这个控件 | 不证明资源内容本身正确或已经加载成功 |

票据是应用分配的身份，不是 ListView 的索引。本例每次绑定都生成不复用的票据，回调捕获它；解绑后立即撤销。单元格实例不变、物品 ID 不变，都不意味着旧票据仍有效。

只检查物品 ID 能挡住 A 的结果写进 B，却挡不住 A→B→A：第三次绑定 A 已成功，第一次 A 的失败刚到，若只比 ID，它仍会把新图改成错误占位。即使两次 A 的图标键也相同，这仍是两次不同的展示请求。若项目要合并同资源加载，应在资源层共享工作，而不是把各单元格的展示资格合并。

## 绑定开始时先清掉旧画面，完成时再检查谁有资格写

本例选择明确的显示政策：新绑定立即显示加载占位；当前请求失败显示错误占位；旧请求的成功和失败都不改当前格子。它会增加占位出现的次数，但不会拿上一件物品的图标冒充新物品。缓存命中可以直接取得正确图，仍应先建立新绑定身份。

每个单元格持有当前目标的快照：物品 ID、图标键、图标版本，以及当前票据、是否绑定、已显示资源的持有记录。快照只包含此次需要的不可变值，不保留一个会被其他代码原地改写的物品对象作为“旧输入”。

下面的伪代码强调交接顺序。假设绑定、解绑、模型更新和完成处理在同一 UI 串行队列运行；图标赋值和撤下操作不会调用能重入绑定的业务监听器。在 Unity 中，这条队列应在主线程执行。后台加载完成先投递到该队列；从资格检查到赋值之间不插入 `await` 或其他可能重入绑定的调用。若项目不满足这些条件，应先增加串行化或重入保护。

```text
Unbind(cell):
    cell.bound = false; cell.ticket = 无       # 先撤销资格
    请求取消旧工作（如果加载器支持）
    撤下旧图、名称、错误和加载状态
    结束旧显示资源的本方持有
    清掉 cell 的旧目标和请求引用

Bind(cell, index):
    Unbind(cell)                              # 不依赖外层恰好先调用解绑
    target = 复制当前 items[index] 的 ID、名称、图标键和版本
    ticket = 新的绑定票据
    cell.bound = true
    cell.ticket = ticket; cell.target = target
    写入 target 的名称；显示加载占位
    启动加载(target.图标键与版本,
             result => 入队 Complete(cell, ticket, target, result))

Complete(cell, ticket, target, result):
    若 cell 未绑定，或 ticket 不是 cell.ticket，或目标快照不匹配:
        仅收尾这份 result 的持有；不修改 cell；返回
    若失败:
        显示本次错误占位；返回
    撤下并结束旧显示持有
    将 result 的持有交给 cell，写入新图
```

加载接口还要把启动时异常转为对应请求的失败，约定一次终态通知和清理责任。不要在回调里读取“当前票据”再给结果盖章，旧结果会因此伪装成新结果。失败、错误角标、加载旋转图标的关闭也要走同一道资格检查，不能只保护成功图片赋值。

若缓存回调能在启动调用中立即发生，先保存目标和票据，再启动；本例额外把完成处理排队，避免回调修改尚未初始化完的请求记录。取消函数也可能触发通知，所以解绑必须先撤销票据。注销的是旧绑定自己的事件订阅，不能让迟到清理去移除新绑定的监听器。

## 取消减少工作，票据决定结果归属

请求取消不是完成证明。.NET 的取消模型明确采用协作方式，由被调用操作响应请求。[3] 其他加载接口有各自约定；本文不假定它们都支持取消，也不假定成功取消后仍必定回调。接入时要确定“取消已终止”“成功”“失败”怎样收尾，不能一直留下等待记录。

安全性要求更直接：**即使旧回调仍然到达，它也不能写新绑定。** 资源系统可以继续加载、放入共享缓存或通知其他使用者；失效的单元格只撤销自己的展示资格。共享加载有多个订阅者时，移除一个格子的订阅不应擅自取消别人仍需要的工作。

忽略结果不等于忘掉资源。本文的模型让每个成功结果带一份可释放的持有：过时结果立即归还，当前显示期间保留，解绑后归还。实际 Addressables 句柄、缓存租用或其他资源接口必须按各自合同适配，不能同时在取消和完成两个入口无条件释放同一份引用。相关的完整加载收尾可读[关闭装备预览后，未完成的资源加载怎样收尾](../../../引擎与工具/运行时系统/异步资源/关闭装备预览后，未完成的资源加载怎样收尾.md)。这里的新增约束是：同一个控件在存活期间会反复换绑定，而不只是窗口关闭。

## 列表重排必须让控件重新认识当前位置

物品排序、筛选或删除可能让索引 7 从剑变成药草。异步回调不能等返回时再查 `items[7]`，把当时加载的剑图写到现在找到的药草控件上。索引只在绑定入口用于取数据，随后的请求使用捕获的稳定 ID、图标版本和绑定票据。

同样，票据无法发现一个应用根本没有通知 UI 的数据变化。若模型已经排序，单元格却仍保留旧绑定，比较旧票据会继续成功。项目应把模型变更与可视绑定刷新安排在同一个受控更新阶段，在下一次结果提交或显示采样之前使受影响的旧绑定失效。Unity 文档提供 `RefreshItem`、`RefreshItems` 与 `Rebuild`；通常数据刷新使用前两者，整表重建更昂贵，并用于文档列出的数据源类型或构造逻辑变化等情况。[4] 不要把“每次都重建列表”当作异步归属检查的替代。

例如两行原为 `[剑, 药草]`，变为 `[药草, 剑]`。刷新后，两行各自得到新票据；之后再交付排序前的两个请求，它们都应被拒绝。若只校验行索引，索引 0 仍等于 0，反而会把剑重新写回第一行。

同一物品换皮肤或图标版本，也要触发相应重新绑定。物品 ID 不变并不等于显示内容没变。若底层缓存忽略资源版本，返回了错误纹理，即使绑定检查通过也仍会显示错图；这时应查资源键解析和缓存内容，而不是继续增加绑定票据。

接到 ListView 时，可在 `makeItem` 创建一次单元格控制器，在 `bindItem` 更新目标并启动上述流程，在 `unbindItem` 撤销资格，在 `destroyItem` 清除长期订阅并做幂等的最终清理。窗口关闭也应主动让自己管理的所有活动单元格失效，不靠某个迟到回调猜窗口是否还开着。具体回调触发顺序仍需在所用 Unity 版本记录核对。

## 在每次完成之间检查，而不是只看滚动停稳后的截图

先放慢到可控的两件物品、一个可视单元格，给加载器装上可以手动放行完成的替身。记录单元格实例、绑定票据、物品 ID、资源键与版本、绑定时索引、完成顺序和实际图标提交。仅有“资源加载完成”日志，不能证明写进了哪个格子。

| 安排 | 本文政策的检查点 | 排除的错误 |
| --- | --- | --- |
| A 已显示，绑定 B，B 尚未返回 | 此刻立即是加载占位 | 仅拒绝旧回调，却保留旧像素 |
| 绑定 A 后绑定 B，先完成 B 再完成 A | B 继续显示，A 不产生图标提交 | 只请求取消，仍接受迟到结果 |
| A→B→A，新 A 成功，旧 A 失败 | 新 A 不变成错误提示 | 仅比较物品 ID 或资源键 |
| 两行实时交换位置，新请求先完成 | 排序前结果不得覆盖当前两行 | 把位置索引当成物品身份 |
| 解绑或关窗后完成 | 没有 UI 写入，结果被收尾 | 只看控件对象仍存在 |
| 当前 B 失败，旧 A 后成功 | B 保持本次错误状态 | 擅自用旧成功结果回退 |

原创 Node.js 试件执行了这些分支，并加测同物品资源版本更新、同步缓存完成入队和控件替换。正常方案通过九组断言；“只取消”“只比 ID”“只比索引”“不清旧图”各有指定反例。试件没有 Unity、纹理或真实滚动，验证的是给定交错下的应用状态和本方持有，不是帧率或可见画面。

随后在实际项目中保留同一绑定路径，用真实 ListView 快速滚动、反向滚动、改变排序和关闭窗口；覆盖缓存命中、失败与重复进入相同物品。每次真实图标提交都检查资格，并配合录屏或帧采样确认是否出现可见串图。提交日志能证明旧写入被拒绝，却不能证明样式、图集或渲染已经正确；反过来，最终一张正确截图也可能漏掉此前的旧图。

全面关闭复用或预加载整个背包，会改变内存与等待成本；它们可以成为特定规模的选择，但不应在未测成本时当作免费修复。保留虚拟化、限定可见请求、合并同资源读取，可以控制负担；每个绑定仍要单独判断是否接纳结果。这样资源加载慢时只是等自己的图，而不是借来别人的图。
