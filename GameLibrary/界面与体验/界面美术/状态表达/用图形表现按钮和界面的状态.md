# 用图形表现按钮和界面的状态

一个“装备”按钮变灰了，但手柄焦点还停在上面。玩家按下确认，没有反应：是装备条件不满足，还是按钮已经接收操作、正在处理？如果焦点边框也跟着变淡，玩家甚至不知道下一次按键会落在哪里。

这不是多画一张“禁用状态图”就一定能解决的问题。同一个控件可能需要同时说明自己是谁、输入指向哪里、当前能否操作，以及刚才的操作处理到了哪里。UI，也就是用户界面，美术制作的一项重要工作，是让这些含义在有限空间里相处，而不是用同一层灰色把它们全部盖住。

本文面向 UI 美术、UX（用户体验）设计师和界面程序员。我们以装备界面中的列表和一个“装备”按钮为例，讨论怎样拆分状态、安排图形、说明组合规则，再把样稿交给实现者。例子是原创设计推演，尚未制作或测试；不是对某款游戏界面的复刻，也不是所有按钮都该采用的规则。

## 先问按钮在说什么，再决定它是什么颜色

设想一个装备界面：左侧显示物品列表，右侧显示选中物品的属性，下面有一个“装备”按钮。项目允许查看尚不能装备的物品，因此“选中了某物品”和“可以装备它”是两回事。

这里还要区分**选择**与**焦点**。选择表示当前查看或操作的对象；焦点表示键盘、手柄等输入当前指向的控件。玩家可以选中一把剑，然后把焦点移到“装备”按钮。列表里的选择标记不应该因为焦点离开就自动被理解成物品不再被选中。

按钮也有几种不同含义：

- **可用或禁用**：此刻能否发起装备操作，以及不能操作的原因。
- **焦点**：当前输入是否指向它。
- **按下反馈**：一次操作过程中的短暂反馈，不代表装备已经成功。
- **处理中**：请求已经进入处理阶段，但尚未得到最终结果。它不一定意味着正在下载资源，也不保证存在可显示的进度百分比。

这些不是四张互斥的图片。例如“不能再次提交”和“仍有焦点”可以同时成立。不过，不应为了凑齐状态表，假定所有组合都合法：某个项目可能让禁用控件退出焦点导航，也可能保留焦点以便解释原因；按下反馈是否持续到处理中，同样要由设计决定。

因此，美术开始绘制前，需要和 UX、程序先确认实际允许的组合。否则程序可能采用“最后一次设置的颜色覆盖前一次”的办法，而这个偶然顺序就变成了玩家看到的状态规则。

## 风格可以克制，含义不能靠猜

《NieR:Automata》的 UI 设计师 Hisayoshi Kijima 在制作回顾中说明，受限配色下曾用字体粗细和明暗表现数值差异，也为芯片类别保留颜色区别；他的流程包含设计、交给程序实现，再在游戏中调整。[1] 这个案例值得借鉴的不是照搬米色，而是：风格限制存在时，仍要为不同信息寻找可用的表现手段。

Bandai Namco Studios 的铃木佑梨在《Tales of Arise》制作介绍中谈到克制的基础配色、特定时刻的强调，以及繁忙战斗背景和多语言文字长度带来的考虑。[2] 这提醒我们，控件不是一直放在设计软件的空白画布上。但这些制作陈述不能证明本文的按钮方案已经容易理解，也不提供通用的可读性阈值。

可以把形状、位置、文字、字重、明暗、颜色和变化过程看成不同的**图形通道**：它们是传递含义的手段。例如，颜色可以辅助说明不可用，原因文字则告诉玩家为何不可用。多用一种通道不自动等于无障碍达标，但避免把关键含义只压在一种颜色上，至少能让团队明确还需要检查什么。

## 给同一个按钮分配几块不互相抢占的位置

下面为例子选择一套候选方案：不能装备时，按钮仍允许获得焦点，以便玩家看到原因；操作被接收后，保留焦点，但不允许重复提交。这里只是明确本例的规则，不建议所有界面照做。

先按含义分配表现，而不是先堆出许多效果：

| 要传达的内容 | 本例的表现安排 |
|---|---|
| 这是装备操作 | 稳定的文字“装备”；必要时配功能图标 |
| 输入当前指向这里 | 按钮外侧独立边框或标记 |
| 当前不能装备 | 可读的原因文字，例如“等级不足”；按钮内容可适当弱化，但不抹掉原因 |
| 一次操作正在被按下 | 短暂的填充或位置变化；不单靠改变焦点边框 |
| 请求已接收、尚未结束 | 文字改为“处理中”，可辅以动态标记；不伪装成已经完成 |

“独立”说的是作用范围，不要求每一种含义都成为一个引擎节点。美术可以用图层标注样稿，程序可以用适合项目的组件结构实现，只要组合后表达的内容一致。

比如禁用时降低整个按钮父容器的透明度，可能连焦点边框和原因文字一起变淡。此时先检查淡化究竟作用在哪些部分，而不是马上把所有资源画得更亮。反过来，如果边框独立保留，仍需检查它是否会被裁剪、遮挡，或者在背景上不明显。样稿分了层，并不意味着实际界面已经正确显示。

## 把优先级写成具体情境，不是一个万能状态排行

当状态同时出现时，团队常说“加载优先于按下，禁用优先于焦点”。这种总排行容易误伤本应保留的信息：处理中可以替换操作文字，却不必抹掉焦点位置；不能再次提交，也不等于没有必要解释当前在做什么。

更实用的做法，是逐个说明哪个部分改变、哪个部分保留。本例可以先做四张组合样稿：

| 情境 | 本例希望看到什么 | 不应让画面暗示什么 |
|---|---|---|
| 条件不足，但按钮有焦点 | 保留焦点标记，显示不能装备的原因 | 有边框就一定可以执行 |
| 可用按钮获得焦点并被按下 | 焦点不丢，按下反馈出现在约定区域 | 按下反馈已经证明装备成功 |
| 操作已接收，按钮仍有焦点 | 保留焦点，“处理中”替换原操作提示，结束短暂的按下反馈 | 同一请求还能反复提交，或结果已经成功 |
| 处理失败，允许重试 | 结束处理提示，说明失败；是否恢复可用由实际条件决定 | 旋转标记消失就代表成功 |

最后一行尤其需要程序参与。图形动画结束不是业务完成的证据：如果实际结果尚未返回，不能仅因动画播完就显示成功；如果条件已经变化，也不能只恢复旧的“可用”图片。

这些是本例的表现与交互约定，尚未验证。允许重试、失败原因、取消处理等行为必须来自产品设计和实际状态，不能由美术样稿自行创造。

同样的方法也适用于旁边的装备列表。选中一件暂时不能装备、但攻击数值更高的物品时，选择标记、不能装备的原因、数值比较可以同时存在。“数值上升”不取消装备限制，而且数值更高是否更有利，还取决于属性含义和比较对象。如果界面决定隐藏某类比较，应明确隐藏条件，而不是让三层效果叠加后偶然看不见。

## 交给程序的不只是切图

**切图**是把设计中的图形部分导出为可使用的资源。交付按钮时，除了这些资源，还应让实现者能重建上面的含义关系。

一份精简的交接可以围绕同一个按钮完成：先给出基础样稿，再用组合样稿标注焦点边框、文字、填充反馈和原因提示的作用范围；指出哪些状态来自交互系统，哪些来自装备条件，哪些等待请求结果。说明文字可以替换、何处允许扩展，以及空间不足时应回到哪个设计决定，而不是让程序自行缩小所有文字。

变化过程也需要画清楚。至少说明按下反馈何时开始和结束，进入处理后哪些部分保留，失败后回到什么可观察状态。这不要求美术编写请求系统，而是避免一张漂亮的“处理中”图片掩盖没有定义的退出情况。

职责可以由同一个人兼任，但问题不能合并：UX 与玩法设计确定行动含义和允许的操作；UI 美术组织视觉层级与风格；界面程序把实际状态接到组件。美术能够在讨论中提出交互改进，程序也能发现图层与布局限制；这不是必须依次交棒的固定岗位制度。

## 先检查组合，再检查真实使用

设计软件里的四张样稿只能回答“打算怎样表达”。把控件放进实际界面后，还要检查它是否真的按约定显示。可以沿着本例走一遍：查看条件不足的物品，把焦点移到按钮；换成符合条件的物品并操作；进入处理；再观察失败或成功后如何退出。

检查时不要只问是否好看，还要核对三件事：当前实际状态是什么，显示的文字和图形是什么，玩家此时允许做什么。若三者不一致，应先修正状态连接或组合规则，再决定是否重画。

接着换成实际会遇到的背景、缩放尺寸和语言文本。原因文字是否被裁掉，焦点提示是否被装饰遮住，处理提示是否挤掉关键操作名称，都是需要在候选界面里观察的问题。颜色之外的文字和形状也可能太小、被隐藏或难以理解；不能因为它们存在，就宣称所有人都能看懂。

实现对应正确之后，玩家是否理解仍是另一层问题。真实输入导航、不同设备操作、语言质量和无障碍需求，需要各自适当的检查与用户研究。本章没有制作这些界面，也没有测量误读率或证明某种图形组合优于另一种。

最后要保留取舍：每增加一种提示，都会占用空间，增加资源和组合维护成本；重复使用同一种提示，又可能混淆含义。先覆盖项目真实存在、影响行动判断的组合，发现空间冲突时回到布局和信息优先级，而不是无目标地画出所有状态排列。
