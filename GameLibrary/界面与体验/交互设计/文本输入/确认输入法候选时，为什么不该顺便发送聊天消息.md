# 确认输入法候选时，为什么不该顺便发送聊天消息

玩家在游戏聊天框里打出拼音，按 Enter 接受候选词，还没来得及补完句子，消息就发出去了。输入框一直有焦点，文字也显示正常，错误却发生在最后一次确认上：同一个动作被解释了两次，一次是选字，一次是发送。

这是本文设定的虚构场景，不是已复现的游戏故障。文章面向游戏用户界面（UI）和输入程序员，讨论怎样区分按键、输入法正在组成的文字、已接纳的编辑内容与应用发送。我们用固定网页规范中的一个序列说明判断漏洞，再用 Unity Input System 的接口职责说明接入时应查什么；不提供适用于所有输入法的编辑器实现，也没有运行浏览器、游戏或合成事件测试。

## 确认一个词，不等于确认整条消息

**输入法编辑器（IME）**让玩家通过拼音等方式选择最终文字。正在组成、尚可改选的内容通常称为 composition 或 preedit；它与聊天框里已经接纳的文本不是同一种状态。

这里需要分清四层信息：

| 层次 | 在聊天例子中回答什么 | 不能直接推成什么 |
|---|---|---|
| 按键输入 | 某个键按下或松开了吗？ | 玩家已经输入了哪个最终汉字 |
| 正在组字的内容 | 当前准备接受或修改哪段文字？ | 这段文字已经成为消息正文 |
| 编辑组件接纳的文字 | 草稿现在包含什么？ | 玩家同意发送整条草稿 |
| 应用发送意图 | 是否按产品规则提交这条消息？ | 服务端已经接收、允许或投递成功 |

即使玩家已经确认了候选词，仍可能继续编辑、删除或取消整条消息。因此，收到最终文字时应更新草稿，而不是自动发送；组字结束时也不能自动发送。W3C 的 `compositionend` 明确包括完成和取消两种结束原因。[1] 网页中的 `input` 也可能在组字期间发生，不能把每个 `input` 都当作最终接纳文字的通知；应按实际编辑组件的职责判断草稿状态。[3]

还要避免另一种重复：如果所用控件已经把输入法结果写入文本，外层又将结束事件里的字符串追加一次，文字可能被重复接纳。应由一个明确的编辑组件负责应用文本变化，其他系统读取其结果；不要同时把控件结果与底层通知当成两份新输入。这里是接入检查建议，不是断言所有控件默认都会重复写字。

## 松开 Enter 时“不在组字”，仍可能是刚才那次选字

一个看似合理的修复是：只在 Enter 松开时发送；如果此时还在组字，就忽略。问题在于，松开时的当前状态不一定能说明这次按键开始时做了什么。

W3C UI Events 的 2026-02-21 工作草案 §3.6.5 给出了退出组字的序列：退出用的 `keydown` 标记 `isComposing=true`，随后是 `compositionend`，对应的 `keyup` 已标记为 false。[1] 把它用于本文假设——这次退出键恰好是用来确认候选的 Enter——就有：

| 时刻 | 来源序列中的状态 | 本例应保留的动作含义 |
|---|---|---|
| Enter 按下 | `isComposing=true` | 这次按键用于输入法确认 |
| 组字结束 | `compositionend` | 编辑会话结束，不产生发送意图 |
| 同一 Enter 松开 | `isComposing=false` | 仍是刚才那次按键的后半段，不是一次新确认 |

因此，“松开时 false”不足以证明这是一笔独立的发送操作。这个反例只采用该草案给出的条件序列，不声称所有浏览器都这样发送事件，更不把网页属性当成游戏引擎的字段。

也不能简单改成“只看 keydown 就万事大吉”。需要核对所用组件是否能可靠识别组字和消费按键、是否接收自动重复、以及事件是否还会流向外层快捷键。换一个回调位置，不等于已经明确了输入归属。

## 让文本组件处理选字，让发送另有明确资格

对开头的单人聊天框，可以先作一项应用层约定：**选字使用的确认动作只完成编辑；发送必须来自另一个符合当前规则的操作。** 这是产品和接入策略，不是规范替游戏规定的交互。

落实时，先由文本组件接收和处理输入法信息。若输入层能够识别某次按键已用于组字确认，就应保留这次动作的归属，不能在组字结束后，把它的松开或重复通知重新提升成发送。组字状态可以结束，但这次按键的用途不会因此倒改。反过来，也不能一律吞掉组字结束后的下一次 Enter：那可能已经是玩家重新按下的独立发送操作。

发送处理应读取当前有效聊天框的已接纳草稿，并确认发送动作没有被编辑过程消费。若平台没有暴露足够的按键配对或消费信息，就不能假造一个跨平台布尔值来填补；应依赖该文本组件明确提供的提交接口，或选择能在目标平台清楚区分的交互，再验证它的行为。

例如，产品可以规定选字后再按一次 Enter，或者使用单独的发送按钮。但按钮也不是天然绕过问题：玩家在组字中点击它时，是先接受当前候选、取消临时内容，还是暂不发送，应有明确规则，并核对组件实际完成了哪一步。不能点击后马上读取旧草稿，又假定尚未交来的文字必然包含在消息里。

还要列清实际发送入口：自定义按键监听、控件 Submit、发送按钮，以及网页表单默认行为。只拦一个监听器，不代表同一动作不会从另一入口再次进入发送。HTML 规定，在用户代理支持隐式提交、表单默认按钮具有激活行为且未禁用等条件下，隐式提交会触发该按钮的 `click`。[4] 这不是说每次输入法 Enter 都必然触发提交，而是提醒接入者核查自己的表单与组件路径。

不要用“延迟一帧再发送”代替这项决定。延迟可能改变事件相遇的时间，却没有解释这次确认究竟属于编辑还是发送。也不要为了阻止业务动作，盲目取消所有 Enter 的默认行为：拦住应用发送、阻止事件继续传播、取消文本编辑默认处理，以及取消输入法会话，是不同动作。

## Unity 接入：启用输入法，不等于正在选字

Unity Input System 1.11 文档页面标示包版本为 1.11.2。它建议不要从键码自行拼出文本，而应使用 `Keyboard.onTextInput` 接收平台报告的字符；这个接口逐字符提供输入，不是一次交来完整的组合字符串。[2] 使用现成文本控件时，应先确认控件已经处理了什么，避免外层再追加同一批字符。

`onIMECompositionChange` 用于接收正在编辑的组合字符串变化，可供临时显示；它不是聊天发送通知。`imeSelected` 则表示输入法文本处理已启用，不能把它当成“当前正在组字”的布尔状态。[2] 否则，聊天框一启用输入法就可能永远不能发送，或把启用状态的切换误当成候选确认。

这些接口职责也没有给出跨平台的按键配对算法。前面的网页序列不是 Unity 的事件顺序保证；具体输入模块和文本控件怎样更新草稿、消费按键、发出 Submit，仍要在实际组件中核对。本文没有给 Unity 添加一个假想的 `isComposing` 字段，也不把几个回调拼成完整输入法编辑器。

关闭聊天框时，需要明确保留还是丢弃未确认内容，并检查返回游戏操作后是否仍有旧确认动作穿透。焦点恢复可另读[关闭弹窗后如何恢复操作焦点](../键盘与手柄导航/关闭弹窗后如何恢复操作焦点.md)，但恢复焦点本身不能证明文字已接纳或消息该发送。

若文字编辑正常，候选窗却在界面缩放后偏离光标，可选读[输入法候选窗为什么会离开文字光标](../../../../管理档案/支持资料/输入法候选窗为什么会离开文字光标.md)，用独立的 SDL 坐标例核对区域与光标偏移；它不是上述 Unity 或浏览器事件行为的保证。

文字已正确接纳，按名称查找却仍然失败，是另一项需要分开的检查。可选读[名称看起来相同，为什么仍然查不到存档](../../../../管理档案/支持资料/名称看起来相同，为什么仍然查不到存档.md)，了解规范等价字符串的匹配政策；它不改变这里的输入法确认规则，也不把显示名当成存档身份。

文字已经接纳，但昵称计数、选区或退格仍对不上时，可选读[昵称计数是三，光标偏移为什么却是八](../../../../管理档案/支持资料/昵称计数是三，光标偏移为什么却是八.md)，先分清计数单位、原串偏移与控件的删除规则。

## 在目标输入法里检查完整操作，而不是只模拟 Enter

下面是针对这一个聊天框的有限检查建议，尚未执行。每次记录所用平台、输入法、文本组件版本及产品规定，并同时看草稿变化和发送调用；不需要采集玩家真实聊天内容。

| 操作 | 本文示例策略下应核对什么 |
|---|---|
| 组字中按 Enter 接受候选，然后松开 | 候选被正确接纳；同次确认没有发送；没有重复追加文字 |
| 接受候选后，重新按一次发送键 | 草稿已更新；新的有效操作按约定发送，不是永久屏蔽 Enter |
| 取消组字，但聊天框原本有草稿 | 保留或撤销相应临时编辑；不能仅因结束通知发送旧草稿 |
| 长按确认键产生重复输入 | 同一次编辑操作的重复通知不变成多次发送；核对组件实际重复规则 |
| 组字中点击发送按钮 | 结果符合预定的接受、取消或暂不发送策略，不偷偷遗漏尚未接纳文字 |
| 组字中关闭聊天框，再重新打开 | 临时内容与旧动作按规则结束，不把迟到通知用到新的聊天编辑中 |

自动构造一个带 `isComposing` 的事件，可以检查应用自己的分支，却不能代替真实输入法与平台的接入检查。本文没有证明任何浏览器或 Unity 接入已通过这些项目，也没有验证完整文字编辑、跨用户输入或网络防重。

回到最初的误发，关键不在于给 Enter 再加一个条件，而在于保留它的用途：**文字被输入法确认、草稿被编辑组件接纳、玩家请求发送，是三个不同的时刻和决定。** 先把这条边界说明白，再选择目标组件能实现和验证的交互。
