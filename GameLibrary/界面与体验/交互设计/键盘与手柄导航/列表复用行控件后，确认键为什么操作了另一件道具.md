# 列表复用行控件后，确认键为什么操作了另一件道具

背包用五个行控件显示几十件道具。焦点原来在第二行的治疗药，滚动后第二行改画了另一件物品。引擎仍报告第二行有焦点，按确认却操作了新物品；另一种情况是玩家已迈到下一项，旧滚动刚结束，又把焦点拉回去了。

对使用键盘或手柄确认的单人菜单，这两种错误都需要把**玩家要操作的数据条目**和**引擎当前聚焦的行控件**分开。这里不讨论弹窗关掉后返回哪一层，也不要求给所有道具各建一个控件。目标是让复用、滚动和筛选期间，一次确认只落在玩家当次实际选定的条目上。

## 行的位置、行对象、道具是三件事

虚拟列表只维持一小批能显示的控件。Unity UI Toolkit 的 `ListView` 用创建、绑定和解绑回调复用可视元素，Epic 的 `UListView` 也明确区分数据项与实际显示的 Entry Widget。[1][2] 这节省节点，却改变了焦点引用的含义：同一个行对象还活着，甚至名字没变，也可能已经不代表之前的物品。排序后，同一个数组下标也可能换成另一件道具。

在菜单模型里用稳定的道具 ID 表示键盘或手柄的**导航目标**。背包有两把同名剑时，要用实例 ID，不能用显示名或共用的图标 ID；一条记录若被真正删除再以同 ID 重建，而旧操作不能作用于新对象，还要有数据实例版本。多选勾选状态、鼠标悬停以及导航目标是不同的，不要因其中一个变动而悄悄覆盖其他状态。

在行控件上只保存它**此刻**绑定的条目和绑定代次。代次是这个行每换一次绑定就变化的编号。重新绑定前清掉属于旧条目的订阅和交互状态，或让创建时只挂一次的通用处理器在执行时读取当前绑定；不要每次绑定都再挂一个闭包而不移除旧的。异步图标、可用状态等旧工作返回时，也不能再写入已经交给新道具的行；单元格如何清除旧图、结束资源持有，可读[虚拟单元格与异步图标的绑定](../../界面编程/列表与数据绑定/背包列表滚动后串图：虚拟单元格与异步图标的绑定.md)。最终可执行操作还应通过当前模型检查道具存在、可用和确有相应权限，焦点匹配不等于一定能使用。

## 先让目标出现在视口，再交给它确认

方向键选中一个不在视口的条目时，先把数据 ID 交给列表，滚动以显现它。此时保持一个明确的过渡状态：旧行若马上要复用，应先把行确认移出它的处理范围。例如把实际焦点临时交给一个能继续接收方向输入和取消、但不会使用任何道具的列表表面。在过渡期间不要画一个仍能立刻操作的旧行高亮，也不要把提前按下的确认存起来，等新行一出现就执行。Xbox 访问性指南对焦点指示可见性的要求，在这里对应一个可检验结果：玩家不应根据屏幕外或已经换了身份的高亮来猜下一次会操作什么。[3]

完成滚动的信号一般只说明某个步骤结束，不说明目标现在仍然正确。把等待分成两个判断：

1. **这还是当前意图吗？** 方向键、点击可操作项、切换页面或策略重算目标，都可以使旧请求失效。为每次聚焦意图发新序号；回调只有序号和页面都仍对应时，才能继续。用户在等待 B 时已经选了 C，即使 B 后来进了视口，也不能把焦点从 C 抢回去。
2. **现在显示的是这次绑定吗？** 按 ID 找当前行；检查行仍属于本列表，实际绑定匹配，已完成布局、位置没有被裁剪得不可操作，且引擎允许聚焦。若回调带着早先捕获的行与代次，须核对代次。某行 B→X→B 后仍叫 B，但原工作不再属于此次绑定。如果完成回调只是一个无载荷的唤醒通知，可以从头重新找当前 B 和它的当前代次，并重新检查，而不是继续使用旧行的几何或状态。

请求焦点之后，再核对实际接收者，并用这个位置画可见指示；只有当前意图仍有效才解除过渡。若用户用指针主动浏览别处，不一定要立刻把列表滚回旧导航目标。可以把原 ID 保作锚点但不允许离屏行收到确认，下一次方向导航再依清楚的规则进入当前可见区域，或显现旧锚点。项目应选一种一致的体验，让玩家知道操作会从哪里接续。

筛选后旧 ID 仍在结果里，只是排序位置变了，可按 ID 回到它。若它消失，不能把原下标当成原条目。背包可以选“同一筛选页里下一个可用条目；没有就选上一个；结果空则回筛选框或可见的返回入口”。例如顺序是 A、B、C、D 且选中 B，筛掉 B 得到 A、C、D，就选 C；若同时改变了排序，先按产品规定确定是在原顺序找仍可见的后继，还是进入新排序的默认入口。数据尚未齐备时走等待分支；加载失败或列表空时要能取消或返回，不能永久停在无落点的状态。

## Unity UI Toolkit：丢弃旧回调，不等于旧滚动没发生

在 Unity 6000.0.22f1 的普通 ListView 默认控制器里，框架给的 ID 默认就是索引，不是背包道具的稳定 ID。即使自定义控制器提供了稳定的 ID 映射，ScrollToItemById 也会**在调用时**把 ID 换成索引再交给滚动控制器。固定高度路径在布局待更新时可安排一次按索引的延迟重试；等待期间如果列表重排，旧请求保存的是当时的索引，不是道具身份。源码还显示，该版本有一条恢复焦点的路径记住的是行索引和行内子控件的路径。因此框架回到同一索引、同一个样式位置，并不能证明回到了同一件道具。[5]

例如 B 原在索引 1。一次需要延迟重试的滚动已经交给框架，背包却在它完成前从 A、B、C、D 改排为 A、D、C、B。如果旧索引 1 被重放，它现在指向 D。应用拒绝旧的聚焦回调，可以防止确认交给 D，**却撤不回框架已执行的视口移动**。即使同一帧内看见 B 的高亮，等行重新绑定或视口再移动，也要重新检查。这里说的是由该版源码推导的条件性风险，不是所有 ScrollToItem 调用都会延迟、导致错滚或自动聚焦。[5][6]

接入时把“发出滚动”和“交还确认”分开：

1. 列表数据改版时，先让旧行确认失效，更新数据并刷新绑定。若玩家的目标 B 还在，保留业务 ID，但废弃基于旧列表数据发出的滚动票据；按新列表重新找到 B 的索引。找不到走前面的回退规则，**不要把查询失败的 -1 传给 ScrollToItem**：这个 API 用 -1 表示滚到最后一项，而不是取消。[6]
2. 由同一个导航控制器串行发起自动滚动。应用自己排队的操作在真正调用前核对菜单、导航序号和当前列表版本，再把当时的 ID 换成当前索引。不要让鼠标主动滚动与旧的自动请求彼此拉扯；玩家接手后撤销应用侧待发请求。已经交给框架的旧滚动不视为已取消；在布局和可见行之后的检查点复核当前目标，仍需显现才补发当前请求，不要每帧反复抢回。若有限次数内未就绪，保留可取消的列表焦点，走明确回退。
3. 最后查实际行与真实焦点。GetRootElementForIndex 找的是活动行中的元素，不是可见性判定。[5] 检查当前行绑定的业务 ID 和代次、所属列表、是否附着到当前 panel，以及可交互区域是否真的落在视口内；若导航规则要求整行露出，则查是否完整露出。发出聚焦请求后再核对框架实际焦点。布局、行绑定或焦点后来发生变化时，下一次确认仍须做同样的资格检查，不靠一次旧的“已经恢复”标记。

调试时在同一条记录里同时写入：调用时目标 ID 和解析出的索引、列表版本、实际滚动偏移、可见行的绑定以及最终焦点。特意在布局更新前发起滚动，再让 B 从第 2 项移到第 4 项。若最终只滚到了第 2 项但没有误触发，说明输入守卫有效、视口仍需纠正；若 B 正确可见但按键落到 D，则继续查真实焦点和确认归属。将 B 再从数据中移除，确认没有因 -1 跳到最后一项。[7]

## 按下时是 B，松开时不能偷偷变成 D

最后还需要区分**输入提交的时机**。如果按钮配置为松开时执行，仅在松开时比较“当前焦点绑定等于当前目标”还不够。玩家按下时目标是 B；在松开前，同一个聚焦行绑定给 D，而另一条界面更新也将当前目标改为 D。松开时三者看起来一致，却不能证明这次按下是给 D 的。

一种可落地的约定是：按下时为确认保存当时的逻辑 ID、行与绑定代次，另带当时的导航意图序号；松开时只在它仍是同一次有效操作时执行。目标、行绑定或输入归属发生变化就作废，需要玩家在新目标上重新按一次。失去窗口焦点、设备断开或菜单交出控制时，主动清除待提交的确认，即使稍后仍回到同一行。通过检查后先消费这次按下记录，再提交捕获的道具 ID；不要在检查后等待一次异步操作，再改用返回时的行。这比在重绘后任意吃掉一帧确认更明确。若交互选择按下立即执行，则记得阻止后续松开或重复按键信号再次提交；指针点击有自己的命中对象与按下／释放政策，不要将键盘导航的目标强塞给鼠标。

下面是同一种合成 `ui_accept` 动作在 Godot 4.6.3 中的[实际试件](../../../../管理档案/实验/列表复用焦点/README.md)。试件复用的是两个普通 `Button`，不是 Godot 内置虚拟列表；它查询真实 `Viewport.gui_get_focus_owner()`、调用 `grab_focus()` 并注入按下和松开，检查最后接到 `pressed` 的条目。[4]

| 试件动作 | 引擎焦点／条目 | 实际记录的业务操作 |
|---|---|---|
| 第二行代表 B 时按确认 | 第二行／B | B |
| 第二行仍聚焦，直接改绑 D 后按确认 | 同一个第二行／D；逻辑仍为 B | 无检查版本操作了 D |
| 等待 B 回到视口，焦点临时交给列表表面 | 列表表面／无条目 | 无 |
| 等待 B 时，玩家改选 C；随后旧 B 回调到达 | 第一行／C | 操作了 C，旧回调未抢焦点 |
| 按下 B 后换绑 D，当前目标也已变为 D，再松开 | 第二行／D | 只检查松开时身份会操作 D；核对按下时的身份则作废，重新完整按一次才操作 D |

另一个试件让同一控件 B→X→B，旧绑定代次的完成被拒绝，随后当前代次才可聚焦 B。这里测到了实际控件焦点和按键动作的分发，没有测滚动动画、裁剪、焦点指示、设备或读屏。Unity 或 Unreal 可按各自的解绑、布局和条目可见通知实现同样的检查，不据此推定它们的焦点时序与 Godot 相同。

对实际菜单，至少分别试三次：让已聚焦的行换成另一条；让旧滚动晚于新导航完成；让按钮在按下与松开之间换绑。不要只看截图或选中索引，逐次确认**实际接收者与你看到的条目一致，并且业务操作落在本次输入开始时的目标上**。当测试驱动意外触发的是出售、装备或购买，还应独立核对业务层收到的实例 ID，不把高亮对了当成验收。
