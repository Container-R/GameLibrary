# 关闭弹窗后如何恢复操作焦点

玩家用手柄在设置页选中“恢复默认”，按确认键打开弹窗，又选择“取消”。弹窗消失了，但方向键不再移动，或者下一次确认又把同一个弹窗打开。画面看似回到了原处，操作却没有接上。

这通常不能靠关窗时补一句“选中上一个按钮”完整解决。弹窗存在期间，原按钮可能已被列表刷新替换、被禁用，甚至所属页面都变了。恢复操作需要记住玩家从哪里来，也要重新判断现在还能回到哪里。

本文面向用户界面（UI）程序、用户体验（UX）设计和测试人员，围绕这个设置页例子说明一套应用层做法。它适用于单个本地玩家的键盘与手柄菜单；不是可直接粘贴的引擎插件，也不涵盖分屏用户和平台系统覆盖层的完整管理。

## 焦点是“下一次操作交给谁”，不只是高亮框

**操作焦点**是当前接收导航、确认等操作的控件。例如“恢复默认”得到焦点，玩家按确认就应操作它。焦点指示则是把这一状态显示出来的轮廓、底色或其他标记。两者必须对应：画出高亮不代表输入已交给该控件；控件收到输入但高亮被遮住，玩家也不知道自己将操作什么。

XAG 113 把焦点指示的清晰可见作为目标，特别指出不可见或移出屏幕的焦点会阻碍导航。[1] 因此，恢复完成要同时回答“实际接收者是谁”和“玩家能否看到它”，不能只检查函数是否调用成功。

这里讨论的弹窗是**模态弹窗**：它打开时，玩家应先处理它，不能继续操作背后的设置页。背景可以仍然显示，但方向导航、确认以及可用的指针点击都不应穿到背景。单纯把画面盖暗，不会自动完成这项输入隔离。

## 打开之前，记住本次从哪里来

在弹窗抢走焦点之前，保存触发它的“恢复默认”按钮，以及它所属的当前设置页面。不要等焦点已经进入弹窗，才去问“刚才选中了谁”。鼠标点击打开时，也应明确记录实际触发按钮，而不是拿屏幕上残留的键盘选择充数。

保存的内容不宜只有按钮名字。假设页面由列表生成，刷新后仍有一个名叫 `Button` 的对象，但它已经代表另一个设置项。恢复到这个同名对象，技术上可能成功，业务上却回错了位置。简单页面可以保存控件引用并验证它仍属于当前页面；会重建或复用控件的列表，还应记住对应的业务条目。

如果产品允许“回到同一个设置项的新控件”，就在新页面中按该条目重新找到控件，再检查它是否适用。这与“无条件找同名节点”不同。若原条目已经不存在，应该走预定回退，而不是猜一个位置最近的按钮。

接着把输入交给弹窗，并等它真正进入界面、数据与布局就绪，再选择初始项。这个例子可以把“取消”设为初始项，以免默认确认落在破坏性操作上；具体选择仍要结合弹窗内容设计。取得焦点本身不应等同于执行按钮。

打开动画期间也要有明确的输入归属。等待布局不是允许确认穿透背景的理由；而固定“延迟一帧”也不能代替真正的就绪条件，尤其是内容还在异步加载时。

## 关闭时，先查原按钮是否仍能接着用

玩家按取消后，先结束这一层弹窗的交互，再恢复下面一层。关闭用的那一次按键应由弹窗消费，不能继续送到刚恢复的“恢复默认”按钮，否则弹窗可能立刻重开。按住确认键是否产生重复输入，也需要输入层明确处理，而不是只在焦点代码里加延迟。若退出动画还遮挡着下层界面，应继续由过渡状态持有输入，等恢复目标可以操作时再交还，不能让玩家在看不见目标时先触发它。

恢复前，应重新检查原按钮：它还在当前界面中吗？它或祖先是否被隐藏、禁用？它允许接收焦点吗？它是否属于现在该操作的页面？焦点指示是否能出现在可见区域？这些问题没有一个单独的 `非空` 判断可以代替。

如果按钮还在，却已滚到可视区之外，先让页面把它滚进视野，等布局稳定后再确认落点。不要让屏幕外的按钮长期接收确认，也不要把“控件的 visible 属性为真”理解为一定没有被祖先裁剪或其他弹窗遮挡。

原按钮失效时，可以采用一条由产品明确的回退顺序：**本页最近仍有效的选择 → 本页默认入口 → 本页安全返回入口**。每个候选都要经过同样检查。例如“恢复默认”因为当前设置已是默认值而禁用，团队可以选择回到仍可操作的设置列表或“返回”按钮，而不是强行聚焦已禁用的控件。

如果设置页本身已经被路由替换，就不要再追旧按钮。新页面应执行自己的初始聚焦规则。若没有任何候选，应显示可操作的错误或返回状态；确实不可取消的短暂加载则要清楚表示，并在完成或失败后接续操作。永久停在没有可用焦点的界面不是一种恢复策略。

最后核对引擎实际选中了谁。请求过程中页面可能再次变化，所以“已请求恢复”不能直接写成“已恢复”。失败时应按当前页面重新判断，而不是每帧不断抢回旧按钮。

## 再套一层帮助框，为什么需要逐层返回

假设确认框里还有一个“说明”按钮。玩家打开说明框，再将它关闭，焦点应该回到确认框的“说明”，而不是越过确认框回到设置页的“恢复默认”。等确认框也关闭，才回设置页。

一种易理解的实现是保存一叠打开记录：每打开一层，就记住它自己的返回位置；只关闭最上层，再取出相应返回位置。程序中通常称它为栈。这里最重要的不是容器名称，而是每一层只恢复到它下面仍然有效的那一层。

还要区分“弹窗类型”和“这一次打开”。确认框关闭后重新打开，旧网络请求才返回，不能因为两次都叫“确认框”，就把新的那一个关掉。可以给每次打开分配独立标识，让关闭回调说明自己属于哪次打开；标识不匹配便不再执行。父框的异步请求也不应趁子框仍在时直接删除最上层。同一次打开收到重复关闭回调时，也只处理第一次有效关闭，不能重复取走下一层记录。

相同原则适用于延迟聚焦。弹窗初始项准备好了，但玩家已经导航到另一个按钮，旧的延迟请求不应把选择拉回去。可以让每次新的聚焦意图产生一个更新序号，延迟工作只在自己的序号仍有效、目标仍属于当前层时执行。单纯比较页面有没有更换还不够，同一页面里的玩家选择也可能已经更新。请求之后的检查或失败回退也要核对这个序号，不能用旧请求的失败处理覆盖后来已经作出的新选择。

这些是本文的应用层建议，不是某个标准规定的通用恢复算法。不要在所有失焦回调中无条件重新聚焦自己，否则两个控件可能互相争抢。

## 换了输入设备，也要接回当前操作

玩家在设置页移动了一下鼠标，不代表键盘或手柄的下一次确认就应失去目标。鼠标悬停在哪个按钮、当前操作焦点在哪个按钮、界面该显示哪种按键图标，是相关但不同的状态。切换提示图标时，不要把仍接收确认的焦点指示一起藏掉；手柄刚接入，也不必无条件跳到页面第一项。

回到确认框例子，如果手柄断开，不应因此自动确认或取消恢复默认。可以保留当前页面和焦点上下文，暂时停止接受失去归属的设备输入；若游戏显示本地“重新连接”弹窗，就把它当作更高一层处理，而不是覆盖掉原确认框的返回记录。

重新连接后，先按项目规则确认该设备由哪个用户操作，再检查当前最上层的有效目标。不要补播断线期间积下的确认，也要说明按住的按钮是否必须先松开、重新按下才算新操作。允许键盘接替还是要求原设备，属于产品与平台策略，不由焦点恢复代码擅自决定；清空全游戏输入也可能影响其他操作，不能当成通用修复。

这些仍是应用层建议，不是平台认证流程。平台自己的覆盖界面与本地弹窗不同：本地聚焦请求应服从实际进入和返回事件，不能假定它等同于本书的弹窗栈。这里没有提供分屏多用户或平台覆盖层的完整实现。

## 实现时要核对引擎的具体含义

通用流程确定之后，再把“仍在界面”“允许聚焦”“最终已选中”映射到实际 UI 系统。下面只是文档说明与有限旧观察，不能相互替代。

**Unity 6000.0 UI Toolkit。** `focusable` 描述元素是否可聚焦；负 `tabIndex` 表示它不参与 Tab 导航，不能据此推断程序化聚焦、手柄或背景点击全部被阻止。[2] 元素必须附着到 panel 才能渲染或接收事件；父元素也不会因为某个后代单独附着或脱离，就自动收到该后代的 panel 事件。[4] 这意味着视图卸载与列表更新需要由实际负责它们的代码报告，而不能只监听一个最外层节点。

Unity 的 `FocusInEvent`、`FocusOutEvent` 在焦点改变前发送，`FocusEvent`、`BlurEvent` 在改变后发送。[3] 因此应结合变化后的通知与当前焦点核对恢复结果，不能把任何名字带 Focus 的回调都当作最终状态。这些依据来自文档，本书没有新建 Unity 项目执行验证。

若同一界面同时使用 UI Toolkit 和另一套 Unity UI 系统 uGUI，还要检查两者之间的输入桥接。Unity 6000.0 文档说明，它们通过 EventSystem 和输入模块处理事件，一方取得焦点会影响另一方。[6] 因此应记录实际输入模块与 Active Input Handling 配置，并检查自定义转发是否让同一次确认执行两遍；只看其中一套系统的高亮，不足以判断最终输入归属。这不意味着框架默认会重复投递，而是混用和自定义接入需要核对的边界。

**Godot 4.6 Control。** 递归焦点行为可以继承，也可以由子控件显式覆盖。文档说明子控件设为 `FOCUS_BEHAVIOR_ENABLED` 时可以忽略父级的递归设置，再按自身模式获得资格。[5] 所以“禁用了背景父级”不自动证明所有后代都无法取得焦点；引擎允许聚焦，也不等于它属于当前应用弹窗。

已有 Godot 无头夹具记录了两种程序化情况：同路径新建的按钮能被朴素路径恢复选中；另一个同实例序列中，子控件显式覆盖后也能重新取得焦点。它们说明为什么要分开检查对象身份、有效资格和当前层归属，不是实际键盘/手柄导航或可见指示测试。所用程序版本是本机自报，未认证与官方源码的构建对应；本次未重新运行。

还应留意通知不等于完整状态历史。Godot 4.6 的 `gui_focus_changed` 在控件取得焦点时发出，单纯失焦不会触发它。[7] 只记住最后一次信号参数，可能漏掉当前已没有焦点的状态。整理后的[回调时序支持小节](../../../../管理档案/支持资料/焦点回调与状态更新的边界.md#回调中的现在不一定是调用完成后的状态)保留了回调中间值与调用返回后状态的区别；需要适配这一版本时再查，不把该有限观察推广成所有引擎的时序规则。

网页对话框的可访问性模式可以启发设计，但 ARIA 标记、浏览器焦点规则不能直接认证游戏引擎。本书以游戏 UI 指南和具体引擎文档为依据，也不据此宣称读屏、平台认证或所有输入路径已经通过。

## 用一次完整操作检查，而不是只看弹窗消失

在目标项目中，先沿开篇的路径走一遍：键盘或手柄选中“恢复默认”，打开确认框，移动到取消并关闭。观察焦点是否回到约定位置、指示是否清楚，下一次方向输入能否继续移动，刚才的关闭动作有没有同时触发背景按钮。

然后只改变一个条件：弹窗打开期间让原按钮失效。可以是禁用原项、刷新列表替换控件，或切换页面。此时应观察预定回退，而不是仍期待无条件回原位置。再打开说明子框，验证先回确认框、后回设置页；让旧请求晚返回，检查它有没有误关新框或抢走新选择。

这些是建议执行的项目检查，不是本书已经完成的玩家测试。旧资料另有纯状态模型覆盖若干恢复、失效和过期请求情况，但模型用布尔值模拟控件资格，不模拟真实布局、设备和可见性，也未覆盖这里所有步骤。

恢复操作的目标并非让高亮“差不多回去”，而是让玩家能预测接下来会操作谁。记住来处、核对现状、逐层返回，并保留失效后的明确去处，才会让关闭弹窗真正接回原来的操作流程。
