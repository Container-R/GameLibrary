# 任务选项改了条件，怎样找出被关掉的剧情路线

作者想取消“只凭徽章就能说服执政官”的捷径，让玩家先帮过居民。改完后，测试员走了一遍任务，仍能正常结束，却没有发现另一条被误伤的路线：已经取得居民信任的人，也不能再谈判了。没有卡死、没有脚本错误，不等于这次修改只改变了作者想改的内容。

本文面向配置条件选项的叙事设计师与工具程序员，介绍一种内容编辑前后的对照检查：从相同的新开局条件出发，记录哪些经历能到达场景、在那里能选什么，再把差异与作者批准的变化比较。例子是有限、确定的任务模型；不加载旧存档，不验证台词表现，也不要求所有版本保留全部旧路线。

## 改动清单既要写删什么，也要写留下什么

用一个原创的短任务说明。玩家在准备阶段只能选择下列一种经历，随后都进入接见场景：

| 先前经历 | 信任值 trust | 持有徽章 badge |
| --- | ---: | --- |
| 帮助居民 help | 2 | false |
| 出示资历 credential | 1 | true |
| 直接赶来 rush | 0 | false |

接见场景始终有“离开”选项 `leave`，进入正常离开结局；满足条件时还有“谈判” `parley`，进入达成协议结局。这里没有返回、物品消耗、隐式访问历史或外部查询。

旧版谈判条件为 `trust >= 2 or badge`。作者此次批准的修改是：徽章不再单独提供谈判资格，但帮助居民取得的信任仍应有效。对应的新条件是 `trust >= 2`。验收约定不是一句“路线少了没关系”，而是三个具体要求：

- `help` 后仍有 `parley` 与 `leave`。
- `credential` 后必须失去 `parley`，保留 `leave`。
- `rush` 后仍只有 `leave`。

这份约定同时包含**必须发生的变化**和**必须保留的行为**。只列允许删除的选项，可能让完全没做修改的版本也通过；只要求新旧完全相同，则会把作者明确批准的修改误判为错误。

条件语法需要按实际工具理解。例如 ink v1.2.1 的固定文档说明，一个选项连续写多个条件块时，它们都必须通过；`and` 与 `or` 表达的要求不同。[1] 把“有信任或有徽章”整理成两个独立条件块，未必只是排版调整。编译通过能检查一部分语法，却不能决定作者要表达的是哪种资格。

## 相同场景不代表相同经历

只给接见场景拍一张选项截图，会丢掉最关键的条件：玩家怎样走到这里。本例需要记录 `scene、trust、badge`，并保存达到该状态的动作序列。仅以 `scene` 去重，会把三种接见状态合并，漏掉其中两种经历。

也不能把所有字段的笛卡尔积当成实际可达状态。例如 `trust=2、badge=true` 不会由本例任一准备动作产生。直接在调试器里把它们同时打开，可以测试一个条件函数，但不能据此宣称玩家能走到该分支。报告应区分“手工注入的条件测试”与“从支持的开局走出的复现路线”。如果未来支持这样的初始配装，就把它加入开局集合，重新检查。

在真实 ink 内容中，所需状态可能不止显式变量。固定实现 `ProcessChoice` 既检查条件，也检查一次性选项的目标访问计数；条件重新满足，不会自动清除一次性限制。[2] 若项目的选项依赖访问次数、轮次、返回栈或外部任务事实，这些差异也可能改变下一步。不能为了缩小测试规模，先把它们合并掉，再把遗漏的路线称为不存在。本例故意没有这些机制，因而三个字段足够；它不是通用 ink 状态序列化器。

## 两版都从开局运行，不把旧执行现场塞进新版

这里的比较单位是内容修订，不是旧存档兼容性。保留修改前后的内容与规则，把相同初始条件分别交给两版。对每版，从开始状态枚举当前合法选项，执行一个选项得到后续状态；遇到尚未处理的完整状态时继续展开，并保存前驱与动作。有限模型可以用队列完成这一步。

本例三个准备动作及其效果都未改变，因此两版的三种接见状态可直接按三个字段对齐。在每个共同状态上比较可用选项 ID 集合：旧版有、新版没有的是删除；新版有、旧版没有的是新增。同时保留只在旧版或只在新版可达的状态，避免交集比较把整段消失的内容静默漏掉。

给每项差异附上两版各自的到达路径、事实值、选项 ID 和条件版本。例如：

```text
开局 → help → audience(trust=2, badge=false)
旧版可选：leave、parley
候选可选：leave
被检查条件：旧 trust>=2 or badge；候选 trust>2
作者要求：help 后仍能谈判
结论：未批准的删除
```

这是可以交给作者和实现者重放的失败证据，而不是“分支覆盖率降低”的总数。原本 `credential→parley` 消失，也会产生差异，但它符合本轮约定，应接受。每项差异都必须带上发生条件，不能因为 `parley` 在某处获准删除，就允许它在所有场景消失。

实际内容的两版可能连前面的动作效果都改了。此时不能直接按旧字段相等配对，也不能往新版注入旧事实。可以用稳定动作 ID 重放同一输入前缀，逐步比较事实；某一步不再合法，先报告这一步的分歧，再分别探索两版后续。场景拆分或动作替换需要作者提供对应关系，无法唯一对应就标成待审，不能按选项显示序号或相同台词猜测。跨版本 ID 在这里用于定位同一项作者意图，应由项目的内容或工具显式维护，不是运行时显示序号，也不等于保证旧执行快照可载入。本例只改条件；如果修改了选项效果或目的地，还要逐项比较“状态—选项—后果”的转换。两个选项交换后果时，选项集合和全局可达状态集合都可能不变。

## 为什么“所有路线都能结束”仍会漏掉这次错误

本次原创 Python 试件分别比较三个候选；没有编译或运行 ink。准备动作和两个结局保持相同，只替换谈判条件。

| 候选条件 | 与旧版相比的主要差异 | 是否仍可从每个可达状态结束 | 按本轮修改约定 |
| --- | --- | --- | --- |
| `trust >= 2` | 资历路线失去谈判 | 是 | 接受 |
| `trust > 2` | 资历、帮助居民两路都失去谈判 | 是 | 拒绝：帮助居民被误伤 |
| `trust >= 0` | 直接赶来也能谈判；资历捷径仍在 | 是 | 拒绝：新增越权且要求的删除未发生 |

原版共有 9 个可达状态，三个候选分别为 8、7、10 个。这里的终点带着到达时的事实，因此相同结局标签下可以有多个不同状态。数量只是结果摘要，不是质量分数：8 个状态通过，7 个和 10 个不通过，原因在具体行为是否符合编辑意图。

三个候选都有 `leave`，所以检查“是否至少能通关”甚至“每个可达状态是否还有结束办法”，都能通过。它们没有回答玩家是否仍能完成作者承诺的谈判路径。反过来，故意删掉资历捷径也不是因为它造成了死锁；它是允许的内容变化。

试件还检查了完全保留旧版的情况：虽然没有新增差异，却因未落实“资历不能独自换来谈判”而拒绝。搜索限制到 2 个状态时则返回未判定，而不是说没有更多差异。输出保存了反例前缀、新增与丢失状态以及逐项验收结果。

## 接入剧情工具时，比较玩家实际遇到的边界

条件函数的返回值只是其中一层。工具应运行到已定义的观察点，例如“一轮自动内容推进结束，等待玩家选择”，再记录实际可见选项及事实。有合法自动跳转时，应继续推进，不能看到一时没有可见选项便认定卡死；已结束、正在等待宿主结果、暂时无可操作项也应分开标记。ink 的无文本 fallback 选项可以在没有其他选项时自动接续，固定源码也有专门的默认选项处理。[1][3] 这些运行规则不能由一个脱离解释器的布尔测试替代。

将模型接进真实故事可分三步：

1. **先冻结比较输入。** 记录两份编译内容、运行时版本、支持的开局及宿主查询输入。复制一份会继续变化的任务字典引用，不等于冻结输入。本文没有随机剧情；若故事会随机分支，需要明确覆盖哪些随机结果，不能把一次采样当成全体路径。
2. **隔离推进，再输出见证。** 测试实例不调用正式奖励、网络或正式任务事件。每个分支从独立状态恢复，运行到观察点后取实际选项列表，用稳定 ID 选择动作，保存两版轨迹。限制自动推进次数和状态数量；超限报告未判定。隔离宿主出口的具体方法可参阅既有 ink 存档迁移文章，但这里不执行任何迁移提交。
3. **把发现交回编辑约定。** 未批准的新增、删除、事实改变和异常结束需要修订；批准项也要确认确实发生。补一条无条件“离开”只能处理某类停滞，不能恢复误删的谈判。若作者确实决定取消帮助居民路线，应修改明确的设计约定及相关台词，再以新约定验收，不是把失败自动加入允许清单。

完整故事通常无法低成本枚举全部状态。可从本轮修改涉及的场景、事实阈值及入口经历开始，并把未探索范围写进结果；对只保存局部事实的抽象模型，需说明被省略的信息为何不会改变选项。没有这样的依据，有限测试只证明所列经历的行为，不能宣布全篇剧情无遗漏。故事好不好、人物是否可信，也仍需作者审读，而不是由可达状态数决定。
