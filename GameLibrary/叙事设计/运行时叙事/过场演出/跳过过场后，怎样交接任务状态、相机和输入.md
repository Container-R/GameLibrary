# 跳过过场后，怎样交接任务状态、相机和输入

玩家按下跳过，过场里的铁门已经升起，角色却撞在空气墙上；又或者钥匙只发了一次，但下一段过场刚接管相机，镜头就被上一段迟到的完成回调切回玩家。前一个问题是**画面到了末帧，任务没完成**；后一个问题是**任务完成了，旧播放仍能动新播放的资源**。两者要分别验收。

本文面向过场制作、叙事设计和玩法程序。以下用一段可跳过的开门剧情，说明如何设计正常完成、跳过和取消三个出口，再用版本明确的引擎试件区分时间轴取样与任务交接。

## 先定哪些结果必须留下

设计约定是：播放到开门，或玩家确认跳过，剧情都算完成。门的碰撞应放行，剧情进度要推进一次，钥匙只能发一次；两种出口都归还本次播放占用的相机和输入。电花、镜头抖动和开门声是过程提示，跳过不补播。离开任务、切走场景而**取消**不是确认跳过：不要发钥匙或把任务推进，仍要清理这次播放拥有的相机和输入。若制作上允许门提前通行，提前发生的动作必须有自己的保留或撤销规则，不能指望取消后自然倒带。回到入口、停在安全位置或保留已经发生的变化，由项目单独规定。

把这份约定拆到三处。时间轴写可被随时取样的门位置和镜头姿态，也可以发短暂表现的提示。任务系统拥有门是否允许通行、剧情记录和钥匙。播放协调器拥有这一回播放的终止状态，以及它借到的相机、输入、遮罩等资源的令牌。一条关键事件可以由时间轴提交给任务系统，但不能把要求「无论是否跳过都成立」的结果，只接在一个会被跨过去的关键帧上。

## 跳到末帧不等于跨过所有事件

Godot 4.7 的 AnimationPlayer 文档把这两步分开：`seek` 可请求立刻更新属性，但跳过中间的事件，跳到末尾不发 `animation_finished`；`update_only` 还会排除方法、音频及动画播放轨。[1] 在 Godot 4.7.2 的两秒非循环试件里，门的视觉开度最终都是 1。分段推进和一次推进到末尾都依序经过电花、钥匙尝试关键帧和完成信号；从开头 `seek(2, true, true)` 三者均无，从电花之后再跳则只保留已发生的电花。一次推进可触发完成，但也扫过本不想补播的关键帧，因此不能只看有没有完成信号来选择跳过做法。

UE 5.8 Sequencer 也把扫区间的 `Play` 和不触发中间事件的 `Jump` 分开。官方 `Go to End and Stop` 示例配合 `Keep State` 保留的是灯光末态，不能据此证明项目的任务回调都被调用。[2][3] 配置引擎节点前列清四项：末态属性要不要取样、跨区间事件会不会触发、是否改变播放状态、是否发出项目依赖的完成通知。不要把不同引擎的节点按名称对号入座。

## 用两个标识解决两种重复

**每次播放的标识**回答「现在有权结束这次过场的是谁」。同一个动画资源播放两次，应当有两个不同标识。把它捕获在连接信号或入队的时候；迟到时再读全局的「当前播放」，会把旧消息误当成新消息。

**一次业务完成的标识**回答「这个存档的这个任务事件完成过没有」。如果读档或重播仍属于同一次交付，业务标识不变，即使播放标识已经不同。若同一任务设计成可重复领取，由任务系统给每轮任务分出新的业务标识，而不是拿片段标题区分。任务系统增奖、写进度、记录这次标识，应在同一个可原子提交的状态里完成；所用存储不支持原子提交时，要设计可重放的记录或可安全重试的操作，不能先写「发过」再赌后续保存成功。

正常完成和确认跳过走同一个出口，入口比较播放标识，并把阶段从「播放中」改成「收尾中」，再允许可能同步回调的操作。取消走另一路，只释放本次合法持有的资源，不过任务完成入口。下面是协调器示意；`apply_once` 不是引擎 API：

```text
finish(playback_id, result):
    playback = active_if_matches(playback_id)
    if playback is missing or playback.phase != Playing: return
    playback.phase = Ending                    # 先挡住重入与重复回调
    if result is Finished or ConfirmedSkip:
        quests.apply_once(playback.completion_key)
    camera.release_if_owned(playback.camera_lease)
    input.release_if_owned(playback.input_lease)
    clear_active_if_matches(playback_id)
```

项目里若保存可能失败，`apply_once` 必须让失败可观察，把待重试保存在任务侧；不要把失败当作完成确认。重试任务提交不等于再次执行旧播放临时资源的清理。剧情或 UI 如果要求「先存档成功才能继续」，就要明确保留哪一层界面、如何重试以及退出后如何恢复。

入口校验不是说后面可以无条件关掉全局的锁。旧过场可能仍有相机，输入却已交给独立的对话菜单；也可能在释放相机时，通过同步监听器立刻启动后一段过场。如果前一段继续执行「启用玩家输入」，就释放了后来的锁。每处释放都应该让资源的拥有者在**改变资源的地方**比较令牌；一个输入层若允许多个持有者，就移除旧过场自己的票据，再按剩余票据决定是否解锁。对活动播放的清理也同理。若两段共用播放器，迟到的 `Stop`、`seek` 或恢复预播放值也必须确认仍属于原播放；不要为了归还旧相机，先无条件停掉当前播放器。只有项目确实保证操作间没有重入、等待或独立转交，才能把这几步当成一段不可打断的交接。

## 验收既看任务结果，也看谁在控制

给开门场景检查三个可独立观察的量：任务进度和奖励、角色能否通过门、相机和输入归谁。让门开了和任务确实进入完成态同时成为断言。安排如下反例，避免两次看似正常的播放把问题挡住：

| 对照 | 应记录的结果 |
|---|---|
| 自然播完，或开头确认跳过 | 门可通行，完成一笔，只发一次钥匙；跳过不补播过程电花；本次播放的资源被归还 |
| 电花之后跳过，旧完成又被投递 | 已播电花不重放，重复消息不再改任务或资源 |
| 旧片段跳过后，新片段先取得相机与输入，再到两次旧完成 | 旧任务仍只完成一次；两项资源都留给新片段 |
| 旧片段取消后，迟到的自然完成到达 | 不发奖励，也不动已转交的资源 |
| 合法播放在收尾中触发下一段，或输入已交给别的界面 | 旧片段只归还自己仍持有的资源；其余归属保持不变 |
| 重新打开同一存档，再次触发旧剧情 | 如果设计允许重播，可产生新的播放归属，不再次提交同一笔任务奖励 |

复现时故意只保留奖励去重，比较任务、相机和输入三项，它能揭示「奖励数字对了，交接仍错」这种失败。再让相机归还触发同步回调，比较只在入口检查和每项按令牌归还。最后在项目里把真正的相机、输入门禁、关卡碰撞和存档回读分别接入断言。内存里的去重集合只能证明同一进程样本，不能代替重启后的存档验收。

Godot 4.7.2 的第二个试件实际把上一段的两次回调放进引擎延迟队列，并在投递前切到下一段的 Camera3D。只按奖励标识去重时，跳过后奖励仍是一份，当前相机却被改回游戏相机，输入门禁也被打开；取消后，迟到的回调甚至写出了奖励。加入播放入口检查可挡住这两种旧消息，但挡不住输入已先转交的情况，也挡不住收尾过程同步启动下一段的情况。逐项比较实际资源令牌，四组才都保住正确归属。这里读的是 Godot 视口的实际当前相机；延迟消息由试件主动注入，输入是项目内的模拟门禁，奖励只存内存。这不是物理碰撞、设备输入或存档重启的集成测试。
