# ink 内容更新后的存档迁移：从旧事实恢复到故事与宿主共同提交

上线后将“知道桥的位置”改名、把布尔奖励档改为整数，旧存档可能照样加载、照样输出下一句，却悄悄取消桥路线，或者把旧奖励档当成普通数值参与运算。另一个风险发生在恢复过程之外：为了把故事走回原处而重放对白，宿主可能又发了一次奖励；保存成功后丢了响应，重试又可能把玩家刚走过的剧情覆盖掉。

本文面向熟悉 ink 与游戏存档的叙事程序员和内容负责人，给出一种**作者批准的语义检查点恢复方法**：先用旧内容解释玩家经历，再在新版专用入口构造隔离候选，最后共同提交故事与宿主动作。它允许明确批准的章节回退，不承诺任意旧快照逐句接续。机制依据固定 ink C# 提交 `35c63e52f1d36060930dc7ed3cfba38ea224b528`；例子来自原创小故事的真实运行，事务例子来自本地 SQLite。跨服务部分另作设计说明。[1][2][3][4][5][6][7]

## 1. 先决定保留经历，还是保留执行现场

故事存档不只是变量表。ink 状态包含执行上下文、访问计数、轮次、故事随机种子及 `previousRandom` 等信息。路径也有执行语义：`ChoosePathString` 默认重置调用栈，随后设置路径并登记访问变化；`ChooseChoiceIndex` 则恢复产生该选项时的线程，再转向选项目标。把几个变量拷到新故事后跳入同名 knot，不能据此称为完整快照恢复。[2][3]

因此，内容更新前应选定产品承诺。若玩家必须从原句、原调用上下文继续，团队需要保留相应内容版本，或为结构与历史状态建立专门的兼容验证。本文选择另一种承诺：恢复到作者维护的检查点，保留决定后续剧情的事实，并明确重建或重置其余历史。

检查点应是一段专门接受事实输入的入口，而不是任意可跳转的位置。它需要说明：进入前有哪些事实、入口会建立哪些状态、运行到哪里停止、哪些选择应该可达，以及哪些已完成内容不应再次触发。若依赖某个函数栈帧的局部变量，就先把必需信息提升为可迁移事实，或选择更早的章节边界。若一次性对白原来依靠访问计数屏蔽，则应设计明确的“已听过”事实，或写出被批准的重置政策。不能一边丢弃访问历史，一边继续承诺所有一次性内容不重复。

这种方案将维护成本从“迁移所有编译位置”转移到“维护事实含义、迁移规则和恢复入口”。代价包括原内容归档、作者逐项决策、版本对的测试，以及玩家可能看到的有限回退；只改文字且原快照兼容已有充分依据时，不必强行重建检查点。

## 2. 用旧内容读旧存档，缺字段也有历史含义

该版本的 `VariablesState.SetJsonToken` 清空全局变量字典后，遍历**正在加载的内容的默认变量集合**。同名保存项存在，就从 JSON token 重建值；不存在，就采用当前内容的默认值。它不遍历所有旧字段寻找语义别名，也不按新默认值的类型自动转换旧 token。与此同时，`dontSaveDefaultValues` 默认启用，保存时会省略与声明默认值相等的全局值。[1][4]

这两个机制必须一起考虑。旧字段改名后，旧值不会自动转到新名字；同名字段改变类型时，显式保存的旧 token 与被省略的旧默认值，又会走不同恢复分支。

原创例子的旧内容声明为：

```ink
VAR knows_bridge = false
VAR score = false
```

新版改为：

```ink
VAR heard_bridge = false
VAR score = 0
```

作者规定 `knows_bridge` 与 `heard_bridge` 表示同一知识事实；旧 `score` 是奖励档开关，新 `score` 是档位数值，因此转换是 `false → 0`、`true → 10`，而不是布尔数值强转。两份旧存档都在等待选择的检查点保存，`knows_bridge` 都为 true，区别是 `score` 的真值。[6]

| 旧 score | 实际保存情况 | 新内容直接加载 | 按旧内容恢复再显式映射 |
| --- | --- | --- | --- |
| true | 保存 bool true | score 仍为 Boolean true；`score + 1` 输出 2 | score 为 Int32 10；输出 11 |
| false | 因等于旧默认而省略 | 采用新版 Int32 0；输出 1 | 从旧默认恢复 Boolean false，再映射 Int32 0；输出 1 |

直接加载的两例都得到 `heard_bridge=false`，只出现 road_route；显式映射后两例都得到 `heard_bridge=true`，出现 bridge_route 与 road_route。特别是 false 例，两种方法的算术输出都是 1，故事能力却不同。只检查加载无异常、数值输出或下一屏文字，会漏掉这种语义损失。初次 false 实验曾错误预测同名值总会保留 bool，实际因默认省略而失败；表中 false 的后续文本来自修正判据后的独立运行，不是那次失败运行的推测。[6]

实施时先保存不可变的原始字节及其内容身份，在隔离的旧 Story 中加载，检查诊断，再读取旧事实。也可以用专门的旧 schema 解码器，但它必须实现那个版本的字段、类型与默认解释，不能仅枚举 JSON 中存在的键。找不到相匹配的旧内容或默认基线时，事实状态是“无法可靠解释”，应停在恢复选择或明确的重置政策处，不能用新版默认值补成历史真相。

迁移规则至少包含旧事实名及类型、业务含义、新事实名及类型、转换政策、适用内容版本和批准的重置范围。整数枚举重排需要逐项对应；同名同类型也可能改变单位或人物身份。删除事实前要追踪未来依赖，不能只看当前选项。列表的条目名、序值及来源还需要独立映射，本文的布尔/整数例子不能替它们提供通用转换器。

## 3. 把事实送入新版入口，而不是伪造旧指针

本例的新版入口 `migration_resume` 直接转到新的路线选择段。候选是全新的 Story，只接收已解释并转换的两个事实，不向它加载旧执行快照。该例明确重置调用栈、访问历史、轮次、随机状态和待选项，然后在新版入口重新生成选择。[6]

一个可执行的构造流程如下，代码是步骤说明，隔离接口需由宿主实现：

```text
source = 读取并冻结旧存档、旧内容、宿主快照与修订
old = 用匹配的旧内容创建隔离 Story，加载 source.save
facts = 按旧规则读取并检查类型与必需历史
mapped = 应用作者批准的版本映射
candidate = 用目标内容创建隔离 Story
设置 mapped 中的目标变量
candidate.ChoosePathString("migration_resume")
有界 Continue，直到批准的稳定停止点
校验事实、选择及禁止发生的宿主变化
序列化 candidate；用同一目标内容重新加载并检查
```

稳定停止点应由协议定义，例如“预期选择已经生成且当前不能继续”，而不是碰巧调用了若干次 `Continue`。为防输入或入口错误导致无限运行，构造器要限制步数、输出量与查询调用量。发现加载错误、未批准的诊断、缺失输入或未知命令时，丢弃候选，不尝试在正式对象上补修。

校验必须同时有正向和负向要求。本例正向要求是两个事实及其准确类型、桥路与公路都可见；负向要求是构造过程中库存不变、不触发正式任务事件。随后应重新加载序列化字节并走代表性后续路径，而不止观察内存对象。实际集成中，true 与 false 两份候选从数据库取出后，分别选择 bridge_route 和 road_route，四例都抵达对应 `Bridge.` 或 `Road.` 终点，无待选项且不能继续。[7]

这些终点验证的是这个小故事的两条路。复杂作品还需按迁移规则覆盖未完成任务、一次性内容、互斥事实和章节交界。映射批准范围之外的输入应被拒绝或转入其他明确政策，不能因这个候选能运行就接受任意历史状态。

## 4. 重放需要冻结输入，也需要隔离所有出口

有些项目无法直接建立检查点，必须按历史选择重放。此时选项身份必须稳定，不能把显示索引当跨版本 ID；找不到原事件对应的选择时应停止。即便记录了选择和随机种子，也未必够用。ink 的序列洗牌还依赖容器路径字符和、循环次数与元素数量。在 seed=235、各取12项的测试里，旧序列自身重跑一致，而增加元素或改容器路径都得到不同轨迹。这说明保留种子不足以保证内容编辑后的序列相同，不意味着每次改名必然改变结果。[2][6]

外部查询也属于输入。无写入副作用的 `has_rope` 若读取玩家当前装备，与旧时刻可能不同。测试中旧值 true 与冻结重放 true 都得到 rope_route，改用当前 false 则得到 walk_route。可采用版本化宿主快照，或按稳定调用身份记录参数及返回值；回放时核对参数、顺序与返回值对应关系，缺项就停。只给会变化的字典套一层只读接口并没有冻结数据。缺失的历史查询不能从最终存档凭空重建。[5][6]

输出方向同样需要完整边界。`lookaheadSafe=false` 控制 ink 的预读行为，正常执行走到该动作时仍会调用宿主委托，并不表示“迁移时不要执行”。官方集成方式还包括变量观察者、tag 和文本命令解析，拦截 EXTERNAL 一种出口不够。[2][5]

| 出口 | 候选期间应如何处理 |
| --- | --- |
| 外部查询 | 读取冻结快照或匹配的历史返回值，校验参数与身份 |
| 外部动作 | 生成结构化待核对命令，不调用正式库存、任务或网络客户端 |
| 变量观察者 | 只写候选投影，不连接正式奖励或成就订阅者 |
| tag、文本命令 | 用隔离解析器识别，未知命令拒绝；不送正式事件总线 |
| 演出、声音、遥测 | 缓冲或写无业务副作用的迁移日志，不触发正式演出链 |

边界应覆盖构造、绑定、赋值、加载、继续、选择与丢弃的整个生命周期。候选对象不能持有正式系统的可写引用；错误处理也不能回落到正式绑定。单独 new 一个 Story 只隔离它的内部状态，不隔离被委托捕获的宿主对象。

四出口测试在两次重放中，各出口分别调用两次。不隔离的本地 mock 库存变为80；隔离绑定只记录8条计划，库存为0。这支持这些出口可以按模式分流，但计划还没有证明历史合法性，也没有与后面的真实候选事务形成全部出口端到端验证。[6]

## 5. 重放见到奖励，不代表玩家还没领过

待核对命令首先要回答历史状态，而不是立即去重执行：

- **已知完成**：权威收据或可靠历史能证明同一业务动作已经执行，且载荷一致。仅核对，不再次执行。
- **已知未完成**：有可靠证据证明尚未执行，并且迁移政策批准现在执行。才能进入提交动作清单。
- **未知**：重放遇到动作，但旧版本未记收据，或记录不足以判断。缺记录不是“尚未领取”，不能自动补发。

可靠证据可以是覆盖该时期且完整的权威事件账本，或由当时协议保证原子维护的领取标记。仅看到当前库存不足，无法证明未领，因为玩家可能花掉了奖励。历史未知时可阻止自动迁移，或由作者制定显式补偿政策；补偿需要自己的事件身份与适用条件，不能伪装成已查明旧奖励遗漏。

**业务事件身份**与**迁移操作身份**解决不同问题。业务事件键可由“账户或存档谱系、作者稳定奖励 ID、有可靠来源的发生序号”组成；按账户、一次通关还是每个存档去重是产品政策。重试不得重新生成奖励键，更新到下一版本也不能把同一次奖励改成新事件。收据应保存规范化载荷或可核查摘要；同键同载荷复用结果，同键不同载荷拒绝，必要修正使用独立补偿动作。

迁移操作键则标识这一次候选提交。它绑定源状态、目标内容、映射与候选，同一提交重试保留该键。若把迁移操作键用作奖励键，第二次升级会得到一个新键，从而可能重复领取同一业务奖励。收据的保留期与去重范围也必须覆盖旧档恢复，不能随活动故事一起回滚。

下节实验的10枚 synthetic-coin 是作者明确构造的测试补偿，不是根据旧奖励缺收据推断出来的未领取奖励。历史三分类是提交前的工程决策要求，实验没有自动实现这项判断。[7]

## 6. 可信构包先完成语义验证，摘要再固定提交内容

候选验证通过后，应把它连同批准动作冻结成提交包。包至少关联：存档所属账户/谱系、源故事与宿主修订、源存档字节摘要、源与目标编译内容、运行时身份、映射版本、检查点政策、候选字节摘要及动作的业务键与载荷。

这些字段必须来自可信构造流程，而不是接受一个任意 JSON 的自我声明。构包器要取得对应工件，核对真实字节摘要、确认版本对和映射被批准、用该目标内容与运行时重载候选，并完成上述事实与后续行为校验。然后冻结校验过的同一份字节和动作，提交器不得在校验之后另读一个可变化文件再写库。生产中可以通过受控内部接口或受验证的构建产物建立信任；仅加一个任意调用者可改的 `validated=true` 没有作用。

包摘要回答的是“这次请求是否仍是同一份声明”，不回答“声明是否真实且语义正确”。有限集成的 `migrate()` 核对包摘要、当前源身份与候选字节，却不重新验证目标内容、映射、运行时和候选的生成关系。它因此只能接收可信构包器已经验证并冻结的输入，不能作为安全的任意包导入 API。[7]

原始存档、完整包、映射、构建工件及校验记录需要可恢复地保留，活动存档正常推进后仍应能解释历史操作。本实验操作表只存包摘要与结果，完整包保留在外部文件中；这没有验证文件丢失后的恢复。生产协议宜把内容身份与存储定位器分开：同字节文件换路径不应改变业务含义。本机原型将绝对 candidate_path 也计入包摘要，路径变化会冲突，不宜照抄为可搬迁的包格式。[7]

## 7. 同库提交：先找历史操作，再判断新操作是否过期

以下方法的前提是故事 BLOB、库存、业务收据和迁移操作记录真正处于**同一数据库事务**。故事文件单独落盘、库存通过网络更新，都不满足这个前提。

为便于实现，可以把持久状态分成四类：`active` 保存当前故事与修订，`inventory` 保存宿主资产，`receipts` 按业务事件键保存载荷与结果，`operations` 按迁移操作键保存包摘要与历史提交结果。真实多玩家系统还需在各表、唯一约束及查询条件中一致包含账户/谱系范围；实验只有单个活动存档和单种货币。[7]

```text
在事务外完成可信构包、冻结和归档
BEGIN 写事务
    查 operations[操作键]
    若存在：
        包摘要不同 -> 冲突并退出
        包摘要相同 -> 返回已保存的历史结果，不写 active 或奖励
    核对当前源存档、内容、故事修订和宿主修订
    任一不符 -> 过期候选，回滚并重新构造
    对每个已批准动作：
        同业务键、不同载荷 -> 整笔回滚
        同业务键、同载荷 -> 复用已完成结果
        未见业务键 -> 更新库存并写入收据
    写入完整候选、目标内容与新活动修订
    写入操作包摘要及历史结果
COMMIT
确认提交后才向 UI 开放新版故事
```

源修订门槛防止构包期间玩家继续推进，或库存、任务等查询依赖变化后仍提交过期候选。所有相关写入路径都必须维护一致的修订约定；只让迁移代码递增修订没有用。本地原型使用 `BEGIN IMMEDIATE` 取得 SQLite 写事务，读取与更新在同一连接中；生产实现仍需定义忙等待、失败重试与所有写者遵守的约定。[7]

为何先查操作，再查源？假设 M 从故事修订7提交到8，响应丢失。重试 M 时当前已经是8，先检查“当前必须等于源7”会错误拒绝本来成功的操作。再假设玩家继续到9，重试时若重新激活 M 的候选，则会把9覆盖回8。正确返回值是“M 曾在8提交成功”，而当前活动状态仍为9。客户端需要当前故事时另读 `active`，不能把历史回执中的候选当成当前游戏进度。

同库原子性也解释了为什么仅调整三次独立保存的顺序不够。先发奖再写收据，间隙失败后可能重复发；先写收据再发奖，间隙失败后可能漏发。收据与对应效果必须共享提交边界。COMMIT 的响应丢失时，按稳定操作键查询持久记录，不以“没有收到返回”推断未提交；数据库不可用时保持结果未知，不另造操作键重新发奖。

### 真实候选的有限故障观察

实验把两份原生候选原样写入 SQLite BLOB，与库存、收据和操作记录共同提交。每份候选各走桥、公路两路，共四例。`synchronous=FULL`，以独立子进程在指定位置退出，再重开数据库。[7]

| 观察时刻 | 故事修订 / 宿主修订 | 库存 | 收据 / 操作数 | 结果 |
| --- | --- | --- | --- | --- |
| 提交前退出后重开 | 7 / 3 | 0 | 0 / 0 | 四类持久状态均保持初始值 |
| COMMIT 返回后立即退出，丢失回执 | 8 / 4 | 10 | 1 / 1 | 候选 BLOB 等于输入字节 |
| 按原操作重试 | 8 / 4 | 10 | 1 / 1 | 返回保存的历史结果 |
| 从库内候选实际走到终点并保存 | 9 / 5 | 10 | 1 / 1 | 保存桥或公路终点字节 |
| 推进后再次重试原操作 | 9 / 5 | 10 | 1 / 1 | 返回历史提交修订8，活动状态不倒退 |

同操作更换 mapping 或 actions 被包摘要冲突拒绝；新操作沿用旧源修订被过期检查拒绝。两者都没有修改当前状态。这些结果支持指定单写者流程的回滚与重试顺序。退出方式是 `os._exit`，不是断电或磁盘损坏；也未覆盖真实并发、多个存档槽、网络存储和完整游戏生命周期，不能称为端到端 exactly-once 认证。

原生执行使用固定上游 C# 源码、SDK 8.0.428 与 runtime 8.0.34，以 Roslyn 和 .NET 8 引用程序集独立构建。原 netstandard 项目构建没有成功，因此这里的观察不等于官方包或原目标构建认证。复现材料保存实际命令、源文件、输入、输出、失败记录与摘要。[6][7]

## 8. 奖励在远端时，保存候选不等于完成迁移

以下是未执行的跨服务设计。它要求远端支持持久业务事件键，且在远端自己的事务中共同写入奖励与收据。同键同载荷返回既有结果、异载荷冲突；客户端独自保存“已发过”不能提供这种保证。

可以采用持久待发送表（outbox）：本地事务写入不可变候选、源修订、操作及批准命令，将迁移记为 PREPARED。保留旧活动存档，但阻止该谱系继续推进。发送器只发送持久化命令，失败后沿用同一事件键，不重新演故事产生另一批命令。远端结果逐项持久确认，全部批准动作完成后，本地事务校验源状态并激活候选，将操作记为 COMMITTED。

远端已完成但响应丢失，或本地还未保存确认时，都以原键查询或重试。全部确认但未激活时，只恢复激活步骤。已经 COMMITTED 的相同操作依然只返回历史结果，不重新发送、不重新激活旧候选。网络分区期间不能保证完成时间。

若一部分奖励已经完成，另一部分被拒绝，本地回滚故事并不能撤销远端奖励。操作应留在 BLOCKED 状态，按授权政策前向修复或发独立补偿动作；补偿自身也可能失败。若产品不接受“奖励已可见而故事尚未激活”的窗口，就需要服务端统一原子批处理、预留后确认或调整业务边界，而不是给客户端重试增加次数。远端既无幂等键又无法查询权威结果时，应保持待解决状态，不能宣称自动保证不重不漏。

## 9. 在自己的项目中验收这条恢复链

把每个版本对的验收对象放在整条链上：旧内容能否解释省略字段；映射是否保留作者承诺的经历；入口是否重新建立所需状态；候选是否关闭所有宿主出口；批准动作是否有可靠历史分类；写入的字节是否就是验证的字节；提交重试是否保护已经推进的新存档。

代表性测试至少应包含一个被显式保存的旧值和一个被省略的默认值，一个“数值或下一屏相同但后续选项不同”的反例，以及一次“提交后丢回执、随后正常推进、再重试”。测试重点是比较事实、允许与禁止的行为和持久状态，而不是累积无异常运行次数。真实游戏还应依据自己的存储、并发和历史记录情况选择故障与输入组合。

这条方法最终保留的不是某个旧 JSON 形状，而是一份明确的恢复承诺：哪些玩家经历仍然有效、哪些执行历史被批准重建，以及每个可持久动作何时才算完成。内容作者决定语义，可信构包器验证候选，宿主事务维护持久状态；任何一环的未知都不能由另一环的“加载成功”替代。
