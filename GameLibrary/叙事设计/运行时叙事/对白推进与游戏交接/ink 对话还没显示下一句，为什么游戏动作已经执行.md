# ink 对话还没显示下一句，为什么游戏动作已经执行

守卫先说“等我看一下”，玩家点下一步才会看到“许可已经签好”。但测试发现，第一句刚出来，通行许可已经加到背包；点下一步又加了一次。两句对白都只显示一次。这不是 UI 按钮连点：故事运行时为了判断一行是否真的结束，可能先执行下一行附近的逻辑，再把自己的状态退回换行处。而游戏背包不会跟着退回。

以下以 ink v1.2.1 的 C# 运行时为例。需要区分三件事：运行时为了排版向前读过什么，`Continue()` 实际交给游戏哪一行，以及游戏应该在哪一刻承认并提交动作。

## 换行读到了，却还不能确定要不要换

ink 的 glue（`<>`）能把源文件中原本分开的文本接到同一行。例如“出口在”和计算出的路名可以连起来。运行时遇到可能的行尾会保存一份故事状态，继续查看：若后面的 glue 去掉这个换行，就继续保留这次求值；若多出新一行的文本或标签，就可以恢复到原来的换行，先把当前行交给调用方。[1][2]

情形的区别在于**谁拥有状态**。ink 能恢复自己的故事状态，包括试探期间改过的变量；调用一个宿主外部函数时，函数已经动过的背包、门或任务记录不在 ink 的快照内。把这样的函数绑定为 `lookaheadSafe: true`，就是允许 ink 在前瞻时调用它，不是给它加了一层自动回滚。

这个试件把故事内外两个计数都记下来。 `ledger` 是 ink 的变量，`stamp()` 每次调用让 C# 宿主的计数加一：

```ink
EXTERNAL stamp()
VAR ledger = 0
等我看一下。
~ ledger += 1
~ stamp()
许可已经签好。
-> END
```

用 v1.2.1 的官方编译器和 C# 运行时实际运行，两个绑定的文本相同，效果计数却不同：

| 绑定方式 | 第一次 Continue 返回“等我看一下。”后 | 第二次返回“许可已经签好。”后 |
| --- | --- | --- |
| 错把 `stamp` 标为前瞻安全 | ink 变量 0，宿主累计 1 | ink 变量 1，宿主累计 2 |
| `lookaheadSafe: false` | ink 变量 0，宿主累计 0 | ink 变量 1，宿主累计 1 |

第一行尤其有用：故事里的数值退回到 0，宿主的数值却是 1，足以区分“多了一次外部调用”和“用户多推进了一行”。在固定版本实现中，标为 false 的已绑定函数若遇到保存的换行快照，会触发恢复，前瞻阶段不会运行该函数；这**不是**“必定等到关联文本显示后才调用”的承诺。第二次 Continue 内部仍会先执行动作，再把文本交给 UI。[2]

## 纯查询和游戏动作分开绑定

- **只需为这一行提供一个值：** 纯计算或读取本次推进固定不变的输入，可以允许前瞻。像读固定快照的地名、格式化数值这一类调用，即使多执行一次也不改变游戏状态。若查询消费随机数、弹出队列首项或改变后续查询的结果，它就不满足这个条件。
- **需要在 ink 求值期间改变宿主：** 把绑定显式设为 false，用独立指令行而非字符串插值或选项文字求值。固定版本在字符串生成期间会拒绝前瞻不安全的外部函数；复杂内容可先在独立指令求必要的值，再使用变量，不能为了消掉错误把副作用标为安全。[2][3]
- **应该由画面、语音或玩法决定提交时点：** 不让外部函数直接发奖励，而让当前对白产出一个动作请求，宿主获得它以后再根据规则应用。

不能靠一律关闭前瞻省掉分类。同一组实测中，纯 `route()` 返回固定的“北门”，仅测试程序记调用次数，后面紧跟 glue。允许前瞻得到一行“出口在 北门。”；设为 false 得到“出口在”和“北门。”两行。两组都只调用一次，差别是 false 的调用阻断了 glue 跨过该换行，破坏了预期的演出切分。C# 常用 `BindExternalFunction` 与底层通用绑定的默认值也不同；直接写出参数，比假定整个 API 都默认为 false 更可靠。[2][3]

## 用返回行交接动作，不用“开始求值”当发奖信号

把第二句改成 `许可已经签好。 # action:license:guard_north:first`。每次 Continue 完成后，立即复制本次 `currentTags`，和返回的文本组成一个交给演出层的数据包。第一句在试验中没有这个标签；第二句有。不要从 `currentTags` 反复轮询发奖，也别按译文去匹配动作：标签里的事件键应由内容定义，并独立于表面文案。[3]

接下来由项目决定提交时刻。若玩家读到这一句就应拿到许可，可在展示系统接收这份已确认的数据包时提交；若要等配音结束、领取或玩家明确确认，就把请求放在对应的步骤，定义跳过或中断时该执行还是取消。取消后，迟到的旧配音完成回调不得再提交已失效的请求。这里还有一个顺序约束：如果后续选项要查询许可状态，且这一状态必须由该事件改变，就要在提交或取消前暂停相关内容的推进，或者让故事先记下已授予的事实再由宿主同步。提前缓冲完整段文本再等配音结束才发奖，可能用旧状态先算出了选项。

一次已返回的标签也可在读档重跑时再次出现。试件保存第一次 Continue 后的 ink 状态，领完许可再恢复这份状态，第二句和标签都会再次返回；宿主保留的已处理键拒绝了第二次增加。试件只恢复 ink，宿主世界没有回滚；它用的是内存集合，不是可跨启动的存档。恢复整个游戏存档时，效果和去重记录应回到同一时点。真正“一次性”的许可应把可稳定识别的事件键和业务效果一起保存，或让宿主命令按该键幂等：效果与去重标记不能一个存成了、另一个还没存。若玩家能在配音等待期间存档，要同时保存未提交的请求，或把故事检查点留在能重新产生该请求的位置；只保存已应用的键防不了待办丢失。若关卡允许再次领取，键还得区分轮次，不能把合法的下一次领取也吞掉。

复查时同时记录 Continue 序号、返回文本和标签、外部函数调用、最终应用的事件键。至少比较三段：第一句停住不点、连续推进到第二句、读档重放同一句。若要等演出完成才发，还要复测跳过和取消。错误绑成前瞻安全会在第一段就露出来；标签回放重复属于另一层，靠宿主提交规则解决。
