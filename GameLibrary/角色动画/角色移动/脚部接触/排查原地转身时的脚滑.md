# 排查原地转身时的脚滑

角色站定后向右转身，身体朝向已经对准目标，支撑脚却沿地面画了一段弧；或者转身片段播放得很好，一回到待机，身体又弹回原朝向。遇到这些现象，先不要急着加脚部 IK。问题可能出在动画与角色控制器重复旋转，也可能出在导入设置、过渡混合或换骨架后的动作适配。

本文面向动画师、技术动画和玩法开发人员。假设你能检查转身片段、角色对象与脚骨位置，目标是在一个可重复的转身场景中找到误差最先出现的位置，再决定应该改动画、运动代码还是足部修正。这里不提供适合所有角色的接触阈值，也不要求使用某个引擎。

## 先弄清楚：身体转了，还是角色对象转了？

**根运动（Root Motion）**是从动画中提取、用来驱动角色整体移动或旋转的运动信息。具体取自哪个骨骼或变换，由引擎和导入方式决定。它与腿、腰等骨骼相对角色的姿态不是同一层，也不等同于脚本最终施加给角色的变换。

以一个向右转 90° 的动作为例，可以采用两种明确的方案。第一种让动画提供整体转角，运动代码接收并处理后应用；第二种让控制器决定转角，动画只配合表现。两者都需要让身体旋转与脚步节奏匹配，但不能未经设计就同时把同一份转角叠到角色上。

如果代码先转 90°，又把动画提供的同轴 90° 完整叠上去，理想化结果就是转了 180°。这只是同轴例子；三维旋转不能普遍按欧拉角相加。它提醒我们检查“哪个环节最终写入朝向”，而不是用一个经验缩放系数掩盖重复旋转。

还要区分**提取**与**应用**。能够读到动画旋转增量，不表示角色已经转动；预览里身体转了，也不表示运行时提取了同样的根运动。后文的引擎设置正是用来核对这个区别。

## 建立一个能看清问题的转身场景

先选一个片段、一种体型和固定起始朝向，在平地上重复同一个 90° 转身。临时绕开过渡混合、瞄准叠加和足部修正，用于隔离问题；不要把这组诊断设置直接当作最终玩法方案。

同时观察三处：负责整体移动与碰撞的角色对象、可见骨架相对角色的变换，以及两只脚相对地面的运动。只看最终朝向会漏掉一种情况：角色对象已经转完，骨架仍带着相对旋转，回到待机时才把它消掉，于是出现回弹。

在动作中选出一段**应保持接触的位置**。支撑脚不一定整只脚都不动：若动作设计为以前脚掌为支点，脚跟抬起或绕支点旋转是预期动作。应先由动画师指出要观察哪个接触点及其时间段，再讨论滑动量，不能把任何脚骨运动都判为脚滑。

建议在同一动画求值与运动更新序列中，对照片段时间、提取出的旋转、实际应用的旋转和接触点位置。所谓“求值”，就是动画系统根据当前时间、权重等条件算出姿态。记录这些量的目的，是找到哪一步开始偏离，而不是收集一张越长越好的日志表。

## 脚相对身体在动，可能正是为了相对地面不动

设角色绕竖直轴转动，而支撑点要留在地面上。此时脚相对角色的位置通常需要反向变化。如果只转角色、完全保留脚的局部位置，脚就会跟着角色绕圈。

可以用一个简化关系理解它：

```text
脚的世界位置 = 角色世界变换 × 骨架相对角色的变换 × 脚在骨架中的位置
```

这里右侧最后一项已经包含脚上方骨链的变换，不是脚骨相对直接父骨的原始局部坐标。这个式子表达坐标组合，不规定引擎内部更新顺序。

因此，排查时至少要说清“这个位置是相对谁的”：动画里看到的脚轨迹、运动代码里的角色位置、地面上的接触点，不能直接拿不同空间的数值相减。对于静止地面，可以跟踪接触点的世界位置；对于移动平台，应转到平台坐标中比较。脚随平台正常移动，不应被算成相对平台的滑动。

在接触开始时保存参考位置，之后观察它相对参考点的偏移即可形成一个简单诊断量。但多大偏移可接受，仍取决于角色比例、镜头和动作意图。数值很小也不自动说明动作自然。

## 单片段就出错：先查运动有没有被漏用或重复使用

如果没有过渡时就滑，先跟踪根运动到角色对象的整条路径：片段是否有需要的旋转，导入时是否保留为根运动，运行时提取到多少，最后由谁应用。平移、绕竖直轴的转向和重力可以有不同负责人，不必用一句“启用了 Root Motion”概括全部行为。

一次动画求值产生的增量，也不应因为多个更新函数读取了它就被应用多次。例如动画只更新一次，运动更新却执行两次；若后者每次都使用“最新增量”，第二次可能重复使用同一份数据。项目需要明确怎样缓存、合并和标记已应用的增量，而不是假定 getter 读过就会清空。

若设计选择控制器驱动转身，也不要只关闭根运动然后结束排查。控制器使用的转速和动画支撑阶段可能不一致：身体已经继续转，动画里的脚却仍按另一套节奏停留。此时应调整动作选择、转身时间或明确的姿态补偿，而不是要求脚部修正无限拉住脚。

恢复碰撞或其他运动约束后，还要比较**请求的运动**与**实际完成的运动**。动画建议走或转多少，不等于角色最终完成多少。发生差异时先解释它来自哪里，再决定如何让姿态配合；不要为了贴脚而破坏碰撞规则。

## 只在过渡时出错：检查支撑阶段是否被混在了一起

单片段正常后，再逐项恢复待机到转身、转身到待机和中途打断。每次只加一种变化，才能看出哪一步引入滑动。

假设转身末尾仍以右前脚掌为支点，而待机姿态已经把重量移到另一侧。把两个姿态平滑混合，不自动等于接触点也沿正确路径变化。旧版资料中的二维几何模型就说明：两个端态都能保持同一世界接触点，并不足以保证直接混合局部位置和根角度后，中间状态也保持该点。这是简化数学反例，不是某引擎混合器必然出错的实测结论。

如果问题只在过渡发生，应查看进入与退出片段时的支撑阶段、根旋转是否随着权重变化，以及骨架相对角色的偏移是否被恢复。把混合时间拉长可能缓和突变，也可能让错误接触持续更久，所以应回到接触点轨迹判断，而不是只凭过渡“更柔和”。

## 最后再决定怎样锁脚

**IK（逆向运动学）**是根据末端目标求解骨链姿态的方法。脚部 IK 可以帮助脚接近指定接触点，但前提是目标、接触时段和角色整体运动已经说清楚。

只在预期接触段建立目标，抬脚时释放，下一次落脚再建立新的接触。不能仅凭脚速度低就断定贴地：悬空停顿也可能低速。角色转得过远、腿够不到目标时，也需要换步、释放或换动作，而不是持续拉伸姿态。

若原动作在源角色上正常、换到另一种体型后才滑，应优先检查**重定向**，即把动作转移到另一套骨架的过程。UE 的 Speed Planting 文档就针对这种情况，结合源脚速度曲线、目标角色 IK Goals 与求解器处理接触。[4] 这是特定工作流，不是所有转身脚滑的通用开关。

锁脚后仍要看最终姿态。若足部修正完成之后，另一个操作又转动躯干或骨架父节点，它可能改变已经得到的脚位置。此时检查实际修正顺序和目标坐标，而不是只增加 IK 权重。复杂骨架约束的排序需要单独分析，本篇不规定所有角色通用的求值顺序。

## Unity与Unreal中，哪些设置值得先核对

以下是文档对应点，不是已经验证的角色方案。

**Unity 6000.0：**在 Humanoid 的 Root Transform Rotation 设置中，`Bake Into Pose` 会把旋转保留在姿态中，使根旋转增量为单位旋转；因此不能仅凭片段里身体转向，就认定 GameObject 会按同角度旋转。[1] 若脚本实现 `OnAnimatorMove`，`applyRootMotion` 不再决定该路径的自动应用，运行时切换这个属性还会重新初始化 Animator。该回调在动画求值后、`OnAnimatorIK` 前执行。[2] 排查自定义运动代码时，应先找到回调和控制器中真正应用增量的位置。Generic 骨架需另核对 Root Node，不直接套用 Humanoid 的根变换解释。

**Unreal Engine 5.6：**除了资产的 `Enable Root Motion`，还要看 Animation Blueprint 的 Root Motion Mode。`Ignore Root Motion` 会提取并移除根运动，却不应用到角色；`Root Motion from Everything` 则按参与姿态的资产权重混合根运动。[3] 所以单个片段的总转角，不能代替过渡期间实际提取和应用的转角。

## 一次排查结束时，应该留下什么

有效的结论应能指出下一项修改。例如：“单片段正常，加入待机过渡后右前脚掌偏移；先调整接触阶段衔接”，或“同一旋转增量由动画回调与控制器各应用一次；先取消重复应用”。相比“开 IK 后看起来好多了”，这样的结论更容易由动画、技术动画和玩法开发共同处理。

随后再扩展到左右转、不同角度、比例不同的角色，以及中途反向等玩法情况。不要将单一角色的一次成功当作全部情况通过，也不要在没有帧时数据时承诺额外修正的性能成本。

## 附记：旧资料中的有限验证

旧资料包含四项二维几何模型检查，只支持坐标组合与重复旋转等简化反例，没有真实骨架或 IK。

另外，一组 Godot 单骨实验采用人工位置/旋转轨道、手动推进动画和无碰撞节点。推进 0.5 秒后读到 22.5° 的旋转增量；未再次求值时重复读取仍是同一增量，只有再次执行应用代码才重复旋转。作者与独立复核各重复两种配置。这个观察支持区分提取、读取与应用，与 Godot 4.6 文档的接口分工对应。[5]

它不包含真实脚部、碰撞控制器、混合或重定向，也不验证 Unity／Unreal。历史安装构建与公开比较源码的精确对应未获认证。本次仅保留已有观察范围，没有重跑或把它扩大为通用角色结论。
