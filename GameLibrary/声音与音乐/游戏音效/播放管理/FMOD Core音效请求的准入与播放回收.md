# FMOD Core音效请求的准入与播放回收

一场爆炸触发几十个碎片碰撞音，脚步系统又重复提交同一次落地事件。把低价值声音设成低优先级后，实际混音的声音少了，但播放对象仍在增加；程序如果见到某个声音变为虚拟就释放自己的名额，下一帧还会继续创建。另一个常见错误发生在失败路径：声音已经创建，只是设置位置失败，应用删除记录，却没有确认这次播放已经停止。

这些问题需要一套贯穿请求、创建和终止的管理方法。本文面向了解基本 FMOD Core 调用与返回值处理的音频程序员和技术音频设计师，给出**先限制请求，再保留每次播放的额度，最后凭终止结果回收**的控制侧方案。目标是让重复事件、突发层数和失败收尾都能得到明确处理，而不是仅调整谁更容易进入混音。

接口依据为 FMOD Engine User Manual **2.04.00（2026-09-29）**，本文没有执行 SDK 原生测试。范围限定为已加载、持续有效的内存 PCM Sound，固定组路由，纯 Core API，由一个控制侧所有者管理播放和记账。流式加载、Studio Event、跨线程回调管理、设备故障后的系统重建不在这条正常播放路径内；遇到无法确认的故障时，下面会明确停在哪一步，而不假装已经恢复。

## 三种上限分别管什么

`Sound` 是可播放资源，`Channel` 是一次播放使用的对象。同一份 Sound 可以对应不同的播放实例，因此不能按素材文件数统计正在管理的播放。[1][2] 这里的 Channel 也不是立体声的左、右输出通道。

要同时记录三个不同的上限：

| 上限 | 由谁决定 | 解决的问题 |
|---|---|---|
| 应用实例预算 B | 本文的播放管理器 | 允许多少次尚未确认结束的播放进入系统 |
| FMOD 总 Channel 容量 M | `System::init(maxchannels, …)` | FMOD 能保留多少播放 Channel，包括虚拟播放 |
| 实际混音容量 R | `System::setSoftwareChannels` | 其中多少 Channel 能获得软件混音资源 |

M 与 R 是不同配置；后者需要在初始化前或关闭系统后设置，不是每次收到爆炸请求时调整的业务阀门。[2] B 则是应用政策，不由这两个接口自动提供。

虚拟化保留播放进度等状态，使一个 Channel 有机会重新成为真实声；总容量不足导致的偷取则可能永久结束原播放。[3] 所以“此刻没有实际混音位置”与“已经没有这个播放对象”必须分开。假设 B=3、M=8、R=1，三次有效播放中有两次虚拟，应用仍可能已经满额。把 B 写成 `isVirtual == false` 的个数，会把虚拟实例漏掉。

若希望避免本管理器触发总容量偷取，应使它的最大在途实例数，加上系统中其他创建者的**可信上界**，不超过 M。仅在某一帧查询到“还有空位”不够：另一个创建者可能随后使用它。本文把全部相关创建串行交给一个所有者；如果项目绕过这个入口播放声音，上述容量保证就不再成立。

## 去重针对事件，层数限制针对同时存在的声音

创建前需要知道为什么请求播放。建议请求至少带上事件身份 `request_id`、发声者身份及代次、声音类别、Sound 标识、必要参数和截止时间。代次用于区分被销毁后复用同一对象编号的新发声者；截止时间采用应用约定的单调时钟，不用素材长度猜测请求还能否使用。本文的资源映射预先确定每份 Sound 的 2D／3D 与循环模式，创建前拒绝与映射不符的请求，不在这一播放流程中临时切换模式。

### 同一事件重投，与不同事件合并

一次落地事件可能被同一逻辑重复提交，两次提交沿用相同的 `request_id`。管理器对已经登记的身份保存处理结果，在约定保留期内重投时直接返回原结果，不再创建，也不把原成功结果覆盖成“重复而拒绝”。同一身份必须始终表示同一事件，不能重用身份来提交不同参数。播放结束也不立即删除这份去重记录，否则延迟到达的同一事件会再次起音。

另一方面，两颗子弹击中相同表面可以使用同一 Sound，却是两个有效事件。是否把它们合为一层，要由声音设计决定。例如以“发声者代次＋效果类别＋短时间窗口”为合并键，只保留窗口内第一声，或保留能量最大的那声。选择后必须说清合并掉了什么信息，不能用“文件相同”替代事件判断。

连续机器声更适合表达为“这个发声者当前应当运行”，重复开机意图更新现有实例，而非每帧追加一次播放。本文后续的实例流程同样可以管理该循环，但循环意图状态与单次事件去重分开保存。停止控制直接按实例身份交给所有者处理，**不经过新增播放的满额拒绝规则**。如果跨线程传递控制，需为停止意图保留可达通路，例如在有界发声者表中覆盖其期望状态，避免新增请求塞满队列后连停止也无法送达。

### 给入口本身设边界

只有播放预算还不够。无限请求队列或无限去重表，也会把突发压力换个地方保存。

一种容易推理的起步政策是：入口最多容纳 Q 个待处理请求，每 tick 最多取 K 个；队列满时立即拒绝新请求，取出时丢弃过期项，处理过的事件结果只保留约定期限。去重表也设容量；若已满且没有可安全过期的条目，就拒绝新的事件身份，不提前驱逐仍受保护的身份。Q、K 和保留期均由业务延迟与重投协议决定，本文不给通用常数。

这里区分两种返回。**未登记拒绝**表示队列或结果表没有空间，本次没有取得处理结果槽位，也没有创建播放；调用方可以在事件仍有效时限次重投，本文不保证记住这种拒绝。**已登记结果**则先取得有界表中的槽位，再进行业务额度检查与创建，随后将成功、业务拒绝或创建失败写回该槽位；保留期内重投只返回这一结果。去重结果表有空间，不代表播放预算也有空间。

例如 X 因结果表满而返回未登记拒绝，稍后条目过期，X 仍未过截止时间，它可以重新竞争准入；若 X 已登记但因碰撞层数满而被拒绝，同一 X 在保留期内仍返回该拒绝，不因后来有空位而补播。这份有限保证既避免无限保存拒绝，也说明了调用方何时可以重投。

在本 tick 的有限批次中，可以按业务重要性降序、再按接收序号稳定排序。排序仅改变**尚未准入**的请求谁先尝试，不会挤掉已有实例，也不能使未进入队列的高价值提示穿过一个已满的普通入口。关键提示若需要预留服务能力，应给入口与实例预算同时留出专用份额，并明确哪些类别能借用剩余额度。

这种立即拒绝策略不会自动补播过时声音，代价是拥挤时确实会丢弃合法事件。如果设计要求排队等待，需要另行决定最长等待、过期与替换政策，不能把所有被拒事件无限重试。

## 一次准入，要同时占住所有相关额度

除全局 B 外，项目可以限制“同一发声者的碰撞层数”或“整场景的碎片音层数”。这些是应用预算类别，不等同于 FMOD 的 `ChannelGroup` 或 `SoundGroup`。一个实例可能同时占全局、类别、发声者三项额度；放行前必须全部检查，成功后一起登记，结束时一起归还。

本文采用满额拒绝新请求，不自动停止旧声来替换。它牺牲了部分临时优先级响应，却避免一次准入同时管理“旧声停止成功了吗”和“新声创建成功了吗”。若确实需要替换，必须先确认旧声终止，或为旧声与新声的重叠另留额度；发出 stop 之后立即把其额度借给新声，会绕过失败保护。

额度计算采用以下不变量：

```text
占用 = 已预留但尚未完成创建
     + 已创建但仍在暂停配置
     + 已提交播放（真实、虚拟或尚未观测）
     + 清理未确认或创建结果未明

对全局及每个适用预算类别：占用不超过各自上限。
```

先预留再调用 `playSound`，使同一批次的后续请求立即看到这个名额已被使用。配置与播放状态变化只移动记录，不再重复加一。自然结束、主动停止和偷取统一进入一个归还函数，每个实例最多归还一次。

每条记录保存应用生成的 `instance_id`、本次成功创建所得的原 Channel 句柄、占用的预算类别、生命周期状态、最近 API 结果和失败原因。若记录存放在可复用槽位中，对外身份使用“槽位＋代次”；旧停止请求的代次不匹配时直接忽略，不能停止后来复用槽位的新声。

发声者预算索引也要有界：没有活动实例且没有其他保留责任的零计数条目应移除，或由有界发声者注册表管理。不能让活动实例受 B 限制，却永久保存每个曾出现的发声者代次。

FMOD 的 Channel 外观像指针，实际上是可识别失效和复用的句柄。[4] 应用身份仍需自己管理：不要解引用它，不按猜测的内部地址认领播放，也不要在回收旧记录时通过池下标重新取一个可能属于新播放的 Channel。

## 暂停创建完成前，额度已经被占用

下列流程是应用设计伪代码，不是可直接编译的 FMOD 包装库。所有步骤由同一个控制侧所有者执行；保留 Core 默认线程安全设置，单所有者只负责使业务检查、预留和记录更新不会彼此交错。

```text
尝试准入(request)：
    如果已有未过期的 request_id 结果：直接返回原结果
    如果事件已过期：丢弃，不创建
    如果结果表没有可用槽位：返回未登记拒绝
    为 request_id 保留结果槽位
    检查参数与资源映射（包括已准备的 2D/3D、循环模式）
    检查全局、类别、发声者额度
    任一失败：在该槽位记录业务拒绝；不调用 playSound

    record = 预留全部相关额度，分配新的 instance_id
    临时 channel = null
    result = System.playSound(sound, group, true, &channel)
    如果 result != OK：
        进入“创建结果未明”故障路径；不使用 channel 输出
        在结果槽位保存创建失败；返回

    record.channel = channel
    record.state = 暂停配置中
    设置本次 priority、volume
    仅对映射已保证 FMOD_3D 的 Channel 设置空间参数
    每一步都检查结果；任一步失败：转入本次实例的清理
    全部成功后调用 channel.setPaused(false)
    若失败：转入本次实例的清理
    若成功：record.state = 已提交播放
    把本次提交成功或配置失败写回结果槽位
```

`playSound` 的暂停创建允许先配置再放开，而且创建时会继承 Sound 的默认频率和优先级。[2] 因而暂停只防止未经配置的起音，不会让这次创建变成“尚未消耗 Channel”。后设 `setPriority` 也不能撤销创建时已经发生的容量竞争；应先解决总容量规划，并在资源准备时核对合理的 Sound 默认值。

`isPlaying` 对已经创建但暂停的 Channel 仍可报告 playing。[5] 所以不能拿“尚未解除暂停”作为不占额度的理由。设置完成后也先记为“已提交”，而非“玩家已听见”或“已经分到真实声”。

`set3DAttributes` 要求对象已经具备 `FMOD_3D` 模式，否则返回 `FMOD_ERR_NEEDS3D`。[5] 上述资源映射校验使这项前提在调用前成立：2D 请求不进入空间设置分支，3D 请求使用已按 3D 准备的资源。若项目要允许每次播放切换模式，应另加合法模式设置及检查，再调用依赖它的空间接口，不能把顺序倒过来。

同一 Sound 被多人播放时，每次播放的属性应在自己的 Channel 上设置。清理本次失败只停止这个 Channel，不停止整个组，不释放共享 Sound。`Sound::release` 会影响该资源的播放实例，属于资源所有者的职责，不是退还一个播放名额的方法。[1]

### 创建失败和配置失败是两类不同问题

配置失败时已经持有成功创建的 Channel，可以对它调用 stop 并检查结果。创建调用本身失败时，不能把输出参数当成有效 Channel 继续清理。

2.04 的公共接口说明没有为所有 `playSound` 非 OK 路径给出一个可供本文依赖的完整原子回滚承诺。`FMOD_ERR_CHANNEL_ALLOC` 的名称只说明分配出错，不能靠名称推定所有内部阶段的状态。[6] 本文因此选择明确的保守故障政策：**任何创建调用非 OK，都保留该预留记录，冻结本管理器的新准入，并上报首个错误**。这不是断言 FMOD 必然留下了播放，只是不再根据未经确认的结果继续记账。

如果项目已经针对指定 SDK、错误类别和调用前提建立“该失败确定没有创建播放”的适配约定，可以只对这些已确认类别取消预留。没有该约定时，未知记录不进入 Channel 轮询，不拿空指针调用 stop，也不在下一 tick 自动重试同一事件。它需要系统所有者按故障恢复流程处理；本文不提供设备或整个 System 的自动销毁重建算法。正常的业务拒绝与调用前参数校验失败则没有发出创建，可直接返回，不进入这种隔离。

这项政策优先保护容量与对象一致性，代价是一次异常可能暂时关闭新的声音。需要更高可用性的项目，应补齐有限、可验证的错误恢复协议，而不是超时后无条件清零所有额度。

## 用终止事实回收，而不是用“听不见”回收

每 tick 先调用一次 `System::update` 并检查结果，再轮询已有记录，最后处理新请求，是本文选用的控制顺序。update 参与虚拟状态更新等工作，但并不把此后的所有查询变成同一时刻的快照。[2] 更新失败时冻结新准入并进入系统故障处理，不把本轮回收当作已经成功。

对拥有有效来源的原 Channel 句柄，依次处理：

| 操作与返回 | 记录如何变化 |
|---|---|
| `isPlaying` 返回 OK，值为 true | 继续占用；需要诊断时再查询 `isVirtual` |
| `isPlaying` 返回 OK，值为 false | 通过统一归还函数关闭该实例 |
| `isVirtual` 返回 OK | 只更新真实／虚拟观测，不变更额度 |
| 对原句柄调用返回 `INVALID_HANDLE` 或 `CHANNEL_STOLEN` | 在下述前提成立时关闭原实例 |
| `stop` 返回 OK | 关闭该实例并归还一次额度 |
| 其他错误 | 不读取该调用的输出值，不退额度；记录并处理故障 |

stop 或自然结束会使原 Channel 句柄失效；句柄章节将被偷取后的错误明确写为 `FMOD_ERR_CHANNEL_STOLEN`。[4][5] 资源管理章的总容量说明另使用了 `FMOD_ERR_INVALID_HANDLE`。[3] 本方法接收两者作为旧播放不可继续的证据，不依赖所有版本、所有终止路径都返回同一个码。

**这里有重要前提：**句柄必须来自本管理器一次返回 OK 的创建，保存后没有被覆盖，所属 System 及固定路由对象仍然有效，期间没有发生未经管理的系统销毁或资源释放。一个未初始化、损坏或错误归属的句柄返回 INVALID_HANDLE，不足以证明某个业务实例正常结束，应转为所有权错误。本文不对已经销毁的 ChannelGroup 指针套用这条句柄规则。[4]

一次 `isPlaying` 返回 true 后，声音仍可能在下一次 `isVirtual` 或 stop 前结束。因此每个调用都独立检查返回值，不缓存一个“刚才有效”结论来免除后续检查。即使把 bool 初值设为 false，调用失败时也不能拿这个初值当成播放终止。

对于“清理待确认”的实例，保留原 Channel，按同样规则轮询；如果仍在播放，在项目规定的限次、退避策略下重试 stop。停止意图一直保留，不能因为某次查询仍为 true 就恢复为正常播放。连续错误达到告警条件后保持占位并冻结新准入，交给故障处理，不能为了让新声进来而抹掉记录。

可以把归还动作集中成下面一个小操作：

```text
finish(instance_id, terminal_reason)：
    找到相同身份与代次的记录
    如果不存在，或已经不持有额度：返回
    把持有标记清为 false
    对记录曾占用的每项预算减一
    废弃本次原 Channel，移除活动记录，留下有限诊断信息
```

在单所有者条件下，这个操作使重复终止观察或重复停止控制不会多减一次。去重表中仍在保留期内的 `request_id` 处理结果不会随活动记录一起消失。若改成多个线程直接修改记录，必须重新解决原子性和对象寿命，不能只把计数器换成 atomic 就视为等价实现。

## 准入之后，优先级才决定哪些声获得混音位置

准入解决“是否创建”，FMOD 优先级解决已存在 Channel 的资源排序。`setPriority` 数字越小越重要，同优先级再比较 audibility。[7] Audibility 是可听性估计，不是实测声学响度或实际波形。[5] 把机器声音调轻，不等于系统已经获知“确认提示比机器重要”。

沿用一个纸面比较：只有机器与确认提示两个已开始的有效 Channel，没有暂停、静音、其他竞争者或解码限制；总容量足够，而实际混音容量为一。两者均未触发静音虚拟化阈值，比较期间参数保持不变。

| 声音 | 优先级 | 假定 audibility |
|---|---:|---:|
| 机器运转 | 64 | 0.1 |
| 玩家确认提示 | 128 | 0.8 |

按文档排序，机器先获得位置，因为 64 比 128 更优先。只把机器估计值改为 0.05、仍不触发静音阈值，不能改变不同优先级之间的先后。若两者都设为 128，提示的 0.8 高于机器的 0.1；若把提示设为 64、机器为 128，则是主动改变资源政策。数字只说明关系，不是推荐值或运行结果。

全部声音设为最高优先级不会增加容量，只会重新变成同级竞争；过多等级又可能让很轻的高优先级声排掉明显更响的声音。[3] 而对已经因应用 B 满额而被拒绝的请求，设置一个很高的 FMOD 优先级更没有作用，因为它根本没有 Channel。

按默认继续位置的政策，虚拟提示的起音可能在等待期间经过；后来成为真实声不会自动补交那段内容。`FMOD_VIRTUAL_PLAYFROMSTART` 可改为从头恢复，但仍不保证提示按时到达。[3] 确认信息必须可靠传达时，应把预留预算、入口策略、内容时效和输出检查一起设计。循环暂时失去资源后如何解释恢复位置，可继续读[循环声音重新听见时，应该从哪里继续](循环声音重新听见时，应该从哪里继续.md)；其 CRI ADX 参数不是 FMOD 设置表。需要安排未来起播和淡入，则见[FMOD Core预约播放的时钟与执行顺序](FMOD%20Core预约播放的时钟与执行顺序.md)，本篇不展开 DSP 时钟与混响路由。

## 跟随一个满额场景，检查每一步剩下多少名额

以下为原创控制侧推演，不是 SDK 日志。全局 B=3，相关类别额度均未先于全局达到限制；A 是真实循环，B 是仍 playing 的虚拟单次声，C 的 stop 尚未确认。三个实例各占一个名额。系统更新成功，资源与句柄前提保持有效。

1. B 的同一 `request_id` 再次到达。去重表返回原处理结果，不创建第四声；即便 B 以后结束，只要仍在保留期内，该重投也不重播。
2. 更高业务重要性的新提示 Y 到达。三份额度分别由 A、B、C 持有，满额拒绝 Y。业务重要性并不让 C 的未知结果消失，也不让虚拟 B 变成空位。本政策不自动停 A 换 Y。
3. 下一 tick 确认 B 已终止，调用 finish 后占用变为 2。Y 的原事件已经被拒绝，不在后台自动重试。若业务此时产生仍有效的**新事件** Y2，它可以通过检查，先预留，使占用重新变为 3。
4. Y2 暂停创建成功，但配置失败。管理器保存首个错误并对 Y2 的原句柄调用 stop；若 stop 返回未分类错误，Y2 留在清理待确认，占用仍是 3。下一条请求不能使用它的名额。若已确认是终止码，则可以立即 finish。
5. 后续轮询或 stop 确认 Y2 结束，占用降到 2。针对 Y2 的重复停止消息因旧身份或已归还标记而无动作，不会再降到 1；剩余两份仍属于 A 和 C。

若 B 不是自然结束，而是被 FMOD 永久偷取，第 3 步同样关闭旧 B，不能再等待它恢复真实。如果 A、B 只有一个真实声，也只能得出某次观测的混音分配状态；不能据此证明提示已经从设备输出，更不能证明玩家已理解。

## 接入时验证不变量，再检查输出和代价

先在目标 SDK 中实现最小单所有者入口，把每个请求的接收序号、事件与实例身份、拒绝原因、占用类别、各步 API 返回值，以及归还原因写入有界诊断记录。不要只存“当前播放数”：那无法区分合法虚拟声、暂停准备和未收尾的失败。

至少检查以下场景，每项都在整个过程中断言全局和各类别计数等于仍持有额度的记录数量，且从不为负：

- **突发与重复：**已登记且仍在保留期内的同一事件多次提交只处理一次；不同事件使用相同素材不会误去重；批内先预留能阻止超额；过期和入口满额发生在创建前。结果表满后的未登记 X 在稍后重投时遵守上述有限保证，不向满表追加记录。
- **模式前提：**2D 请求不调用空间接口；需要 3D 的请求若映射到 2D 资源，在创建前拒绝；正确映射的 3D 请求才执行空间配置。
- **暂停与虚拟：**暂停创建期间仍占额度；降低实际混音容量后，虚拟实例仍占额度；单次声在虚拟期间结束后能够回收，循环则按停止控制处理。
- **自然结束与取消相撞：**先后到达的轮询和停止结果只归还一次；槽位复用后，旧代次停止不会影响新声。
- **失败路径：**在每个配置步骤模拟失败，分别输入 stop 成功、终止码和其他错误，检查记录是否留存；创建失败不读取失败输出，也不自动重试。模拟返回值只验证应用分支，不能证明 FMOD 在真实失败时的内部行为。
- **容量偷取：**在隔离测试中故意降低 M，观察旧句柄返回结果并确认应用关闭旧记录。把这种测试与正常容量规划分开，不让正式入口依赖偷取兜底。

原生测试应记录实际运行库和头文件版本、初始化参数、素材与循环模式、每次状态和返回值。文章中的推演目前只说明期望的应用决策，未给出这些运行结果。

最后再用代表场景决定 B、类别上限及 R。若碎片音使确认提示频繁遭到应用拒绝，先检查入口与预算分配；若没有被拒却总是虚拟，检查优先级、可听性和混音容量；若清理待确认持续增长，修正错误处理而非单纯提高 B。增大 R 会改变实际处理工作，增大 B 则允许更多在途实例，二者的 CPU、内存及声音效果需分别测量。轮询每 tick 的工作随活动预算规模增长，其收回名额的时机也受观察频率影响。

这套方法的交付是可解释的播放生命周期：请求被拒有原因，已创建对象始终有人负责，虚拟状态不丢失记账，终止只归还一次。它不保证每个请求都被播放；当信息必须到达玩家时，容量政策之后仍需核查实际输出与提示效果。
