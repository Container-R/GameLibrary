# 对白第一次播放迟到：预热完成以后，首块音频还在吗

同一句对白在编辑器里反复试听正常，打包后第一次触发却慢半拍，马上再播又正常。另一份报告说它“吞了第一个字”。这两种反馈可能听起来相似，修法却未必相同：整句迟到需要找起播等待；开头内容确实缺失，还要查起播偏移、淡入、解码和播放政策。

本文面向了解音频资产导入与播放调用的开发者，用 Unreal 的流式音频缓存说明如何排查第一次播放。目标不是给所有对白统一加一段延迟，而是先确定丢的是时间还是内容，再判断预热、保留首块是否值得占用内存。

## 资源对象已经加载，不代表声音数据已经备好

流式音频缓存把压缩音频拆成可按需读入的块。Epic 的概览指出，加载 `USoundWave` 对象不保证声音马上可播；缓存压力还可能让预先准备的内容被替换。[1] 因而应分别记录三个事实：资产对象可用、预热已经完成、实际播放时需要的块仍然驻留。前一个不能代填后一个。

**预热（prime）**是提前请求缓存内容，不是提前播放。以 UE 5.1 的加载行为文档为例，Prime on Load 会载入首块，但闲置后仍可能被淘汰；Retain on Load 则在对象生命周期内保留首块，直到对象销毁或显式释放相应数据。配置还存在覆盖顺序：Sound Wave 自身、所属 Sound Class、上级 Sound Class，再到全局设置。[2] 排查时先看真正生效的资产设置，不要只改一个全局值就认定实验条件变了。

这里有两项直接影响选择的限制。首先，保留的是首块，不是整条长对白的全部内容；后续播放仍需要后续数据。其次，数据驻留只减少这一段准备工作，不会把游戏线程、解码、混音及设备输出的等待全部清零。

本文对加载行为采用带版本参数的 UE 5.1 文档，对缓存机制采用访问时标为 UE 5.9 的概览。概览把全局 Prime 与 Retain 都写成数值 2，而 5.1 枚举页分别列为 2 与 1。[1][2] 因此下面用命名选项表达实验，不提供跨版本通用的控制台数值；接入者应以自己的 SDK 和实际资产配置核对。

## 先区别整句迟到和前缀缺失

不要只记“第一声在请求之后多少毫秒”。素材自己可能有静音，包络可能压低开头，采集也可能没从同一个位置开始。需要对照输出中出现的是素材的哪一段。

本文制作了一秒、48 kHz、单声道的原创 PCM WAV：开头放 20 ms 标记，0.20 秒处放另一段不同标记，0.40 秒处放后续测试信号。它不是人声，也没有经过 Unreal。脚本分别在完整素材前添加 120 ms 静音，以及直接删除素材的前 80 ms，再读回 WAV 检查样本。所得位置以各文件起点为零：

| 文件 | 第一个非零样本 | 开头标记 | 0.20 秒标记在输出中的位置 |
| --- | ---: | ---: | ---: |
| 原始参考 | 0 ms | 0 ms | 200 ms |
| 完整素材推迟 | 120 ms | 120 ms | 320 ms |
| 前 80 ms 被删除 | 120 ms | 缺失 | 120 ms |

最后一行的首个非零样本也在 120 ms，是因为原素材两个标记之间有静音。两份异常文件若只按“首次有声”统计，会得到同一个数字，却是不同的内容变化。脚本还确认：去掉延迟文件的新增静音后，剩余样本与原始文件完全相同；删除前缀的文件则只等于原始文件的后缀。

这个对照检验的是诊断方法，不模拟磁盘、缓存或真实吞字。真实输出经过压缩编码、重采样或混音后，不能再要求字节相等。先在独立、无效果的测试路径中，用多个已知标记定位整段的相对偏移，再核对开头是否仍存在；回到人声时结合波形、听音和内容检查。如果开头被掩盖或采集信噪比不足，应记为“无法辨认”，而不是“已经删除”。

## 在打包构建里做四组有区别的检查

先固定目标平台、引擎版本、打包配置、音频编码和采样率。核对目标构建已启用流式音频缓存，且目标资产实际使用这条路径；否则下表不适用。挑一条可以稳定触发的 Sound Wave，禁用随机选句、循环、非零起播位置和人为淡入，采用固定增益的独立输出路径；避免并发限制或虚拟化悄悄改变播放。先用带标记素材检查观察方法，再用真正出问题的对白复验。

UE 5.1 的 AudioMixerLibrary 文档提供 `prime_sound_for_playback(sound_wave, on_load_completion)`；Sound Cue 的对应函数没有这个完成参数。[3] 这里从单一 Sound Wave 开始，是为了避免把“已提交 Cue 的预热”误记成“选中的句子已准备好”。这些是对应蓝图/C++ 接口的资料入口，不要求把 Python 当作游戏运行时。

| 对照组 | 播放前的安排 | 想排除的解释 |
| --- | --- | --- |
| A：按需 | Load on Demand；确认本次首块未驻留，再请求播放 | 记录需要现场取数据的基线 |
| B：预热后立即播 | 预热完成后尽快播放，记录间隔 | 若改善，检查准备工作是否确实移到了请求之前 |
| C：预热后有竞争 | 与 B 相同地预热，再按固定顺序预热或播放其他素材，确认实际发生块请求；等待后再播放目标 | 检查完成过的预热是否仍能覆盖真正使用时刻 |
| D：保留后有竞争 | 目标资产用 Retain on Load，确认首块就绪，保持对象存活，施加同样负载 | 对照目标首块不再被普通淘汰时，结果是否改变 |

这些组是待执行方案，不是本文的引擎测试结果。每次保留配置和负载序列。若要区分等待本身与其他声音的竞争，可补做一组同样时长的无额外负载等待。C、D 使用相同的等待时长和负载安排；不要把 A 的新进程与 B 的旧进程随意混在一起。新进程只说明应用状态重新开始，不代表操作系统文件缓存已冷。能确认的是音频缓存缺块，就报告“音频缓存未命中”；没有磁盘层证据，不称它为物理冷读。

一份记录至少要能串起：本次播放身份、目标资产、有效加载行为、预热请求与完成时间、完成至播放的间隔、播放请求时间、首块驻留或缺块的证据，以及输出中各标记的位置。若工具不能提供可靠驻留信息，就把这一栏留为未知，不能从“播得快”倒推“首块一定在”。

旧版 UE 4.27 概览给出了 `stat audiostreaming`，可查看缓存块、加载时间和解码器使用数量。[4] 它是目标构建可用时的观察入口，不承诺所有新版或 Shipping 构建都有同样界面。普通截图也不是播放瞬间的原子快照；短暂淘汰和重新加载需要结合该版本的跟踪或日志确认。

应用时间和录音采样位置必须分列。若要求“请求到设备输出”的延迟，采集要有能与请求对应的时间基准并说明同步误差；引擎内 submix 录音只覆盖其采集位置之前的链路。没有这样的对齐，仍可比较标记是否完整，却不宜报告精确的端到端毫秒数。

## 哪种结果值得改缓存政策

若 B 比 A 更早开始、内容都完整，并且加载记录显示准备工作移到了播放前，这支持把预热放在可靠的先行事件上，例如玩家接近一段确定会用到的对话。不要在 Play 前一行才发预热就期待异步工作必定完成，也不要为每条声音固定等一个猜出的毫秒数。

若 B 正常，C 再次迟到，同时观察到目标首块被淘汰，而 D 在同样负载下保持首块并改善，就有理由为这组关键对白评估保留策略。代价是占用更多驻留空间，可能挤压其他声音；应记录目标及其余声音的加载情况、缓存占用和播放异常，不能只盯目标一句。对很短且时机严格的声音，还可在目标版本支持时评估整条非流式路径，但要重新核对内存、解码和实际输出，不把它当成免费选项。[2]

如果 D 仍迟到，不要马上把缓存再翻倍。先区分首块是否真的就绪、后续块是否欠载，以及等待是否位于另一段处理链。如果完整对白只是向后平移，继续追查起播链路；如果开头标记缺失或被压低，检查实际起播偏移、素材导入结果、包络和播放政策。观察到缺失也没有自动证明磁盘吞了样本。

对白业务还须决定准备未完成时怎么办：允许延后整句、暂缓配套镜头、改用已准备的短提示，或者按内容规则取消过期对白。选择涉及字幕、口型和剧情时钟，不能让缓存模块悄悄跳过已经过去的词。取消后到达的预热完成通知，也只能结束自己的准备工作，不能把过期对白重新触发。

最后回到代表性场景，用同一份已打包资产重复检查第一次、重复播放、预热后长时间等待和资源竞争。记录每次的等待分布及内容完整性，而不只展示最快的一次。本文给出的 WAV 对照不证明哪种加载策略最快；它让“迟到”和“缺内容”成为不同的验收项，使团队有依据决定改缓存、改接入顺序，还是改对白编排。
