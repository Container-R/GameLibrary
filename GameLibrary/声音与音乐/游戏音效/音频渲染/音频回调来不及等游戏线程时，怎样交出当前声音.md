# 音频回调来不及等游戏线程时，怎样交出当前声音

玩家按住切割器，马达声持续响起；刀头接触材料后，声音随负载加重。玩法程序负责判断接触和目标强度，音频程序把这些变化变成连续的声音。两边合作得好，并不意味着两边必须同时完成每一次更新。

设想一种接法：音频侧需要下一块声音时，先锁住切割器对象，读取最新强度；若对象正在更新，就等待游戏线程。这很直观，却把声音的连续供应绑在了另一条线程的进度上。游戏线程可能正在加载场景，也可能被其他工作占用。音频侧此刻缺的不是“最新值”这个概念，而是能按时交出去的这一块数据。

本文用这个虚构切割器说明一种组织方法：把准备资源、交接控制、生成当前声音和回收资源分开。具体接口以 PortAudio 的回调式输出为例；这不是已经运行过的切割器实现，也不提供可直接复制的并发队列。

## 回调收到的是一块声音的工作，不是一次玩法通知

音频通常以 PCM 样本表示，也就是按时间采样得到的数值。一份**样本帧**包含同一采样时刻各通道的样本；立体声的一帧不是两个连续时刻，而是同一时刻的左、右通道。

**音频渲染回调**是在输出流需要数据时，被调用来处理或生成样本的函数。PortAudio 通过实际的 `frameCount` 告诉它这次要处理多少样本帧；输出格式和通道组织则由打开流时的配置决定。回调需要填满本次输出，即使它准备返回结束状态。[1]

假设某次需要 256 帧，采样率为每秒 48,000 帧，那么这块数据的名义时长是：

$$
256 / 48000\ \text{秒} \approx 5.33\ \text{毫秒}
$$

这不表示操作系统保证给回调独占 5.33 毫秒 CPU，也不表示玩家按键后 5.33 毫秒内一定听见变化。它只是这块音频覆盖的时间长度。实际实现应处理每次收到的帧数，不把示例的 256 写成所有调用都不变的前提。

PortAudio 对这个回调明确限制阻塞和耗时不可预测的工作，包括内存分配、文件访问等；教程也特别提醒互斥等待的风险。[1][2] 即使游戏侧持锁代码很短，音频侧何时能够等到它运行并释放锁，仍不是这段回调自己能决定的。这个依赖已经值得改造，但不能据此断言某台机器必然爆音或死锁。

## 最新控制没到，也要有当前可用的声音

对切割器，可以先把工作分成三处。普通线程准备马达素材、所需存储和控制消息；交接处只发布已经准备好的内容；音频侧维护自己的播放位置和当前强度，用安全可用的数据完成本次样本生成。这里的“自己的”是指更新责任明确，不是把游戏对象原封不动地共享过去。

如果新强度没到，音频侧可以按约定继续现有强度，而不是同步询问游戏线程。若资源根本未准备好，则要提前选择退路：暂不启动马达声、维持已有声音，或者生成静音。若选择淡出，也必须已有能在有限工作内完成的处理路径，不能在回调中临时加载另一份素材。

这些退路都有表现代价。沿用旧强度可能让声音短暂落后于负载；静音可能中断反馈；突然切换还可能产生不自然的接缝。**完成一块数据，不等于这块声音好听。** 音频制作者需要参与决定哪些变化可以延迟，哪些变化必须另行处理。

无论采用哪种退路，都不能把未写的缓冲区域当作静音。静音也要按实际样本格式、通道布局和本次帧数正确填写。本文不假定所有格式都能用相同的字节填充值，也不把“清空内存”当成通用音频处理方案。

## 用队列交接时，先回答“装不下怎么办”

队列让游戏侧提交控制消息，音频侧在适当时机取走；它能解除直接等待，却不会自动替团队决定消息的命运。对切割器而言，“把强度改成 0.6”和“停止这一次马达声”就可能需要不同的处理政策。

下面只做一个未实现的演算：一个生产者提交消息，一个消费者读取；队列初始为空，最多容纳八个固定大小的记录。假定存储已正确准备，容量和记录大小为正，且在使用期间一直有效。消费者尚未取走任何消息时，生产者连续尝试提交九条。若选定的政策是“满了就拒收新消息”，前八条被接收，第九条必须向提交者报告未接收，不能也记作成功。

再假设每块最多处理两条。若第一次实际取走两条，仍有六条积压；若没有新消息且每次都处理两条，原来八条要到第四次处理才全部取完。这个演算没有给出推荐容量，也没有给出准确生效时间：回调的安排、块大小以及控制如何作用于样本仍要另行确定。

因此，“调用了一次入队函数”不是“全部交出去了”。PortAudio 自带的环形缓冲区工具——循环使用固定存储的缓冲结构——也返回实际写入的元素数量，空间不足时不会凭空接收全部请求。[3] 项目必须检查自己的交接接口究竟接收了什么。

对频繁的强度更新，可以考虑在生产侧合并**尚未交接**的旧意图，只保留较新的目标；但这不是让生产者随便覆盖消费者正在读取的槽位。停止、触发和回收消息也不能照搬“丢掉旧强度就好”的规则。比如停止请求被拒收后，系统如何避免马达一直沿用旧状态，必须有明确安排；本文的八槽示例并没有解决所有消息类别。单纯加大队列，也只能推迟持续过载时装满的时刻。

## 少处理几条，还不够让工作有界

“每块最多两条”限制了条数，却没有限制每条做什么。如果一条消息要求加载文件、创建复杂对象，或者一直重试到成功，那么两条仍可能把不确定工作带进回调。

这里需要的**有界工作**，是每次处理的数量和每项处理的工作都受到控制，而不是只给队列贴上“无锁”标签。即使出队操作不等待互斥锁，“一直处理到队列空”为止也可能因为生产者持续提交而扩大工作量。改成忙等同样没有消除依赖，只是换了一种等待方式。

PortAudio 的这个工具本身限定单读者、单写者，并要求调用方预先提供存储；它不是任意多个线程可直接同时使用的通用容器。[3] 这些条件也不能代替项目对并发实现、处理成本和目标平台的检查。本文不实现队列，不把其中某个字段或“无锁”一词当成跨平台实时保证。

## 消息过去了，资源不一定就能释放

切割器控制消息可以很小：目标强度、某次播放的标识，以及已准备素材的标识。但标识不是素材本身，更不是素材永久有效的承诺。若游戏侧发出“改用新素材”后马上释放旧素材，音频侧可能还在用旧数据生成这一块声音。

因此，资源准备、发布、停止使用和实际回收要分别确定责任。普通线程应在音频侧不再借用旧数据之后再回收，而不是把“替换消息已经入队”当作这个依据。也不要因为使用了共享所有权，就让最后一次释放恰好在回调里触发沉重的析构工作。

音频侧若需要告诉普通线程“旧素材已经不用了”，这条反向通知也有容量和迟到问题。不能一边说渲染不等待，一边为了等回收确认而停住它。保留待回收资源需要空间；长期收不到通知时如何处理、关闭声音系统时如何结束借用，也需要设计。这里给出的是必须落实的责任，不是一套已经验证安全的回收协议。

## 排查时，把四个时刻分开

切割器声音没有及时变强时，先不要只问“消息发了吗”。沿着同一条请求看四件事，通常更容易定位问题：

1. **交接是否接收。** 队满拒收与成功接收不是同一种结果。
2. **音频侧是否消费。** 已接收但还在积压，不能记成已经应用。
3. **控制是否进入某块样本。** 消费消息后，应用还可能安排平滑变化或其他处理；记录消费本身并不证明样本已经改变。
4. **相应声音是否输出。** 写好缓冲之后还有输出路径；生成完成不等于玩家已经听见。

这些观察应通过不会阻塞回调的诊断路径取得，而不是在回调内临时写文件日志。诊断记录自身也有满载政策；一个平均耗时数字不能保证以后每块都及时。PortAudio 的输出欠载标志可作线索，但它不是“游戏线程锁导致故障”的唯一诊断。[1]

INSIDE 团队在2016年的讲义中报告过一个具体例子：场景换载期间，他们暂缓调用 Wwise 的更新接口，积累命令，开始淡入后、淡入完成前再恢复处理。讲义随后讨论较大命令队列下的音频瑕疵，并说明曾通过输出录音发现短暂的零值样本段，而 Wwise profiler 没有报错。[5] 这是该项目的历史报告，不是本文运行得到的结果；暂缓更新调用也不能理解为暂停音频线程。它与前面的 PortAudio 填充样本回调不是同一种接口。

这个例子提醒我们：诊断工具没有记录错误，与输出内容符合预期，是两个判断。项目若怀疑声音被意外截断，可以把获准采集的输出片段与当时的控制过程一起核对；但零值段本身仍可能是内容设计，不能一见静音就认定故障。该团队在讲义中记录了缓冲调整，也不能据此给所有项目开出“把缓冲调大”的通用处方。

若比较游戏请求与音频输出的时间，还要确认两者使用的时钟如何对应。接口里的回调调用时刻与首样本输出时刻也不是同一个量；不能拿游戏日志时间直接减一个音频流时间，就宣布得到玩家听见变化的延迟。[1]

## 不要把所有叫 callback 的接口混在一起

如果项目使用 FMOD Studio，高层事件通知并不要求调用者每次填写一块 PCM。FMOD 2.04 的 Studio 指南分别讨论命令处理和事件回调；这里说的 PortAudio 样本回调是另一种职责。[4] 不应把本文当成要求普通 Studio 使用者自行接管混音线程的教程，也不应把一个 API 的调用限制机械套到所有中间件通知上。

真正可以迁移的是工作划分：普通线程准备，交接层如实报告接收，渲染侧不依赖普通线程此刻赶来救场，回收侧等到借用结束。至于实际采用哪种接口、如何同步和如何测量，仍要回到项目使用的版本及平台。

切割器例子最终需要检查的，不是“有没有使用无锁队列”，而是新数据迟到、消息装满、旧资源仍在使用时，当前声音是否仍有明确的完成办法，以及为此接受了什么表现代价。本文没有运行音频流或进行听测，不能据此承诺达到某个截止时间、延迟上限或无爆音。
