# 音源经过门框时，遮挡音量为什么会啪一声

墙后的机器声一直在播。人走过门边，声音本来只该变闷、变轻，却多出一个很短的“啪”；贴着门框走时，又会反复忽响忽轻。这两种现象可能同时出现，却要分别处理：**一次目标增益跳变可以制造波形接缝，检测结果反复换边则会让增益一直追着新目标走。**

这里固定一个持续音源，只讨论用于模拟遮挡的衰减，不把门后的低通、传播路径和混响一起改。这样能用同一段输入定位是谁制造了异常：素材、检测、控制值，还是音频输出中的增益过渡。

## 先看增益变化发生在第几个样本

设输入样本为 x[n]，应用到它的线性增益为 g[n]，输出就是 y[n] = x[n] × g[n]。若 g 从 1 一步跳到 0.2，而切换处输入约为 0.5，仅增益变化就会带来约 −0.4 的幅度变化；它跟是否达到 0 dBFS 是两回事。反过来，恰好切在接近零的样本，断点可能很小，不能只拿一处零交叉宣布修复。真实音色、切换所在相位和混音背景都影响听感。[1]

先把实际游戏里**遮挡检测的原值、决定的目标增益、音频端应用变化的时刻**分别记下。保留同一素材和播放点，录下增益处理前后、限幅器之前的波形。然后不改播放，只把遮挡目标钉死：如果“啪”还在，先查源素材、循环接缝或其他处理；如果只有目标切换才出现，就在同样的切换时刻比较阶跃和样本之间连续的过渡。只在游戏 Update 里让数值缓慢变化，但把每次更新作为一个瞬时阶跃发给音频端，仍可能产生较小而重复的跳变。

## 反向时，从当下的增益继续

音频端收到新目标后，可用短斜坡，或让增益逐样本趋近目标。举例，用一阶指数，当前目标是 T，转向的起点是 g₀，经过 t 秒后的增益可写成 `T + (g₀ − T) × exp(−t/τ)`。τ 是时间常数，不是结束时间：经过 1τ，走过变化量的约 63%；3τ 约 95%。如果项目要在指定时限精确到达，就使用有确定终点的斜坡，或定义容许误差。比较参数时先确认两边都在说线性增益，或都在说分贝；两者使用同一个数值曲线并不等价。[1]

用 FFmpeg 7.1.5 的信号表达式离线生成同一段 48 kHz、1 kHz 载波，峰值 0.5。第一次在 25 ms 从 1 转向 0.2，指数的 τ 为 5 ms；反向的试次在 30 ms 转回 1。两个时刻都选在载波正峰，便于直接比较浮点样本。下表的“跳幅”是事件样本与前一个样本的绝对差，包含正常波形运动；恒定增益作为参照。[2]

| 增益处理 | 25 ms 跳幅 | 30 ms 实际增益 | 30 ms 跳幅 |
| --- | ---: | ---: | ---: |
| 恒定 1 | 0.004278 | 1.000000 | 0.004278 |
| 一步到 0.2 | 0.395722 | 0.200000 | 0.000856 |
| 平滑到 0.2，保持目标 | 0.004278 | 0.494304 | 0.001505 |
| 从当前增益平滑转回 1 | 0.004278 | 0.494304 | 0.001505 |
| 反向时先硬设为旧目标 0.2，再平滑到 1 | 0.004278 | 0.200000 | 0.145647 |

最后一行说明：两边都配了平滑仍可能响，问题是**取消旧过渡时丢了实际增益**。30 ms 时本来才降到约 0.494，却先被硬设为 0.2，等于又切了一刀。音频端应知道上一段曲线运行到事件时刻的值，以它为新起点，不从游戏线程记着的上个目标重开。若 API 一次安排多段自动化，还要取消会覆盖未来的旧段，并保留取消点的曲线值。Web Audio 1.0 的 GainNode、setTargetAtTime 与 cancelAndHoldAtTime 可作为查阅例子；上述数据来自 FFmpeg 计算和回读，未用浏览器或游戏中间件验证。[1][2]

## 门缝来回抖，要修的是发目标的规则

平滑不能决定哪边才是正确的遮挡。若每次射线扫过门角就给一个新目标，延长平滑只会在响应灵敏与持续起伏间换来另一种折中。先看遮挡原值是否在边界反复波动。如果检测返回多条探测线中被挡比例一类的连续量，一种做法是用不同的进入和退出阈值：例如达到 0.60 才进入遮挡，降到 0.40 或以下才退出，夹在中间就保留原状态。在附录的十项序列中，单阈值 0.50 会切换 6 次，这组双阈值只切换 2 次。它只说明这组数据的判定差异，不表示两个数值适合所有关卡。若项目只有一条线的二值结果，两个数值阈值不会挡住 0 与 1 的交替，可用时间确认或多点检测，但要复查短暂遮挡是否被漏掉。

交付前至少录三段：远离门框的单次经过、贴边的反复经过、刚开始过渡又反向。量检测切换次数、增益实际响应时间和事件前后波形，最后在原有总线与真实音色下听一次。想让遮挡成立时来得快、解除时慢一点，可以分别配置两个方向的时限；若角色离开很久才恢复清晰，检查检测等待和音频平滑是否把延迟叠加了。先减掉不必要的切换，再把留下的切换做连续，两个环节分别验收。
