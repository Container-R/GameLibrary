# 如何标记和检查PCM音乐循环区间

一段音乐在制作软件中可以反复播放，交进游戏后却在接缝处听起来不对，或者重复几次后与预期节拍错位。接手的人看到“循环结束：94138”，但不知道它指的是最后一个要播放的位置，还是第一个不要播放的位置；也不知道它对应原文件，还是已经裁剪过的新文件。

这时先不要急着重做混音。值得先排查的是：两边是否在谈同一段数据。本文面向音乐制作、音频设计和音频程序人员，解释怎样用明确的帧区间交付循环主体，再核对工具实际取出了什么。它能帮助排除少一帧、混入留量、坐标起点不一致等错误，不能单凭数字正确就证明循环听起来无缝。

## 先弄清“一帧声音”有多长

PCM 是把声音在离散时刻的幅度记录成数值的表示方式。**采样率**说明每秒有多少个这样的采样时刻；48,000 Hz，也常写作48 kHz，表示每秒48,000个。

双声道在每个时刻分别记录左、右声道的值。我们把同一时刻的一组声道值叫作一个**样本帧**，下文简称帧。它不是视频帧，也不是压缩编码中的音频包。一个双声道帧包含两个声道样本，但仍只占一个采样时刻的时长。

本例采用48 kHz、双声道、每个声道样本16位的PCM。16位等于2字节，因此：

> 一帧 = 左声道2字节 + 右声道2字节 = 4字节PCM数据

48,000帧的时长是一秒，而不是因为有左右声道就变成两秒。若用 `N` 表示帧数，时长就是 `N÷48000` 秒；PCM数据量则是 `N×4` 字节。换成别的采样率、声道数或位深，必须重新计算。FMOD文档对PCM时间单位和PCM字节单位也作了这种区分。[1]

这些字节只指音频数据，不含WAV文件的头部和其他描述信息。WAV是装载音频数据及相关信息的文件容器；不能一律用整文件大小除以4来推断帧数，也不能仅凭扩展名就认定内部一定是本例的PCM格式。

## 结束位置究竟包不包含在循环里

先用一个很短的例子。把帧从0开始编号，想要第2、3、4帧，可以记为 `[2,5)`。左边的方括号表示包含2，右边的圆括号表示不包含5。这样的写法叫**半开区间**。

它有两个方便之处：长度直接是 `5−2=3` 帧；下一段可以从5开始，不会和前一段重复。本文统一用它描述素材意图：

> `[begin, end)` 包含begin，结束于end之前；长度为end−begin。

但这不是说所有工具都采用同一种端点。某个接口如果要求“最后一个要播放的帧”，上面就应填写4，而不是5。先确定单位、编号从哪里开始、终点是否包含，再换算；不要只把“结束”后面的整数复制过去。

## 一小节音乐不一定恰好对应整数帧

现在回到一份实际可交接的素材描述：48 kHz，123 BPM，4/4拍，一小节主体。这里明确BPM以四分音符为一拍；4/4的一小节有四拍。每分钟123拍，所以一拍长 `60÷123` 秒，一小节的理想帧数为：

> 48000 × 60 ÷ 123 × 4 ≈ 93658.536585帧

PCM区间只能选完整帧，不能保留半个左右声道帧。本例选择“取最近整数，恰好半帧时向上”的交付政策，于是主体定为 **93,659帧**。这是一项明确的项目选择，不是所有音乐软件的默认规则。

所选周期比理想数学周期长 `19/41` 帧，约9.65微秒。如果单纯把这个整数周期重复，与理想周期的算术差额会累积；这不等于已经测出某个中间件的实际漂移，因为运行时可能另有调度、重采样或变速安排。需要长时间同步时，应一起确认素材周期与音乐网格的关系，而不是把取整过程藏起来。

拍速标记也不能替代这个检查。例如FMOD Studio的Tempo Marker用于定义拍速和拍号，服务于拍、小节量化；设置了标记，并不证明输入音频的主体帧数已符合你的意图。[2] 本例不处理变速曲线或其他拍单位。

## 把主体与前后留量分别标出来

假设这份源文件在主体前留了480帧，主体后另留2,400帧。仍从源文件第一帧0开始编号：

| 区域 | 源PCM中的帧区间 | 长度 |
|---|---|---:|
| 前置留量 | `[0,480)` | 480帧 |
| 循环主体 | `[480,94139)` | 93,659帧 |
| 尾部留量 | `[94139,96539)` | 2,400帧 |

主体的最后一个帧编号是94138，94139已经属于尾部。整个文件有96,539帧，但循环周期只有93,659帧；两者并不矛盾。按本例格式，主体PCM数据应有 `93659×4=374636` 字节。

“留量”这里只表示主体之外的数据，不预设它一定是静音或混响。真实音乐的尾音是否继续播放、怎样与下一次或下一段重叠，是音频设计的另一个决定。不能因为文件还有尾部，就默认每次循环都应把它算进周期，也不能不问创作意图便直接删掉。

还有一个容易漏掉的变化：**裁出主体后，新文件的帧号重新从0开始。** 源文件中的 `[480,94139)`，在只含主体的新文件中对应 `[0,93659)`。长度相同，不代表起止数字还能照抄。交接单必须说明区间属于哪一份文件。

## 到具体工具时，再转换一次端点

通用标记与工具参数应分开保存。下面两个接口正好说明为什么不能只写一个“结束帧”。

FFmpeg的 `atrim` 是音频裁剪过滤器。固定版本文档规定，`start_sample` 是首个输出位置，`end_sample` 是首个丢弃位置；这组参数按通过过滤器的样本计数，而不是用输入时间戳定位。`atrim` 本身不修改时间戳，若希望输出从零时间开始，需另做时间戳调整。[3]

FMOD Core 2.04的 `Sound::setLoopPoints` 则把开始和结束位置都包含在循环内。在PCM单位下，源文件主体的结束参数应是94138。该接口还要求结束大于开始、端点处于声音范围内，并使用适当循环模式；已缓冲流另有注意事项。[4] 本文只解释文档映射，没有运行FMOD，也不能把Core接口的约定直接套到Studio时间线区域。

| 使用对象与约定 | 开始 | 结束 |
|---|---:|---:|
| 源文件，本文半开标记 | 480 | 94139，不包含 |
| 源文件，FFmpeg上述计数裁剪 | 480 | 94139，首个丢弃位置 |
| 源文件，FMOD Core PCM循环端点 | 480 | 94138，包含 |
| 裁好的主体文件，本文半开标记 | 0 | 93659，不包含 |
| 裁好的主体文件，FMOD Core PCM循环端点 | 0 | 93658，包含 |

对于本例这样的有效非空区间，“包含式末帧 = 半开终点−1”成立。但还须满足目标接口自己的长度与模式要求，不能把这个换算当作所有API都适用的通行证。

## 先检查取对了数据，再检查声音是否接得上

旧研究用过一份专为检查边界构造的数值PCM，而不是真实音乐：主体首尾放入容易识别的左右声道数值，普通主体帧与前后留量也不同。这样，少取一帧不必靠听觉猜测，就能在结果里定位。

该离线检查用 `[480,94139)` 得到93,659帧；误把包含式末帧94138当作裁剪的排除终点，则得到93,658帧，并丢失约定的主体末帧。两个结果都能被工具处理，问题不是文件打不开，而是裁剪意图没有被准确表达。

这说明**工具成功处理与取对区间是两回事**。它没有说明少一帧一定可听见，更没有测量咔哒声的感知阈值。本次改写没有重新裁剪、解码或播放。

接手真实素材时，可以按以下顺序检查，而不是从文件显示的近似秒数开始：

1. 确认收到的文件版本和实际数据格式，区分源文件与裁后文件。
2. 核对主体起点、排除式终点和相减后的帧数，检查是否都落在有效范围内。
3. 核对提取后的帧数，并检查首尾附近是否确实来自约定位置。数值标记适合测试素材；真实音乐应核对实际内容，不能擅自加入测试标记。
4. 在目标工程中检查循环入口、返回位置、尾部处理及多次重复，再由音频人员试听接缝和节奏。

最后一步不能被前面的算术替代。听到接缝问题时，端点是排查方向之一，不是唯一原因；也不能仅凭首尾某两个数值相同就宣布音乐自然连续。若要采用淡化或交叉混合，应把它视作会改变素材表现的设计处理，而不是用来掩盖不清楚的循环区间。

## 一份简短而不含糊的交接说明

作曲或音频设计可以先用普通语言写清楚：这是哪个段落、哪一版文件，以什么拍单位计速，哪一拍开始，主体有几小节；前后留量分别用于什么。再附源PCM格式和整数帧区间，把本例的取整选择明确写出来。

音频程序接收时，不只是看见“123 BPM”就完成导入，而是确认区间对应当前资源，按目标接口转换单位和端点。转换后若又裁剪、重采样或编码，原来的数字不能未经核对便继续沿用。检查结果应分别记录“数据范围已核对”和“目标工程播放已检查”，不要把前者代替后者。

若交付多个可以叠加的分轨，常称为 **stem**，还要确认它们的音乐起点与主体范围是否对齐。两个文件时长近似相等，不代表其中的节拍入口相同；帧数完全相同，也不说明叠加效果已经试听通过。

对这类素材而言，重要的不是交接表字段有多少，而是下一位接手者无需猜测：应该循环哪一段，单位是什么，在哪份数据中数，以及哪些检查仍然没有做。

## 编码与播放是后续问题，不在本篇混成一个结论

本文讲的是PCM区间。发行时若使用压缩编码，编码包累计时长、容器记录的位置与最终解码得到的PCM长度，不能不加区分地当作同一个终点。

旧文另有固定Ogg Opus文件的完整编码/解码观察；它与前面的测试主体长度相同，但内容不同，并不是同一份音乐经过所有工具仍保持字节不变。该专题涉及起始跳过、尾部裁剪和包时长，详细计数与适用限制保留在旧资料的[编码计数支持章节](../../../../solutions/music/pcm-loop-frame-contract.md#7-编码补充呈现帧数最终-granule-与包时长不是同一数字)。已有完整解码观察也不等于任意位置启动或循环重入已无缝。

因此，本篇能提供的是清楚的PCM单位、区间和检查顺序。它不承诺压缩格式兼容性、设备输出延迟、无限循环的时钟同步，也不代替音乐创作和目标播放环境的听感判断。
