# Steam Input 重绑后，为什么按键提示还在显示旧按钮

玩家打开菜单，把“确认”换到另一个按钮。新按钮已经能操作菜单，屏幕下方却仍显示旧提示。此时重画图标通常不是第一步：图片可能没有画错，错的是界面一直拿着进入菜单时的绑定结果。

本文面向已通过 Steam Input 动作 API 接入 Native 模式的界面与输入程序员，以一个虚构菜单为例，说明如何让提示跟随动作的当前绑定；不把它当作只接收仿真键鼠等低层输入的 Legacy 模式教程。[4]例子和伪代码没有在 Steam 客户端、SDK 或手柄上运行，不是可以直接复制的完整接入实现。

## “确认”、绑定来源和按钮图不是同一件事

“确认”是游戏动作：接受当前选择。它的含义不应该因为玩家改了键位，就变成“按 A”。玩家用哪个物理输入触发它，是另一层；界面如何画出那个输入，则是第三层。

可以先把接入关系写成：

```text
菜单确认动作 → 这位玩家设备上当前绑定的来源 → 对应的提示字形
```

Steam Input 的 `GetDigitalActionOrigins` 接受控制器、动作集和数字动作句柄，返回来源数量，并将来源写入调用者提供的数组。模拟动作有对应的 `GetAnalogActionOrigins`。得到来源后，`GetGlyphPNGForActionOrigin` 或 `GetGlyphSVGForActionOrigin` 才负责提供相应图片的本地路径；把图片载入游戏并显示，仍是游戏的工作。[1]

因此，“确认”的文字和按钮图可以有不同的生命周期。文字表达稳定的操作含义；按钮图依据当前来源。若把两者一起做成永不更新的“按 A 确认”贴图，重绑后就很难只更新变化的那一层。

## 先确定在问谁、问哪个菜单动作

同一台电脑可以连接多个设备；同一控制器在菜单、步行、驾驶时，也可能使用不同动作集。只知道“这是某品牌手柄”，不足以知道菜单确认映射到了哪里。

本例约定：调用方已经完成 Steam Input 初始化和所需的帧更新，已选定这位玩家使用的控制器，菜单动作集已经启用，查询的动作确实属于它。为了只讨论提示更新，**本例没有启用 Action Set Layers**。这些前提不是下面几行伪代码自动保证的。

实际项目若有层，还须核对自己的上下文管理。Valve 的层文档说明，层可以修改基础绑定，并受叠加顺序影响。[3] 因而“设备没换”不代表绑定语境没变；但本文不提供多层冲突解析算法，也不推测应把某个层句柄传入查询就一定得到所有最终绑定。

## 先看返回数量，再决定怎样显示

同一个动作不必只有一个来源。Valve 的接入指南明确讨论了多来源提示，并建议轮换显示。[2] 对本菜单而言，团队也可以选择能容纳多个替代提示的布局；这是呈现决定，不是接口返回的按键执行顺序。

下面是原创流程示意。`origins` 的容量须按 API 的 `STEAM_INPUT_MAX_ORIGINS` 准备；素材加载、错误处理和多提示布局只是项目函数，不是额外的 Steam API：

```text
每帧，当菜单提示需要显示时：
    n = GetDigitalActionOrigins(选定设备, 当前菜单集, 确认动作, origins)
    若 n < 0 或 n > STEAM_INPUT_MAX_ORIGINS：停止使用这次结果，记录接入异常
    否则若 n == 0：显示项目约定的“当前无可用按键提示”表现
    否则：
        仅处理 origins[0 ... n-1]
        为各来源取得或复用对应提示资源
        按约定布局展示“确认”及这些替代来源
```

这里的零不能自行翻译成“手柄断了”或“玩家忘了绑定”。所读 Origins 条款没有列出完整的零返回原因；也不能拿动作数据的 `bActive` 说明，替代这个查询的失败诊断。没有取得来源时继续显示上次的按钮，会把未知状态伪装成确定指令。

同样，多项来源不能直接画成“先按第一项再按第二项”，也不能默认是必须同时按的组合。本文处理的是可返回多个来源这一事实，不实现所有激活器、组合键或配置语义的解释器。具体配置需要更丰富提示时，应另核接口和项目行为。

## 更新绑定结果，不等于每帧重新加载图片

玩家可能在提示出现后打开配置界面并修改绑定。Valve 的开发指南因此建议，在屏幕上显示提示期间每帧重新取得 origins，而不是一直显示第一次查询的结果。[2]

设旧查询返回来源 P，重绑后的新查询返回 Q。这是纸面场景，不是实际客户端记录。如果界面仍显示 P，先检查是不是缓存了“确认→P”，而不只是检查 Q 的图片有没有导入。

图像资源缓存则是另一回事：同一个来源、尺寸和样式对应的已加载资源，可以按项目的资源管理策略复用。重新查询绑定，并不要求每帧读文件、解码 PNG 或重新创建纹理。更新提示列表与管理资源的拥有、加载失败和释放，应分开安排；异步加载时也要避免旧请求完成后覆盖新的提示选择。

若用自带图集，还要注意来源枚举可能随 Steam 客户端支持的新设备扩展，超出编译时头文件或数组的范围。[1] 先做边界检查；没有自带素材时，可考虑 API 提供的字形资源，并为实际加载失败保留清楚的缺省表现。这里不保证所有未来设备永远免维护，也没有验证图片在项目尺寸和背景下的可读性。

## 换一套设备图标，不等于查到了重绑结果

`GetActionOriginFromXboxOrigin` 看起来也能返回一个可用于显示字形的来源，但它回答的是另一个问题。官方说明明确指出，这个接口直接翻译按钮，不考虑用户配置中的重映射。[1]

如果游戏始终从固定 Xbox 按钮出发，只把它翻译成另一款设备的图标，可能解决“图标风格不像当前手柄”，却没有回答“确认动作现在绑定了什么”。原生动作接入应从动作及其查询语境出发；不能因为最终都得到一个 origin，就把两条链当成等价。

## 用一个菜单检查整条链

交付前可以围绕确认动作安排少量项目检查，而不是只看默认配置下的一张截图：同设备重绑后返回菜单，提示是否跟随新查询；有多个来源时，是否明确表示替代选择；没有可用来源时，是否停止冒用旧图；切换玩家设备或动作集时，查询对象是否仍对应当前菜单。

这些检查尚未在本文执行。真正核对时，分别记录动作语义、选定设备与动作集、当前返回来源和最终显示，再确认操作接入。提示换了一张图，不证明确认事件一定进入了正确控件；按钮能触发，也不证明提示说明了正确的来源。

本题与按钮是否禁用、焦点在哪不同。后者见[《用图形表现按钮和界面的状态》](../../../界面与体验/界面美术/状态表达/用图形表现按钮和界面的状态.md)。两条链都需要正确：一条告诉玩家“现在可以做什么”，另一条告诉玩家“在当前配置下，用什么操作”。
