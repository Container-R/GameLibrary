# Steam DLC下载进度查不到，为什么不能直接进入新关卡

游戏增加了一章可选下载的剧情。玩家点下“下载章节”，进度条出现了一会儿，下一次查询返回了false。程序把它理解成“已经不需要下载”，关闭提示并切换场景，结果新关卡加载失败。

这里混淆了两个问题：**现在能否取得下载进度，以及这个章节是否已经可以进入。** 本文面向接入Steam可选DLC的程序员，用一个原创章节选择例子说明怎样分开处理它们。DLC指附加内容；以下讨论有独立下载内容的可选章节，不是购买流程或服务端发奖方案。

## 进度查询的false，不是安装完成事件

Valve的接口文档规定，`GetDlcDownloadProgress` 在指定DLC存在且当前正在下载时返回true，并提供已下载和总字节数；否则返回false。[1] 因而它不是一个“是否下载失败”的查询，也没有把false定义成“已经安装”。

从逻辑上看，“存在并且正在下载”的否定，不能自动变成“下载成功”。若把进度查询结果直接反转为可进入标志，就把没有取得进度的各种情况合成了成功分支。这个错误即使没有网络波动也成立，不需要先猜测某次false究竟由什么引起。

安装判断有另外的入口：`BIsDlcInstalled` 的true表示当前用户拥有该DLC且它已安装。[1] 反过来的false仍不能单独说明“用户没有买”，因为它也没有把所有未满足条件的原因分别返回。不要据此立即把按钮改成“购买”。

## 先安排一条能恢复的章节加载路线

Steam允许把DLC配置为不自动下载，由游戏按需触发安装；玩家也可能在Steam客户端手动安装它。[2] 因此，进入章节菜单时不能只等待“本次点击下载”之后的事件。玩家可能早就装好了这一章。

假设项目中的章节A对应一个明确的DLC App ID。App ID是Steam识别这份内容的编号；它不是章节列表里的第几行。我们为这个例子设计以下流程，不声称这是Steam内部状态机：

1. **菜单打开或重新检查章节时，先查询安装条件。** 若 `BIsDlcInstalled(A)` 为true，就进入游戏自己的内容加载检查。若为false，保留“当前尚不可进入”，不要擅自解释成购买失败或下载失败。
2. **在项目已经确认可请求安装、且玩家选择下载后，调用 `InstallDLC(A)`。** 它返回void，不提供一个同步的成功布尔值。[1] 在本例里，调用结束只记作“已发出请求”，不马上切换关卡。
3. **等待期间，把进度当作显示信息。** 查询成功时显示字节进度；查询false时停止使用这次未取得的数值，改为不带百分比的状态说明，并重新检查安装条件。不要继续展示上一轮100%的旧数值，也不要仅凭false宣告完成。
4. **收到 `DlcInstalled_t` 时，先核对它携带的 `m_nAppID`。** 文档将此事件定义在用户拥有且DLC已安装之后。[1] 若事件对应A，就重新检查A；仅当安装条件仍为true，且玩家仍在请求进入A时，才进入同一条游戏侧加载检查路径。若对应章节B，不能因此放行A。

示例假设项目已经正常接入Steam回调处理。启动时的主动查询与后续事件都通向同一条内容检查路径。项目应保证重复检查不会重复启动同一场景，例如在A已经加载中时仅刷新状态，而不再次发出进入请求。这是游戏侧需要实现的去重规则，不是本文已经验证过的SDK行为。

## 四组输入如何导致不同决定

下面是用于审查调用方逻辑的四组彼此独立的假设观察，不是一次Steam下载日志。各行不承诺按此顺序出现，也不穷举所有组合。`P`表示进度查询是否成功，`I`表示A的拥有且安装检查，`L`表示本游戏的章节资源是否已成功加载。

| 观察 | P | I | L | 本例允许的处理 |
|---|---|---|---|---|
| 刚打开菜单，尚未取得可用安装条件 | false | false | false | 不显示已完成，不进入A |
| 正在取得下载进度 | true | false | false | 显示进度，仍不进入A |
| 安装条件已经满足，章节尚未载入 | false | true | false | 开始游戏侧加载，保留加载提示 |
| 游戏侧加载成功 | 不参与本次判断 | true | true | 可以完成本例的进入流程 |

关键反例在第一行与第三行：两行的P都是false，但处理完全不同。只保存P的程序已经丢掉了做决定所需的信息。第三行与第四行又说明，平台安装完成和引擎完成场景加载是不同步骤。

这里的L由项目自己定义，例如章节清单能读取，引用的场景能加载，并且加载器给出了成功结果。本文没有规定所有引擎都使用相同的资源检查，也不假定安装检查能证明任意文件完好、内容版本兼容或联网会话已经接纳玩家。若加载失败，应留下章节和资源错误，返回可恢复界面，而不是把一次安装成功改写成一次场景加载成功。

## 排查时，别把另一个“可用”也接进来

`BGetDLCDataByIndex` 的 `pbAvailable` 描述的是DLC在Steam商店中的可用性，不是当前玩家的安装状态。[1] 枚举到条目、获得标题和看到商店入口，适合用来组织菜单信息；它们不能代替上面的I。

实际调试可把章节编号、对应App ID、安装判断、进度查询结果与游戏侧加载结果分开记录。先检查“哪个观察使程序允许进入”，再追查这个观察是否真的支持那一步。这样能直接区分错误的条件反转、其他DLC的事件误匹配，以及安装后的资源加载失败。

这套检查建议尚未执行。正式接入还需在获准的测试账号与构建中检查启动前已安装、客户端手动安装、不同章节的事件以及加载失败后的恢复；不要假设本文的四行涵盖Steam所有离线、更新或授权变化。尤其不要把客户端的 `BIsDlcInstalled` 当成授予游戏内物品的依据，Valve明确限制了这一用途。[1]
