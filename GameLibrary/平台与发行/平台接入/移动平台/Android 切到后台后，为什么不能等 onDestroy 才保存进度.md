# Android 切到后台后，为什么不能等 onDestroy 才保存进度

一款单机闯关游戏刚保存了检查点 42。玩家继续进入下一关，拿到钥匙，又完成了一段任务；这些变化组成了准备保存的状态 43。此时玩家切去回复消息，游戏在离开前台时把 43 放进普通的进程内工作队列，计划最后在 `onDestroy` 中再检查一次是否保存成功。

问题在于，这个“最后一次”可能根本不会发生。Android 可以回收后台应用的整个进程，而不调用 `onDestroy`；从 Android 13 起，缓存进程还可能得到很少的执行时间，甚至暂时得不到执行时间。[1] 队列里留着一项工作，并不能让它脱离进程继续完成。

本文面向负责 Android 平台接入与游戏存档的程序员，讨论怎样把生命周期通知接到已有的保存系统。42、43 是贯穿全文的原创例子，不是事故记录或 Android API。这里假设游戏已有可用的持久存储层；“提交完成”按该层的接口契约解释，不额外承诺设备断电时的结果，也不提供 Unity、Godot 或原生引擎的完整接入代码。

## 先分清：界面重建了，还是整个进程不在了

Activity 是 Android 中承载界面的组件，不等于游戏进程本身。理解恢复问题时，至少要区分三种情况。

第一种是玩家短暂离开后返回，原进程和相关对象仍然存在。这时游戏可能沿用仍有效的内存状态。看起来“后台回来没有丢进度”，不代表存档真的写过一次；它可能只是从来没有丢掉那份内存。

第二种是 Activity 被重建。配置变化默认可能导致这种情况，例如设备旋转；应用也可以声明自行处理某些变化。[2][4] 旧界面实例结束，新实例重新出现，并不要求整个进程已经死亡。使用 Android `ViewModel` 的界面，可以借它保留配置变化期间的数据，但它本身不能跨越系统发起的进程死亡。[3]

第三种才是整个进程被回收。进程里的游戏对象、普通工作线程和等待中的任务都不能再被当作恢复依据。系统有时会保留供界面重建使用的状态，但那不是游戏自行保存的全部内存，更不是一次永久存档。[1][3]

因此，旋转屏幕后能继续玩，只检验了其中一条路线。即使这条路线确实调用了 `onDestroy`，也不能据此推断后台回收同样会给它一次收尾机会。`onDestroy` 适合在收到通知时释放相应资源，不适合作为所有重要进度的唯一保存入口。

## 恢复到同一个面板，与保住游戏进度是两项工作

假设玩家离开时打开的是背包，并选中了刚取得的钥匙。重新进入后恢复到同一个面板很有用，但“显示哪一页”与“钥匙是否已经成为永久进度”需要不同的依据。

可以把少量界面恢复材料设计成：

```text
存档槽标识
当前面板
选中物品的稳定标识
```

这些字段帮助新界面找到该显示的内容。真正的检查点则保存游戏约定要保留的关卡、库存和任务结果。恢复材料没有替持久存储完成这份工作；把某个钥匙编号写进它，也不能证明钥匙对应的任务变化已经一起提交。

Android 的 saved state 机制适合小量、可序列化的暂时状态。它可以帮助处理系统重建，但不替代长期存储；`ViewModel` 也不是长期存储。[3] 在传统 Activity 中，`onSaveInstanceState` 是提供这些材料的入口之一。它不是每次离开界面都会调用，明确结束 Activity 的路径也可能没有它。[4]

这里还容易出现一个时序误会：`onSaveInstanceState` 若被调用，对目标 SDK 从 Android P/API 28 起的应用，它位于 `onStop` 之后；对更早目标则位于 `onStop` 之前，与 `onPause` 的先后没有统一保证。[4] 这是目标版本条件，不能仅看测试手机的系统版本，也不能写出一条适用于所有目标版本的“先完整存档，再让系统保存界面”假想流程。

界面恢复材料最好能够失效而不伤及存档。重新读取检查点后，发现选中的物品已经不存在，就回到一个合理的默认选择；没有恢复材料，也仍然可以从持久存档进入游戏。不要反过来用一份旧面板状态覆盖较新的进度，更不要把空的状态参数解释成“应当新建并覆盖默认存档”。这些是本例的应用设计选择，不是 Android 自动提供的合并规则。

## 检查点应在游戏仍正常运行时推进

把保存从 `onDestroy` 移到 `onStop`，通常仍不够。真正需要改变的是：重要进度不再长期堆在内存里，等平台宣布离开时才第一次准备写出。

当前 Android 生命周期指南建议，在前台寻找合适时机保存持久数据；找不到更合适时机时，才在 `onStop` 处理。它同时明确指出，`onPause` 很短，不应在这里安排保存、网络调用或数据库事务等工作。[2] 这并不要求把所有 I/O 堵在主线程，也没有承诺从 `onStop` 启动的任意异步操作都能做完。

回到检查点 42。它代表游戏已经接受并提交的一组进度。进入下一关后，项目应先决定哪些时刻形成新的检查点：完成一段任务、通过安全区域，还是玩家主动保存。选择取决于玩法允许丢失多少尚未提交的过程，不能由 Android 替游戏决定。

形成状态 43 时，应由真正拥有游戏状态的代码，在明确的安全点整理保存输入。钥匙和关联任务标记应当来自同一个被游戏接受的状态，不能一边读库存、一边让任务系统继续修改，再把两次读取拼成一份看似完整的存档。

之后，把这份独立输入交给已有保存入口；保存方使用期间，不再改写这份输入。保存可以异步执行，但需要持续区分“已经提出请求”和“存储层已经完成”。如果玩家此时又产生了新的修改，43 的完成也不能把后来那些修改一并标成已保存。应用需要知道一次完成对应哪个槽、哪份输入，而不是只维护一个由所有任务随意清除的布尔标记。

离开前台的通知可以促使系统处理尚未保存的变化，但它是补充机会，不是无条件的最后保障。也不应为等候完整世界序列化而无限阻塞生命周期回调。如果产品要求某次奖励在向玩家宣布完成后绝不能因重启而消失，就要把相应持久化纳入这个业务操作的完成条件，而不是期待退出回调替它兜底。

本例采用较有限的约定：检查点之后、尚未提交的过程可能需要重玩。这项约定应体现在保存提示和恢复行为中，不能一边允许丢弃未提交进度，一边提前显示“已保存”。

## 43 还在等待结果时，重新启动究竟读哪一份

“没有收到完成通知”也不能简单翻译成“43 肯定没有保存”。需要沿着同一份输入，看进程消失在什么位置。

如果 43 只是进入队列，工作尚未执行存储提交，随后进程被回收，那么它不会因为下次启动而自动完成。此时，能恢复的仍是实际保存且验证通过的检查点 42。

另一种情况是，存储层已经完成 43 的提交，但进程在把完成结果送回界面之前消失。界面上最后一次看到的可能仍是“保存中”；新的进程却可能读到有效的 43。不能因为旧进程没有更新内存里的“最后保存编号”，就主动把它降回 42。

这两个分支说明，恢复必须检查真实存储内容，而不是只重演上一轮内存里的任务状态。启动时先通过项目已有的读取和校验流程确定可用检查点，再让界面恢复材料选择合适的面板。无法读取、格式不支持或内容损坏，应进入明确的错误与恢复处理，不能为了让主菜单出现而立即覆盖唯一存档。

这里的“检查点”指游戏承诺保留的一组进度，不是 SQLite 用于转移 WAL 内容的数据库检查点。如果项目使用 SQLite，已提交数据库与单个主文件的关系，可继续读[SQLite 存档已经提交，为什么只复制数据库文件还会漏掉进度](../../../引擎与工具/运行时系统/缓存与存档/SQLite%20存档已经提交，为什么只复制数据库文件还会漏掉进度.md)。格式升级的接纳条件见[迁移函数返回了数据为什么还不能直接保存](../../../引擎与工具/运行时系统/缓存与存档/迁移函数返回了数据为什么还不能直接保存.md)。本篇不重新设计这些存储协议。

如果同一进程恢复时，云同步已经把磁盘换成另一份进度，还会出现旧内存再次覆盖新文件的问题，那是[Steam 动态云同步恢复后的存档冲突处理](../云存档/Steam动态云同步恢复后的存档冲突处理.md)讨论的另一条边界。控制旧写者仍然重要，但它不能让一个已被 Android 回收的进程继续运行。

## 平台通知要交给真正拥有状态的代码

前面的流程刻意没有给出“覆盖某个 Activity 方法，再直接调用引擎保存函数”的代码，因为收到 Android 通知的地方，不一定就是游戏状态的所有者。

例如 GameActivity 的官方概览把 Java 侧、JNI、`native_app_glue` 和游戏代码分开：事件由平台侧进入，再交给原生线程上的游戏代码处理。[5] 这不意味着可以把 Java/Kotlin Activity 示例逐行搬进任意 C++ 游戏，更不说明 Unity 或 Godot 的某个回调与它完全等价。

接入时应顺着项目真实的调用路线核对：谁收到通知，谁能读取游戏状态，谁负责构造保存输入，谁持有输入直到保存方不再使用。若必须跨线程交接，就交出具有明确有效期的数据，而不是把仍在变化的世界对象地址塞进队列。

复制一个指针没有复制它指向的内容。反过来，即使已经复制出独立的一组字节，也只解决了后续读取这组输入的问题，没有完成存储提交。这是“最小状态交接”和“游戏检查点”必须分开的另一个原因。

本篇不规定 GameActivity 直接回调与 glue 的分配释放写法；它们属于不同接入层，需要对照项目实际采用的包、头文件和所有权约定。对已有引擎，也应使用其支持的平台接入方式，而不是为加一次保存抢占引擎已有的生命周期处理。

## 验证时分别制造恢复条件

验证目标不是让每个生命周期函数都打印一次，而是确认玩家最终恢复到了哪份有效进度，以及界面为什么能展示它。以下是建议的检查计划，本文没有执行 Android 设备或模拟器测试。

先用可丢弃的测试存档建立已提交的 42，再制造等待保存的 43，记录保存请求、存储提交结果和重新读取的内容。至少区分这些条件：

- **Activity 重建，进程仍在**：确认新界面接回正确状态，不因重建而重复发放钥匙，也不启动两个互相竞争的保存所有者。
- **短暂进入后台，进程保留**：确认恢复使用的对象仍有效；这一项通过不能替代进程回收测试。
- **后台进程消失后重新启动**：分别观察提交前与提交后丢失进程的情境，恢复内容应依据实际存储，而不是依据有没有打印销毁或完成通知。
- **明确退出后的冷启动**：允许轻量界面材料不存在，但已提交的游戏进度仍应按产品约定读取。
- **保存失败**：检查空间不足、读取失败或格式不兼容时，不提前显示保存成功，也不把默认新档写回去掩盖错误。

具体怎样制造进程回收，应由测试环境选择并记录。强制停止、清除应用数据、仅销毁 Activity 和系统回收进程不是同一件事，不能用其中一个按钮覆盖全部结论。

这套设计不保证最后一个尚未提交的动作永远不会丢失。它让团队能够准确回答：什么已经成为可恢复的游戏进度，什么只是等候处理的请求，什么仅用于把界面重新摆回来。做到这一步，`onDestroy` 是否到来就不再决定玩家此前全部进度的命运。
