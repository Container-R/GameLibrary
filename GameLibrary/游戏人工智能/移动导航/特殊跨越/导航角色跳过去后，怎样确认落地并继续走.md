# 导航角色跳过去后，怎样确认落地并继续走

敌人沿导航路线跑到沟边，起跳动画播完，却落在矮一层的检修台上。日志里“已接地、有导航点”都是对的，导航找的却不是要去的那座桥。有时角色身体还在桥边，下一帧又被导航代理拉到另一头。这里要解决的不是路线能否把两边连起来，而是：**谁控制这次跨越，怎样确认真正落在预期出口，什么时候把移动交还给导航。** 如果路线从一开始就没有到目的地，先查[如何判断导航路径是否真正可用](../路径查询/如何判断导航路径是否真正可用.md)。

## 路径决定走哪条连接，身体要自己走过去

普通地面上的一段路径可以交给常规跟随器，让角色朝下一个路径点走。跨沟、翻护栏或经过脚本控制的门时，连接表示这两个导航位置**可以尝试用某种动作连通**，不保证当前身体能过去。把入口、出口、出口允许的支撑面和跨越动作作为连接的数据；进入前用当前路线确认连接、方向和角色能力，检查入口位置和起跳条件。若桥还没放下，或这条路径的连接此刻已禁用，留在入口侧重新找路或等待，不先起跳再靠导航纠正。

跨越一开始，普通路径跟随不再驱动身体。把本次入口/出口和一个唯一的跨越编号交给动作控制器，由它在物理步里处理移动及碰撞。动作可以来自跳跃速度、动画位移或其他移动方案，但同一个物理步不要再叠加普通跟随器的位移。目的地这时变了，可以先保存最新目标；新路径算完也不要直接替换身体的驱动者。已起跳的角色若遇到远端关闭，能否继续落地或要进失败恢复是动作规则，不是路径查询回调的副作用。单纯换目标的案例可以继续完成已开始的跨越，再从真实落点重算。

## “已着地，而且附近有网格”还不够

落地后，分开查三个事实：脚有没有碰到地；支撑脚的碰撞面是不是这条连接允许到达的面；实际脚点能否合法接回出口侧的那片导航区域。对最后一项，至少核对出口侧标识及允许的偏差，别把“能找到任意最近点”当成合格。标识可以是单独烘焙的区域、关卡制作的出口区域，或关卡能稳定判定的楼层与方向条件。若两个楼层同属一个区域，区域 ID 不能当楼层 ID；若一张碰撞网格覆盖好几层，用同一个 Collider 引用比较也不够，需要区分支撑面的空间范围或制作语义。候选即便在正确区域、离脚点只有 0.08，也可能隔着栏杆或缝隙。真实接回还要按角色体积检查从脚点到候选的短程移动不会穿障碍，沿途有可走的支撑；验的是项目允许的回网格动作，不是两个点的距离。

下表用出口采样点 (4, 0) 和较低的另一导航点 (4, −0.35) 演示诊断。宽松规则是“接地且在 0.50 单位内有任意采样点”。严格规则是“支撑面正确，且最近点属于出口侧、偏差不超过 0.15”。脚点在表内按普通直线距离比较；这是点模型，不是引擎的实际最近点算法，数值只为区分这些情况。表中的“可接回出口”仅通过了点模型的筛选，未验证真实近程移动；通过一行不等于可以跳过上述检查。

| 动作后的脚点 | 最近导航点及距离 | 接地且有附近点 | 正确支撑 / 可接回出口 | 判定 |
| --- | --- | --- | --- | --- |
| 悬空在出口上方 (4, 0.12) | 出口，0.12 | 否 | 否 / 是 | 不交回 |
| 落在下层检修台 (4, −0.35) | 下层，0 | 是 | 否 / 否 | 不交回 |
| 落在目标桥面未烘焙的凸沿 (4.35, 0) | 出口，0.35 | 是 | 是 / 否 | 不交回 |
| 落在出口上方的独立薄板 (4, 0.08) | 出口，0.08 | 是 | 否 / 是 | 不交回 |
| 落到正确的桥面 (4, 0) | 出口，0 | 是 | 是 / 是 | 交回 |

下层检修台的采样距离已经是零，缩搜索半径仍不能把它排除。凸沿属于正确桥体，却还不能接回导航；应该检查烘焙覆盖、落点设计或项目明确支持的回到网格的移动。相反，独立薄板即使贴着正确网格也不是桥面。按角色半径、落地误差、烘焙留边和相邻楼层间距选容差，别照搬表中的 0.15。场景会改动时，使用一致的导航状态核对出口；若出口失效，留在动作恢复状态，不提交一个已失效的出口。[1][2]

## 先验收身体，再同步导航代理

可以把控制流程写成“普通跟随 → 动作跨越 → 验收落点 → 恢复跟随或失败恢复”。跨越完成事件要带本次编号；旧动画回调或重复事件不改变当前状态。同编号的动画回调若来得太早，角色还在空中，应该继续由动作控制器移动；只在实际落错或动作超时等明确失败条件下进入恢复。一次合格落地只允许提交一次。先让身体完成该步移动，再读真实支撑和出口导航条件，才调用引擎的完成或对齐步骤。代理位置与身体位置可能是两份状态，交回前比较它们，以及下一次普通移动要从哪里开始。收到新目标时从确认后的实际落点重规划；错误落点或无法继续接网格时，用有碰撞检查的恢复方案找到安全支持面，再恢复跟随，不能盲调用“成功完成”。

Unity 6000.0 关闭 `autoTraverseOffMeshLink` 后，代理会在连接处等待，官方示例先做自定义移动，再调用 `CompleteOffMeshLink()`。这个方法操作当前连接，不接受你保存的跨越编号；先核对代理仍处于本次同一条连接、同一方向，再提交。它把代理挪到另一端最近的有效导航位置，不是一次物理着地检查。不要把跨越中调用 `ResetPath()` 当成普通取消：官方明确它会立即完成当前连接。若角色由物理控制器或动画驱动，重新开启 `updatePosition` 又会使 Transform 立即对齐 `nextPosition`；完成后读回实际代理位置，确认它锚在正确一侧，再看两份状态是否已一致；把可接受的对齐误差、物理控制器的处理和失败分支写清楚。可以由同一套外部移动器继续驱动角色、只取代理的导航意图，不一定要切回自动同步。[3][4][5]

Godot 4.6 的 `link_reached` 通知的是到达连接入口；入口/出口元数据取决于标志及所有者类型，不是落地完成回调。让信号只留下请求，在物理步处理；官方类文档提醒，在代理信号里调用会更新路径的查询有递归风险。用 `CharacterBody3D` 时，当前步实际调用 `move_and_slide()` 后再读 `is_on_floor()`，它说的是最近一次该调用的地板状态，不会替你验证是哪块地板。动作接受落点后，才恢复普通的路径采样与移动循环；不要找一个名字像 Unity 完成接口的信号来代用。[2][6][7]

验收时用固定镜头和慢速/逐步运行，至少摆出正确桥面、下层和未烘焙凸沿。每个物理步记下跨越编号、控制者、预期出口、真实脚点、支撑面/导航侧、采样偏差、完成次数。在跳到一半时换目标，再注入一次上一跳的完成回调：应该只有同编号的真实落地能交回，且新路径起在确认后的那一侧。如果角色突然出现在出口而身体检测没通过，先查是不是误调用了完成、清路径，或过早打开了位置同步。若角色正确落地仍不走，再看接网格的偏差、出口版本和下一路径是否已从真实位置刷新。用这套记录才能区分“导航认为已过”和“角色确实过了”。
