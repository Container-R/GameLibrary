# 效用AI的目标保留与行动切换

机器人一直选择“采矿”，却在两座矿点之间反复转向。行为日志里的动作名没有变，移动任务却一次次重新开始。给“采矿”加一点保留奖励也没用，因为两个矿点都拿到了这份奖励。另一个修补办法是降低决策频率，但矿点消失后，机器人又可能继续奔向旧位置。

这类问题横跨三个环节：**当前选择指向谁、分差多大才值得换、原选择何时必须退出。** 只改评分曲线，很容易修好其中一个环节，却把问题留在另一个环节。

本文面向已了解基础效用评分、能够编写持续行为的 AI 程序与行为设计人员，给出一套确定性选择器的接入方法。范围是单个角色、单个管理者、一次执行一个具体候选、停止能够同步完成的行为。读完后可以定义候选身份和资格，将保留奖励接到开始、持续更新、停止与再次选择，并用日志分辨小分差抖动和必要切换。文中的机器人、参数和验证程序均为原创示例，不是某款游戏的内部实现。

## 1. 当前选择要包含真正会改变行动的目标

效用评分（utility score）把某个选择在当前情境中的吸引力表示为可比较的数值。它不天然等于概率、经济收益或完成时间。Graham 强调共同评分尺度，并区分取最大分与按权重随机抽样；后文使用的是确定性最大分选择，不把二者混用。[1，§9.2.1、§9.6]

先规定一个候选键：

```text
候选键 = (行为类型, 目标身份)
(采矿, 矿点A) 与 (采矿, 矿点B) 是两个候选
```

这里的键用于判断“是不是还在继续同一个选择”。它应包含那些改变后需要重新接管行为的参数。例如，同一台设备上的两个操作槽若有不同预订和到达位置，也可能需要进入键；只是目标位置随物体移动而更新，则未必意味着新选择。不要把每帧变化的位置或评分放进键，否则同一行动也会不断被判作新候选。

目标身份还要稳定。若对象池重复使用整数编号，旧目标被删除后新对象恰好拿到同一编号，仅比较编号会误认成继续原目标；应使用能区分对象代次的句柄，或在替换时显式结束旧选择。本文示例约定目标编号不复用，执行实例也只有一个，不用候选键代替异步操作的实例编号。

**把保留规则放在真正决定目标的层。** 假设高层选择器只决定“采矿还是充电”，低层才从 A、B 中选矿点：高层持续选择采矿，低层仍可每次换矿点。此时应让低层记住当前矿点，或将高层改成比较完整的行为—目标候选；不能仅扩大高层奖励。

Dill 将角色中的不同决策者与它们选择的选项分开讨论。[2，§5.2、§5.4] 实际项目也可能把对象选择放在规划器外：Orkin 描述的 F.E.A.R. 历史实现，一次规划只围绕已选武器和目标推理，由其他子系统决定关注谁。[3，页12] 这些资料支持检查职责层次，不意味着上述项目采用本文的候选键或奖励算法。

## 2. 先区分开始资格和继续资格

“值得做”与“现在能够做”应分开。候选不合格时不参加比较，不能只把它的分数设成零，然后再加保留奖励。否则无效旧候选的 `0+50` 可能胜过合法候选的 `30`。相反，合法候选也可以得到零分；在本文规则里，它仍是候选。

但有效性检查不能机械地复用开始条件。以需要独占操作位置的充电台为例：

| 时刻 | 能否开始一次新充电 | 当前充电能否继续 |
|---|---|---|
| 台位可用，尚未被占用 | 可以 | 尚无当前行为 |
| 本角色已占用台位，设备仍可用 | 不允许再开始一次 | 可以继续自己的充电 |
| 台位损坏或目标消失 | 不可以 | 不可以 |

若每次都用“台位空闲”检查当前行为，角色一占用就使自己失效；若只看目标仍存在，则可能继续使用已经损坏的设备。应分别定义 `can_start(key)` 和 `can_continue(current)`，并明确它们读取哪些对象事实。Dill 讨论保留上下文时也指出，失去执行能力后仍应改变选择，而不是为了连贯性强行继续。[2，§5.5]

一次普通评分的候选集合这样构成：

1. 当前行为尚未完成且通过继续检查时，把它加入集合。
2. 对其他行为—目标组合，只有通过开始检查才加入。
3. 按候选键去重。当前候选不得因“不满足重新开始条件”而被第二步覆盖或删除。

例子中，开始会预订目标，停止会释放预订。真实项目不一定需要预订，但必须保持同样的含义区分。开始时消耗一次材料、进入后获得临时权限等规则，也可能使开始与继续条件不同。

资格必须来自当前可用的世界知识。高频读取一份没有更新的“目标有效=true”，不会让角色更早发现目标失效；感知更新、资格检查和最终停止之间的时间应分别记录。

## 3. 奖励只给具体当前候选，并写清比较规则

Graham 在惯性（inertia）一节讨论给正在进行的行动增加权重，以减少接近评分之间的反复选择。[1，§9.7] 下面把这一思路具体化为一种加法规则；常数和并列处理均是本文的设计，不是原作者给出的通用参数。

令 `U(k)` 是候选的基础分，`c` 是当前候选，`h>=0` 是保留奖励：

```text
排序分 R(k) = U(k) + h，若 k 等于 c
排序分 R(k) = U(k)，其他情况
```

从合格候选中取排序分最高者。排序分并列时，优先保留当前候选；并列者中没有当前候选时，使用项目约定的稳定顺序。候选为空返回“没有选择”。分数必须有限且处于一致尺度，NaN 等异常应作为评分错误处理，不能让容器遍历顺序替你决定行动。

一个直接实现如下。这里 `eligible_scores` 已按上一节完成资格过滤和去重：

```python
def choose(eligible_scores, current, h):
    if not eligible_scores:
        return None
    return min(
        eligible_scores,
        key=lambda k: (
            -(eligible_scores[k] + (h if k == current else 0)),
            k != current,
            k,  # 示例用候选键的稳定顺序处理其余并列
        ),
    )
```

假设当前是 `(采矿,A)`，A、B 的基础分分别为 600 和 610，h=50。只有 A 得到奖励时，650 胜过 610，继续 A。若奖励误加到所有“采矿”候选，比较变成 650 与 660，仍然换 B。两边同时加同一个数，不会改变分差；把 h 增大到 500 也修不好这个层次错误。

当 A 降到 400、B 升到 900，B 仍能胜过 A 的 450。因此保留奖励不是锁死当前候选，而是要求竞争者至少更好一定幅度。

这一规则形成评分上的迟滞（hysteresis）。只有 A、B 两个有效候选时，令 `D=U(B)-U(A)`：

- 当前是 A，只有 `D>h` 才切到 B。
- 当前是 B，只有 `D<-h` 才切回 A。
- 两个等号边界都保留当前。

两个方向使用不同门槛，所以小幅反转不会立即反向切换。但若 D 每次都在 +60 与 -60 之间跳变，h=50 仍允许每次切换。**评分迟滞不保证最低持续时间。** 若设计要求有效行为至少持续 T 秒，需要另外定义普通改选的时间限制，以及目标失效、完成或紧急反应是否例外；不要把该要求隐含在一个评分常数里。

## 4. 保留目标还要接到行为生命周期

即使每次选出同一个候选，如果调用侧每次都重新执行 `start`，路径、预订或交互进度仍可能不断重置。因此一个管理者需要同时持有当前候选和它对应的执行状态，只有管理者能改变它。

下列方法采用一个明确的调度取舍：当前资格和执行结果每次行为更新都检查；偏好评分按较低频率进行。当前行为失效或结束后立即退出，但**等待下次普通评分**再找替代，不拿缓存中的旧分数临时补位。这样实现简单，代价是退出后可能有短暂空闲。紧急事件是否触发额外评分，需要另行决定。

### 一次更新按什么顺序执行

1. 接收本次已知的世界状态与执行结果。检查当前行为的继续资格与完成、失败状态；需要退出时记录原因、清理执行和预订，再清空当前候选。本例同时遇到失效与完成时，优先记录失效。
2. 到了普通评分时刻，重新生成合格候选并为本次比较计算基础分。不能把新候选的分数与上次当前候选的分数混在一起。
3. 按上一节选出候选。选中当前候选时，不调用 `start`，保留现有执行。
4. 选择改变时，先同步停止旧行为并清空当前；然后尝试开始新候选。只有开始成功，才把新候选保存为当前。开始失败则保持空闲，记录失败，下次普通评分再决定；不在同一更新内循环重试。
5. 若有正在执行的当前行为，调用一次持续更新。执行器保存更新后的状态，在下一次步骤1检查完成或失败后退出；已经结束的执行不会再接受下一次持续更新。这个检查相位必须与执行器约定一致。

这里的停止合同很重要：`stop` 返回时，旧行为已不再占用新行为要接管的能力，旧预订已释放。若你的动作只能异步停止，不能把“已发停止请求”当成这个返回条件，直接同时启动互斥的新动作。那需要独立的停止与接管协议，可参见[计划继续与动作结束的区别](../行动计划/Killzone3如何判断计划继续和动作结束.md)。

实现时可把清理集中成一个只处理当前执行的函数，避免完成、失效和普通换目标各写一套：

```text
leave(reason):
    若 current 为空，返回
    stop(current, reason)       # 本文要求同步清理
    current = 空

普通评分得到 next 后：
    若 next == current：保持现有执行
    否则：
        leave("更换选择")
        若 next 非空且 start(next) 成功：
            current = next
```

此流程要求同一更新内没有其他管理者并发改变预订，且开始失败不遗留占用或其他未清理的副作用。部分成功后才报错的接口必须先在适配层完成收尾，不能直接套用这里的失败分支。

`start` 仍要确认开始资格。即使评分时合格，接入真实系统后预订或资源获取也可能失败。此时不把失败的新行为记成当前，不把旧行为假装成仍在执行，也不无限尝试其他候选。本文选择短暂空闲并等待下一次评估；若项目必须保证无缝替换，需要能在放弃旧行为前确认新行为可接管的专门机制。

还有一个常见遗漏：完成之后若条件和分数仍允许同一候选，下一次评分可以再次选中它，那是**新一次执行**，不是上一段继续。如果本次退出恰好发生在普通评分的同一个 tick，清理后可以在该 tick 开始新一次执行，并不一定再等一个周期。一次性采集应由世界状态移除已耗尽资源；可重复交互应有自己的再次开始条件。选择器不负责猜测“做完就永远不再做”。

## 5. 用一条完整轨迹核对保留、退出和恢复

下面约定行为更新每 10ms 一次，普通评分每 100ms 一次，h=50。目标占用由这个单角色同步维护，基础分使用整数千分位。示例只验证选择和执行调用，不模拟真正的移动与采矿。数值是用于区分规则的输入，不是响应预算建议。

当前执行 A 时，A 的新开始资格为假，因为台位已被自己占用；继续资格仍为真。这是检查是否误用开始条件的关键时刻。

| 时刻 | 已知变化与评分 | 管理者应做什么 |
|---|---|---|
| 0ms | A=600，B=590，均可开始 | 开始 A，记录当前 A |
| 100ms | A=600，B=620，A 可继续 | 600+50 胜过 620；只更新 A，不再次开始 |
| 200ms | A=600，B=700 | 停止 A，释放 A 的占用，再成功开始 B |
| 241ms | A、B 均失效的信息进入模型；尚未到下个行为 tick | 尚未执行检查 |
| 250ms | 继续资格检查发现 B 失效 | 停止 B并清空；不使用旧评分替补 |
| 300ms | 新评分时没有可开始候选 | 保持空闲 |
| 351ms / 400ms | 351ms A 恢复，400ms 评分为合法零分 | 400ms 开始新一次 A，不恢复旧执行计数 |
| 420ms / 430ms | 420ms 第三次更新达到人工完成条件 | 430ms 检查完成并停止 A |
| 451ms / 500ms | A 不可用、B 恢复；500ms 开始 B 时注入失败 | 保持空闲，不在本轮重试 |
| 600ms / 630ms | 新评分后成功开始 B，更新三次达到完成条件 | 630ms 检查完成并停止 B |

在 241ms 与 250ms 之间，模型的检查相位造成了 9ms 等待；从世界变化到信息可用的感知延迟并未模拟。退出和下一次评分又是两个时刻。只记录“250ms 改了 current”，会把停止旧行为和开始新行为混成一个事件。

附属程序实际调用 `start/update/stop` 并保存逐步记录，用它检查：第一次 A 未因小分差重启；换 B 前 A 已清理；B 失效后不再更新；无候选时没有沿用旧对象；恢复 A 是新开始。主轨迹记录了5次开始尝试、4次成功开始、4次停止、31次持续更新，最终没有占用。另一个小用例在已有 A 运行时让替换 B 的开始失败，确认顺序是停止 A、尝试 B 失败、保持空闲，而不是假装 A 仍在运行。模型工作计数只是验证连续更新是否被重置，不代表游戏产量或行为质量。此程序未注入运行中的失败状态；接入真实执行器时，仍须按第4节实现并单独检查运行失败的退出分支，不能用开始失败用例代替。

这条轨迹补齐的是调用合同，不证明机器人能到达矿点、动画能够停止，或更少切换一定提高任务成功率。将它接入项目后，需要用实际执行器重新观察这些结果。

## 6. 调整奖励前，先知道你愿意放弃什么

保留奖励是在稳定与及时改选之间做取舍。只以“切换次数越少越好”为目标，会把有效的应变也压住。

**先查奖励的尺度。** A=500、B=530、h=50 时会留 A；如果基础分整体乘十而 h 不变，就会选 B。连 h 一起乘十才保留原比较关系。对响应曲线、分项权重或截断方式做非线性修改，不能只用这个比例关系补偿。奖励后的数只是排序量，超过基础分上限不需要自动截断；若截断，需重新检查并列和切换门槛。

**再选择可接受的小分差区间。** 从代表性的游戏情境记录“继续当前候选”和“最好竞争者”的基础分差，区分感知噪声、轻微机会变化与必须响应的事件。h 应保护前两者中你愿意忽略的部分。若真正重要的候选长期只高出很小的分差，它可能一直无法胜出；此时应重新检查评分语义、降低 h，或明确使用随时间变化的保留政策，而不是把“不换”当成可靠。

**按重启代价决定是否使用统一奖励。** 换一个无需转身的注视目标和重新走到远处的交互点，代价未必相同。固定 h 简单、易解释，适合首先诊断；若改成随行为或时间变化的奖励，每次日志也要保存实际使用的 h，重新检查边界。不要把一个固定 h 宣称为真实路程或资源消耗的精确折算。

**最低持续时间与紧急响应要明写。** 加分允许明显更优者随时胜出；时间锁定限制的是何时允许普通切换；等到动作完成才决策，则把选择机会绑定到执行结果。Graham 把这些列为不同惯性处理方式，并描述过在互动队列空后才作下一决定的历史项目做法。[1，§9.7] 应按行为的可中断性和响应需要选择，而不是把各种机制叠起来后仅看表面是否安静。

对于必须及时处理的危险，首先确保事件能更新到相应决策层，并能触发需要的检查或评分。单纯把危险评分设得很高，不能让尚未评分的候选提前出现。本文的等待下一次普通评分策略不适合直接承诺即时避险；允许事件触发额外评估时，还应核对执行层是否真的可被中断。

## 7. 让日志回答“为什么换，以及是否真的换了”

排查时不要只记录最终动作名。对一次比较保存：评分时间、候选键、开始或继续资格及原因、基础分、实际奖励、原当前候选与最终选择。另在执行侧记录开始尝试、开始成功、停止原因、完成或失败，以及持续更新属于哪次执行。

用这些信息可以分开定位：

- 动作名没变、目标不断换：先查候选粒度和负责选目标的层。
- 候选键没变、开始次数一直增加：查调用侧是否把重复选择当成重启。
- 一开始就退出：查自己占用资源后是否误用了新开始条件。
- 分数看似足够高却没有切换：查比较是否发生、分数是否来自同一次快照，以及实际门槛。
- 目标已失效仍继续：沿世界变化、感知可见、资格检查、停止完成逐段查时间。

验收至少保留小分差反转、超过门槛、等号、当前失效、无候选、开始失败和完成后再次可用这几类输入；并用一个开始与继续条件不同的行为走完完整轨迹。先检验规则和调用是否符合项目合同，再观察实际改道距离、交互完成情况和玩家可理解性。后面这些结果需要代表性游戏场景，不能从选择次数或模型计数推出。
