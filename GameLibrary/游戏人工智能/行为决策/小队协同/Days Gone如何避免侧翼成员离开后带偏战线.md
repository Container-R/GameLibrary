# Days Gone如何避免侧翼成员离开后带偏战线

两名队员原本一起对敌，其中一人开始绕侧翼。为了不让绕行中的角色把整队方向拉走，程序把他从队伍中心的计算里排除。结果，留下的队员没动，敌人也没动，队伍朝向却立刻变了。

这不是浮点误差才能造成的问题：**删掉一个参与平均的位置，本身就可能改变平均位置。** 如果后续系统用这个中心判断战斗方向、站位是否合法，角色还没完成绕行，队伍就可能先忙着调整阵形。

本文面向小队 AI 程序员和参与战斗行为配置的设计师。开头是原创的简化情境，不是项目故障记录。下文借《Days Gone》的一项公开处理办法，解释为什么“别跟着这名角色移动”不一定等于“立即删除他对共享计算的贡献”。我们只追踪中心与方向，不复刻整套战斗 AI。

## 从角色位置到共同的战斗方向

Tobias Karlsson 在《Squad Coordination in Days Gone》中介绍，游戏用一条前线组织小队与敌人的空间关系，其方向依据合格友方与敌方的平均位置确定。这里的“前线”是供行为计算使用的空间描述，不是关卡里预先画好的一条不可穿越的墙。[1]

先用一个可以手算的平面例子看问题。所有坐标使用同一单位：友方 A 在 `(-2,0)`，友方 B 在 `(2,0)`，敌方中心固定为 `(0,10)`。不考虑高度、掩体、碰撞和感知变化。我们定义友方中心为参与计算的两个位置的算术平均，再用“敌方中心减友方中心”表示朝敌方的方向；向量长度不是攻击距离参数。

```text
友方中心 C = ((-2,0) + (2,0)) / 2 = (0,0)
朝敌方向 D = (0,10) - C = (0,10)
```

现在 B 要绕行。可以比较三种处理，不必先运行整个游戏：

| 怎样对待 B | 参与中心计算的位置 | 友方中心 C | 朝敌方向 D |
|---|---|---|---|
| B 还在原位 | A 和 B 原位 | `(0,0)` | `(0,10)` |
| 立即排除 B | 只有 A | `(-2,0)` | `(2,10)` |
| B 移到 `(8,6)`，继续使用其当前位置 | A 和 B 新位置 | `(3,3)` | `(-3,7)` |

第二行最容易被忽略。虽然删除的目的是不跟随 B 移动，删除动作却已经让中心偏向 A，方向也不再竖直。第三行则是另一种影响：保留实时位置后，绕行真的会牵动共同方向。二者不能只用“加个平滑”混成同一个原因。

这些坐标和表格是本文原创算例，不是原游戏的配置、测量或完整前线算法。实际前线还包含其他空间量，表里没有计算它们。

## 留住一个代表位置，而不是同时算两个人

原作者指出，排除友方侧翼成员仍会改变中心，因此让绕行者留下一个不移动的 ghost：更新前线时，用这个代表位置替代该成员的实际位置。原文图8、图9对比了删除成员与保留代表位置的区别。[1]

回到我们的例子，在 B 离开时保留 `(2,0)` 作为其代表位置。B 真正走到 `(8,6)`，共享计算仍使用 A 的 `(-2,0)` 与这个代表位置：中心还是 `(0,0)`，方向仍为 `(0,10)`。这只隔离了本例中 B 的绕行对中心的影响；A 或敌方移动时，结果仍然可能变化。

这里最关键的是**替代**。若同时加入 B 的当前位置与旧位置，就成了三个输入：

```text
C = ((-2,0) + (8,6) + (2,0)) / 3 = (8/3, 2)
D = (0,10) - C = (-8/3, 8)
```

这既不是原来的两成员中心，也不是只冻结 B 贡献的结果。排查时不能只问“有没有创建代表点”，还要确认旧输入确实被替换，而不是多加了一份权重。

同样，不要把计算中的代表位置自动当成场景里的真实角色。是否有人挡住通道、是否命中目标、能否到达掩体，各自需要合适的真实输入。本文的建议是让这个替代只作用于已明确的共享计算，不能为了稳定一个平均值就冻结所有系统看到的角色位置；这不是原作者公开的完整对象实现。

## 稳定不是永远不变：什么时候应该移除代表位置

原文中的 ghost 不是永久缓存：对应成员重新加入前线、死亡或离开小队时会清除；前线相对放置时的位置或方向改变超过阈值，也会清除。因为代表位置固定不动，战斗整体迁移后继续保留它可能产生不合理结果。[1] 文中没有给出可直接用于任意项目的阈值数值。

假设 B 真的死亡了。此时只剩 A，中心转到 `(-2,0)` 可以是正确的成员变化，而不再是我们想屏蔽的暂时绕行。若为了让曲线平稳，继续把已死亡的 B 留在平均值里，数值稳定了，描述的却是已经不存在的队伍。

相反，B 绕行结束后重新参与正常站位，计算应回到其适用的真实位置。交接时需要说明：什么状态使用当前位置，什么状态使用固定代表位置，什么状态完全不贡献。把这三种含义都写成“暂时忽略 B”，实现者很容易选择不同的做法。

还应想清楚最后一个有效输入被移除时怎样处理。上面的算式要求至少一个参与者；空集合没有这个算术平均。项目可以结束这次协调、等待重新形成队伍，或采用明确的后备行为，但不能悄悄把除零结果当成新的战斗方向。敌我中心恰好重合时，方向向量为零，也需要另外的决定。这里提出的是接入前要补齐的情况，不声称原游戏公开了对应代码。

## 检查输入含义，再检查运动是否平滑

为自己的实现做有限检查时，可以先记录每名成员实际贡献的输入：真实位置、固定代表位置，还是不参与。再记录中心与下游使用的方向。用前面的两人例分别走过离开、绕行、返回和死亡，比较中间数值；这比只盯最后角色有没有抖动，更容易区分重复计数、退出遗漏与预期的成员变化。

之后再看真正的站位行为。一个稳定方向不保证掩体有效、路径可达或玩家读得懂战斗；代表位置也不是对所有 NPC 都合适。若角色的移动本来就应该迅速改变队伍决策，冻结其贡献反而会造成迟钝。需要先定义哪些移动只是局部动作，哪些变化意味着共同战况真的改变，再决定用哪一种输入。

若问题是两个候选行为分数接近、反复互相抢占，可另看[AI为什么在两个差不多的选择之间来回切换](../../../../管理档案/支持资料/AI为什么在两个差不多的选择之间来回切换.md)。那讨论的是选择结果怎样保持；本篇讨论的是选择之前，共享空间描述究竟由哪些输入构成。二者可以同时存在，不能互相替代。
