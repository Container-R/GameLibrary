# 如何计算关卡完成率

玩家第一次挑战失败，读档再试，终于过关。完成事件发送时网络超时，客户端又补发了一次。现在日志里可能有两条开始、一次失败和两条完成。

如果直接用“完成行数 ÷ 开始行数”，结果是 100%。按实际尝试算，却是两次里完成一次，只有 50%。按玩家算，这名玩家最终完成了，又是 100%。三个数字看起来矛盾，实际回答了不同问题，其中第一个还把重复上报当成了新完成。

本文面向策划、数据分析和测试人员：先确定想了解的是尝试还是玩家，再处理读档、重复上报和晚到记录。下面的小数据是为解释口径构造的例子，不是真实玩家表现，也没有新增数据库实验。

## 先给“一次尝试”划边界

一次游戏会话，通常指玩家从进入游戏到离开的一段活动；一次关卡尝试，则是从某个约定起点出发，直到完成、失败或仍未得到结果的一次挑战。一个会话里可以重试多次，同一次挑战也可能因暂停、退出和恢复而跨越多个会话。不能直接拿登录次数代替挑战次数。

读档尤其需要由玩法和分析共同定义。在开篇例子里，我们约定：失败结束当前尝试，按“重试”从关卡起点重新挑战，就开始下一次。新挑战即使恢复了同一份游戏存档，也不能因此复用前一次尝试的身份。否则第一次失败和第二次完成可能被揉成一条自相矛盾的记录。

另一款游戏可能允许中途存档后继续同一次长关卡。此时恢复未必算新尝试。没有通用答案，关键是报表要和游戏规则相符：你想研究“每次挑战能否过关”，还是“每次进入检查点以后能否推进”？先选一个，并让开始与结束事件遵守同一边界。

此外，还要区分**重新游玩**与**重新发送**。前者产生新的尝试；后者只是同一个事件再次抵达。事件自己的标识用于识别后者，尝试标识用于把开始和结局配对，玩家标识则用于汇总一个主体的多次尝试。三者不能互相代替。

Unity Analytics 的 REST 文档分别描述用户、会话和事件 UUID，并说明事件 UUID 用来防止意外重复插入。[1] 这能帮助理解身份分层，但不意味着所有分析系统都具有相同的去重规则，也不替你的项目决定读档算不算新尝试。

## 用同一张小表，算出三个有用的比例

假设我们选取某一时间段内开始的尝试。这样的“一批按相同条件选中的对象”常称为 cohort，本文称它为**开始批次**。截至第一次出报表时，整理后的记录如下：

| 玩家 | 尝试 | 当时已知的结果 |
|---|---|---|
| P | a1 | 完成 |
| P | a2 | 失败 |
| Q | b1 | 完成 |
| R | c1 | 尚无有效结局 |
| S | d1 | 结局记录冲突，暂不能确定 |
| T | e1 | 尚无有效结局 |

这是六次尝试、五个玩家，不是六个玩家。P 的两次挑战都应保留，但统计玩家人数时只能算一次。

如果策划问“开始一次挑战后，有多少已知完成了”，分母是六次开始，分子是 a1、b1 两次完成，结果为 **2/6，约 33.3%**。它描述的是截至当前所知的完成比例，不是最终完成概率。还有三次不知道结局，必须一起报出来。

如果问“进入过这批挑战的玩家中，有多少至少完成过一次”，P 和 Q 满足条件，分母是 P、Q、R、S、T，结果为 **2/5，即 40%**。P 有一次失败，不会抹去他已经完成过的事实；同样，多完成几次也不会把他算成多个人。这个指标适合看覆盖到多少玩家，却不能说明一次挑战的难度。

如果问“已经明确结束的挑战里，有多少成功”，只纳入两次完成和一次失败，得到 **2/3，约 66.7%**。GameAnalytics 的 Progression 指标中，Win percentage 使用的就是 complete 与 fail 组成的已结束尝试分母。[2] 这里借它说明一种指标定义，不声称我们的手算复现了供应商整套后台处理。

因此，报告里不宜只写“完成率 66.7%”。写成“已结束尝试中的成功比例 2/3；本批共开始 6 次，其中 3 次结局未确定”，设计师才知道哪些对象被排除了。没有一个分母天然更正确，只有它是否回答了眼前的问题。

## 没有看到结局，不能直接填成失败

R 的 c1 没有完成记录，可能还在游玩，也可能记录尚未送达。S 的 d1 则是另一种未知：同一个结局事件出现了“完成”和“失败”两种内容。它们都暂时不能进入明确完成或明确失败，却不应该被解释成同一种游戏行为。

GameAnalytics 的事件文档讨论了关闭应用时 session end 可能来不及处理、之后再恢复上报的情形。[3] 这是终止记录可能缺失的一种工程例子，不是对 c1 的诊断；session 结束也不等于关卡尝试结束。

在这张表采用的整理办法里，相同事件标识、相同业务内容的重复行只算一次；相同标识却出现不同结局，则把该事件的冲突版本一起隔离，暂不选其中一条。这是一项明确的示例政策，不是所有项目都必须采用的唯一方案。若系统另有可信的更正机制，可以设计对应规则，但不能让“数据库里碰巧最后读到哪条”替团队决定结果。

如果完成事件找不到对应开始，也先单独记下，而不是直接塞进本批分子。它可能属于其他时间段的尝试，也可能漏了开始记录，需要继续查。完成和开始不能仅凭数量配对。这里的“玩家”也只是数据中约定的主体标识；跨设备是否合并、多人共用账号如何处理，要另有身份规则，不能凭一列 ID 就认定是真实个人。

对于当前这批，我们应能说明：两次完成、一次失败、三次未知，合计六次有效开始。冲突和孤立完成另有多少，也应让分析与测试人员看见。这个总数核对是为了发现遗漏，不是证明数据已经包含了所有真实游玩。

## 报表有两个时间：游戏何时发生，数据何时被看见

把小例子的时间写得更明确：只选取在虚构时间 0 秒至 100 秒之前开始的尝试，且只把从各自开始到 100 秒之前发生的有效结局计入。100 秒本身不属于这段窗口。

第一次报表只使用截至 100 秒已经抵达的记录。第二次仍看同一段游戏发生时间，但允许使用截至 200 秒抵达的记录。假设 c1 的完成发生在 90 秒，直到 150 秒才送达，那么它不会出现在第一份报表，却会进入第二份。

此时已知完成增加到 a1、b1、c1：按尝试是 **3/6**，按至少完成过一次的玩家是 **3/5**，按已结束尝试是 **3/4**。关卡没有因此变简单，我们只是晚些时候知道了更多事情。

反过来，如果另一条完成发生在 110 秒，即使报表已经收到它，也不属于刚才固定的结局窗口。若想回答“这批开始最终有没有完成”，就需要另订跟进时长，而不是悄悄把结局范围拉长。按开始日期分组后给每次尝试相同的跟进时间，是另一种可选设计；它与统一截止日的含义不同，也要等待足够时间后才能比较。

因此，报表至少应让读者看见两句话：“统计哪些发生时间内的开始与结局”和“数据收集到什么时候”。Unity 的 REST 文档明确说明，不提供事件时间戳时会用接收时间推定。[1] 若源数据只有接收时间，就不能假装已经恢复了准确的游戏内时间；真实时钟漂移也不是加一个字段就自动解决。

后来看到的新信息不一定只会抬高完成数。如果 d1 最初只抵达“完成”版本，报表可能先把它计入；冲突版本后来抵达后，按上述政策它会退回未知。这是数据判断的修订，不是玩家撤销了已经发生的动作，更不是设计退步。保留旧报表及其截止条件，才能解释为什么同一历史日期的数字发生变化。若开始记录本身晚到或发生冲突，批次成员和分母也可能修订；本例第二份报表保持六次开始，是这个例子的设定，并非所有历史分母都会固定。

## 从手算走到实际报表，应先能说出每个成员

数据分析不宜一开始就只验证百分比。先列出这批有哪些尝试，哪些算完成，哪些算失败，再核对各玩家是否至少完成过一次。如此才能发现“分子漏了一个，分母也漏了一个，比例看起来还差不多”的问题。

对这个有限例子，处理顺序是：按收集截止时点选出可见记录；辨认重发与冲突；根据有效开始选出批次；把有效结局配回各自尝试；最后分别按尝试和玩家汇总。冲突检查不能只看最后想计入的完成行，否则把冲突另一半先过滤掉，就可能制造出看似确定的结果。

测试人员可以围绕游戏动作检查这些约定：失败后重试是否真的产生新尝试；补发完成是否仍代表原事件；读档继续是否延续了项目规定的那一次挑战；开始与结局是否属于同一玩家。遇到多个不兼容的开始或结局，不要静默挑一条，让记录看起来整齐，而应先查清生成规则。

零分母也应单独处理。如果选定窗口内没有任何符合条件的开始，“完成 0 次／开始 0 次”表示这项率没有定义，不是 0% 完成率。否则一个没有数据的关卡会被误读成所有玩家都失败。

已有资料保留了一份原创的 18 行合成事件模型，按两种收集截止时间生成报告，并核对有限的输入排列和上述成员结果。它使用 Python 标准库，不是 SQL 查询或供应商服务调用。本文只保留其计数思想与适用范围，没有重新运行它，也没有把合成结果当成真实游戏数据。它不能证明生产投递可靠性、跨设备身份准确性或任意数据都能被正确处理。

## 完成率帮助定位问题，不替你解释所有原因

如果本轮要判断“玩家能否不靠主持人提示理解出口”，那么得到帮助后的完成应保留为完成，但要另记帮助情况。帮助字段缺失时是未知，不能直接当作无人帮助。终点事件只告诉你触发了什么，不直接告诉你玩家理解了什么。

同样，两版本完成率不同，可能来自人员构成、观察时长、重试定义、记录完整性或关卡改动。先让这些口径可比较，再讨论难度变化。一次读档、一次网络重发和一条晚到事件都不是小到可以忽略的技术细节：它们决定的是你在数玩家、数挑战，还是数消息。

这份分析报表也不应直接授权发奖。统计端把重复记录只算一次，不等于游戏端已防止重复领取；奖励仍应依据游戏认可的完成条件，并正确处理重复请求。两者解决的是不同问题，不能用报表中的一个完成事件代替发奖检查。

最有用的报告不只是一个百分比，而是一句完整的话：**哪一批对象，在多长的观察范围内，截至哪次数据收集，有多少已知完成，还有多少未确定。**
