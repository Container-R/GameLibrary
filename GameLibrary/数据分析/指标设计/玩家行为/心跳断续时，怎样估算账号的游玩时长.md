# 心跳断续时，怎样估算账号的游玩时长

一名玩家在手机上玩到一半切后台，稍后用平板接上。手机没及时上传最后一批心跳，还补发了一条已经收过的记录。如果拿第一个和最后一个心跳相减，后台空档会算进去；如果分别算两台设备再相加，同时在线的那几秒又会算两遍。

做玩法漏斗或版本对比时，先把指标定义成“同一账号在业务日内，至少一台设备处于合格游戏状态的估计时长”。本文用定期心跳重建这些区间。它区别于连接在线时长，也不是人的注意力测量：一人在两台设备同时挂着仍算一个账号，不代表真的有一个人在玩。

## 先定什么状态算游玩

以一款对局制游戏为例，只在本机可交互、且本地玩法状态处于对局时记为合格。加载页、后台和暂停不合格；普通动画、思考或观战是否计入，得由用途决定，不能用“多久没按键”一概代替。用客户端发出进入与离开合格状态的事件以及状态心跳；如需诊断掉线，另记连接状态。短时离线能继续玩的模式不必仅因连接断开就删掉那段行为。

Android 的 Activity 完全不可见时会进入 Stopped；多窗口下 Paused 仍可能可见。生命周期事件可以参与合格状态判断，不等于游戏逻辑或玩家注意力。离开事件也可能没送达，例如进程被杀时，虽然回调可能早已发生，上传仍未必成功。[Android 活动生命周期](https://developer.android.com/guide/components/activities/activity-lifecycle#onstop)

每条事件保留账号、设备会话与进程代次、稳定事件 ID、同流序号、事件类型、发生时间和到达时间。重试沿用原 ID 和发生时间。Unity Analytics 也说明网络确认失败时可能重发事件；下面的去重策略是本文的项目约定，不假设 SDK 会替你完成。[Unity Analytics FAQ](https://docs.unity.com/en-us/analytics/faq#events)相同 ID 和业务载荷去重；同一 ID 出现冲突载荷要标异常，不让“最后到的那条”改写已知边界。进程重启或账号切换要换流；旧流的最后一条不能直接连到新流的第一条。

同一设备流用单调时间和序号判断间隔、先后及重放。跨设备求并集则要把端点映射到同一时间轴。例如在一次校时握手中记录单调时刻与对应的 UTC 估计，再把同段后续事件的单调差加到这个 UTC 基准上；同时保存网络时延带来的误差与校时期限。不能直接比两台设备启动后经过的毫秒数，也不该拿上报时间当发生时间。Android 的 `elapsedRealtime()` 从开机计、包括深度睡眠；这不是一种“正在游玩”的时钟，也不是 UTC。映射不可靠时，把对应账号日标成数据不全，或单列设备时长；不要发布看似精确的去重账号时长。[Android SystemClock](https://developer.android.com/reference/android/os/SystemClock)

## 从采样点还原区间

先在同一设备流内按单调发生时间和同刻序号处理，不能按到达顺序改当前状态。这里用以下可调整的估算合同，示例心跳间隔 20 秒，允许衔接的最大间隔为 30 秒：

1. 进入合格状态是该段的第一个采样点；离开前合格心跳更新采样点。两点间隔不超过 30 秒才连成区间。该做法假定短间隔内状态持续，心跳本身并不能证明每秒都有活动。离开是硬边界：可在相同间隔规则下连到这个确定的端点，之后要等下一次进入，旧心跳不能重新打开区间。若明确知道同一客户端流已经换代，就把该时点作为旧流的截断点；不能把新进程的心跳当旧流的续点。
2. 超过 30 秒的间隔不整段补齐，包括“最后一条心跳到明确离开”的长间隔。不外推档在最后采样点收口；敏感性档在收口处向后补至多 20 秒，不能越过更早的已知边界或本次报表的事件时间观察截止。比如 0 秒进入、20 秒心跳、60 秒离开，两个结果分别是 20 秒与 40 秒，不会仅凭这条离开消息算出 60 秒。若两档差很大，先看丢报和生命周期链路，不急着把变化归因于玩法。
3. 每个区间都写成 `[起点, 终点)`。保留跨日事件上下文先重建，再按业务时区的两个相邻日界截取；只捞当天心跳会漏掉跨日那一段。日界按指定时区的日历算，遇到夏令时不是每天都长 86400 秒。
4. 每个账号日将裁好的区间按起点排序。下一段起点不晚于当前合并段终点，就把终点取两者较大值；否则输出当前段、另起一段。最后只加合并段的长度。如果想回答“设备总投入”，才在设备内先并集、再按设备求和。

这两档是同一批记录在两种尾部假设下的**估算**，不是对真实游玩时间的置信区间或上下界。若前台进入消息丢了，本合同不会用孤立心跳推断进场；这个选择减少误记后台，但也漏记合法会话，应单独统计此类缺口。

## 同一段重叠算几次

下表用同一条时间轴上的秒数。A 在 60 秒明确离开，180 秒再进入；B 的结束消息缺失。进入记录已算该段的首个采样点。

| 设备 | 发生时刻及类型 | 不外推的区间 |
| --- | --- | --- |
| A | 0 进入，20、40 心跳，60 离开 | `[0,60)` |
| A | 180 进入，200、220 心跳 | `[180,220)` |
| B | 190 进入，210、230 心跳 | `[190,230)` |

直接按设备相加是 140 设备秒；按账号做并集得到 `[0,60)` 和 `[180,230)`，即 **110 账号秒**。允许最多补 20 秒时，A 末段补到 240，B 补到 250，并集为 **130 账号秒**，A 的第一段不补进后台。若 230 的同 ID 心跳重发，结果不变；若是之前没收到的 B 的有效 250 秒心跳，旧窗口要重算，不外推档变为 **130 账号秒**。

## 晚到要改旧窗口，而不是改玩家历史

实现时可把原始事件和 `账号×业务日×指标版本` 的输出分开保存。先发布暂定值，分别注明纳入了哪一时刻前收到的数据、估算截至哪个发生时刻。在可修正期内按受影响的设备段与账号日重算，替换旧结果，而非把晚到心跳的“增量秒数”直接加上去：新收到的离开事件可能让结果**缩短**。离线补传横跨日界时，受影响的可能不止到达日。在窗口标明最新版本、允许迟到多久和之后走人工回补还是丢弃；将迟到率、未知尾部贡献、无进入记录或已离开却仍称合格的心跳、以及时钟对齐失败比例按平台分别监控。流式处理中，水位线（watermark）是对事件时间进度的估计，不保证旧窗口不会收到数据；迟到事件如何处理是另一项策略。[Apache Beam：水位线与迟到数据](https://beam.apache.org/documentation/programming-guide/#watermarks-and-late-data)

上线前回放切后台后迟到、掉网恢复、手机和平板重叠、版本混跑及跨日边界；对比两档和各端异常率，防止 SDK 发包时机一变，分析就把遥测差异当成玩法效果。上述数字是合成事件的区间计算，不包含设备实测或真实玩家数据。
