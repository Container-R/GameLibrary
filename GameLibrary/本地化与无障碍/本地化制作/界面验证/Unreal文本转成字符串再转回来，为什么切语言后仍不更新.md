# Unreal文本转成字符串再转回来，为什么切语言后仍不更新

菜单刚打开时，文字正确。玩家切换语言，其他提示变了，这一块却仍停在旧语言。检查变量类型，交给控件的明明已经是 `FText`，为什么还会这样？

一个值得追查的地方是：它一直保留着原始文本，还是先把当时显示的内容转成 `FString` 缓存，后来又用 `FText::FromString` 包回来？类型名称重新变成 `FText`，不代表丢失的本地化信息也一起回来了。

本文限定 **Unreal Engine 5.6**，面向实现与检查界面本地化的程序、工具和测试人员。下面用一个原创、未运行的菜单例子说明数据流；不涉及复数、异步加载或自定义文本序列化，也不把某个现象直接诊断成唯一原因。

## 当前显示的字，不等于还能生成下一种语言的文本

`FString` 保存字符序列。`FText` 则可以携带支持本地化的信息；Epic 将其中用于按文化设置重建文本的机制称为 **text history（文本历史）**。[1] 这里不是指编辑器的撤销历史，也不是保存所有旧译文。

以可本地化的文字条目为例，Namespace 与 Key 标识它是哪一项内容，Source String 是翻译的基础。显示为同一句话的两个条目，可以有不同身份，未来也可能需要不同译文。[1] 只拿到当前画面中的几个字符，无法反推出这些信息。

`ToString()` 取出的结果不携带原来的本地化数据；`FromString()` 根据普通字符串创建文本，也不会恢复它们。[2] 因此，下面的示意数据流不能当作无损往返：

`原始可本地化 FText → 当前显示字符串 → 缓存 FString → FromString → 新 FText`

最后的对象可以被文本控件显示，却不再因为“原对象曾经可翻译”就自动获得原条目的身份。症结是中途只留下了结果，而后续仍希望它像保留了来源的文本一样工作。

## 先把缓存放在哪里说清楚

假设项目已有一条菜单提示，英语与中文译文都已接入，并且直接使用原始 `FText` 的控件已经确认能正常切换。我们给这条假设内容起名为 `OriginalPrompt`，不在本文提供资源创建或打包教程。

在初始语言下，界面数据层准备三种值：

| 路线 | 数据层保留的内容 | 面板从哪里取文字 |
|---|---|---|
| A：保留原文对象 | 原始 `FText` | 直接使用该 `FText` |
| B：保存显示快照 | 一次 `OriginalPrompt.ToString()` 得到的 `FString` | 每次用 `FText::FromString(Snapshot)` 包装同一份快照 |
| C：刻意不翻译 | 虚构玩家名 `Rin_42` | 用 `FText::AsCultureInvariant` 表明它不参与本地化 |

表中的 `Snapshot` 只是本例保存 `FString` 的变量名，不是UE的 `FTextSnapshot` 辅助类型。

路线B的快照保存在比面板活得更久的数据层中。关闭、重开面板时，**不重新从原始提示获取当前文字**，而是继续使用这份缓存。这个条件很重要：若每次重开都重新取得当前译文，那是另一条数据流，不能拿它说明旧快照自己恢复了本地化能力。

按文档机制推演，在没有其他刷新或替换逻辑、使用非编辑器构建的条件下，B不能凭这次普通字符串往返找回原条目。A保留了本地化所需的信息，但它是否实际更新仍取决于资源和控件接线；C不随语言改变则符合本例需求。玩家名不应仅因显示在界面上，就被当成需要翻译的内容。[1][2]

这不是运行结果表。它把需要比较的三种意图分开：继续随语言生成文本、保留某一刻的显示内容，以及刻意保持不变。后两者看起来都可能“不更新”，但并不一定都是缺陷。

## 怎样检查，才能不把所有旧语言都归咎于转换

可以把上述三条路线安排成一个小型对照检查。以下步骤尚未执行：

1. **先建立可工作的基准。** 选一条已具备两种明显不同译文的提示，先确认A在目标构建和控件上能切换。如果A也不变，先查译文是否存在并被加载、语言设置是否生效、控件是否更新，不急着把原因归到B。
2. **在切换前记录快照时点。** 确认B只在初始语言下取过一次字符，之后没有被其他绑定、回调或面板重建悄悄替换。否则比较的就不是同一个缓存问题。
3. **改变的是language，不只看locale。** UE把译文选择使用的language，与数字、日期等格式使用的locale区分开。[3] 只改变格式地区，不能用菜单词句未变来判断本地化故障。记录实际值，而不是只记录设置页按钮被点过。
4. **比较当前面板与重新打开后的面板。** 若B仍从旧快照取值，重开并不会给它补回原身份。若重开后变了，要查它是否重新从原始文本生成了快照，不把这个结果误读成普通往返无损。
5. **保留不该改变的对照。** 核对C的名字仍原样显示，避免修复时把所有字符串都塞进翻译查找，改变原本正确的不翻译内容。

还要记录使用的是哪一种运行方式。Epic说明，PIE和UMG本地化预览并不总能完整代表运行时状态：PIE和UMG本地化预览本身只加载本地化数据，不改变language或locale设置；文档建议用Standalone核对实际表现。[3] 不过，从编辑器启动Standalone也不能仅凭名称就当成“非编辑器构建”。测试记录应说明构建类型与启动方式，避免把下面的编辑器差异混在一起。

## 编辑器里能变成本地化文本，不代表恢复了原身份

Epic对 `FromString` 明确区分两种情况：非编辑器构建中，它与 `AsCultureInvariant` 的行为相同；编辑器构建中，它不会给文本打上culture-invariant标记，因此赋给保存资产的 `FText` 属性后，仍可能成为可本地化文本。[2]

这个区别不能省略，也不能反过来用它证明往返无损。“后来能成为一项本地化内容”和“仍然是原来的那一项内容”是不同结论。普通显示字符串没有携带原Namespace、Key和历史，不能仅凭重新保存一个资产，就宣称恢复了它们。

因此，排查时不要只问最终变量是不是 `FText`。还应问它从哪条原始数据创建、何时经过字符串边界、是否进入过资产保存流程，以及项目准备交付的构建采用哪种行为。本篇没有验证任一资产导入或保存流程。

## 把转换留在真正只需要字符的边界

如果界面需要随语言变化，优先让数据层继续保留原始 `FText`，将它传到需要显示文本的位置，而不是先存一份显示字符串再到处重建。若项目缓存的是最终显示内容，就应明确谁负责在语言或源内容改变后重新生成它，不能期待 `FromString` 替缓存恢复已经丢掉的意义。

这不等于禁止使用 `ToString()`。外部接口只接受字符串、或者底层输出已经不再需要本地化信息时，取出字符是合理边界。[1] 关键在于上层是否仍保留原始文本和更新责任；如果再返回界面时只剩那份旧字符，就需要重新设计数据流。

也不要把本文推成“凡是字符串形式都一定丢失信息”。Epic另有 **Text Value Marshalling**，用包含文本信息的表示进行编组，而不是只保存给人看的结果。[1][2] 这是与普通 `ToString`／`FromString` 不同的路径。本文没有核对完整接口兼容性，不提供可直接采用的存档或网络序列化实现，更不建议自己拼出几个字段就宣布等价。

修复后的验收仍要回到原始需求：应该变化的提示是否在当前面板和重开后都取得正确译文，刻意保持不变的玩家名是否未被改写，数据层是否仍在重复保存旧快照。由字符串重新包出一个对象，只是一次类型转换；要让文本继续随语言工作，还得保留它赖以重建的来源。
