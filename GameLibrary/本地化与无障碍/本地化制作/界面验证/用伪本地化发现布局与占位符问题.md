# 用伪本地化发现布局与占位符问题

任务面板显示“收集钥匙：2 / 10”，下面是“领取奖励”按钮。中文恰好装得下，团队便按这个宽度完成了界面。等较长的译文到来，进度数字被挤出面板，按钮只剩半句话；另一个界面更糟，数字直接变成了 `{count}`。

这些问题不必全部等正式翻译完成才发现。**伪本地化**是按规则把原文变成测试用文字，例如加明显标记、替换部分字符或扩展长度，让原本不易看见的接入和布局问题暴露出来。它不是生成译文，也不是模拟所有语言。

本文面向用户界面程序、美术、本地化与测试人员，以这个任务面板说明怎样保住动态参数、看懂测试结果，并把伪本地化与真正的语言验证接起来。以下面板及变换示意为原创说明，未在实际游戏中运行。

## 先让测试文字走真正的本地化路径

假设任务文本在字符串表中保存为：

```text
收集钥匙：{count} / {target}
```

字符串表是按条目保存原文与各语言文字的资源；`{count}`、`{target}` 是运行时填入数值的位置，称为**占位符**。这里用命名占位符说明概念，不暗示所有格式库都接受完全相同的写法。

当 count 为 2、target 为 10 时，玩家应看到“收集钥匙：2 / 10”。伪本地化应作用在这条实际使用的消息路径上，而不是另外造一张只供预览的图片。这样才能观察任务面板、更新后的进度、弹出的奖励提示是否真的使用了本地化资源。

例如，可以给显示文字加首尾标记，再增加测试用文字：

```text
[收集钥匙——测试扩展：2 / 10]
```

这是预期外观示意，不是某个工具的实测输出。首尾标记能帮助看出文字是否被截掉，明显变化则让未经过同一路径的文字更容易被发现。Unity Localization 的伪语言资源就是从 String Table 取值并按需变换的一种具体实现。[1]

不要在所有界面文字最终赋值的地方，无条件统一“变花”。否则程序里硬编码的文字也被加工，反而掩盖了它没有进入字符串表的问题。屏幕上某个标签没变，也先当作待查线索：它可能是硬编码，也可能是图片里的字、刻意豁免的产品名、动态参数，或者缺表后回退的内容，不能只凭外观立即定罪。

## 占位符里有程序要读的语法，不能当作正文装饰

对任务消息做扩展时，“收集钥匙”可以变化，但 `count` 不能随便改成另一串字符。程序仍然按原参数寻找值；名字被改坏后，即使大括号成对，参数绑定也可能已经失效。

因此要分开看三件事：文字是否变长，格式是否仍能解析，以及值是否填进正确位置。比如把 count 和 target 交换，可能仍然得到合法的“10 / 2”，却不符合这条任务消息的含义。没有报错不等于消息表达正确。

对简单消息，可以先用两个明确不同的数检查位置，再换成长数字检查布局。如果参数是道具名，还要使用一个较长的合法名称；只测试短数字，发现不了名称挤压。缺少参数时也应能定位到原条目，而不是把原样留下的 `{count}` 当正常测试文字继续放行。

有些消息还带富文本标签，用来控制颜色、字号等。例如数字需要着色时，标签名和属性是文本组件的语法，不是玩家要读的内容。它们也需要按实际格式保护；参数里出现 `<` 或大括号时，应按项目约定转义或作为文本处理，不能意外变成控制标记。

Unity 的 Preserve Tags 可以让指定分隔符围住的部分不被后续方法修改，但这并不等于它是任意嵌套消息或富文本的完整解析器。[2] 不宜临时写一个“找最近一对大括号”的替换规则，就声称所有占位符已经安全。

## 分别检查长度、字形和方向，不要一次制造所有变化

先只加首尾标记，确认任务文字作为一条完整消息显示。若界面出现多个分离的标记，值得追查是否把句子拆成“前缀＋数字＋后缀”分别拼接。不同语言可能需要改变顺序；把整条意思交给本地化，比要求译者适应固定拼接位置更有空间。国际化组件库 ICU（International Components for Unicode）的消息指南也强调完整消息与包含完整句子的分支有利于翻译上下文。[3]

接着单独增加长度。观察任务面板有没有裁切、数字是否仍在、按钮是否盖住相邻控件，以及文字换行后能否保持可操作。短按钮和长句要分别看，不能用同一个扩展比例代表所有翻译。W3C 指出短文本可能有较大的相对扩展，字形宽度、高度及不可断的长词也会影响空间需求。[4]

这里要看的不是字符总数，而是实际字体在容器里的占用。修复也未必是把字号一路缩小：可以考虑让容器伸展、允许合适换行、调整按钮布局，或由内容人员确认更合适的表述。若选择省略号，还要确认省略的部分是否恰好是玩家作决定需要的信息。

再用明显字符替换检查字体。出现方框或缺字，说明当前测试字符没有被正确呈现，值得查字体资源或回退；但一组带重音的拉丁字母能显示，不代表汉字、阿拉伯文字或其他文字系统都完整支持。应在目标分辨率和界面缩放下看，而不是只看表格编辑器里的预览。

即使字体覆盖清单里的每个码点都能查到，也还没有回答整串文字怎样显示。**码点是文本中的编号，字形是字体中用于呈现文字的形状**，两者不必一一对应。以 FreeType 2.13.3 为例，在已成功选择 Unicode 字符映射表（charmap）的前提下，单码点查询得到非零字形索引，只表示该映射有对应条目；它没有给出整串所需的字形选择和相对位置。[7] 这不是让界面作者逐个调用底层接口，而是提醒程序与内容人员：覆盖清单和实际文字呈现检查回答不同问题。

比如，一个测试字符串包含基字符和随后出现的组合标记。即使分别查到两者的字形，也仍需知道标记应放在基字符的什么位置；仅把两个初始字形像普通字符一样并排，不能证明组合正确。字形塑形（shaping）会结合文本上下文、字体、文字系统和语言，选择并定位这一串所需的字形。[8] 具体是保留多个字形、调整位置还是发生替换，要看实际规则，不能规定每一对字符都必须合成一个字形。

字体回退也要放回这条实际处理路径里看。HarfBuzz 的塑形调用使用传入的字体和文本片段；一次调用本身不证明项目已经正确组织了多字体回退。[8] 若缺字后换用了另一份字体，应继续确认文本组件怎样选择字体、保留所需上下文，以及目标字符串的组合位置是否正确，而不是把“回退名单已配置”当成完成。这里不要求团队自行重做排版引擎；应检查正在使用的组件，而非用已有 ICU 格式化或双向索引结果代替字体呈现检查。

最后才考虑独立的方向模拟。Unity 的 Mirror 方法反转字符串，可用于初步观察方向相关的布局假设。[2] **反转英文不是阿拉伯文**：实际从右向左文字还会与数字、标点、拉丁名称混排，并涉及字形连接、光标和选择行为。这些要用真实目标语言与实际文本组件验证，不能靠镜像后的外观宣布完成。

如果你正在接入底层双向文本库，可选读[双向文本的索引映射为何不能直接用来重排字符串](../文字排版/双向文本的索引映射为何不能直接用来重排字符串.md)。它解释一个含表情的字符串为何可能在逐码元复制时损坏，不是完整的从右向左语言支持教程。

上述配置分开做，是为了知道失败来自哪里；需要组合压力时再组合，并保存所用配置。不是要求项目永远只测一种变换。

## 有复数和选择分支时，要用实际格式器检查

“收集钥匙：2 / 10”还比较简单。如果英文奖励提示要根据数量显示不同句子，消息可能包含复数分支。ICU MessageFormat 的 `plural` 和 `select` 可以包含嵌套子消息，撇号还涉及引用规则；Unity Smart Strings 则基于修改版 SmartFormat，具有自己的选择器和格式器。[3][5] 两种工具都使用大括号，不表示语法兼容。

若自定义伪变换，应尽量由对应语法的处理方式识别“显示文字”和“控制结构”，只改前者；处理后再交给项目实际格式器检查。若缺少可靠的结构处理能力，就明确限制支持范围并人工复核复杂消息，不要静默把不认识的嵌套当作普通文本。

测试不仅要确认能解析，还要用代表参数走到需要的分支，核对实际句子。例如一个分支本来该表达“一把钥匙”，正文却被换成“多把钥匙”，格式器仍可能正常工作。正式译文也不能机械要求占位符顺序或全部分支与原文一模一样：目标语言可能需要重新排序和不同的复数类别。代表输入应按目标语言、实际数字格式与业务范围挑选，不能把源语言的少数整数当作全部覆盖。合法的回退正文也可能漏掉这条消息原本需要表达的区别；反过来，项目允许几个类别共用正文时，缺少独立分支不必然是翻译错误。

还要确认参数表示“总数”还是“剩余数量”。例如一条组队提示的 `count` 已经包括领队，且业务只允许至少一人的整数。下面是传统 ICU MessageFormat 的简化诊断消息，不是正式多语言资源，也没有在本次研究中运行：

```text
{count, plural, offset:1 =2 {领队和唯一一名队员} other {领队和#名队员}}
```

这里的 `offset:1` 不能理解成先把所有地方的 count 都减一。显式 `=2` 先比较原始总人数；没有显式匹配时，复数类别才根据减一后的数选择。本例只提供 `other` 回退，所以总人数为 2 时选第一段，总人数为 3 时选第二段，里面的 `#` 表达 2 名队员。若先减一再匹配 `=2`，三人队伍反而会被写成只有一名队员。[6] 要检查的不只是文字能否解析，还包括选了哪段话、显示数量是否符合参数含义。

`#` 的这项替换限于当前复数子消息内未被引用、且不在嵌套参数中的位置；普通 `{count, number}` 仍格式化原输入，不能机械替换 `#`。如果程序已扣掉领队，再用 `offset:1` 就会重复扣减。正式资源仍要由目标语言人员安排需要的类别与句子；这个简化例子不验证其他语言、分数或实际界面，也不适用于 MessageFormat 2 或 Smart Strings 的同形语法。[6]

已有旧正文记录过有限 ICU 格式化样例：把语法关键字一起变换会产生语法错误；只改变显示正文可以保持可解析；交换分支正文则可能解析成功而意思不符。另有英语与阿拉伯语诊断标记的有限分支检查。这些仅是格式选择层的历史结果，不是 Unity 集成、真实译文、字体或双向显示结果；本次没有运行格式器，也没有用它们扩大呈现覆盖。

需要接入 ICU 的程序人员，可选读旧资料的[接口状态与对象释放说明](https://github.com/Container-R/GameLibrary/blob/1a7bf18b24ba56395892c4c0cdb3b2acecc16985/solutions/localization/pseudo-localization-contract.md#实际补充四个-icu-messageformat-输入)，不要仅凭返回了对象就判断格式化成功。需要为目标语言补测试输入时，则看[复数分支与合法回退的区别](https://github.com/Container-R/GameLibrary/blob/1a7bf18b24ba56395892c4c0cdb3b2acecc16985/solutions/localization/pseudo-localization-contract.md#目标-locale-的分支覆盖合法回退不等于满足消息意图)。其中已发表的样例只检查有限整数；分数、输入写成 `1` 还是 `1.0` 所涉及的表示与格式设置，并没有由这些样例获得验证，不能借用整数结果代替。它们是可选的程序支持资料，不要求界面作者先学会全部格式器接口。

## 在任务面板里走完一次，而不是处理完字符串表就结束

回到游戏路径：打开任务面板，查看 2 / 10，再让进度变化到新的数值，最后进入可领取奖励的状态。伪文字应在动态刷新后仍然来自同一测试配置，参数没有丢失，按钮和布局也依然可用。若项目支持运行时切换语言，还要看较早的异步加载结果是否把新语言覆盖回去。

发现问题时，保留能让同事找到它的信息：哪条任务、哪个界面、原文和测试文字、使用的参数、字体与缩放，以及问题发生在哪个操作之后。允许录制时可以补截图；不要把玩家输入或敏感参数原样长期收进诊断日志。

修复先分清原因。数字没有填入，应先查格式和绑定；某个固定标签没变化，应查它从哪里来；文本完整但超出容器，再处理布局。否则程序错误产生的一长串 `{...}` 可能被误当作“译文太长”，团队开始调整根本不该调整的按钮尺寸。

测试过程中遇到缺条目、缺表或无法解析的消息，应明确报告。发布版为了不中断游戏采用回退文字，是另一项产品决定；回退到可读原文不代表这条消息的本地化接入已经通过。同样，“处理了一千条字符串”也不代表实际访问了它们出现的一千种界面状态。

## 伪本地化结束后，还需要真正的语言验证

伪本地化能较早暴露空间不足、接入遗漏、拼接限制和语法破坏，却不能判断译文是否自然、任务意思是否准确、文化表达是否合适。正式语言质量检查还要看真实字体、断行、数字日期、复数、混合方向和输入行为。

对这张任务面板，伪文字不截断只是第一步。真正的译文仍要确认玩家能否理解自己收集了多少、目标是多少，以及何时可以领取奖励。界面朗读或其他无障碍支持也有自己的验证要求，不能因为显示测试成功就一起勾选。

把伪本地化当作提前施加压力的方法，而不是一张语言支持证书：它最有价值的地方，是在正式译文到来之前，让内容、界面和程序团队有机会修正那些本来会被短原文掩盖的问题。
