# 玩家昵称为什么会影响旁边数字和标点的顺序

聊天成员列表里有这样一条标签：

```text
Player {name}: 12 points
```

这份英文界面规定整条标签从左向右阅读，昵称在运行时填入。换成从右向左书写的昵称后，程序保存的文字没有丢字，冒号和分数却可能出现在读者意料之外的位置。此时先别反转昵称，也别急着给冒号换位置：应先让排版组件知道，哪一段是玩家的名字，哪一段是应用自己的说明。

下面面向接入文本组件的开发者，沿用这条虚构标签说明行内片段的方向边界，分别讨论 HTML 与受约束纯文本接口。

## 同一行里，昵称和分数是两段不同的意思

双向排版并不是把一整行简单翻转。不同文字有不同方向属性，数字与标点的显示位置还会受上下文影响。应用若只交出拼好的一长串字符，排版算法并不知道“12是应用记录的得分，不属于前面的昵称”。WHATWG 的 HTML 规范就用用户名、冒号和发帖数说明这种问题。[3]

在本例里，应把 `{name}` 作为一个完整片段。昵称自己包含的括号或其他标点仍属于昵称；模板提供的冒号、空格与 `12 points` 留在外层。不要只包住其中几个从右向左的字母，漏掉昵称本身的标点，也不要把后面的分数一起包进去。

这不是规定所有语言都采用这条英文顺序。换语言时，完整标签仍应由本地化资源安排；这里先固定外层方向与模板，单独检查嵌入内容的边界。

## 隔离让两边各自排版，不是替昵称改字

**方向隔离**让一个片段内部的方向处理不向周围文字扩散，周围文字也不进入它的内部方向处理。按 Unicode 双向算法，隔离片段作为整体，对外层次序的影响相当于一个中性字符。[1] 这不表示它固定在某个屏幕坐标，只是让外层不再把昵称内部的强方向字符直接当成自己的上下文。

昵称仍以逻辑顺序保存，再交给实际文本组件排版。不要把显示出来的顺序写回账户名、聊天记录或搜索数据。手动倒序既没有表达这个边界，又可能拆坏字符；强制覆盖所有字符方向也不是同一操作。

接下来要看组件能接收什么：HTML 可以用元素表达边界，纯文本接口可能需要方向控制字符。不能把一种接口的写法直接搬到另一种引擎。

## HTML 中，可以把未知方向昵称放进 bdi

对于HTML，标签的结构可以示意为：

```html
<p dir="ltr">Player <bdi>{name}</bdi>: 12 points</p>
```

这里的 `{name}` 只是占位说明，不是可直接执行的模板语法。实现时应把昵称作为文本填入，不能将未经处理的玩家内容拼成HTML标记。

`bdi` 表达行内方向隔离，未写 `dir` 时默认采用 `auto`，不会像普通元素那样直接继承父元素的方向。[3] W3C的国际化指南也建议：未知方向的运行时片段可用 `bdi`，或给已经紧密包住片段的元素设置 `dir="auto"`；若调用方确实知道方向，则可明确使用 `ltr` 或 `rtl`。[2]

“自动”只是按字符信息判断方向，不是识别玩家的语言或意图。由数字、表情、标点组成的昵称尤其值得另查。这个HTML例子也不表示游戏富文本控件支持 `bdi`；应先核对所用控件的文档和实际行为，而不是把标签原样塞进一个只支持颜色与字号的字符串。

## 只有纯文本时，开始和结束必须配对

Unicode 16.0的固定规则提供了几种行内隔离字符：[1]

- 已知从左向右：LRI，U+2066。
- 已知从右向左：RLI，U+2067。
- 方向未知：FSI，U+2068，按片段中第一个强方向字符判断，跳过嵌套隔离里的内容。
- 结束相应隔离：PDI，U+2069。

因此，在组件确实支持且昵称内容满足限制时，可以把显示用结构理解为：

```text
Player [FSI]昵称[PDI]: 12 points
```

方括号里的名称只是为了让边界可见，实际接口若采用这条路径，需要的是相应码点，不是字符串“[FSI]”。它们也不是给整个段落选方向的替代品。

FSI还有一个容易漏掉的条件：按这里引用的Unicode16规则，如果片段里找不到强方向字符，就按从左向右处理，不能笼统说它一定继承外层方向。[1] 也不能据此推定HTML `auto` 的所有上下文细节都完全相同。选择纯文本路径后，应分别检查有明确方向的名字与只有数字、符号的名字。

## 给任意玩家输入加两个字符，不等于安全封套

上面的结构示意先限定昵称没有换行和方向格式控制字符。若实际允许任意输入，单纯拼接 `FSI + 昵称 + PDI` 还不够：昵称内若已经含有一个未嵌套的PDI，它可能提前结束外层FSI，后面的内容便落到原隔离之外。这是固定规则中隔离配对方式的直接后果，不是本次浏览器观察。[1]

所以项目需要先决定昵称字段允许什么，再选择组件提供的结构化隔离或受约束的纯文本路径。已有格式控制、嵌套和段落边界怎样处理，应有明确政策；不要一面原样接受所有控制字符，一面承诺外面再包一层就不会影响周围。

HTML转义处理标记注入，Unicode方向控制的处理又是另一件事。两者都不能靠“把所有从右向左文字删掉”解决，也不应无差别反转或静默改写玩家的名字。方向隔离更不能替代昵称身份、仿冒风险或权限检查。

## 回到同一条标签检查，而不是只看名字能否显示

接入检查要同时看昵称和它旁边的应用文字：昵称里的标点是否仍跟随昵称，应用的冒号、得分和单位是否仍组成预期说明。可以用不含个人信息的短名字，分别覆盖从左向右、从右向左、混合文字及纯数字；若字段允许格式控制或换行，还需按字段政策检查这些输入，不能跳过后直接宣布通过。

这些是接入时的检查建议，不是已经取得的浏览器或引擎结果。不要仅凭标签里出现了 `bdi` 或FSI，就认定字体、换行、选择、复制及无障碍朗读也已正确。这里解决的是一个更小的问题：让文本组件知道昵称到哪里结束，后面的分数又属于谁。
