# 双向文本的索引映射为何不能直接用来重排字符串

游戏的聊天框要显示从右向左的文字，消息里还带着一个表情。程序拿到双向文本库给出的下标表，按表把原字符串中的元素依次复制到新数组：下标没有越界，每个元素也恰好复制一次。只含普通字母的测试通过了，带表情的消息却变成了非法编码。

问题不一定出在双向算法。**一份正确的位置对应表，不一定能当作字符串的搬运顺序。** 如果表里的下标以 UTF-16 码元为单位，一个表情可能占两个元素；逐个搬运会把它拆开。

本文面向接入文本库、聊天组件或字幕系统的程序人员。我们用 ICU 76.1 的固定接口和一个很小的例子，区分位置查询、生成字符串与实际排版。例子不是完整聊天系统，也不证明某种语言已经正确显示。

## 先分清内存顺序和屏幕顺序

文字保存在内存中的顺序通常是逻辑顺序，也就是输入和处理这段文字所用的顺序。它不必等于屏幕从左到右看到的顺序。双向文本算法处理的正是这种差别：一段文字可能主要从右向左阅读，其中的数字或拉丁文字片段又按另一方向排列。[1]

不要先把整条消息反转，再交给一个本来就负责双向排版的组件。接入前首先要确认职责：组件需要逻辑文本，还是某个旧接口明确要求已经重排的内容？把显示结果写回聊天记录、搜索索引或复制缓冲区，也可能丢掉原本合理的逻辑顺序。下文讨论的是确有字符串转换需求时的接口选择，不是建议所有游戏自行预处理文字。

位置表的用途则不同。某个显示位置对应原文哪里，是“对应关系”；要把一串合法字符写到另一个缓冲区，是“生成内容”。这两件事可能使用同一份双向分析结果，却有不同的保证。

## 一个字符可能占两个数组元素

UTF-16 使用 16 位的**码元**保存文本。许多字符占一个码元；一些字符要用一对码元共同编码，这对元素称为代理对。前一个是高代理项，后一个是低代理项，不能随意交换。[6]

取如下原创测试序列，用十六进制表示内存中的码元，避免网页本身的双向排版干扰观察：

```text
下标       0     1     2     3
码元     05D0  D83D  DE00  05D1
含义     字母   └─ 一个表情 ─┘  字母
```

`05D0` 和 `05D1` 是两个希伯来字母。`D83D DE00` 共同表示 U+1F600；它是一个 Unicode 码点，不是两个独立字符。这个例子有四个 UTF-16 码元、三个码点。这里也没有把码点数量当成最终字形数量或光标停靠点数量。

假设这段文本作为一个从右向左的片段处理，下标从片段尾端向前排列，便得到：

```text
映射表：3, 2, 1, 0
```

若程序把映射当作复制指令：

```text
输出[v] = 输入[映射[v]]
```

结果就是：

```text
05D1  DE00  D83D  05D0
```

每个下标都合法，每个输入元素也只出现一次，但代理对被倒置了。低代理项 `DE00` 不能在这里先于高代理项 `D83D` 出现，因此这不是一个良构的 UTF-16 字符串。问题由错误的适配代码制造，不能据此说双向库损坏了文本。

只用两个单码元字母测试很容易漏掉这个问题。`05D0 05D1` 倒成 `05D1 05D0`，编码仍合法；这个通过的对照并不能证明同一搬运方法适用于补充字符。

## ICU 的两个接口为什么会给出不同结果

ICU 76.1 的 `ubidi_getVisualMap` 返回视觉位置到逻辑位置的对应关系，形式为 `map[visualIndex] = logicalIndex`。固定源码中，普通从右向左片段的映射通过逐一递减逻辑下标填写，没有把代理对合成一个数组元素。相邻的逻辑映射接口说明也明确提醒代理项和组合字符的顺序问题。[2][3]

`ubidi_writeReordered` 则是写出重排字符串的接口。它明确保证多码元字符的完整性；在本例所用的零写出选项路径里，实现从尾部找到一个完整字符的起点，再按该字符内部原有次序复制码元。[2][4] 因而代理对作为整体移动，得到：

```text
05D1  D83D  DE00  05D0
```

两个字母交换了位置，表情内部仍是先 `D83D`、后 `DE00`。这就是“位置表正确”和“逐元素构造正确”之间的差别。

这里采用明确的窄范围：段落级别为 1，默认重排模式，重排选项与写出选项均为 0，不插入或移除控制字符、不做镜像，也没有组合附加符、分行或字形塑形。Unicode 16.0 的属性数据把两个选定字母列为从右向左类型，把表情所在范围列为其他中性类型；固定 ICU 源码是本例分析依据。[5] 不能把这张四元素表当成任意混合文字的通用排列规则。

此外，`[1, 0]` 和 `[3, 2, 1, 0]` 都是倒序后再倒序便恢复原样的排列。仅靠这两个数字结果，不能判断程序究竟调用了“视觉到逻辑”还是“逻辑到视觉”接口；必须检查实际绑定和接口说明。测试数据看起来对，不代表接口方向已经验证。

## 接入时怎样避免把两个问题混在一起

先在代码中说清下标属于什么。变量名 `characterIndex` 往往太含糊：它可能表示 UTF-16 码元、Unicode 码点，或排版系统自己的字形编号。映射还应属于确定的一版文本；原字符串发生变化后，旧位置对应关系不能继续直接套用。

然后按实际需求选择操作。如果需要查询位置，就使用映射的约定，并处理接口可能返回的“没有对应位置”。如果确实需要一份重排后的字符串，就使用承担字符串构造职责的接口，不要靠“所有下标在界内”和“是一一排列”替代编码完整性检查。

在 ICU 76.1 中，插入或移除方向控制信息会影响对应关系、长度和缓冲区容量；某些写出选项也不会同步调整原映射。因此本例长度恰好不变，不代表所有配置都能按输入长度分配空间。[2] 应根据实际配置核对处理长度、结果长度、输出容量与返回状态，而不是把这里的四元素数组直接推广。

`ubidi_writeReordered` 使用分析对象保存的原文本引用，输入在相应使用期间必须继续有效且不能被修改；源缓冲区和目标缓冲区不得重叠。[2] 这些是接入代码的责任，改用正确函数不等于可以省去生命周期和容量检查。

最后，把“生成了合法编码”和“玩家看到了正确文字”分开。这个例子没有字体、阿拉伯文连接形式、组合符处理、换行、选择区域、光标移动或无障碍朗读的测试。保住代理对只是必要的一步，不是完整排版方案。游戏最终仍要通过真正的文本组件，用真实目标语言检查显示与交互。

## 调试这种问题时保留什么

当含表情的文本失败而普通字母通过，先保留最小输入的码元序列、索引单位、调用方向、配置和输出码元，而不是只截一张“显示乱码”的图。若测试把非法序列自动替换成替代字符，错误可能已经被遮住；诊断时应让严格编码检查明确失败。

不需要为了定位这个问题长期保存玩家原始聊天。可以从实际失败条件中构造不含个人信息的短序列，像上面的字母与表情组合，并在回归测试中区分“映射符合预期”“输出编码合法”“实际排版正确”三类判断。每一类都要有自己的依据，不能用第一类的通过代替后两类。
