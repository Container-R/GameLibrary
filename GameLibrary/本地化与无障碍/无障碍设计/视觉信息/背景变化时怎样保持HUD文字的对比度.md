# 背景变化时怎样保持HUD文字的对比度

任务提示“前往北门”在灰暗墙面上很清楚，玩家一转身，文字落到明亮天空前，便像消失了一样。设计稿里的字体、字号和颜色都没有变，游戏也没有漏画文字；变化的是文字背后的画面。

HUD 是 heads-up display，指游玩时叠在画面上的信息显示，例如任务文字、生命值和方向提示。制作这类界面，不能只问“白字是不是足够亮”，还要问：**它与实际背景之间保留了多大差别？背景变亮后，这个差别还在吗？**

本文面向用户界面美术、技术美术和渲染协作者。下面用一个原创、未渲染的任务提示例子，说明怎样把这个问题算清楚，以及计算结束后还需要检查什么。它不是某款游戏的问题诊断，也没有实际玩家阅读结果。

## 黑色背板为什么不一定够黑

给白字加黑色背板，是很直观的处理。完全不透明的黑色会遮住原背景；半透明黑色则仍让一部分游戏画面透过来。所以，同样一块“50% 黑色背板”，放在暗墙和亮天空前，合成后的颜色并不相同。

先区分两个对象：背板本身的颜色，与玩家最终看到的、文字周围的合成背景。计算文字对比时，需要后者，而不是只把素材里的黑色与白字比较。如果团队把白字和背板一起降低透明度，文字也会受到背景影响；那又是另一组条件，不能沿用下面的计算。

Microsoft 的 Xbox Accessibility Guideline 102（XAG 102）专门指出，游戏背景不断变化，画面元素未必在所有情境中都保持足够对比；其建议包括可调整透明度的文字背板、颜色选项和高对比模式。对于非纯色背景，它要求检查与文字对比最低的区域，而不是挑最有利的位置。[1]

这并不要求所有游戏都采用同一种黑框。它给出的实际问题是：这行任务文字会经过哪些背景，而所选处理能否应对那些背景？

## 对比度算的是相对亮度，不是RGB数字之差

这里采用 W3C 定义的对比比值：

```text
对比比值 = (较亮颜色的相对亮度 + 0.05)
           ÷ (较暗颜色的相对亮度 + 0.05)
```

相对亮度用 `L` 表示。在这套定义中，黑为0，白为1；相对亮度相同的两个颜色得到1:1，黑白得到21:1。它不是两组 RGB 通道直接相减，也不是测量显示器实际发出多少光。[2]

对于 sRGB，计算相对亮度时，要先把编码的红、绿、蓝分量转换成线性分量 `R、G、B`，再计算：

```text
L = 0.2126R + 0.7152G + 0.0722B
```

若输入分量 `c` 已归一化到0至1，sRGB 解码规则为：`c≤0.04045` 时取 `c/12.92`，否则取 `((c+0.055)/1.055)^2.4`。[2] 这一步不能省略：材质面板里显示的0.5，可能是编码值，也可能已经是线性值；只看到数字，无法判断该怎样代入。

下面直接使用已明确含义的线性亮度，避免把颜色空间问题藏在算术里。

## 同一块50%背板，在暗墙与天空前会怎样

把例子的条件说清楚：

- 使用标准动态范围（SDR），线性工作空间采用 sRGB 原色，背景不透明，相对亮度在0至1之间。
- 黑色背板按普通“前景覆盖背景”（source-over）合成，背板的不透明度记为 `a`。
- 白色文字本体完全不透明，亮度为1；背板透明度不会同时作用到文字。
- 暂不加入色调映射、曝光调整、后期处理、抗锯齿边缘或量化误差。

这里的线性合成是例子明确选择的条件，不是在宣称所有引擎都会这样处理界面。source-over 的颜色由前景贡献与保留下来的背景贡献相加。[3] 黑色前景贡献为零，因此若原背景亮度为 `Lb`，背板后的亮度就是：

```text
背板后的背景亮度 Lp = (1 − a) × Lb
白字与它的对比比值 C = 1.05 ÷ (Lp + 0.05)
```

让背板不透明度为 `a=0.5`。暗墙取线性亮度 `Lb=0.1`，透过背板后只剩0.05，于是白字对比为 `1.05÷0.10=10.5:1`。

再把背景换成亮度为1的天空，背板后仍有0.5，对比便成了 `1.05÷0.55=21/11`，约为 **1.91:1**。

这两种情况没有更换文字，也没有假设预乘透明度接错。若需要先分清预乘表示与混合工作空间，可选读[预乘透明度与普通透明度的混用问题](../../../技术美术/环境管线/纹理与材质/预乘透明度与普通透明度的混用问题.md)。仅仅因为黑色背板仍让背景透过来，同样的配置就能产生明显不同的对比数值。例中的0.1是已经线性化的亮度，不是8位图片中随手取出的灰度10%。

## 从目标比值反推背板，但别把答案当成通用参数

假设这行任务提示属于 XAG 102 所说的、提供重要游戏信息的标准尺寸文字，我们选择该指南的 **4.5:1** 建议作为本例目标。[1] 先限定这个适用场景，再计算，而不是把4.5套在所有文字、图标和状态上。

在本例允许的背景范围内，白字最不利的情况是 `Lb=1`。要让它仍达到4.5，必须满足：

```text
1.05 ÷ (1 − a + 0.05) ≥ 4.5
1 − a + 0.05 ≤ 1.05 ÷ 4.5 = 7/30
a ≥ 49/60，约为0.81667
```

这给出了**本例理想条件下**的边界。例如取 `a=0.85`，最亮背景经过背板后为0.15，对比为 `1.05÷0.20=5.25:1`。这些结果首先由纸面推导得出，不是引擎输出。

因此，结论不是“所有游戏把透明度填成82%就解决了”。一旦文字也透明、背景或输出经过其他变换、混合在编码值上进行，前提就变了。实际数值还可能受有限精度影响；不能把低于目标的结果向上舍入成达标，W3C 的解释文档也明确提醒阈值不应这样处理。[4]

如果一个假设工具仅能保存8位背板不透明度，也不能随手把边界舍入到最近一级：`208/255` 低于 `49/60`，而 `209/255` 高于它。这只是量化级别的数学比较，不是对某个引擎滑块或 GPU 精度的测试。

完全不透明的黑背板可以在这个例子里隔离背景变化，代价是遮住更多游戏画面。提高不透明度、调整位置或面积、提供可选背景，都涉及信息与画面的取舍，不存在只靠一个比值就能决定的唯一方案。

## 先确认要应用哪条建议，再谈“达标”

XAG 102 对不同内容有不同建议：标准尺寸的重要文字和视觉元素为4.5:1，大尺寸为3:1，不可交互元素上的文字也建议至少3:1；高对比模式另有7:1的建议。其“大尺寸”定义与平台、分辨率等条件有关，不能从设计软件里任选一个字号就宣布属于大字。[1]

W3C 的 WCAG 2.2 是面向网页内容的准则。它的相对亮度和对比公式可用于说明本文的计算，但其最低对比条款对不可交互控件文字有豁免，不能拿这个豁免覆盖 XAG 的游戏建议。[2][4] 同样，完成这一个计算，不等于游戏获得无障碍认证，也不等于整套界面符合某个平台的全部要求。

更高对比也不代表对每位玩家都一定更好。XAG 强调可配置选择，并提醒部分有阅读或认知困难的玩家可能不适应高对比界面。[1] 可以提供清晰的默认方案及调整入口，而不是为了追求更大数字，移除其他合理选择。

## 回到游戏里，要核对哪一层颜色

计算前，界面与渲染两端需要对同一条提示达成一致：文字和背板分别是什么颜色、各自透明度是多少、在哪个工作空间混合，以及界面是在曝光和色调映射之前还是之后绘制。**源素材颜色、混合中间值、最终输出颜色与显示器实际发光，不是同一层东西。**

如果目标是检查玩家会遇到的颜色关系，就不能只比较素材图里的白与黑，也不能拿任意场景像素代替背板合成后的背景。应沿实际输出流程确认文字与相邻背景预期呈现的颜色，再选择与输出条件相符的评价方式。本文的 SDR 算式没有证明 HDR、广色域或显示校准条件下应该怎样计算。

抗锯齿还需要单独理解。文字边缘通常不是全覆盖的白色；不能因此把每个边缘混合像素都硬套为必须达到名义比值的独立文字颜色。W3C 的网页解释允许依据规定的前景、背景颜色评价，同时提醒细字体可能在实际显示中显得更淡。[4] 这既不是随机挑一个最白像素就足够，也不是对游戏截图提出一套已经验证过的测量规程。

对我们的“前往北门”，可先让实现者核对文字和背板是否按预期分别合成，再安排实际可能出现的暗处、亮处和复杂背景检查。一个暗底样稿不够，一张有利截图也不能穷尽动态场景。即便颜色关系符合选定建议，字体、字号、移动画面、显示距离和信息拥挤仍会影响阅读；玩家是否能及时理解任务，还需要适当的实际验证。

这章解决的是一个较窄但可行动的问题：不要把“加了半透明黑底”当作结论，而要弄清它在什么背景范围、什么合成条件下保留了怎样的文字对比。本文没有实际渲染、截图判读或用户测试，也没有借用已有透明度文章的 CPU 数值实验来证明 HUD 效果。
