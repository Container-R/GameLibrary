# 不用长按，怎样让玩家有意地确认丢弃道具

背包里的「丢弃」要求按住确认键两秒。团队加了无障碍选项，把两秒改成零。现在菜单中残留的一次确认就可能丢掉道具：持续施力的负担不见了，暂停下来检查对象的机会也不见了。更好的替代是保留两种操作，允许玩家把**持续按键**换成**不限时的两步确认**，而不是把破坏性操作直接改成单次按下。

这里的丢弃是背包里一次性、不可撤回的命令，不是按住三秒修理、松手取消的持续玩法。如果动作确实还需要三秒世界时间，别用本文消掉玩法耗时；那类设计见[持续按住改点按](把持续按住改成点按时如何保留取消与完成的含义.md)。Xbox 无障碍指南建议为持续输入提供较低负担的替代；它并不规定所有丢弃界面的防误触方式。[1]

## 让第二次动作真的表示同意

先让玩家点「丢弃……」，这一步只打开确认框。标题写「丢弃修理箱？」；正文说明准确数量、无法恢复等后果；两个按钮写「取消」和「丢弃修理箱」，不要都叫「确定」。焦点先放到「取消」或提示文本上，不要直接落在会丢掉道具的按钮；若把焦点放在文本上，仍要能逐一到达两个按钮。玩家可读完再移动到提交按钮，没有要求多久内按第二次、也没有快速双击门槛。默认把焦点放在破坏性最低的动作，是 W3C 模态对话框在难以撤销场景的建议；这是借用交互原则，不是拿网页规则为主机游戏认证。[2]

用目标平台的读屏或屏幕朗读确认打开提示时能获知道具、数量和后果；取消、目标变动和丢弃成功分别有反馈。让确认动作使用玩家当前改键，取消也应可独立到达，不要求组合键。如果允许撤销，有时「先删除，再给一个易到达的撤销」比多道确认更清楚；但没有真实恢复能力时不应把它写成可撤销。

## 权限交给这一个弹窗，不给沿用的按键

用键盘或手柄从一个菜单切进另一个菜单，打开时确认键可能还按着。如果把自动重复的按下交给弹窗，或者同一个事件先触发打开、再触发弹窗内的按钮，玩家就没有做过第二个意图。

| 情况 | 该做什么 |
| --- | --- |
| 第一次激活打开确认框 | 消费这次逻辑激活；把后续事件路由到新弹窗，不再交给父菜单 |
| 键仍按住、驱动发出重复事件 | 不把它变成新确认；等输入回到中立，以后新激活才可送给当前按钮 |
| 同一次启用后来才送达，弹窗已换代 | 旧弹窗 ID 的排队事件不能提交现在的对象 |
| 设备断开、窗口失焦或新菜单覆盖 | 取消这个待确认；恢复后重新同步输入状态，不把丢失的松手当作同意 |

“新激活”可以是按键经历松开后重新按，也可以是可信的无障碍控件激活事件。后者不一定有物理的按下和松开；对同一次逻辑操作仍需去重，并明确派发给当前那个按钮。对鼠标和触屏，由控件按其取消/激活语义处理；不要把它们一律改成指针按下就丢弃。如果焦点在「取消」，确认键应启动取消，即使它是一个新按下，也不直接执行丢弃命令。

## 提交时，还要是玩家刚读到的那件东西

弹窗打开时存一份待确认快照，例如 `(弹窗代次, 道具稳定 ID, 数量与版本)`。如果背包在对话期间重新排序，行下标不再有意义；如果同一 ID 的堆叠从 3 个变成 12 个，也不能沿用“丢弃 3 个”的确认去删除 12 个。提交时由实际拥有道具的规则层检查该快照仍有效，不是 UI 先查一次、随后不带条件地删除。若数量、归属或权限已变，就告诉玩家并让其按新信息重新确认。

联机时可把一次有效提交用唯一请求 ID 标识，绑定身份与操作内容。确认成功但回执丢了，重试同一请求只返回原结果；不同道具不能复用那个请求 ID。真正实现要让检查版本、实际修改和幂等结果在同一权威事务内落地，或用等价的原子机制；下面的内存试件不测试宕机和重试并发。发送以后如果没有取消协议，就别让取消键暗示能撤回已经生效的请求，应显示处理中或最终结果。关闭 UI 与撤回服务端操作是两件事。

## 用这四次操作验收

1. 按住打开键不松，在确认框停留，故意制造重复事件。背包不变。松开以后，先激活默认取消按钮，应退出；重开后显式选「丢弃修理箱」，才应提交一次。
2. 打开 A 的确认框，再让列表滚动或重排。弹窗仍只指向 A；另用道具堆叠版本改变的反例，确认即使 A 仍在原行也不能执行旧命令。
3. 取消或切出应用，再重开一个确认框，让旧确认事件迟到。应被拒绝；读屏与视觉提示应说明当前要处理的是谁。
4. 在联网故障试件中丢弃成功后模拟丢回执。重试不第二次删除，换成不同内容的重复 ID 要被拒绝。无障碍验收另用真实设备及目标玩家测慢速操作、清楚后果和独立取消。
