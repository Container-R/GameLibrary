# 菜单朗读的过期淘汰与操作结果保留

玩家在大厅设置里快速把焦点从A移到B、再移到C。声音还在解释A，字幕设置的保存失败已经返回，匹配倒计时又连续产生了“8、7、6”。把所有文字按到达顺序读完，会让操作落在C，说明却停在A；让每条新消息都覆盖旧消息，又可能只剩“6”，保存失败再也无从得知。

这是一个构造的菜单场景。问题不只是怎样比较文字的重要性，还在于这些信息的寿命不同：焦点描述随导航失效，倒计时数值随时间失效，一次操作的结果却可能在离开页面后仍然有用。**优先级决定先说谁，替代关系决定哪些旧信息可以不再说；两者需要分开设计。**

本文面向熟悉焦点、异步回调和基本队列的游戏UI程序、无障碍设计与QA，给出单用户菜单的应用层做法：保存语义状态，淘汰过期请求，在提交朗读前重新生成内容，并用可回查结果承接被打断的信息。讨论限于设置的完整替换保存和普通大厅状态提示，不覆盖紧急操作期限、战斗听觉或完整存储并发控制。平台部分以Windows UI Automation（UIA）和固定NVDA源码解释接入边界。文中模型没有连接声音设备，不提供已通过读屏或玩家体验测试的保证。

## 先给信息划出可以替换的范围

全局先进先出队列会保留所有过时焦点；全局只留最新会把独立操作结果一起抹掉。简单分成“高、中、低优先级”也不够：同为高优先级的两次失败，可能是同一目标的重试，也可能分别属于字幕与画质，处理方式不同。

可以把菜单里的信息分成以下三类。表中的身份是应用自己的记录，不假定平台会理解这些键。

| 信息 | 应绑定的身份 | 新消息能替代什么 | 离开页面后怎样处理 |
| --- | --- | --- | --- |
| 当前焦点的说明 | 页面实例、控件业务身份、聚焦意图序号 | 已被新焦点替代的旧说明 | 淘汰该实例的请求 |
| 当前匹配状态或倒计时 | 匹配会话、状态修订、页面实例 | 同一有效会话的旧状态快照 | 停止该页面的数值请求；会话本身由匹配系统管理 |
| 保存操作的结果 | 资源范围、用户意图、操作ID | 不凭到达时间覆盖历史；当前摘要可以重算 | 保留仍有意义的结果与回查入口 |

“页面实例”指这一次打开，不是字符串“设置页”。关闭后又打开同名界面，实例已经改变。“聚焦意图序号”在玩家作出新选择时更新，用来拒绝同一页面里迟到的聚焦或文字准备结果。仅检查页面名或对象非空，都可能让旧工作影响新操作。

保存资源也要具体：例如“档案P的字幕设置”，而不是一个叫Save的按钮。不同档案、不同资源或不同字段集合，不能因为提示都叫“保存失败”就合并。同一个用户意图可以有多次尝试；把字号从24改成28产生新意图，重试保存24则仍是在完成原目标。用户在明确终态后发起的新尝试使用独立操作ID，并绑定当时的目标值；同一次操作的重复投递或重复回执仍关联原ID。等待超时但结果未知时，先按原ID确认状态，不把传输重试自动当作新的业务尝试。

XAG106要求焦点移动后停止旧焦点项的未完成朗读，允许取消、重听与调节语速，也要求周期状态提示不干扰其他朗读。[1] 这些目标说明为什么需要淘汰旧信息，但没有替项目规定下面的队列结构或所有类别间的抢占顺序。

## 把操作记录、待播请求和正在输出的内容分开

应用至少需要三种不同的状态。

**操作记录**回答“发生过什么，以及现在确认到哪里”。它由保存或匹配系统的结果更新，不随一次朗读结束而删除。**待播请求**回答“下一次有机会时，应读取哪个对象的什么信息”。它可以被替换或淘汰。**输出记录**回答“这一次提交的是哪段内容，平台是否报告开始、结束或取消”。最后一种记录只有在接入接口确实提供相应信号时才能维护。

一种适用于本例的安排是：焦点说明只有一个当前槽位；每个有效会话只保留一个状态读取请求；操作结果先进入记录，再产生结果摘要请求。待播项可以保存资源ID或会话ID，而不是提前固定“保存失败”“剩余8秒”的字符串。真正准备输出时，重新读取状态，才知道这个失败是否已被重试解决、8秒是否已经变成6秒。

更新流程可以按下面的顺序实现。这是应用层伪代码，不是UIA接口实现：

```text
收到事件：
    先按操作ID或会话身份更新业务记录
    再处理页面实例、焦点意图与待播请求
    丢弃已失效的视图请求，但不丢弃仍有效的业务结果

准备提交一条请求：
    检查它是否仍属于有效页面、会话或可回查资源
    从最新状态生成当前摘要或当前控件说明
    检查生成期间状态是否又变了；变了就重新判断
    为这次输出分配独立token，交给选定的输出接入层

收到输出回调（仅在接口提供时）：
    只更新回调token对应的输出记录
    旧token不能清除新输出，也不能改写操作结果
```

同一套UI逻辑若在一个线程中处理，可以把记录更新、资格判断和提交安排在一个明确的处理阶段。若文字生成、翻译查找或平台提交会异步返回，就把生成时的相关修订一起带回，提交前再核对。这样做针对的是一次状态变化后的旧工作，不是要求每帧把全部队列重建一遍。

对于应用能控制取消与完成的内建朗读，本例选择：新焦点抢占当前输出；被抢占的焦点与普通倒计时请求丢弃，操作结果仍可重新生成；当前焦点完成后，先处理尚需报告的结果，再处理仍有效的普通状态。这个选择优先保持导航反馈，代价是连续导航会推迟结果。遇到必须及时决定的邀请、付款确认或即将失去的操作机会，需要单独制定期限与提示策略，不能直接套用“状态最后说”。

### 用一段完整操作检查身份有没有混淆

下面把同名页面、独立保存与旧回调放在同一条轨迹里。表中的“完成”是内建接入层提供相应信号时的处理；在本文测试中它只是人工注入的占位回调。

| 事件 | 应用记录与待播请求的变化 |
| --- | --- |
| 打开大厅设置p1，焦点A→B→C | A、B的输出请求失效，保留C；每次输出使用不同token |
| 发起字幕保存r1、画质保存r2；倒计时8 | 两次操作分别登记；普通倒计时请求等待 |
| r1失败，倒计时更新为7 | 保存r1结果；7替代同会话的8，不覆盖r1 |
| C完成；随后倒计时又更新为6 | 请求r1的当前结果说明；状态请求仍只有一个 |
| r1说明完成，准备读倒计时 | 按此刻有效截止点重新求值，而不是直接读曾缓存的6 |
| 关闭p1，同名p2打开并聚焦C | 淘汰p1的视图请求；保存操作记录不随页面销毁 |
| p1的旧完成或旧聚焦回调到达 | token或页面实例不匹配，不结束p2输出、不移动p2焦点 |
| r2晚到失败，p2的新字幕保存r3也失败 | 保留两条不同资源/操作的结果；r2明确属于先前画质保存 |

这条轨迹同时说明，**拒绝旧页面回调影响UI，与接受该页面发起操作的业务结果，是两个决定。** 视图可以已经消失，保存仍可能成功或失败；只用一个“页面已关闭”判断把回调全部丢掉，会丢失玩家需要知道的结果。

## 保存失败晚到时，先问当前目标是否还没完成

另以字幕保存为起点看一组尝试：s1保存字号24失败。它的失败说明尚未输出时，s2已经返回。不能仅凭“s2比s1新”就决定是否覆盖，至少要区分以下情况。

| s2的含义与结果 | 对s1历史的处理 | 当前摘要应表达什么 |
| --- | --- | --- |
| 同一24目标的重试成功 | s1仍失败，关联重试s2成功 | 目标已经确认保存，不再要求重试s1 |
| 玩家改成28，随后保存成功 | 原24意图被新意图替换，s1并没有成功 | 当前28已保存；历史保留旧尝试 |
| 画质保存成功 | 不改变字幕s1的失败 | 两个资源分别说明 |
| 新请求仍在等待 | 不记为已补救 | 保存中或结果待确认 |
| 本地等待超时，没有权威终态 | 记录结果不确定 | 不断言“没有保存” |

因此，结果历史与自动摘要可以有不同内容。历史行保留“s1请求24失败”，当前摘要可能已经是“字幕字号28已保存”。当用户主动回查时，再同时提供请求目标、操作结果及后续关联。自动输出不必把每次已过时失败重新念一遍，也不能用一条成功摘要删掉所有失败记录。

保存结果还涉及一个更隐蔽的顺序：请求发起顺序、回调到达顺序、权威端实际提交顺序可能不同。本文的有限模型假设每个资源按完整值替换，保存系统为每次成功提交提供严格递增的修订号与实际接受值。收到较旧修订时，更新对应操作历史，但不把最后确认快照倒退；如果旧意图反而获得更高提交修订，就必须记录它，并指出已存值与当前期望不符。后者需要保存系统的串行化、条件写入或重新核对，朗读器不能修复存储竞态。

请求值与实际接受值也不是一个字段。若请求28而权威端确认接受26，历史保留这两个值，当前摘要不能把这次成功解释成“28已保存”。模型要求成功输入明确给出接受值；没有它的接口必须使用自身的数据契约或重读机制，不能默认用请求值补齐。

例如，s2把28保存为修订11，后来才收到s1把24保存为修订10的回执，最后确认值仍是28。若s1实际后写入并取得修订12，最后确认值就成了24；因为s1来自旧页面就忽略它，会错误地继续声称28已保存。

这个比较依赖接口明示的版本含义。HTTP的ETag是不透明校验值，不保证能按字符串大小排序；If-Match可以把写入约束为服务器上的前提仍成立，但不是所有游戏保存接口都提供此能力。[2] 若接口只报告某次请求成功，却没有足够信息确定当前资源状态，应采用其确认或重读机制；缺少依据时，摘要保留“该次操作报告成功，当前状态待核对”。同一资源还有可能改写它的未决请求时，也不能把已收到的一个成功当成稳定终态。

这里的“最后确认”只覆盖应用已掌握的证据。跨设备写入、字段合并、版本重置和事务需要相应的数据契约；把它们交给一个UI自增序号，并不会得到正确的保存历史。

## 倒计时要在提交时重新计算

时间0收到剩余8秒的状态，朗读队列一直被焦点与结果占用，到2.4秒才准备提交。即使没有新tick事件，缓存的8也已经过期。若该会话的有效截止点是8秒，提交时剩余5.6秒；本例按与视觉显示一致的向上取整规则生成6秒。实际项目采用什么取整和措辞，应与界面含义一致。

待播请求只需指向页面实例与会话。提交时读取当前状态和截止点：会话已换、页面已离开或权威状态已取消，就淘汰；会话仍在计时，再计算剩余量。较旧状态修订不能覆盖后来调整的截止点。截止点已经过去但尚未收到开始确认时，停止报旧数字，不把算出的0直接变成“游戏已开始”。有必要时，另提供“等待开始确认”这样的状态说明。

会话内的tick序号不足以确定当前会话。新会话已排队“20”，旧会话后来送来自己的较新tick“7”，也不应覆盖20。本例由匹配系统提供当前会话绑定及其递增修订，仲裁器先检查绑定，再检查会话内序号；切换时淘汰旧会话的待播请求，并在应用拥有取消能力时停止其占位输出。绑定本身若异步到达，也须拒绝旧修订，不能由“最后收到哪个tick”推断会话切换。

暂停是否冻结倒计时，由业务决定。本地可暂停计时器可以在暂停时记录剩余量，恢复时以当前时刻重建截止点；服务器大厅计时不一定随本地菜单暂停。Python的monotonic时钟原点没有定义，只保证适合比较同一时钟域内的差值，不能直接减去服务器UTC时间戳。[3] Windows QPC独立于UTC，并计入待机、休眠时间，也不会自动服从游戏暂停。[4] 跨时钟换算及网络误差应由匹配或时间同步系统提供。

重新计算保证的是请求生成时的新鲜程度。外部读屏可能稍后才开始播报，应用又未必能撤回已经提交的消息。对于很短的剩余时间，单纯提高数值更新频率可能增加积压；应结合实际输出延迟与消息长度，判断是否使用更简短的阶段提示。不能从一次算例推出适用于所有语速和译文的安全秒数。

## 取消、重听和回查要各有明确含义

“停止朗读”只处理输出，不取消保存操作。否则玩家只是嫌说明太长，就可能意外改变业务结果。对于应用可控制的内建输出，可以取消当前token，并让这次明确停止抑制该项的自动重播，直到新的相关事件或玩家主动重听；不要让调度器下一帧把刚停掉的内容立即放回来。用新焦点打断结果与用户明确停止结果，是两种不同原因，不能共用一个无条件重入队分支。

“重听当前项”应读取当前焦点及其最新值，不从全局“最后说过的话”恢复旧控件。若值或语言已经变化，重新生成说明。“查看操作结果”则进入有明确名称的结果区域，提供资源、目标、状态和可用动作；返回后再接回原来的有效焦点。结果到达时不必先抢焦点才能让人知道，W3C的状态消息说明也讨论了不改变用户上下文的通知方式；这可作为交互参考，不等于本文方案通过网页或游戏平台认证。[5]

连续导航可能让结果长期排不到，所有结果都不打断又要保证每条在有限时间内说完，在单通道下无法无条件兼得。本例选择保留导航响应，并提供当前状态摘要与结果回查。产品仍需决定哪些结果值得稍后主动提示、哪些可以合并，以及历史保留多久。合并应作用于同一资源的当前摘要；不能仅因达到队列容量，就悄悄删除未处理失败或把不同操作算作同一条。

对于高频生产的后台事件，先在业务侧减少无行动价值的通知，再控制自动播报频率。若结果数量已多到无法逐条听取，可以提示“有待处理结果”并提供可访问入口，但入口必须真实可用。它不是把重要信息永久放进一个玩家找不到的日志。消息开始、被打断或回调完成也不等于用户已经理解，不应据此销毁业务记录。

## 外部读屏不能冒充应用拥有的播放队列

内建TTS与外部读屏的关键差别，是谁掌握已经提交的输出。内建接入若能可靠报告开始、完成与取消，应用可以按token维护当前输出，并在打断后重新生成仍有用的结果。没有可用播放进度时，重播可能从短消息开头开始；一条操作历史对应两次输出请求是合理可能，不能承诺一次且仅一次可听。

UIA的UiaRaiseNotificationEvent接受provider、处理偏好、显示文字和activityId。activityId用于标识动作或动作组；成功返回S_OK表示函数调用成功。客户端的通知回调接收这些信息，也没有因此成为发送方的“玩家已听完”回执。[6] 应用可以在提交前过滤过期信息，不能凭空给提交后的外部队列维护一个准确busy状态，也不能把activityId当作已验证的定向取消句柄。

NotificationProcessing区分全部保留、只留最新、让当前完成后接最新等偏好。ImportantAll本身有信息洪泛风险；ImportantCurrentThenMostRecent还带有Windows build 26100的引入条件。[7] 枚举描述不等于每个客户端都实施了相同队列，更没有在这些页面中给出足以保证按应用替代键隔离的协议。

一个具体反例来自NVDA在2026-10-19的固定提交。其UIA基类默认处理器接收但不使用activityId分组；MostRecent与ImportantMostRecent进入同一分支。非say-all路径调用speech.cancelSpeech；ImportantCurrentThenMostRecent被映射到优先级NEXT，而没有实现同源“当前加最新”的压缩。[8] 沿取消路径读取speech manager，可以看到它取消合成器并重置优先队列，而不是仅按某个activityId移除旧项。[9]

因此，把每秒倒计时都发送为MostRecent，可能影响同一manager中的其他内容，而不只是更新自己的旧数字。这是固定源码路径的推导，不是本文试听到的游戏故障；应用模块、子类、插件、say-all状态和安装版本都可能改变路径。它足以说明：**替换键与优先级先在应用内成立，再验证目标客户端的实际行为；不能只完成一张语义种类到枚举的映射表。**

外部路径还可能同时输出盲文，不能把它视为只有声音的播放器。[8] 当游戏同时提供内建朗读与外部读屏时，应明确让玩家选择输出方式并验证切换，避免两个自动播报路径重复同一信息。不能仅凭检测到一个进程就断定读屏已接管，也不应为消除重复声音而移除仍供其他辅助技术使用的控件语义。

## 检查完整任务，而不是只看通知函数返回

本文使用两个原创Python模型检查不同层次：仲裁模型以人工完成回调重放焦点、独立结果、关页重开与打断；业务模型以人工权威回执和时刻检查结果因果与倒计时求值。有限输入中，旧token没有结束新输出，独立结果没有被倒计时覆盖；同目标重试与新意图替换得到了不同历史关联；较旧保存修订未倒退已知状态，旧意图实际后写入则被显露；倒计时在提交时更新，并在到期、取消或会话失效时淘汰。这些模型没有连成真实产品输出管线，也未实现显式停止、重听或可访问结果面板；这些交互仍属于待接入验证的设计。

接入项目时，可沿开篇操作同步记录三层事实：

1. **应用决定：** 当前页面/焦点意图、操作或会话身份、状态修订、为什么替换/淘汰，以及提交时生成的文字。
2. **接口事件：** 发给哪个输出路径、请求参数、返回值；若用UIA观察器，再记录其收到的sender与activityId。观察器收到事件仍只说明事件可见。
3. **实际输出与操作：** 哪段开始了、何时被打断或遗漏、玩家下一次输入实际作用于谁。内建回调与外部读屏试听分别记录，不能互相代替。

让测试人员在结果排队时关闭并重开页面，再让旧保存回执返回；随后重试同一目标、改成新目标，检查当前摘要和历史是否一致。另让长焦点说明拖过倒计时截止点，确认不会读旧数字或误报已开局。最后验证明确停止不会马上自动重播，重听读的是当前项，结果区域可进入、可理解、可返回。仅听到一条“保存成功”，不足以通过这条完整任务。

不同语速、长译文、输入方式、内建与外部输出切换，都可能改变信息积压和操作负担。需要目标平台运行和相关玩家参与的任务验证，才能判断提示是否足够及时、是否容易找到结果。本文的可迁移部分，是把信息寿命、历史事实、当前摘要和输出能力分开；能否让人顺利完成菜单任务，还要由真实接入证据回答。
