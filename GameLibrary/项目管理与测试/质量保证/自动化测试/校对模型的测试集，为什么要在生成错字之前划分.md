# 校对模型的测试集，为什么要在生成错字之前划分

团队准备训练一个对白校对模型：拿已经校对过的台词，人工替换几个字，把原句与错字句一起交给模型学习，再留出一部分检查效果。训练集与测试集没有完全相同的字符串，看起来已经分开了。但如果测试中的错字句，恰好来自训练时见过的原句，这次检查究竟是在考“新台词”，还是在考“熟悉台词的另一种写法”？

本文面向准备或验收模型辅助检查工具的测试人员、工具程序与内容协作者，解释这种划分错误如何发生，以及怎样保留原句与变体之间的关系。这里的**训练集**用于学习模型，**验证集**用于选择设置，**测试集**用于最后评估。本文不训练模型，也不提供校对准确率；下面的中文台词是原创构造例子，只用于核对数据划分。

## 要留出的不只是字符串，还有它的来源

从一条原句生成多个替换、删除或插入字符的版本，是一种数据增强：增加可供学习的样本，但这些样本仍有共同来源。假设我们要检验工具处理“没有参与本次训练的新原句”的能力，那么留出一个错字字符串还不够。它的正确原句和其他变体如果出现在训练中，就已经把与测试高度相关的信息交给了模型。

这不是说模型一定记住了每条台词，也不是说结果一定提高多少，而是测试条件与要回答的问题不一致。模型可能利用熟悉的词序、句式或原句恢复关系；即使得到高分，也不能直接把它当成对未见原句的表现。

Cygames 在 CEDEC2022 的对白错字检测报告中展示过这个具体问题。讲义第21–22页说明按游戏中显示的一行准备原文和加入错字的文本；第35页对比两种流程：旧版先加入错字，再洗牌划分训练与测试，图中明确指出两侧包含同一原句派生的文本；新版先把原始剧本划分为训练用与测试用，再各自加入错字。[1] 这里借用的是划分机制，不是复现作者的模型。

## 八个不同字符串，仍可能没有留出新原句

给四条原句各造一个改字版本，保留来源编号。下表的“改字”只是本例设定的扰动，不能当成脱离上下文的通用错字判定规则。

| 来源编号 | 原句 | 改字版本 |
|---|---|---|
| A | 请把钥匙交给守卫。 | 请把钥匙交给守位。 |
| B | 桥边的灯已经亮了。 | 桥边的灯已经凉了。 |
| C | 钟响以后再打开城门。 | 钟响以候再打开城门。 |
| D | 先把地图收进背包。 | 先把地图收进背抱。 |

现在按下面方式分成两组：

- 训练：A原句、B改字、C原句、D改字。
- 测试：A改字、B原句、C改字、D原句。

两组各四条，各有两条原句与两条改字句，字符串完全没有重复。但把每条样本追溯到来源后，两组都包含 A、B、C、D。测试没有留出任何一个新的来源编号。**行数平衡、类别比例相同、字符串去重，都没有解决这个问题。**

改成先划分来源：A、B归训练，C、D归测试，再把每条原句及其改字版本放进所属一侧。两组仍各四条、各含两条原句和两条改字句，但训练来源是 A、B，测试来源是 C、D，交集为空。

真实项目不必照搬这个微型例子的比例。只有四条原句也不足以形成有意义的模型评估集。它展示的是两个不同检查：字符串是否重复，以及已知来源是否跨集。

配套的[原创集合检查脚本](../../../../管理档案/研究记录/proofreader-source-split/check_split.py)下载后可用 `python3 check_split.py` 运行，不依赖机器学习库。它构造这八条文本，核对两种划分的条数、标签数量、字符串交集和来源交集，并与[记录的输出](../../../../管理档案/研究记录/proofreader-source-split/result.json)对应。脚本不读项目数据，不调用模型，也不计算准确率。

## 在生成变体之前，决定哪些来源属于哪一侧

如果目标是评价未见原句，可以按以下顺序组织数据。这是根据案例与分组评估原则整理的工作建议，不是 Cygames 内部流程的完整记录。

1. **整理原始样本并保留来源。** 为每条原句记录稳定的来源编号，能追溯到对应文本版本；不要等生成变体后再靠字符串相似度猜它来自哪里。已有变体如果缺少可靠来源关系，应先恢复关系，不能直接认定它们彼此独立。
2. **在来源层面划分。** 先决定训练、验证、最终测试各自包含哪些来源，再分别生成变体。同一来源的正确版本、错字版本和其他增强版本继承相同归属。如果需要多折交叉验证，每一折也必须遵守同样的隔离关系。
3. **检查交集，也检查覆盖。** 不同集合间的来源编号应无交集。随后检查每侧包含多少原句、多少变体、哪些错误类型、哪些角色或文本类别。类别比例不好时，可以重新选择整组，而不是为了凑比例把同源变体拆开。
4. **保存划分清单。** 记录数据版本、来源归属与增强规则。后续重新生成或新增同源变体时沿用归属，避免一次数据更新悄悄把已留出的来源送回训练。

scikit-learn 的分组交叉验证说明了相同原则：当样本存在组内关联、目标是评价未见群组时，验证组不能同时出现在对应训练折。`GroupKFold` 是保持群组不跨两侧的一种工具。[2] 但工具不会替项目决定“组”是什么；把每个变体都当成一个独立组，仍然没有隔离原句。维持类别比例的分层划分，也不等同于维护来源关系。

如果团队真正要回答的是“对已经收录的固定台词，新出现的错字能否识别”，允许训练与测试共享原句可能符合那个任务。此时应明确描述已知台词的评价条件，并另外检查所关心的错误是否未见过，不能把结果改称为对全新内容的泛化能力。

## 来源编号分开之后，还有哪些泄漏与盲区

来源编号不同，不代表内容真的独立。两条记录可能是复制后换了编号的相同台词，也可能来自同一模板。若目标是处理新章节、新项目或未来新增内容，仅按单句隔离仍可能太弱。应依据实际使用目标审查重复和近重复，必要时把章节、模板家族、项目或时间边界作为更大的划分依据。这些是评估设计建议，不能倒推成作者当年已经这样做过。更大的隔离单位也可能减少可用组数、改变各侧文本分布，需要报告代价，而不是只追求“没有交集”。

即使来源已经隔离，测试信息仍可能通过其他途径进入开发。例如，用全量数据拟合词表或其他需要学习参数的预处理，再做划分；或者反复根据最终测试结果修改规则、选模型。scikit-learn 的数据泄漏指南要求先划分，再只在训练部分拟合相关处理。[3] 预处理管线有助于控制拟合时使用哪些数据，却不会自动发现共同原句或修正错误的分组。这里不要求对所有固定、不学习数据的文本转换一概禁用，也没有核查预训练模型是否曾接触这些台词。

因此，调参应使用训练范围内的验证安排，最终测试应留到方法确定后再用。如果查看测试失败样本后继续据此改模型，应承认该集合已经参与开发，并为后续最终评估安排新的独立留出数据。[2][3]

最后，人工制造错字与真实写作错误不是同一个分布。它们可能缺少作者真正会犯的错误，也可能把角色有意使用的写法标成错误。来源不跨集只能排除一种可检查的关联，不能证明错误标签正确、自然错误覆盖充分，或工具已经适合生产。Cygames 第35页也没有给出只改变划分方法的消融比较，不能把报告中其他版本的分数变化归因于这一步修复。[1]

对这类工具，验收时先问清楚“哪些原句未见过、哪些错误未见过、评估结果准备代表什么”，往往比只问一个准确率更有用。交接给 QA 和内容负责人时，应一起保留划分清单、标签依据、检测任务定义，以及仍需要真实内容评估的范围。发现疑似问题、定位改字位置和给出正确修订是不同任务，不应只用一个含义不明的总分替代。
