# 游戏设置页的操作序列与异步完成测试

玩家先选日语，又选法语。法语先加载好，字幕预览已经正确；稍后第一次请求才返回，旧日语覆盖了法语。玩家再调一下缩放，预览重建，画面又恢复法语。测试若只在缩放后截图，会通过；若只等待“法语出现过一次”，也会通过。

这个假设故障说明，设置页回归需要同时回答三个问题：**实际发生了哪串操作，异步结果属于哪次请求，在哪一步判断界面正确。** 只列按钮排列，或统一在点击后等待一秒，都没有把这三件事接起来。

本文面向熟悉基本回归测试与异步回调的 QA 和 UI 程序，给出语言、缩放与字幕预览的测试建模方法。示例产品采用“最后受理的语言选择生效”；加载期间显示占位，失败显示错误，不自动退回较早请求。它是原创设计案例，不是 Unity 缺陷报告。配套程序执行了有限状态模型；Unity 部分是官方接口与固定源码的分析，以及待接入项目的观测方案，没有运行 Unity 或真实游戏。

## 把一次点击拆成可以判断的阶段

语言切换至少经过以下过程。不同项目可能合并某些阶段，但测试不能仅因事件名字里有 Changed 或 Complete 就把它们视作同一件事。

| 阶段 | 可以证明什么 | 仍需检查什么 |
|---|---|---|
| 输入发出 | 脚本请求了点击或选项变更 | 控件是否可操作、请求是否被产品受理 |
| 请求受理 | 产品接受了目标语言，并给出请求身份 | 内容能否获得，以及哪次结果最终进入当前预览 |
| 内容获得 | 某项加载返回成功或失败 | 它是否过时、回退语言是否符合规则、文本是否真正写入控件 |
| 内容提交 | 当前控件被写入了具体文本 | 排版是否使用这份内容与当前缩放 |
| 布局采样 | 一次布局阶段后的几何状态已被读取 | 几何是否符合规则，后续图形重建与实际画面是否正确 |

Unity Localization 1.5.14 的 `OnSelectedLocaleChanged` 在初始化操作完成、预加载结束后调用；这段约定没有说项目中的所有文本控件都已赋值，更没有承诺布局与呈现完成。[1] `LocalizedString.StringChanged` 又可能由首次订阅、语言变更、变量或引用变化、显式刷新触发；内容已加载时，新增订阅者也会收到现有字符串。[2] 因此，收到任意一次字符串通知，无法单独证明刚才那次点击已完成。

测试需要产品自己的**受理回执**：请求被接受、拒绝，还是与已有请求合并。比如 `RefreshString()` 在已有加载仍活动时可能返回 `false`，表示本次刷新没有发起。[3] 这不等于所有 Unity 语言选择都会被丢弃，也不必然是产品错误。若产品规定加载中禁用刷新，拒绝可能正是正确结果；脚本却不能继续等“第二次刷新成功”，再把超时误报为加载卡死。

以下约定用于贯穿全文：设置页在预览关闭时仍可修改语言与缩放。此时受理只更新设置模型中的目标值，回执为“设置已应用”，不启动预览内容加载，也不等待不存在的布局。P打开预览时，创建新界面代次，读取当前目标语言、内容与缩放，并发起一次内容请求。预览已打开时，新的语言选择则更新目标值并立即发起新内容请求；缩放改变让当前布局失效，等待自然布局过程处理。关闭预览保留设置目标，但撤销旧界面的展示资格，不据此声称底层加载已停止。

因此，用户操作回执与内容请求并非总是一对一：闭预览的L没有内容请求，P会创建内容请求。同值重复选择在本例中也可生成新请求，以便测试身份；实际产品若采用同值幂等或合并，就记录“沿用请求r”，不要虚构新的一次完成。操作编号用于关联用户意图，内容请求身份用于追踪实际异步工作。

## 先后覆盖、连续操作和完成交错是三种目标

先固定一个可恢复的起点：构建、测试存档、语言与缩放已确认，预览关闭，本行之前的请求无权写入新界面。再定义三个带参数的用户操作：`L` 选择语言、`S` 改变缩放、`P` 打开字幕预览。下表暂将每项操作完成后才进行下一项，讨论串行操作覆盖。闭预览的L/S只等目标设置回读一致；P以及开预览后的L要等当前内容请求与布局检查完成；开预览后的S要等该缩放版本的布局检查完成。不能把这些不同阶段统称为“画面已完成”。

| 计划 | 覆盖的先后关系 | 没有包含的连续操作 |
|---|---|---|
| L → S → P | L在S前、L在P前、S在P前 | L紧接P |
| P → S → L | P在S前、P在L前、S在L前 | P紧接L |

这两行包含三种事件任意一对的两个方向，却没有直接执行 L→P。NIST 的序列覆盖数组（sequence-covering array）正是这种允许中间夹入其他事件的覆盖：每行是事件符号的一次排列，选中的 t 个事件按要求次序出现即可，不要求相邻。[4] 它适合“曾经发生过A，后来B受其状态影响”的风险。若 S 会重建缓存并修好 L 留下的错误，只用 L→S→P 就可能避开问题；应增加 L→P，并在 P 后、S 前检查。

这里的“连续”指没有插入另一个用户操作，内部仍可能发生加载回调。若风险就在回调顺序，则必须进一步拆开请求与完成。异步交错用例从已打开且起始内容已就绪的预览开始，避免把闭预览的设置变更误当加载。令L1、L2是依次受理且各自启动内容请求的两次语言选择，C1、C2是各自的结果到达。在“L1先于L2，结果不能先于自己的请求”这几个约束下，有三种合法次序：

1. L1 → C1 → L2 → C2：第一项已经完成，才发第二项。
2. L1 → L2 → C1 → C2：两项重叠，按发起顺序完成。
3. L1 → L2 → C2 → C1：两项重叠，后发先完成。

每次都等 L1 完成再点击 L2，只会执行第一种，恰好排除了开篇的竞态。测试可以在加载接口处安装可控制完成顺序的替身，保持产品的受理、绑定、提交与布局路径不变，再逐次放行结果。另保留使用真实加载器的集成测试，核对缓存、资源与调度实际如何工作。替身能保证测试尝试某种交错，不能证明真实平台所有交错都已覆盖。

覆盖对象还必须带上参数和投影规则。`L(ja)→L(fr)→L(ja)` 不能压缩成一个 L；请求1与请求3也不能因为都选 ja 就合并。用户操作的相邻，与内容提交的相邻，是不同记录。本文不把这些有限序列解释成整个设置页状态空间已穷尽。

## 请求身份必须从工作开始时一直带到提交处

给每个有效预览分配 `view_generation`，关闭重开时改变它；给每次受理的内容请求分配 `request_id`。二者组成请求身份。即使新界面的局部编号重新从1开始，界面代次也不能与仍可能返回结果的旧界面重复。

请求记录同时保存语言、表与条目、格式参数快照、预览内容版本。语言码不是身份：同样的 ja 可能对应不同的一次打开、不同字幕内容或不同参数。格式参数若指向之后还会变的对象，只有复制外层列表也未必冻结了输入，应保存本次格式化真正需要的值。

一个可审查的绑定路径可以采用下面的伪代码。`BeginPreviewContent`只在预览已打开时调用：可以由P创建界面后调用，也可以由已打开预览的语言选择触发，并在记录中关联发起它的用户操作。闭预览时只更新设置目标，不调用它。代码假设所有状态变更在同一串行队列上处理；内容写入过程不调用会重新进入设置流程的用户代码。真实项目若不满足这两点，必须先加入串行化或重入处理，不能把比较 token 的一行代码当作完整并发保证。

```text
BeginPreviewContent(locale, originating_operation):
    确认当前预览已打开
    若拒绝或合并，返回明确回执，不伪造新请求
    r = 新建记录(view_generation, request_id, locale, key, 参数快照, originating_operation)
    current = r.token
    状态 = loading；撤下旧内容的“已就绪”标记
    记录 Accepted(r)                    # 在启动前保存
    loader.Start(r.输入, result => 入队 Complete(r, result))
    return r.token

Complete(r, result):
    若 r 的终态已处理，记录重复通知并返回
    标记此次结果已接收
    若界面已关闭，或 r.token != current，记录过期结果并返回
    若 result 失败，提交属于 r 的错误状态并返回
    校验结果与 r 的表、条目及回退政策
    将 result 的实际文本写入当前目标控件
    内容版本加一；使旧布局快照失效
    记录 ContentCommitted(r.token, 从控件回读的文本, 内容版本)
```

观察器必须在发操作之前注册。缓存命中或同步替身可能在 `Start` 内就给出结果；若受理记录在它之后才建立，日志会先出现完成、后出现请求。统一将完成入队还能避免回调在 `BeginPreviewContent` 的调用栈中改写半初始化状态。记录 Accepted 是内容请求受理，不等于加载一定成功；`Start` 本身抛出异常也要走该请求的失败终态。

最危险的做法是：回调返回时读取全局 `current`，再把它贴给这份结果。旧日语就会披上新法语请求的身份。应该捕获发起工作的请求记录，并将该记录送入实际提交入口。测试读取实际控件状态与提交日志，不只检查加载替身“准备返回”的理想值。失败路径同样校验身份，否则旧请求的失败会把已经正确的新预览改成错误提示。

若使用 Unity 的主动取串接口，`LocalizedStringDatabase.GetLocalizedStringAsync` 有显式 `Locale`、表与条目参数，并返回操作句柄；可以将该句柄与捕获的请求记录关联。[5] 这比在无身份的广播到来后猜它属于哪个按钮更容易核对。本文没有提供可直接复制的 Unity 加载器：句柄持有与释放、事件解绑、回退语言、初始化和异常路径仍由项目适配层实现。也不能为了测试而另写一条永远正确的绑定路径，绕过实际产品使用的 `StringChanged` 绑定。

对于已有的自动绑定，先找到真正赋值控件的位置。如果该处根本不知道结果来自哪次工作，单加日志无法补出因果。可选择给底层加载与绑定补请求关联，或者保持黑盒测试，检查代表性文本和可见状态，同时明确无法证明具体请求身份。两种证据能力不同。

取消与关闭也走同一个归属规则：撤销展示资格后，迟到结果只能被记录和收尾，不能改当前界面。底层取消是否成功要另有终态；资源生命周期的完整处理可读[关闭装备预览后，未完成的资源加载怎样收尾](../../../引擎与工具/运行时系统/异步资源/关闭装备预览后，未完成的资源加载怎样收尾.md)。

## 布局检查点要带着它使用的输入版本

文本正确并不意味着布局已经使用它。长法语替换短日语后，文字节点可能已经变化，但面板仍沿用旧高度；随后缩放触发布局，问题才消失。Unity UI 1.0 的自动布局说明中，重建默认延后至渲染前执行，并依次计算宽度、设置宽度、计算高度、设置高度。[6] 所以，在文本赋值后立刻读取矩形，与在布局阶段后读取，可能是两个不同状态。

为布局建立输入签名，例如：

```text
E = (界面代次, 当前请求身份, 内容版本, 缩放版本, 字体版本, 视口版本)
```

签名中的字段按项目实际依赖选择。若安全区也会改变本例布局，就加入其版本；固定不变的字段也应在运行夹具中有明确值。每次相关输入改变，都让上一份布局快照失效。布局观察器保存该轮开始使用的 E，在阶段完成后比较它与当前 E；不能到结束时直接取当前版本，给一份旧布局补上新标签。

可以据此建立一条具体的 uGUI 观察路径。以字幕面板由标准布局组控制、没有排版动画和自定义 PostLayout 改写为例：

1. 在该轮 `Prelayout` 保存输入签名，并确认预览有效。观察器只登记自己的观察，不替产品额外标脏或强制重建面板。
2. 在项目实际使用的布局根上，记录本轮是否真正执行了布局。可在布局组适配层的 `SetLayoutVertical` 中调用原实现并记录阶段到达；若面板有多个独立布局根，分别记录。只观察到另一个组件的回调不算本面板完成。
3. 在该轮 `PostLayout`，要求所有相关根确实经过本轮布局，输入签名没有变化，控件仍有效，期间没有布局异常。此时读取相关 RectTransform 的实际矩形及文本信息，保存 `LayoutSample(E, frame, geometry)`。
4. 读取后若内容、缩放、字体或视口改变，立即作废这份“当前布局”状态，但保留历史样本用于诊断。若项目在 PostLayout 或更晚还会改尺寸，就必须把观察点移到那些修改之后，或将其纳入新的布局版本。

这是待在项目中校验的适配方案，不是只要实现 `ICanvasElement` 就自动获得的保证。观察器可能得到自己的阶段通知，而产品面板根本没有按预期重建；因此必须同时观察真实布局根，并检查实际几何。初始静态且无需重建的界面，可以使用同一 E 下已确认的有效样本；输入变化后不能继续沿用它。

到达布局采样点之后，还要执行产品判据。例如，本例可以规定正文完整显示、说话人标签不与正文重叠、二者位于面板裁剪区域内。检查前将文字的实际可见范围、标签与裁剪矩形变换到同一坐标系；仅比较文本节点矩形不能证明字形未被截断。可用布局后的矩形做早期几何检查，再结合图形生成后的字形数据或画面检查可见内容。签名匹配只说明本次样本关联到了哪组输入，不是这些规则已经通过。

尤其不要直接把 `LayoutComplete()` 当作“布局成功”的业务事件。Unity 官方 uGUI 固定源码快照中，正常更新会遍历 Prelayout、Layout、PostLayout 后调用它；但清理已销毁元素、注销元素、禁用元素时也会调用它。更新循环还会捕获并记录布局异常，然后继续处理。[7] 所以，即使收到这个通知，也可能根本没有得到一次成功的新布局。该结论来自标为 uGUI 7.0.0 的源码快照；接入其他版本要核对项目实际包实现，不能把文档与源码拼成一套已经实跑过的环境。

同一源码在布局之后继续做裁剪与图形重建。[7] `LayoutSample` 因而只支持相应阶段的几何判断，不证明这一帧已显示给玩家。若要查可见闪帧，增加与请求、帧号对应的画面采样或录屏；若只关心禁止旧结果进入控件，则在每次真实内容提交处检查即可。

也不要在每个断言前调用 `ForceRebuildLayoutImmediate` 来“保证测到最新布局”。这个接口直接执行子树布局；官方源码注释把它与正常的延迟重建明确区分。[8] 若缺陷就是产品没有正确触发布局，测试主动重建可能先把缺陷修好。需要验证强制重建功能时可单独测试它，但普通设置序列应观察自然执行路径。

## 在修复发生之前检查，并继续观察旧工作如何结束

回到开篇，将缩放重建记为S。下面是**假设错误实现**的过程，不是引擎日志；预览在L1之前已经打开。本反例额外假定S会从设置目标重新绑定内容，因此可以把错误内容修回法语。前文的基本适配方案只要求S更新缩放并使布局失效，并不保证S具有这种修复作用。测试应先核对自己的产品哪些操作确实会重新绑定，而不是假定每次缩放都修复文本。C2后的“法语正确”仅表示此刻内容与相应布局已就绪。

| 事件 | 当前目标 | 错误实现的预览 | 此时应该判断什么 |
|---|---|---|---|
| L1(ja) | 日语 | 加载占位 | 请求1已受理 |
| L2(fr) | 法语 | 加载占位 | 请求2已受理，请求1失去展示资格 |
| C2及其布局完成 | 法语 | 法语 | 请求2内容与布局匹配 |
| C1迟到 | 法语 | 被覆盖成日语 | 旧请求不得提交；立即保留差异 |
| S重建 | 法语 | 法语 | 可另测恢复，但不能覆盖前一步失败 |

“在期限内进入正确状态”和“进入正确状态以后不被旧工作改坏”是两项判据。前者可以有界等待；后者必须持续观察本次安排的旧请求，直到它们完成并被拒绝、失败，或得到明确的取消终态。仅仅发出取消命令不算终态；加载永不结束时，观察段到上限仍未闭合，应保留超时与未决记录，不写成安全通过。

采样方式决定能够下什么结论。每帧检查只发现采样时存在的错误；同一帧内旧文本写入又被改回，可能逃过它。对“从未接受过期提交”的要求，应在每次实际提交记录上做断言。对“玩家看到了错误一帧”的要求，提交日志又不够，仍需捕获渲染后的可见结果。这两者应分开报告。

Unity Test Framework 的 `UnityTest` 支持跨帧执行，`yield return null` 只是跳过一帧。[9] 可用它驱动有上限的条件等待，但成功路径的条件应是指定 token 的内容已提交、匹配 E 的布局样本已获得且判据已完成，而不是“下一帧到了”。预期当前请求失败的用例则等待对应 token 的错误状态与终态，不等待成功内容。超时输出最后停在哪一阶段：请求未受理、加载未终结、内容未提交、布局版本落后，还是画面复核未完成。这样才能区分产品问题与测试入口或观察器的问题。

## 组成一组能解释失败的回归，而不是只堆排列

先用少量固定内容验证链路，再按布局风险扩展语言与字体样本。身份用例宜包含翻译明显不同的文本，但还需一个不同语言恰好同文的例子，防止测试只靠字符串相等就错误归因。语言、条目与允许的回退结果来自测试内容包，不由被测加载器的当前输出反推期望。

| 用例目的 | 操作与安排 | 关键检查 |
|---|---|---|
| 串行基线 | L完成→S完成→P，以及所需逆向路径 | 实际受理和各自完成条件，不只看脚本步骤 |
| 连续风险 | L→P，先检查，再S | 后续重建之前的内容与布局 |
| 乱序结果 | L1→L2→C2→C1 | C2正确，C1不得再次提交或写错误提示 |
| 同值返回 | L1(ja)→L2(fr)→L3(ja)，安排C1晚到 | 第一次ja不能冒充第三次ja；同值合并则核对合并回执 |
| 界面重建 | 请求A→关闭→重开→请求B→A返回 | 旧界面代次不能写新界面，即使局部编号相同 |
| 输入在布局间变化 | 内容提交→开始布局→改变缩放→旧布局回执 | 旧E不能标记新缩放就绪，继续等新E样本 |
| 失败与取消 | 当前失败、旧失败、取消后迟到分别执行 | 当前错误属于当前请求；旧失败不破坏新界面；取消不是成功 |
| 缓存与受理 | 同步完成、延迟完成、拒绝或合并、重复通知 | 日志因果顺序、终态只处理一次、不等不存在的请求 |

这些用例按失败机制选择，不是统一强度的覆盖数组。完整组合生成的起点、值域与覆盖计算，可读[游戏 UI 配置回归的约束建模与组合覆盖](游戏UI配置回归的约束建模与组合覆盖.md)。不要把每个序列与所有配置机械做笛卡尔积：先确认哪些平台、字体或布局配置会改变异步路径，再为这些风险安排组合，并保留未测范围。

每行开始时确认起点并隔离旧展示资格；一行内部不要偷偷重建界面以便下一步成功，那会抹掉正在测试的状态。起点恢复失败记为准备失败，不计入本行路径执行。脚本通过产品操作入口与直接调用绑定控制器，也要区分：后者能检查控制器，不能验证输入绑定、按钮可达性与实际点击。

执行报告至少保留运行与构建身份、起点、请求参数和受理结果、请求/界面身份、每次真实提交、布局E与帧、完成和取消状态、判据及失败证据。覆盖由实际轨迹计算：L2若被拒绝，就不能计为已执行“两项重叠加载”；C1若始终没返回，也不能宣称完成了C2→C1。已经发生并被观察到的失败路径仍算尝试过，失败不能从轨迹中删掉。计划覆盖、实际执行覆盖和判据通过率应分别报告。

有限模型可帮助检查测试判据本身是否有区分力。例如，故意去掉旧请求校验后，末尾重建仍能让最终检查通过；逐次提交检查则应失败。若二者都通过，先查测试是否只观察了理想模型或最后一帧，而不是把“所有结果绿色”当作绑定实现可靠。替身和观测代码也要维护，但不应通过主动修正状态来制造成功。

## 复现材料与采用边界

[有限模型及运行说明](../../../../管理档案/研究/TASK-2026-0308/model/README.md)包含原创 Python 程序与保存的真实输出，用于核对请求身份、终态与布局版本的状态转换。它不计算字形、布局矩形或帧时序，不调用 Unity，不代表上述产品适配层已经实现。将模型接入项目时，还需真实核对：所有写入是否经过观察入口、布局根的阶段是否覆盖实际依赖、缓存与延迟路径是否一致，以及截图是否对应同一个请求和帧。

这套方法的交付不是“所有按钮都点过”，而是可解释的一条链：操作确实被受理，结果归属于正确的请求与界面，布局使用了被检查的输入，判据在可能被修复之前执行，迟到工作也没有在观察段内把结果改坏。每一环缺证据时，报告具体缺口，而不是让最终正确的截图替整段过程作证。
