# 命中停顿里按下的连招，输入缓冲该从什么时候计时

一击命中后，角色停了几帧。玩家在停顿期间按下第二击，恢复动作后却没接上。调长缓存似乎有用，可换一台卡顿更明显的机器，反而是同一个早按键更容易接上。这两个现象未必来自同一个参数：一处决定输入按哪只钟老去，另一处决定送到游戏手里的时候，是否把输入当成了刚刚发生。

取消窗口回答的是“当前动作什么时候准许下一招开始”；输入缓冲回答的是“较早按下的请求还能不能用”。这篇只讨论一次已识别的按键怎样跨过命中停顿，以及如何区分它**过期了**、**还没送到**和**仍有效但不允许出招**。不讨论连段去重和打断后的清理。

## 先分开事件、收件和角色的动作进度

以单个攻击者的局部命中停顿为例。角色用于判断取消窗口的动作计时停住，控制器输入采集可以照常工作，画面和其他角色也不一定停。别拿动画播放器的播放进度冒充规则进度：如果项目只让画面停而战斗规则照常推进，那么下文的冻结动作钟并不适用。

| 记录什么 | 回答的问题 |
| --- | --- |
| 输入事件时间 | 输入后端给这条边沿事件的时间戳是什么？它未必是手柄电路刚接触的时刻。 |
| 回调接收时间 | 这条输入什么时候进入应用收件箱？没有事件时间时，只能知道输入最迟在这时已到达应用，不能把它叫作发生时间。 |
| 模拟步、局部动作时间 | 规则在哪一步看到这条输入？此刻动作推进了多少？局部停顿时，连续多个模拟步可以对应同一动作时间。 |

这里的现实时间指不受游戏缩放影响的单调时钟，不是日历时间。事件时间与接收时间可能来自不同后端或单位，不应直接相减。接入时把事件时间映射到同一时间基准；做不到就记录“只有接收时间”，不要假装精确还原输入发生时刻。

如果设计希望玩家真正早按太久就放弃，使用**从事件起算的现实时间**。如果希望停顿不消耗接续机会，就用**从事件映射出的局部动作时间**。如果产品有意提供“从进入应用收件箱起再给一段寿命”的容错，可以从接收起算，但不同交付延迟会改变规则结果。这是第三项设计选择，不是前两项的替代。使用动作钟也不等于允许菜单或硬直期间无限积攒输入：按状态决定是否接收、最多留几条、退出动作时何时清理。

## 让同一个早按键迟到一次

设角色动作钟在现实时间 `[80,145)` 毫秒停住；第一个允许接续的检查在现实时间 155 毫秒，此时动作钟是 90 毫秒。缓存寿命为 55 毫秒，本文在年龄恰好 55 时先判过期。先用同一个 85 毫秒的事件测试两次，只改变它进入收件箱的时刻，不改模拟状态、取消窗口或过期上限。

| 事件 → 交付（毫秒） | 从事件算现实年龄 | 从接收算现实年龄 | 从事件算动作年龄 |
| --- | --- | --- | --- |
| 75 → 150 | 80，过期 | 5，接续 | 15，接续 |
| 85 → 86 | 70，过期 | 69，过期 | 10，接续 |
| 85 → 145 | 70，过期 | 10，接续 | 10，接续 |
| 100 → 101 | 55，过期 | 54，接续 | 10，接续 |
| 105 → 106 | 50，接续 | 49，接续 | 10，接续 |
| 105 → 156 | 未到达 | 未到达 | 未到达 |

只测 85 → 145 这一次，后两种策略都得 10，看起来像正确实现了“停顿不耗寿命”。加上及时交付的那一次，就知道是不是回调在替旧事件重新盖章。105→156 这一行只说明 155 的检查没看到它，不代表它永久失效；后来还能否进入窗口，要由项目的下一次检查、过期与迟到政策决定。若该项原本就不该被接收，也应记成“状态拒绝”，不是过期。

## 在引擎适配层保留时间，在动作规则里决定是否消耗

输入端把每次按下记录成有稳定身份的命令，至少保留事件时间及来源时基、应用接收时间和稳定顺序。不要留着只能在回调期间使用的引擎对象，之后再从它读时间。分配给模拟步时，把接收步骤和依据记下来：在同一个动作钟刻发生的多个按键不会自动有先后，仍要按明确的来源顺序或方案规定排序。回放或回滚系统应保存映射后的命令和步号，或者保存足以重建年龄的同一时基数据；不要重演时重新取当前墙钟。

固定步项目可以保存一小段动作历史。为每个模拟步保存统一时基上的计划起止时刻、步号、角色动作编号及**步首的局部动作刻**；用左闭右开区间查事件落在哪一步，恰好在步末的归下一步。取步首动作刻是本文给出的量化政策：同一步内没有更细粒度，不用回调延迟去补精度。连续停顿几步就重复记相同局部刻，但步号照样递增。时间边界来自模拟步的时间映射，不是回调实际在哪一帧跑到。例表用连续毫秒方便算账；固定步可改用步首刻，并用同样单位表达寿命。按项目允许的迟到范围保留历史；源时戳缺失、落在已丢弃的历史或查到别的动作时，按约定拒绝或明确降级为收件政策并记日志，不伪造原始动作刻。

例如 75 ms 发生、150 ms 才交付的请求，动作钟从事件时的 75 走到检查时的 90，年龄是 15 ms；把它当作收到时才发生，动作年龄就只有 5 ms。若本招动作时钟寿命设为 12 ms，真实早按应过期，错误地按收件时的动作刻却会接招。按历史取事件时的动作刻，正是为了保留停顿前已过去的那一段。

应用规则可以用这个检查顺序：

1. 先取得本步已经交付的请求，按本步确定的事件顺序处理。模拟步快照切换后到的请求交给下一次；如果采用按发生时刻回滚或补算，则显式执行该策略，不悄悄补到已经结算的步。
2. 在所选时基内部计算年龄。如果用动作钟，把事件时刻映射到该角色的动作进度，而不是读处理回调时的动作钟；局部停顿区间和动作身份要能对应。如果跨动作不能继承缓存，切换或打断时撤销旧请求。
3. 清除达到上限的请求。只对仍有效的请求判断当前招式、取消窗口及可选的优先级；确认实际换招后只消费一次。记录“未交付”“已过期”“仍有效但窗口未开”和“已消费”，不能只记下这一帧有没有播第二击。

换引擎时真正需要适配的是事件获取、时钟换算、步分配与回放输入，不是把战斗规则改写成某一个引擎的回调集合。Unity Input System 1.14 的 `CallbackContext.time` 与 `Time.realtimeSinceStartup` 同一时间基准，通常来自触发该动作的输入事件而非当前回调。交互若并非由这次按下直接触发，应核对记录的是哪种时间。SDL3 的键盘事件载有 `SDL_GetTicksNS()` 基准的纳秒戳；这仍不是测得的实体按键时间。[1][2]

## 把结果放在相邻两行日志里

Python 夹具实际执行了上面的六组断言。另一个独立的 Godot 4.7.2 无窗口探针启用输入缓冲，提交两次合成键事件，在主动冲刷前后分别读取 `_input` 次数。两次都用自定义元数据携带同一个人为事件时间（不是 Godot 的原生事件字段）；第二次刻意等待 50 毫秒才冲刷，回调收到得更晚，但携带的事件戳未改。它只验证指定注入与主动交付路径中，接收可以晚于提交，并未测真实键盘、引擎自动冲刷、设备时间戳或玩家体验。[3]

项目验收时，把一条请求的事件戳、接收时刻、目标步、动作时刻、年龄、窗口和消耗结果放到同一条日志。再用相同事件做及时、晚交付两次，检查差异落在哪一列。若设计要求动作钟，测试长短两种停顿下的相同动作进度；若要求现实钟，测试边界恰达上限和窗口前一刻。最后在真机上分别测键盘和手柄，并核实配置下的实际交付；这一步用来验证接入和体验，不由模型代替。
