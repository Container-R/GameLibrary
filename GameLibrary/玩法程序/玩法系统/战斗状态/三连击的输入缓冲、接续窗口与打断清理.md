# 三连击的输入缓冲、接续窗口与打断清理

玩家在第一击还没结束时再次按下攻击，程序既不能立刻打断当前动作，也不能把这次意图丢掉。于是实现里出现输入缓存和动画通知：先记住按键，在通知到来时取走。然而，跳转动画、重复通知和打断后的迟到通知，会使“何时能接下一击”同时受两套状态控制。一次输入可能没被消费，也可能被旧攻击重新使用。

本文面向理解状态机和固定更新的玩法程序员，给出一个单角色、本地三连击的完整教学规则。读者可以据此逐步判断输入被缓存、过期、拒绝或消费的时刻，并实现打断后不复活旧请求的接续逻辑。输入已经按顺序分配给连续的整数模拟步，设备采集与时间分配由外层负责。本文不实现命中、根运动、动画混合或完整引擎角色控制器。

## 让规则拥有接续资格

动画播放到某处与规则允许转换状态，是两件事。本文让模拟步决定接续资格；动画只读取已经发生的攻击转换，并播放对应动作。这样即使表现晚开始、跳过一段或通知重复，规则也不会重新消费同一输入。代价是项目必须明确维护规则时间与动画显示的对应关系，不能一边让规则计步，一边又让通知独立开启接续窗口。

我们用很短的数字便于手算，不把这些时长作为手感建议。角色有 Idle、第一击、第二击、第三击四种状态。每击最长持续6步。第一、第二击只在相对步 `[3,5)` 接续，也就是开始后的第3、4步；第三击不接续。接下一击立即替换当前攻击，重新计时，而不是等当前攻击自然结束。

缓存只容纳一个请求。请求在步 `t` 接收，失效步为 `t+2`；到 `tick >= expiry` 就清除。缓存满时保留先来的请求，拒绝后来的请求。每个请求使用本次角色控制器生命周期内唯一的 ID，同一 ID 再次送达不续期、不重新入队。第三击期间的新请求拒绝，不预约下一套连招。这里“消费”专指一次请求实际启动一击；缓存并不承诺一定能出招。

## 更新顺序也是玩法规则

每一步严格执行以下顺序：

1. 处理打断。有打断就进入 Idle、清空缓存、递增代号，并拒绝本步的全部攻击输入；本步结束。
2. 删除到期的缓存请求。
3. 若当前攻击已持续6步，进入 Idle，并删除旧攻击留下的缓存。
4. 按外层提供的顺序处理本步请求。新 ID 先登记为见过；Idle 中启动第一击，第一、第二击中尝试存入空缓存，其他情况拒绝。
5. 检查第一、第二击的接续窗口。窗口内若仍有请求，取出并清空缓存，消费该 ID，进入下一击，重置开始步。

因此，到期与窗口打开同时发生时，到期优先；自然结束与新输入同一步时，新输入可以启动新第一击；打断与新输入同一步时则拒绝输入。这些差别不是实现偶然顺序，而是本文选定的政策。

如果同一步有多个不同 ID，第一个在 Idle 中启动第一击，第二个可以填入缓存，其余被拒绝。缓存中的第二个请求可能早于窗口到期。产品若不希望一次输入批次同时做这两件事，需要修改第4步的政策，而不是靠动画通知顺序掩盖它。

## 一个可直接检查的最小实现

下面是原创 Python 教学核心，与配套模型的状态转换相同。[1] `tick` 从0开始连续调用；`requests` 是本步按顺序交付的、可散列的唯一请求 ID。运行期不要复用这些 ID。

```python
class Combo:
    def __init__(self):
        self.stage = 0  # 0 为 Idle
        self.start = 0
        self.generation = 0
        self.attack_id = 0
        self.pending = None
        self.seen = set()
        self.starts = []
        self.consumed = []
        self.effects = set()
        self.last = -1

    def enter(self, t, stage, request):
        self.stage, self.start = stage, t
        self.attack_id += 1
        self.starts.append([t, stage, request])
        self.consumed.append(request)

    def tick(self, t, requests=(), interrupt=False):
        if t != self.last + 1:
            raise ValueError("ticks must be contiguous")
        self.last = t
        if interrupt:
            self.generation += 1
            self.stage = 0
            self.pending = None
            self.seen.update(requests)
            return
        if self.pending and t >= self.pending[1]:
            self.pending = None
        if self.stage and t - self.start >= 6:
            self.stage = 0
            self.pending = None
        for request in requests:
            if request in self.seen:
                continue
            self.seen.add(request)
            if self.stage == 0:
                self.enter(t, 1, request)
            elif self.stage < 3 and self.pending is None:
                self.pending = (request, t + 2)
        if self.stage in (1, 2) and 3 <= t - self.start < 5 and self.pending:
            request, _ = self.pending
            self.pending = None
            self.enter(t, self.stage + 1, request)

    def notify(self, generation, attack_id, marker):
        if self.stage == 0 or (generation, attack_id) != (self.generation, self.attack_id):
            return False
        key = (generation, attack_id, marker)
        if key in self.effects:
            return False
        self.effects.add(key)
        return True
```

`enter` 是唯一的消费入口。通知函数不调用它，也不修改缓存或段数。`seen` 包括被拒绝的 ID，所以满缓存时被拒绝的请求不能稍后换个时刻重新投递。持续按键是否生成新的请求，应该由输入层明确决定，不能通过反复提交同一 ID 实现。

这个有限模型保留全部见过的 ID 与表现键以便检查，长时间运行会持续占用内存。项目实现需要有明确的角色实例生命周期或安全退休边界，再回收集合；在仍可能收到旧回调时直接清空去重集合，会重新放行旧事件。本文没有实现无限运行的回收策略。

## 顺着一条输入记录走到第三击

给出 `A@0、B@2、C@5`，其中 `@` 后是交付步：

| 步 | 输入和状态变化 | 步结束时的状态 |
|---:|---|---|
| 0 | Idle 收到 A，消费 A | 第一击，开始步0 |
| 2 | 收到 B，缓存失效步4；相对步2尚不接续 | 第一击，缓存 B |
| 3 | B尚未到期，进入窗口，消费 B | 第二击，开始步3 |
| 5 | 收到 C，缓存失效步7；相对步2尚不接续 | 第二击，缓存 C |
| 6 | 消费 C | 第三击，开始步6 |
| 12 | 第三击持续满6步 | Idle |

配套模型的实际输出为 `[[0,1,A],[3,2,B],[6,3,C]]`，每个 ID 消费一次。[1] 如果把 B改为在步1交付，它会在步3先到期，恰好错过窗口。若改为步5交付，第一击的窗口已经关闭；步6自然结束时清掉缓存，也不接续。这解释了为什么“收到输入”与“完成连击”不能写成同一个布尔值。

再看 `A@0、B@2`，步3同时发生打断和输入 X，步4输入 D。模型只记录 A在0启动第一击、D在4启动新的第一击；B未消费，X被拒绝。[1] 若需求是打断当步仍允许闪避，应另设闪避规则和优先级，不能把这里拒绝攻击输入的政策直接套到所有行为。

## 迟到的动画通知只能请求表现

进入一击时分配新的 `attack_id`；打断时还会递增 `generation`。表现侧创建任务时捕获这两个值，并在回调时带回。不能等回调到达才读取角色“现在的 ID”给它盖章，否则旧回调会伪装成新攻击的通知。

`notify` 先拒绝 Idle、旧代号和旧攻击，再对同一次攻击的同一 marker 去重。返回 true只表示可执行一次该表现请求，例如显示火花；不表示已命中、已造成伤害或可再次消费攻击输入。一个循环特效若需要同名 marker 多次发生，必须采用新的事件身份设计。本例刻意只接受每击每 marker 一次。

原生方法轨的有限观察说明为何需要这个边界。既有测试用一个自报 Godot 4.6.3 的程序，在手动处理、立即回调、独立播放器、无混合的条件下，放置0.1和0.2秒两个方法键；初始化回调为空。推进至0.3秒时，`advance(0.3)` 交付两个键，`seek(0.3,false,false)` 当下不交付，`seek(0.3,true,false)` 只交付后一个键，`seek(0.3,true,true)` 当下不交付。[2] 时间位置相同，方法交付并不相同。

“不交付”也不能解释成后续永久静音。在另一组独立播放器中，键为0.2、0.4、0.6秒；延迟 seek到0.5后再 advance 0.15，无论那次延迟 seek的 update_only 是什么，都交付0.6秒键。[2] 固定源码的 `seek_internal` 仅在立即更新分支传递 `update_only`；方法轨区分 seek取键和普通范围取键。[3] 这能解释指定分支的机制，但运行程序与该固定源码的构建身份尚未建立对应，官方发行字节来源也未确认，不能把有限结果推广为所有 Godot 安装的保证。

配套应用模型只把上述四种已记录的回调标签作为表现输入重放，三击启动序列没有变化。[1] 这验证的是我们写下的职责隔离，不是一次原生连招测试。项目接入时，让规则转换发出带身份的播放请求，再让动画回调进入受限表现接口；不要让回调直接访问 `pending`、`enter` 或伤害状态。若玩法必须由根运动或动画事件驱动，应重新设计规则与动画的依赖，不能直接宣称动画只读。

## 如何定位一次接续失败

先记录首个不同的步，而不是只看最后播了几次动画。逐步比较输入 ID、当前段、开始步、缓存 ID与失效步、打断标记和消费记录。缓存到期说明输入太早或缓存太短；窗口外仍有缓存说明输入到达时机不合适；出现重复消费则检查是否绕过了唯一入口。规则启动一致而画面不一致时，再查播放请求及回调身份，不要用重放动画修补规则记录。

短缓存和先按优先让判断明确，但不保证玩家体验最好。后按优先、第三击预约下一套、允许输入跨越自然结束，都可以是合理产品选择；改动时应同时修改状态转换和边界用例，而不只移动动画中的一个标记。本文的数字、结果和代码提供一个可审查起点，没有提供玩家测试或跨引擎体验结论。
