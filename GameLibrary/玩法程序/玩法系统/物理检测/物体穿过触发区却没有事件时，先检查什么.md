# 物体穿过触发区却没有事件时，先检查什么

一颗高速圆形子弹从检查线左侧飞到右侧。检查线被做成一个窄矩形触发区，不阻挡子弹，只负责记分。画面上子弹经过了它，程序却没有收到预期事件。第一反应往往是提高物理频率、增加子步，或者打开连续碰撞检测。但在改参数之前，应该先问：**这条检测路径检查的是某一时刻的重叠，还是一段运动中曾经经过？**

本文面向接入物理引擎的玩法程序员，以 Box2D 的两个固定版本说明怎样排查。讨论的是传感区域，Box2D 称为 sensor：它检测重叠，但不产生实体阻挡响应。本文没有运行引擎；下面的运动示意是几何推理，不是一次实际漏报日志，也不代表所有引擎都有相同行为。

## 两端都在外面，不代表中间没有经过

把例子进一步说清楚：触发区静止，圆形物体沿直线从左往右移动，没有墙改变路径。某一步开始时，圆形完全在区域左侧；这一步结束时，圆形完全在右侧。只检查这两个时刻，答案都是“不重叠”，但连续路径可以经过区域。

这说明端点重叠的信息不足，不是在证明某个引擎必然漏报。引擎可能另有连续检测路径，正是用来补充端点之间的信息。

玩法也并非总需要这种补充。恢复区可能规定“这一步结束时仍站在里面才回血”；竞速检查线则可能规定“这段运动经过就算通过”。两者都可以叫触发器，却需要不同的信息。先把规则写成其中一个问题，才能判断没收到事件是否真是错误。

还要区分“求解器内部多做几次计算”与“应用把世界分成更多次更新”。增加 solver substeps 不自动意味着 sensor 在每个子步都重新观察整条路径；把完整世界更新分得更细是另一种采样方式，但也不能在没有速度、区域厚度和检测路径条件时保证不会漏掉。

## 先查版本：旧版经验可能已经不适用

Box2D **3.1.1** 的官方文档明确说明：sensor 不检测一个时间步内完整穿过区域的对象，并建议快速对象或很小的 sensor 使用射线或形状查询。[1] 因而，不能仅凭启用 bullet（用于高速物体的刚体标志）或增加求解子步，就认为这个历史版本的传感事件已经变成了路径检测。

但 **3.2.0** 的固定文档和实现不同：快速形状经过静止 sensor 已有连续检测路径；文档仍限制快速移动 sensor 的可靠性。[2][3] 所以前面的静止检查线示意，**不能直接拿来当作 3.2.0 连续路径的漏报反例**。也不应该因为看过旧版文章，就在新版无条件再实现一套检测。

核对版本时要落到实际使用的版本，而不是搜索结果或滚动网页的一句话。本文分别固定了这两个发布标签的源码；并没有查明这项变化最早出现在哪个中间版本。

## 在另写扫掠之前，先确认事件路径真的启用了

对前面的静止检查线，使用 3.2.0 时先检查这几件会直接改变判断的事：

- **触发区确实是 sensor，子弹的参与形状是什么？** 连续路径中的快速形状本身若是 sensor，会被跳过；不要把“实体子弹经过静止传感区”与“高速移动的传感判定体”当作同一配置。[3]
- **双方都开启了 sensor 事件吗？** 只给区域打开 `enableSensorEvents` 不够；涉及的两个形状都需要开启，默认并不开启。[2]
- **过滤允许这两个形状相遇吗？** 事件开关不绕过碰撞过滤。还要检查是否有实体障碍先挡住了子弹：不能把被阻挡后的实际路径，与原本想移动到的位置混为一谈。[3]
- **什么时候读取事件？** 该版在世界更新末尾处理 sensor 结果；调用完成后再读取本步事件，而不是在更新之前找本步事件；应用修改形状等操作也有文档规定的处理时机。[2]

这些检查是在确认输入条件，不是承诺任意速度、任意数量的区域或任意运动都一定完整捕获。若条件看似正确，仍应把问题缩成一颗子弹和一个区域，记录起止形状、过滤及更新顺序，再检查项目实际行为。本文没有替项目做这一步验证。

## 必须由游戏查询时，要扫什么，不能只问扫没扫

如果使用的是旧版不覆盖的路径，或玩法对象超出了所选事件机制的范围，可以考虑由游戏查询层检查运动区间。但“加一条射线”还不是完整决定。

**射线只代表一个点沿线移动。** 若规则关心子弹整个圆形是否碰到检查线，中心线没有碰到，不等于圆形没有碰到；相应的形状查询才表达这个体积。Box2D 的 shape cast 沿给定平移移动一个形状，适合说明“静止目标、形状不旋转、沿直线移动”的有限情景。[4]

初始位置也要单独想清楚。子弹生成时已经在区内，是立即算通过、等它离开再进入，还是不计分？这首先是玩法规则。不要用最近射线命中接口顺手代替初始占用检查：3.2.0 的 `b2World_CastRayClosest` 会忽略比例为零的初始重叠结果；这与通用射线回调入口的处理并不相同。[5] 这里不把这一条规则推广到所有查询接口。

查询还有自己的过滤。该版的世界射线和形状查询并非一概排除 sensor，但仍检查查询与目标的类别和掩码；开启 sensor 事件，不等于配置好了查询过滤。[5] 查询到候选区域以后，应用仍要决定它是不是本次记分对象。

若一段运动经过多个区域，回调到达顺序也不能直接当作通过顺序。官方文档说明多命中查询结果可以无序送达；需要沿路径排序时，应收集相应结果再处理，且另定相同比例时的规则。[4] 最后还要指定由谁结算：如果引擎事件和额外查询同时报告同一次经过，两条路径不能各加一次分。

## 移动和旋转超出这个小例子的范围

上面的直线查询把目标视为静止。如果区域本身也移动，拿它在某一刻的位置做一次查询，没有自动描述两者整个时间区间的相对运动。不能把静止目标方案直接当作移动双方的修复。

细长武器绕中心转动也类似。中心可以完全不动，武器末端却扫过一大片区域。只提交“中心位移为零”的线性 cast，就没有表达这次旋转；这不是查询代码已经被证明漏报，而是输入根本没有描述想检查的运动。Box2D 有包含初末姿态的连续检测输入，但对应文档仍保留旋转碰撞的限制。[6] 本文不提供通用旋转扫掠算法或安全子步数。

因此，排查顺序可以收束成一条具体路线：**先写明要判断占用还是经过；再核实际版本和事件条件；需要查询时，明确体积、起点、运动范围及过滤；最后才决定多结果顺序和玩法结算。** 这比先把所有精度开关调高，更容易知道到底缺少了哪一种信息。

如果问题其实是模拟步怎样推进，继续读[用固定时间步组织战斗模拟](../时间与模拟/用固定时间步组织战斗模拟.md)。固定时间步让观察时刻更清楚，但不会替你选择传感检测方法。
