# 用固定时间步组织战斗模拟

一段攻击动画在每台机器上看起来差不多，但高帧率时冷却更快结束，卡顿以后又连续触发了几次攻击。问题可能不是动画本身，而是战斗规则跟着画面刷新次数走了：显示一帧，就减一次计数；一帧补算多次，又重复使用了同一个“按下攻击”标记。

本文面向玩法程序员，讨论以数值、状态机和离散规则为主的战斗系统。我们先用几个小数字说明固定时间步如何工作，再组织输入、模拟和显示。目标不是提供完整物理引擎或联机框架，而是让你能回答：规则推进了多少次，每次用了什么输入，以及卡顿时剩下的时间怎么处理。

## 画面刷新一次，不等于战斗推进一次

先区分三种时间：

- **现实经过时间**：机器上的单调时钟测得的时长。单调意味着它不会因系统校时突然倒退，适合测量间隔。
- **游戏时间**：项目决定计入游戏的时长。暂停时可以不增加，慢动作时可以比现实时间走得慢。
- **模拟步编号**：战斗规则已经执行到第几步，常称为 tick。每一步代表固定长度的游戏时间。

画面刷新则有自己的节奏。同一段现实时间里，可以显示许多帧，也可能只显示几帧。固定时间步不是强迫画面固定帧率，而是让战斗每次只推进相同长度的时间。

例如为了便于手算，设每步 `h=10毫秒`，也就是每游戏秒100步。这只是教学选择，不是战斗游戏统一推荐频率。一段持续30毫秒的规则，在本例可以明确占据三个模拟步；无论这三步之间画了几帧，都不应该被画面刷新次数重新定义。

固定步长也不是说“所有计算都不再乘时间”。若速度单位是每秒，更新位置仍需要乘固定的 `h`。区别在于每次规则推进使用同一个 `h`，而不是把忽长忽短的显示帧间隔直接传进去。

## 用累积时间连接两个节奏

把尚未模拟的游戏时间存进一个变量，称为**累加器**。每次主循环加入新经过的游戏时间；每够一个 `h`，就执行一步并扣掉 `h`。不足一步的余量留到下次。

这正是 Fiedler 在 *Fix Your Timestep!* 中讨论的模拟与渲染解耦思路；该文也讨论了补步追赶的负担和显示插值。[1] 下面的数字及过载选择是本文的具体例子。

假设开始时累加器为0，连续三次主循环分别增加6、17、7毫秒：

| 本次新增游戏时间 | 加入后待处理时间 | 本次执行 | 留给下一次 |
|---:|---:|---:|---:|
| 6毫秒 | 6毫秒 | 0步 | 6毫秒 |
| 17毫秒 | 23毫秒 | 2步，共20毫秒 | 3毫秒 |
| 7毫秒 | 10毫秒 | 1步，共10毫秒 | 0 |

累计30毫秒，规则执行三步。第一帧不执行战斗、第二帧连执行两步，都可以是正常情况；不能要求每个画面帧恰好有一次战斗更新。

因此应有一个明确的模拟入口，例如“推进一步战斗”。冷却、攻击窗口和状态转换都从这里推进，而不是部分放进画面更新、另一部分又放进固定更新。若引擎已经替你调度固定回调，就用它作为这一入口；若选择自己管理累加器，就不要再让另一个固定回调推进同一份战斗状态。

## 卡顿以后，先决定欠下的时间怎么办

假设突然积累了100毫秒，按本例需要补10步。若所有步都立即执行，画面可能继续卡住。补算越多，下一轮又积累越多时间，便可能形成追赶不上的循环。[1]

一个常见保护是限制每次主循环最多执行 `K` 步。但**限步只决定这一次花多少工作，尚未决定剩余时间的去向**。

本文选择 `K=4`，并保留剩余时间。于是本轮推进40毫秒，留下60毫秒等待以后处理。没有跳过战斗步骤，但模拟现在落后于目标游戏时间；持续过载时，输入响应和显示都会受影响。只有后续确实有计算余量，才可能逐渐追上。

另一种政策是舍弃部分累计时间。这能避免无限追赶，却改变了现实时间与游戏时间的关系；需要记录丢掉多少，并重新考虑按时间戳分配的输入和计时器。它不等于“仍然完成了所有战斗步骤”。尤其在共享权威状态的联机设计中，不能让每个客户端各自决定跳过不同的规则步骤。

同样，有意让整个游戏钟慢下来，与已经承诺推进却没算完的时间不是一回事。本文只实现保留余量的选择，不把它宣称为所有项目最佳策略。若持续积压，应该降低非关键工作负担，或由上层决定暂停、减速或重同步，而不是悄悄清零后继续假装没有发生过。若选择减速，还应分开记录“计划推进多少游戏时间”与“相对这个计划尚未完成多少工作”，并明确哪些计时义务仍按现实时间走。游戏钟已经变慢，工作仍可能继续积压；反过来，有意放慢的那部分时间也不应全算成待追赶的债务。

## 输入必须分配给模拟步，而不是复制给每次补算

假设一次主循环开始时收到了“按下攻击”，随后需要补三步。如果这三步都读取同一个 `attackPressed=true`，一次按键就会变成三次攻击请求。

要分开两类输入：

- **持有状态**，例如移动方向。项目可以规定它持续有效，直到后续输入更新。
- **一次性事件**，例如一次按下攻击。它应作为一条命令交给某个模拟步，并在消费后移走，而不是每步重新生成。

还要避免在采集时就把一次按下漏掉。例如 SDL 3.2.0 的 `SDL_GetKeyboardState` 给出当前键盘状态；如果处理事件前已经完成按下和松开，那次按下可能不会出现在随后读取的状态里。[7] 因而，一次性攻击不宜只靠比较前后两次持有状态来恢复；采用键盘事件时，应按项目规则处理 `repeat` 标记，识别一次有效按下，再把它记成命令，而不是将持续持有或键盘重复当作同一种意图。这是事件采集与命令分配的区别，不是本篇做过的设备输入测试。

一个容易起步的本地政策是：收集输入时，把新命令分配给“下一个尚未执行的步”。命令记录目标步、角色和顺序号，同步到这一步后消费一次。它简单，但不是唯一选择，也不保证设备操作发生在现实时间的哪一刻，就落在精确对应的历史模拟时刻。

例如积压了很多步以后才收到一个新按键，按这个政策，它会进入最早尚未算完的那一步。若项目需要按设备时间戳还原输入发生时刻，就必须另外建立时间到步编号的映射，并处理迟到命令。拒绝、移到未来步或回滚重算是不同政策，不能静默混用。

**相同模拟步命令记录，与相同现实按键动作不是一件事。** 两台机器在不同主循环时刻采样，可能把同一次现实操作放进不同步。要比较规则复现，应重放已经记录好的“第几步收到什么”，而不是重新采样键盘后期待日志天然相同。Fiedler 的锁步文章也强调输入所属模拟帧，并指出确定性还受计算环境和处理顺序影响。[2]

暂停同样需要明确输入处理。如果玩法停止消费，但菜单或常驻输入节点仍在收集攻击，恢复后可能执行旧命令。可以根据设计清空攻击事件、重新取得移动持有态，或允许某些预约；关键是明确选择。暂停期间仍应更新现实计时基准，恢复时不要把暂停的几秒误当成需要补算的战斗时间。本例暂停时也停止处理暂停前留下的欠账：保留累加器，恢复后再按补步上限继续处理，而不是仅把新增时间设为0。

## 将方法写成一个调度循环

现在可以组合前面的决定。下面是教学伪代码，不是引擎可直接粘贴运行的完整实现：

- `h` 为严格大于0的固定步长，并与 `gameDelta`、`A` 使用同一时间单位；`K` 为正整数补步上限。
- `A` 初始为0，保存待模拟游戏时间；`nextTick` 是下一步编号。
- `current` 是当前战斗状态；`previous` 初始为它的独立副本。
- `Step` 只推进一步规则。命令队列已按前述政策分配到目标步。
- `simulationPaused` 明确表示模拟是否暂停。现实计时基准在每轮都更新；暂停期间 `gameDelta=0`，未暂停时它是应用时间缩放后的非负新增游戏时间，本例没有偷偷截断它。

```text
A = A + gameDelta
steps = 0

while not simulationPaused and A >= h and steps < K:
    previous = 独立复制(current)
    commands = 取出并移除目标为nextTick的命令
    current, events = Step(current, h, nextTick, commands)
    将events交给表现接收者
    nextTick = nextTick + 1
    A = A - h
    steps = steps + 1

记录本次steps与剩余A

if simulationPaused or A >= h:
    显示current
else:
    alpha = A / h
    显示previous与current之间的可插值属性(alpha)
```

暂停时循环执行0步，不消费战斗命令，既有 `A` 保留。例如上一轮留下60毫秒，即使足够再补步，也必须等恢复后处理。本例暂停期间显示最新完成的 `current`，不继续插值；若进入暂停前显示的是插值位置，切到 `current` 可能产生小幅跳动。这是明确的教学选择，项目也可以另行冻结最后一帧的显示结果，但不能因此推进战斗。

`previous` 不能只是指向同一可变对象的别名，否则更新 `current` 后，“前一个状态”也一起被改掉，插值失去意义。表现接收者只能读取结果，不应再根据画面帧数减少冷却或重复结算伤害。

时间累积采用什么数值表示，也需要实现者决定。本文数字可以精确手算；实际程序要留意浮点累计误差或整数计时单位的精度，不能任意加入一个容差就假定所有边界都正确。

## 插值改善显示，不推进战斗

模拟只更新到离散时刻。如果直接显示最近状态，物体的显示位置可能阶梯式变化。**插值**就是在两个已知状态之间计算一个显示值，而不是多执行一次规则。[1]

正常情况下 `0≤A<h`。假设前一步位置是0，当前位置是10，余量为 `A=0.3h`，则线性插值显示3。这个显示来自过去两个完成状态之间，按这种做法通常会落后目标游戏时间一个模拟步；它不是预测未来位置。

若限步后还欠 `A=6h`，直接拿 `A/h=6` 当权重会得到远超两个状态之间的位置，那已经是外推。上面的方案此时选择显示最新完成状态，不声称它已经追上现实时间。

也不是所有字段都应该插值。位置可以按所选规则平滑，瞬移要单独处理；“是否死亡”、伤害结算和一次攻击事件不能按0.3次来显示或重新发生。一次模拟产生的声音／特效请求，应由接收者按事件身份处理，而不能每个画面帧看见同一快照就重新创建。回滚后的重复、撤销和新增表现需要另一套规则，本文不提供恰好一次发布保证。关于重放期间哪些输出应保留、撤销或新增，可进一步看[客户端纠正中的表现处理](../../../网络与在线服务/实时同步/移动预测/客户端移动预测与服务器纠正.md#重算一次移动不该把所有输出再做一次)。

## 固定步不替你决定战斗规则，也不自动带来确定性

如果一次攻击在本地攻击步6、7、8有效，可以写成半开区间 `[6,9)`：包含6，不包含9。执行到9时应结束有效窗口，不依赖画面恰好经过了哪个时间点。这是一个明确的玩法规则示例，并不是所有技能都必须按整数步配置。

不过，A和B在同一步互相造成致死伤害，仍然需要决定是允许相杀，还是先手击杀会中断反击。固定步长本身没有答案。即使每次都按同样的角色顺序计算，结果可重复，也可能实现了设计不想要的先手政策。例如A、B都只剩1点生命，本步各应造成1点伤害：若按步开始时的存活状态确认两次攻击，再统一结算，双方都会死亡；若先扣掉B的生命，再检查B能否攻击，则只有A存活。把A固定排在前面只能让后一结果每次相同，不能让它变成相杀规则。这里是手算示意，不是本次执行结果；实际伤害、治疗或复活如何冲突仍需项目另定。

**确定性**通常指相同初态和输入得到完全相同的结果。要争取这种性质，还要管理随机数、命令顺序、配置版本以及计算环境；浮点、编译选项或物理后端的差异可能破坏复现。[2] 固定时间步为比较提供了清楚的编号，不能凭空保证跨平台物理一致。

项目接入根运动或物理碰撞时，还需要明确它们在哪一步参与、结果怎样影响战斗。根运动是从动画得到的位移或旋转；如果它决定实际移动，就不能把动画系统假设成纯粹只读的画面层。本文的调度结构不消除这种依赖。

## 接入项目时，先检查这几件事

先用一小段可辨认的命令记录，而不是整个战斗关卡，检查以下现象：

| 情况 | 本文所选政策应发生什么 |
|---|---|
| 主循环分别新增6、17、7毫秒，h=10毫秒 | 执行0、2、1步，最终无余量 |
| 一次积累100毫秒，K=4 | 执行4步，保留60毫秒；显示不外推 |
| 一次攻击按下之后补3步 | 该命令只进入指定的一步，不复制成3条 |
| 规则窗口为[6,9) | 6、7、8有效，9无效 |
| 相同命令记录采用不同画面分片 | 比较到相同步编号的状态，而非不同进度的同一现实时间 |
| 保留60毫秒欠账后暂停与恢复 | 暂停执行0步、不消费战斗命令，保留60毫秒并显示current；现实计时基准继续更新，恢复后按上限补算，并按既定政策处理积存输入 |

这些是实施检查建议，没有在本文重跑。若发现差异，先记录首个出错步及其输入，再追查调度、消费和规则计算，通常比只看最终血量更容易找到原因。

## 附：引擎接口与既有验证能说明什么

Unity 6000.0 的文档说明，最大时间步会限制记录与模拟的时间，游戏时间不一定追上现实经过时间；Input System 1.11.2 又区分 Dynamic、Fixed、Manual 输入处理。[3][4] 因此接入 Unity 时，应先确认使用的是哪种时钟和输入更新方式，不能把本文“保留全部余量”的政策默认归给引擎。本文没有运行 Unity。

Godot 4.6 文档区分随画面更新的 `_process` 与固定频率的 `_physics_process`。[5] 本库旧研究曾在本地自报4.6.3的程序中，用单一固定回调消费预先指定到步的输入，并让普通更新只读取数值状态；在所测30/60/144配置下，运行到相同120步终点的结果一致。这个有限观察没有包含真实设备输入、可见渲染、刚体碰撞或卡顿余量策略，也没有建立本地程序与官方发行源码的认证对应。

其中人工时间模式使用的 `--fixed-fps` 会关闭实时同步，不能把它当成真实显示帧率测试。[6] 本章只保留这些理解结果所需的范围说明，不迁移旧日志或新增运行。原有Python调度模型及Godot各专题的材料仍分别保留；它们不能替项目完成平台、物理和联机验证。
