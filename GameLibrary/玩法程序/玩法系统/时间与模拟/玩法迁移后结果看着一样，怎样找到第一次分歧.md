# 玩法迁移后结果看着一样，怎样找到第一次分歧

把网格规则从旧引擎搬进新运行时，跑完一段移动后，位置和所在格都对上了。可是旧版会在踏入边界另一侧时触发机关，新版没有。角色绕回了同一个地方，漏掉的触发已经从最终状态里看不出来。只比终点，很容易把这种迁移判为通过。

对已经能按步执行的离散规则，先让新旧实现读取同一份小记录，再比较每步真正收到的命令、影响后续的状态和发出的规则事件。这样不必先抽象整个引擎。你要验收的是这一块规则的行为，以及接入层有没有把同一件事递给两份实现。

## 先让两份实现做同一道题

最小记录分三部分：

- **开局条件**：记录格式版本、规则与内容版本、起始步和规则初态。按需要加入规则读取的冷却、待处理队列、随机数状态等，而不是一份屏幕上看得见的摘要。要从第 50 步接跑，就保存第 50 步结束后的完整恢复状态，并从第 51 步起消费命令。
- **每步输入**：记录目标步、步内序号和内容。步内序号按命令彼此的执行顺序生成，不从散列表遍历顺序推断。命令与冷却到期、查询等规则阶段的先后也要随规则版本固定，例如同一步先取消护盾再检查到期，和先检查到期，会发出不同事件。也记录空步或明确允许推导空步，不把冷却、到期检查等没有命令的步跳过去。规则若会读取引擎查询、时钟或异步结果，就确定这些信息在哪一步进入、以什么顺序交付。
- **每步输出**：保存本步消费的命令标识、结算后的规则字段，以及按约定顺序发出的规则事件。进格事件若会触发机关、造成伤害或推进任务，就在规则输出处记录，不用摄像机、音效或动画的结果代替。没有事件也要有一条明确的空输出。

例如测试碰撞后发不发伤害，先把旧运行时的查询键与命中事实一起记录，复跑时要求新实现按相同步和顺序请求同一组查询，并把这些事实交给它。不能让一个未匹配的请求静默复用前一条命中结果。若这样能对上伤害，只说明**给定同一组查询事实时**两份结算相同。还要让新旧运行时用可比场景分别做真实查询，比较送进规则的事实，才能验收物理接入。这两次测试不能互相代替。

Riot 的《英雄联盟》服务器恢复实践也是先选择对玩法重要的状态，再按帧记录不能消除的输入，包括按服务器接收顺序的网络输入。团队保留了可变帧间隔并记录它，没有为此把服务器切成固定步。[1] 借鉴的是捕获真正影响结果的信息；本例的固定步是被迁移规则已有的约定，不是重放的硬性前提。

## 看第一处不同，而不是最后差多少

下面只迁移一条进格规则。格宽 10，格 k 的区间定义为 [10k, 10(k+1))；位置以整数单位记录，步末落入和上一步不同的格才发事件。不枚举两端之间穿过的格。初始位置和格号都是 0，依次移动 −1、+1、−10、+1、+9、+10。

| 步 | 位移 | 步末位置 | 按区间定义：格 / 事件 | 直接用 C++ 整数除法：格 / 事件 |
|---:|---:|---:|---|---|
| 1 | −1 | −1 | −1 / 进入 −1 | 0 / 无 |
| 2 | +1 | 0 | 0 / 进入 0 | 0 / 无 |
| 3 | −10 | −10 | −1 / 进入 −1 | −1 / 进入 −1 |
| 4 | +1 | −9 | −1 / 无 | 0 / 进入 0 |
| 5 | +9 | 0 | 0 / 进入 0 | 0 / 无 |
| 6 | +10 | 10 | 1 / 进入 1 | 1 / 进入 1 |

第 1 步消费的位移相同，位置也都正确，最早不同的字段是格号。按半开区间定义，−1 属于 [−10, 0)，应在格 −1；C++ 整数商向零截断，−1 / 10 得到 0。C# 的普通整数除法也向零截断。如果旧 C# 实现正确，不是因为换了语言就一定变了，而是它原本落实了格子的取整政策，移植时必须保住。[2][3] 这里用 Python 整数的向下整除当作另一份对照，先由区间定义判断期望，再让两份实现互相核对。[4]

在格宽为正、位置和商都在约定整数范围内时，C++ 可先算 q = x / width、r = x % width，若 r < 0 则 q 减 1。r 为 0 表示恰好踩在边界，第 3 步的 −10 仍是格 −1。不要为方便先转浮点再取整；这样又加进一个精度约定。这份例子把轴位置和位移限制在 ±10⁹，64 位的加法中间结果不会溢出；迁移真实规则时，连中间乘加的范围和溢出处理都要进入约定，不能只规定最后字段的位宽。

[本地复现](../../../../管理档案/实验/玩法迁移重放/README.md)将 C++ 两种取整结果和 Python 独立实现逐步比较：错误版本第一步就不同，改过的版本六步均和 Python 对照相同。第 6 步连本步发出的事件都恰好相同，整段事件却已经无法从尾部恢复。这只是整数格子规则的验证，并未运行旧 C# 或任何游戏物理。

## 输入、规则和输出分开查

找到日志中第一处差异后，按产生的阶段缩小范围。它是已记录字段的第一处差异，不保证是程序内部最早犯错的位置：

1. **消费前已经不同**：比较原始记录和两边解码后的命令。检查实体映射、单位、编号、步内排序、丢掉的空步。如果规则本身还没跑，先不去改碰撞或公式。
2. **消费相同，状态第一次不同**：确认上一步具有同一个完整规则初态，本步外部查询与时间数据也相同。再展开第一个不同字段的中间值，如本例的除数、商和余数。有些字段（如剩余冷却、随机流位置）画面不可见，却可能是更早分歧的起点。
3. **规则字段对得上，发出的事件不同**：比较事件类型、稳定实体标识、顺序、参数和重复次数。先对比规则发出端；如果这里已一致而游戏里仍漏了表现，才查接收器。这两层可能都错，修完一层要重新跑整段。

记录本身也会引入分歧。本地第二个试件用 Node.js 按默认方式解析 JSON：数值 9007199254740992 和 9007199254740993 在解析后相等。把两者作为规范十进制字符串写出，接收端直接转 BigInt，则仍是两个不同 ID。[5] 如果这种 ID 先被转成 Number，稍后改成字符串也无法找回已经丢失的那一位。输出端要从精确整数直接编码，接收端先检验格式、位宽和正负范围，再转入自己的整数类型；命令与事件的顺序用数组表示，不借助 JSON 对象键的排列。

## 让对照能进日常测试

从一个读者或测试人员能手算的短场景开始：原点两侧各一步、恰在边界、离开后回到原状态。保存旧版输出作对照，但同时写下独立的设计期望，避免两份实现共享同一个错误。有些旧版行为的确要有意改变，单独列出哪些输入、哪个步、哪个字段或事件应该变，不要把全部基准重新生成来消掉差异。规则或内容更新后保留版本，无法比较的版本不直接判通过。

短测试直接逐步比较结构化字段即可。长重放若要压低日志量，可按段保存由**每步**规范化记录组成的摘要：固定字段类型与编码、以稳定 ID 排列没有顺序含义的对象、保留有语义的命令与事件顺序，并给记录加长度或采用明确边界的编码。同一段摘要不同，再用原记录或从最近的完整检查点复跑，展开该段第一步有差异的字段。只保留段末状态的摘要，仍会错过绕出去又回来的情况；摘要一致也只覆盖放进去的字段。JCS 是一种规范化 JSON 字节的做法，使用它之前仍需约定大整数等数据的表示，不能把已发生的精度损失交给规范化补救。[6]

如果规则原本依赖引擎里的碰撞、随机数或回调顺序，先把实际决定行为的少数边界记录下来。只给这些边界写转换和对照，通常比先定义一套覆盖引擎的通用接口更容易找出第一处不兼容。逐步测试通过后，再用真实内容测输入接入、碰撞和表现各自的运作；那是新运行时还要单独履行的部分。
