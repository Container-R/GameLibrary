# ATLAS为什么用水面拟合平面来决定船的目标姿态

船的中心正好停在海面高度，船头却已经顶进浪里。把中心抬高一点，另一端又可能离水太远。排查这种示意情景时，问题不只是“船应该多高”，还包括“船覆盖的这片水面向哪边倾斜”，以及船要多快地跟随这种变化。

本文面向玩法与物理程序员，也供需要提供水面数据的图形程序和技术美术阅读。我们从 ATLAS 的公开演讲取舍出发，用四个采样点说明：**水面高度、局部倾斜和船的实际响应，是需要分别处理的信息。** 文中的数值与几何推导是原创纸面例子，没有运行船体或水面模拟。

## 讲者保留采样，改变的是怎样使用采样

2019 年 GDC 课件比较了逐样本施力与另一条响应路径：保留水面样本，拟合平面，用它构造船的目标变换，再用弹簧跟随。讲者列出的约束包括采样随时间的噪声、服务器模拟常低于 10 Hz、刚体动力学的延迟和不稳定，以及大浪中的玩家舒适感。[1] 这是当时演讲说明的设计取舍，不能仅据此还原游戏各版本的改动历史。

下面只借这个问题展开几何与接入分析，不重建团队的算法。逐点施力时，样本要先转成作用，再参与后续动力学求解；以平面构造目标时，样本先描述一个希望船去接近的空间状态。两条路径对数据的用途不同，判断它们是否合适，也需要不同的检查。

## 相同的平均高度，可以藏着不同的倾斜

先选一个固定世界坐标系：`x` 沿本例船的长向，`y` 沿横向，`z` 向上，长度单位均为米。这里是在水平面上选一个长 4 米、宽 2 米的矩形采样范围，不是给船建立完整船底几何。

在四个位置分别取得水面高度。为方便比较，情况 A 是水平面 `z=0`；情况 B 是倾斜平面 `z=x/2`：

| 水平位置 `(x,y)` | A 的高度 z | B 的高度 z |
| --- | ---: | ---: |
| `(-2,-1)` | 0 | −1 |
| `(-2,1)` | 0 | −1 |
| `(2,-1)` | 0 | 1 |
| `(2,1)` | 0 | 1 |

两组的四点算术平均高度都是 0；在中心 `(0,0)` 取得的高度也都是 0。如果只把这一个数交给船，接收方就无法分辨 A 与 B。

但在 B 中，沿 `x` 从 −2 米走到 2 米，水面上升了 2 米；沿 `y` 改变位置，高度没有变化。平均以后，这项方向信息被消去了。问题不是平均数算错，而是它回答的只是一个高度问题。

若把 B 的四个高度统一再加 3 米，水面会整体抬高，倾斜程度保持不变。这个简单变化说明，还应把**整体升降**与**朝向变化**分开表示，避免用一个参数同时承担两件事。

## 平面提供了朝向，但还不是船的完整姿态

平面的朝向可以用**法线**表示：它是垂直于平面的方向。我们统一选向上的一侧，并将向量长度归一化为 1，便于比较。

A 的向上法线是 `(0,0,1)`。对 B，沿 `x` 每前进 1 米，高度增加 0.5 米，因此平面内有方向 `(1,0,0.5)`；沿 `y` 的平面内方向是 `(0,1,0)`。同时垂直于它们的向上方向为 `(-0.5,0,1)`，归一化后得到：

`nB = (-1/√5, 0, 2/√5)`

所以 A、B 虽然平均高度相同，法线却不同。B 相对水平面的倾角是 `atan(0.5)≈26.565°`，其中 `atan` 是反正切。**这个角度只描述本例平面的倾斜，不是 ATLAS 船体实际旋转的角度，也不是应直接写入船对象的欧拉角。**

本例四点分别精确落在同一平面上，可以直接写出这两个平面，没有使用任何最小二乘损失、样本权重或团队的拟合代码。真实波面上的点未必共面，那时才需要定义：用哪个平面近似这些点，以及怎样衡量误差。选择不同的拟合规则，可能得到不同目标；“做平面拟合”这句话本身还没有规定这些细节。

即便已经有平面，也只解决了部分空间信息。假设规定船体的上方向与法线对齐，绕这条法线转动船头，仍满足这个规定；船沿平面移动，也不改变这个平面。因此，目标构造还要处理：

- **船头朝向。** 航向与转向规则怎样参与，不能只从水面法线推出。
- **船与水面的偏置。** 哪个船体参考点对齐到哪里，船底或甲板离平面多远，需要单独定义。
- **实际移动与碰撞。** 目标若进入码头、其他船或障碍，最终状态由哪部分处理，不能靠水面平面自动解决。

这些是使用这种表示时必须补充的设计问题，不是本文发现的 ATLAS 内部规则。把它们藏在“对齐水面”的函数名下，只会让问题晚一点暴露。

## 有了目标，仍要决定怎样接近它

假设连续两次采样得到 A、B。目标平面从水平变为倾斜，表达的是新的期望状态；船现在已经在哪、怎样朝它变化，是另一层问题。

如果每次得到平面就立即改写船的变换，输入中的突变也会直接进入船的运动。接入一个跟随过程，则需要明确当前状态、目标和推进时间，并选择响应速度。设计者要在可接受的滞后、倾斜幅度和变化速度之间作取舍，不能只以“数值更平滑”判断玩法是否合适。

本例不提供弹簧公式，也不借“弹簧”这个名称保证稳定。具体响应取决于选用的模型、参数、时间推进和输入。应该先分别显示目标与实际姿态：如果目标本身在跳，检查采样与拟合；如果目标符合预期而实际运动不合适，再检查跟随方式及与其他运动的组合。否则，把响应调得越来越慢，可能只是把错误目标藏了起来。

时间安排也要说清楚。水面样本属于哪个时刻，目标在哪次更新生成，跟随在哪次更新推进，应有一致约定。画面重绘不应悄悄变成额外的模拟推进。需要先整理这层关系时，可读[用固定时间步组织战斗模拟](../时间与模拟/用固定时间步组织战斗模拟.md)；它说明调度边界，不替这里选择弹簧或船体规则。

## 先确认查到的是目标位置的水高

上面的四点例子直接给出了世界位置的水高。实际接入前，还要确认水面接口返回的量是什么。原课件说明水面输出包含三维位移，并给出迭代近似来反查水高。[1] 因而，不能未经核对就把未变形表面的采样坐标，等同于位移后的世界位置。

本例把这一步留给水面查询接口，没有实现反查。固定迭代次数、误差阈值和无有效结果时怎么办，都不能从“迭代近似”四个字中得到保证；若查询已经错位，后面的平面拟合仍可能得到一个形式正常、位置却不对的结果。

查询还要说明它代表哪一种海面细节。《War Thunder》的 2015 年课件给出了另一个项目的取舍：物理使用低分辨率 CPU 海面，在服务器与客户端采用同步时间和同一频谱；绘制则按画质采用不同分辨率，从最高分辨率频谱向下重采样。这里的频谱可以理解为生成波浪所依据的成分，并不是一张所有使用者共同读取的最终水面网格。[2]

两条路径的更新节奏也不同：课件中的物理按固定步推进，图形在客户端逐帧更新。课件对“同步时间和同一频谱”的说明，针对服务器与各客户端的物理模拟；不要把它读成物理与图形每帧同时更新，或不同分辨率的位移逐点相同。排查“船明明浮在物理水面上，画面却像穿浪”时，除了反查坐标，还应确认船读的是哪一路水面，以及它与画面细节之间允许有多大差异。这是由案例引出的接入检查，不是 ATLAS 采用了该实现，也不是两条路径在任意项目中都能直接互换。

## 用这四个点检查接入，不必一开始就调大海

实现者可以先把真实海面替换成上述已知输入，分别观察采样点、目标平面和船的实际状态。下面是建议的检查，不是本库执行过的测试：

1. **输入 A。** 目标应能表达水平朝向。船的高度是否为 0，仍取决于已声明的参考点与偏置规则，不能只凭水高判错。
2. **输入 B。** 即使平均高度仍为 0，也应保留与 A 不同的倾斜信息。若目标完全相同，检查是否在拟合前就把样本压成了单一平均值。
3. **把 B 的所有高度加 3 米。** 在本例所要求的几何表示中，平面应整体上移、法线不变。这可以帮助发现位置与方向的混用。
4. **让采样范围失去宽度。** 若所有点都落在 `y=0` 且满足 `z=x/2`，那么 `z=x/2+c·y` 对任意 `c` 都经过这些点。数据已无法唯一确定横向倾斜，应由实现明确处理这种退化，而不是接受一个任意法线。

最后再接回真实波面，检查非共面样本、采样失效和运动冲突，并观察目标变化与实际响应是否符合玩法需求。平面只是局部水面的简化表示，不能保留各点之间所有起伏，也不直接给出真实排水体积或受力分布。即便四个角点都吻合，它们之间仍可能有未采到的弯曲与浪峰，不能因此判定整个船底与水面都贴合。若玩法需要局部碰撞、船体结构受力或其他水动力信息，就要另行提供这些信息，不能指望一个朝向与高度包办。

回到开头：只把船中心放到正确高度，仍可能丢失船头与船尾之间的关系。这个案例值得借鉴的，是先问清采样要提供什么，再把局部几何、目标构造和运动响应分别检查，而不是把某个更“物理”或更平滑的选项当成通用答案。
