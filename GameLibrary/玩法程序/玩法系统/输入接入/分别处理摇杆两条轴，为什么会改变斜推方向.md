# 分别处理摇杆两条轴，为什么会改变斜推方向

角色本来应该沿一个斜方向移动，接入代码改成分别读取摇杆 X、Y 之后，却更偏向其中一条轴。两边配置的死区数值明明相同，是不是手柄坏了？

先别急着换设备。对于二维输入，**分别处理两个分量，再把它们拼起来，不一定等于处理整个向量**。死区处理如果包含重新缩放，即使两个分量都没有被清零，比例也可能改变。

本文面向玩法程序与输入接入人员，用 Unity Input System 1.11.2 的两种固定实现说明这个区别，再做一个纸面计算。没有连接控制器或运行 Unity；例子中的输入是进入处理器的数值，不是实际测得的设备报告，也不代表玩家意图已被准确捕获。

## 死区不只是“小于门槛就忽略”

死区常用来忽略中心附近的小输入。但如果只把小值设为零，跨过门槛时，输出可能直接跳到那个非零值。因此，还需要弄清所用处理器是否会把剩下的范围重新映射。

这里的 `AxisDeadzoneProcessor` 处理一个标量：输入绝对值低于 `min` 时归零，超过 `max` 时饱和到 +1 或 −1，中间则先减去 `min`，再除以 `max−min`，最后恢复正负号。[1] 对本篇采用的有效参数，恰好位于两个边界的输出分别为 0 和 ±1。

`StickDeadzoneProcessor` 先求整个二维向量的长度，对长度做同样的映射，再按新长度与旧长度的比例一起缩放 X、Y。[2] 按本文的理想实数解释，因为两个分量乘的是同一个数，输出非零时保持输入方向。这称为**径向死区**；它控制离中心多远，而不是分别问横向和纵向离中心多远。

以下都显式使用 `min=0.2`、`max=0.8`，且只讨论有限数值。这些参数为了便于手算，不是推荐设置。在这个版本中，字段写成 0 会改用 InputSettings 的默认值，不能把填 0 当成必然关闭死区。[1][2]

## 同一个斜向输入，为什么得到两个方向

设进入处理器前的向量为：

```text
v = (0.3, 0.4)
长度 = √(0.3² + 0.4²) = 0.5
```

先分别处理 X 与 Y。两者都处于 0.2 到 0.8 之间，因此：

```text
X 输出 = (0.3 − 0.2) / (0.8 − 0.2) = 1/6
Y 输出 = (0.4 − 0.2) / (0.8 − 0.2) = 1/3
拼回向量 = (1/6, 1/3)
```

原输入的 Y/X 比例是 4/3，输出却是 2。方向已经变了。原因并不是哪条轴被截成零，而是**两个分量分别减掉相同的门槛，改变了它们之间的比例**。

再看径向处理。原长度为 0.5，映射后的长度为：

```text
新长度 = (0.5 − 0.2) / (0.8 − 0.2) = 0.5
统一缩放比例 = 新长度 / 原长度 = 1
输出 = (0.3, 0.4)
```

本例恰好得到原长度，不表示径向处理从不改变幅度。它保留的是非零向量的方向，而长度仍按门槛重新映射。

这些是依据公式所作的理想实数计算，不是 Unity 的逐位浮点输出。如果把逐轴结果再单位化，也只是同时放大两个分量，其比例仍为 1:2，不能把原方向找回来。反过来，逐轴处理并非每次都会改向：沿坐标轴或两个分量对称时，就可能保持方向。

## 最大门槛和最终长度也不是同一回事

再取输入 `(0.6,0.8)`，它的长度为 1，已经超过本例的 `max=0.8`。径向处理把长度限制为 1，仍得到 `(0.6,0.8)`。

逐轴处理却得到 `(2/3,1)`：X 仍按区间缩放，Y 恰在最大门槛。两个分量分别不超过 1，合成向量的长度却是 `√13/3`，大于 1。若后续用向量长度控制速度，就还需要明确怎样处理这个结果，不能把“每条轴已限幅”当成“整个向量已限长”。

两者忽略输入的区域也不同：逐轴处理在 X、Y 都落入各自门槛时归零，中心区域是方形；径向处理按向量长度归零，中心区域是圆形。哪一种更合适，取决于操作语义。连续二维朝向与两项独立轴操作不一定需要相同选择；这里没有给所有移动、瞄准或菜单导航指定一种最佳方案。

## 在 Unity 里，先确认究竟读了哪一层

这不仅是两个自定义函数的比较。固定版本的 `StickControl` 文档明确区分整个摇杆与各轴的死区处理，并提醒两种读取结果不必相同。`GamepadState` 为摇杆声明 `stickDeadzone`，而 `StickControl` 为 X、Y 子控件声明 `axisDeadzone`。[3]

这是所查默认布局的具体依据，自定义布局或替换处理器仍可能改变路径。因此，整体读取摇杆与分别调用轴级 `ReadValue()` 后拼成向量，不应直接视为等价。也不要误读为整体路径必然先把两条轴各做一次死区，再做径向死区：所查 `Vector2Control` 的未处理读取路径直接取状态中的向量，或读取子轴的未处理值，而不是调用子轴已经过处理的 `ReadValue()`。[4]

这里的“未处理”是相对于控件处理器而言，**不是硬件原始数据的保证**。平台、设备布局或控制值转换仍可能处于更前面的环节。接入时要说清正在比较哪一层的数值，而不是把任何名为 unprocessed 的读取都当成电气或驱动原始报告。

此外，控件、绑定与动作上都可能配置处理器。已经处理过的值再经过一次死区，得到的是另一条计算链。[5] 本文没有审查某个项目的完整配置；不能仅凭处理器名称和相同参数，就认定实际输入只映射了一次。

## 先找到改向发生的位置，再调参数

如果出现开头的斜向偏移，先确认玩法实际需要什么：要保留二维方向和推杆幅度，还是把两个轴当成独立命令？然后沿接入路径找三处数值：进入死区前、死区后、最终转换成期望速度或瞄准方向后。这些数值需要在项目中实际观察，不能从最终移动方向倒推。

具体要回答：读取的是整个 stick 还是各轴？控件、绑定和动作是否重复处理？`min`、`max` 最终取到的是显式值还是默认值？之后是否还有限长、单位化、灵敏度曲线或方向离散化？只改死区门槛而不核对这些环节，可能把另一层的改向误认为死区效果。

输入过滤与碰撞响应也要分开。方向进入移动器之前就变了，和碰撞后去掉朝墙速度，是不同问题；后者可继续看[贴墙移动中的位移与速度修正](../角色移动/角色贴墙移动时为什么要分别修正位移和速度.md)。确认数值链后，还需要用项目实际支持的设备和玩家操作评估手感；纸面上的方向保持，不会自动证明硬件校准正确、操作更舒适或满足无障碍需求。
