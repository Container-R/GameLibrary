# 本地合作手柄断开后，怎样恢复原来的玩家席位

双人合作中，P1 的手柄没电了，P2 还在移动。P1 插上一只同款手柄：如果它继承了 P2 的角色，或者按下“恢复”就顺便让角色用了道具，重连虽成功，游戏却恢复错了。要保留的是 **P1 对角色的控制权**，而不是系统手柄列表的第一项，也不是上一只手柄的型号。

这里讨论同一台机器上、各玩家各有独占手柄的玩法。系统负责报告设备是否连接；游戏负责决定哪个玩家可以用它，以及从何时开始把输入交给角色。共享键盘、多个设备共同控制一个席位和线上重连需要不同的绑定关系，但仍可沿用这个职责划分。

## 枚举索引、连接实例和玩家席位不是一回事

| 信息 | 能回答的问题 | 不该拿来做什么 |
| --- | --- | --- |
| 枚举索引 | 此刻在设备列表的第几项？ | 作为长寿命绑定键。前面一项移走，后面会前移。 |
| 连接实例 | 事件来自哪一次仍然活着的连接？ | 跨断开识别玩家。同一物理手柄重连也可能换 ID。 |
| 型号、名称、设备 GUID | 当作哪类手柄配置、显示什么图标？ | 将无法区分的同款设备自动分给原玩家。 |
| 玩家席位 | 谁控制哪个角色？该角色的道具、进度和席位设置属于谁？ | 由热插拔列表的顺序重新分配。 |

在 Linux 上用 SDL2 2.32.4 连接两个同名同 GUID 的虚拟手柄，第一只为「索引 0、实例 0」，第二只为「索引 1、实例 1」。拔掉第一只（在实验中为虚拟移除），第二只仍是实例 1，却移到索引 0。再加同款，添入通知写 1，新实例却是 2。随后移走已前移的第二只手柄：它在索引 0，移除通知写的仍是实例 1。

原因是 SDL2 的设备事件字段 `which` 在加入事件里指**索引**，在移除事件里指**实例 ID**。加入时尽快从当前设备信息打开设备并确定实例，不把裸索引存起来供以后认领。若积压事件、打开失败或设备列表已换过，重新核对当前的活动实例与已开启的设备，不把用旧索引查出的另一个设备当作原事件对象。试件中的每个阶段都收到 joystick 和 controller 两类通知；只需要一种抽象时就只消费一种，兼容两类时把热插拔统一到实例层，幂等更新，而不是每收到一条通知就创建一个玩家。[1] SDL2 的有效 ID 可以是 0，SDL3 的无效 ID 才是 0；SDL3 的 joystick 设备通知加入、移除都用实例 ID。[2] 适配层应该先消除版本差异，再交给同一套玩法逻辑。

Unity Input System 1.4.3 的文档也给出一个不易察觉的情况：它会尝试对比设备描述，在平台不能区分同款手柄时，另一只也可能被报成 `Reconnected`。[3] 这个事件可以让恢复界面出现，不能单靠它把席位交出去。如果平台提供能消除歧义且当次可验证的玩家配对，可按该证据自动恢复；如果只有描述或旧设备对象，就请持有新手柄的人明确选回自己的席位。自动恢复省一步操作，却需要可靠配对；显式恢复多一步，但不必猜同款之间的归属。

## 先解除旧绑定，再开放恢复

保留「席位 → 角色」，把「席位 → 本次连接」做成可替换的路由。每席再有一个**绑定代次**，换绑定或解除绑定时递增。异步排队的按钮边沿既带采集时的连接身份，也带采集时的绑定代次；派发时再比对。不应在从队列拿出事件时补上当前代次，否则已拆下的旧输入会伪装成新绑定。若后端会重用连接号，适配层再加连接代次，区别同号的两次连接。

一次掉线可以在同一输入更新边界处理：

1. 只解除该实例拥有的席位。立即取消该席位的移动值、按住动作、游戏输入队列和相关震动；不能把系统仍记着的旧按下留给下一帧。用“取消”而不是伪造一串会触发技能的松手：若某动作松手代表确认或释放，断开不应该让它完成。已经进入模拟的事实，例如之前启动的动画，按玩法自身规则处理，不回滚其他人的输入。
2. 保留角色、道具和席位分配，显示“P1 手柄断开”；P2 的路由不变。合作压力大的玩法可以明确暂停全局，允许不中断的玩法可只停 P1。暂停是游戏规则，而不是清空整个设备路由；恢复界面打开时也要明确哪只设备可以操作它，不要默认抢 P2 的菜单焦点。
3. 给仍在等待的 P1 一个“换手柄/恢复此席位”的入口。新加入玩家走另一条路径，不能因插入空闲手柄便覆盖 P1。若队友可代开恢复界面，完成配对仍要明确指明目标设备和席位。持有确认键对一些玩家是负担，可提供点按、经明确选择的替代控制器，或由辅助输入确认的路径；替代入口也使用同一个绑定检查。只有显式退出或项目已说明的保留规则才释放角色；刚失联不能同时当作退出。

认领请求绑定**活动连接、目标席位、本轮代次和一次性请求**。由一个输入更新阶段集中提交，在写之前检查请求仍有效、席位确实空缺、设备没被别席使用。检查与写入必须是一个不可被另一请求插入的操作。一个简单策略是同一更新中，同一设备被两个席位选择、或两个设备要同一席位时，拒绝冲突双方并提示再选一次；互不冲突的请求可一起成功。也可以让配置好的主控来裁决，代价是更多界面操作。不要用回调先后、数组顺序或设备编号作为对玩家不可见的裁判。先按请求标识把同一份载荷的重复投递合成一次，再统计争用；同标识但指向不同席位或连接时拒绝并记下冲突。已消费请求的重放不再改变绑定。

## 认领按键不能同时成为游戏动作

即使绑对席位，支持按住连发的输入层也会将确认键或仍偏着的摇杆传进去。只在“按下确认”的那一帧吞掉事件不够：下一帧键还按着，轮询仍读得到。可以把恢复拆成几个可观测的阶段：

| 阶段 | 允许什么 | 何时前进 |
| --- | --- | --- |
| 等待认领 | 恢复界面采样；不发游戏动作 | 在有效采样确认已松开后，接受一次新的、指向该席的确认 |
| 已绑定，等待释放 | 新设备已独占该席，只供恢复界面使用 | 在绑定后的有效采样中，参与恢复的按钮和当前映射的玩法按钮均松开，玩法相关轴进入各自的中立区 |
| 已恢复 | 游戏接收新边沿和连续轴值 | 中立样本只作为新基线；之后第一次真正的按下才是游戏动作 |

轴中立要用设备和动作定义的死区：摇杆、扳机的静止值未必一样。设备断开、应用失去输入焦点或轮询失败时，不把填充的默认 0 当成真的回中立。例如 SDL2 的 `SDL_JoystickGetAxis` 在失败时也会返回 0，要结合有效设备、轴能力和错误状态确认采样。[4] 若目标设备没有某个可选轴，就按能力表从等待条件排除它；必要控制无法采样时则保持未恢复，并提供重新选择，而不是悄悄跳过检查。不要强迫无关按钮或闲置轴回中立，避免一个不用的轴漂移让玩家无法回来。这个例子以全席位释放为条件，容易理解但有等待成本；若项目需要做到每个动作独立恢复，可在映射启用时为各动作单独建立基线，已经按住的那个动作仍须释放后才能产生第一次按下。

在示例轨迹中，P1 的旧按下迟到，一只新手柄带着被按住的确认键出现，中间又读到一个无效的默认零值。三者都没有交给游戏。该手柄放开后重新确认，绑定成功；确认键继续被按住时仍不允许操作，松开确认键但摇杆未回中、或还按着另一个玩法按钮时也不允许。只有有效中立之后的新一次按下进入 P1 的玩法。另一个同款设备的竞争请求不会改掉已接受的绑定；P2 的移动和角色没有变化。两次掉线时上一代的预置认领和游戏输入也都应失效。后两项由合成状态轨迹检验，是本文选的应用规则，不是 SDL 或 Unity 的内置行为。

## 用一次回放判断到底哪层串了号

测试时给事件日志同时记「事件类型与原始编号、归一后的连接及代次、席位与绑定代次、采样是否有效、是否被界面消费、最后交给了哪个角色」。然后逐个缩小问题：

- 拔掉列表靠前的 P1，保持 P2 摇杆在动。若 P2 变成了 P1 或停止，先查索引绑错、重复设备回调或一并清了其他席位，不先调死区。
- 两只同款保持可用，用空闲的一只选择 P1，另一只同时选择 P1；再让同一只同时申请两个空席。以「同一设备同一时刻至多属于一席」为断言，并倒转回调顺序。再断开刚绑定的设备重来，检查旧请求是否待在新一轮队列里。
- 认领时按住确认、使摇杆偏离，然后让它先后释放。日志应该能区分认领已消费、失效的零值、有效中立基线和真正投入游戏的第一按。还应在项目支持的平台上做 USB、蓝牙、无焦点或暂停后返回、更换同款与项目实际使用的辅助设备。加测丢线时正在充能、恢复界面正在操作和多个控制器共用接收器等情况，确认玩法没有偷偷改动角色。

实际 SDL2 虚拟试件验证了枚举及事件含义；合成试件检查了席位路由和操作隔离。物理手柄的身份、蓝牙重连时序和各引擎的输入适配仍需用项目实际设备测。[复现实验](../../../../管理档案/实验/本地合作手柄重连/README.md)
