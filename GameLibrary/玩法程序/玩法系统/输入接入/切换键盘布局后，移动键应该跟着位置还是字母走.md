# 切换键盘布局后，移动键应该跟着位置还是字母走

玩家把“向前移动”绑到一个顺手的位置，随后切换键盘布局。游戏仍提示原来的字母，但按那个位置时不再前进，换到另一个位置却可以。先不要只改提示文字：接入程序可能保存的是字母所代表的键，而产品原本想保留的是手指位置。

这是本文构造的排查场景，不是已复现的游戏故障。本文面向键盘输入与玩法接入程序员，讨论绑定究竟保存什么、匹配什么，以及提示为什么需要另外更新。具体接口限定于 SDL 3.2.8；没有运行 SDL、操作键盘或验证真实布局。为排除按住期间换布局的另一类问题，以下均假设**切换前相关键已经全部释放**。

## 先说清楚，“保留绑定”要保留什么

设同一把假想键盘上有两个位置 P、Q。布局 A 将 P 解释成逻辑键 X、Q 解释成 Y；布局 B 则交换这两个解释。X、Y 只是教学符号，不对应某两个真实字母或国家布局，也不包含修饰键、输入法和平台特殊映射。

在布局 A 下，玩家按 P 绑定“向前”。至少有两种可以自洽的产品约定：

| 项目选择 | 保存的绑定含义 | 切到布局 B 后，哪一个位置符合绑定 |
|---|---|---|
| 保留手指位置 | 向前 → 物理位置 P | P，尽管它现在对应 Y |
| 保留逻辑键 | 向前 → 逻辑键 X | Q，因为假设中的 X 已在这里 |

两行都不是“绑定丢了”。分歧在于绑定承诺了不同的事。需要保持一组相邻移动键的位置关系时，物理方式可能合适；需要让命令跟随指定逻辑键时，则可能采用另一种方式。不要把其中一种宣布成所有游戏的正确答案，也不要用默认布局下看不出的差异替玩家作决定。SDL 的官方使用建议同样区分按位置操作与按指定键操作。[1]

因此，绑定数据至少要让人看得出动作、身份种类和该种类中的值，例如本例的“向前／物理／P”。这是应用层数据设计示意，不是 SDL 存档格式。若只存一个没有类型的数字，后来读配置的人就无法知道应该拿它与哪个字段比较。修饰键是否参与匹配，也需要单独约定；本例的抽象表不替项目作这项决定。

## 在 SDL 里，比较的字段不能偷偷换掉

SDL 3.2.8 的键盘事件同时携带多个字段：scancode 是 SDL 物理键身份，key 是虚拟键值，mod 是修饰状态，raw 则是平台相关扫描码。[2] SDL 的 scancode 定义独立于语言和键盘映射。[3] 不应因为 raw 看起来“更底层”，就把它当作同一个可移植身份。

对前面的产品选择，可以把检查对象明确写出来：

| 已声明的身份种类 | 事件进入绑定判断时比较什么 |
|---|---|
| SDL 物理键 | 事件 scancode 与保存的 SDL scancode |
| SDL 事件式逻辑键 | 事件 key 与按同一事件映射政策保存的 SDL keycode |

这是两个**匹配条件**，不是完整的移动实现。它们没有处理按下、松开、重复、多个绑定同时有效、菜单消费或角色移动状态。尤其不能只在 key-down 时把向前设为真，却省略状态结束，再宣称已有可用控制器。

逻辑方式还需多问一句：这里的逻辑值经过什么映射？SDL 的 key 并不是无条件照抄当前布局的字符。它会应用 SDL_HINT_KEYCODE_OPTIONS；该版本默认含 french_numbers 和 latin_letters。[2][4] 如果捕获绑定与之后匹配采用不同政策，两个值即使都叫 keycode，也不能直接视作同一种承诺。

对于确实要按修饰状态查询布局映射的代码，SDL_GetKeyFromScancode 的 key_event=false 与 true 不能互换：false 使用给定修饰状态转换，true 请求用于事件的映射。[5] 固定实现的 true 分支会重设通常的修饰状态并应用相应选项，false 分支直接查询原键盘映射。[4] 这也说明为什么不能自行把 Shift 理解成“给字母转大写”。

本文选择对这些政策作显式约定，而不提供完整快捷键或组合键系统。平台后端是否提供相同信息、具体布局怎样映射，仍须在目标环境核对。上面的 X/Y 交换表不模拟 SDL 默认选项，更不证明每个真实布局都会这样交换。

## 提示是当前解释，不是绑定本身

回到采用物理方式的“向前”。切到布局 B 后，保存的目标仍是 P；界面却可能需要展示它在当前布局中的名称。若把第一次显示的 X 当成永不更新的提示，就会出现“输入没变，说明变旧了”。若为了让说明变成 Y，反过来把绑定改存为逻辑 Y，又悄悄改变了它以后遵守的规则。

对这个不使用组合键的示例，项目可以约定提示采用“无修饰”的解释：将保存的 scancode 交给 SDL_GetKeyFromScancode，并显式传入 SDL_KMOD_NONE、false，再将返回值交给 SDL_GetKeyName。[5] 这里是在生成界面说明，不是改写绑定，也不是重建玩家输入的文字。

布局变化会影响这份说明。SDL 定义了 SDL_EVENT_KEYMAP_CHANGED，用于输入语言或布局等系统变化引起的映射变更。[2] 项目可以据此让派生提示失效，并在重新进入绑定界面时重新查询。这是刷新策略建议，不是对所有平台通知完整性或实时顺序的保证。

查询也未必得到可显示名称。SDL_GetKeyName 对没有名称的键返回空串。[5] 本例可以显示“已绑定，名称不可用”，并保留重新绑定入口；不能继续冒用旧字母，或猜一个键帽文字。实际产品如何表达这种情况，应由界面与本地化设计决定。

更不能为了方便保存而把显示名当成唯一身份。SDL_GetScancodeName 的接口明确警告：名称可能跨平台变化、缺失或重复，不适合作为稳定的双向映射。[5] 配置保存所选身份及其类型，名称则在显示时生成；不要让翻译、大小写或一次查询结果替绑定作身份决定。

## 三处记录，比只盯着角色有没有动更有用

若要检查开头的故障，先在项目里明确“向前”采用哪一种政策，然后分别记录：

- 配置实际保存了什么身份种类和值。
- 本次输入用哪个字段匹配，采用什么映射与修饰政策。
- 提示从哪一份绑定、哪次布局解释生成。

在本文假设表中，物理方式若仍匹配 P、提示却停在 X，应先查提示刷新；若匹配位置变成 Q，应查是否实际上保存或比较了逻辑 X。反过来，产品若选择逻辑 X，切换后仍强行匹配 P，也可能违背约定。这个推理只检查所给映射，不替代真实设备观察。

后续可在目标平台进行有限检查：相关键全部释放后切换布局，重新打开绑定界面，分别检查触发位置和提示，再确认保存、重载配置没有改变身份种类。这些检查尚未执行。按住期间换布局、焦点丢失、修饰键组合和多个键盘的行为，需要独立约定与验证，不由本例保证。

最后，按键名称和输入文字仍是两条用途不同的链。不要用 keycode 或提示字符串自行拼接聊天文本；SDL 提供单独的文本输入事件。[1][6] 若问题是确认输入法候选时误发消息，可读[确认输入法候选时，为什么不该顺便发送聊天消息](../../../界面与体验/交互设计/文本输入/确认输入法候选时，为什么不该顺便发送聊天消息.md)。若项目接入的是 Steam Input Native 动作 API，则另读[当前绑定来源与提示字形](../../../平台与发行/平台接入/手柄输入/Steam%20Input%20重绑后，为什么按键提示还在显示旧按钮.md)，不要把本文的低层键盘字段直接替换进那套接口。
