# 游戏 UX 设计师：从交互意图到可操作流程的接收责任

## 定位与责任边界

本文把游戏 UX 设计师的一个工作单元限定为：**把玩家要完成的决策，交接成含有状态、操作、反馈和返回路径的流程，并明确需要什么证据才能接收。** 它不是 UX 全职业百科，也不把 UX 等同于画界面。

一张线框图显示了按钮，不证明运行时能选到它；文字已翻译，不证明在布局中可读；工程检查通过，也不证明玩家理解了操作后果。这些差别正是流程交接应保留的内容。

UI 美术、UI 程序、UX 研究和可访问性工作可能分开，也可能由一人兼任。本文把它们当作需要分配的接口，不规定六个岗位编制，更不从职位名称推导修改权或验收权。UX 设计师可以提出研究问题、使用研究结果，但不能仅凭作者判断声称已经完成玩家研究。

## 常见任务与交付物：围绕一个决策组织

以下为原创责任建议，尚未实施。

| 输入与任务 | UX 侧推动形成的交付物 | 接收问题 |
|---|---|---|
| 玩法/产品给出功能目标 | 玩家目标、可选行动及后果，待确认规则单列 | 是否知道玩家在这里需要作出什么决定，而非只有屏幕清单？ |
| 目标转为流程 | 入口、正常/等待/错误状态、退出与返回，以及必要反馈 | 每条操作是否有去处，取消的后果是否与保存区分？ |
| 流程进入视觉和实现 | 状态标注、信息优先级、输入与返回意图、候选身份 | 图示意图是否被转换成实际可操作行为？ |
| 增加语言和需求配置 | 文本上下文、空间不足时的优先级、关键操作与信息的可用要求 | 哪些由内容解决，哪些需要布局或交互改变？ |
| 接收结果与迭代 | 实际观察、专业审查、玩家研究及未验证项分别记录 | 证据是否足以支持本次结论，下一问题交给谁？ |

工具可以是流程图、线框、可交互原型、任务记录或候选构建链接。关键不是工具品牌，而是能否看出不同状态、所需证据和接收者。高保真不自动比低保真更能回答流程问题；原型也不必然包含真实输入系统、内容或错误处理。

## 原创有限工作表：改设置后确认、取消，再继续编辑

**完全假设，未制作或测试：**玩家修改一个设置，打开确认框，选择取消，然后返回继续编辑。先由项目决定“取消”是放弃修改还是仅关闭确认，不用一个常见词替代规则。

| 接口 | 本例需交接什么 | 不能代替的证据 |
|---|---|---|
| 决策意图 | 设置的当前值与拟改值、确认/取消后分别发生什么；等待与失败能否出现 | 视觉按钮名称不定义保存语义 |
| 实际交互 | 哪一层当前接收输入；打开后选择起点、退出操作、返回目标失效时的期望回退 | 流程箭头不证明焦点请求最终生效或真实设备可操作 |
| UI 表现 | 当前值、待修改状态、选中与禁用信息如何区分；空间不足时保留什么 | 静态图不证明运行中布局、提示层级或每个状态都正确 |
| 本地化内容 | 确认/取消的语境、必要变量、长文本和格式变化的目标条件 | 字符串语法通过不证明翻译准确、实际排版可读 |
| 可访问性 | 声明需求下是否能获知后果、找到当前选择、完成或退出操作 | 多加一个提示或选项不构成完整可访问性保证 |
| 研究与验收 | 候选与检查条件、已观察行为、专业审查意见，以及仍需研究的问题 | 作者讲解后的顺利操作不证明无提示理解 |

六行是六类接口，不是六位必须招聘的员工。具体项目应让合适的人承担并确认责任；研究者负责的方法和证据，不因 UX 设计师也会做原型就自动成立。

### 接收决定的三个分岔

1. **关闭了，但接不上操作。** 假设确认框视觉消失，返回后却没有可用焦点。此时应保留“关闭显示已发生”和“继续编辑未建立”的差别，交给 UI 实现核对实际状态。用[模态焦点恢复](../../solutions/ux/modal-focus-recovery.md)确定专门检查点，不在本角色档案重写恢复栈。
2. **操作接上了，但内容不可读。** 假设返回可用，但特定语言下解释文字被截断。先定位消息、布局和状态，不把它仅标成“翻译问题”。[伪本地化与占位符契约](../../solutions/localization/pseudo-localization-contract.md)帮助组织格式检查，但不能代替真实布局和内容接收。
3. **技术路径成立，但后果仍被误解。** 若真实观察发现玩家不理解取消后保留什么，需要保留任务和提示条件，再提出研究或设计修订；没有这种观察时只能把它列为未验证问题，不能虚构误解率，也不能宣称已易用。

上述三项均为假设分岔，不是来源工作室的已发生故障或本库测试。实际项目中也可能多层同时失效；接口分离用于定位，不要求机械地按单一顺序排查。

## 典型工程难题与相邻专业

- **流程状态少于实现状态。** 线框只有成功界面，实现却有等待、重试、失去目标等状态。UX 与程序应补齐决策和反馈意图；不能让程序临时猜一个默认后果。
- **设计目标与运行观察混淆。** “返回刚才位置”是意图，还需指定目标不存在时的策略及实际结果。焦点测试通过也不证明所有手柄、读屏或系统覆盖层都兼容。
- **文字条件变化未进入接收。** 同一空间在不同语言或设置下可能容纳不同信息。格式成功和布局成功应分别说明，不用缩小所有文字掩盖内容优先级问题。
- **配置存在被当作可用。** [关键非语音声音的信息等价](../../solutions/accessibility/critical-sound-information-contract.md)说明需要先确定关键内容与渠道；它没有替本例验证可访问性，也不能用“有字幕”概括所有需求。

[玩法程序](../programming/gameplay-programmer.md)协助确立状态和操作后果；[游戏 QA](../qa/game-quality-assurance.md)保留版本与复现证据；[试玩干预与证据边界](../../solutions/production/playtest-intervention-evidence.md)约束研究结论。跨专业意见不同时，应记录各自判断对象和依据，而非把“设计已通过”写成实现、研究和可访问性全部通过。

## 后续研究与适用限制

下一步应在获准的实际界面中选一条流程，确认候选、输入方式、内容与配置范围，再取得相应证据。本文没有运行 UI、实际设备导航、翻译布局、可访问性检查或玩家研究；其工作表只是可用于准备接收的原创建议。

已有焦点、格式化等文章包含各自有限观察，不可搬来充当这一完整流程的验证。此档案只补 UX 的一个责任接口，不建立全球统一职称或完整岗位矩阵。
