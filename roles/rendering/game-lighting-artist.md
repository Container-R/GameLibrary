# 游戏光照美术：共享灯具交给别人摆放后，应该改哪一层

## 定位与责任边界

本档案聚焦游戏光照美术的一项生产责任：**将可复用的带光道具交给其他内容作者摆放，并在具体场景不符合视觉意图时，帮助判定应调整实例、共享预设还是场景条件。** 这不同于只画出气氛目标，也不同于实现渲染算法。

“Lighting Artist”在这里是责任入口，不规定所有公司的岗位结构，也不把环境美术、look-development、技术美术和图形程序统一当作别名。一个人可以兼任多个接口；重要的是具体变更由谁接收、谁有权批准，以及尚缺什么证据。光照美术提出视觉修改，不自动获得材质、关卡结构或全局曝光策略的单方修改权。

## 两个实践样本

- **Ognyan Zahariev、Georgi Gavanozov，《The Division》访谈，2016-12-20。** 两位当时的 Ubisoft Sofia 光照实践者描述了由关卡设计和环境美术分布的灯光道具，并强调接收表面粗糙度及雾/云相关控制。[S1] 这是具体制作接口的自述，不是本库测得的性能或玩家引导效果。
- **Justine Cannarella，Point'n Think 访谈，日期未确认。** 她讨论了前期的灯具/氛围准备、制作中的跨专业配合和《Mirage》的昼夜状态检查。[S2] 文章中的职务与经历按访谈时点理解，不代表已核实的现任职位。

两篇都是独立出版者承载的具名第一手回答，不是工作室技术规范。下列字段、分层判断和比较方案均为本库原创，未声称工作室采用它们，也未重现来源配图。

## 作者、摆放者与场景接收者各自交什么

这里的“灯具”是便于沟通的复用单元，不预设某引擎 prefab 或组件模型。下表拆分责任，不强制新增三个人或三套工具。

| 接口 | 建议交付内容 | 不应被默认为已解决 |
|---|---|---|
| 灯具/预设作者 → 摆放者 | 可见灯具或发光表面与实际光源的关系；预期视觉用途；可选变体；允许调整的参数与范围；需要共同决定的参数 | 有可见发光外观，不自动证明存在预期照明贡献；组件完整不证明艺术意图成立 |
| 摆放者 → 场景接收者 | 实际实例、位置/朝向、所选变体与局部覆盖；附近承接表面、遮挡及相关构图意图 | 同一预设在别处通过，不证明此实例也合适 |
| 场景接收者 → 光照作者及相邻专业 | 当前几何/材质、环境光与雾、时间状态、曝光策略及评审视角；具体哪里偏离约定意图 | 看起来不对不等于光源参数错误，也不等于材质错误 |
| 变更提出者 → 受影响内容作者 | 改动层级、引用范围、保留局部覆盖的决定、需要复查的代表实例与未决项 | 修改一个共享资源，不代表影响只限于当前画面 |

所需能力包括构图与光色判断、识别材质和场景依赖、在引擎内容工具中定位实例/共享设置，以及说明取舍。本文不提供通用灯数、亮度、粗糙度或性能阈值；工具可帮助查引用和参数，却不能独自判断视觉目的。

## 原创有限例子：同一盏共享灯，两个接收区域

**完全假设，未搭建或渲染。** 预设 L 被放入区域 A 与 B；二者附近表面和遮挡不同。美术评审提出“A 的当前表现不符合局部构图意图”，但尚未解释原因。没有预先假定 A 更暗、B 更亮，也没有已测得的材质或照明缺陷。

不应立即提高 L 的共享强度，再把其他区域的变化当作附带代价。先确认评审对象及授权目标，再选择可回答的问题：

| 决策分支 | 拟做的受控检查（均未执行） | 能支持的下一步与保留边界 |
|---|---|---|
| 是否是单个实例的摆放或覆盖？ | 在 A 内固定相机、曝光策略/适应状态、时间状态及其他场景条件；只调整一个获准的摆放量或局部覆盖，记录改动 | 可形成局部修改候选；不能因此宣布预设对所有场景正确 |
| 是否需要共享预设修订？ | 在相同接收条件下比较 L 的旧/候选设置，并分别回看 A、B 的约定用途；不要同时换材质和预设 | 若形成共享修订提案，应列出引用范围及反例；两个区域不足以覆盖所有实例 |
| 是否是接收表面或几何条件需要讨论？ | 保持灯具设置与评审条件不变，在获准的隔离副本中比较具体表面/遮挡变更；把材料意图和关卡约束交给对应作者 | 只帮助定位待讨论的依赖；不能仅凭两张图断定渲染算法或原作者有错 |
| 是否涉及场景级策略？ | 固定局部内容，单独讨论环境、雾、时间或曝光策略的一项候选；注明其作用范围 | 若目标本就要求全场景变化，交由该策略的责任人决定；不要用全局修改掩盖未解释的局部问题 |
| 多项相互作用或目标仍不清楚？ | 记录哪些条件不能固定、哪些意图相冲突，暂停“只改这一层”的归因 | 输出未决问题和需要的接收者，而非强行指派一个专业返工 |

“固定相机/曝光/时间”是可比较性要求，不是本文实现了冻结工具：自动曝光、动态天气或其他时变内容若无法稳定，就必须记录这一限制。A 与 B 的表面不同，本来就不是只差一个变量的实验；不能把两区差异直接归因于粗糙度。以上是寻找修改范围的生产检查，不是已执行的因果实验，更不提供物理正确性证明。

### 怎样关闭交接，而不是只关闭工单

接收结果应明确属于哪一种：**局部实例调整、具有引用影响范围的共享修订、场景策略变更，或仍未解决的艺术/技术问题。** 保留为什么选择该层级、由谁接收以及哪些实例尚未复查。共享修订可能需要合并或保留局部覆盖；一律删除覆盖与任意复制新预设都会带来新的维护成本，来源没有给出最优策略或成本数字。

艺术评审接受某个候选，仍不证明其技术开销满足目标设备预算；技术测量通过，也不证明玩家理解了设计提示。若用途涉及路线或危险提示，应另行取得对应玩法与玩家证据，不能把光照作者的意图写成实测效果。

## 与相邻职责及已有证据的关系

- [环境概念美术](../art2d/environment-concept-artist.md)交代视图中的保留、修改和未知意图；本文新增的是**复用灯具的作者与摆放者分离之后，修正应落在哪一层**，不是另一个入口修订表。
- [关卡设计](../../管理档案/历史正文/roles/design/level-designer.md)提供空间和玩法约束。为画面移动遮挡物不能自动改变其通行或机制意义。
- [技术美术](../technical-art/technical-artist.md)可支持内容工具与处理检查；资产接入有效，不保证特定摆放的视觉接受。
- [图形程序](../../管理档案/历史正文/roles/rendering/graphics-programmer.md)处理渲染功能与技术证据。本文没有执行其矩阵接口、纹理预算或任何性能实验；观感问题不能自动归因为 shader 缺陷。

下一步若获准实际实施，应只选一个共享灯具及有限引用场景，先明确修改权限与评审条件，再保留真实比较和接收记录。本文尚无图片检查、场景制作、运行、性能、玩家或可访问性验证；不宣称建议降低了返工，也不宣称完整覆盖光照职业。
