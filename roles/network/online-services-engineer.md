# 在线服务工程师：把服务调用成功交接为可验证的游戏会话

## 定位与责任边界

在线服务工程师关心的不只是某个 API 返回成功，而是玩家的一系列操作能否穿过客户端、服务与对局实例的边界，形成可解释、可运营的游戏流程。本文聚焦**进入对局前后服务链的实现、集成与验收交接**：组队、排队、会话分配、连接及结果交接是可能的工作范围，不是每个产品必须具有的固定架构。

`online-services-engineer` 与 `backend-engineer` 在不同团队可能重叠，但不能直接当作同义岗位。实时同步程序通常更关注对局中的状态与延迟；基础设施、运维、安全、商业服务也可能由专门团队负责。小团队兼任是组织选择，不代表一个人天然拥有全部服务权限或上线决定权。

### 两个第一方样本支持到哪里

- **Bandai Namco Studios，日本团队访谈。** 青木描述团队同时负责基础设施、服务器应用、CI/CD 与管理工具；松岛说明客户端与服务端分属不同公司时的技术协调；何涉及跨项目基础服务及匹配后的开局支持；天野的技术总监职责偏向整体协调。来源呈现的是不同责任范围，而非一个人人包办的统一职位。[S1]
- **Riot，VALORANT 历史项目。** Keith Gunning 介绍 Core Services 团队的扩展性、可用性与监测责任，并区分逐帧玩法服务器和其他平台服务。本文采用这个分界，不将该项目架构推广为所有在线游戏都应采用微服务。[S2]

主分类使用已有 `NET`；`LIVE` 对接运行与事故响应，`PLATFORM` 对接具体平台约束，`QA` 对接证据，`PROD` 对接跨团队范围和排期。岗位标题和关联标签不自动授予跨团队职责。

## 常见任务与交付物：原创责任接口

下表是依据上述样本提出的交接建议，**未在实际团队实施，也不是两家公司的内部流程**。

| 输入与任务 | 建议由在线服务侧提供的产物 | 接收方与验收问题 |
|---|---|---|
| 玩法/产品给出开局与结束流程 | 操作链、各阶段成功/失败含义、取消与超时的归属；明确哪些阶段不在本团队控制内 | 客户端、玩法和产品：界面上的“已匹配”“可连接”“已进入对局”是否分别对应可观测事实？ |
| 多团队共同实现接口 | 请求/响应与版本约定、依赖端点清单、错误分类和关联标识 | 客户端、合作开发方：能否定位一次失败停在哪个边界，而非只得到总的“网络错误”？ |
| 服务代码与配置成为候选 | 候选身份、功能检查结果、依赖版本与被替代组件清单 | 构建、QA：运行对象是否与本次报告对应，外部配置是否已记录？ |
| 容量需求转为测试计划 | 工作负载来源、到达节奏、会话持续时间、后台请求、服务拓扑与资源约束；标注估计值 | QA、基础设施：测的是哪种需求组合，是否遗漏实际客户端的后台流量？ |
| 受控环境执行与观察 | 每阶段功能结果、延迟/错误/资源记录、观测时段及未覆盖范围 | 运维、QA：高吞吐是否以跳过必要步骤或业务失败换来？ |
| 准备上线或改变服务链 | 未决依赖、告警责任、故障分流与恢复验证计划 | 发布与事故责任人：何时停止晋级，谁接手遗漏边界，谁有权接受风险？ |

这里没有给出通用超时、容量或错误率阈值。阈值必须来自产品体验、服务依赖与实际测量；“运行了很多请求”不是阈值来源。请求关联标识也不是 exactly-once、鉴权或防作弊机制。

## 工作案例：平台压测不能替代真实玩法服务器测试

Riot 的 2020 年文章说明：服务各自测试不足以覆盖跨服务调用链，因此构造模拟客户端，执行场景操作及后台轮询；匹配场景包含排队、选择 Agent 和连接已分配服务器。其模拟游戏服务器复现分配与结果记录，**不执行实际玩法逻辑**；文章另外区分玩法服务器测试。平台压测以整个时段内的监测指标是否满足约束判定，而不是只看一次成功响应。[S2]

这是一份第一方历史实践说明，不是本库的运行证据、当前 VALORANT 架构保证或可移植的吞吐基准。本文不重用其规模数字，也未读取或复现内部压测源码。

**原创工程推论：替身不是错误，但替身必须限制结论。** 如果测试有意用轻量服务器替代实际对局进程，那么它可能回答平台服务链的负载问题，却不能回答玩法 tick、真实网络协议兼容、客户端场景加载或渲染是否达标。即使同一次测试经过了“连接”阶段，也必须说明连接到什么实现。

## 有限交接工作表：这次“成功”覆盖了哪条链？

下面是**完全假设、尚未执行**的项目工作表。它不声称 Riot 或 Bandai Namco Studios 使用这些字段，也不假设游戏必须分成这些服务。先根据产品删改阶段，再填实际证据。

| 阶段 | 要区分的事实 | 本次实现身份应填写什么 | 缺口接收者 |
|---|---|---|---|
| 组队进入队列 | 请求被接收，不等于队伍已获得对局 | 实际客户端或请求生成器；组队/队列服务版本；必要背景请求是否运行 | 客户端与服务负责人 |
| 匹配或选择完成 | 获得匹配结果，不等于有可接收连接的对局进程 | 真实规则实现或替身；输出会话标识；等待或失败的判定 | 设计、服务与 QA |
| 分配对局 | 分配请求成功，不等于进程已就绪或连接端点可用 | 分配服务和对局进程分别是真实还是模拟；实际就绪证据 | 服务与基础设施负责人 |
| 客户端连接 | 接口可达，不等于目标版本客户端完成协议与游戏状态交接 | 实际客户端/协议替身身份；目标实例；握手与必要加载步骤 | 客户端与玩法程序 |
| 对局结束与结果交接 | 生成结果、接收结果、可查询结果不是同一事件 | 真实对局结果或人工构造数据；接收与查询的证据 | 玩法、后端与 QA |

建议每行再附上**责任人、候选版本、实际环境、结果位置、未测项**，不要求增加没有消费者的文档字段。关联标识应在允许范围内足以串联步骤，不应为了调试而记录认证令牌或不必要的个人数据。

### 一个有区分力的接收决定

假设报告宣称“端到端开局通过”，但实际只运行请求生成器 → 真实平台服务 → 模拟对局服务器。不能把整份报告丢弃，也不能照单全收：

1. 保留其实际覆盖的操作、并发条件和监测结果；若结果本身未提供，也不能凭替身设计推定通过。
2. 把结论重命名为对应范围，例如“指定平台请求链在声明工作负载下的观察”，而非真实客户端完整开局。
3. 明确遗漏的真实客户端握手、加载和对局执行由谁验证；若这些属于本次发行承诺，在取得对应证据前保持未决。
4. 后续真实集成若失败，按边界定位，不自动认定原平台测试造假，也不拿原报告否认新失败。

这套判断不要求所有测试都使用真实组件。替身可以降低成本并隔离问题；代价是必须维护替身与实际协议的相关性，并另行安排被省略部分的证据。工作负载模型同样会过时，产品新增后台轮询、会话阶段或地区部署后，应重新评估原报告的适用范围。

## 核心技术、工具与典型瓶颈

工作涉及接口与序列化约定、服务间调用、会话管理、部署配置、观测、负载建模与故障定位。选工具应服从可验证的问题，而不是岗位清单：服务图用来定位谁依赖谁；日志与指标用来证明哪一步发生了；负载生成器用来重现声明的请求组合。工具名、单机并发数或“使用云”本身都不证明产品容量。

优先研究的难题可以是：客户端重连与取消如何跨越多服务边界；分配成功但实例尚不可用时谁负责反馈；结果处理完成的定义如何对齐；测试替身省略了哪些协议行为。本文没有实现这些协议，也不承诺全局重试、幂等、分布式事务或安全策略。涉及账号、支付与安全时，应明确专门责任人与验证要求，不能由这个岗位档案代为认证。

- [客户端预测与确认重放](../../solutions/programming/client-prediction-authority-boundary.md)：是对局中同步问题；现有离散模型与来源不能证明平台服务链容量。

- [游戏 QA](../qa/game-quality-assurance.md)：帮助区分缺陷、证据范围与发行风险；不把运行一次压测等同于放行权限。
- [Destiny 配置准入与回退案例](../../GameLibrary/网络与在线服务/在线运维/配置与回退/Destiny2配置回退事故中的数据恢复问题.md)：说明另一条真实运行准入/恢复边界；它不是本文假设链的故障复现。

下一项有价值的研究不是再做一个假 HTTP 服务来获得绿色测试，而是选择获准的真实项目，写清一个具体服务链与替身边界，取得相应集成或负载证据。本岗位档案只推进全学科职责矩阵的一部分；没有建立全行业组织标准。
