# 关卡策划：从遭遇意图与白盒到可验收的空间交接

关卡策划需要把“玩家在这里做什么决定”落实成可进入、可操作、可观察的空间与事件，而不只是提交平面图或摆好模型。本文聚焦三维动作/探索类内容的交接问题：**设计意图、当前可行性和玩家理解，是三种不同的主张，需要不同证据。** 不覆盖所有关卡类型，也不是行业统一岗位标准。

本文使用 `DESIGN` 下已有的“关卡策划”方向及 `level-designer` 标签，不把任务策划、环境/关卡美术、技术关卡策划一律登记为同义词。谁制作导航数据、谁实现移动控制、谁批准美术交付，应按项目约定，不能从职位名称推导。

## 公开岗位与制作案例分别说明什么

- **ORCA，レベルデザイナー**：日文职责直接包括 Unreal Engine 中敌人与物品配置、地图规划与规格书、事件设计和实现。这支持“空间内容与事件可共同属于该岗位”，不是所有日本策划职责的定义。[L1]
- **Ubisoft Annecy，Lead Level Design**：该 AAA World 团队岗位强调与 Level Art、Tech Level Design、技术部门，以及玩法、程序、TA、QA 协作，管理空间质量和生产约束。它是特定团队的负责人职责，不能把管理责任或汇报线套到所有关卡策划。[L2]
- **Double Fine，《Psychonauts 2》跳跃制作案例**：团队制定跳跃度量以支持关卡布局；后续新增或调整移动能力可能使已有布局假设失效。其编辑器跳跃预览复用模拟，并反映调参结果。它提供了“移动规则变化会影响空间内容”的具体生产接口，不证明所有引擎都提供相同工具。[L3]
- **Ubisoft Toronto NEXT 2024–2025**：历史挑战区分任务设计文档与可玩白盒，并对俯视图标注、设计意图、模块适应性和玩家选择提出要求。这是公开挑战的评价例子，不是我们获得了工作室内部验收规程；未读取另行提供的第二阶段详细包。[L4]

以下交付矩阵是基于这些边界提出的**原创协作建议**，不是上述公司的内部表单。小团队可由同一人承担多项责任，但仍应区分证据类型；多人团队则为每个交接指定实际接收人。这里不声称已经比较不同规模团队的效率。

## 六阶段交付与验收矩阵

| 阶段与问题 | 输入 → 可交付物 | 可审查的接受条件 | 接口及不能代替的证据 |
|---|---|---|---|
| 1. 遭遇意图：要让玩家判断什么？ | 玩法能力、目标与叙事前提 → 简短意图卡：预期决定、可用信息、合法替代路径、失败/恢复方式、尚未确定的假设 | 接收人能指出某个空间/事件如何服务该决定；“紧张、好玩”被拆成可观察问题，而非凭形容词签收 | 关卡与玩法/叙事共同确认；清晰意图不等于玩家会理解 |
| 2. 白盒：意图是否变成可操作内容？ | 意图卡、移动能力 → 可运行内容版本、标注平面/空间图、入口出口、敌人与物品/事件配置、未实现项 | 指定构建能进入目标片段；流程前提与占位功能明示；能检查主要路线、遭遇次序和恢复点 | 程序协助实现必要交互；截图、设计文档或漂亮几何不能代替操作证据 |
| 3. 移动与导航：当前内容依赖什么能力？ | 移动配置、碰撞与代理条件 → 版本化能力/布局约束表及代表性检查点 | 记录使用的能力、尺寸、状态和目标；分别检查碰撞通过、移动动作、导航数据就绪与到达判据；未知项不写通过 | 程序/AI 与关卡共同定位问题；关卡策划不因此独占导航实现责任 |
| 4. 试玩：观察回答了哪个设计问题？ | 问题、构建与起始条件 → 观察记录、提示/中断标记、替代解释、候选改动 | 能从原始事件追溯结论；区分未援助行为与援助后完成；未测试条件保留为未知 | 研究/QA 可参与；可运行和可通关不自动证明首次理解或节奏适宜 |
| 5. 美术交接：什么可改，什么须复核？ | 已知可行的内容修订 → 关键可交互体积、视线/线索、碰撞与导航依赖、艺术自由范围和待确认项 | 接收人知道哪些改动需要回看玩法；美术整合后对受影响点重查，不将白盒结果直接继承为最终证据 | 环境美术负责视觉生产，TA 支持资源/工具/性能接口；关卡约束不等于替美术规定所有实现 |
| 6. 变更与接受：当前版本为何可交付？ | 移动、几何、事件或美术差异 → 变更影响表、复查记录、缺陷/未决风险、接收人 | 结论绑定实际内容与配置；失败、阻塞、未测分别列出；说明哪些假设仍依赖后续试玩 | QA 提供功能与回归证据，制作协调范围/风险；技术检查通过不替代体验判断 |

接受条件应在测试前按项目目标确定。没有通用的走廊宽度、通关比例或“好玩分数”；也不需要把每段关卡变成庞大的审批表。重点是一次内容变更能找到它依赖的规则、需复查的点和作出决定的人。

## 不要把四种“能走”混成一件事

1. **路线与遭遇意图**：这里是否允许绕行？哪条路线要展示线索或付出代价？这是设计要求，可能刻意包含暂不可达区。
2. **移动与碰撞可行性**：指定角色状态能否完成跨越、通过门洞或着陆？需考虑当前控制器、碰撞体、输入条件与实际几何；美术网格看起来有缝不等于碰撞能通过。
3. **导航系统状态**：NPC 使用的数据是否就绪、代理条件是否匹配、返回的是完整还是部分路线？路径存在也不等于角色已沿路到达；数据未就绪不能直接判成关卡不可达。参见[导航就绪与部分路径](../../solutions/ai/navigation-readiness-and-partial-path.md)。其 Godot 实验仅支持记录条件下的系统边界，不是本岗位职责的唯一实现或新的跨引擎证据。
4. **玩家理解与选择**：玩家是否注意到路径、理解目标，或有意不走？它需要匹配问题的观察证据。设计者知道出口、自动测试找到路、主持人指路后玩家完成，都不能独立回答首次发现问题。参见[试玩干预与证据边界](../../solutions/production/playtest-intervention-evidence.md)。

这些检查相互关联却不可相互替代。例如 NPC 导航通过只回答特定代理条件，不能推导玩家跳跃可达；玩家通过只说明该次动作成立，不能推导所有目标玩家都理解空间。

## 版本化的移动—布局兼容记录

最小记录可以放在内容工单旁，而不是新建复杂系统：

| 字段 | 要回答的问题 |
|---|---|
| 内容与规则身份 | 哪个关卡/几何、碰撞、移动配置和构建？可用提交或受控资产版本；不能只写“最新版” |
| 所需能力与初始条件 | 单跳/二段跳、助跑或静止、解锁状态、角色尺寸、可用资源是什么？ |
| 意图与候选检查点 | 哪个跳跃要成立，哪个捷径按设计暂不允许？检查点如何重现？ |
| 已得证据 | 操作轨迹/缺陷复现、导航状态或试玩观察分别在哪里，使用哪一版本？ |
| 改动触发与责任 | 移动、碰撞、路径/代理或美术变化后，谁评估影响、谁复查、谁接受剩余风险？ |

“兼容”不是要求永远冻结角色移动，而是避免旧布局在新能力下继续无条件继承通过状态。Double Fine 的生产案例说明这种依赖确实存在；上表的字段和流程是本文建议，并非其原样规程。[L3]

### 假设案例：跳得更远，为什么原来通过的关卡要重查？

以下是原创静态推演，**不是运行结果或真实玩家记录**。

某片段原本希望玩家先取得通行物，再由下层进入出口；高台间隙被当作尚不可跨越的分隔。后来玩法团队调整空中控制或增加移动能力。变化可能让玩家直接跨到出口，也可能只是让普通路线更容易；没有复查就不能断言一定发生绕关。

合格处理不是立即缩小跳跃距离或加隐形墙，而是：

1. 保留原规则/内容身份，把新规则标为待评估，查明哪类角色状态可能打开新路线。
2. 在新构建中检查目标间隙的实际动作与落点，区分运动可达、碰撞阻挡和出口事件是否满足前提；静态距离比较不够。
3. 与关卡、玩法和叙事确认捷径究竟是有趣的替代玩法，还是会跳过必要状态。决定接受捷径、改几何或改事件条件时，记录设计理由，不把任何偏离原路径自动称为 bug。
4. 若改几何/美术，复查视线、碰撞、NPC 导航及其他受影响动作；若改事件规则，复查正常路径和恢复状态。改变多项条件时，不把结果单独归因于某一项。
5. 技术层面成立后，如果问题是“玩家是否理解新路线”，仍需相应试玩。一次开发者成功操作不产生玩家理解结论。

该例的交付物是可讨论的变更与证据清单，而非假造“已修复、已验证”的结论。

## 工具能力与相邻岗位

需要的能力包括空间布局、基础编辑器操作、配置与事件制作、版本对照、可重现问题记录，以及读懂团队暴露的移动/导航/性能可视化。工具服务于项目合同：ORCA 明示 Unreal Engine；Double Fine 描述自有跳跃预览；这些不构成必须统一某个引擎或购买某插件的建议。[L1][L3]

- 与[玩法程序](../programming/gameplay-programmer.md)约定能力、事件前提及可观察状态；可以要求工具，不假设策划独自维护控制器。
- 与[技术美术](../technical-art/technical-artist.md)及实际环境美术接收人协作：区分玩法关键几何、视觉表达、资产与性能约束。TA 不等于所有场景美术岗位。
- 与[游戏 QA](../qa/game-quality-assurance.md)共享构建、重现步骤和风险；功能缺陷证据与体验观察分开保存。QA 可以参与试玩，这不是组织隔离规定。
- 与研究及制作协作安排观察条件、版本、修订范围；不把一次已提示的通关包装成已验证的关卡引导。

后续值得具体研究的是“移动参数变更如何定位受影响关卡检查点”及“美术替换如何保持交互线索与碰撞约束”。本档案不声称已有自动依赖追踪、组织试用效果或所有规模团队的完成范式。
