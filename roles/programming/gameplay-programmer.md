# 玩法程序：从设计规则到可验收系统的责任边界

## 定位与样本边界

玩法程序（Gameplay Programmer / 游戏逻辑程序）把规则、玩家输入和内容资源连接成可运行、可调试、可迭代的交互。该岗位不是“按设计文档写代码”这么窄，也不默认拥有所有玩法设计决策权。

本档案依据截至 2026-10-31 可访问的三家雇主说明与 ScreenSkills 职业档案。它描述**公开样本与可执行协作方法**，不是全球岗位标准，也不是对任何工作室内部流程的调查。招聘文案仅证明雇主公开表达的期望，不证明其实际团队每天如此分工。

### 原始资料支持了什么

- **ScreenSkills [S1]**：连接设计与实现，涉及规则、调优、修错、优化，并与设计、美术、其他程序及 QA 合作。这支持“玩法代码与交付协作不可分”的基本定位。
- **Larian [S2]**：职责跨玩法、引擎功能、UI、音频、动画、脚本和工具；要求可自动测试、可维护的代码，并参与范围评估与实现建议。因此不能简单推出“大工作室的玩法程序只写一个狭窄模块”。
- **ETC Interactive [S3]**：创业工作室的初级岗位样本覆盖移动、武器、库存和 UI，并涉及客户端服务接入、分析和代码评审。它是 startup 样本，**不能据此将所有独立团队等同于该工作室**。
- **Ubisoft 中国 [S4]**：历史应届生项目材料把设计规则与动画、音效等内容转化为可玩交互，并列出概念、实现、优化和调试阶段。该页面不是当前职位空缺证明。

## 可执行的工作—交付—验收矩阵

以下矩阵是依据上述协作需求提出的**原创工程建议**；具体负责人和阈值应由项目约定，不能冒称来源中的固定流程。

| 工作问题 | 输入与协作接口 | 玩法程序交付物 | 建议验收证据 |
|---|---|---|---|
| 规则能否被实现和调优？ | 设计提供目标、例外与反馈；程序提出成本/歧义 | 可玩原型、规则状态图、参数数据与非法组合校验 | 设计用预定场景试玩；边界状态可复现；参数修改无需改核心代码 |
| 技能是否重复触发或错过窗口？ | 输入、战斗设计、动画提供事件/时序语义 | tick 命令契约、技能状态机、取消/打断规则、事件去重 | 同日志重放事件序列一致；按下/持续/松开区分；端点和中断测试 |
| 动画与物理谁驱动角色？ | 动画/TA 提供根运动与通知语义；控制器提供碰撞结果 | 明确移动/旋转所有者、表现适配层、诊断日志 | 不重复应用位移；阻挡和混合切换可观察；不可把脚滑一律归因于动画师 |
| 玩法是否能在线同步？ | 网络程序约定权威、预测、回滚及迟到策略 | 可序列化状态、命令/事件 ID、确定的错误处理接口 | 丢包/乱序/重复消息场景下按协议处理；未经测试不宣称跨平台确定性 |
| 内容能否安全接入？ | 内容作者提供资产/配置，工具程序提供管线 | 资源 ID 契约、缺失资源回退、配置检查和错误定位 | 有效与无效样本均测试；错误指出具体资产/字段；失败不破坏其他内容 |
| 缺陷能否稳定复现？ | QA 提供构建、场景、操作与观察 | 最小复现、自动回归或明确人工步骤、状态日志 | 修复前后同用例比较；记录版本和未覆盖范围；不能只以“我这里好了”关闭 |
| 性能是否满足场景预算？ | 技术负责人给目标设备/负载/预算 | 捕获数据、热点分析、语义不变的改进 | 同设备/构建/场景比较；关注峰值与分配，不以平均 FPS 掩盖卡顿 |

## 不同团队规模：同一责任可以由不同人承担

**已知事实**：上述样本均要求跨职能协作；Larian 仍列出宽职责。样本不足以量化独立与大型团队的职位边界。

**用于项目分工的建议**：

- 小型独立团队可由同一人兼任玩法、工具、构建和部分设计，但仍将“决定规则”“实现规则”“验证规则”分别列出。没有第二个人时，也用独立测试阶段避免把实现意图当成验收结果。
- 多团队项目应写清模块所有者和消费方。玩法程序可提出网络或动画需求，但更改公共协议、资源格式、角色控制器时须让相应负责人参与，不靠职位名称推定权限。
- 原型阶段允许短生命周期试验，但在进入正式内容生产前明确哪些是可丢弃代码、哪些成为共享接口；否则快速原型会无意中变成内容作者依赖的生产工具。

这些是风险控制方案，不是独立团队必须承担更多任务、或大型团队必然更专业化的事实断言。

## 一个最小交付包：近战技能

不把“角色能挥剑”当作完成。建议交付包含：

1. 设计约定：触发/取消条件、生效区间、目标规则及反馈目标。
2. 接口契约：输入命令何时归属某 tick；动画通知是否仅作表现；命中与伤害由哪个系统认定。
3. 可调配置：范围、时间、资源 ID、版本；拒绝无效区间和缺失资产。
4. 可复现证据：同一输入日志、重复按键、被打断、暂停/恢复、失焦和内容缺失案例。
5. 交接说明：已验证的环境、未验证的联机/平台范围、已知限制、调试入口与负责接口。

[固定 Tick 与表现边界方案](../../solutions/programming/fixed-step-simulation-boundary.md)给出第 2、4 项的具体基础，以及纯模型测试不等于引擎集成测试的限制。它不取代设计对手感的评价，也不证明整个战斗系统已经正确。

## 能力与工具选择

需要状态建模、数据结构、调试、测试、配置与资源接口意识，并理解所用引擎的生命周期及限制。Larian 样本使用 C++/专有引擎背景，ETC 样本使用 Unreal C++ 与 Blueprint；这不能变成所有玩法程序都必须掌握同一语言的规定。优先按项目现有管线选择工具，避免把一个技术栈名单当作岗位定义。
