# 环境概念美术：从透视图中的意图到可解释的制作交接

## 定位与责任边界

本档案聚焦环境概念美术的一项交接：**在已有空间草模或白盒视图上提出视觉设计时，让接收者知道哪些是表现目标，哪些是制作决定，哪些仍然没有定义。** 这里不覆盖全部角色、武器、宣传插画或场景生产职业。

概念图可以帮助团队选择方向，也可以为资产制作提供细节，但一张有说服力的透视图并不自动成为完整的建造规格。画面里看不见的背面、连接方式、实际尺度和运行条件，需要另外说明或协商；另一方面，概念图与最终画面存在差异，也不必然意味着制作出错。

环境概念美术可能使用绘画、三维草模或混合方法。本文不把概念作者限定为只做二维，也不规定环境美术天然拥有玩法审批权。岗位可兼任，职责与修改权限应在具体项目中明确。

## 工作案例与证据

**PlatinumGames，西井智子，2025-09-19。** 《NINJA GAIDEN 4》制作文章区分用于共同方向的氛围意向图（image art）、资产设计和覆盖绘制（paintover）。背景示例以已有白盒截图为输入，在保留其设计要求的同时加强视觉信息和氛围；公开材料经过编辑，可能与最终结果不同。[S1] 这是具体工作方式的说明，不是本库看图比较或玩法验证。

**Bungie，Eric Cassels，2013-05-30。** 这位环境美术在访谈中描述把概念转为可玩空间，通过模型、贴图及编辑器场景组合开展工作。[S2] 该历史访谈提供接收侧职责样本，不能据此推导所有团队的岗位边界、当前组织结构或成品质量。

**原创推论：**交接应首先说明一份图的用途，而不是统一要求“严格照图做”。探索氛围的图和已经约定局部结构的图，可以有不同精度；若不标明这些差别，接收者只能猜哪些像素是约束、哪些只是表达手段。

## 常见任务与交付物

以下为原创、尚未实施的协作建议，不是两家工作室的内部流程。

| 输入与任务 | 概念侧可交付的内容 | 接收问题与边界 |
|---|---|---|
| 世界观与场景目标 | 方向候选、选择理由、关键视觉意图与未决项 | 美术方向负责人选择目标；画面吸引人不证明玩家理解路线 |
| 白盒与空间约束 | 输入修订及视图、保留条件、拟议变化、待确认问题 | 关卡/设计判断变化影响，不能从图中透视推算可靠尺寸 |
| 选定的局部设计 | 需要表达的形状、材料关系、结构细节及尚未定义的部分 | 环境/模型人员能否开始制作，还是需要补视图或讨论？ |
| 已制作候选 | 与目标的差异说明及可接受/需调整的理由 | 不将所有偏离一律视为错误，也不静默更改原意 |
| 方向或空间发生变化 | 旧图失效范围、保留目标和重新确认点 | 接收者能否识别当前依据，而不是使用最漂亮的旧稿？ |

交付物不必是一套厚重文档。工单中的少量标注、图的修订身份和对未定义问题的回答，可能已经足够。是否需要多视图、三维草模或材料说明，应由具体接收问题决定，而非套用固定张数。

## 原创有限工作表：入口区域的覆盖绘制

**完全假设、没有绘制或测试：**作者在一张白盒入口视图上提出装饰框、灯光强调和材料变化。这里不是来源图像的复原，也没有对任何游戏画面作视觉判断。

| 标注类别 | 本例应记录什么 | 接收者可以据此决定什么 |
|---|---|---|
| 用途 | 是探索氛围、细化已选方向，还是提出入口结构变化？ | 目前能否进入制作，哪些仍只供讨论 |
| 输入身份 | 哪个白盒修订、哪一视点；是否另有实际尺寸或空间约束依据 | 不能把旧视图的标注无条件套到新布局 |
| 保留 | 已由设计确认的通行、交互或视线要求，指向实际约束来源 | 不以透视图的视觉宽度代替规定尺寸 |
| 拟改 | 装饰是否伸入通行空间；材料、光照或形状变化意在强调什么 | 需要美术解释、技术评估还是设计重新确认 |
| 未定义 | 背面、接缝、重复模块、材料实现等图中未回答的问题 | 哪些可由接收者在授权范围内决定，哪些须补充说明 |
| 建造后差异 | 候选身份、与目标不同的地方、差异理由及接收意见 | 是合理解释、约束冲突还是需要迭代，而非只数不一致像素 |
| 未验证结果 | 空间可操作性、视觉目标、玩家发现或理解分别缺什么证据 | 不把概念通过误登记为所有下游检查通过 |

“保留／拟改／未定义”是本库建议的标注方法，不是原文公开的字段。若一项视觉建议会改变空间，应明确把它升级为待讨论的设计变化；若只是装饰，也仍需检查实际实现是否意外改变了空间或信息。

### 一个有用的分歧处理例子

假设接收者做出的装饰框缩小了入口。不能仅看结果就判定“建模没照图”或“概念不可实现”：

1. 核对双方使用的白盒与概念修订是否一致。
2. 查找图或附注是否明确了框的立体厚度、通行要求及允许变化范围；透视效果本身不回答这些问题。
3. 若原意未定义，承认这是交接缺口，补充约束或授权接收者解释；不要事后把新要求伪装成原本已说明。
4. 若确实提出了结构变化，由项目指定的设计与制作责任人评估，不能因为画面更好看就默许修改。
5. 对选定方案分别接收美术目标、技术产物及受影响的空间行为；尚未获得的玩家证据继续保留为未知。

这套分歧处理未在真实团队实施，也不证明能降低返工率。它的用途是让下一项决定基于已说明的意图和约束，而不是猜测作者想法。

## 核心技术、工具与典型难题

工作涉及构图、透视、尺度感、材料表达、视觉层级，以及把设计选择讲清楚的能力。绘图、三维草模、截图覆盖绘制和标注都可用于沟通；使用三维工具并不自动意味着交付了最终可用资产。

常见难题是：图的氛围依赖特定视角，而游戏允许其他视角；某个材质表现只在绘图中成立；一处视觉强调暗示可交互，但规则并非如此；白盒更新后旧概念仍被使用。应记录这些假设并找到接收者，而不是要求概念作者独自解决所有导入、碰撞和渲染问题。

## 职业交叉关系与证据边界

- [关卡策划](../design/level-designer.md)：提供遭遇与空间意图，明确美术变化何时需要复核。其方案不是本文入口案例的实际玩法证据。
- [技术美术](../technical-art/technical-artist.md)：负责相关资产/工具接口的支持。可重复导入不能证明概念意图已实现。
- [glTF 属性与几何验收](../../solutions/modeling/gltf-interleaved-attribute-contract.md)：有限实验区分数据合法、属性解释与预期几何；未验证本文资产、DCC 流程或视觉保真。
- [试玩干预与证据边界](../../solutions/production/playtest-intervention-evidence.md)：若要判断玩家是否读懂入口线索，应取得匹配问题的观察；设计者能解释图片不构成玩家理解证据。

下一步应在获准的实际设计交接中选一份明确用途的稿件，记录接收者仍需回答的问题，再评估是否需要补图、补规格或修改空间。本文没有制作资产、运行场景、检查来源图片或取得玩家结果。

此档案只补 ART2D 下环境概念的一项接口，不把一种工作室实践写成全行业流程，也不宣称全学科岗位矩阵已经完成。
