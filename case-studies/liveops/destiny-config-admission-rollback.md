# Destiny 2 配置回退事故：实例准入与角色数据恢复不是同一道验收

## 案例事实：限于开发团队当时的解释

[Bungie开发团队2020年2月11日的复盘](https://www.bungie.net/7/en/News/article/48723)报告：先前角色数据问题用服务配置覆盖修复；2.7.1.1部署时，部分WorldServers启动崩溃后的手工重启同时绕过覆盖加载和版本验证。测试账号恰好访问正常实例，未覆盖异常部分。团队于10:30 PST停服，并将全部角色数据恢复至08:30 PST的备份状态，而非逐一筛选受影响账号。

该文称新增热补丁版本防护已在当日投入使用；启动崩溃修复待Season 10部署，永久可执行代码修复及避免跳过配置等措施尚属后续安排。**这些是2020年发布时的状态，不是本库验证它们后来全部完成。** 这是团队自述，不是我们独立读取其生产日志。

下面不复述完整事故，也不还原未公开的服务实现；提出可供其他项目审查的两道门槛。

## 1. 门槛一：这个实例现在是否有资格修改持久状态？

**原创推论与设计建议，不是Bungie内部架构描述。** 把“进程已启动”“预期配置已生效”“业务不变量通过”“允许承接会修改状态的请求”分成独立观察。一个布尔healthy无法解释它到底证明了哪一层。

建议把一次实例启动的批准记录写成以下逻辑元组，而不是只记录部署任务成功：

```text
boot_identity
+ executable_identity
+ effective_configuration_identity
+ approved_compatibility_rule
+ semantic_check_result
=> eligibility_for_specific_mutating_operations
```

这些是待项目实现的字段，不是已经测过的服务接口。effective应指已解析、实际生效的配置，而不是配置仓库中“打算下发”的版本；身份摘要也不能自行证明内容语义正确。

最低审查问题：

- 正常发布、异常启动后的重试、手工重启和扩容是否都经过同一批准条件？是否存在默认放行的旁路？
- 准入证据绑定本次boot还是可能沿用上一进程的成功记录？配置热变更后谁重新判断资格？
- 某条看似读取/登录的业务路径是否含自动修正、迁移或清理写入？接口名称不能代替写集合审查。
- 无法确认有效配置时，是隔离实例、降级只读还是暂停该操作？必须同时评估容量与可用性代价，不能把“安全失败”当免费策略。

### 技术词汇对照，不作历史技术栈推断

[Kubernetes探针文档](https://kubernetes.io/docs/concepts/workloads/pods/probes/)区分startup、liveness和readiness：启动完成、是否重启和是否接收匹配Service流量不是同一目的。readiness失败会改变相关EndpointSlice中的可用端点；错误的liveness设计还可能放大故障。

这里只借用一个官方定义清楚的例子，**没有证据表明该Destiny事故采用Kubernetes，也没有部署探针**。即使路由不再选择一个实例，也不能据此证明已在途操作取消、旁路调用停止或过去的写入撤销；这些仍需独立业务协议。

## 2. 验证覆盖要能回答“测到了哪些实例和启动路径”

这是原创验收矩阵，尚未执行，不是事故重演：

|受控非生产场景|需要观察的证据|不能用什么替代|
|正常启动，批准的程序/配置组合|该boot的有效身份与业务条件均通过|部署流水线绿色|
|重试启动，配置加载未完成|危险操作尚未获准；恢复后重新生成有效证据|端口已监听|
|人工重启，旧批准记录仍存在|旧boot记录不能授权新实例|上一轮健康结果|
|运行中配置变化|重新评估资格，记录影响范围与未完成请求处理|只看启动时校验|
|同集群存在不同版本组合|测试路由与实例身份可追溯，覆盖预定组合|只统计登录成功次数|

不要凭空规定“抽查百分之几即可”。若测试样本没有实例、版本组合和生命周期路径标签，重复成功可能只重复观察同一类正常状态。该矩阵没有给出统计置信度、采样独立性或全覆盖证明；项目需另定覆盖目标与成本。

## 3. 门槛二：停止新损害之后，哪一份数据可被批准恢复？

**原创恢复审查协议，未执行。** 程序/配置切回批准状态与角色数据回到可用状态应分别签收：前者限制继续产生错误，后者处理已持久化影响。二者不是同一个rollback按钮。

恢复计划至少应标明：

1. **写入隔离边界：** 哪些服务、第三方访问路径、后台任务和在途请求仍可能写入？隔离动作的完成证据是什么？
2. **恢复点与一致性范围：** 备份时间、涉及哪些存储和关联状态；不能从“有一个备份”推断跨系统一致。
3. **保留与损失：** 哪些故障前后有效进度可能被回退，哪些记录需要保留以便后续核对；需要明确授权，不伪装成无损修复。
4. **恢复后的验收：** 用项目定义的不变量、代表性记录和恢复演练确认，而非只确认服务可以登录。
5. **重新开放条件：** 数据验收和实例准入均通过才进入批准阶段；若需要例外，记录决策人、范围和退出条件。

本案例不提供可套用的备份一致性参数、RTO/RPO数值、数据库事务方案或玩家补偿公式。既有[经济账本](../../solutions/design/single-player-economy-ledger.md)和[云存档写入隔离](../../solutions/platform/cloud-save-resume-boundary.md)可以帮助分解职责，但不能证明这套线上服务的恢复协议。

## 4. 明确未知，而不是补齐一幅想象架构图

原文没有给出可供本库复核的配置分发实现、精确启动控制流、逐实例路由记录、备份一致性机制或完整恢复演练资料。本库也没有核实文中未来承诺的最终上线结果。因此不声称根因机制已独立复现，不推算准确故障比例、检测时延或总停服时长，不认定特定数据库/容器/一致性协议。

**可迁移的分析问题是：实例资格的证据是否覆盖所有生命周期入口，数据恢复是否有独立验收？** 上述字段和矩阵是为回答这两个问题设计的原创建议，不是已证明能避免所有事故的产品实现。
