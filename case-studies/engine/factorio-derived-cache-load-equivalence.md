# Factorio 派生缓存失同步：读取前失效与读档后重算必须遵守同一语义

## 第一方事实：修复不是“把缓存存起来”

Klonan 于 2020-03-27 发布的 [FFF #340，Unit group max speed](https://www.factorio.com/blog/post/fff-340)描述：单位组最大速度有缓存，不随存档保存，而在加载时重算；0.17 新增的地块/脚本速度变化打破了此前只依赖 prototype 的假设。移除地块速度修饰能让问题暂不出现，但只是定位手段。文中报告的修复是单位在相关速度变化时通知组重新计算，**不是新增缓存序列化**。

以上仅为开发团队当时的解释；没有独立复现，也不补写未公开字段、存档格式、修复补丁号或触发 tick。本文不复述该页面的其他失同步案例。

## 1. 原创分析：派生属性仍可能影响规则状态

下面的决策门槛与工作表是本库原创建议，不是 Factorio 官方流程或其实际测试记录。

把一个值称作“可重建缓存”，只说明它可以从别的数据计算出来，并不保证运行中的缓存值、当前依赖和重建结果在规则读取时一致。真正需要回答的是：**何时允许读到旧值？运行中与加载后是否都采用相同的答案？**

设权威依赖为 D，派生计算为 F(D)，缓存为 C。不要直接把 `C = F(D)` 当成任意时刻都成立的事实：它可能只在特定阶段、版本或首次读取后成立。项目应明确允许的不变量，例如：

- 急切更新：每次相关依赖变化后，在后续规则读取前完成重算。
- 惰性更新：依赖变化使缓存无效；每个规则读取入口必须确认版本/有效性，必要时重算。
- 分阶段更新：在明确的阶段边界统一刷新；阶段内哪些读取能使用旧值必须是规则的一部分，不能由调用路径偶然决定。

这些是不同可选设计，并非本文验证过的实现。无论选哪种，加载恢复过程都必须与其一致。若运行中合法读取的是某个旧阶段结果，加载后立刻换成新结果可能改变行为；若旧值本来就不该被读取，把它序列化只会延续错误。**保存与重建都是机制，不是正确性的证明。**

## 2. 原创验收工作表：从依赖改变追到下一次规则读取

建议为一项影响模拟的派生值填下表，而不是先增加随机网络扰动。表中“证据”是未来项目应采集的内容，本库没有执行这些检查。

| 边界 | 需要记录的事实 | 应拒绝的模糊结论 |
|---|---|---|
| 缓存填充 | 输入集合、计算规则/配置版本、缓存对应的阶段或有效性标记 | “这是缓存，所以不属于模拟” |
| live mutation | 哪个依赖由哪个入口改变；内容效果、脚本、编辑器或系统更新是否都经过该入口 | “主 setter 通知了，所以所有修改都通知了” |
| invalidation | 通知/dirty 标记是否抵达全部消费者；依赖移除、替换与成员变化是否纳入 | “发出通知就等于读取端已刷新” |
| 下一次规则读取 | 实际读取的 C、当时的 D、是否需要重算、采用哪个阶段规则 | “最终数值正确，所以中间也没影响” |
| save/load | 哪些数据保存，哪些重建；初始化、关联恢复与缓存读取的先后关系 | “存档能打开，所以继续运行等价” |
| continuation | 同一声明状态边界和后续输入下，两条执行的首次状态/事件差异 | “稍后重新收敛，就证明此前没有分叉” |

依赖清单应覆盖实际影响 F 的值，而不是照抄结构体字段。新功能使某个参数从不可变变成可变、或新增一个写入口时，即使缓存代码本身没有修改，也应重新评估这个契约。不能只复测网络报文解析而忽略规则读集合已经扩大。

### 一组应当成对保留的验收轨迹

项目可在同一合法检查点 P 建立两个候选续跑分支：A 不经存档恢复，B 从 P 对应保存数据恢复。两者固定内容/代码版本、后续输入与项目声明的随机状态，比较同一逻辑 tick/阶段，不比较不同墙钟时刻。

把检查点放在有意义的位置，例如依赖变化之前、变化已经登记但刷新尚未发生、刷新后但规则尚未读取。**只有系统支持的合法保存边界才能作为等价性要求**；如果中间状态不允许保存，应验证阻止/延后保存，而不是强行制造不受支持的 checkpoint 后指控实现错误。

先比较加载完成后的恢复范围，再观察首个依赖读取和后续状态/事件。若两条轨迹不同，保留缓存值、依赖值、失效记录与阶段归属，避免只有一个最终 checksum 不同却无法定位。比较字段需要规范化，不能把地址、临时句柄或不影响规则的日志顺序直接当作模拟差异。

以上是待执行的诊断协议，不宣称必须逐字节保存所有派生值，也没有给出通用 checksum 或存档 schema。

## 3. 消除触发条件不等于修复规则

调试时可以暂时关闭一个输入来源，判断差异是否还出现；但产品验收应让该功能重新开启，核对预期语义仍被保留。移除功能、让所有实体冻结或让两边都使用同一个错误常量，都可能消除某种差异，却不能单独说明系统正确。

对于缓存策略，至少把以下代价明确交给设计/引擎/QA 共同决策：

- **急切重算**增加变更传播与频繁更新成本；批量变更可能反复重算。
- **惰性重算**降低部分无用工作，但每个读取入口都必须遵守检查，且首次读取的成本可能集中。
- **序列化派生值**增加版本迁移与一致性校验责任；输入已改变时保存值未必仍有效。
- **加载后统一重建**简化部分保存数据，却要求初始化依赖完整，并验证它与不经加载的合法续跑一致。

这些是工程取舍，不是本案例测得的性能数据。若允许近似或延迟更新，应把允许差异的范围写成规则；不能在出错后才把所有不一致解释为“缓存本来可以晚点更新”。

## 4. 一个短对照：环境变量也可能是复现条件

Rseding 在 2024-06-14 的 [FFF #415，Deterministic multithreading is hard](https://www.factorio.com/blog/post/fff-415)报告，特定区块生成/修改组合与不同 CPU 核数共同暴露失同步；模拟较少核数帮助本机复现。文中称修复将进入 2.0，但没有披露算法。不能推断修复是稳定排序，也不能把这句话当成对后续发行版的独立验收。

本案例的原创建议是：把复现条件登记成可控轴，而不是从“换了机器/操作系统/模组后发生”直接得出原因。缓存依赖实验与调度环境实验是不同问题，不必为每项缓存测试盲目扩展成所有平台组合。
