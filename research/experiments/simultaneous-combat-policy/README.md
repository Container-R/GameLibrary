# 同 tick 相杀：稳定顺序不等于选定规则正确

这是 SOL-PROG-001 固定步文章的有限补充，不是新文章或引擎夹具。2026-10-31 实际使用 Python 标准库执行。没有Godot、物理、联网、真实玩家或生产战斗数据。

## 先冻结规则，再写实现

`source-gate.md`记录读过的现有文章/模型、第一方背景来源及访问失败；`contract.json`在实现前写入并计算SHA256：
`509e8144472248bfd6d69dbe2dc320d8f24d805382e8ae9b3404cf790b74b5df`。
运行器固定核对该摘要。它不是事后从模型输出生成的预期。

**原创选择的政策**：同tick开始时，攻击者与目标都存活才有资格；已合格的攻击不因本tick内的死亡取消；收集伤害后统一提交。每actor最多一个攻击，每次伤害1，仅A/B，HP只允许0/1，无治疗或复活。别的游戏完全可能有意选择先手击杀阻止反击，本例不把那种规则称为引擎缺陷或不公平。

最小手算表：

|tick7初态|选定政策终态|事件|
|---|---|---|
|A=1、B=1，互相攻击|A=0、B=0|两条伤害、两条死亡|
|A=0、B=1，互相攻击|A=0、B=1|无；死者不能攻击，死目标也不可攻击|
|A=1、B=0，互相攻击|A=1、B=0|无；同上|

比较的是按身份规范化的状态及事件记录；没有规定实际事件发出的时间顺序。伤害事件身份含tick、攻击者、action及目标，死亡事件按tick、actor表示。这里不是跨重放去重服务；重复调用相同tick会重新得到同一事件，不提供提交凭据或exactly-once保证。

## 实际运行与结果

从仓库任意目录，用脚本真实位置替换下面的路径，并将输出放到新位置，避免覆盖历史记录：

```sh
python -B /path/to/experiment/run.py > /tmp/new-combat-policy.json
python -B -O /path/to/experiment/run.py > /tmp/new-combat-policy-optimized.json
python -B /path/to/experiment/test_model.py
```

运行器只读合同/源码、向stdout输出；不清理或改写归档结果、不启动子进程。失败抛异常并非零退出，不能把旧输出文件当作这次成功。规则检查使用显式异常而非assert；`-O`正常执行相同检查。

实际原始输出：`author-results.json`、`optimized-results.json`、`test-stdout.txt`、`test-stderr.txt`。Python与平台实测值、源摘要都在结果内。两种模式的12条traces完全一致，只有记录的optimization字段不同；不是两个独立平台。

- 3种冻结初态 × 2种actor映射构造顺序 × 2种命令遍历顺序 = **12种有限输入**。同时结算全部符合手算预期。
- 对同样12种输入分别运行朴素立即修改与固定排序后立即修改。两者各在4种双方存活输入中违背同时结算政策；8种初始死者边界与预期一致。
- 朴素立即修改：第一个遍历的攻击者存活，交换命令顺序使胜者改变。
- 固定排序立即修改：A始终先行动并存活。虽然结果可重复，仍不满足选定的双方死亡政策。
- 每种双方死亡结果再进入tick8，原攻击意图不产生事件：**4次相邻tick检查**，不额外算4种主枚举初态。
- **5个unittest方法**检查部分非法输入与返回值不别名调用者状态；不是5种额外战斗政策或完整输入验证证明。

运行器还核对调用者HP未被三种实现修改。Counter仅累计已合格攻击的目标；读取资格使用当前tick开始快照，而不是在遍历中更新的HP。

## 对既有证据的增量

已有固定步Python模型是每tick一个加法标量，Godot固定步夹具是单x/axis和攻击窗口标签；它们准确证明自己的调度/回调合同，但没有表达多人资格与伤害提交。本补充不重测渲染分片或增加随机种子，而是将一条业务规则写成能失败的判据：**时间切分正确、命令排序稳定，仍不能替设计者决定同tick冲突语义。**
