# Rocket League 输入缓冲：生产节奏不等于权威端消费映射

2026-11-01。证据状态：**source-backed**。本文依据历史演讲的原始文本，提出原创、未执行的交接问题；没有运行游戏、网络或模型，也没有观看视频或解释动画图示。

## 同一个“frame”字样，不能省略映射合同

以下分析为原创，不是复原 Psyonix 的完整控制器。

接收端需要区分至少四种东西：客户端生成的输入记录、服务器实际接纳的记录、从等待队列移出的记录，以及权威模拟步。输入到达快慢、队列占用和模拟推进不是同一个量。改变生产节奏与改变消费映射，也不是可互换的修复开关。原创决策问题是：这次干预要改变新输入的生产节奏，还是改变已有输入的复用与映射？两者应分别定义接收语义，不能仅凭缓冲回到目标范围就推断性能或正确性改善。

尤其不能把“每帧消费两个输入”补写成“两次完整物理世界步”，或补写成取最后一个命令、平均、累计位移或分成子步；所选文字没有给出这些机制。若接收团队不先写明含义，相同的输入计数就可能掩盖不同的玩法时长与状态更新规则。

## 一个只用于明确单位的记账式

可以另行提出以下队列定义：B是区间开始时等待记录数；A是该区间实际接纳入队的新记录数；C是实际移出的记录数。若没有其他删除、清空、丢弃、溢出或重复插入，且C≤B+A，则：

`B' = B + A − C`。

这是原创建议中的守恒记账，不是所选幻灯片公开的算法。网络上尚未送达或未接纳的记录不算A；再次使用已保留的旧输入不自动算一次移出。幻灯片中的“消费”也不能未经证据直接等同这里的C。

该式只帮助检查计数口径，不能求出合理缓冲长度、生产调节幅度、何时重复输入或控制器是否稳定。若还有丢弃、过期、合并或队列重置，必须分别记账，不能继续用缺项的等式解释全部变化。

## 原创交接表：先回答什么，再讨论调节策略

这张表是未执行的接收提案，不是 Psyonix 的字段表或既有遥测规范。

| 交接面 | 必须说清的问题 | 需要保留的区分 |
|---|---|---|
| 输入生产 | 一个记录代表瞬时状态、边沿事件还是某段时间的输入？生成时间与序号如何定义？ | 客户端生成记录数不等于服务器已收到或已应用数 |
| 网络接纳 | 什么记录可以入队？重复、过期和无法使用的记录如何处理？ | 原始到达、有效接纳和实际执行分开 |
| 权威步消费 | 每个权威步采用哪些输入身份？复用或多个输入参与时，具体状态更新规则是什么？ | 队列移出数不等于物理世界步数，也不自动决定模拟时长 |
| 缓冲变化 | 哪个操作改变了队列占用？是否存在丢弃、清空或重置？ | 计数守恒不代替调节策略或稳定性分析 |
| 纠正与延迟 | 哪些状态需要纠正？输入等待与后续纠正分别造成什么成本？ | 缓冲占用、等待时间和纠正幅度不是彼此的测量替代品 |

这不是建议客户端自行增加权威模拟时间，也不是建议所有游戏都重复输入或一次消费两个记录。可选策略要服从实际输入语义、状态更新合同和另外取得的验证证据。
