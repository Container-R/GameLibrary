# PSO 预缓存首显验收：新增 pass 应对照什么，而不只等待什么

核对日期：2026-11-01。本文依据 Epic **Unreal Engine 5.6** 版本化手册，提出原创、未执行的组件首显接收方案。没有运行 UE、编译 PSO、操作驱动缓存、观察缺失的 PSO 或测量性能；也没有检查引擎实现。

[呈现队列与输入时效](../../solutions/rendering/presentation-queue-latency-boundary.md)讨论呈现请求与上游工作，不验证 UE 的 PSO 覆盖。本条关注更具体的交接：**渲染程序为组件增加一个 pass / render-target 组合后，收集路径是否描述了实际绘制需要的状态，以及准备不足时允许显示什么。**

## 文档支持的有限机制

Epic 的 [PSO Precaching（5.6）](https://dev.epicgames.com/documentation/en-us/unreal-engine/pso-precaching-for-unreal-engine?application_version=5.6)说明：资源收集可能缺少组件状态；组件的不同 pass 都需要相应 PSO。未完成时可延迟代理而跳过绘制、暂用默认材质，或继续并阻塞等待编译。`r.PSOPrecache.ProxyCreationDelayStrategy` 的值 `0/1` 分别对应前两项，且依赖 `r.PSOPrecache.ProxyCreationWhenPSOReady=1`；这里不定义“策略 2”。

加载页讨论等待**当前**请求。编译完成后，首次从驱动缓存取回仍可能有成本。验证区分 shader-only、minimal、full，full 包含 render-target 信息；前两种统计依赖 `r.PSOPrecache.Validation.TrackMinimalPSOs`。Missed、Too late、Untracked 不同，shipping 缺少相应调试信息时，Untracked 会显示为 Missed。默认 hitch 阈值不是产品帧预算。

定位：*Configure PSO Precaching*；*Component PSO Precaching / Proxy Creation Delay Strategy*；*Loading screen*；*Manage System Resources / Memory*；*Validation and Tracking*。上述为紧凑概述，不是参数表转载。页面标为 5.6，但补丁、不可变提交与首次发布日期未确认；可变手册不能代替某个构建的实现审查。单独 API 页未成功读取，不据此推断计数器的并发语义。

## 一个新增组合的接收表（原创，未执行）

假设项目给一个组件增加了实际绘制 pass / render-target 组合。已有报告只说“加载阶段剩余请求曾归零”和“shader-only 没发现缺失”。**没有假定新组合一定遗漏，也没有假定它会卡顿。** 待解决的是这两项报告是否足以接收新增功能。

| 接收问题 | 交付方应提供的具体对照 | 接收方作出的决定 |
|---|---|---|
| 新绘制路径改变了什么？ | 指定组件、材质、vertex factory、pass、目标格式/状态及声明适用的渲染配置；标明是新组合还是既有组合 | 把验收对象固定到这一组合，不把同材质其他路径的通过结果移用过来 |
| 收集路径如何覆盖它？ | 对照该组合的预收集输入与实际绘制输入；指出改动落在收集器、绘制路径或两者 | 缺少完整状态观察时保留“未建立覆盖”，不能以 shader 身份相同代替 |
| 未就绪时能显示什么？ | 明确该组件实际支持的处理方式，并给出临时缺席、默认材质或等待对该对象的影响 | 分别签收画面退化与时间代价；不把“少一次编译等待”自动等同于功能正确 |
| 出现异常时去查哪里？ | 保留实际状态分类、关联组合及对应时刻；先区分未覆盖、已排队但太晚、已覆盖仍有首显成本 | 分类是调查入口，不是单独的根因证明；不同 build 的分类信息不可机械等同 |
| 首显是否满足产品要求？ | 记录约定场景中首次使用的实际画面与时间观察、缓存条件、验证设置；明确未覆盖配置 | 用项目预定标准接收，不以计数归零或没有默认阈值事件替代结果 |

文档中 *Extend PSO Precaching with Engine features / FMeshPassProcessor* 与 *Debug a PSO Precache Miss* 给出收集与绘制状态的调查入口。本表借此提出接收问题，**不是声称已经比较过任何实际收集器代码或证明其遗漏**。

## 画面退化也需要一个明确的负责人

例如，一个对象承载操作提示或遮挡关系。暂时不绘制可能影响信息传达；默认材质可能保留轮廓却改变表面含义；等待可能保住外观却增加时间代价。这些是需要产品、内容与渲染共同检查的可能性，不是本库观察到的事故或玩家研究结论。

因此，提交者应说明“允许的临时画面是什么”，而不只说“采用了预缓存”。若对象不允许缺席或替换，应另外决定准备何时触发、何时允许它进入可见流程以及如何接收等待成本；不能凭一个全局策略编号假定所有组件均支持相同处理。本文没有推荐普遍关闭等待、保留全部 PSO 或采用默认材质。

## 这项接收不能证明什么

当前请求归零只描述当时观察的请求范围，不证明未来内容已提交；shader-only 结果不覆盖完整状态；完整状态覆盖也不等于首显时间已达标。三项需要互相关联，却不能互相代替。

同样，本方案不能诊断全部帧卡顿、证明所有平台无停顿，或给出线程数、内存保留量与加载时间的通用最优值。只有选定组合的真实观察，才能把本表从接收计划变成结果；没有观察时应保留未知，而不是用“PSO 已完成”补写保证。
