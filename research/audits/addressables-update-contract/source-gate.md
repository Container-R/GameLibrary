## One original falsifiable engineering question

**For a particular already-released player P on platform T, can the update job prove it consumed P/T’s preserved original state file rather than a different release’s cached state file, and can that exact player resolve the intended changed and unchanged assets through the proposed catalog?**

The documented fallback makes “the remote baseline URL was configured” weaker than “these are the state bytes used.” This is materially different from Godot cache-mode ownership: here the baseline is a build-time dependency that selects names/references for an installed player. A successful build and an unchanged player executable hash do not establish the whole player-plus-catalog-plus-bundle combination was tested.

## Bounded next step if source-only analysis is approved

Develop a concrete release-lineage intake rule, not a generic worksheet: record player release/platform, preserved baseline-state digest and origin actually selected, group restriction configuration, Unity/Addressables/build-script versions, resulting catalog/hash/bundle inventory and target content endpoints. **Original proposed gate:** if the selected baseline cannot be tied to the intended published release, stop candidate promotion rather than infer correctness from build success. This is our policy derived from documented inputs, not a claim the package validates a custom digest for us.

For later actual Unity work, a minimal original project could preserve two independently named release baselines, alter one static-group asset, and contrast intended-baseline versus controlled stale-cache selection. Freeze the documented remote-missing condition exactly; do not generalize it to all HTTP failures. Record selected state bytes, generated references and actual old-player loads of changed/unchanged assets. A mismatched baseline might fail or produce output; no outcome is assumed. Separate cold/warm runtime bundle cache from **build-time previous-state cache**. No fabricated runtime result can substitute for this missing test.

## Limits and decision

Actual-runtime feasibility is unresolved until a compatible licensed Unity project/toolchain and controlled hosting setup are legitimately available; this gate neither installs nor requests credentials. No claim of end-to-end CDN rollout order, rollback safety, manifest signatures, platform compliance, universal type-tree compatibility or live mid-session replacement. The sources do not establish every HTTP/cache fallback error path or give a complete compatibility algorithm. Keep those unknown rather than invent another Python simulator that only enforces our own policy.
