# 设置页异步完成顺序：有限教学模型

本材料服务于 TASK-2026-0308，目的只是区分“最终内容看起来正确”与“每次提交都有正确归属”，不是原生引擎实现。源码为本轮独立编写的 Python 标准库模型，未使用外部实现代码。实验把执行观察绑定到明确的输入和主张，保留命令、环境及实际输出，不把教学模型冒充完整游戏验证。

## 运行与真实产物

在这三个文件所在目录执行：

```sh
python3 settings_model.py > results.json
```

运行环境：Python 3.12.14（Clang 22.1.3），Linux 6.18.57 x86_64，glibc 2.41。脚本输出自身环境，实际记录见 `results.json`。没有安装额外依赖。断言失败时进程非零退出；JSON 仅在全部断言完成后输出，不将异常转为通过。执行结果：15 项通过，包含三请求先受理后的全部六种完成排列。此数字是案例数，不是覆盖率。

文件：

- `settings_model.py`：可审阅、可复现的完整源码。
- `results.json`：上述命令的实际标准输出，包含输入操作事件、被忽略结果、内容提交、布局回执及逐项支持的主张与未测边界。
- `README.md`：解释观测范围及复现方法。

## 执行前判据与模型约定

代码中的断言就是本次固定判据，没有以输出结果改写通过条件。

1. 受理后的 token 为 `(generation, request_id)`，标识请求实例，不能以语言字符串比较替代。request_id 在当前 Preview 实例寿命内单调递增，close 和 reopen 均改变 generation。不同 Preview 实例并不共享回调接收器；若生产实现共享跨实例接收器，需另加实例唯一标识或保证 generation 全局唯一。
2. 受理时先记 records、current 及 pending，再调用 start。start 可以同步调用 complete。完成入口只使用加载启动时捕获的 token，不以完成时的 current 替换它。
3. complete 的校验与提交被建模为一个串行步骤。只有视图仍打开、token 等于 current、记录存在且未终结时才处理。成功和当前失败均终结该请求，因此重复完成不可重试成功。显式新请求才是重试。
4. “最后受理的请求生效”是提交归属规则，不是无条件的成功保证。本模型的 content 保留上次成功提交的逻辑历史值，不描述实际画面。新请求 pending 或 failed 时，产品可以显示占位、错误提示或旧内容；本文正文采用占位策略，本模型没有实现显示层，不能用保留的 content 证明旧内容实际上屏。若产品选择继续展示旧内容，这是另一种产品策略。成功提交后的 status 名为 content_ready，仅表示内容提交已完成，并不表示布局就绪。拒绝受理不改变 current。取消会撤销 current，并非证明加载器实际取消。
5. 布局输入是 `(generation, content_version, scale_version)`。成功内容提交或缩放改变使先前布局完成标记失效。回执只能确认完全相同输入；本模型不计算文本尺寸，不含伪造的几何数据。重复的相同有效布局回执只重复赋同一个标记，不代表新一轮布局工作。
6. 布局输入针对已提交内容，不针对仍在加载的请求意图。旧内容的有效回执可以在新请求等待时发生；它不能用于断言新请求已经成功。`operation_ready(token)` 显式要求视图打开、传入 token 非空且同时等于 current 与 committed_token、status 为 content_ready、layout_done 匹配当前非空布局签名。这是本次操作的逻辑就绪条件，不是上屏证明。对应测试覆盖仅内容完成、旧回执到达新请求等待期、当前失败、缩放改变和关闭重开。

## 各项观察的意义

JSON 中每项均含 `supports` 和 `not_tested` 字段。主要分辨如下：

- 乱序与 ja/fr/ja：值相同不能合并请求实例，迟到旧结果不提交。
- close/reopen 与跨视图布局回执：请求和布局回执均要隔离视图代际。
- 当前失败、过期失败与旧内容保留：错误的归属也要检查，失败不可冒充成功。
- 取消后迟到、重复完成、拒绝受理：分别检查撤销有效身份、终结状态以及受理边界。
- 同步缓存完成：检查启动前受理记录已可见，而不是假设所有异步 API 都会延后回调。
- 旧布局回执：内容版本与缩放版本任一改变，均使旧回执无权确认新输入。
- 六种完成排列：穷举的是三次请求全部先受理这一有限子集，不是穷举所有状态交织。
- 刷新掩盖反例：独立执行 L1(ja)→L2(fr)→C2→C1→S。故意错误的回调不检查身份，C2 先提交 fr，C1 又提交旧 ja；S 在这个有限模型中被明确定义为缩放操作附带按当前目标 fr 重建，因此最终恢复 fr。S 是本实验人为定义的行为，不是 Unity 或通用布局系统机制，不能据此声称引擎缩放一定重建语言内容。
- 完成时重贴 token 反例：保留另一条独立序列，在完成时使用当前 token 校验旧 payload，先非法提交旧 ja，再提交 fr。两例最终逻辑快照正确而历史均存在一次非法旧提交。此处 `passed` 意为反例成功出现并被断言检出，不代表错误实现通过正确性要求。

## 不能从本次运行推出什么

没有 Unity、真实布局、帧时序或游戏验证，没有字体、字号、换行、像素测量、性能或体验结论。事件顺序是人为指定的序列，不是实测网络延时。模型假设校验到提交间不发生重入；真实多线程入口需串行化/同步保护，真实 setter 触发重入时还需检查提交边界。没有验证资源所有权、Addressables 引用计数、取消后的释放、错误报告线程、布局请求合并、缩放范围与 NaN、重复 open/close、长整数回绕、用户关闭后持久化偏好如何处理。records 在本模型中保留全部记录便于观察；生产实现应设计终结记录与迟到回调的生命周期，不能照搬为无限增长容器。

单次 request_id 和版本号是逻辑计数器，不能被引用为帧号或真实系统耗时。错误提交是否上屏还需在实际引擎中观察渲染时序；本反例只能证明最终快照遗漏了提交历史，不能声称用户看到了闪烁。
