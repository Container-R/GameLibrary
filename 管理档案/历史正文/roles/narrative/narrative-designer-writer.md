# 游戏叙事设计与写作：让对白意图、知识状态和实现条件一起交接

> **历史技术补充（迁移衍生），不是当前读者书。** 当前阅读请见[《游戏编剧与叙事设计师如何协作》](../../../../GameLibrary/叙事设计/剧情制作/岗位与协作/游戏编剧与叙事设计师如何协作.md)。以下保留旧正文的完整技术上下文、来源和未执行范围；此次只增加历史标记并调整链接，没有重新运行或重新认证历史主张。原路径与前后文件绑定见[迁移记录](../../迁移记录-source-group.json)。


## 定位与责任边界

本档案只聚焦一项工作：**把互动对白的叙事意图，转成接收团队能够解释、实现和检查的条件，而不只交付台词文本。** 一句台词能显示、选项能点击，并不证明它符合角色当前知道的事，也不证明选择兑现了向玩家作出的承诺。

Narrative Designer、Writer、Scenario Planner 和 Quest Designer 不是可直接互换的全球职称。具体团队可能由同一人编写、配置和检查内容，也可能分工协作。本文不设统一审批链，不要求写作者独自实现状态系统，也不假定只有程序员才能修改分支。

这里的职责样本不覆盖全部世界观、线性剧情、过场导演或叙事研究工作。核心是让**角色意图、可成立的情境、实际系统行为和未决项**有明确交接。

## 工作案例与证据

**Guerrilla，Annie Kitain，2023-04-17。** 访谈将她介绍为《Horizon Forbidden West: Burning Shores》的 Lead Writer；她谈到写作与 Quest、Design、Art 协作，并以《Forbidden West》的任务顺序和隧道情境说明如何考虑角色已知信息与开放世界变体。[S1] 这不是她声称覆盖了所有排列，也不意味着所举例子都属于 DLC。

**Monolith Soft，河野、佐藤、岩本，2023-07-18。** 剧情策划（シナリオプランナー）访谈描述超出文字编写的规划与事件制作职责，明确范围因项目而异；主线及场景变化会影响内容调整，录音和海外翻译也构成下游时程约束。[S2] 不能把每项职责归到某一部未明确指认的游戏。

**Guerrilla，玩法程序员 Leszek Szczepański，GDC 2017。** 《Horizon: Zero Dawn》任务系统演讲以图结构和行动词连接故事事件与规则，也指出进度回退及行动词覆盖的限制。[S3] 这是任务架构样本，不是两篇访谈团队共用的对白数据库规范。

**本库推论：**交接既要说明“希望角色表达什么”，也要说明“在什么状态下这句话才成立”。以下字段和问题均为原创建议，不是上述工作室的内部模板或已执行流程。

## 常见任务与交付物：一份语义交接表

| 任务 | 建议交付的内容 | 接收方要回答什么 |
|---|---|---|
| 定义一次交谈的作用 | 说话者欲望、当前知识、玩家角色知识、这段对话改变什么理解或机会 | 这句承认的是世界事实、角色相信的事，还是尚未兑现的承诺？ |
| 组织可出现的内容 | 分支身份、内容修订、资格条件、重复进入含义、优先级及无匹配回退 | 同时满足多个条件时谁先出现？无条件匹配时如何结束或补救？ |
| 对接玩法状态 | 条件的事实来源、对白请求的动作、动作完成证据、失败/中断后的规则 | 点选即提交，还是待某系统确认？台词说“给你”不等于资源已入账 |
| 提供语言与表演上下文 | 说话者/听者、指代对象、语气、条件含义、可能前后文、占位符语义 | 离开原编辑器后，接收者是否仍能解释这行话？ |
| 接收修订 | 修改的是措辞、知识前提、资格条件、状态效果还是表现；受影响对象与未决项 | 哪些原有批准仍适用，哪些需要内容、实现或语言侧重看？ |
| 定义有限验证情境 | 作者认可的状态快照、预期语义分支、可观察效果及明确排除范围 | 实际结果是否满足该情境，而非只是文本相同或脚本无报错？ |

这些不是强制字段表。小团队可以用表格和可复查的配置；复杂项目可能由工具维护关系。重要的是把分支、文本与状态含义对应起来，不以易变行号或显示字符串代替所有身份。身份与修订只能定位内容，不能证明它写得好。

## 原创假设：桥修好了，但这项任务未必完成

**以下为虚构、未实现、未运行的交接情境，不是 Horizon 隧道复刻或 Monolith 的游戏内容。** 某 NPC 有两种问候：承认玩家已经修桥，或者请玩家修桥；交谈另有一项领取报酬的选择。玩家可能通过另一项任务提前修好了桥。

### 1. 将三个判断分开

- **世界事实：**桥是否已修复？由哪个系统提供，何时读取？
- **角色知识：**NPC 是否知道修复已经发生？是否需要玩家告知，或允许角色尚不知情？
- **任务资格：**本任务是否达到报酬条件？是否要求交付证明、完成别的步骤或尚未领过？

三者可以相关，却不能未经设计决定就共用一个“完成”标记。若 NPC 不知修复，仍请求修桥可能是有意的信息差，而不是 bug；必须有角色和任务规则支持，不能事后把任何矛盾解释为设定。

### 2. 把优先级变成可接收的决定

如果“桥已修复”和“任务进行中”同时成立，交接应给出预期问候或说明暂未决定。不要让编辑器行序意外成为产品规则；但也不禁止项目有意采用并记录有序优先级。

为每个选项说明可见、可选和执行后的含义。例如“询问报酬”可以只是提问，并不意味着立即发放。若选择会请求发奖，应分别确定请求、实际效果和反馈的观察点；这里不规定通用事务或幂等实现。

### 3. 中断不能由台词本身定义结果

假如玩家选择报酬后离开交谈，内容方与实现方需要约定：承诺是否已作出，奖励是否已经提交，下次进入应该说什么。已发生的世界效果不会因为对白退出就自动撤销；反过来，已经播放一句承诺也未必说明效果发生。

这是一组待项目决定的问题，不是本文已经验证的中断协议。若接口尚不能反馈结果，就明确尚未验证，不用一个“对话结束”事件代替全部效果证明。

#### 独立 ink 例子：向前探测不等于宿主动作提交

ink **v1.2.1** 的固定 C# 实现提供一个具体机制：为了判断换行是否被 glue 合并，引擎会保存故事快照、继续向前求值，再按后续内容恢复。允许 lookahead 的宿主外部函数因此可能提前或重复调用；恢复故事快照不能被当作撤销宿主副作用。[S4]

这里还有不能凭名称猜测的默认值差别：`BindExternalFunctionGeneral` 的 `lookaheadSafe` 默认 **true**，所核对的无参数 Func／Action 便利重载默认 **false**。后者在换行快照后的探测中会暂不调用宿主函数；但字符串求值中的 unsafe 调用会报错，不能靠把参数改成 true 来掩盖。[S4]

把它放回**原创、未执行的桥梁场景**：如果发奖函数绑定到 general 入口却省略参数，作者看见前一行对白还未结束，不足以断言奖励尚未发生。假设函数已在探测中执行，随后故事恢复，不能据此把宿主奖励账目也恢复。这里没有运行脚本或断言固定调用次数，更不是 Guerrilla 或 Monolith 的实现案例。

具体交接应是：对白作者与宿主程序共同指出哪些外部动作不能接受提前／重复求值，对它们显式选择 `lookaheadSafe=false`，并放到允许这种调用的普通执行位置。需要显示结果时，可先在普通语句求值再用于文本；**移到文本之前，不等于移到玩家选择之后**。若发奖必须由已选项触发，还须安排到相应已选分支的执行路径，不能放在仅生成选项文字时执行的位置。

这项配置只处理所述探测边界，不是幂等或恰好一次机制：再次进入分支、读档或重试仍需另定规则。只读函数也不能仅因“不写文件”就标 safe，提前／重复求值的结果必须可接受。本例未验证具体选择脚本、奖励事务或玩家表现；它补的是外部函数执行位置与绑定策略，不替代前文提交结果的观察责任。

### 4. 让本地化接收到条件，而不只是“完成了”

为相关条目提供“完成”指桥梁修复、任务登记还是奖励领取的上下文；说明说话者、指代与语气。译者不应被迫从孤立短句猜测系统状态。语言侧可能发现原文歧义并反馈，但不能要求译者替团队选择奖励规则。

如使用变量插入，另交付其语义、类型与格式规则；[伪本地化与占位符契约](../../../../solutions/localization/pseudo-localization-contract.md)处理的是格式及布局风险，不证明本段对白的翻译或叙事含义正确。

## 原创、未执行的有限接收情境

| 条件组合 | 内容方先约定 | 以后实际集成时观察 |
|---|---|---|
| 桥未修，NPC知情，任务未完成 | 请求内容与可用选择 | 实际分支身份、选择资格及未发生的状态效果 |
| 桥经别的任务修复，本任务尚未登记 | NPC是否已知；问候及登记/报酬规则 | 奖励与再次请求均符合约定的任务资格及NPC知识状态，不由单一“已修”标记替代这些规则 |
| 两条候选问候均满足条件 | 明确优先级或调整资格使其互斥 | 实际选中项与约定一致；不以显示顺序碰巧合理验收 |
| 发奖请求后中断，再次进入 | 哪个提交点已越过；重复交谈的叙事及玩法含义 | 实际状态、反馈与再次进入分支分别记录 |
| 台词改写或资格条件调整 | 变更影响的语义、翻译上下文和旧批准适用性 | 不把文本相同视为逻辑未变，也不把每次文字变化都判为必须重录 |

这张表没有执行结果，也不是状态空间穷尽。只有技术轨迹时，结论止于对应分支和效果；对白自然度、人物一致性、译文质量与玩家理解仍需各自适当的评审或观察。

## 核心能力、工具与交叉责任

有用的基础包括角色与情境写作、条件和状态阅读、对任务/对白图的理解、版本变更定位，以及向接收者表达歧义。工具可以是表格、叙事编辑器或引擎配置；本文不推荐一个未经验证的通用工具链。

[玩法程序](../../../../roles/programming/gameplay-programmer.md)帮助落实真实规则与反馈，[关卡设计](../design/level-designer.md)提供空间及任务约束，[QA](../../../../roles/qa/game-quality-assurance.md)保留具体条件与复现，而不替作者决定全部角色意图。职责可能由同一人兼任，但创作决定、实现证据和语言判断不应互相冒充。

[既有 Cygames 案例](../../../../GameLibrary/叙事设计/剧情制作/对白与配音/Cygames如何衔接剧本修改与录音制作.md)继续负责文字/录音/批准的生产交接；本档案不重复其中的录音版本与认可范围交接说明。[ink 来源分析](../../../../research/source-notes/ink-save-content-compatibility.md)讨论另一条内容更新边界，且未执行运行时验证；能恢复路径不证明角色的知识状态和新内容含义仍吻合。

下一项有价值的工作是让真实项目选择一个受控对白，先决定上述语义，再检查实现和接收语言包。当前没有运行对白、验证存档、录音、翻译或玩家结果；本文不能支持完整分支覆盖、发布审批权或效率提升声明。
