# 交互音频设计：从声音意图到游戏内验收的责任接口

> **历史技术补充（迁移衍生），不是当前读者书。** 当前阅读请见[《交互音频设计师的工作与协作》](../../../../GameLibrary/声音与音乐/游戏音效/岗位与协作/交互音频设计师的工作与协作.md)。以下保留旧正文的完整技术上下文、来源和未执行范围；此次只增加历史标记并调整链接，没有重新运行或重新认证历史主张。原路径与前后文件绑定见[迁移记录](../../迁移记录-source-group.json)。


## 岗位定位：交付行为，不只交付文件

交互音频设计需要把“玩家应听懂什么、感到什么”变成可在游戏状态、空间和时间条件下工作的声音行为。本条将它作为跨声音创作与实时实现的责任集合，而非断言所有工作室都有同名职位。

**核心产出建议**：一套能说明意图、来源、触发、变化、结束、资源成本与验收证据的音频功能。单独好听的 WAV、DAW 工程、中间件工程和游戏构建各自都不是完整交付。

## 四种责任轴：可以一人兼任，不能无人负责

| 责任轴 | 首要决策 | 典型交付 | 需要明确的越界接口 |
|---|---|---|---|
| 声音设计 Sound Design | 声音语言、可识别度、变化与听感层级 | 素材/变体、事件意图、参考与批注、游戏内混音调整 | 不凭单段试听决定运行预算；触发时机需与玩法确认 |
| 技术音频设计 / 集成 Technical Audio Design | 将创作意图编成可维护的事件图、参数、路由和构建管线 | 中间件工程、映射表、导入/命名检查、调试场景 | 修改公共接口、线程或生命周期策略时需工程负责人验收 |
| 音频程序 Audio Programming | 运行时正确性、平台行为、工具与性能 | API 适配、资源/句柄管理、诊断、自动测试、性能证据 | 不把返回成功当成体验验收；不自行替代作曲判断转场音乐性 |
| 作曲 / 交互音乐 Music Composition | 音乐叙事、主题、结构、编配与音乐连续性 | cue/stem、段落与桥段、节拍/入口/尾音说明 | 是否负责中间件实现、录音与最终混音须在委托范围中写明 |

音频总监或指定负责人裁决声音方向与范围；玩法设计确认信息语义；制作人员安排依赖与交付窗口；QA 检查可复现行为。小团队可合并岗位，但“制作完成”“集成完成”“体验通过”仍应分开记录。

## 从需求到接收：六个门槛（原创交付流程）

### G0：需求能被观察

先问：这是命中确认、危险预告、位置线索、环境氛围还是音乐情绪？谁应听到，何时不应听到？同一个动作的预备、成功、失败和取消是否不同？

交付一页 brief：玩家目标、必听信息、参考、触发条件、终止条件、空间/混音假设、平台与输出设备范围、验收场景、排除项。不用“更有冲击力”代替可讨论目标，可补充“密集战斗中，命中确认不能被同类连续声音完全覆盖”的场景描述。

### G1：资产可追溯、可重新生成

每批素材附 manifest。以下是**字段建议而非已执行 schema**：

| 字段组 | 必须明确的内容 | 拒收或待澄清情况 |
|---|---|---|
| 身份 | 稳定 asset_id、版本、内容哈希、负责人、替代关系 | 覆盖旧文件却不更新版本，无法判断构建用了哪版 |
| 来源记录 | 原创/录音/素材库/委托、来源链接或内部编号、授权文件位置、批准的使用范围 | “网上下载”或“免版税”却无具体来源与审核记录 |
| 可再生成性 | DAW/插件版本、依赖清单、可用导出或替代方案 | 只有他人无法打开的工程，缺离线渲染备份 |
| 格式 | 容器、编码、采样率、位深、声道数、声道布局、时长 | 不按项目规格；声道含义不明 |
| 循环/尾音 | 是否循环、循环区间及单位、前导静音、尾音、停止方式、是否允许交叠 | 只标注“loop”却无边界，首尾或停止行为未说明 |
| 音乐专用 | stem 对齐基准、共同起点/长度、节拍/拍号及变化、入口/出口、桥段 | stems 单独导出后失去同步；只有 BPM 没有结构说明 |
| 电平/响度 | 项目采用的度量、测量工具/版本、窗口/测试场景、峰值与目标容差 | 只有一个不带单位或条件的“响度值” |
| 资源策略 | 是否流式、内存与并发预期、平台转换/压缩规则的负责人 | 内容作者擅自固化运行时编码或成本假设 |

来源记录是审核入口，不是本文给出法律许可结论。商业发行、宣传片、原声带、素材转交等使用范围是否覆盖，应由项目授权审核确认；未知时不进入可发布资产集合。公共知识库只保存说明与链接，不把受限素材或采购证明直接公开。

**不要伪造全行业响度标准。** 本条不指定统一 LUFS/dBTP 数值，也不把流媒体母带目标套到游戏每个音效。项目须分别约定原始素材、总线和实际玩法混音的测量对象与验收方法；数值合格仍不等于可读性、动态与听感合格。

### G2：事件合同能解释“什么时候”和“对谁”

最小事件条目应包含：语义 ID、调用方、一次性/持续类型、参数范围/单位/默认值、状态作用域、重复请求规则、结束/取消语义、对象销毁行为、失败回退、路由、空间假设、并发/优先级负责人。

例如蓄力武器不能仅交付 `Play_Charge`：必须回答松手、击退、死亡、武器卸载分别如何结束；释放声音是否依赖真正成功发射；多个玩家是否各有实例；迟到通知是否可能作用到新武器。游戏玩法提供事实，音频设计提供表达，不应由资产文件名暗示游戏规则。

音乐接口直接复用[音乐状态交接契约](../../../../solutions/audio/music-state-transition-contract.md)：期望模式、成功提交与实际观察分开；异步启动/重试联合检查 generation、生命周期和 revision。不要复制一份较旧状态机并漏掉“退出后资源才就绪”与“旧 revision 重试覆盖新意图”的验收。

### G3：导入构建可重复

接收方在干净工作区验证依赖、命名、ID、素材范围与构建目标，记录游戏版本、中间件版本、工程/素材版本、构建配置。自动检查适合捕捉缺失引用、非法格式和 ID 冲突；不能宣称它已替人听过接缝、遮蔽、情绪或空间问题。

若构建产物与源工程不同步，阻止进入集成验收；不要用“在作者电脑上能播”作为关闭条件。插件缺失、素材路径错误、授权未核实分别报告，不能都归入“音频坏了”。

### G4：游戏内功能与性能共同验收

建议按同一场景交付三类证据：输入/状态日志，实际实例与资源捕获，带设备/设置标记的听感记录。分别回答：规则是否正确、代价是否可接受、玩家是否能听懂。

| 场景 | 集成检查 | 声音/音乐检查 |
|---|---|---|
| 正常触发与高频重复 | 实例数、去重、参数与资源归属 | 重复感、遮蔽、混音层级 |
| 循环长播与中途停止 | 边界、退出路径、资源回收 | 接缝、尾音截断、意外静音 |
| 快速进入/退出与异步加载 | 已取消会话不复活；旧任务不覆盖新请求 | 无意外重启或过期转场 |
| 多对象与空间移动 | 作用域、监听者、路由、销毁 | 定位是否符合产品意图 |
| 密集战斗/低配压力 | 峰值并发、CPU/内存/流式读预算 | 必听反馈是否仍存在 |
| 暂停、后台、设备变化、场景重载 | 产品策略与实际生命周期一致 | 恢复无异常重复/断裂，输出符合设置 |

预算、测试平台和容差由项目填写。本条没有实测结果，不能把上表视为已通过测试。

### G5：可发布、可回退、可维护

交付接收记录至少区分 `asset-ready / integration-ready / experience-approved / release-approved`。这是建议状态，不是中间件自带 API。每次批准对应具体版本、负责人、已通过用例、例外与未覆盖范围；声音已批准不等于版权/平台/性能已批准。

保留上一组已验证的源工程与兼容构建产物。回退资产时检查事件 ID、参数映射与游戏代码契约是否仍兼容，不只替换音频文件。临时禁用一个声音也应记录影响范围，避免永久“静音修复”掩盖生命周期错误。

## 如何处理分歧，而不是甩给“音频部门”

- **孤立素材好听，战斗中听不清**：声音设计与混音负责人在实际场景评审；同时检查路由、优先级与触发。不能先要求所有素材统一加大音量。
- **中间件预览正常，游戏里不响**：集成人员先查事件身份、参数、资源与作用域；程序提供生命周期和错误证据；内容作者确认对应版本。预览成功不能证明游戏内实例被正确控制。
- **音乐节拍对齐，情绪过渡仍生硬**：作曲与交互音乐设计检查入口、乐句、和声/桥段；音频程序不通过反复重启来掩盖结构问题。
- **性能超预算**：共同选择减少并发/变体、改变加载策略或调整内容。任何优化必须复验关键反馈，不能以 CPU 降低自动判定体验不变。

## 能力证据与进阶，不以工具名单替代交付

面向本责任集合，建议评审一个可复现功能，而不是仅展示音效合集：给出 brief、原创贡献、事件图、manifest、构建步骤、一次失败诊断、优化前后证据及未解决问题。可在受限素材条件下使用自制合法测试音色展示系统；必须标明演示与正式美术/声音目标的差异。

学习路径可由素材制作与可追溯导出开始，进到参数/事件与混音，再到构建检查、状态压力测试和预算分析。写脚本或 C++ 是服务于问题的能力，不是所有交互音频岗位的统一入门门槛；本轮 Larian 样本要求它们，也不代表所有声音设计岗位都如此。
