# League 服务器分配：观测到的低负载，不等于下一场对局的余量

> **历史技术补充（迁移衍生），不是当前读者书。** 当前阅读请见[《英雄联盟如何用负载信息分配对局服务器》](../../../../GameLibrary/网络与在线服务/在线服务/服务器调度/英雄联盟如何用负载信息分配对局服务器.md)。以下保留旧正文的完整技术上下文、来源和未执行范围；此次只增加历史标记并调整链接，没有重新运行或重新认证历史主张。原路径与前后文件绑定见[迁移记录](../../迁移记录-source-group.json)。


## 可证实背景与有限事实

Tomasz Mozolewski 在 Riot **2025-01-16** 的[第一方技术报告](https://www.riotgames.com/en/news/tech-blog-cpu-usage)中介绍 League 的服务器分配改进。以下仅概括其历史报告，不是本库测量或当前线上保证。

团队比较 LeastCPU、LeastGameCount、RoundRobin、Random 等策略。作者报告的模拟反例是：**CPU 观测每 30 秒刷新，而新对局初期耗用较低，随后增长；按最低 CPU 分配会把年轻对局集中到看似空闲的机器，形成后续峰值。** 他们最终选择 RoundRobin，考虑的是多种场景中的稳定表现与维护简单性，而非每项场景第一。文章还描述上线分区比较，报告负载波动降低；本文不复用其成本收益数字。

来源中的工作负载采集按分钟，不能与上述决策输入刷新周期混为一谈。模拟包含机器准入条件、同一场景内硬件一致的简化，并考察刷新、启动、编排器等条件；有准入约束不等于选择器本身需要按 CPU 排名。原文未在可读正文中提供完整代码、原始数据或图中评分公式，本文未读取图形数值。

这是一份**有明确工程机制的历史自述**。不能从中推导“CPU 永远不能用”“RoundRobin 总是最优”，也不能把上线前后比较提升为排除了所有混杂因素的因果实验。

## 本文的原创问题：一个读数遗漏了哪两段时间？

分配器面对的不是抽象的“空闲机器”，而是某一时刻、用某种窗口测得的状态。以下分析是原创推导，不是对 Riot 未公开实现的还原。

第一段时间在**采样与决策之间**：测量完成后可能又接收了新工作，决策时读数已经陈旧。第二段时间在**分配与需求增长之间**：即便刚刚采样，新工作也可能尚未进入高耗用阶段。加快刷新只能针对第一类遗漏，不能自动解决第二类。

因此，可迁移的问题不是选一个名字更聪明的算法，而是：

> 分配负责人能否知道正在比较多旧的观测？玩法性能负责人能否说明已分配的年轻对局以后怎样消耗资源？两者之间尚未反映到指标的工作由谁记录？

这些问题不预设必须使用预测模型、预留令牌或分布式锁。具体机制需要项目数据与一致性需求；本案例没有提供它们的实现或正确性证明。

## 原创五方交接表：测量、放置与准入分开

下表是**未执行的工程建议**，不是 Riot 内部数据格式。每项只记录必要的技术证据，不采集无关玩家身份或认证信息。

| 提供方 → 接收方 | 应交接的可核对事实 | 它支持的判断；不能替代什么 |
|---|---|---|
| 玩法性能 → 在线服务/容量负责人 | 不同模式与对局年龄的资源需求观察、构建配置、波动与缺失范围 | 刚开局的消耗能否代表后续需求；不能把平均曲线当成每局上界 |
| 遥测 → 分配器 | 样本时间、聚合窗口、可供决策使用的时间、单位、缺失/过期状态 | 比较是否基于相近时点；新鲜读数仍不保证未来余量 |
| 分配器 → 监测与诊断 | 决策时点、候选机器集合、被选机器、策略版本、自上次观测后分配的工作及其结果 | 能否重建一次分配集中现象；请求发出不等于工作已启动或需求已计入 |
| 机器生命周期 → 分配器 | 新机器可接收工作的就绪证据、退出/排空状态、集合变化 | 扩容请求不等于可用容量；尚有对局的退役机器不等于可自由再用 |
| QA/运维 → 变更负责人 | 场景边界、逐机器/逐时段异常与功能结果、模拟和实际部署的差异 | 哪个有限结论足以支持试运行；不能只靠全体平均值宣布所有机器安全 |

**选择与准入是两个问题。** 排名决定在候选集合里选谁；准入决定谁有资格进入集合。如果团队采用不按 CPU 排名的策略，也不能因此省略就绪状态、容量约束或异常机器隔离。反过来，存在准入阈值也不证明刷新间隔内的连续分配仍然满足该约束。

本表特别要求记录“分配后尚未反映到读数中的工作”，但不假定一种通用计数方式。超时、取消、重试或多个编排器可能改变记录语义，应由实际服务协议定义；本文没有据公开文章推定 Riot 如何处理这些情况。

## 有区分力的验收问题，而不是新造一个基准分数

以下均为**待实施检查**。只有取得获准的真实项目数据与测试环境后，才可能产生运行结论；本文没有编写模拟器或生成伪玩家数据。

### 1. 先验证输入能否回答问题

- 工作负载是否区分模式、对局年龄与持续时间，还是只保存一个日均 CPU？缺失细节时，应限制分析，而不是编造分布。
- 观测时间和进入分配器的时间是否分别可见？只记录日志写入时间，不能据此重建指标的新鲜程度。
- 启动中的机器、已就绪机器、排空中的机器是否分别计入？若只有机器总数，不能断言当前可分配容量。

### 2. 预先分开两个反例条件

使用同一份允许使用的工作负载证据，在声明的场景内分别考察：

- **观测延迟变化**：输入反映相同类型工作，但决策时可见的样本年龄不同。
- **年轻对局集中**：即使输入及时，近期分配是否集中于尚未表达后续需求的一批对局。

这样能避免把所有差异归因于“指标过期”，也避免把一次改善错误归因于算法名称。若比较过程中同时改变机器类型、模式混合与扩容规则，必须记录这些变化，不能声称只测了刷新周期。

### 3. 同时看受损对象与使用成本

每个候选策略应说明：功能是否成功、哪些机器在什么时段受压、是否存在持续集中、需要怎样的调参和观测成本。全体平均值可能掩盖少数机器的问题；单个最高点又不能独自解释持续时间与受影响范围。具体阈值由产品和测量决定，不借用别的游戏的 CPU 数字作为质量标准。

### 4. 模拟结论与部署结论分别签收

回放或模拟可用于筛选假设，但其硬件、需求和生命周期模型必须显式列出。实际受控试运行要重新记录候选版本、模式/地区范围、观察窗口、停止条件和未覆盖场景。不能将模拟中排名第一自动转换成生产准入，也不能因历史案例报告过节省成本而预填收益。

这套验收过程不承诺必须重建完整生产环境。它要求的是**结论与证据粒度一致**：只能测一种模式时就只讨论该模式；无法观察未来需求时就保留预测缺口。

## 成本与未知：不把个案变成规则

记录更细的需求与决策轨迹会增加存储、追踪和维护成本；工作负载改变后，旧判断可能失效。更复杂的模型也可能产生配置负担。应先判断某个观测缺口是否影响决策，再决定增加何种记录，而非无上限采样。

本次阅读没有建立这些实现细节：同负载时怎样打破平局、多个编排器如何协调、待启动工作的预留语义、失败后的回收路径、完整准入算法，以及异构机器如何归一化。来源提到改变机器大小的场景，不等于已验证混合容量机群。真实线上比较的精确日期、完整原始数据与混杂因素控制也未获核实。

没有读取图中的公式和参数，便不应声称复制了作者评分。本文支持的是**观测年龄、需求年龄与容量就绪应在交接中分开**这一原创分析框架，不是任何算法、阈值或云平台的通用保证。
