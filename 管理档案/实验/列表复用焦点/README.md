# 列表复用与焦点：Godot 控件与合成确认

从本目录执行（Python 3.12.14 及可运行的 Godot 4.6.3）：

```bash
set -o pipefail
python3 -B godot/run.py | cmp - godot/observed.json
```

脚本在临时无窗口项目创建两个普通 Button、一个临时列表接收面，并调用真实 `grab_focus()`、`gui_get_focus_owner()`。向引擎提交合成 `InputEventAction` 的 `ui_accept` 按下／松开，记录实际按钮的 `pressed` 被认作哪一个条目的业务操作。没有真实设备，图标、布局、滚动与复用由试件中的业务流程人工推进；不是引擎内置列表的行为验证。

复现观察：
- 无守卫的 B 直接换绑 D，实际控件仍为 Slot1，下一次确认进业务列表的是 D。
- 过渡期间阻止条目确认；较早的 B 回调既不能夺回 C，也不能使用 B→X→B 前捕获的旧绑定。仍有效且匹配当前代次的完成可恢复 B。
- 按下时 B，松开前同一个 Slot1 改绑且逻辑目标改为 D；只看松开时身份时收到 D，保存按下的行、ID、代次和意图时则拒绝这个松开。重新对 D 完整按一次才收到 D。

本试件的按下记录仅模拟一个本地确认输入流，不测试同时按多设备、指针命中、可见焦点框、按键布局、真正滚动容器的裁剪、读屏或线上业务授权。观测 JSON SHA-256：`f885e4d632f5b5b59b3f868c20953f59255817519629d51570e55d93818c9ff1`。

## 延迟滚动的独立应用模型

`python3 -B deferred_scroll_model.py`（本次 Python 3.12.14）打印和 [记录的输出](deferred-scroll-observed.txt) 相同的四行。先故意按旧索引查新列表，再从当前业务 ID 解析索引；目标被删除时对照 -1 的末项含义。另检查：布局裁剪、缺少实际焦点、旧行绑定代次或更新的意图都不能交还操作。这里的可见性、版本和焦点是试件输入，不模拟 Unity 的实际布局、调度或设备。见[脚本](deferred_scroll_model.py)。
