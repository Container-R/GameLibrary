# 对白起播的内容与时间：合成 PCM 对照

本目录是文章的样本级复算附件，不是 Unreal 工程，也没有模拟其缓存或磁盘。

## 运行

需要 Python 3 标准库。本次执行环境 Python 3.12.14。

```sh
python probe.py
```

脚本在自身目录重建 `reference.wav`、`whole_delayed.wav`、`prefix_removed.wav` 以及 `observed.json`。三份 WAV 均为 48 kHz、单声道、16-bit PCM。标记是确定性的二值测试信号，没有对白内容，不用于人声可懂度或音色判断；不必播放便可检查样本。

参考文件有三个不同的确定性信号块：0–20 ms 开头标记，200–240 ms 后续标记，400–800 ms 后续信号，其余为零。延迟文件在参考前加 5760 帧零；前缀删除文件移除前 3840 帧。两者的第一个非零样本都位于文件第 5760 帧，但只有延迟文件保有开头标记。

脚本读回每份 WAV，验证格式、内容、标记位置及两项整体等式：延迟文件去掉新增静音等于原样本；删除文件等于原样本后缀。精确匹配仅适用于这些无处理的 PCM 产物，不应直接用于真实有损编码/重采样后的输出。

`observed.json` 的位置单位为帧；除以 48000 得秒。它记录的是文件内位置，不是播放 API 到设备的延迟。

## 没有执行的部分

未执行 UE、stream-cache 压力对照、打包构建、输出设备采集、人声试听或玩家测试。文章四组方案需要在实际目标版本另做。已生成的 WAV 只能帮助区分整体平移与前缀内容缺失，不能认定缺失由 I/O 导致。

## 生成文件与校验

仓库只保存生成器和复算结果，不保存生成的 WAV 二进制。运行脚本即可重建；`observed.json` 的 `sha256_wav` 给出本次三个 WAV 的完整 SHA-256。Python 版本字段随执行环境变化，样本与 WAV 哈希应保持一致。不要把 WAV 哈希相等误读为引擎播放验证。
