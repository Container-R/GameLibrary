# 菜单朗读仲裁：确定性事件轨迹

状态：应用层教学模型，非 Windows、NVDA、引擎或听觉测试。输入为逻辑步骤，不是毫秒；合成的 `complete(token)` 仅表示测试驱动器释放占位输出，不能解释为玩家听完。

## 执行前的判据

本轮要区分三件事：同一状态的新快照能否替代旧快照；独立操作结果能否保留；旧视图和旧输出回调能否影响新实例。

1. 基线全局 FIFO 输入 `焦点A、焦点B、焦点C、r1失败、倒计时8、7、6` 后仍含 A、B，不能满足“当前焦点只有 C”的约束。
2. 基线全局 latest-only 的同一输入最后只剩倒计时6，不能保留独立的 r1 失败。
3. 分类策略中，A→B→C 替换旧焦点；倒计时8→7→6只在同一页面实例、同一匹配会话内替换；r1、r2、r3结果按操作身份分别保留。
4. 关闭页面后，同名新页面不能接收旧焦点回调；旧页面发起、仍有意义的结果留在操作记录中，并说明结果所属对象，不把它写成新页面刚发起的保存结果。
5. 重复的终态回调不新增朗读；这是本模型“每个 operation 只有一个终态”的前提，不是所有业务的一般去重规则。明确终态后的新尝试使用新 operation ID；同一次操作的重复投递仍关联原 ID，超时但结果未知时不能直接当成失败后新尝试。
6. 旧 `complete` 不得结束新 token 的占位输出。以页面名或当前全局 busy 布尔值代替 token 会留下竞态。
7. 另行构造结果播放被新焦点打断的轨迹：结果记录只有一条，输出请求会有两次；旧结果 token 的完成不影响新焦点。这排除把“去重回调”误说成“中断重播也只会请求一次”。
8. 审稿后新增会话切换回归：当前会话由匹配系统的绑定及其递增修订给出；同页新会话20排队后，旧会话较新序号7不得覆盖它。旧绑定修订也不得切回旧会话；切换时正在输出的旧会话倒计时应取消，其晚到完成不得影响新输出。

## 这份模型主动做出的产品选择

焦点改变抢占当前占位输出；被抢占的操作结果重新排到结果队列前端，瞬时焦点和倒计时丢弃。焦点完成后，先请求尚未报告的操作结果，再请求仍有效的最新倒计时。这里的“结果优先于普通倒计时”只适用于本例：没有即将超时的强制决策、紧急警告或战斗提示。

关闭页面清掉该实例的焦点与倒计时，但不取消保存操作、不擦除操作记录。结果属于独立操作，而不是属于一个永不变化的按钮。读完的结果仍可回查；占位输出完成状态也不等于用户已理解，因此不能据此删除业务记录。

这种策略仍会在连续导航时推迟结果。不能靠一个更高优先级数字解决所有冲突：需保留可访问的结果区域、区分“重听当前项”和“回查操作结果”，并由真实项目确定是否需要适时简短提示。无限输入流下既不打断导航又保证每条消息有限延迟，在单通道上不是无条件可满足的承诺。模型不证明可接受的等待时间、队列容量或玩家体验。

“最后收到的值”也不总等于“请求输出时的当前值”。本模型没有真实时钟，只能证明8/7被6替代；若结果朗读持续很久、后续tick又没送到，6本身也可能过期。实际倒计时应保留有效会话与截止时刻，在准备提交时按项目使用的时钟重新求值，并处理暂停、取消或已结束。这项时效检查尚未在该模型实现，不能把本轮轨迹写成完整的倒计时方案。

## 代表操作与应观察到的结果

页面实例 `p1` 与 `p2` 都名为“大厅设置”。倒计时属于 `p1/match1`。`r1` 是字幕保存，`r2` 是画质保存，`r3` 是在 p2 发起的新字幕保存。

| 步骤 | 输入 | 分类策略的决定 |
| --- | --- | --- |
| 1–4 | 打开p1，焦点A→B→C | 只保留当前焦点；A/B的输出占位被取消 |
| 5–9 | 发起r1/r2，倒计时8，r1失败，倒计时7 | r1保留；7替代8；不抢走当前焦点C |
| 10–12 | C完成，倒计时6，r1完成 | 先请求r1；随后请求6，不请求8或7 |
| 13–15 | 关闭p1，同名p2打开并聚焦C | 取消旧倒计时输出；新焦点使用新页面实例 |
| 16–18 | 旧倒计时完成、旧焦点回调、r1重复失败 | 三者都不改变p2焦点；r1不重复入队 |
| 19–21 | r2晚到失败；p2发起r3并失败 | r2/r3都保留，互不替代，来源实例不同 |
| 22–24 | p2焦点完成，r2完成，r3完成 | r2明确为之前画质设置的结果；再请求r3；不改写p2输入状态 |

执行命令：`python3 trace_model.py`。实际输出保存为同目录 `trace-result.json`。脚本使用标准库，无网络、声音输出或产品 API；没有把第三方代码拉到本机执行。

补充轨迹包含10步：打开、聚焦、发起操作、失败、结束焦点占位、移到新焦点、旧结果完成回调、新焦点完成、结果重播完成、重复终态回调。结果 `r4` 有两次输出请求，但操作历史只有一个终态，旧完成回调被忽略。它显示重播成本：应用缺少可靠的播放进度时，可能要从短消息开头重新请求，不能声称做到精确“续读”或一次且仅一次可听。

审稿后的第三条轨迹包含11步，实际输出见`session_switch_trace`：同页旧会话8排队，权威绑定更新后新会话20排队，旧会话序号2的7和旧绑定修订均被拒绝；焦点占位完成后提交20。再次切换到另一会话时取消20的占位输出，提交30；20的晚到完成不影响30。原版本只有每会话序号，没有当前会话门，不能支持这项保证；修订后的模型显式保存绑定、修订与输出所属会话。绑定事件来自匹配系统是模型前提，不是网络接入实测。

## 外部读屏接入时，哪些部分不能照搬

应用可以在调用 UIA 前合并尚未提交的状态，过滤过期视图事件，并保存操作结果。已经交给外部读屏的消息如何排队和取消，由客户端决定。当前研究所读 UIA 事件接口没有一个可供应用把本模型 `complete(token)` 直接接上的“玩家已听完”回执，也不能把 `activityId` 当作已验证的按键取消句柄。

因此，内建 TTS 的可取消播放状态机和外部读屏的事件发送器必须分别验证。外部路径不应伪造 busy/完成，也不能为了重听而强制把用户焦点移回旧页面。下一步的原生测试至少记录：应用决策、provider/sender、activityId、发出请求与HRESULT、观察客户端收到事件、以及实际试听到的开始/打断/遗漏。观察事件收到不等于输出已完成。
