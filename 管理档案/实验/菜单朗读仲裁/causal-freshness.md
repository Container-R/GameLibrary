# 操作回执与倒计时：提交朗读前还要检查什么

2026-11-10接续研究。本文是连续研究解释与实验设计，不是已审稿正式文章。它补充原事件模型的两个明确缺口：不能只有失败记录，也不能只保留最后收到的秒数。

## 先分开历史与现在

玩家将字幕字号设为24，保存请求r1失败；随后按重试，r2成功。“r1失败”作为历史仍然是真的，“字幕字号仍未保存”却可能已经不真。若r1的朗读仍在排队，等到r2成功后才机械读出“保存失败”，会把历史结果误当成当前操作建议。

需要保留三组身份：资源及其作用范围、这次用户意图、执行该意图的操作。这里的资源不是“保存按钮”，而是例如同一档案的字幕设置；不同档案、字段集合或账户不得只因文案相同就合并。一个意图可以有多次尝试；只有玩家改变目标值，才产生新的意图代际。每次尝试使用独立operation ID，并绑定当时的目标值。

| 后来发生什么 | 旧失败怎样保留 | 当前自动提示怎样决定 |
| --- | --- | --- |
| 同一目标的重试成功 | r1仍失败，另关联r2成功 | 可概括目标已保存，不重复要求重试r1 |
| 改成字号28后保存成功 | r1失败，原24目标已被新意图替换 | 说明当前28已保存，不能说r1成功 |
| 画质设置保存成功 | 字幕失败不变 | 两个资源的结果各自处理 |
| 仅发起r2、尚无权威结果 | 不能假装已补救 | 当前仍在保存或待确认 |
| 请求超时，没有权威终态 | 记录结果未知，不记成确定失败 | 不保证没保存，也不盲目当作失败重试 |

**历史行保留发生过的事，自动播报使用提交时的当前解释。** 同一资源的过时失败提示可以被较新的已确认状态摘要代替，但历史行不被覆盖。用户主动查历史时能得到“r1请求字号24失败；随后r2保存字号28成功”的区分。这里的回查入口与“重听当前焦点项”不同：前者打开有明确标签的结果区域，后者读取当前控件的最新名称/值。状态到达本身不应把焦点强拉回旧页面；用户主动进入结果区域时才按通常导航规则处理。

### 本地意图编号不等于保存版本

请求发起顺序、回调到达顺序、权威端实际提交顺序是三件事。若旧请求r1在新请求r2之后才真正写入，r1即使属于旧页面，也可能改坏当前持久状态。可以拒绝它抢焦点，却不能仅因UI代际过期就丢掉其业务结果。

本模型明确假设：每个资源的权威端为**完整替换**提供严格递增的提交修订号；成功回执携带该修订号与实际接受值。接收旧修订只更新操作历史，不倒退最后确认快照；若旧意图反而获得更高提交修订，保留这个事实并提示当前期望值与最后确认值不同。后者需要保存系统串行化、条件写入或重新核对来处理，朗读器本身不能修复存储竞态。

不能把任意version字符串当作该修订号。RFC9110 §8.8.3将ETag定义为不透明校验值，比较用于等价判断；其值可能来自哈希或其他机制，不保证可以按大小排序。§13.1.1中的If-Match在服务器处理变更前检查前提，能用于避免并行覆盖；它不是朗读完成协议，也不代表所有游戏存储已实现条件写入。[1]

如果接口不给出可比较的权威修订，应使用其实际提供的确认/重读机制；没有依据时只能说“r2报告成功，当前保存状态尚需核对”，不能编造单调顺序。此模型也不处理字段合并、跨设备写入、资源版本重置、事务或进程崩溃后的历史恢复。即使已收到成功，同一资源仍有可能改写它的未决请求时，摘要要同时保留“已确认值”和“仍有请求待确认”，不作稳定终态承诺。

## 倒计时排的是读取意图，不是旧数字

时间0记录“剩余8秒”，等焦点与保存结果结束，已经是2.4秒。即使没有新tick事件，提交时也只能按当前有效截止点求得5.6秒，再按本例约定向上取整为6秒；不能照读缓存的8。数字取整必须与视觉显示及产品措辞一致，向上取整只是本例选择。

待播项保存页面实例与会话身份，提交前查最新会话状态、修订号和截止时刻。新会话不能复用旧消息；权威取消/结束后停止数值提示。截止点已经过去而尚未收到开始确认时，淘汰过期数字，不把数学上的0伪装成“游戏已开始”。如果项目需要提示等待确认，应是清楚的状态说明。

暂停也是业务状态，不是时钟性质。本地可暂停计时器可在暂停时保存剩余量、恢复时重建截止点；服务器大厅倒计时不一定随本地菜单暂停。Python3.12文档只保证monotonic不会倒退、不受系统时间修改影响，且原点无定义；不能直接减去服务器UTC时间戳。[2] Windows QPC独立于UTC，并计入待机、休眠等时间，因此不能假设它会自动冻结游戏倒计时。[3] 跨时钟映射、网络延迟和同步误差需要由实际计时系统提供，本模型不估计这些误差。

提交前重新计算只能保证**请求生成时**的信息新鲜。外部读屏可能稍后才发声，应用未必有可撤回队列或实际开始回调；内建TTS若提供可靠开始前钩子，可再核对一次，但不能把该能力强加给UIA。需要精确传递即将截止的信息时，应另评估播报长度、读屏延迟与提示策略，不能由这个模型认证安全时间窗。

## 执行前的测试设计

脚本 `causal_freshness_model.py` 为原创标准库模型；所有权威回执、修订与时刻是人工输入。与原 `trace_model.py` 分工：旧脚本检验仲裁和token，新增脚本只检验提交前业务解释，不复制平台或声音实现。

- C1：r1失败、同意图r2成功。历史r1失败保留，当前确认已保存，关联为重试成功。
- C2：新意图r2先成功、旧r1后失败。最后确认值不倒退；旧失败属于被替换目标，不显示为当前失败。
- C3：同资源两个成功回执乱序。较旧修订不覆盖新修订；如果旧意图真实获得更高修订，则必须显露当前期望与已存值不一致。
- C4：另一资源成功或仅开始新请求，均不能把失败当作已补救。超时状态为不确定，后续权威成功可完成确认。
- C5：r1失败消息排队期间r2成功，提交时重新解释为当前状态；历史与自动提示分别输出，不改写r1终态。
- C6（审稿后回归）：请求28、权威回执接受26时，历史分别记录请求值与接受值，最后确认26，当前解释为confirmed_different；相同终态重复可忽略，但不同接受值不是相同回执。缺少接受值的成功输入不得自动确认请求值。
- T1：8秒快照等候2.4秒后提交，结果应为6；到期后不输出0或“已开局”。
- T2：暂停后时刻前进不输出流逝秒数；恢复时从冻结剩余量重建截止点。
- T3：旧页面、旧会话、较旧修订、已取消会话不能生成当前数字；同会话较新截止点在提交时生效。

结果文件为 `causal-freshness-result.json`。通过只说明这些有限输入符合显式模型契约，不是存储、网络、时钟、读屏或玩家体验实测。

## 实际执行与所得判断

2026-11-10执行 `python3 causal_freshness_model.py`。上述有限判据通过；保留完整人工事件输入、最终操作历史、每次计时求值输入与输出。未进行网络请求、存储变更或声音输出。

核心区别确实出现：r1终态仍为failed，但分别得到retry_succeeded与superseded_by_confirmed_intent两种关联；后发请求未确认时只得到superseded_intent_unconfirmed。旧意图若获得更高权威提交号，当前解释变成confirmed_different，没有因UI事件“过期”而隐藏。排队期间成功后，按资源重新生成的提交视图为confirmed_current，而不是缓存的失败句子。

计时轨迹中，8000ms截止点在2400ms提交得到6秒；8000ms本身返回到期淘汰。截止点后更新到12000ms、修订2，再到的修订1没有覆盖它；8500ms求得4秒。9000ms暂停冻结3000ms，20000ms恢复为23000ms截止，21000ms求得2秒。旧页面、取消与替换会话都返回明确淘汰原因。没有进行OS休眠或暂停行为测试。

原始仲裁模型也重新执行，24步主轨迹与10步打断轨迹仍通过。两个模型没有接入真实输出管线，因此不能把合并检查称为完整系统集成测试。

审稿指出原`Ledger.finish`只收status/revision，确认快照却直接采用请求值，与本文“回执携带实际接受值”契约不一致。经代码核实后，修订接口为显式accepted_value，历史保留它，确认快照只采用该字段；成功输入缺少它时拒绝，重复终态比较也包含它。新增两个命名情形实际执行通过，因果情形总数由6增至8；计时日志仍为15条。这是修正模型与契约落差，不是发现了真实服务会改写请求值。
