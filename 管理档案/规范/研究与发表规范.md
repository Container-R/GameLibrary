# 研究与发表规范

## 首要标准：面向读者的图书馆

原55篇存量正文的改写、内容去向核对与根目录归并已完成本轮限定验收，研究已恢复。可查看[整改关闭时的状态记录](https://github.com/Container-R/GameLibrary/blob/2a9573326c8a280965aa2881d41022d7a634c5df/.agent/state.json)。这不表示学科知识已经完备，也不表示所有历史实验或来源都经过新一轮复现。

下列读者标准持续适用于新增和修订内容。来源核对或脚本检查通过，不能代替检索、理解和实际技术用途的验收；优先补齐已有文章的真实缺口，不为增长篇数拆出重复文章。

### 读者应当怎样找到一本书

- 仓库根目录提供图书馆大楼 `GameLibrary/` 和直接可读的入口导览；维护、验证和历史材料与读者书架分开。
- 正文按 **学科层／专业区域／主题书架／书** 组织。读者应能从文件夹逐级进入，例如技术美术层、环境管线区域、具体主题书架，再打开技术文章。
- 同一篇文章只保留一个主要位置；跨学科通过导览链接到它，不复制多份正文。目录名称要让读者知道里面有什么，不以文档类型或内部任务编号代替主题。
- 迁移前列出旧路径与新路径、链接修改和历史证据保留方式。按已审清单逐组迁移，核对入站引用和实际读者入口；不得把部分目录移动称为全库整改完成。

### 一本书必须是一篇能读懂的技术文章

1. 先说清实际问题、读者需要的前置知识和文章要帮助做出的决定，再解释原理、做法、例子及取舍。标题应能让开发者判断是否值得打开。
2. 使用自然、完整的技术语言。首次解释必要术语，避免反复堆叠“合同、边界、接收、证据”等抽象词。不能要求读者先理解代理的工作流程，才能理解技术内容。
3. 不把整篇文章写成审计表、免责声明或检查清单。重要限制放在对应论述旁说明；身份哈希、运行收据、审查过程等放在附属材料，不打断主线。
4. 用具体例子把概念讲透，区分原作者结论、本文推导和实际实验。未验证的内容不得伪装成事实，但诚实标注也不能替代足够的技术深度。
5. 文末设置“参考资料与引用”，列出真实可访问的原始来源、作者或机构、题名、版本或日期及必要章节定位。正文可用简短引用标记对应文末资料，不把密集长链接插入每一段。
6. 基础原理和工程方法应能服务不同引擎。Godot 或其他本地工具可以用于有限验证，不能因为工具方便，就把全库写成该工具教程。引擎特定结论单独说明，不能从单一环境外推通用保证。

### 每次发表或实质修订的验收

- **能找到：** 从入口导览和学科文件夹都能定位目标书架与文章，没有断链或靠猜测内部分类才能进入的路径。
- **能读懂：** 不参与写作的审阅者能用自己的话概括问题、方法和适用条件，指出文章如何帮助实际开发；仅确认事实没有错不算通过。
- **有内容：** 解释、推导或实现细节足够支撑结论，不用空泛摘要和格式完整冒充质量。
- **有来源：** 文末引用可追溯，关键说法与来源相符，原创分析和实验范围明确。
- **不偏工具：** 通用方法与工具实例分层，读者不使用 Godot 仍能理解并判断如何迁移。

两小时督导应优先检查上述结果和当前研究、维护中的实际工作，不再按文章数、提交数或归档检查通过数判定读者体验健康。迁移和重写保持可恢复、非破坏性；历史证据不得凭记忆改写。历史执行材料按已授权范围逐组去除环境信息，保留技术事实、失败与来源，并明确标注衍生处理；未经逐项审查不能直接批量移动或重发。新公开记录不得带入私有路径、进程身份、凭据或私人互动。

## 仍然适用的研究与工程要求

- 以明确工程问题和适用约束为起点，不把链接收藏、分类骨架、排队或时间戳视为成果。
- 优先阅读原作者论文、源码、官方文档；记录原始 URL、作者/组织、版本、章节、访问日期、用途和许可边界。不同语言镜像不是独立验证。
- 每篇知识维护稳定 ID、类型、证据状态、主学科、更新时间与来源索引；这些机器字段保存在管理清单，不以 YAML 或审计表占据读者开篇。正文有清晰标题、文末引用及必要的适用范围。
- 区分来源断言、原创推理与亲自执行的实验。source-backed 不等于已测试；verified 仅用于记录了具体范围的复现，不外推跨平台或性能结论。
- 需要具体流程、失败模式、方案取舍和可复现检查。未经验证的生产集成应明确标记。
- 第三方资料默认仅链接、少量必要引用和原创分析。公开可读不等于获准再分发。不得归档其他私有项目内容、个人数据、凭据或付费课件。
- 修改前检查实际默认分支、当前 HEAD、队列负责人和租约；租约为协作提示而非分布式锁。保留他人的在途工作，不强推、不改可见性、不绕过保护。
- 一项研究一个逻辑增量，验收后写入目录、来源索引及恢复记录。仓库记录真实已完成动作、未完成部分和可执行下一步。
- 研究覆盖逐步扩展至分类骨架所列方向；低覆盖领域也要解决具体问题，不制造空文档。

## Git对象发表与等待故障恢复

先完成本地载荷准备、完整文件审查和路径/对象摘要核对，再单独发远端请求；不要把大段本地输出和远端变更放进同一个长等待封装。树内容采用较小分组（当前经验阈值约9万字符，不是GitHub的服务上限）；超过该阈值的单个文件可单独创建blob，按返回SHA重新读取并逐字节比较，再在树中引用。

每个请求立即保存已确认的对象标识；每组树读回完整预期基线与累计差额，不以“API返回成功”代替内容核对。中间树不移动公开分支，正文、附属材料及“已发表”状态须在最终树中一致。只有完整树已核对后才创建提交，并以事先读到的HEAD作预期值更新分支，不强推。

请求的yield/wait时间不是已经验证的服务端截止时间。本地竞争计时能帮助暴露未返回请求，却不证明服务器取消了操作。未返回、超时或被中断后，先区分未引用blob/tree、commit与分支更新的阶段，读实际HEAD及已知对象；结果不确定时不能直接按失败重发。故障等待期间不计研究进展。恢复后读回HEAD和关键正文，再更新本地的已发表基线；保留原失败，不宣称一次成功恢复已根治服务等待问题。

## 恢复队列校验

修改 `.agent/queue.json` 后，从仓库根目录运行 `python3 管理档案/工具/queue/validate_queue.py . --taxonomy 管理档案/分类/disciplines.json --queue .agent/queue.json --expected-task-count 175`。命令中的预期数量须与已核队列一致；增删任务时须据独立核对更新预期，不从待验输入自动生成通过值。学科 ID 必须来自当前 taxonomy；产物可用可选 `artifact_paths` 明确记录，已发表任务声明的路径必须存在。旧 `expected_artifact` 描述仍保留，不自动当路径解析。未声明路径的旧任务不算已完成产物检查；目录存在也不证明内容已验收。工具范围与测试见 [queue guard](../工具/queue/README.md)。

## 证据适用范围必须按产物身份核对

委派、加深或复核既有文章前，先读当前正文及对应管理记录。仅当待审结论依赖实验时，在已获准且必要的范围内核对相应实验说明与证据；未核部分明确保留，不因编辑流程扩大材料访问或再次发布范围。在审查记录中写明实际核对的具体路径、修订、已执行范围和排除项。主题、引擎标签、另一篇文章的成功或对话记忆，不能替代这些检查。来源准确性审查与仓库既有证据范围审查是两项不同门槛。

新结论只能绑定实际支持它的夹具/模型与配置；例如 Python 接触几何模型不能改称 Godot 根运动实测，Godot 动画事件测试也不能证明 Unity Rig 约束顺序。发现错误继承时，先拒绝该草稿结论、保留审查纠正记录，再重新核对目标产物；不要改写旧日志或扩大原实验范围。

## Future runner writable-location setup

For new process-running fixtures, explicitly prepare and validate HOME, XDG_CACHE_HOME, XDG_CONFIG_HOME, XDG_DATA_HOME and TMPDIR beneath a fresh caller-owned temporary root, using [the additive helper](../工具/evidence/isolation.py) or equivalent reviewed checks. Keep private execution mappings out of public records; publish only reviewed relative fixture descriptions and technical results, never complete environments, private paths, process identifiers or installed-binary fingerprints. Own root lifetime, partial-creation cleanup and process lifecycle separately. This selected-location check is not filesystem sandboxing or a complete environment policy. Preserve any exceptions and failed attempts rather than widening acceptance after execution. Existing fixture hashes, old receipts and focus-only normal fresh-harness coverage are not retroactively altered by this requirement. See [exact finite acceptance and limitations](../研究记录/source-notes/runner-environment-contract.md).
