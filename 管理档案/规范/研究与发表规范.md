# 研究与发表规范

本库按专业问题持续研究、编辑和发表。当前采用逐篇与分专题的验收，不以文章数量、提交数量或检查脚本通过代替内容质量。历史版本中的固定书目数和已完成整改标记不再作为当前要求。

## 正文与导航

正式技术正文只有一个主要位置：`GameLibrary/学科/专业方向/专题/文章.md`。学科、方向和专题使用实际专业名称。面向开发者解释机制、制作方法或工程判断的材料都按文章管理，不能放在管理目录后改称“支持资料”免于审稿。

各级入口只承担当前层选择：根 README 指向直接项目与维护入口；GameLibrary 首页列学科；学科页列方向；方向页列专题；专题页列同目录文章。允许返回上级，专题可列少量相关专题。文章可引用必要的相关正文、来源和复现材料。上层不展开后代文章，不以跨层推荐代替分类。

代码、数据、测量、来源摘录和审稿保留在管理位置。正文讲完它承诺的方法，不能要求读者打开管理笔记才能补齐核心公式、步骤或前提。独立问题可以另成文章，但不能把一套方法拆成只能互相指向的零散提醒。

## 研究与写作

立题时说明目标读者、生产困难、必要基础和读完能够完成的判断或操作。先读现有正文，确定是在补齐原问题还是形成独立问题。专业深度来自因果解释、方法、取舍和采用条件，不来自术语密度或篇幅。

优先核对原作者论文、官方规范、固定版本源码和团队材料。关键结论附近就近引用，文末列机构或作者、题名、版本、原始链接和必要定位。需要图像、声音或数据才能成立的判断，须实际检查相应材料；文字介绍不能替代观察。

区分来源陈述、原创推导与实际运行结果。算例只支持它解释的机制；有限实现测试不自动成为引擎、画面、性能或玩家体验结论。引用来源的公开可读性不等于再分发许可。保护私人信息、凭据和未授权材料。

开篇呈现具体问题和用途，随后按读者理解需要说明机制、做法与边界。公式、代码、图示和案例应帮助读者行动。把会改变结论的限制放在相应段落，取证流程和审查历史放入管理记录。每次实质增补后重读全文，检查标题、读者和主线是否一致。

## 独立审查

- **技术审稿**读全文并核对决定结论的原始材料，检查专业价值、因果、实施细节、证据、取舍和必要解释是否完整。
- **读者审读**由未参与初稿的审读者，只凭正文、明确前置知识和读者可见附录，设计并完成代表任务。不能只复述作者示例，也不能靠审读者常识补正文缺口。
- **导航审查**只给根入口和真实需求，不给目标路径；记录逐层选择，检查位置、标签和各级职责。

技术审稿与读者审读分别独立执行，导航可由读者编辑兼任。送审不提供预期答案、自评等级或先前通过结论。模型审查如实标明，不冒称真人试用或学术同行评议。

结论采用通过、需修订或研究不足。发现必须落到具体位置、影响和修正条件。实质修改后复核受影响论证并重新通读全文；通过记录绑定最终正文、主要来源记录与实际核对的版本摘要。任何实质缺陷不能用其他项目的通过抵消。

## 迁移与发表

先列旧新路径、正文去向、入站引用和附属材料，再做可回退的有限批次。保留技术细节和历史，不批量清空重建。未整理部分写明具体下一步，不能把局部完成称作全库合格。

发表前核对当前 HEAD、负责人和在途修改。把正文、相关导航和必要记录作为一致的逻辑变更提交，遵守分支保护，不强推或重写历史。结果不明时先核远端对象与分支，再决定是否重试；核实远端正文后才报告发表成功。

当前状态只保留活动问题、证据位置、已完成进展、阻碍和下一动作。独立问题另立任务，不把旧任务无限扩充成通用容器。机械检查负责结构、链接、JSON 和摘要等可判定事项，不认证真实性、专业性或可读性。

本次规范替换前的运维经验、检查器说明和历史验收仍可从[固定历史版本](https://github.com/Container-R/GameLibrary/blob/b3eeb2c47311a98006e18ef027336ae33633b83e/管理档案/规范/研究与发表规范.md)追溯。它们不恢复已退出的固定数量和旧导航要求。
