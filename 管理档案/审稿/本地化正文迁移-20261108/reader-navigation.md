## 文章一：固定精度与复数类别

路径：GameLibrary/本地化与无障碍/本地化制作/数字与消息格式/显示成 1.0 时，复数类别为什么不能只看原值.md

正文 SHA256：64fe395dc2cddbcfd430e0f1329ac9ba2e000c419caffc74aad2053b86bf8143

### 自拟代表任务

同一个英文 en cardinal 普通十进制数值 1，被两个面板复用：A 必须显示两位小数，B 必须显示零位小数。现有程序按原值缓存一个类别给两个面板；另一个优化准备复用同一个格式结果对象，在提取 A 文本后先格式化 B，再给 A 选择类别。判断两项优化是否成立，给出 A/B 的预期表示与类别，并提出无需反解析文本的接入顺序。不是复用文中一位小数冷却提示的单一对照，而是检查跨精度缓存和可复用对象的时间边界。

### 实际回答与过程

1. 正文给定 ICU 76.1 / CLDR 46 的 en cardinal 规则是 i=1 且 v=0 才为 one。v 包括尾零。A 的显示表示是 1.00，i=1、v=2，因此 other；B 是 1，i=1、v=0，因此 one。两者数学值相同，不意味着类别相同。
2. 原值 double 1 的 uplrules_select 路径在正文表中给出 one。只按原值缓存这个结果，给 B 正确，给 A 错误。这里需要的是不同显示策略下的类别，不是为数学值永久指定一个类别。
3. A 先格式化为 UFormattedNumber，提取 1.00，并在结果仍属于 A 时调用 uplrules_selectFormatted 获取 other。B 再按零位策略格式化并提取 1、选择 one。也可以分开持有两个结果，但不需要为了该方案假设额外 API。
4. 第二项优化在 A 提取文本与 A 选择之间把对象改成 B 的表示，违反正文明确的同份结果条件。即使数值没有变，精度信息已经不属于 A。应完成 A 的文本/类别对，再允许覆盖结果。
5. 记录原值、locale、精度、最终文本和类别，检查状态、容量、对象寿命。之后若手工删掉 A 的两个尾零，必须重新处理文本/类别一致性，不能继续使用原结果类别。

必要条件：这里的产品明确要求类别跟随显示精度；规则限定 en cardinal 普通十进制与所引版本；没有百分比、科学记数或额外舍入案例；分支名不是最终语法，译文由目标语言人员确认。改变选择的条件：若改用其他语言，不能沿用 i=1/v=0；若产品并不要求按显示精度选类别，需要先重新确认语义策略。

### 可读性、外部知识与承诺

正文解释了数学值、可见位数和格式对象之间的因果关系；“源码字面量 1.0 不携带尾零”消除了常见误读。上述判断和处理顺序均能在正文中找到依据，不需要打开研究记录或凭外部专业常识补上核心方法。普通程序人员理解对象复用和 API 状态属于开篇约定的基础。

本轮没有写可编译的 ICU 接入程序。正文未交付完整函数签名、格式器初始化代码或缓冲区范式，读者做实际代码仍需查所链接的 API 文档；但标题与开篇承诺是解释表示差异及接入原则，不是完整 SDK 教程。因此这不是本轮代表判断任务的缺口。文中对舍入等外延排除清楚，没有借“未实测”逃避已经承诺的规则推导。

## 文章二：昵称的行内方向隔离

路径：GameLibrary/本地化与无障碍/本地化制作/文字排版/玩家昵称为什么会影响旁边数字和标点的顺序.md

正文 SHA256：010da0f281f294c5a790810e92023ffbf4baa2e29babd7b44d0b8605ec2f30ed

### 自拟代表任务

英文 LTR 排行标签为 Member {name}: 27 wins。两种显示端分别是支持标准 HTML 的网页和已确认支持 Unicode 16 隔离控制的纯文本组件。昵称策略禁止换行和方向格式控制，但允许用户自己的括号、数字及不同方向文字。输入样本包括一个以 RTL 强字符开始并带自有括号的昵称、一个只含“(42)”的昵称，以及违反策略、夹有未嵌套 U+2069 的昵称。设计两端的边界，说明无强字符时能推导什么、违规输入能否仍直接包裹，并提出验收点。任务给定首样本的强方向属性，不额外查询字符数据库。

### 实际回答与过程

1. 整个 name 是片段，昵称自有括号和数字留在内部，模板冒号、空格、27 wins 留在外部。把分数一起包住会失去本任务要表达的语义边界；只包 RTL 字母也会遗漏昵称自己的标点。
2. HTML 使用外层 dir="ltr"，内部以 bdi 包住作为文本插入的完整昵称，随后才接模板冒号与分数。bdi 未指定 dir 时默认 auto。用户内容不能当 HTML 标记拼接；转义/文本插入与 Unicode 方向控制策略是两件事。
3. 纯文本外层方向由组件另行设定为 LTR。对符合输入政策的未知方向昵称使用实际 U+2068 + name + U+2069；不能输出字面的 [FSI]。第一个样本的首个强方向字符为 RTL，所以 FSI 采用 RTL；隔离保护两边的方向上下文，不是把昵称倒序存储。
4. 对“(42)”而言，按正文给定的“没有强方向字符”条件，Unicode 16 FSI 按 LTR 处理。不能把这个推导原封不动宣称成所有 HTML auto 上下文的行为；网页端应检查实际结果。本文已明确这个限制，因此不是需要外部知识才能作答的隐藏跳步。
5. 对夹有未嵌套 PDI 的输入，外包一层 FSI/PDI 不是安全封套，内部 PDI 可能提前关闭隔离。这个样本违反本任务已定昵称策略，不能直接接受并声称安全；应走字段的拒绝/纠正流程，而不是静默反转名字或删除 RTL 文字。具体产品采用拒绝还是提示用户修改，不由本文替项目决定。
6. 两端验收都看完整标签：昵称括号是否留在昵称内，模板冒号、27 和 wins 是否仍构成预期说明。分别覆盖 LTR、RTL、混合和纯数字/符号昵称，并检查违规样本确实被输入政策处理。保留逻辑顺序用于账户名、聊天和搜索，不把屏幕视觉顺序写回数据。

必要条件：HTML 真正支持 bdi；纯文本端真正支持所用隔离控制；外层方向与模板已经确定；受约束文本的字符政策实际落实。改变选择的条件：如果纯文本端不支持隔离，不能照抄码点方案；如果昵称政策允许任意控制或换行，需重新选择结构化能力或明确控制政策，不能沿用本任务的简化接入。

### 可读性、外部知识与承诺

文章由现象、语义边界、隔离机制逐步过渡到两类接口，继而处理任意输入的反例，全文主线清楚。FSI/PDI 首次出现就有作用和码点；“逻辑顺序”“方向隔离”均有足够上下文。本文并不负责给出所有字符的 Unicode 属性，任务已经明确首强方向属性；这不是靠外部知识补核心方法。
