## 自设代表任务与推演

代表输入不是原文的 10/20/30 数量串：已提交角色进度为 level=8、金币 gold=120、背包药剂 potion=3。保存协调函数要把等级改成9、金币改成80；背包辅助函数暂把药剂改成5；另一个辅助函数记录道具 `(item=42, owner=77)`，其所有者必须存在。业务要求：等级与金币是必需进度；药剂增量可能因校验失败被丢弃；缺少真实所有者时不可捏造所有者来换取成功。

1. **提交权**：协调函数在共享同一连接上开启外层 `BEGIN`，管理整次接受或取消。辅助函数建立自己的内层保存点，只汇报局部已处理。依据“同一份数量，三个阶段”和“RELEASE 也并非永远不提交”，辅助函数成功 RELEASE 不得触发保存完成 UI。直到外层 COMMIT 成功，才报告该数据库保存被接受；仍不把它扩写成断电耐久性或云备份完成。
2. **药剂规则拒绝但允许保留必需进度**：等级和金币更新在药剂保存点之前；药剂改成5后业务检查拒绝，执行 `ROLLBACK TO` 药剂保存点，再 `RELEASE`，恢复 potion=3，保留尚未提交的 level=9、gold=80。协调函数决定继续并最终成功 COMMIT 后，这一组合成为接受结果。依据“只撤销辅助函数”段，不能误用裸 `ROLLBACK`，否则连等级与金币都会撤销。
3. **后续判断必须取消整次保存**：即便药剂辅助函数此前已成功 RELEASE，协调函数仍可裸 `ROLLBACK`，回到 level=8、gold=120、potion=3。依据第一节，局部成功不保留独立提交权。同连接中途读到9、80、5不能证明已经提交。
4. **延迟外键拒绝**：事务开始前启用并读回外键检查为1；关系声明为 `DEFERRABLE INITIALLY DEFERRED`。记录 item=42/owner=77 的内层插入和 RELEASE 可成功，外层提交仍可报787且事务继续打开。若77确为合法待保存所有者，协调函数可补正确父行后重试提交；本代表任务规定没有合法所有者时不可创造，所以选择明确 `ROLLBACK`，不向玩家报告成功，也不把提交报错当自动撤销。依据“局部步骤成功”与外键观察段。
5. **即时约束变体**：若外键不是延迟约束，缺父行时 INSERT 就失败；本案例不能继续按“内层保存成功”的路径走。按正文即时约束分支明确回滚整次事务。正文足够支撑这一保守选择，没有要求读者自行补出任意错误的局部恢复算法。
6. **独立调用变体**：若辅助函数被独立调用、没有外层活动事务，其最外 SAVEPOINT 的 RELEASE 会成为提交边界，并受延迟外键检查。要么约定该函数只准在协调函数事务中调用，要么明确单独调用时的结束职责；不能在辅助函数里无条件加整个连接的 COMMIT。
