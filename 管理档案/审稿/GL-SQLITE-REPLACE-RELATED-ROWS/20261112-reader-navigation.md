## 用正文完成任务：独立输入推演

另设初始父表两行 `(73,12)`、`(90,6)`；子表三行 `(73,'ember')`、`(73,'guard')`、`(90,'haste')`。采用正文普通表结构、已开启外键、无其他约束/触发器/修改者前提。意图只将装备 73 耐久改为 11，保留两件装备的全部词条。

### 故障判断

若实际 SQL 为 `INSERT OR REPLACE INTO inventory_item(item_id,durability) VALUES(73,11)`，依据“编号相同，不代表没有删除过”：73 主键冲突导致删除旧父行；ON DELETE CASCADE 删除 ember、guard；随后插入 `(73,11)`。90 与 haste 不受这次冲突影响。只查询 73 编号和耐久会误判保存正确。应查看实际写入 SQL、父表约束、子表外键动作及连接配置，不能仅凭症状直接断言所有丢失都由 REPLACE 导致。

### 满足保存意图的选择

从未损坏的同一初始数据开始，用：

```sql
INSERT INTO inventory_item(item_id,durability) VALUES(73,11)
ON CONFLICT(item_id) DO UPDATE SET durability=excluded.durability;
```

按正文“更新已有装备”节，冲突落在 item_id，只改变 durability，不删除父行、不改父键，因此父表为 `(73,11)`、`(90,6)`，原有三条词条仍在。两分支不能串接来证明修复，UPSERT 不重建已经被删的 ember、guard。

### 变化条件

- 将待存编号改成不存在的 101、耐久设为 4：没有主键冲突时走插入，不会自动创建任何词条。如果业务意图严格禁止新增装备，本篇给出的 UPSERT 不是这一额外需求的完整方案，应另定“必须已有”的写入规则；不能把本文的示例直接当该需求实现。
- 对已有 73 传入 `NULL` 耐久：表有 NOT NULL；不能把 UPSERT 当忽略约束开关，也不能承诺保存成功。正文已说明唯一性范围与 DO UPDATE 约束失败的 ABORT 边界；实际错误必须处理，失败不算完成业务保存。
- 真实表有自定义触发器、额外唯一约束、父键更新或其他连接并发时，正文明确不覆盖完整效果，必须重新核验实际结构与路径。不能从本例泛化“任意 UPSERT 都保留所有关联”。

### 接入前后的明确检查条件

1. 核实实际嵌入 SQLite 至少 3.24.0，并查看包装器最终 SQL，而非仅看方法名。
2. 确认构建保留外键能力；各相关连接在事务外启用 foreign_keys，并读回 1，不依赖默认值。
3. 核对真实表的唯一约束、外键动作、用户触发器、所改列；不靠关闭外键或 recursive_triggers 避免本例级联。
