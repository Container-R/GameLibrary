## 独立成文价值与全文完整性

值得作为窄范围的独立文章保留。生产困难不是“reset 是什么”这一孤立知识点，而是保存 API 报告正常完成、数据库值也合法，保存意图却已失真。文章将这类源端错误和备份丢失区分，给出可执行的判断：先核对每行参数来源，再选择完整重绑或清空后赋值，最后用业务对应关系而非行数验证结果。它没有承诺语句池、通用重试或性能评估，因此不应为了篇幅扩展这些主题。

第一节的两个整数参数、表约束和先 reset 再重绑的顺序，足以让熟悉基本 SQL 和 C 接口的读者重建故障。第二节四条替代分支并非连续执行，避免编号冲突混淆；第三节给出采用条件与业务读回对象。必要解释均在正文，无需打开后台笔记才能知道为什么第二件会沿用 7，或为什么 clear 后漏绑会在此表中失败。

## 核心结论核对

- “语句可以重新执行，参数却还在”：符合 reset 的直接契约。第一次成功写入后，只重绑编号不会影响数量参数，故 `(2,7)` 推导成立。
- “完整重绑，与清空后漏绑，是不同结果”：四条分支均成立。clear 使数量参数为 NULL，不是 0；给定普通 INSERT、NOT NULL 和无额外冲突机制，漏绑数量导致约束失败。
- “完整重绑不必强制 clear”：成立。所有本行需要的参数都已成功赋值时，没有残留数量可沿用。文章同时要求检查绑定结果，未把尝试绑定等同绑定成功。
- “查本行值从哪里来”：两条独立记录各自取得数量，具有直接的诊断和修复意义。按编号核对 7 和 3 可以发现这次值串用，单数两行不能。
- 返回码和范围：正文要求检查 reset、clear、bind 与执行阶段失败，并明确不提供错误恢复循环、不将 reset 等同提交或回滚；因此未用文档语义冒充完整事务实现。

## 主动反例及其影响

1. **数量允许 NULL。** clear 后漏绑数量可能成功，不再以约束错误暴露。正文第二节已经明确处理这一反例，所以没有把 clear 错写成通用漏绑检测器。
2. **不是漏绑数量，而是 clear 后漏绑编号，只绑定数量。** 当前表的 INTEGER PRIMARY KEY 可以自动生成编号，故不能从“有主键”推断所有漏绑必然失败。官方 CREATE TABLE §5 支持此反例。正文的失败断言仅指表格第三行的数量 NOT NULL，且结论要求每个本行参数明确来源，没有作更广的保证；不构成缺口，不要求增加旁支讲解。
3. **上次 step 后不 reset，直接再次 bind。** 官方 bind 文档规定这会返回 SQLITE_MISUSE，不能用保留参数推导覆盖此调用错误。正文各替代分支均明确从成功 reset 后开始，第一节也按这个次序操作，条件已满足。
4. **绑定调用失败却继续 step。** “代码包含完整绑定调用”本身不保证本行值完整。正文已把绑定成功纳入纸面推演条件，并要求检查调用结果。若日后扩写可复制的循环代码，应把失败时停止本轮写入写进控制流；本稿不是该实现，不据此阻塞。
