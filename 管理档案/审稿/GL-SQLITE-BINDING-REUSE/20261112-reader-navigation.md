## 自行设计的变化输入与操作推演

### 不同输入：数量为零也必须来自当前记录

使用正文相同的表和普通 INSERT，但独立选择三件道具：期望 `(41,12)`、`(42,0)`、`(43,9)`。假定相应 API 调用成功，每行 id 唯一，没有触发器或包装器干预。

第一行绑定两个位置后执行完成。第二行 reset 成功后，如果只绑定编号 42，`?2` 仍为 12，实际写入将是 `(42,12)`。零不是“无须赋值”，也不是“没有新值”：正文的“每个参数本行来源”要求数量零同样显式绑定。执行成功只说明这些值满足本例 SQL 的要求。

我会选择每行在 reset 检查成功后完整绑定 id 和 qty，检查每次绑定结果，再执行并确认完成。第二行完整绑定 `(42,0)` 后，若第三行又漏绑 qty，沿用的会是零而非最初的 12。这说明污染源是该语句当前保留的绑定状态，不必总是第一件道具，也不是数据库自动从相邻行复制数量。

正文依据：第一节区分执行状态与绑定保留；第二节说明完整重绑不依赖 clear；第三节要求逐参数审查本次来源。

### 改变条件：清空、漏绑与可空列

在原 NOT NULL 表中，reset 后 clear bindings，再只绑 id 42，会使 qty 为 NULL，第二次执行应报告约束失败，不能把它列为正常保存，也不能据此宣称“已正确写成零”。若 reset 或绑定本身失败，我不会继续把这条记录列为保存成功；具体恢复循环不属于本文交付。

若改成允许 NULL 的数量列，同样漏绑可能成功写入 NULL。此时 clear 无法充当通用检测器，仍需当前记录的完整赋值与业务读回。由此我的默认选择仍是完整重绑；额外 clear 可避免静默沿用旧值，却不能替我确定本次数量。明确需要空值的字段应把 NULL 当成本行意图，而不是偶然的未绑定状态。

正文已明确给出这一会改变诊断结果的条件，不需要后台笔记才能推出。我的变化输入不是照搬文中 7 与 3 的成功示例。

### 读回与故障分流

完成保存后，按 id 对照本次预期的完整映射 `{41:12, 42:0, 43:9}`，不能只数三行或只查最后一个返回码。若源表里已是 `{41:12, 42:12, 43:9}`，先查第二行赋值与绑定调用，不把错误交给备份接口解决。若源值正确而备份缺失，再进入正文给出的备份文章，检查复制对象与完成条件。

若期望值也从错误数据库读回再充当基准，比较会自洽但不能发现意图损失；本次操作把输入记录作为预期依据。这是正文“本次保存意图”“各自记录”和按编号核对数量在本任务中的具体落实，不是新增实测结论。
