## 首次必须修复的问题（均已解决）

### 1. 更新步骤真实执行，但不是被调用的 update 方法

位置：正文第5节“附属程序实际调用 start/update/stop”；模型 `README.md`“start/stop 是实际被调用的本地 Python 方法”附近和“人工 update”描述应一起校准。

`behavior_fixture.py` 确实定义并调用 `start`、`stop`。持续更新则是 `Fixture.tick` 内联执行 `self.work += 1`、增加计数并追加 `op='update'` 日志，没有独立的 `update` 方法或执行器回调。因此更新并非虚构，31次计数也正确，但“实际调用 start/update/stop”的接口级断言不准确。不能把一条名为 update 的调用日志当成实际存在该方法的证明。

通过条件：将正文改成准确的“实际执行开始、持续更新和停止步骤，开始/停止为方法，持续更新内联在 tick 中”，或者抽出并实际调用 update 方法后重新运行和保存输出。最小修复优先采用准确表述，无需为措辞扩建框架。

### 2. 区分开始失败与运行中的失败

位置：正文第4节步骤1、步骤5提到执行结果的完成/失败；第5节介绍附属程序验证范围；模型 `README.md` 边界说明。

正文给出的运行失败退出处理是合理设计，但夹具只读取 `complete`，没有运行状态 Failed，也没有运行中失败的输入。500ms 的失败属于 start 失败，不是 update 已执行后的行为失败。不能将现有轨迹当作完整验证了第4节全部终止分支。

通过条件：在复现材料说明中明确“运行中的失败状态与退出分支未建模，已验证的是开始失败；接入执行器时须按第4节处理并测试运行失败”。也可加入一个最小运行失败用例，但不是发表所必需。无需改掉正文合理的通用接入步骤。
