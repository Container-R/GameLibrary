## 一、需要修订的具体问题

### R1 暂停配置顺序没有保证空间接口的模式前提

位置：第 91 行“依次设置本次 priority、volume、所需空间参数及播放模式”，以及第 29 行请求参数和第 78 行笼统参数校验。

反例：固定、有效、内存 PCM Sound 以 2D 模式准备，本次请求要求按 3D 播放。如果按列出的顺序先调用 set3DAttributes，再准备 setMode(FMOD_3D)，第一次空间调用就会返回 NEEDS3D。该输入不违反目前给出的范围。清理逻辑虽能守住额度，却把正常请求变成可避免的配置失败。基础 API 知识不能替代文章自己写出的顺序条件。

官方证据：[ChannelControl::set3DAttributes](https://www.fmod.com/docs/2.04/api/core-api-channelcontrol.html#channelcontrol_set3dattributes)，本轮页面第 1965 行明确要求对象已经设置 FMOD_3D。

通过条件：把模式前提落实到主流程。可以先确定并应用合法的 Channel 模式，再设置依赖该模式的空间属性；也可以明确资源映射已固定 2D/3D 模式且在预检中拒绝不匹配请求。无需扩写整篇空间音频教程，但应给一个实际顺序，并注明每步失败仍走现有清理分支。测试列表补一个模式不匹配或模式切换输入即可。

### R2 去重结果的保存承诺与入口/去重容量拒绝之间缺少明确界线

位置：第 33 行“在约定保留期内重投时返回原结果”；第 43 行入口满、去重表满时拒绝新身份；第 78–80 行“检查过期、重复…任一失败：记录拒绝结果”。

反例：去重表全部条目仍受保护，新身份 X 到达，被表容量拒绝。此时不能再把 X 的拒绝结果塞进已满的表。稍后其他条目过期，但 X 的有效截止时间尚未到，同一 X 再次到达。依据“新身份有空间可处理”它能获准；依据“重投返回原拒绝结果”它又不应获准。入口 Q 已满时的拒绝也有相同的记录归属问题。已有实例不会因此超额，但读者必须自行选择不同的重投协议，文章承诺的明确去重处理尚未闭合。

同一段伪代码还把重复统一并入“记录拒绝结果”，容易使实现用重复拒绝覆盖原成功结果；应让重复直接返回已有结果，不走生成新拒绝记录的分支。

通过条件：区分“尚未被入口接收/无去重槽位”的拒绝与“已经取得去重槽位并完成处理”的结果；明确前者是否允许有效期内重投，且不声称保留不了的拒绝已被记住。后者在任何播放创建之前确保有结果槽位，重复直接返回原结果，处理后的成功或业务拒绝在保留期内不覆盖。补一段短伪代码或文字顺序即可，并用表满后重投 X 的算例检验。本文可选择不保证入口拒绝的幂等结果，无需为全部拒绝建设无限缓存。

## 二、独立核对后成立的主要论证

1. B、M、R 分工正确。System::init 的 maxchannels 是总播放 Channel 容量；setSoftwareChannels 是实际软件混音额度且有初始化时机限制。先预留使批内后续请求看到已占用额度；单所有者、其他创建者可信上界的条件足以支撑本文的应用容量推理。
2. 暂停配置、虚拟播放、待清理都保留占位合理。isPlaying 对暂停播放仍可为 true；虚拟并不等于结束。当前方法没有把 isVirtual 当作回收信号。
3. 原始成功句柄、资源和 System 存续前提下，stop 成功、自然终止或两类终止错误归入统一 finish 是可靠的控制侧方法。每次 API 独立检查结果，旧身份代次验证和一次归还标记处理了查询后终止与槽位复用问题。
4. 创建非 OK 与创建后配置失败的分离是有价值的。公开 playSound 说明和错误枚举没有给出覆盖所有失败阶段的事务保证；保留额度并冻结准入是作者选择的保守政策，不是 FMOD 必然泄漏的事实。文章把这点和可用性代价讲清了。系统重建不在本篇实现范围，不因此要求作者提供自动恢复器。
5. 优先级纸面比较与官方规则一致，且限定了阈值、竞争者和解码条件，没有伪装成 SDK 实测。应用拒绝发生在创建前，后续 FMOD 优先级无法救回未创建请求的解释成立。
6. 控制侧流程已经包含请求期限、批次、去重、类别额度、暂停配置、清理、终止和观察代价，正文而非管理笔记承担了必要解释。修复 R1、R2 后，目标读者可据此实施最小入口并判断失败记录是否应保留。
