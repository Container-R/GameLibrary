# 为了少画物体，为什么反而卡在等待GPU结果上

一堵不透明墙后有一个复杂物体。程序希望先问 GPU：它是不是完全被挡住了？如果是，就不再提交完整模型。这听起来比直接绘制更省，但若程序发出查询后立刻停下来等答案，省下的绘制工作可能换成另一段等待。

**遮挡查询**让 GPU 统计一段绘制操作中通过相关测试的样本。应用可以用较简单的代理几何，例如合适的包围体，询问复杂物体是否可能可见；代理不能随意代替真实物体写入深度、遮住其他对象。发出并结束查询，只是安排了这项工作，不表示 CPU 此时已经拿到结果。

下面以一个原创、未运行的墙后物体例子说明决策区别。场景限定为普通不透明绘制，深度测试正确，查询能力可用、计数位非零且计数不溢出，代理与测试设置对所考察物体是保守的。这里“保守”指不能把本来可见的物体误判为不可见；任意包围盒在任意裁剪条件下并不自动满足这个前提。

## 未返回的结果，不是零

在历史 OpenGL `ARB_occlusion_query` 接口中，读取 `QUERY_RESULT_ARB` 可能使主机等待；`QUERY_RESULT_AVAILABLE_ARB` 则用于询问此刻取结果是否还需要等待。[1] 它们回答不同的问题：

- “结果可用吗？”是在检查工作是否已经给出答案。
- “结果是多少？”才是在读取该次查询的计数。

因此，未就绪不能填成零，再按“完全遮挡”跳过绘制。结束查询后立即读取，也不能保证比直接画物体更快。CPU 停在这里时，可能无法继续准备本可与 GPU 重叠的工作；查询本身也有提交和处理成本。GPU Gems 的历史讨论正是从逐个查询、逐个等待的问题出发。[2]

把等待改成不停轮询，同样没有凭空创造有用工作。检查可用性有助于决定先做什么，但不是“没有成本”或“一定在下一帧前完成”的保证。现代项目应按实际采用的 API 核对语义，不能把这个历史 OpenGL 接口名直接套到所有平台。

## 昨天被墙挡住，不代表今天仍被挡住

用 Q0、Q1 分别表示前后两次查询，而不是两个保证按帧返回的时钟。

| 时刻 | 已知事实 | 还不能推出什么 |
|---|---|---|
| 前一帧 | 相机在墙前，查询 Q0 返回零 | 下一帧仍然完全遮挡 |
| 当前帧 | 相机移到墙边，物体已有一部分露出；已安排当前条件下的 Q1 | Q1 已完成，或它也会返回零 |
| CPU 需要决定是否绘制时 | Q1 尚未就绪，手上只有 Q0 | 可以把旧零值当成本帧跳过的依据 |

本例中，露出物体是设定的几何事实，不是一次 GPU 测量。如果一直沿用 Q0，直到下帧才补画，就可能在本帧漏掉本应出现的物体。相机没动而遮挡墙移开，也会破坏类似推断。反过来，旧结果认为可见，而当前已经遮住，通常意味着做了本可省掉的工作；在本文的正确不透明绘制条件下，深度测试仍会处理被挡住的片段。

两种猜错的代价并不对称：**多提交一些工作，与把本该出现的内容剔掉，不是同一种错误。** 即使拿到了一个已完成结果，也要知道它对应哪次相机、物体代理与深度条件，不能只凭查询对象编号就称它是当前答案。

## 不立即等，不等于永远不需要答案

对 Q1 未到的情况，可以先处理不依赖它的工作，例如其他已决定绘制的对象，之后再回来检查。若这次结果表明物体可见，就要在本帧相应绘制阶段结束前处理它；不能等到画面已经结束，才把“后来知道了”说成本帧没有遗漏。

如果最后仍没有答案，就要明确选择。继续等待会保留反馈依赖，不能承诺没有停顿；或者按可能可见处理，提交这个物体，让正常绘制处理其遮挡。在本例前提下，后一种选择避免因这条未解决查询而漏画，代价是可能增加提交、几何或着色工作。它不证明整个剔除系统没有其他错误，也不保证整帧更快。

Wimmer 与 Bittner 的历史一致性层级剔除方法（CHC）提供了一个正向例子：利用此前的可见分类安排当前查询与绘制，并在当前结果到达后处理新露出的节点。旧分类用于调度，不是无条件跳过当前验证。其伪代码在没有其他遍历工作可做时仍可能等结果，不能简化成“延后一帧，等待就消失了”。[3]

这不是建议把完整层级算法移植到每个项目。如果场景几乎没有可剔除内容，或者查询成本高于节省的工作，增加查询可能不划算。应比较整条处理路径，而不只记录“剔除了多少物体”；本文没有测量这些成本。

## 接入时先检查哪一个判断

排查墙边物体突然出现的问题时，可以先分清：程序拿到的是当前结果、旧结果，还是根本没有结果；随后查看缺结果时执行了等待、延后处理，还是直接跳过。若只把所有情况压成一个“可见/不可见”布尔值，就很难看出漏画是如何发生的。

代理几何和绘制状态也必须成立。例如近裁面裁剪可能使代理测试不再保守，不能因为查询返回零就一概跳过。[3] 本文没有给出完整近裁面处理或遮挡物选择算法；这里的例子也不覆盖透明混合、alpha-test、所有多通道渲染和跨帧复用策略。不要把透明物体的外包围体当作一堵不透明墙写入深度。

这份支持只解释反馈时机与决策的关系，没有运行查询、检查画面或给出性能数字。真正需要核对的是：为了节省绘制，是否引入了不必要的立即等待；为了避开等待，又是否把未知或过期判断悄悄当成了当前遮挡。
