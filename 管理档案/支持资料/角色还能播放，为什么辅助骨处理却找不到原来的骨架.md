# 角色还能播放，为什么辅助骨处理却找不到原来的骨架

角色的抬臂动作还在正常播放，接入的辅助骨处理却读不到预期节点；或者节点还在，按旧父骨骼解释它的局部位置，结果却不对。这时，继续调整动作或辅助骨参数，可能没有碰到真正的问题：**负责播放的动画数据仍然存在，不代表自定义处理还能通过原来的场景层级、在原来的阶段读到它。**

这是一个面向技术动画接入者的假设情境，不是某款游戏的故障记录。这里要区分的不是“先算哪个约束”，而是处理所依赖的骨架表示是否还成立。

## 同一个姿态，可能在不同地方

接入时，至少要把三种数据位置说清楚。

- **场景中的 Transform 层级**：脚本可以沿父子关系查找节点，局部量以该节点的父级为参照。但运行配置不一定保留制作时看到的整棵树。
- **辅助骨系统自己管理的数据**：处理器可以保留自己的骨骼关系和计算缓存。这里的父子关系、输入更新和结果写回，需要由接入方维护，不能因为名字相同就视为场景层级的实时副本。
- **动画图正在处理的 AnimationStream**：图内某个阶段的姿态，与图外某次读取场景 Transform 得到的状态，不应未经核对就当成同一份输入。需要的可能是紧接某段动画处理后的状态，而非更早读出的缓存。

这三者不是所有系统都必须照搬的架构，而是排查时有用的区分。角色画面上仍能动，只能说明播放链路提供了可用姿态，不能独自证明自定义处理的查找路径和读取时机正确。

2023 年，Square Enix 的佐々木 隆典在 KineDriver 辅助骨系统接入 Unity 的讲义中，讨论了自行管理 Transform 数据和图内状态位置，并展示了优化后的外部层级变化。[1] 这提供了一个具体历史例子：问题不只是处理顺序，也包括处理器究竟从哪里取得它所理解的骨架。

## 父级变了，“局部位置”也换了参照

用一个不依赖引擎的纸面例子来看。假定层级是 `Root → Parent → Child`；Root 无旋转、无平移，Parent 相对 Root 零平移、绕 Z 轴正向旋转 90°，各级尺度均为 1。Child 相对 Parent 的局部位置为 `(1, 0, 0)`。

在通常的右手坐标旋转约定下，Parent 的局部 X 方向在 Root 参考系中指向 Y，因此 Child 在 Root 参考系的位置是 `(0, 1, 0)`。

现在**仅为教学**假定把 Child 直接挂在 Root 下，同时保持它在 Root 参考系中的位置。新局部位置就应是 `(0, 1, 0)`，不能再把旧的 `(1, 0, 0)` 当作相对新父级的同一个位置。若辅助骨算法仍按“相对旧 Parent”解释新读到的数值，即使节点名字相同，也已经换了问题。

这不是 Unity 实际重挂接数据的观察，更不说明某个优化器一定怎样改写每个分量；它只说明：**比较局部值以前，必须先核对父参考系。** 节点是否可访问与访问到的局部量是什么意思，是两个问题。

## 历史接入选择，不是可以照抄的初始化顺序

讲义第 105–107 页展示了优化后外部节点不再按原树暴露的情况，以及作者先绑定流句柄、再在运行初始化时优化的选择。作者还区分了预览与播放时的处理。[1] 不能由此推导“所有项目先绑定、再优化就解决了”。

另对照 Unity **2022.3** API 文档：`BindStreamTransform` 的绑定对象有前提——该 Transform 已绑定到相应 Animator；这不是将任意场景节点自动变成所需骨架关系的接口。[2] `OptimizeTransformHierarchy` 文档则明确指出，运行时调用会重新初始化 Animator。[3] 因而它不能被描述成动作途中随时打开、对已有状态没有影响的透明开关。两页文档也不足以保证任意句柄在任意重初始化过程后都可继续使用。

对实际交接，更有用的是先回答三个具体问题：处理需要的是旧父骨骼下的局部量，还是优化后暴露节点的量？这些量在何时进入处理器，是场景读取、自己维护的缓存，还是图内流？初始化所需的节点何时存在，优化或重新初始化后，谁负责重新确认这些约定？答案明确以后，再决定保留哪些可访问节点或调整接入路径，而不是先改动画资产。

本文未运行 Unity、KineDriver 或真实角色资产；坐标例是原创纸面推导。2023 年讲义不是某个已确认商业游戏的实现记录，文中引用的不同 Unity 版本信息也不足以锁定该插件的完整测试环境。这里不提供通用初始化配方、性能结论或句柄生命周期保证。
