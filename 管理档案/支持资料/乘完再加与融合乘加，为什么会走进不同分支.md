# 乘完再加与融合乘加，为什么会走进不同分支

回放在同一个模拟步第一次出现差异。命令、随机数和三个输入数都相同，代码也都在计算 `a × b + c`，但一边得到0，另一边得到一个很小的负数。如果下一步按“结果是否小于0”选择行为，两边就会分开。

这不一定是浮点数在随机变化，也不能仅凭这个现象认定编译器有错。这里用一个原创纸面例子说明：**同一条实数算式，在哪里舍入，也是计算过程的一部分。** 本文面向排查回放分歧的玩法程序员，没有编译代码、运行引擎或观察某台处理器。

## 先乘再加，中间可能已经丢掉一部分信息

浮点数只能保存有限精度。用 `rn(x)` 表示将精确值 x 按指定规则舍入成可保存的值，则两种过程分别是：

```text
分别运算：rn(rn(a × b) + c)
融合乘加：rn(a × b + c)
```

**融合乘加**（fused multiply-add，FMA）把乘积与加数作为一次操作求值，最后只舍入一次；它不是先把乘积保存到同精度临时量再相加。[1] 两行不是在争论乘法和加法谁先执行，而是在说乘积是否先被舍入。

下面固定所有条件：输入与每个指定舍入结果使用 IEEE binary32（二进制32位单精度），采用“舍入到最近值，恰好居中时取偶数”的规则，不使用额外精度的中间结果。正常数（normal number）的有效精度为24个二进制位。[2] 本例的非零数都是正常范围内的数，没有溢出、下溢或非数值。

## 一个可以逐步核对的例子

取三个能被这种格式精确表示的输入：

```text
a = 1 + 2^-13
b = 1 - 2^-13
c = -1
```

`2^-13` 表示1/8192。先按精确实数展开乘积：

```text
a × b = (1 + 2^-13)(1 - 2^-13)
      = 1 - 2^-26
```

关键在于1下方的浮点间距。在 binary32 中，紧挨着1、比1小的可表示数是 `1 - 2^-24`。精确乘积 `1 - 2^-26` 距离1只有 `2^-26`，距离下方那个数则有 `3 × 2^-26`，所以舍入到最近值时选择1。这里没有恰好居中的平局。

于是，**分别运算**先把乘积舍入成1，再加 c：

```text
rn(a × b) = 1
rn(1 + (-1)) = 0
```

**融合乘加**不先舍入乘积，保留它与1之间的差，再完成相加：

```text
a × b + c = -2^-26
rn(-2^-26) = -2^-26
```

最后这个负数本身可以精确表示，因此不需要把它舍成0。若本例人为规定 `结果 < 0` 才进入某分支，分别运算不进入，融合运算进入。这只是用于展示差异如何被后续规则放大的条件，不是碰撞或战斗判定的推荐阈值，也不是已发现的游戏故障。

FMA在这个例子里反而保住了精确实数结果。问题不是“更准确的计算错了”，而是**更准确**与**重现原来的计算路径**是两个不同要求。

## 源码写成两步，不足以证明实际也舍入两次

上面两条 `rn` 过程是明确规定的运算模型，不是对任意 C/C++ 源码的自动承诺。实际是否把乘加融合，还受编译模式和目标支持影响。[1]

例如 GCC 14.2 的 `-ffp-contract` 文档区分禁止融合、按语言规则融合及允许目标支持的融合；这是一个需要核对的构建条件，不是一条放到所有编译器上都有效的命令。[3] 不能只看源文件里有一个临时变量，便宣布没有融合；同样，也不能只看到处理器支持FMA，就宣布这个表达式一定用了它。

排查时先保留首个分歧步、进入表达式前的操作数及其精确表示，再核实际构建配置与该计算路径。若要归因到融合，应确认实际生成或调用的运算组织；只有两条最终血量日志，不足以证明原因。以上是建议的诊断顺序，本次没有检查二进制或运行回放。

最后不要把禁用融合当成确定性认证。本文只隔离一种舍入差异，没有处理运算重排、数学库、额外求值精度、随机值消费或输入归属。固定步提供了比较位置；它并不替程序约定这一位置内的全部计算规则。
