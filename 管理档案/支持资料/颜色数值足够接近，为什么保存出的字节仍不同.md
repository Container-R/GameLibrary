# 颜色数值足够接近，为什么保存出的字节仍不同

设想一种交付检查情形：工具检查颜色转换时，浮点结果已在允许误差内，保存为每通道8位的纹理后，两个版本却差了一个整数。这不一定说明浮点检查写错了：**“足够接近”和“量化后相同”是两种要求。** 对负责导出与渲染交接的人，关键是先分清交付需要哪一种，而不是继续增加结果打印的小数位。

## 一个跨过舍入边界的绿色分量

沿用主文的颜色条件，只看绿色：输入为编码 sRGB 的 `64/255`，alpha 为 `128/255`，背景是不透明黑。设 D 为 sRGB 解码，E 为编码，参考输出为 `r = E(D(64/255) × (128/255))`。这里借用固定 CSS Color 4 的非规范性转换示例作数学参考，不把它当成任意颜色管理库的输出保证。[1]

按该公式，`255 × r ≈ 44.523106773`。现在假设检查要求是：**在重新编码后的、归一化到0至1的 sRGB 分量上，绝对误差不超过0.0001**。它不是线性光域误差，也不是视觉差异阈值。换成0至255的码值，这个允许范围为参考值上下各0.0255。

构造另一个数 `r′ = r − 0.000095`。它满足上述浮点条件，但 `255 × r′ ≈ 44.498881773`。若最后不加抖动、采用最近整数舍入，参考值得到45，构造值得到44：两者分处44.5的两侧。本例没有恰好落在半整数上，也没有越界，因而不用借助平局舍入规则或裁剪来制造差异。

这只是**允许范围内存在不同字节结果**的反例，不是两次 LittleCMS 调用产生了这些不同输出。0.0001来自旧有限实验的预先门槛，并非所有8位颜色都应采用的标准；这里也没有证明一个码值的差异能被玩家看见。

## 输入输出用 double，不能替代这项判断

`double` 是双精度浮点类型，但接口两端使用它，不代表中间每一步都保留同样精度。LittleCMS 2.19 的固定源码提供了具体例子：`UnrollDoublesToFloat` 将输入转入32位浮点数组，`FloatXFORM` 使用浮点中间数组，`PackDoublesFromFloat` 再把结果写入双精度输出。[2] 输出容器变宽，不会自动找回较早一步丢失的精度。

这只说明所列实现路径，不能据此断定所有插件、自定义转换或安装构建都走同一路径，也不能把上面的构造偏差归因于其中某次类型转换。旧 LittleCMS CPU 观察仍保留在主文及[来源与范围说明](../研究记录/source-notes/lcms-transfer-boundary.md)中；本篇没有重跑它，没有重新证明内部白点适配，更没有执行纹理保存或 GPU 测试。

## 把数值检查和交付检查分别定义

如果工具只要求数值近似，应写清参考算法、比较发生的颜色域及绝对或相对误差，不能只说“误差很小”。如果下游还要求颜色通道字节相同，则要另外约定输出位深、量化位置、舍入和平局规则，以及范围外数值的处理，并在这些规则下比较实际通道字节。通道相同也不自动意味着包含元数据或压缩的整个文件逐字节相同。

接近舍入边界的样例能揭示两种检查为何不能互相替代。对这里的45而言，参考码值到44.5仅约0.023106773，小于允许的0.0255；因此这条浮点门槛本来就不足以保证45。工程上要明确是否真的需要稳定字节，再决定转换和量化的共同约定，而不是把有限数值通过当成交付字节已经通过。
