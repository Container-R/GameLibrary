# 拖动物品时，事件目标为什么不是落点

网页游戏里，一件物品从背包格子 A 拖到了格子 B 上方。玩家松开鼠标，程序却发现 `pointerup` 的 `target` 仍是 A。这不一定是坐标错了：如果 A 捕获了这个指针，浏览器正是在按要求把事件继续交给 A。

这里讨论用 Pointer Events 自己实现的网页界面拖动，不是 HTML 原生拖放，也不是 Unity 或 Godot 的输入接口。例子只有一个鼠标指针和左键；格子不移动，没有遮挡、滚动、缩放或跨文档。

## 收到事件的元素，与可以放东西的格子，是两回事

指针捕获解决的是“移出原控件以后，谁继续收到输入”。A 在按下时请求捕获，捕获生效后，即使鼠标已经离开 A，相关指针事件仍以 A 为目标。W3C 的分派规则明确把捕获目标放在正常命中测试之前。[1]

这对拖动有用。物品不会因为鼠标稍微离开原图标，就突然失去后续输入。但它也意味着：不能把 `event.target` 直接当作放置格子。

假设 A 位于横坐标 20–120、纵坐标 20–120 的矩形内，B 位于横坐标 220–320、相同纵坐标范围内。玩家从 `(50,60)` 按下，拖到 `(250,60)` 松开。在这个无遮挡的固定布局里，该位置落在 B；捕获中的 up 却仍交给 A。一个是坐标与布局的关系，一个是事件的接收关系，并不矛盾。

应用需要另外确定放置候选，再检查它能否接纳这件物品。例如 B 是否禁用、物品类型是否允许、是否需要交换原有物品。这些都是游戏规则，不由捕获 API 决定。本例可以直接检查矩形；真实界面若有拖动预览层、缩放、滚动或遮挡，就必须相应处理坐标和命中，不能把这套矩形判断当成现成背包系统。

## 正常松手后，也会失去捕获

另一个容易误解的通知是 `lostpointercapture`。标准要求在 pointerup 或 pointercancel 之后清除待定捕获，并处理相应捕获变化。[1] 因此，收到 lost 不能单凭名字判断“刚才的拖动失败了”。

仍用前面的例子。应用在 up 时确认落点是 B，规则允许，于是接受了这次移动。随后正常释放捕获又产生 lost。如果 lost 处理器无条件把物品放回 A，就会撤销一项已经接受的结果。

反过来也不成立：lost 不能直接成为“移动成功”的入口。应用可以在按钮仍按着时主动释放捕获，取消也会结束捕获。这些情况都没有替游戏确认 B 是合法落点。

一种适用于这个小例子的做法是：把拖动保持为待定状态；匹配指针的 up 到来时，重新判断位置与接纳规则，再明确记录接受或取消；清除预览与临时输入状态时，不再重复决定物品去向。这里的提交时机是原创产品选择，不是 W3C 要求。如果项目允许把捕获转交其他控件，还需要另行定义转交，不能机械规定任何意外 lost 都必须回滚。

## 取消与点击还需要各自的规则

pointercancel 是指针事件流被抑制的通知，不是一次正常松手。它的坐标沿用同一指针最近已分派的事件数据，不能被当作刚刚确认的新落点。[1] 对本例，可以选择取消尚未接受的拖动，而不是因为 B 仍高亮就补做一次移动。

也不要指望释放捕获自动吞掉 click。如果浏览器生成了 click，而导致它的 up 在捕获中分派，那么 click 的目标仍按该 up 的目标决定，即使 lost 已经发生。[1] 同一物品既能拖动又能点击使用时，团队需要决定如何区分这两种操作，避免一次拖动结束后又触发使用。这里不声称每次拖动都会生成 click。

本例没有检验触摸、手写笔、浏览器平移、真实设备或无障碍替代操作。捕获不等于键盘焦点或 Pointer Lock，也不保证浏览器永远不会取消输入。要把例子用于产品，应先确认它解决的是“输入交给谁”，再分别检查“落在哪里”和“业务是否接受”。
