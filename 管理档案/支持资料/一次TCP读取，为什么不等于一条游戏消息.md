# 一次TCP读取，为什么不等于一条游戏消息

假设团队为游戏房间自定义了一种 TCP 通信格式。发送端连续提交两条消息，接收程序却把每次读取回调当成一条消息：有时只拿到半个头，有时两条内容一起到，解析器便报出莫名其妙的字段错误。

这里的问题不是 TCP 把消息传坏了，而是**应用没有先定义怎样从字节流中取出消息**。本文面向自行接入字节流协议的程序员，不假定所有房间服务都用 TCP，也不建议绕过已有消息库重做传输。以下采用固定 libuv v1.53.0 的回调契约，例子只是纸面推演，没有运行服务器或网络测试。

## 传输保持字节顺序，不替应用标出每条消息

TCP 提供可靠、有序的字节流。发送调用、TCP报文段与接收缓冲的边界没有一一对应的保证；PSH也不是消息结束标记。[1] 因而“一次发完”不能推导出“对方一次读完”。增大读取缓冲、等待一会儿或改变发送节奏，都不能替代消息格式。

**组帧**在这里指根据应用格式，从连续字节中识别一条完整消息，不是动画帧或音频采样帧。长度前缀、固定长度和分隔符都可能是协议选择；必须与对端一致，不能给已有格式随意加头。若所用库已经交付完整应用消息，应先按该库契约处理，而不是把这段 TCP 例子套到 ENet packet 上。

## 用九个字节看清楚需要保存什么

为便于手算，本例自行规定：每条消息先放**两个字节的无符号大端长度**，高位字节在前；长度只计算后面的正文。正文允许1至8字节，零长度拒绝。这些都是教学设置，不是 TCP 或 libuv 的默认格式及大小限制。

两条正文分别是 ASCII 的 `ABC` 与 `DE`。它们编码后的连续字节为：

```text
00 03 41 42 43 00 02 44 45
长度3    ABC   长度2   DE
```

同一串字节可以分几次交给解析器：

| 本次得到的字节 | 解析后留下的状态 |
|---|---|
| `00` | 头部只有1字节，还不知道长度。 |
| `03 41` | 头部齐，正文长度3；只收到正文的A，仍缺2字节。 |
| `42 43 00 02 44 45` | 先补齐ABC，再用同批剩余字节读出DE；最后没有残留。 |

第三行不能在得到 ABC 后直接返回并丢掉剩余字节。反过来，如果九个字节一次全到，也仍应取出两条消息，不能把整块输入当成一条。回调的切分只改变“本次能推进到哪儿”，不改变消息内容及顺序。

每条连接因此需要保留自己的解析状态：头部已有几个字节、完整头部声明了多少正文，以及正文还缺多少。一次回调结束不清空这些状态；消息完整取出后才开始下一条。

## libuv交出的数量与缓冲容量不是一回事

固定版本的 `uv_read_cb` 中，只有 `nread > 0` 的那段字节是本次数据；`nread == 0` 不是 EOF，也不是一条空消息。EOF用 `UV_EOF` 表示，其他负值按读取错误处理，不能先转成无符号长度再送入解析器。[2]

`buf.len` 是缓冲容量，不能代替实际读取量。`uv_alloc_cb` 收到的 suggested_size 也不是下一条消息的长度。缓冲的释放由应用负责；未完头部或正文若还依赖其中的字节，必须在释放前保存到自己管理的状态中，不能留下悬空指针。[2][3]

发送侧若不在提交写请求后改变阻塞模式，`uv_write` 保持缓冲写入顺序，提交的内存须存活到写回调；该回调报告写入结果，不是对端应用处理完成的通知，也不规定对端读取回调的次数。[2] 请求完成、字节交付、消息完整和业务完成仍是不同阶段。

## 先检查声明长度，再准备正文空间

本例收到完整头部 `00 09` 时，就已知道正文声明为9字节，超过允许的8字节。因此应按本例的协议错误策略停止接纳，不为这个声明准备正文空间，更不等它慢慢送齐。`00 00` 同样按本例规则拒绝；这不意味着所有协议都禁止空消息。

一个足够窄的接收顺序是：先补齐固定长度的头，读取并检查声明，再收集规定数量的正文；齐了就交出这条完整帧，随后继续消费当前输入里剩余的字节。不足时保存状态、等下一次输入，而不是在当前回调里反复等待。

实际实现还须核对长度能否由所用类型表示、分配是否成功。如果计算“头长加正文长”或把数据追加到现有缓冲，先检查剩余容量和算术范围，不能等整数溢出后再比较。这里选择逐段消费，只保留当前未完帧；不是先无限累计所有回调数据，再靠单帧上限补救。

单条消息不超过上限，仍不能保证整个程序资源受控：许多连接、许多已完整但未消费的消息，以及长期送不完的半条消息，都需要各自的容量与等待政策。本例没有实现这些队列、背压或超时机制，也不把8字节说成通用安全阈值。

## EOF要看解析器停在哪里

假设读取方向结束，解析器已处理所有先前交来的字节：

- 只收到 `00`：头还缺一个字节，不能猜它是0。
- 收到 `00 03 41`：正文只到A，不能把A当成已经声明的ABC。
- 收齐上面的九字节：解析器恰好停在消息边界，ABC与DE都已完整取出。

前两种都属于本例的截断消息，应记录并丢弃未完帧，而不是补零或继续分派。第三种只说明没有组帧残留，不能证明这两条业务已被接受或完成。若此前已有完整帧交给业务，后来的截断也不会自动撤销它们。

EOF结束的是读取方向；TCP允许两个方向分别关闭。[1] libuv错误或EOF分支还要按接口要求停止读取或关闭，并完成对应资源清理。[2] 本文不提供半关闭回复协议、重连续帧或扫描字节重新同步的实现；新的连接不能无条件继承旧连接的半个头。

最后，长度正确和字节齐全只解决了消息边界。内容是否合法、调用者是谁、是否有操作权限，仍须另行判断。TCP自身不提供密码学身份认证，[1] 这个长度检查也不是完整安全方案。
