# 写了有限值检查，为什么还要检查编译选项

资产导入器接收一个移动速度。普通有限数值可以进入后续处理，NaN（非数值）与正负无穷则应被拒绝。代码里已经写了 `std::isfinite(speed)`，交接时却还不能只凭这一行断言：发行版本一定拒绝了这些输入。

原因不在于分类函数不好用，而在于编译时可能给出了相反的前提：允许优化器假定参与计算的参数和结果根本不会出现 NaN 或无穷。检查代码要识别的情况，恰好被构建配置排除了。

这篇补充面向 C++ 工具和构建工程师，说明怎样审查这类配置矛盾。它依据 GCC 15.2.0 与 Clang 20.1.0 文档，没有编译下面的示意程序，也不判断任何具体发行包已经失效。

## 先说清楚检查要接收什么

下面只表达有限值分类这一步，不是完整的速度合法性检查：

```cpp
#include <cmath>

bool has_finite_speed(float speed) {
    return std::isfinite(speed);
}
```

在能够表示这些浮点类别的实现上，需求是让普通有限值通过，让 NaN、正无穷和负无穷不通过。通过分类以后，仍需按游戏规则判断速度是否为负、是否超过上限；“有限”不等于“这个角色可以采用的速度”。

现在设想导入模块继承了全项目的 `-ffast-math`。GCC 15.2.0 将 `-ffinite-math-only` 包含在这个选项组里；后者允许以参数和结果均不是 NaN 或无穷为前提进行浮点优化。Clang 20.1.0 也明确列出了同类前提。[1][2]

因此，源码中的检查意图和这套编译前提并不相容。能从文档得出的结论是：**不能只凭检查代码的存在，证明最终产物拒绝了这些输入。** 至于某个编译器、标准库和目标配置实际生成了什么指令，还要检查相应产物。本篇没有观察到“函数被折叠成恒真”，也不把这种可能性说成所有版本的统一行为。

## 不要把几个数学开关混为一谈

`-ffast-math` 是一组选择，不只是“让乘法更快”。GCC 的普通 `-O2`、`-O3` 也不能直接等同于它。`-funsafe-math-optimizations` 与 `-ffast-math` 的选项集合不同，只关闭前者，不能据此认定另外启用的 finite-only 假设也已经撤销。[1]

Clang 还提供分别处理 NaN 和无穷的开关。文档说明，同时使用 `-fno-honor-nans` 与 `-fno-honor-infinities`，效果等同于 `-ffinite-math-only`。即使只启用了其中一项，也要核对它排除的那一类输入是否正是验证代码需要识别的。排查时应看实际生效的组合，不能仅搜索命令行里有没有 fast-math 这个词。[2]

这也不是乘加融合的问题。`-ffp-contract` 关系到是否融合乘法与加法；把它关掉，并不意味着已经恢复了识别非有限值所需的前提。反过来，撤销 finite-only 也不代表舍入、异常、次正规数等所有行为都已满足项目要求。

## 沿着交付版本找到真正执行检查的位置

对于这个速度字段，可以按下面的顺序检查：

1. **找到接收函数实际编译的位置。** 核对交付目标的有效参数，而非只看编辑器中的配置名称。函数如果写在头文件里，或通过模板实例化，真正编译它的可能是调用方。
2. **让验证代码采用相容的浮点前提。** 如果职责是看见 NaN 与无穷后拒绝，就不应让这部分代码依赖“它们不会出现”的假设。优先从正常语义配置出发审查需要的优化，而不是先继承 fast-math，再凭单个反向开关猜测已经全部恢复。
3. **检查最终的组合与边界。** GCC 的 `-fno-finite-math-only` 针对这一特定假设；Clang 还应核对 NaN 与无穷的相关选项。头文件内联、参数覆盖，以及链接时优化（LTO）都需要放进实际项目的审查范围。仅把声明放入另一个文件，不足以证明检查已隔离。
4. **用真正的交付候选核对预期。** 为普通有限值、NaN、正无穷与负无穷分别规定接收结果，再观察候选产物是否一致。保留目标、编译器版本、有效选项与观察结果。本篇只给检查建议，并未执行这一步。

后续热循环可以根据自己的真实条件选择优化方式，不必由此推出“整个游戏永久关闭全部浮点优化”。但输入有限也不保证计算结果有限，例如范围内的输入经过运算仍可能溢出。若热循环采用“参数和结果均有限”的前提，这两端都要有依据。

也不要急着把 `std::isfinite` 换成 `x == x` 或手写位掩码。换一个表达式不等于撤销编译假设；位级方法还需要明确目标表示与解析方式。这里首先要修正的是验证职责与构建条件之间的矛盾，而不是寻找一种看上去更隐蔽的写法。
