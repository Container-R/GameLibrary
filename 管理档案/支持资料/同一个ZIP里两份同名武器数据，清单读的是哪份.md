# 同一个ZIP里两份同名武器数据，清单读的是哪份

假设试玩包用 ZIP 保存武器数据，构建脚本为包内每个成员生成检查清单。脚本先枚举成员，记录名称和长度，再按名称读取内容。清单有两行 `weapons/rifle.json`，长度都是 13 字节，看起来两行记录都完整。但这两行读到的，还是各自那份数据吗？

这个情境不是实际游戏事故。下面用原创小数据做有限观察，说明**列出了哪个成员**与**按名字重新选中了哪个成员**可能不是一回事。它适用于检查自有 ZIP 打包工具，不证明任何引擎的资源加载行为。

## 两份数据一样长，内容却不同

准备两段 UTF-8 字节：A 是 `{"damage":1}` 后接一个换行字节，B 是 `{"damage":2}` 后接一个换行字节。两者都是 13 字节。实验只在内存中创建 ZIP，采用不压缩的 `ZIP_STORED`，每个包含两个成员，不解压到磁盘。[1]

对每个包，从 `infolist()` 取得成员对象 `info`，保留它不作修改，同时观察两种读取：`read(info.filename)` 只把名字交回去；`read(info)` 交回这一个成员对象。表中每格的两个字母，分别对应枚举的第一行、第二行。唯一名称对照用 rifle 与 pistol 两个名称，其余三个包都重复使用 rifle 名称。

| 包内成员顺序 | 两行记录的长度 | 按名字读取 | 按原成员对象读取 | 本例项目规则 |
| --- | --- | --- | --- | --- |
| 不同名的 A、B | 13、13 | A、B | A、B | 接收 |
| 同名的 A、B | 13、13 | B、B | A、B | 拒绝 |
| 同名的 B、A | 13、13 | A、A | B、A | 拒绝 |
| 同名的 A、A | 13、13 | A、A | A、A | 拒绝 |

这是实际输出的归纳，不是预期值冒充结果。可用解释器自报 Python 3.12.14；同一操作者启动两个新进程执行完整四案例，两次观察一致。每个包都枚举出两个不同的成员对象。三个重名包在构造时各捕获一次重复名称警告，唯一名称包没有；读取阶段均未捕获警告。构造时显式采用记录警告的设置，不能据此保证采用“警告即错误”配置的调用者也会成功。[1]

最值得看的是第二行：第一份成员本来是 A，按名字取得的却是 B。因为 A、B 一样长，这次连长度核对也发现不了内容差异。反转顺序后，按名字得到的又变成 A；它并没有理解哪个版本更新、哪份伤害值才符合设计意图。

## 名字不是成员的唯一身份

Python 3.12 文档明确说明，`open`、`read` 可以接收名称或 `ZipInfo`，并指出成员重名时可以用后者区分。[2] 这里应传回从同一个已打开包取得、未修改的对象，不是根据名字另造一个对象。

固定 CPython v3.12.0 按名称选择**最后一个同名中央目录项**。[3] 不应把这推广到其他 ZIP 库，或等同于本地文件头的物理顺序；它也不是本次 3.12.14 运行的二进制身份证明。

## 诊断读准了，不等于这个包可以发

对这个试玩工具，可以分两步处理：

1. **诊断清单保留每一个成员。** 用成员序号区分同名行，让每行元数据与同一个成员对象读出的内容对应起来。不要先按名称折叠成一行，再说已经检查过所有成员。
2. **交付检查执行项目约定。** 如果项目要求一个资源名称只能对应一个成员，发现重复名称就拒绝这份候选，返回打包输入查找来源；不要依赖读取顺序替团队决定用哪份。

这是本例选择的项目规则，不是 Python 要求所有 ZIP 拒绝重名。所以最后一行即使两份内容完全相同，也仍被拒绝：违反的是名称唯一约定，而不是字节内容检查。接收唯一名称对照，也只表示它通过这条规则，不表示完整游戏已经验收。

如果运行时使用另一套 ZIP 库或资源索引，还必须核对那个入口的行为。本观察没有运行游戏、生成哈希清单、测量性能，也没有检验名称大小写、Unicode 归一化、提取覆盖或恶意文件；不能拿它替代那些检查。它解决的是更小的一步：清单里这一行，究竟有没有读到这一行对应的成员。
