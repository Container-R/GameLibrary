# 把声音调小，为什么不等于它会先让出声道

工厂场景里，机器运转声和玩家的确认提示同时播放。接入者把机器调轻，希望声音拥挤时先让它退下；但资源不足时，被移出实际混音的仍可能是提示音。问题不只在增益，还在系统怎样比较这两个播放对象。

这里用 FMOD Core 2.04.00 的声道排序说明一个有限问题：**谁获得实际混音资源，与失去资源后怎样继续计时，是两项决定。** 本文不规定所有游戏的声音重要性，也不把 Core 声道当成完整的 Studio 事件。

## 先分清比较的两个量

FMOD 的 Channel 是一次声音播放所用的对象，本文简称声道，不是立体声中的左、右输出通道。`Channel::setPriority` 设置的是资源排序优先级：数字越小越重要；不同优先级之间先按它比较，同优先级才优先保留 audibility 较高的声道。[1]

**Audibility** 是系统计算的可听性估计值，不是测得的声学响度，也不直接代表实际波形。它用于有限资源下的选择；只看到某个音量滑块的数值，还不足以知道这个估计结果。[2] 因此，把一份声音调小可能影响排序，但不能替代“这个声音应该比哪个声音先退让”的决定。

## 两份声音，只有一个实际混音位置

做一个原创纸面比较。只有机器与确认提示两个有效 Core 声道，两者都已开始、没有暂停或静音，未触发静音虚拟化阈值，没有其他竞争者或解码资源限制。总声道容量足够保留两者，但实际混音容量只容纳一个；比较时的设置和估计值保持不变。实际混音上限与总声道容量是不同配置。[4]

| 声音 | 优先级 | 假定的 audibility |
| --- | ---: | ---: |
| 机器运转 | 64 | 0.1 |
| 玩家确认提示 | 128 | 0.8 |

按上述文档规则，先保留机器，不是因为它更响，而是64比128优先。若只把机器的估计值降到0.05，并且仍不触发静音阈值，两个不同优先级之间的先后关系不变。

若把两者优先级都设为128，保持估计值为0.1与0.8，则提示排在前面。若项目决定提示必须优先，也可以把提示设为64、机器设为128；这次改变的是资源竞争政策，而不是要求提示素材变响。所有数字只为说明关系，没有运行 FMOD，也不是推荐参数或实测值。

资源被保留仍不代表提示已经被玩家听见或理解。反过来，把每种声音都设成最高优先级，也没有创造新的容量，只是让它们回到同级竞争。过多固定层级还有代价：较轻但优先级高的声音可能排掉明显更响的声音，退出更容易暴露。[3]

## 排序之后，才轮到被挤出的声音怎样继续

在本例仅触及实际混音上限的前提下，失去位置的声道可以处于虚拟状态，保留播放时间推进；它不是被暂停，更不等于已经结束。若另一层的总声道容量也耗尽，FMOD 文档另有永久停止被抢占声道、使其句柄失效的结果，不能把两者都写成“稍后恢复”。[3]

循环如何返回，可回到[循环声音重新听见时，应该从哪里继续](../../GameLibrary/声音与音乐/游戏音效/播放管理/循环声音重新听见时，应该从哪里继续.md)。该书的 CRI 配置不能直接移植成 FMOD 设置。本例也不承诺提示后来一定获得资源；若提示的重要起音已经在虚拟期间经过，保留播放时间并不会补上那段输出。

## 接入时先检查竞争关系，再检查输出

先挑一组确实会同时出现的声音，写清哪项信息应保留，再确认资源限制落在 Core 声道、Studio 事件还是其他层。随后对照同一时段的实际优先级、audibility、虚拟状态和播放位置，不用单个音量值代填其他状态；最后检查输出及提示是否仍有效。

刚调用 `playSound` 后，不要立刻把 `isVirtual` 当成本轮竞争的结果；FMOD 文档说明虚拟声道排序需要经过 `System::update`。[3]

这是一条待实施的排查顺序，不是一套已经验证的管理器。提高优先级仍可能遇到同级或更高优先级的竞争、静音阈值和其他限制；本文没有中间件运行、设备输出、听音或性能结果，也没有核验其他产品的等效配置。
