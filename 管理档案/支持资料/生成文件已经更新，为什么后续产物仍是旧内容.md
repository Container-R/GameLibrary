# 生成文件已经更新，为什么后续产物仍是旧内容

[返回构建工程师正文](../../GameLibrary/引擎与工具/构建发布/岗位与协作/构建工程师如何交付可用的游戏版本.md)

在一条简化的 Ninja 文本构建链里，原输入已经修改，中间文件也有了新内容，下游结果却仍保留旧字节，构建还成功退出了。这时可以检查一个具体问题：构建图是否只表达了“先生成，再继续”，却没有表达“生成文件变了，后面的结果也需要重做”？

这次观察用 Ninja 1.13.2 的两个复制步骤说明区别。文件都是原创的普通文本，不是真实规则表或游戏资源；复制程序也不是资产编译器。我们实际运行的是手写 Ninja 图，不是 CMake 生成的工程。它补充的是一个有限可观察例子，不能替代主文中仍属文档解释的 CMake 行为。

## 同一份内容，经过两次复制

这条链只有三个文件：

```text
recipe.txt → generated.txt → bundle.txt
   原输入       中间生成文件      下游结果
```

初始内容是 `asset-version=A`，末尾有一个换行。生成步骤把它复制到 generated.txt，后续步骤再复制到 bundle.txt。之后仅把 recipe.txt 改为等长的 `asset-version=B`，检查 B 是否沿两步传到了最后。

两组规则使用同一个复制程序和相同命令，唯一差别在下游输入前的分隔符：

```ninja
# 第一组：静态隐式输入
build bundle.txt: bundle | generated.txt

# 第二组：仅顺序输入
build bundle.txt: bundle || generated.txt
```

这里的“隐式”不表示不用声明。`|` 后的文件仍参与重新构建的判断，只是不出现在方便拼接命令的 `$in` 变量中。`||` 后的文件同样不进入 `$in`，但它只提供先后约束，其变化本身不使下游失效。[1][2] 本例的复制程序按固定文件名读取内容，命令不用 `$in`，因此没有因为换分隔符而改变实际读取对象。

## 初次都成功，差别出现在增量变化后

我们用同一个从固定官方源码构建的 Ninja，在两套全新目录中重复上述对照。每个重复都包含两组图，每组按“初次、无变化、改输入、再无变化”执行四次。两次重复得到相同行为；下表列出每个重复的观察。次数指实际启动的生成／下游复制程序，不是构建进度条上的总数。

| 阶段 | 隐式组生成／下游次数 | 仅顺序组生成／下游次数 | 隐式组中间／最终内容 | 仅顺序组中间／最终内容 |
|---|---:|---:|---|---|
| 初次，输出不存在 | 1 / 1 | 1 / 1 | A / A | A / A |
| 无变化再构建 | 0 / 0 | 0 / 0 | A / A | A / A |
| 仅原输入改为 B | 1 / 1 | 1 / 0 | B / B | B / A |
| 变更后再无变化构建 | 0 / 0 | 0 / 0 | B / B | B / A |

最有用的是第三行：`||` 组确实执行了生成步骤，中间文件也确实变成 B；但下游复制没有启动，bundle.txt 保留 A。这次 Ninja 调用仍成功退出。第四行又说明，继续执行同一份图，并不会自动发现“下游还在用旧内容”。完整的 16 个阶段、实际字节和程序调用记录见[观察包](Ninja依赖变化观察/README.md)。[3]

初次构建掩盖了这个区别。因为最终文件原本不存在，两组都需要产生它。只看一次干净构建，回答不了“上游改动之后，已有下游结果是否会失效”。

## 等待上游完成，不等于把自己标为过期

Ninja 的固定源码把这两个判断分开：遍历所有输入时，会考虑其生产步骤是否已经就绪；但是，只有非 order-only 输入的过期状态和修改时间参与下游失效判断。[2]

这正好解释本例。下游若需要执行，`|| generated.txt` 会让它等待生成工作；可是在第三阶段，下游文件已经存在，命令也没有改变，而 generated.txt 被列为仅顺序输入。它发生变化，便不足以让这一步重新复制。

因此，排查时可以先问：**这个文件只是开工前需要准备好的东西，还是其内容会影响我的输出？** 对本例中实际被读取并复制的 generated.txt，后一种关系必须表达出来。静态隐式输入是这里使用的一种写法；普通显式输入也有相应的失效语义，但会进入 `$in`，不能不检查命令就机械替换。[1]

也不要反过来宣布 order-only 没用。官方手册举过先生成头文件、后由依赖文件补充真实隐式关系的引导用途；那是另一套完整关系，不是本次反例。[1] 同样，`||` 不意味着下游永远不会执行：输出缺失、命令变化等因素仍可能使它重建。[2]

## 怎样把这个检查用到自己的管线

先找到实际写出旧结果的那一步，核对它读取了哪些文件，再检查这些文件在真实构建图中属于哪类输入。不要只确认生成命令排在前面，也不要只看图上是否画了一条边。

然后保留初次构建，增加一次明确的单输入修改和两次无变化检查。每次都同时看程序有没有启动、输入和输出实际是什么。若只有“清空后成功”，还不能说明增量关系正确。

时间条件也要控制。Ninja 的增量判断使用修改时间等信息，不是替每个输入自动比较内容摘要。[1][2] 本次在写入前后使用固定短等待，并确认改后的源文件时间严格晚于旧输出；没有把时间设到未来。无变化阶段用于发现意外重复构建，文件字节检查用于区分“时间变了”和“内容确实传到了下游”。[3] 自己的检查若不满足这些时间前提，应保留失败并调整验证方法，不能把它归因于依赖类型。

本次没有配置 restat、depfile、dyndep 或缓存，也没有测试多生产者、跨机器、网络文件系统或性能。两次重复来自同一操作者、同一环境和同一个已构建工具，不是独立环境复现。它能说明这两张小图的差别，不能证明真实资产管线已经完整记录了所有输入。
