# 构建来源字段的保留去向

[构建工程读者正文](../../GameLibrary/引擎与工具/构建发布/岗位与协作/构建工程师如何交付可用的游戏版本.md)讨论怎样交付候选，而不展开供应链标准。本说明承接旧稿中必要的字段区别，不增加一本书。

## 看产物、构建定义，还是一次执行？

按 SLSA v1.2 的来源格式，`subject` 指认输出产物；`buildDefinition` 描述构建输入；`runDetails` 描述这一次执行。其中 `metadata.invocationId` 指认某次构建调用，可用于查找相应日志，具体含义由构建者定义。[1] 因此，产物身份、构建定义和调用标识不能互相替代。

`resolvedDependencies` 记录构建时依赖，但至少到 SLSA Build L3，其完整性仍是尽力记录，不能仅因列出了依赖就断言没有遗漏。[1]

实际验证还要检查产物摘要、来源签名、预先信任的签名者与构建者组合，以及预期的构建类型和外部参数。[2] 单独保留一个摘要或调用编号，不等于完成这些验证。

这些区别可帮助解释候选包来自哪里，但不能证明游戏功能检查通过，也不提供发布授权。本说明没有实现签名验证、执行构建或声明符合某一 SLSA 等级；岗位样本也不因此成为采用 SLSA 的证据。
