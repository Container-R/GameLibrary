# 改了组件字段，为什么缓存还没收到更新通知

一个单位的速度从 3 改成了 1，调试窗口已经显示新值，依靠“组件更新通知”刷新的缓存却仍然是 3。先别急着把通知再发一遍：需要确认，刚才的赋值究竟有没有经过会发通知的入口。

以 EnTT 3.13.2 的默认组件存储为例，拿到普通组件的可写引用，和调用库的显式更新接口，是两条不同的路径。这里借用速度缓存说明接入问题；它不是 Factorio 的实现，也不表示 Factorio 使用了 EnTT。

## 组件是可写的，不等于每次赋值都被观察

假设组件只有一个普通整数字段：

```cpp
struct Speed { int value; };
```

实体已经持有这个组件，值为 3，项目也已经订阅它的 `on_update`。下面的写法可以把字段改成 1：

```cpp
registry.get<Speed>(entity).value = 1;
```

在这个固定版本的默认路径中，`get` 交出的是组件引用；赋值随后直接发生在这个普通整数上。它没有因此自动调用组件存储的更新通知。把 `on_update` 理解为“所有字段写入都会被捕获”，就会遗漏这条入口。[1]

另一条路径是显式调用 `patch`，把修改操作交给存储：

```cpp
registry.patch<Speed>(entity, [](Speed &speed) {
    speed.value = 1;
});
```

默认存储先执行修改，再发布更新通知。回调此时可以读取修改后的组件。[1] 因而，订阅者是否收到事件，不取决于调试窗口是否已经显示新值，而取决于修改实际走了哪条路径。

这两个短片段只用来对比入口，并不是完整可运行程序；都要求实体有效、确实拥有 `Speed`，且有关对象与订阅保持存活。自带 setter、观察机制或定制存储的组件可能有另一套规则，不能用普通 `int` 的例子替它们下结论。

## 收到更新，也不等于新旧值不同

反方向也容易误判。如果当前值已经是 3，又通过 `patch` 将它设为 3，固定源码中的默认更新路径仍然发布通知。这里没有先比较整个组件的新旧值，再决定是否通知的步骤。[1]

因此，`on_update` 更接近“这个组件经过了一次显式更新操作”，不是库已经替业务证明“这个数值发生变化”。如果某个订阅者只需把缓存标记为待刷新，重复通知也许可以接受；如果它要据此播放升级音效、记录一次有效速度变化，就不能只靠这条事件作判断。是否需要比较、比较哪些字段，应由具体业务决定。

这也说明为什么不能用通知次数直接替代修改次数：绕过通知入口的真实变化可以没有事件，设回同值的显式操作也可以有事件。

## 一个可以直接对照的有限观察

对这三个入口，本文用固定版本的原始头文件做了两次同条件观察。每个条件都从独立的 registry、值为 3 的组件和缓存开始，订阅在写入之前建立，并保持到读回结束。缓存初值为 3；唯一的回调会读取当前组件值，并把这个值写入缓存。这是例子明确安排的刷新策略，不是库自动提供的缓存。

| 操作 | 操作后的组件值 | 回调次数 | 回调中读到的值 | 操作后的缓存 |
|---|---:|---:|---|---:|
| 通过 `get` 的引用直接写成 1 | 1 | 0 | 无回调 | 3 |
| 通过 `patch` 写成 1 | 1 | 1 | 1 | 1 |
| 通过 `patch` 再写成 3 | 3 | 1 | 3 | 3 |

两次新副本构建与执行得到相同的三行结果。第二次是同一操作者按相同条件重复，不是另一环境的独立复现；也没有增加条件种类。结果说明这个普通整数例子的通知差别，不证明整个游戏的缓存都能正确失效。[3]

## 先统一写入入口，再决定怎样刷新

对只由这个速度字段决定的简单缓存，可以让所有相关写入都经过项目约定的更新入口，或在允许直接写入的路径中另行执行失效处理。关键是两者至少有一条真正落实，而不是给变量起了“可观察”的名字就算完成。

还应检查实际连接，而不只是看订阅代码是否出现过。EnTT 的 `scoped_connection` 离开作用域时会断开连接。[2] 若把它作为一个很快销毁的临时对象，后面的修改可能已经没有接收者。反过来，保持连接也不应该让回调访问已经销毁的缓存对象。接收者、连接和 registry 的存活顺序需要明确安排。

这里的建议不要求每次更新都立即重算复杂结果。立即重算、先标记过期、统一阶段刷新仍是不同策略；选了其中一种后，要检查所有写入与读取入口是否遵守它。通知被触发本身，不能替代对缓存依赖和读取时机的判断。
