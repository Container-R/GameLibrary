# 文件解析成功，为什么还没有读出稀疏属性

工具已经用 cgltf 打开 glTF 文件，找到了一个包含四个元素的 accessor。接着逐个调用 `cgltf_accessor_read_float`，却得到失败返回。文件是否坏了？不一定：**这个固定版本的单元素接口不支持稀疏 accessor，而另一个批量展开接口支持。** 选错读取接口，与文件声明非法不是同一件事。

这份说明面向需要读取 glTF 属性的工具程序员。它用下文完整列出的四元素稀疏标量例子，说明固定 cgltf v1.15 的调用分工，并给出真实 C 执行及一次独立复跑的有限结果。它不是完整导入器教程，也不涉及把网格送入引擎或 GPU。

## 先确定这四个数应该是什么

稀疏 accessor 先取得基底，再替换指定元素。[3]本例从零开始编号，目的编号为 1、3，新值为 7、9。

| 基底来源 | 替换前 | 应得到的完整数组 |
|---|---|---|
| accessor 指向密集基底 view | `[10,20,30,40]` | `[10,7,30,9]` |
| accessor 省略基底 bufferView 与 byteOffset | `[0,0,0,0]` | `[0,7,0,9]` |

这里的稀疏编号选的是 accessor 元素，不是三角形连接索引。也不是把新值加到基底上；第一行不应得到 `[10,27,30,49]`。

两个配置使用相同的 44 字节数据：前 16 字节存放四个密集基底值，后面分别安排稀疏索引和替换值及填充。无基底配置仍保留前面的原字节，但 accessor 没有引用它们；因此未替换的元素必须是零，不能凭“buffer 里有数”就把 10、30 读回来。完整字段和字节见[密集基底输入](dense.json)、[无基底输入](zero.json)与[十六进制数据](fixture.hex)。这些是本库已有教学语义的两份自产输入，不是商业模型。

## 四个 API 阶段，不是四种“打开成功”

固定 cgltf 的接口注释与实现将这些责任分开。[1]

1. **`cgltf_parse` 解析结构。** 它把 JSON 声明转成库的数据结构。返回成功不表示 buffer URI 的字节已经加载，更不表示稀疏属性已经展开。
2. **`cgltf_load_buffers` 取得 buffer 数据。** 本例只加载输入里自带的 base64 data URI，没有外部文件或网络资源。本例检查加载后的全部 44 字节与冻结输入一致。
3. **`cgltf_validate` 做额外检查。** 本例在核定元数据、范围、对齐、目的索引与实际字节后调用它；它不是未知文件的完整安全验证器，成功也不等于已经得到属性值。
4. **`cgltf_accessor_unpack_floats` 生成完整浮点数组。** 对本例，它先读取密集基底或清零，再将稀疏值写到指定元素。此时才有可以与上表逐项比较的输出。

因而排查时不要只留下一个“文件加载成功”。先确认结构是否符合预期，再确认数据已经取得，最后检查所选 API 实际生成的值。否则，缺失数据、接口不支持和数值错误容易混成同一种故障。

## 输出容量按 float 个数，不是按字节数

`cgltf_accessor_unpack_floats` 的容量和返回数量以 **float 个数**计。传入空输出指针可以查询所需数量，但这次查询本身不是解码结果。

本例是 SCALAR、count 为 4，所以需要四个 float。执行时先确认查询返回 4，再提供完整的四项输出空间；实际展开也必须返回 4，并且四项数值全部正确。对于 VEC3 等多分量元素，元素数与 float 个数不再相等，不能照搬这里碰巧相同的两个“4”。本次没有验证那些类型。

不要把容量查询当作“传一个小数组也会自动安全截断”的承诺。这份检查只提供完整容量，不测试部分输出；也不将这种调用方法包装成可以接受任意文件的通用函数。

## 单元素读取返回 false，说明的是接口边界

固定版本的 `cgltf_accessor_read_float` 遇到稀疏 accessor 会直接返回 false；`cgltf_accessor_unpack_floats` 则有基底与稀疏覆盖两遍处理。[1]

在两份有效输入上，本次分别观察到单元素接口返回 false，同时批量展开得到预期数组。失败返回后的输出变量没有被继续使用。这里应调整读取路径，而不是把合法的稀疏文件报成损坏，更不能在返回失败后仍把输出当成成功读出的坐标。

## 本次实际检查到了哪里

2026-11-02，固定 cgltf v1.15 源码在 C99 程序中完成一次有限执行。两份输入的 parse、load_buffers、validate 都返回成功；完整展开分别得到 `[10,7,30,9]` 与 `[0,7,0,9]`，返回 float 数均为 4；两次单元素读取均返回 false。编译和原生进程退出码均为 0，原生 stderr 为空。[2]

随后，另一操作者在同一宿主上使用相同冻结包的新副本、新目录，重新编译并执行一次。两次编译与原生执行均退出 0，编译和运行 stderr 均为空，输出逐字节相同。[2] 这不是跨平台检查，也不是独立算法交叉验证。

这里**共进行了两轮执行，每轮都读取相同的两个配置和同一套 44 字节布局**，不是四种输入，也不是完整模型导入，也没有增加到任意稀疏类型的覆盖。两份输入都是紧密排列的 FLOAT SCALAR，目的索引为 uint16；不覆盖交错基底、矩阵、normalized 整数、压缩扩展、蒙皮或 morph。程序只接收冻结输入，并核对完整输出容量；不提供恶意输入、防溢出或全面格式验证保证。

本次没有重跑旧 160 字节交错读取、旧 Python 稀疏读取器、Godot 导入或 MikkTSpace 检查，也没有观察渲染画面或测量性能。公开协议省略了准备阶段的本机环境观察，公开清单也据此重新计算；它们是**没有按此副本执行过的脱敏衍生资料**，不是当时冻结文件的原样副本。两份结果文件是原执行的脱敏摘录：保留真实阶段状态、技术输出，以及未改源码、输入、检查程序和运行脚本的身份；不把公开协议的新摘要写成旧执行的输入。
