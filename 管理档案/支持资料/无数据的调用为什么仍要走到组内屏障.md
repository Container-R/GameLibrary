# 无数据可处理，为什么仍要走到组内屏障

计算着色器一次处理一批数据，最后一组却没有填满。为了避免越界，代码让没有输入的调用立即退出。单独处理每项数据时，这种边界判断很自然；但如果后面还要等全组交换中间结果，提前退出就改变了另一项条件：**需要参加同步的人没有到齐。**

本文给图形程序一个有限的求和例子，用 OpenGL GLSL 4.60.8 的组内共享变量和 `barrier()` 说明问题。文末再单独讨论一个 HLSL 原子计数误区。两部分都不是 GPU 故障复现，也不是适用于所有着色语言的同步模板。

## 十个输入，不会自动变成一组八人、一组两人

设输入是十个整数 `1,2,…,10`，工作组尺寸为 `(8,1,1)`，派发尺寸为 `(2,1,1)`，即每组八次调用、一共两组。工作组是共同执行着色器、能交换组内共享数据的一组调用，不是整张 GPU 上所有工作。[1]

第一组处理全局索引 0–7；第二组仍有八次调用，其全局索引是 8–15。后六次没有对应输入，不代表它们根本不存在。计划让每次调用把一个输入放到共享数组，等全组都写完后，由组内编号 0 汇总八个槽。

下面的安排便出了问题：

```text
如果全局索引 >= 输入数量：退出
把当前输入写入本调用的共享槽
组内屏障
由组内编号 0 汇总八个槽
```

第二组只有编号 0、1 会走到屏障，编号 2–7 已退出。GLSL 要求同组调用到达对应的屏障；控制流规则也把部分调用提前返回之后的路径列为可能不一致的控制流。[1] 不能因为这段代码没有越界，就认定整个求和已经正确。本例没有运行，因此不报告某设备实际挂起、超时或输出了什么值。

## 没有输入，也可以贡献一个不改变答案的值

求和中，加零不改变答案。因此，可以让没有输入的调用仍完成自己的共享槽初始化，只是不读取输入数组；所有调用再会合。

以下是流程示意，不是完整可编译的着色器。约定每组八次调用、输入与输出容量充足，输入只读，各组输出槽互不重叠：

```text
本次贡献 = 0
如果全局索引 < 输入数量：
    本次贡献 = 输入[全局索引]
共享槽[组内编号] = 本次贡献

组内屏障

如果组内编号 == 0：
    小计 = 0
    对组内编号 0 到 7：
        小计 += 共享槽[编号]
    分组结果[工作组编号] = 小计
```

第二组的共享内容现在是 `9,10,0,0,0,0,0,0`，纸面小计为 19；第一组小计为 36。两份小计尚不是一个已经写出的最终总数。我们只让每组的一次调用读取本组数据，没有让它读取别组仍可能没写好的结果。

这里有两个不能省掉的步骤。第一，**所有槽都要写入**，不能只让有输入的调用写共享槽。GLSL 的共享变量在执行开始时没有可依赖的初值，不能假定剩余六个槽已经是零。[1] 第二，屏障应在分支重新会合之后，而不是藏在“有输入”的分支内部。没有数据可加载，不等于没有同步责任。

零只是求和的选择，不是通用填充值。例如取最大值时，若有效数据全为负数，补零会把答案改大。应先确定运算的无贡献值，或同时记录有效性，再安排尾组处理。这是算法输入的选择，不由屏障替你决定。

## 内存顺序与等待其他调用，不是同一件事

在这里限定的 GLSL 版本中，`barrier()` 同时提供组内执行会合以及共享变量所需的同步；这不表示它自动覆盖所有其他类型的内存访问。反过来，不能把它换成 `memoryBarrierShared()`，便认为全组已经都写到了当前位置：内存屏障函数与执行会合承担不同责任。[1]

HLSL 的 `GroupMemoryBarrierWithGroupSync` 也明确要求组内线程到达调用，并把发散分支中的使用列为未定义行为。[2] 这是另一个接口的相近警告，不是把两套语言的函数逐字互换的依据。

同样，组内屏障不是整个派发的全局屏障。要继续合并 36 与 19，或让后续 GPU 工作、CPU 读取分组结果，还需另行设计跨阶段的执行与可见性条件。本文没有给出这些 API 操作，不能把流程示意直接当作可提交的完整程序。

## 原子计数也不能替别人完成写入

下面单独换用 HLSL 的 `InterlockedAdd` 说明一个相邻误区，不把它当作前面 GLSL 流程的替换实现。这个函数保证对目标整数的加法是原子的，也可以取得加法前的值；官方文档同时明确，它不隐含内存屏障。[3]

例如，多个调用通过共享计数器分配输出槽：先加 1，拿到原值作为槽号，再往那个槽里写数据。假定计数器已经正确初始化为 0，容量足够且不会溢出。某次调用拿到槽 0 后，计数器已成为 1，但该调用尚未执行 `数据[0] = 结果`。此时的 1 说明一个槽已经被预订，不能说明一份结果已经写完。即便另一次调用用原子方式取得这个计数，结论也不会改变。

这是操作先后关系的反例，不需要假设缓存读到旧数据，也不是本文观察到的一次 GPU 故障。原子性保护的是计数器那次更新，不会把后面的数据写入提前完成。

再考虑另一种设计：输出槽已由其他方式确定，写完数据后才递增一个独立的完成计数器。这也不能只凭 `InterlockedAdd` 就推导其他调用已经能够安全读取数据：对其他存储的顺序和可见性仍需相应同步规则。[3] 不能用“原子”两个字代替这项设计，更不能把一个组内屏障当作所有工作组的完成通知。若后续步骤要消费整组或整个派发的结果，应先明确它等的是哪个范围的执行完成，再核查相应存储的可见性。

排查尾组错误时，先分开问三件事：是否只读取有效输入；所有将被读取的共享槽是否已初始化；需要参加屏障的调用是否都沿正确路径到达。修好第一个条件，并不会自动修好后两个。
