# 名称看起来相同，为什么仍然查不到存档

玩家把一个存档命名为“Café”，后来在列表里输入同样的名称，按完整名称筛选却没有结果。文字没有乱码，输入也已被编辑组件接纳；问题可能不是输入法没有提交，而是两边保存了不同的 Unicode 序列。

下面是一个原创、未运行的存档列表例子，面向界面与本地化程序。本文主线讨论**完整显示名是否匹配**，末尾再区分编号标签的显示排序；不实现模糊搜索、账号身份验证或文件系统命名规则。存档本身另有稳定 ID；显示名只是供玩家识别和查找的标签。

## 一个 é，可以是一项，也可以是两项

Unicode 的**码点**是字符编号。带尖音符的小写 é 可以用预组字符 U+00E9 表示，也可以用小写 e（U+0065）后接组合尖音符（U+0301）表示。Unicode 将这两种序列定义为规范等价，而不是说它们恰好在某个字体里相似。[1][2]

本例把保存的标签与后来输入的查询写成码点，差别就清楚了：

| 对象 | 码点序列 |
|---|---|
| 存档标签 A：Café | `0043 0061 0066 00E9` |
| 查询 B：Cafe 后接组合尖音符 | `0043 0061 0066 0065 0301` |

直接逐码点比较，A 与 B 不相等。即使两边都使用同一种 Unicode 编码，单纯更换成 UTF-8，也不会把这两种序列自动变成同一份内容。反过来，不能仅凭截图宣布任意两个相似名称都等价：本例的等价关系来自字符规则，不来自肉眼投票。

**NFC（Normalization Form C，规范组合形式）**是一种 Unicode 规范化形式。对本例两个完整字符串作 NFC 后，都得到第一行的码点序列，再按相同表示比较即可匹配。[1][2][4] 这不意味着 NFC 会把每个可见文字都压成一个码点；没有合适组合或受到组合规则限制时，组合标记仍会保留。

## 先决定匹配政策，再生成用于比较的值

假设产品明确规定：这份列表按完整名称匹配，规范等价的写法应当命中，大小写仍然区分。可以把处理思路写成下面的伪代码；`NFC` 表示符合所选 Unicode 版本的规范化操作，不是让接入者照这个例子手写替换表：

```text
查询键 = NFC(编辑组件已接纳的完整查询)
候选项 = 所有满足 NFC(存档显示名) == 查询键 的存档
显示候选项，并保留每项自己的稳定 ID
玩家选择哪一项，就用那一项的 ID 打开存档
```

这是本例选择的应用政策，不是标准要求所有游戏都如此。两边必须采用同一规则：只规范化查询、不处理已有标签，仍可能匹配不上。若为效率缓存比较键，标签改变时也要更新它；旧数据是否需要重建键，应按实际存储安排处理，而不是擅自改写所有名称。

尤其不要让“匹配相同”变成“存档是同一个”。假设两份原本独立的存档恰好保存了 A、B 两种标签，规范化后会同时命中。列表应保留两项，并用时间、地点等合适信息帮助玩家选择；不能随意取第一项、合并记录或覆盖其中一份。查找规则可以扩大候选集合，不能替产品决定数据所有权或唯一性。

保留显示文字与独立 ID，也让未来修改查找规则时不必改动存档身份。如果某个既有协议已经规定字符串键必须逐码点精确匹配，则应遵守协议；不要在接入层悄悄加规范化，使原来不同的键被合并。

## 逐段处理过，不代表拼完仍然规范

输入可能分批到达。假设先接纳 `Cafe`，后来又接纳 U+0301。前一段单独作 NFC 不变，后一段单独作 NFC 也不变；把两段结果直接相接，末尾仍是 `0065 0301`，而不是完整字符串作 NFC 后的 U+00E9。

UAX #15 明确指出：两段都已规范化，不保证连接后的字符串仍处于同一种规范形式。[1] 因此，本例在建立比较键时处理当前完整的已接纳值，不能把“每个输入回调都处理过”当作整体保证。更复杂的增量实现可以处理拼接边界，但那需要相应算法，不是简单追加已处理片段。

这也不是建议强行改写输入法尚在组字的内容。正在编辑的候选与已接纳文字仍按文本组件的职责处理；比较键是后续查找用途。若在编辑过程中替换字符串，长度和偏移还可能改变，不能把旧光标索引原样套到新串上。本例不提供光标映射或输入法编辑器实现。

## NFKC 不是“更彻底所以更安全”

NFC 保持规范等价关系；NFKC 还处理兼容等价，可能消除原来有意义的差别。例如带圈数字 `①`（U+2460）经兼容规范化成为 `1`（U+0031），而 NFC 不作这种替换。[1][2][4] 若某个关卡标签故意用带圈数字区分样式或含义，不能因为匹配数量变多，就默认这是正确的改进。

规范化也不是大小写折叠、翻译或视觉防混淆。W3C 的字符串匹配说明用不同文字系统中外观相近的 P 形字符说明：看起来相同，不保证会被规范化成同一字符。[3] 所以本例的政策只承诺规范等价写法匹配，不承诺 `Café` 与 `café`、所有相似字形或所有语言里的“同义名字”都匹配。

实际接入时，可保留一小组明确的例子：A 与 B 应同时命中；同名不同 ID 的两份存档都保留；本例区分大小写；若使用 NFC，`①` 与 `1` 不因兼容映射而合并。再检查真实输入、粘贴、读取旧存档和更新标签的路径是否采用同一政策。这些是待执行的检查建议，不是已通过的实现测试。

## 名称已经匹配，列表为什么仍把10排在2前面？

现在同一份列表能找到名字了，却按 `Save 1`、`Save 10`、`Save 2` 显示。若实现逐码点比较，这个顺序并不奇怪：共同前缀之后，字符 `1` 在 `2` 前面，程序没有把连续的 `10` 当成编号十。前面的 NFC 处理解决的是等价写法，不会自动把比较规则改成按编号大小排序。

如果产品希望名称中的编号按数值先后显示，可以选择支持这项政策的**文本排序比较器**。ICU 称之为 Collator；它结合选定语言/地区及选项比较字符串。以固定的 ICU 76.1 接口说明为例，打开 `UCOL_NUMERIC_COLLATION` 后，连续十进制数字按数值比较，因此上述相同前缀例子的编号部分可按1、2、10排序。[5][6] 这不是所有语言都共享的唯一“自然顺序”；其他字母、重音、大小写和标点仍要按项目选定的规则处理。不要为了修这三个名称，就顺便改掉已经约定的完整名称匹配政策。

这里的“数字”范围很窄。该选项处理 Unicode 十进制数字类别 `Nd` 的连续数字串，不把负号、小数点、指数或分隔符一起解释成一个数；带圈数字、罗马数字也不属于这里的数字串。单段还有长度限制：不计前导零，最多254位，超出部分作为另一段处理。[5] 因此，如果另一个列表要按存档里的完成率、游玩时长或带正负号的分数排序，应比较相应的业务数值，而不是先把它格式化成标签，再指望这个选项恢复数值含义。这里没有指定负数标签的实际排列，也没有运行比较器。

接入时先固定这一次排序使用的语言/地区和选项，再比较同一批显示名。比较器认为两项等价时，仍保留两份存档；若产品要求相对次序固定，可另约定稳定的次级顺序，例如按独立ID打破平局。它只是展示策略，不改变原来的存档身份或名称匹配结果。

若后来为减少重复比较而缓存**排序键**，要把它当作某套比较规则生成的派生数据，而不是永久身份。ICU说明，同一比较器生成的键可用于取得与直接比较一致的顺序；不同语言/地区、强度或其他设置生成的键不能混着比较，版本升级后的持久化键也需要重建。[6] 所以切换排序政策时不能只给新存档生成新键、让旧键继续混在其中。没有缓存需求就不必引入排序键；是否值得缓存也不能仅凭这一说明判定。
