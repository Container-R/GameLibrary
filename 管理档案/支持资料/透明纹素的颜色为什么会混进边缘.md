# 透明纹素的颜色为什么会混进边缘

一个完全透明的纹素直接参与普通合成时不贡献颜色，但它保存的 RGB 仍可能先被过滤器读到。若透明区域藏着蓝色，邻近的不透明红色在缩放取样时就可能混入这份蓝。问题不一定出在最后的混合因子：**先混颜色再乘 alpha，与先逐纹素乘 alpha 再混颜色，是两种运算。**

下面只做原创手算，不生成图像，也不运行 GPU。两个输入都是 straight RGBA，已经处于同一个线性 RGB 工作空间；只考虑普通非发光颜色，以各一半的非负权重平均，忽略编码、量化、压缩及图集边界。

| 纹素 | RGB | alpha |
|---|---|---:|
| 不透明红色 | `(1,0,0)` | 1 |
| 完全透明、但藏有蓝色 | `(0,0,1)` | 0 |

## 两条路径，最后乘一次仍不相同

**逐纹素预乘，再平均：** 红色贡献为 `(1,0,0)`，蓝色因 alpha 为零，贡献为 `(0,0,0)`。平均得到预乘 RGB `(0.5,0,0)`，alpha 为 `0.5`。

**先平均 straight，再预乘：** RGB 先变为 `(0.5,0,0.5)`，alpha 同样为 `0.5`；再将 RGB 乘这个 alpha，得到 `(0.25,0,0.25)`。

两行现在都是同一工作域的预乘颜色贡献，可以直接比较；它们不是最终显示器像素。后一行既少了红色，也带入蓝色。最后那次乘法只拿到混合后的颜色与 alpha，不再知道蓝色来自全透明纹素，因此不能单靠乘一次恢复前一行。随后正确进行 source-over，也不会自动改回这段已经混合的输入。

这不是说两种顺序永远不同：若参与平均的 alpha 都相同，或只选中一个纹素，就没有本例的差异。这里也不讨论负权重滤波或特殊图像运算。

## 排查时，把乘法位置追到过滤之前

Porter 与 Duff 的原论文定义了预乘颜色表示。[1] OpenVG 1.1 则提供一个具体接口例：图像插值采用预乘表示，但在图像自身的颜色空间中进行。[2] **这不能证明它默认在线性空间插值，更不能推成所有 GPU 都自动如此。** 本文预先选定线性域，是为了只比较 alpha 乘法的顺序。

接入时应确认：过滤器接收哪种表示、每级缩小图像怎样生成、着色器拿到什么，以及最终混合期待什么。若只在已过滤样本上补乘 alpha，就没有检查到本例的问题；若改为预乘流程，还须保证后续不会再乘一次。

不要据此批量清黑透明 RGB：本例即使把透明蓝改成透明黑，先平均再乘仍只得 `(0.25,0,0)`、alpha `0.5`，没有恢复前一路径的红色贡献。改模式也不是万能修边方案。straight 资产的透明区颜色处理、颜色解码和缩小层级各有约定，应保留原图并核对实际管线。这个反例只解释一种信息混合顺序，不证明任何真实素材已出现或已消除可见边缘。
