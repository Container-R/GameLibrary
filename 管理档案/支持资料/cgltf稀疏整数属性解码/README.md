# 稀疏属性换成四个字节后，读出的为什么不是四个整数

一个模型工具已经能展开浮点标量的稀疏属性。换成每个元素包含四个字节的数据后，它却又遇到两个问题：输出空间到底按“两个元素”分配，还是按“八个数”分配？字节里的64和191，应该保留成整数，还是变成介于0和1之间的小数？

这两件事分别由**元素的分量数**和 **normalized 编码标志**决定。稀疏替换仍然按完整元素进行，不会改变这两个解释规则。这份说明接续[浮点标量的 cgltf 稀疏读取说明](../cgltf稀疏属性展开/README.md)，用固定 cgltf v1.15 的三个小输入检查它们如何组合。它面向读取模型数据的工具程序员，不是完整蒙皮或引擎导入测试。

## 先把两个元素和八个分量分开

本例只有两个 `VEC4` 元素，每个元素包含四个无符号8位整数。整个 buffer 为16字节：

| 字节范围 | 内容 | 用途 |
|---|---|---|
| 0–3 | `[255,0,0,0]` | 密集基底的第0个元素 |
| 4–7 | `[0,255,0,0]` | 密集基底的第1个元素 |
| 8 | `1` | 要替换的元素编号 |
| 9–11 | `0,0,0` | 填充，本例不作为属性读取 |
| 12–15 | `[64,191,0,0]` | 新的完整元素 |

稀疏编号1的意思是“替换第二个四分量元素”，不是“替换输出数组里的第二个数”。因此，密集基底展开后，后四项应由 `[0,255,0,0]` 换成 `[64,191,0,0]`。[1][2]

`cgltf_accessor_unpack_floats` 的容量单位是 float 个数。两个 `VEC4` 需要 **2×4=8** 个 float，而不是2个，也不是32个“字节单位”。本次先查询所需数量，再提供完整的8项输出空间；不测试小容量输出，更不把容量参数理解成任意稀疏输入的安全截断保证。

## normalized 转换的是每个分量，不是整组权重

三个配置共用上面的字节，只改变基底引用和 `normalized` 标志。预期数值在执行前按规范与固定源码写定：[1][2]

| 配置 | 第0个元素 | 稀疏替换后的第1个元素 |
|---|---|---|
| 有密集基底，normalized=true | `[1,0,0,0]` | `[64/255,191/255,0,0]` |
| 无基底，normalized=true | `[0,0,0,0]` | `[64/255,191/255,0,0]` |
| 有密集基底，normalized=false | `[255,0,0,0]` | `[64,191,0,0]` |

对无符号8位规范化整数，转换是逐分量除以255。它既适用于基底，也适用于替换值；不能只转换原数组，却把后写入的64和191原样留下。反过来，`normalized=false` 时，批量浮点接口仍返回 float，但数值应是255、64、191，而不是自动缩放后的值。

无基底配置尤其值得单独看。buffer 前八字节仍然存在，但 accessor 没有引用密集基底，所以第0个元素从零开始；稀疏替换只改第1个元素。**文件里有这些字节，不等于当前属性引用了它们。**

这里没有 `JOINTS`、`WEIGHTS`、mesh 或 skin 对象。无基底配置中的全零元素可以用来检查一般 accessor 的零初始化，却不能因此说它是一组合法蒙皮权重。关节编号映射、跨集合权重总和及资产修复是另外的条件，见[关节编号与权重的读取区别](../glTF关节编号和权重为什么不能按同一种数值读取.md)。

## 固定库实际返回了什么

2026-11-03，首轮按预先冻结的三个配置编译并执行 C 检查程序。三个配置的结构解析、内嵌数据加载、额外验证均成功；容量查询与完整展开均返回8。两个 normalized 配置的替换分量以九位有效数字输出为 `0.250980407` 和 `0.749019623`；它们分别在执行前规定的绝对误差 `1e-7` 内接近 `64/255` 与 `191/255`。其他分量按表中值精确比较。raw 配置保留64和191，零基底配置的前四项为零。[3]

三份输入上的 `cgltf_accessor_read_float` 都返回 false。固定版本的该单元素接口在遇到稀疏 accessor 时直接拒绝；批量展开接口才处理基底与稀疏覆盖。程序没有继续使用失败调用的输出变量。不能把这一 false 解释为输入损坏，也不能忽略返回值继续消费输出。

随后，另一操作者在同一宿主上，用相同冻结包的新副本和新目录重新编译、执行一次。两轮编译与原生进程退出码均为0，编译输出和原生错误输出为空，数值输出逐字节相同。原始输入、工作副本与清单在执行前后核对一致。[3] 这共是两轮、每轮三个相同配置，不是六种配置；也不是独立算法实现或跨平台验证，没有从旧 FLOAT SCALAR 实验借用复跑结果。

三个配置共享同一布局，并不是任意 VEC4、任意稀疏数据的覆盖。这里只接收完整冻结输入、紧密排列的 UINT8 分量和完整输出空间；没有测试交错基底、矩阵、压缩扩展、部分容量、恶意文件或安全验证器，也没有执行蒙皮、引擎导入、GPU 绘制或性能测量。
