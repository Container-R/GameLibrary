# GPU复制完成与顶点数据可读，是同一个条件吗

假设游戏要更新一组顶点：先把准备好的数据放在暂存缓冲区 S，再让 GPU 用 `vkCmdCopyBuffer` 复制到顶点缓冲区 V，随后绘制使用 V 的模型。复制命令写在绘制命令前面，最后 CPU 也等到了这批工作的完成信号，这是否就够了？

还不够。需要解释的不只是“先写了哪条命令”，而是**复制对 V 的写入，怎样成为后续顶点输入可以读取的数据**。这与 CPU 何时能重新覆盖上一帧存储有关联，却不是同一个问题。

这是一个虚构、未运行的接入场景。以下限定 Vulkan 同一条支持图形和传输的队列，合法启用 synchronization2；S 的内容已经正确准备，两个缓冲区的用途、范围、绑定和寿命均合法，没有其他读写或别名访问。复制与屏障在渲染过程开始之前记录，之后的正常绘制从 V 的对应范围取顶点。这里没有另一个信号量依赖来代替屏障，也不涉及跨队列所有权转移。

## 写在前面，不等于已经交给下一用途

Vulkan 的提交顺序让“前面的命令”和“后面的命令”有明确含义，但顺序本身不建立执行或内存依赖。执行依赖回答哪些操作必须先完成；内存依赖还要使相应写入的值对后续指定读取可见。[1]

因此，不能只把 `copy → draw` 排在同一份命令记录里，就认定 draw 会正确读取复制结果。这是一次先写后读的关系，需要覆盖它的适当内存依赖。也不能根据缺少依赖就预言模型一定变黑、一定读到旧值或必定报错；本文没有这样的运行观察。

最后等待这批工作关联的 fence，回答的是主机何时得到相应完成通知。即使等待成功，也不会倒过来为已经提交的 copy 与 draw 补上一条原本缺失的读写依赖。[1] 不能把“这一批结束了”当作“这一批内部的数据交接本来就正确”。

## 屏障要同时说清：哪一步，哪种访问

在这个限定场景中，可以在复制之后、顶点读取之前记录有效的管线屏障。屏障不是“清一下所有缓存”的口令，而是声明前后操作的数据交接范围。

Khronos Guide 的同队列上传示例采用下面这组设置。表格保留其实际使用的宽访问掩码，没有将它改写成更窄掩码后冒称原例：[2]

| 要交接的部分 | 阶段（stage） | 访问（access） |
|---|---|---|
| 复制已经写入 V | `TRANSFER`：传输操作所处阶段 | `MEMORY_WRITE`：该范围内的写访问 |
| 绘制将从 V 取顶点 | `VERTEX_ATTRIBUTE_INPUT`：顶点属性输入阶段 | `MEMORY_READ`：该范围内的读访问 |

这里省略了枚举名称的 `VK_PIPELINE_STAGE_2_`、`VK_ACCESS_2_` 等前后缀，以突出含义；不是可直接粘贴的完整初始化代码。Guide 使用 `vkCmdPipelineBarrier2KHR`，相关功能必须在实际设备和应用中合法可用。

**stage 选择操作所在的阶段，access 选择这些操作中的读写类型。** 宽访问掩码仍受相应同步范围约束，不表示所有未来工作都已安全。尤其要注意，作为顶点缓冲区被读取，发生在顶点属性输入阶段，不应仅因为数据最终进入顶点着色器，就把两者当作同一用途。[1]

按这个例子，完整安排是：复制写入 V，建立覆盖该写入与随后顶点读取的内存依赖，再绘制。屏障并非唯一同步方式；Guide 也讨论了适当信号量依赖可以替代此处屏障的情形。本篇只解释这一条同队列路径，不提供所有同步组合的配方。[2]

## 别把另一条正确上传路径误判成缺屏障

矩阵正文采用的是另一组条件：CPU 普通写入 host-coherent 存储，然后提交读取它的工作。该限定路径利用提交提供的主机到设备交接保证，不需要凭空再加一次刷新或通用屏障。

这里则多了一次 **GPU 对目标 V 的复制写入**。主机已经准备好 S，不等于这次设备写入到后续顶点读取的关系也自动处理好了。排查时应沿实际数据路径找写入者和读取者，而不是看到“上传”两个字就套同一同步步骤。

本支持只作固定来源分析，没有创建 Vulkan 设备、运行验证层、读取 GPU 结果或测量屏障成本。它不覆盖图像布局、跨队列、非 coherent 主机刷新或完整资源管理，也没有借用既有矩阵编译与 CPU 计算结果来证明这条 GPU 路径已运行成功。
