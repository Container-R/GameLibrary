# 辅助保存函数已经成功，为什么外层回滚仍会撤销它

调用者正在保存一整次游戏进度，其中一个辅助函数负责道具数量。辅助函数执行完修改，成功释放自己的保存点，然后返回。调用者却在后续检查中决定取消整次保存。

道具数量应该保留下来，还是随整次保存一起撤销？不能只看辅助函数有没有报错，还要看：**它完成的是外层事务中的一部分，还是整个事务的提交？**

## 同一份数量，三个阶段

以下是原创假设，按 SQLite 文档推导，**不是运行记录**。设表 `save_item` 已提交唯一一行 `id=1、qty=10`，没有触发器或其他修改者，使用支持回滚的日志模式，不使用 `journal_mode=OFF`；所有列出的 SQL 均执行成功。[2]调用者与辅助函数使用同一个连接：

```sql
BEGIN;
UPDATE save_item SET qty = 20 WHERE id = 1;
SAVEPOINT item_helper;
UPDATE save_item SET qty = 30 WHERE id = 1;
RELEASE item_helper;
ROLLBACK;
```

这里，调用者先将数量改为20，辅助函数在自己的保存点内改为30。释放内层保存点后，这些变化仍属于外层事务；最后不带 `TO` 的 `ROLLBACK` 撤销整次事务。[1][2]

| 时点 | 此连接查询数量的推导值 | 辅助函数能怎样解释自己的工作 |
|---|---:|---|
| 开始前 | 10 | 已提交的基线 |
| 调用者修改后、建立保存点时 | 20 | 辅助函数将从这里接手 |
| 辅助函数改为30并释放保存点后 | 30 | 局部操作完成，仍等待外层决定 |
| 调用者回滚整次事务后 | 10 | 外层和辅助函数的修改都撤销 |

这不是辅助函数的修改“突然丢失”。在这个设计里，调用者负责整次保存是否接受，辅助函数只完成其中一段。它可以返回“道具部分已处理”，却不能据此直接向玩家宣布“整次进度已保存”。这项职责划分是接入建议，不是 SQLite 自动认识了游戏里的模块边界。

也不要用同连接能查到30来代替提交判断：上表刻意展示了尚能被回滚的中间值。[4] 原存档正文讨论的是**已经提交**后，备份是否拿到了完整数据库；这里补的是更早的一步，不推翻那个前提。

## 只撤销辅助函数，与撤销整次保存不同

换一个独立选择：仍从已提交的10开始，调用者改为20，建立 `item_helper`，辅助函数改为30。但这次不先释放，而是执行：

```sql
ROLLBACK TO item_helper;
RELEASE item_helper;
COMMIT;
```

`ROLLBACK TO` 撤销保存点之后的修改，但保留目标保存点；所以这里回到20，后续仍可释放 `item_helper`。最后成功提交外层事务，保留的是20，而不是30或10。[1] 这组命令是前一序列的替代结尾，不能接在前面的完整回滚之后执行。

因此，遇到辅助步骤不能接受时，团队要先说明要放弃哪一层：只放弃辅助步骤，还是连调用者此前的修改也放弃。不能把两个名字都含 `ROLLBACK` 的操作当作同一种取消。

## RELEASE 也并非永远不提交

再考虑没有任何活动事务的连接：它直接建立一个最外层 `SAVEPOINT`，修改数据，再成功 `RELEASE`。当这次释放使事务栈清空时，作用就是提交。[1]

所以，不能只看函数末尾写了 `RELEASE` 就判断提交边界。接入约定需要说清它是否要求调用者已经开启外层事务。若同一辅助函数还允许独立调用，也应明确这时谁负责结束事务；不要为了“确保保存”在辅助函数里随意追加整个连接的 `COMMIT`。SQLite 的 `BEGIN` 本身也不能作为嵌套事务入口。[2]

## 局部步骤成功，约束也可能等到提交才检查

前面的数量修改假定每条 SQL 都成功。再加一个不同的教学条件：道具行必须引用已存在的所有者 `owner`，外键声明为 `DEFERRABLE INITIALLY DEFERRED`；连接在事务开始前已启用外键检查，并读回 `PRAGMA foreign_keys` 为 1。以下只按官方文档推导，不是新增运行结果。[5]

假设调用者先 `BEGIN`，辅助函数在内层保存点插入一件道具，但对应的所有者行尚不存在。此时插入和内层 `RELEASE` 可以成功；若缺失关系一直没有补齐，外层 `COMMIT` 仍会因外键约束被拒绝，而且事务继续打开。[5] 因此，调用者不能把“辅助函数返回成功”升级为“整次保存已被接受”，也不能把这次提交失败当成已经自动回滚。

接下来要由调用者决定如何收束。若业务上确实应保存该所有者，可以在仍打开的事务中补齐合法父行，再尝试提交；若不能接受这次保存，则明确回滚。这里的“补父行”只是说明数据库允许的修复路径，不是为了消除错误而凭空创建玩家账号的建议。外键违反对应扩展错误码 `SQLITE_CONSTRAINT_FOREIGNKEY`（787）；这个分类说明失败原因，却不替应用决定修复还是放弃。[6]

还要分清两个相似入口：没有外层事务时直接建立的最外保存点，其 `RELEASE` 要通过与提交相同的延迟外键检查，不能绕过缺失关系；若将本例外键改为即时约束，那么在显式事务中插入这件道具时就会失败，而不是等到最后提交。[5] 保存流程需要分别处理“局部 SQL 完成”“约束允许提交”和“失败后的事务收束”，不要用一个成功标记代替三者。


## 用 Python 接入时，别让包装层改变前提

若用 Python 3.12 `sqlite3` 对照这些序列，要同时看 `autocommit` 与 `isolation_level`。在 `LEGACY_TRANSACTION_CONTROL` 模式下，`isolation_level=None` 允许自行用显式 SQL 管理事务；它不是“SQL 再也不能开启事务”。其他模式不能仅凭同一个 None 推断相同行为。[3]

逐条 SQL 与 `executescript` 也不能随意互换：该 legacy 路径的 `executescript` 会在执行脚本前提交已有事务，可能破坏本例要保留的外层边界。[3] 上面的代码块用来说明操作次序，不是一份可以不检查连接模式、错误和事务状态就直接投产的保存函数。

## 两个连接实际读到了什么

在一组另行冻结的有限观察中，写连接 W 逐条执行操作，读连接 R 每次完成查询并关闭游标，不保留自己的显式事务。三个分支各用新文件数据库，初始化数量均为 10，实际核对 DELETE 日志模式和私有缓存连接。上面的假设说明与下表运行记录分别保留，不把文档推导冒充实验。

| 实际检查点 | W 读到的数量 | R 读到的数量 |
|---|---:|---:|
| A：内层改成 30 并 RELEASE 后 | 30 | 10 |
| A：随后回滚外层 | 10 | 10 |
| B：ROLLBACK TO 后再 RELEASE | 20 | 10 |
| B：随后提交外层 | 20 | 20 |
| C：最外保存点内改成 40，尚未释放 | 40 | 10 |
| C：RELEASE 最外保存点后 | 40 | 40 |

A 最直观地说明了区别：辅助函数释放后，W 确实能查到 30，R 却仍看到旧的 10；之后外层回滚把 W 也带回 10。B 的后续 RELEASE 实际成功，且外层提交留下 20。C 则防止把结论误记成“RELEASE 永不提交”。独立连接看见什么还取决于读取时机、事务与缓存设置，不应把这张顺序表当成任意并发负载下的保证。[4]

主编与独立审查者各执行 1 次，均使用同一环境中的新目录；两轮各 14 个检查点与运行前的字面预期一致。第二位操作者事先知道首轮结果，不是盲复现或跨平台验证。自报 Python 3.12.14、SQLite 3.53.1，只是运行版本信息，不是安装来源或固定 SQLite 源码认证。完整输入、输出和限制见[保存点的两连接有限观察](SQLite保存点两连接/README.md)。这不是断电恢复、WAL、锁竞争、性能或完整游戏保存测试，也没有重用旧备份实验的结果。

## 提交被外键拒绝以后，连接还处于哪一步

另一次有限观察专门补查上述错误路径，不沿用前一组数量表的结果。三个分支各从空的所有者表与道具表开始。道具 `(1,7)` 表示编号为 1 的道具引用所有者 7；父行 `(7)` 表示该所有者存在。W 和 R 都在事务外开启并查询确认外键检查，其他设置仍为显式事务、DELETE、私有缓存、读查询耗尽并关闭游标。

| 本次实际操作 | 写连接 W 的结果 | 读连接 R 的结果 |
|---|---|---|
| A：延迟外键，内层 RELEASE 后再 COMMIT | RELEASE 成功；COMMIT 报787。道具行仍在、父行仍缺，事务未结束 | 两表仍空 |
| A：补入父行，再 COMMIT | 提交成功，父子行都在，事务结束 | 能读到父子行 |
| B：无外层 BEGIN，最外 RELEASE 被787拒绝后，ROLLBACK TO 原保存点 | 回滚到空表成功，事务仍开放；随后 RELEASE 成功结束 | 全程为空 |
| C：同样缺父行，但外键改为即时约束 | INSERT 报787，未留下道具行；事务仍开放，随后明确 ROLLBACK 结束 | 全程为空 |

B 不只是看见一个“事务仍打开”的标志：实际使用同名保存点回滚、再释放都成功。C 则把检查时点前移到插入语句，不能拿它的拒绝时机解释 A。每例都只说明这组明确设置和错误类型，不能推广为磁盘错误、锁错误或任意提交失败的恢复策略。

主编和独立操作者各执行一次，各13个检查点与预先冻结的字面预期一致；同一环境、新目录、新数据库，第二位事先知道首轮结果，非盲或跨平台验证。运行自报 Python 3.12.14、SQLite 3.53.1，不认证安装来源。完整输入、两份输出及限制见[延迟外键的两连接观察](SQLite延迟外键两连接/README.md)。旧14点观察保持原样；两组均未验证业务授权、崩溃恢复或完整游戏保存。
