# 复用保存语句时，为什么上一件道具的数量会留到下一件

程序准备把两件道具的数量分别保存为7和3，读回却发现两件都是7。如果源数据库里已经如此，备份再准确也不能补回本来想写的3。使用 SQLite C 接口复用保存语句时，值得检查：**重新开始执行语句，是否被误认为已经清空了上一次的参数？**

## 语句可以重新执行，参数却还在

预处理语句可以理解为一份已准备好的 SQL，其中的参数位置由程序另外填值。假设本例使用下面的表和一条重复使用的语句：

```sql
CREATE TABLE save_item(id INTEGER PRIMARY KEY, qty INTEGER NOT NULL);
INSERT INTO save_item(id, qty) VALUES(?1, ?2);
```

`?1` 接收道具编号，`?2` 接收数量；程序使用 C 接口的整数绑定把值交给这些位置。[3] 本例没有触发器、额外冲突处理或包装器替程序修改参数。

先绑定 `?1=1、?2=7`，执行第一行。准备保存第二件道具时，对同一个语句调用 `sqlite3_reset`，再把 `?1` 改成2，却漏掉数量绑定。第二次使用的参数会是 `(2,7)`，而不是期望的 `(2,3)`。

原因不在于 reset 没生效。它把语句的执行状态恢复到可重新执行的位置，**不会清除已有绑定值**。[1] 编号变了，数量参数仍保留7；语句成功写入这样的值，并不能证明它符合游戏原本的保存意图。

以上是文档支持的纸面推演，不是运行记录。假定建表、准备、整数绑定及 reset 均已检查成功，第一行执行得到 `SQLITE_DONE`，正常第二行执行也完成；没有借用主文的 Python 备份观察作为 C 接口证据。

## 完整重绑，与清空后漏绑，是不同结果

下面各行是**从第一件道具已写入、语句成功 reset 后出发的替代选择**，不是依次向同一个数据库重复插入编号2：

| 保存第二件之前的处理 | 第二次执行所用参数 | 本例的含义 |
|---|---|---|
| 只绑定编号2 | `(2,7)` | 旧数量仍在，合法数值却不是本次意图 |
| 绑定编号2和数量3 | `(2,3)` | 两个参数都来自本次保存 |
| clear bindings 后，只绑定编号2 | `(2,NULL)` | 数量不满足 NOT NULL，执行失败 |
| clear bindings 后，完整绑定编号2和数量3 | `(2,3)` | 清空后仍由程序提供完整的新值 |

`sqlite3_clear_bindings` 把全部参数设为 SQL 的 `NULL`，并不是设为0，更不是替程序找出本次应该保存的3。[2] 本表的数量列明确要求非空；普通 INSERT 没有改写冲突策略，因此第三种选择会违反约束，不能把这一行也标成“正常执行成功”。[4] 清空和绑定调用仍应检查结果，约束失败则是执行阶段必须处理的失败。

完整重绑所有需要的参数，本身就可以避免本例的旧值沿用，不必把每次 clear 当作强制仪式。反过来，先清空也不能替代完整赋值；如果换成允许 NULL 的列，漏绑甚至可能合法写入 NULL，不能把 clear 当成通用漏绑检查器。

## 查本行值从哪里来，而不只看执行是否完成

接入时可以按每次保存列出参数来源：哪些字段本次必须赋值，哪些确实允许延续，哪些需要明确绑定 NULL。对于这两件独立道具，数量应分别来自各自记录，不能依赖“上一件刚好相同”。

还要检查 reset 的返回码，而非只凭名字认为它一定成功；SQLite 文档说明它也可能报告执行或重置相关错误。[1] 本文没有提供错误恢复循环，也不把 reset 当作回滚已写入行、提交事务或完成备份的操作。

保存完成后的业务读回仍有价值：这里需要核对编号1对应7、编号2对应3，而不只是表中有两行。若源值就错了，先修写入参数；若源值正确而备份缺失，再回到主文的备份路径。本文没有调用数据库或运行 C 程序，也不将这一直接 C API 行为无条件推广到 Python、ORM 或引擎包装器。
