# 同样十件材料，分两次兑换为什么少了一枚金币

玩家用十件材料兑换金币，一次全交能拿15枚；分成两次、每次交五件，却只拿到14枚。两次请求都有不同编号，材料没有重复扣除，账本也完全对得上。问题不在重复发奖，而在**哪一步舍去了不足一枚的部分**。

下面只讨论虚构的单机兑换：材料和可用金币都以整数计数，每件材料固定换 `3/2` 枚金币，没有手续费、数量折扣、兑换上限、玩家交易或真实货币。所有数字是纸面例，不是某款游戏的行为。

## 规则不能只写“每件换1.5枚”

如果规定“每次兑换先按材料总数算金额，再向下取整，舍去的部分不保留”，五件材料就是：

```text
5 × 3/2 = 7.5
向下取整后发7枚
```

这里的向下取整是取不大于原数的最大整数，即 `floor` 的含义；并非所有“取整”都采用同一方向。[1]

于是两种操作得到：

| 交付方式 | 每笔实际发放 | 最终新增金币 |
|---|---|---:|
| 一次交10件 | floor(10×3/2) | 15 |
| 分两次各交5件 | floor(5×3/2)，再floor(5×3/2) | 7＋7＝14 |

两次各舍去半枚，最终相差一枚。这不是必须由二进制浮点误差才能造成的问题；即使用精确分数计算，**先分别取整再相加，与先相加再取整，也不是同一个运算**。

反过来，如果每笔向上取整，两次各五件会各拿8枚，共16枚，而一次十件仍是15枚。向上取整 `ceiling` 取不小于原数的最小整数。[2] 因此，不能只把函数换成另一种方向，就宣称拆分问题解决了。

## 账本正确，不代表兑换规则没有意外激励

游戏资源系统既涉及产生和消耗，也涉及一种资源向另一种的转换。[3] 对这里的转换，要分别看材料去了多少、金币来了多少，以及规则希望玩家怎样选择批次。

若两次都确实扣了五件、各发七枚，账本如实记录这两笔，仍然可能完全自洽。幂等检查也不应把第二笔拦住：它是另一笔真实兑换，不是第一笔请求的重试。

此时应由设计者先决定：批量兑换是否本来就应该影响回报？如果差异是有意的，需要在说明和预览中表达清楚。如果本来希望“总材料一样就得到一样的回报”，那么取整时机已经改变了规则，不能把它归咎于玩家分批点击。

分组结果不同也不自动等于无限套利。本例向下取整使拆分少拿钱，向上取整才会让拆分多拿；材料仍被消耗。是否存在可反复获利的循环，还需要其他兑换路径和条件，本文没有建立那种系统。

## 想保留零头，就把零头也当作状态

一种可选规则是：不足一枚的部分不立即丢弃，而是留到下一次同类兑换。对固定 `3/2` 比例，可以用“半枚金币”为内部计算单位，不需要先把整数金币余额改成小数。

设 `r` 表示此前留下的半枚单位数，只可能是0或1；本次交 `n` 件材料：

```text
待结算的半枚单位 = 3×n + r
发出的整枚金币 = 待结算单位除以2的整数商
新的r = 除以2的余数
```

从 `r=0` 开始，第一次交五件得到15个半枚单位，发7枚，留下 `r=1`。第二次再交五件，共有 `15+1=16` 个半枚单位，发8枚，余数回到0。两次合计15枚，与一次交十件相同。

这并不是把第一次的奖励偷偷改成8枚，而是明确保存了第一次未发出的半枚。每笔都满足：

```text
2×本次发币数 + 新余数 = 3×本次材料数 + 旧余数
```

在固定比例、同一份余数持续保留的前提下，把多笔等式相加，中间余数会抵消；总发币数与最后余数便只取决于总材料数和最初余数，而不是如何分批。这是本例的代数推导，不是存档实现已经可靠的证明。

如果退出游戏时丢了余数，或者每个新请求都把它重置成0，就又回到了分批丢零头的规则。材料扣除、金币发放和余数更新应按同一次业务变化处理；重试也不能再消费一次余数。具体的持久化与幂等问题仍见主文，不因多存一个字段就自然解决。

这个办法也不是通用兑换引擎。比例改变、退款、负数输入、上限、费用或多种货币，需要重新定义余数归属及处理方式；实际整数乘法还必须检查表示范围，不能把纸面算式当成不会溢出的代码。

## 在调价格之前，先比较这些操作

测试同一批材料时，除了“金币算得对不对”，还应比较一次兑换、不同拆分、连续兑换后重开，以及同一请求的重试。分别问清楚：哪些结果应一致，哪些是有意不同，留下的零头到哪里去了。

不要为了追求一致就默认保留余数是唯一正确答案。固定兑换包、明确的逐笔舍弃，或者更细的内部计量单位，都可能是设计选择。关键是规则、预览、实际发放与保存状态讲的是同一件事，而不是只在表格里写一个小数倍率。
