# 提前做完一项任务，为什么试玩日期没有跟着提前

提示图提前一天画完了，团队却还是要等到原定时间才能试玩。这个结果不一定说明美术的努力没有价值：如果另一路必须准备好的工作还没结束，合并后的交付就仍在等它。

制作排期要看的不是孤立的“谁省了一天”，而是从当前输入到目标交付的整条依赖。下面沿用机关提示的虚构情境，只讨论固定时长、资源充足时的先后关系，不把纸面数字当作真实估工。

## 先画清楚谁必须等谁

假设提示意图、状态和资源规格已经确认。美术可以画最终提示图，程序可以用占位图准备状态逻辑；两份工作都完成后，才进行最终整合和检查。

| 工作 | 持续时间 | 开始前必须完成 |
|---|---:|---|
| A：制作最终提示图 | 3个工作日 | 已备齐输入 |
| B：准备提示状态逻辑 | 2个工作日 | 已备齐输入 |
| C：整合最终图像与状态逻辑 | 1个工作日 | A和B |
| D：检查这份整合结果 | 1个工作日 | C |

A与B由不同且可完整投入的人员承担，不争用设备；所有工作使用同一工作日历。除此之外没有审批等待、额外日期约束、切换损耗或未列出的必要工作。后续工作必须等前项完成才能开始，检查也暂按无需返工处理。

A和B可以同时开始，却不能把四个时长直接相加，也不能只取最长任务的3天。整合要等两路都结束，因此从共同起点算：

```text
最早完成时间 = max(3, 2) + 1 + 1 = 5个工作日
```

**关键路径**在这个简化计划中是 A→C→D，总长5天。B→C→D共4天，暂时不是决定终点的最长路径。检查D虽然只有1天，但它在关键路径上；判断一项工作是否影响终点，不能只按它自身的时长排序。[1]

## B晚一天与晚两天，是两种后果

如果只有B的开始时间推迟1天、持续时间仍为2天，它在第3个工作日结束，C仍能在两路齐备后按原安排开始，终点仍是第5个工作日。

若B推迟2天开始，则到第4个工作日才结束，C和D都得跟着后移，终点变成第6个工作日。A没有变慢，但决定完成时间的路径已经转向B这一侧。

本例B有1个工作日的**总浮动时间**：在其他条件不变时，它可以延迟这么多，而不推迟所研究的终点。这里的终点是D完成，不是商店发行、整个游戏完工或任意一个更早的内部交接。[1]

这个数字不是独立发给每项工作的假期。如果把B的2天拆成前后相连的两个1天子任务，这两项都可能显示1天总浮动，但共享的是同一份1天空隙。前项已经用掉1天，后项再独自多拖1天，仍会把整条支路推迟2天，最终影响交付；不能把两个“1天”相加，宣称团队多了2天缓冲。[1]

## 把关键工作再缩短一天，也不一定继续见效

回到原计划。若A从3天缩成2天，B仍为2天，结果是：

```text
max(2, 2) + 1 + 1 = 4个工作日
```

这次确实提前了一天，但两条支路现在一样长。若仅把A再缩成1天，B不变：

```text
max(1, 2) + 1 + 1 = 4个工作日
```

终点不会再提前。若目标仍是提早完成，就需要重新看B或后续C、D是否有合理的改进空间，而不是一直催促已经不再决定汇合时间的A。减少时长也必须有真实做法支撑，不能靠删掉必要检查让表格变短。

GAO排程指南特别提醒，关键路径会随工作提前、延误和依赖变化而改变，重要工作或长任务并不因此自动属于关键路径。[1] 所以要比较的是更新后的整张计划，而非一直沿用上周标红的任务名单。

## 浮动时间不是对发布日期的保证

上面的5天只在明确列出的假设下成立。若同一个人要同时完成A和B，或者D发现问题后必须返工，就已经不是这张简单网络。主文中关于人员容量和不确定性的讨论仍然适用。

实际工具还可能加入固定日期、多种日历和资源平衡规则；此时不能见到“总浮动为零”就脱离上下文认定它一定是推动最终交付的那条路径。[1] 先核对真正需要的输入是否漏了、依赖是否正确，以及浮动究竟计算到哪个目标节点。

把计算带回沟通时，可以问得更具体：这项工作延迟会先影响谁？对方是否仍能按原时点开始？如果我们投入人手提前它，目标交付是否真的前移？这些问题比单独汇报“又完成了一个任务”更能帮助团队判断该在哪里行动。
