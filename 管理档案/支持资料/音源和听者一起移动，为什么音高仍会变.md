# 音源和听者一起移动，为什么音高仍会变

设想玩家与身旁的机器一起向前移动，双方距离没有改变，机器声却出现了不希望有的音高变化。先别重新导出素材：游戏里的运动，与音频接口实际收到的运动信息，可能不是同一回事。

下面只用 OpenAL 1.1 的接口约定解释一种可能原因，并做纸面计算。它不是已发生的项目故障，也没有播放、录音或听感测试。

## 位置跟上了，不代表速度也交对了

OpenAL 将位置与速度作为独立输入，不会从连续位置更新推算速度。声源与听者的速度默认都是零。[1] 因此，接入者需要查实际交给接口的状态，而不只是看画面里机器是否跟着玩家走。

实际引擎或封装层可能替项目计算速度。应先找到负责这一步的代码或配置，再决定哪里需要修改，不要未经检查又补算一遍。

## 用同一段移动，比较两份提交状态

本例选世界坐标模式 `AL_SOURCE_RELATIVE=false`，将多普勒系数 DF 固定为1，声速 c 固定为343.3米/秒。假设使用单声道素材，其他音高控制保持不变；这里只计算多普勒因子，不计算最终混音。

只看 X 轴，其他坐标为零。开始时机器在0米，听者在10米；一秒后分别在30米、40米。两者都向正 X 方向以30米/秒移动，听者始终在机器前方10米。

多普勒效应在这里表示运动造成的频率倍率。OpenAL 的计算使用两份速度在“声源指向听者”方向上的投影；将听者、声源的投影分别记作 vL、vS。在本例的低速范围内：[1]

```text
频率倍率 = (c − DF × vL) / (c − DF × vS)
```

本例的投影方向就是正 X。正确提交时，vL与vS均为30：

```text
(343.3 − 30) / (343.3 − 30) = 1
```

现在只改一件事：机器的速度仍提交30，听者的位置照常更新，但它的速度漏掉了，仍为0：

```text
(343.3 − 0) / (343.3 − 30)
= 3433 / 3133
≈ 1.095755
```

两种情况的画面可以一样，交给公式的输入却不同。后一结果约比原频率高9.58%；这只是上述状态的数学结果，不是实测输出，更不能据此保证玩家一定听得出差别。

## 排查时，把两端放在同一张记录里

可以请接入程序员记录同一次更新中的声源位置、听者位置、两端速度，以及这些值各由谁产生。对照上面的简单移动，先检查是否漏了一端、读到了旧值，或者使用了不同的坐标约定。这里提出的是待执行的排查步骤。

速度的单位应与声速一致。[1] 因此不要只看数字大小，交接时应写清每个量的含义。本例特意采用米和米/秒，便于检查一秒内的移动。

这份计算限定为非零间距、远低于声速、世界坐标模式。不要拿它处理重合位置、瞬移、接近声速或相对听者模式，也不要把一个接口的约定推广成所有引擎的行为。修好这两份输入后，仍需回到项目自己的素材与配置检查；若音高异常仍在，再寻找其他原因。
