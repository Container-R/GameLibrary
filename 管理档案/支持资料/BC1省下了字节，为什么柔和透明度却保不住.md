# BC1省下了字节，为什么柔和透明度却保不住

一张带柔边的贴图改用 BC1 后，尺寸没有变，数据量也符合预算，边缘却不像源图了。先不要用调整混合因子来补偿：压缩后的纹素是否还保存着原来的透明度，是更早一步的问题。

BC1 每个 4×4 块占 8 字节，但这 8 字节并不是给十六个纹素各存一份完整 RGBA。它保存两个颜色端点，以及每个纹素选择哪个候选颜色的短编号。带透明度的模式只给纹素提供全透明或全不透明两种 alpha，不直接保存源图的 `0.2、0.6` 等柔和数值。[1][2]

## 看一个块，就能知道透明信息去了哪里

这里构造一个解释用的小块，不运行压缩器或 GPU。两个端点采用 RGB565：红、绿、蓝分别占 5、6、5 位。令第一个端点 `c0=0x0000`，第二个 `c1=0xFFFF`，即黑与白。十六个纹素各用两位编号选择候选值；只看第一行，编号依次为 `0、1、2、3`，其余行不影响这四格的解释。

模式比较的是两个打包后的 **16 位无符号整数**，不是颜色亮度。由于本例 `c0<=c1`，它属于三色模式：编号 0 和 1 选择两个端点，编号 2 选择逐颜色分量的中间值，编号 3 则留给特殊值。[2]

| 第一行的编号 | RGB 含义 | 按 OpenGL 的 RGB DXT1 格式解释 | 按 OpenGL 的 RGBA DXT1 格式解释 |
|---|---|---|---|
| 0 | 黑端点 | 不透明黑 | 不透明黑 |
| 1 | 白端点 | 不透明白 | 不透明白 |
| 2 | 两端点的中间灰 | 不透明灰 | 不透明灰 |
| 3 | 黑 | 不透明黑 | 全透明黑 |

这里故意不规定中间灰最终落到哪一个整数码值；重点是最后一格。同一份块数据，在这两个 **明确不同的 OpenGL 内部格式**下，最后一格的透明含义不同。不能只看到文件里是 DXT1 数据，就省掉接入端的格式核对。[2] 这个接口例也不意味着所有图形 API 都用同样的枚举名称。

若 `c0>c1`，则采用四色模式：另外两个候选颜色由端点作三分之一、三分之二插值；这里没有为编号 3 留出透明含义。等于的情况属于前面的三色分支，不能把条件误写成严格小于。颜色插值逐分量进行，不能直接对打包整数插值来代替颜色运算。[1][2]

## 过滤出的半透明，不等于源图的半透明被保存了

带 alpha 的 DXT1 解码纹素只有 0 或 1，并不表示后续采样结果永远只有这两个值。过滤器若组合透明和不透明纹素，仍可能得到中间 alpha。但它组合的是**已经压缩、解码之后的值**；这个中间结果不是源图每格原有透明度的存档。

例如，某个源纹素本来需要 alpha `0.6`，把它映射成 1 后，单独读取该纹素不会自动变回 `0.6`。邻近位置过滤得到恰好 `0.6`，也不能证明原来的渐变被完整保留。实际编码器如何选择透明阈值、是否调整内容，需要查具体工具；不能把某个 API 的编码规则当成所有离线压缩工具的默认设置。

另外，RGBA DXT1 的透明编号同时解码为黑色 RGB，无法在这个编号里继续保存“全透明但 RGB 是红色”这样的隐藏颜色。[2] 若管线下一步还依赖这些颜色作处理，应检查格式本身是否适合，不能期望改个标签或在着色器里除以 alpha 找回它们。

## 调整资产前，先确认是哪一种损失

对需要连续透明度的柔边图标、烟雾或渐变，先查看目标平台导入后的实际格式，以及解码后代表纹素的 alpha，再决定是否换用能表达更多 alpha 级别的格式；不能只看源文件仍有四通道。对本来就用透明裁剪的叶片，二值透明可能符合用途，但仍要检查轮廓、较小 mip 和最终取样表现。本文没有比较任何真实素材的压缩质量，也不把某一种替代格式指定为所有平台的最佳选择。

若 alpha 的表示已经丢失，改预乘混合不能恢复它；若信息仍在，却在过滤或混合时接错，才该沿着那条管线检查。可接着读[预乘透明度与普通透明度的混用问题](../../GameLibrary/技术美术/环境管线/纹理与材质/预乘透明度与普通透明度的混用问题.md)，区分编码能力与后续运算。两者都可能影响边缘，但不是同一个故障。
