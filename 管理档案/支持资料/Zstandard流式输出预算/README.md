# 输出缓冲只有8字节，为什么仍要单独判断整份资源能否接受

加载器不断把解码器写出的内容搬进候选资源。每次只能写8字节，看起来很克制，但候选资源的累计大小还在增长；即使库说“这一帧结束了”，游戏也可能已经不能接受它。下面用很小的原创输入，观察这两个判断怎样分开，而不是把64KiB缓冲或真实关卡带进测试。

## 三个输入，三个不同的交付结果

本次实际调用固定 **Zstandard v1.5.7** 的原生 C 流式解码接口，每次输出空间8字节，应用累计接纳预算32字节。输入是按固定格式自行构造的 raw-block 帧：块内直接存放原文字节，没有运行压缩器。前两个是32/33字节内容的完整有效帧；第三个只从32字节版本末尾删去一个载荷字节，块头仍写着 Block_Size=32。

三份输入都没有帧内容尺寸字段，查询结果均按 harness 断言为 `ZSTD_CONTENTSIZE_UNKNOWN`。这里的“块长32”不是帧头 FCS 声明；也不能把未知尺寸本身当作损坏。[1][2]

| 输入 | 本次实际产出与暂存 | 库是否完成一帧 | 应用是否接受整份资源 |
|---|---|---|---|
| 32字节完整帧 | 产出32，接纳32；41字节输入全部消费 | 是 | 是，字节与预先固定的原文一致 |
| 33字节完整帧 | 产出33，只接纳前32；42字节输入全部消费 | 是 | 否，最后1字节超过预算，拒收新块并放弃候选资源 |
| 32字节块缺末字节 | 产出31，暂存31；现有40字节输入全部消费 | 否 | 否，输入已尽但帧未完整，不能发布前缀 |

这里的“接纳”只指进入候选缓冲，不等于资源已经发布。第二例最能说明边界：第五次调用既产出了最后1字节，也返回了帧完成；库并没有出错，应用仍必须执行自己的32字节政策。第三例则说明，所有现有输入都被消费，只代表手头没有更多字节，不代表它原本就是一个完整帧。

另一个容易误判的细节是：R32的第二、第三次调用中，输入位置都停在40，但每次仍产出8字节。处理仍在推进，不能仅因输入位置未增加就判为卡死；这不等于对所有内部缓冲路径作了验证。

表中32/31及调用分割是这份固定输入的实际轨迹，不是接口对所有帧的分块保证。原始明文、每次产出和候选前缀均与事先写定的明文字节 比较，没有用解码结果反过来生成预期。

## 接入加载器时，分别保存哪几个判断

先分清库此次产生多少、应用已接纳多少、帧是否完成，以及输入是否按项目容器规则完整消费。不能拿库的正返回值当产出字节数，也不能在某次缓冲写满或额度用满时直接宣布成功。[1]

本例每次重新把输出位置设为0，因此调用后的输出位置才是此次产出。接纳新块以前，先确认旧累计值未超预算，再比较新块是否大于剩余额度。超额时整块拒收，不自动截成“刚好凑满额度”；即使已经暂存了一个正确前缀，也不把它交给关卡。

这是一份具体观察，不是完整加载器。项目还要定义允许几个帧、如何处理剩余输入、错误后的清理和资产格式验证。本次没有测试拼接帧、字典依赖、复杂压缩块、窗口上限、真实资产、内存峰值或性能；不能把 raw-block 路径的三个结果推广成全部解码路径保证。旧支持文中的16MiB/64KiB仍是纸面算术，旧包与同名字典仍是未执行的交付情境。
