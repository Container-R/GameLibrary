# 目录监视返回成功，为什么资产索引仍会漏更新

资产工具可以靠文件变化通知，只重新解析改过的内容。但如果通知详情已经丢失，一次成功返回就可能让旧索引继续冒充当前状态。危险的不只是界面显示旧名字：清理工具可能据此判断某个脚本“没有引用者”，虽然刚保存的门对象已经在使用它。

下面用 Windows 的 `ReadDirectoryChangesW` 说明一个具体分支，再把它接回资产关系查询。这是独立的接入反例，不描述 Horizon 的内部实现；门与脚本的序列是原创条件推演，尚未执行。

## 先明确这里读取的是同步结果

假设工具已成功取得一个本地目录句柄，具有 `FILE_LIST_DIRECTORY` 权限，打开目录时使用 `FILE_FLAG_BACKUP_SEMANTICS`。本例不使用 `FILE_FLAG_OVERLAPPED`，调用时 `lpOverlapped` 和完成回调均为空，输出缓冲按 DWORD 边界对齐。

为缩小问题，只监视该目录内的文件，不包括子目录：`bWatchSubtree` 为假，过滤器选 `FILE_NOTIFY_CHANGE_FILE_NAME | FILE_NOTIFY_CHANGE_LAST_WRITE`，分别覆盖所选的文件名变化与最后写入时间变化。这个范围不是整个项目、任意属性或被监视目录本身的变化。最后写入时间变化的检测还受实际写盘和缓存刷新影响；本例不据保存结束承诺通知已经全部到达。[1]

在这条**同步**路径上，非零 BOOL 表示操作成功，`lpBytesReturned` 才是写入结果缓冲的字节数。Microsoft 文档明确说明，通知缓冲溢出时可以丢掉全部详情，仍返回成功和零字节。因此，“成功而没有记录”不能解释成“目录没有变化”。但也不能反过来只凭零字节断言一定溢出：文档还列出了缓冲过大、系统无法分配的情况，并要求通过枚举目录或子树计算变化。[1]

另有一条需要分开处理的失败路径：返回 FALSE 后取得 `ERROR_NOTIFY_ENUM_DIR`，表示系统未能记录全部变化，文档同样要求枚举。它不是刚才那次成功返回附带的错误；不要在成功后读取遗留错误值，给零字节编造原因。异步调用更不能套用本例：非零 BOOL 只表示排队成功，`lpBytesReturned` 在异步调用中未定义。[1]

## 一条丢掉的更新，怎样变成错误的“无引用”

把关系索引想成一张很小的表：初始记录是 `Gate.core → Old_Logic.core`。门的内容明确引用旧脚本，索引也已正确提取这条边。

随后发生一次有限批处理：创建 `New_Logic.core`，把门的链接改指新脚本，并删除旧脚本。同批还有其他变化。现在假设通知详情已丢失，下一次同步调用成功返回零字节。这里没有规定能诱发该结果的操作数量或缓冲尺寸，也没有声称观察过它。

错误处理很容易写成：“调用成功，记录数是零，保持索引不变。”于是，门仍被记成引用旧脚本，新脚本没有引用者。即使另一个工具从磁盘列表中发现新脚本，也可能因查询这张旧表而将它列入清理候选。索引查询本身可以很快、没有报错，结论却已经缺少依据。

更合适的应用策略是：**把受监视范围的增量记录视为不完整，先停止用旧索引证明‘没有引用’。** 这是根据资产工具用途提出的恢复要求，不是 Microsoft 提供的资产数据库算法。

## 枚举找回文件集合，内容提取找回关系

为了单独观察这个区别，先假设上述批处理结束后不再有写入。恢复至少要完成两件不同的事：

1. 枚举同一个受监视目录，与旧清单对照。这个例子中，待核对的结果是新脚本存在、旧脚本不存在，索引不能只追加新文件而保留已删除的旧条目。
2. 重新读取门的相关内容并提取链接，更新关系。只得到文件名列表，还不知道门已从旧脚本改指新脚本；旧边应被替换，新脚本应能查到门这个引用者。

不能只重做仍然拿到通知的那几个文件，因为缺失的详情恰好可能属于其他文件。实际恢复策略必须覆盖失去记录的监视范围；若枚举、读取或解析失败，结果仍应保持待恢复，不能把“扫过一遍”当作关系已经完整。

现实中的工具通常不能假设大家停止保存。扫描期间又有新增、改写或删除时，如何接续后续变化、处理再次丢失并发布新基线，需要另外设计和验证。这里的 API 文档要求枚举恢复变化信息，并没有替应用提供一个无竞态的一致快照协议。上面的静止假设只是为了看清错误，不是生产环境保证。

增大缓冲也不能追回已丢掉的详情。文档还规定，系统的通知缓冲在首次调用时分配，容量在同一目录句柄的生命周期内固定；不能把下一次调用的长度调大，就认定该句柄的历史缺口已经补上。[1]

对资产工具来说，可迁移的检查点很具体：监视完成了吗、变化详情足够吗、文件集合恢复了吗、关系重新提取了吗，是不同的问题。恢复时可能要额外读取内容，并不否定正常查询由索引回答的价值。本例没有实现完整恢复算法，也没有运行 Windows 监视器、资产索引或性能测试。
