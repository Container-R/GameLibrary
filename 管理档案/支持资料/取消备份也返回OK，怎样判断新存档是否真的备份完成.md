# 取消备份也返回OK，怎样判断新存档是否真的备份完成

道具数量已经从 3 变成 7，程序开始把新存档备份到一个原本保存着数量 3 的目标数据库。复制刚进行一部分，玩家按了取消。程序调用 `sqlite3_backup_finish`，返回 `SQLITE_OK`。

这个 OK 能不能让界面显示“数量 7 已备份”？**不能。收尾没有报告错误，并不表示这次复制已经完成。** 本文用一组直接调用 SQLite C 接口的有限观察，把这两个结果分开。

## 两个OK，目标却是两份不同进度

两条分支各自使用新的源和目标，不是先完成备份、再拿同一个目标测试取消。每支开始前，都关闭创建连接并重新打开，确认源为数量 7，目标为数量 3。源包含固定填充数据，使数据库有 18 页；每次只请求复制 1 页。

| 接入选择 | 实际 step 结果 | finish 返回值 | finish、关闭连接后，新只读连接查到的目标数量 |
|---|---|---|---|
| 继续至完成 | 共 18 次；前 17 次 OK，末次 DONE，剩余 0 页 | OK（0） | 7 |
| 提前取消 | 仅 1 次，OK，仍剩 17 页 | OK（0） | 3 |

这里的 `SQLITE_DONE` 数值为 101，`SQLITE_OK` 为 0。观察中的两个 finish 都返回 0，但只有第一条分支先得到过 DONE，目标读回也符合这次新进度。

第二条分支并不是得到一份“完成了十八分之一的新存档”。SQLite 的接口约定是：如果尚未完成复制就调用 finish，目标上仍活动的写事务会回滚。[1] 本次目标原本已提交数量 3，取消后另开连接仍读到 3。这个读回很重要：不能只凭 finish 的返回值替目标内容作保证。

## 界面应该保留什么判断

接入者可以把三个问题分别记下来：

1. **复制到终点了吗？** 保留 step 是否真正返回 DONE，不把某次 OK 当成完成。
2. **收尾成功了吗？** finish 的结果仍需处理，但它不能覆盖“这次已取消”的状态。
3. **候选里有本次业务内容吗？** 结束目标写入后，重新打开候选，核对本次预期。本例是唯一道具 `id=1` 的数量 7；真实存档还要检查自己承诺保存的任务状态或版本。

因此，取消分支适合显示“已取消本次备份”，而不是“新备份已保存”；旧值仍存在也不等于新进度已经备份。完整分支则有 DONE、正常收尾和目标业务读回三份不同依据。若只保存一个最后返回码，恰好会把这个区别抹掉。

不要为了刷新界面，在备份尚未 finish 时查询目标连接。官方限制从成功初始化到对应 finish 期间，不得把目标连接用于其他 SQLite API；即使已经得到 DONE，也先 finish，再读回。[1] finish 以后备份对象失效，不能拿它继续 step。“暂停后继续”与“结束并取消这次复制”需要不同处理。

这个例子为便于观察，直接使用一个有旧值的测试目标；它不是覆盖唯一可恢复备份的产品建议。实际接入仍应按[原文](../../GameLibrary/引擎与工具/运行时系统/缓存与存档/SQLite%20存档已经提交，为什么只复制数据库文件还会漏掉进度.md)保留候选和原有可恢复副本。

## 这次实际验证了多少

本库已完成作者与独立操作者各 1 次执行：两次在同一宿主、相同固定输入下分别使用新目录，从官方 SQLite 3.50.4 源码编译 C driver。两轮编译和运行返回码均为 0，编译标准输出、标准错误及运行标准错误均为空，两份技术输出与结果摘要逐字一致。上表来自实际输出，不是纸面序列。独立操作者已知作者结果，因此不是盲复现，也不是跨机器或独立算法实现。

本次使用单线程构建、4096 字节页和 DELETE 日志模式，无并发写入。旧文中 Python `Connection.backup` 与 WAL 主文件复制的观察保持原样；那组记录已观察过分步进度及目标读回，本次新增的是**直接取得 C finish 返回值，并在未完成时主动收尾，再检查旧目标内容**，不把旧观察重新算成新的 C 试验。

这不是崩溃或断电试验，也不检验 BUSY/LOCKED 重试、多个文件的一致性、云同步或通用恢复可靠性。目标正常重新打开可读，不等于任何故障下都能恢复。

### 附录：输入和检查的边界

源和目标都只有一张 `save_item` 表、一行 `id=1`。源为数量 7 加 65536 字节零 blob，目标为数量 3 加零长度 blob。读回不只比较数量，还检查精确表结构、唯一行、blob 类型、长度与零字节内容。填充只是确保这次复制确实分步，不是性能负载。

输入固定后，runner 先核源码和协议摘要，复制到新目录后再次核对；使用隔离的环境变量目录和有界编译、运行时间。预执行审查曾拒绝初版 runner 的子进程清理与目录防护方案，修改并重新审查后才执行。这是运行工具的准备修订，不是一次 SQLite 备份失败，也没有失败后换数据重跑。超时清理本身没有经过本次实验实测；POSIX 进程组清理和目录限制不是完整安全沙箱。

协议、输入摘要、C driver 和两轮技术输出见[分步完成与取消的有限观察](SQLite备份提前收尾/README.md)。源码不随包转载，复现者按固定官方地址取得原件并核验；不以系统里任意一个同名库替代。
