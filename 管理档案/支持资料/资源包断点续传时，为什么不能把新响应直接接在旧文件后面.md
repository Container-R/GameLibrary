# 资源包断点续传时，为什么不能把新响应直接接在旧文件后面

试玩包下载到一半断了。下载器记住“已经收到4字节”，重新请求同一地址的剩余部分，最后文件长度也对得上。可是解包失败了：前半段属于昨天的包，后半段属于今天的包。

这个假设问题不是构建没成功，而是**下载器把地址相同误当成了两段内容属于同一份文件**。下面面向自行接入 HTTP 下载与续传的工具程序员，解释接收响应时要做的判断。不是某款引擎下载器的故障报告，也不建议绕过已有资源系统另造下载器。

本文只讨论单个资源、连续前缀、单段字节范围，假定示例中的响应没有内容编码变换。依据 RFC 9110 作纸面推演；没有启动服务器、发送这些请求或执行网络实验。

## 长度对得上，内容仍可能是拼出来的

用10个 ASCII 字节代替实际的大包，每个字符恰好占1字节。两版内容分别是：

```text
候选 A：ABCDEFGHIJ
候选 B：1234567890
```

下载中断前保存了 A 的前4字节 `ABCD`。HTTP 字节位置从0开始，所以接下来想要的是位置4及之后的内容，即 `Range: bytes=4-`。[1]

如果地址已经改为提供 B，而请求只表达位置，没有约束两次响应的表示身份，便可能收到 B 的后6字节 `567890`。机械追加会得到：

```text
旧前缀 ABCD + 新后缀 567890 = ABCD567890
```

它也是10字节，却既不是 A，也不是 B。检查长度能够发现某些截断，不能排除这种混合。这里的字符串是原创示意，不是一个真实可解包的文件。

HTTP 所说的**表示**，可以理解为这次请求选定、要传输的具体数据形式。同一地址的内容会更新，也可能有不同编码形式。续传需要把本地前缀与它所属的表示关联起来，而不只是保存文件名和偏移量。

## 用 If-Range 表达“没变就续，变了就重新给”

假定最初 A 的响应提供了正确的强 ETag `"pack-A"`，下载器把它与前缀一起保留。ETag 是服务器提供的不透明校验标记；这里的名称只是示意，不要求它等于文件摘要。

续传请求可以带上这两项：

```http
Range: bytes=4-
If-Range: "pack-A"
```

`If-Range` 的意思是：表示仍匹配时，处理所请求的范围；不匹配时忽略 Range，按正常请求处理。[1] 对这里其余条件正常的 GET，后者可以给出新表示的完整响应，而不是原来期待的尾段。因此，**发出了 Range，不等于收到的一定是可追加的206响应。** 服务器也可以忽略 Range；先前见过 `Accept-Ranges: bytes` 不是未来每次都部分返回的保证。

用于该条件的 ETag 不能带弱标记 `W/`。强弱不是“摘要算法够不够高级”：弱标记允许不同字节被视为适合某些用途的等价内容，而拼接部分字节需要更严格的同一表示条件。不能自行删掉 `W/` 冒充强标记，也不能把普通版本名塞进 If-Range 当作服务器认可的 ETag。规范另有日期形式的条件，本文不采用它，不把任意 Last-Modified 日期当作强校验器。

这项机制仍依赖对端正确提供和处理校验器。它不是来源认证；相同 ETag 也不应拿来比较两个不同资源是否逐字节相同。

## 收到200还是206，决定怎样处理已有前缀

下面限定刚才已保存 `ABCD`、期望从位置4继续的情况：

| 实际响应 | 这个例子中怎样理解 |
|---|---|
| `206`，同一表示，`Content-Range: bytes 4-9/10`，本次确实收齐6字节 | 可以把这一段放到位置4–9，检查得到的完整候选 |
| `206`，同一表示，`Content-Range: bytes 4-6/10`，本次收齐3字节 | 现在只有位置0–6，仍缺7–9；不能宣布下载结束 |
| `200`，完整内容为B的10字节 | 这是从头开始的候选，不能接在A的4字节后面 |

表中“同一表示”是前提，不是只凭状态码206就自动成立。RFC 9110 要求合并的部分共享相同的强校验器，并检查实际范围。[1] 应在接收逻辑里区分这件事与“HTTP请求没有报错”。

第一行的范围两端都包含，因此本段长度是 `9-4+1=6`。第二行说明，响应可能只提供所请求内容的一部分；客户端应按收到的 `Content-Range` 判断，而不是按自己请求了多少来填完成进度。206中的 `Content-Length` 即使存在，描述的也是本次响应内容长度，不是整个包的总长。

收到200时，一种明确的接入政策是另开完整候选的接收过程，保留或丢弃旧前缀由临时文件管理规则决定，但不把两者拼在一起。若错误地追加，例子会变成 `ABCD1234567890`，共14字节。这次长度检查也许能抓住错误，但正确性不应依赖错误恰好造成长度变化。

无效的范围不能拿来合并；位置、实际收到的字节与表示关系没有核清，也应保留为未完成或重新获取，而不是写出“下载成功”。`416 Range Not Satisfiable` 只表明这次范围请求不能按该条件满足，不能直接当作“本地已经完整”。远端变短或已有部分归属错误，都需要另行判断。这些失败处理不是本库已实现的下载器。

## 续传一致，还不等于拿到了获准测试的候选

假设测试要求的就是候选 A，地址却已经提供 B。即使正确取得完整 B，并且所有分段都一致，也不能悄悄把它当成 A 交给测试。

所以这里有两层判断：传输层问这些字节能否组成同一表示，交付层问这是不是预定候选。后者仍需要与可信的候选记录、文件清单及内容摘要对应；ETag 不能代替团队的发布决定，也不能证明包内新武器表现正确。

另外，若响应经过内容编码，HTTP字节范围针对编码后的字节序列。[1] 已解码文件的长度不能直接拿来当这个范围的偏移。本例特意排除了编码变换；实际客户端若会自动解码，需要先核查库交给应用的字节属于哪一层，不能照抄例子里的偏移计算。多段响应、重定向、并发下载、鉴权、崩溃恢复和原子安装也都不在本说明的实现范围内。

对正在排查的工具，先拿一份可区分的候选，记录旧部分属于什么、续传实际得到什么状态和范围、最后接收了哪份候选。检查的是这条具体转换，不是看到同一个下载地址和一个100%进度条就停止追问。
