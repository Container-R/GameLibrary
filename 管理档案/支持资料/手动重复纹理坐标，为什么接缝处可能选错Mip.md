# 手动重复纹理坐标，为什么接缝处可能选错Mip

一块地面要重复铺同一张纹理。着色器先把 UV 乘以重复次数，再取小数部分，让地址每到 1 就回到 0。地址看起来没错，接缝附近却可能使用过大的采样范围，进而偏向更粗的 mip。此时继续提高纹理分辨率，未必是在解决真正的问题。

这里讨论的是着色器作者手动重复坐标的情形，不是说普通的纹理重复寻址必然出错。先分清两件事：**到纹理的哪里取样，以及这次取样应覆盖多大范围。** mip 是逐级缩小的图像；选择它时，除了地址，还需要判断纹理坐标在屏幕上变化得有多快。

## 地址跨过边界，不代表纹理突然缩小

假设经过连续缩放后的水平纹理坐标，在两个相邻教学位置上分别是 `0.99` 和 `1.01`。两者相差 `0.02`，表示连续地跨过一个重复边界。GLSL 的 `fract` 取小数部分；处理后两个地址变成 `0.99` 和 `0.01`，相差 `-0.98`。

| 输入 | 左侧 | 右侧 | 右减左 |
|---|---:|---:|---:|
| 连续坐标 | 0.99 | 1.01 | 0.02 |
| `fract` 后的地址 | 0.99 | 0.01 | -0.98 |

第二行的变化幅度是第一行的 49 倍。它来自地址回绕，不是地面在接缝处突然需要把更多纹理压进同一屏幕范围。如果隐式采样梯度反映了这个跳变，就可能高估取样范围。

这是原创纸面差分，不是某块 GPU 的测量。实际导数有实现允许的近似，GLSL 也区分细粒度与粗粒度求导；不能据表格断言驱动必定返回 `-0.98`，更不能据此指定实际选中了哪一级 mip。[1]

## 保留连续变化，再交出最终地址

**梯度**在这里描述纹理坐标相对于窗口横向、纵向位置的变化。对二维纹理，需要两份二维变化量：沿屏幕横向怎样变，沿纵向怎样变，而不只是一个水平差值。

修正思路不是取消重复，而是保留两套信息：最终地址仍可回绕，采样梯度则从希望连续变化的参数取得。在 GLSL 中，`dFdx`、`dFdy` 用于求导，`textureGrad` 允许把梯度显式交给纹理查找。[1] 应在**预期的连续缩放、重复次数等变换之后，`fract` 之前**取得相应梯度；随便拿最原始 UV 的导数，也可能漏掉实际重复倍率。

求导位置同样重要。GLSL 对非一致控制流内的导数有限制——例如相邻处理位置进入不同分支时，不能假定分支里的导数有效。先在这样的分支里取得未定义的导数，再传给 `textureGrad`，不会自动修好它。应在满足求导要求的位置安排计算，而不是仅替换采样函数名。

历史上的 GPU Gems 2 分块纹理示例也把连续缩放坐标的梯度与最终块内地址分开处理；这是该例中可借鉴的思路，不表示必须采用它的整套纹理拼接方法。[2]

## 放进图集后，梯度还要换单位

图集把多块内容放在一张大纹理里。假设本例选定区域的原点和大小固定，它占整张图集宽度的四分之一、高度的一半。块内地址转换成图集地址时，水平坐标要乘 `1/4`，竖直坐标要乘 `1/2`，再加上区域原点。

梯度也必须按对应分量缩放。若连续参数沿屏幕横向变化 `(0.02, 0)`、沿纵向变化 `(0, 0.02)`，图集坐标中的两份梯度应为 `(0.005, 0)` 和 `(0, 0.01)`。这里原点固定，不贡献变化量。把块内梯度原样传给图集采样，会让地址与梯度使用不同尺度。这仍是限定条件下的手算，不是一段已经验证的着色器。

还要区分手动回绕与采样器的重复寻址。OpenGL 的 `REPEAT` 按整张纹理的尺寸处理寻址，不会自动知道图集中哪个子矩形才是你想重复的单元。[3] 给整张图集设置重复模式，不能替代子区域的地址设计。

## 正确的梯度不会补好图集边缘

即使地址和梯度都正确，采样仍可能混入邻图的颜色。原因在于：**地址是一个位置，过滤却可能组合它周围的多个纹素。地址在图块内，不代表参与过滤的纹素也全在图块内。** 这与前面因坐标跳变而选错 mip 是两个问题。

先固定一个 mip 级，只看一维的 8 个纹素，编号为 0 到 7。前四个属于红图，颜色都是 `(1,0,0,1)`；后四个属于蓝图，颜色都是 `(0,0,1,1)`。地址从 0 到 1 覆盖整条纹理，红区占 `[0, 0.5)`。所有颜色已在同一线性 RGB 工作空间，alpha 全为 1。下面是原创纸面算术，不运行 GPU，也不涉及 mip 选择、导数、编码转换、压缩或各向异性过滤。

在红区内选地址 `s=15/32=0.46875`。按 OpenGL 的单级线性过滤规则，纹素中心位于 `(编号+0.5)/纹理宽度`；换成以整数编号表示中心的刻度，取样位置为：[3]

```text
x = 8 × s − 0.5 = 3.25
```

它位于纹素 3 和 4 的中心之间，向纹素 4 走了四分之一的距离。因此线性过滤给红色纹素 3 的权重是 `3/4`，给蓝色纹素 4 的权重是 `1/4`，结果为 `(0.75,0,0.25,1)`。alpha 没有变化，蓝色也不是透明区域藏着的颜色；它来自另一个图块。这个一维两输入例只用于解释邻纹素怎样进入权重，不是二维图像或 GPU 观察。

给整张图集设 `CLAMP_TO_EDGE` 也挡不住本例。OpenGL 的这项规则把纹素索引限制在整级纹理的 `0…size−1` 范围；这里就是 0 到 7。[3] 索引 3、4 都合法，采样器并不知道 3 与 4 之间是应用划定的图块边界。因此，检查 UV 没有走出红区，还没有检查完这次过滤。

回到带 mip 的图集，需要分开做两类检查：

- **检查已经存下来的内容。** 查看实际导入结果中会被使用的各级 mip，确认图块边缘保存了什么。若生成缩小图像时已经混入邻块颜色，之后传入正确梯度也不能将其还原。GPU Gems 2 的拼块案例就把低 mip 内容作为独立问题处理。[2]
- **检查运行时怎样组合内容。** 对选中的级别确认取样位置周围会用到哪些纹素。OpenGL 的 `LINEAR_MIPMAP_LINEAR` 在两个 mip 级之间混合时，先分别求各级过滤结果，再按权重组合；只要两级都有贡献，就需要检查两者。[3]

由此可见，基础级加了一圈边缘填充，并不能自动证明所有 mip 和过滤范围都安全。制作边缘数据时，要先确定图块应该保持自己的边缘颜色，还是在本图内部重复，再把各级内容、图集布局和实际过滤方式一起核对。本文不给统一的填充像素数，也没有验证目标平台的边缘表现。

因此，先核查连续参数、梯度尺度和求导位置；这些都正确后，再追踪过滤实际读到的纹素与各级内容。不要看到接缝就认定是导数，也不要看到 `textureGrad` 或整图 clamp 就认定图集已经安全。

以上没有编译或渲染验证，不提供具体画面、性能或 mip 选择保证。本文先解决一个输入问题：**重复的地址可以跳回起点，但采样所需的连续变化信息不应因此被误换成地址接缝的跳变量。** 图集边缘的内容与过滤检查仍需单独完成。
