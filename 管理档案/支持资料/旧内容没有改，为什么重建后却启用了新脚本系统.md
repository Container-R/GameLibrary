# 旧内容没有改，为什么重建后却启用了新脚本系统

团队准备把玩法规则从旧的块式系统迁到新脚本系统，但下一次试玩仍想使用旧规则。代码和内容都没有改，重新构建后却出现异常。除了检查旧文件是否进入新包，还要反过来问：**试制时留下的新文件，会不会让旧候选意外进入新系统？**

这里的问题不是文件新旧本身，而是谁决定它应当被执行。若程序把“发现新脚本”直接解释为“启用新系统”，工作目录的历史就参与了玩法选择。

## LoR 的旧系统试玩为何受到新脚本影响

Riot 的 Patrick Conaboy 和 Jeff Brock 在 2021 年介绍《Legends of Runeterra》（LoR）的脚本迁移时，记录过一次内部试玩故障。新路径原本只在有 Python 脚本时启用；复用的构建节点却保留了此前生成的 Python 文件，使旧块式内容的重建混入两种脚本。作者据此提醒，替换旧系统时，显式开关可以是一道重要防护。[1]

这是作者对历史事故的说明。原文没有公开开关实现，也没有说此次故障实际就是靠加入某个开关修好的。下面是针对这一风险的原创检查建议，不是 Riot 的内部流程。

## 把“选择谁执行”与“拿哪份内容执行”分开

假设一份候选计划使用旧规则解释器，即负责读取并执行旧规则的程序。它应读取旧内容修订 A；新解释器和新内容修订 B 仍在试制。这些名称只是示意，不对应 LoR 的实际版本。

应先表达两个独立要求：本次选择旧解释器；该解释器取得的是约定的 A。目录里出现 B，不应自行改变前一个决定；找到 A，也不证明程序实际选择了旧解释器。

显式选择可以由项目的构建配置或运行配置表达，但配置本身也可能错。检查时仍要把候选、实际生效的选择和被读取的内容对应起来，不能只确认配置文件中写过“旧系统”。

接着定义遇到矛盾时怎么办。若选择旧系统，却同时发现 B，项目可以要求隔离并忽略 B，也可以拒绝这份候选；两种约定的检查结果不同。如果确实允许新旧系统并行，则需要另行说明内容怎样分配、是否允许重复执行，不能让文件发现顺序替团队决定。

同样，选择新系统却缺少 B 时，应有明确的失败或回退规则。若产品允许回退，接收者应能知道实际用了什么；不能悄悄退回旧系统后，仍把这次试玩算成新系统验证通过。

## 比较目录历史，但观察实际执行路线

对同一个计划使用旧系统的候选，可以安排两次对照：一次从没有试制残留的工作目录构建，另一次在含有 B 的复用目录构建。保持所选配置和约定内容一致，只改变这项目录历史。

然后按事先约定判断：若允许忽略隔离的 B，两次都应选择旧解释器并读取 A；若规定有冲突就拒绝，第二次应明确失败，而不是意外进入新系统。另准备“选择新系统但缺少 B”的输入，检查缺失处理是否符合约定。

这些是尚未执行的检查。需要观察实际选择、实际内容及能区分两套规则的行为，而不只是构建是否绿色、文件数量是否相同或游戏是否启动。一次对照也不能覆盖所有文件组合和运行路径。

显式选择解决的是启用意图，不能代替内容兼容检查、目录隔离或正确清理。反过来，清掉残留使一次试玩恢复，也不能证明启用条件已经可靠。把两件事分开，团队才能知道这次验证的是哪套系统，而不是由构建节点碰巧留下什么来决定。
