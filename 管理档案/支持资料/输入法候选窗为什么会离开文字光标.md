# 输入法候选窗为什么会离开文字光标

聊天框放大以后，输入的文字和光标仍对齐，输入法候选窗却偏到旁边。先别把它归为选字或提交事件处理错误：**画出光标的位置，与交给原生输入法的位置，可能使用了不同坐标。** 这是一个假设的接入问题，下面没有实际打开输入法验证。

界面自己的排版坐标、窗口坐标、窗口中可寻址的像素，不应默认混用。界面可能经过缩放、滚动或居中留边才显示出来；高像素密度又是另一层关系。看到系统设置为某个缩放比例，不能据此把所有位置统一乘同一个数。

## 先查接收端要什么，再转换光标位置

以 SDL 3.2.0 的 `SDL_SetTextInputArea(window, rect, cursor)` 为例：`rect` 是文本输入区域，单位是**窗口坐标**；`cursor` 是当前光标相对 `rect.x` 的横向偏移，也用窗口坐标单位。[1] 它不是字符编号，也不是光标的绝对横坐标。

这两个参数表达了不同信息：区域说明文字占在哪里，偏移说明关注点相对区域左边在哪里。它们不能一个来自放大后的显示位置，另一个还保留放大前的排版数值。

SDL 自己的渲染坐标也不必等于窗口坐标。固定版本的 `SDL_RenderCoordinatesToWindow` 会考虑视口、渲染缩放、逻辑呈现区域以及像素到窗口坐标的换算。[2] 如果文字确实使用这条窗口渲染路径，可以据此核对转换；自定义 UI 或离屏纹理还要先说明它们怎样进入这条路径，不能只因函数名合适就直接传入任意坐标。这里的“窗口坐标”也不能统一改称“物理像素”。[3]

## 同一个光标，为什么不是把 120 直接传进去

只看一个原创纸面例子。规定本应用的 UI 坐标到窗口坐标的关系为：

```text
窗口 x = 2 × UI x + 40
窗口 y = 2 × UI y + 20
```

这是人为规定的两倍界面缩放与位置偏移，不是通用 DPI 公式。本例还规定窗口坐标与可寻址像素一一对应，不再叠加其他变换。

UI 中的文本区域为 `(x=10, y=20, 宽=100, 高=16)`，光标在区域左边向右30个 UI 单位的位置。转换如下：

| 要交接的量 | 计算 | 窗口坐标结果 |
|---|---|---:|
| 区域左上角 | `(2×10+40, 2×20+20)` | `(60,60)` |
| 区域宽高 | `(2×100, 2×16)` | `(200,32)` |
| 光标横坐标 | `2×(10+30)+40` | `120` |
| 相对区域左边的光标偏移 | `120−60` | `60` |

因此，本例要交给该接口的是 `rect=(60,60,200,32)`、`cursor=60`，不是 `cursor=120`。若把绝对横坐标120当成相对偏移，关注点会变成 `60+120=180`。另一方面，只把区域位置乘2，又会漏掉窗口中的平移。两种错误都不是改变字体大小就能自动修好的。

宽高没有加上位置偏移，是因为它们描述长度；位置才需要移动原点。这个例子刻意使用整数和正比例缩放，未解决分数取整、旋转区域或复杂裁剪。实际组件应明确怎样形成整数输入区域，而不是照搬这组数字。

## 交接的是当前区域，不是对候选窗的精确摆放命令

实现时，应在当前文字布局与显示变换确定后取得区域和光标，再转换到接收接口所需的坐标。光标移动、文本滚动、界面布局或窗口显示状态变化时，都要检查旧区域是否仍有效；文字已经移动，输入法却一直收到旧位置，同样会造成两边脱节。这是接入检查建议，不是本文执行过的刷新时序。

还要区分“区域已提交”和“候选窗已按预期显示”。SDL 的说明是原生输入法**可能**把建议窗口放在光标附近，避免遮住输入文字，并不承诺候选窗左上角精确等于某个坐标。[1] 应核对调用结果，但成功返回不能替代在目标平台、输入法和实际控件中的视觉检查。

本例只解释 SDL 的坐标契约，不给 Unity 或浏览器添加同名接口，也不改变主文关于组字确认与聊天发送的事件边界。候选位置正确不能证明发送归属正确；发送不再误触，也不能证明候选位置正确。本文没有调用 SDL、调整真实窗口或运行输入法，没有取得候选窗截图。
