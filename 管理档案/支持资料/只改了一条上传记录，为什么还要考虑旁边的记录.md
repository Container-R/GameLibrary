# 只改了一条上传记录，为什么还要考虑旁边的记录

CPU 准备更新一条 48 字节的矩阵记录，旁边另一条记录还在被 GPU 读取。两条记录的字节没有重叠，是否就能各自推进？对 Vulkan 的非 host-coherent 内存，答案还取决于设备报告的 `nonCoherentAtomSize`：主机与设备访问的同步范围可能比这 48 字节更大。

这篇补充面向手动管理 Vulkan 上传内存的渲染程序。它接着矩阵正文的两槽说明，具体区分三个容易混用的位置：缓冲区内偏移、内存分配内偏移、映射指针内偏移。采用 Vulkan 1.3.296 固定规范，以下全部是未执行的纸面例子，不是设备故障记录。

## 同一个字节，可以有三个不同的偏移

假设有一块 4096 字节、主机可见但不具有 `HOST_COHERENT` 属性的内存，设备的 `nonCoherentAtomSize` 为 256 字节。成功映射的是分配内的 `[512,1024)` 区间，返回指针记为 `p`。这里使用左闭右开区间：512 包含在内，1024 不包含。

一个普通、非稀疏缓冲区绑定在这块分配的偏移 768 处；我们要更新它内部 `[16,64)` 的 48 字节记录 A。假定内存类型、绑定大小、绑定对齐及缓冲区用途的其他要求均已满足。这不是声称任意设备都允许这样的绑定，也不是说 16 满足统一缓冲区的动态偏移对齐。

于是，同一条记录的位置分别是：

- 相对缓冲区起点：`[16,64)`。
- 相对内存分配起点：`[768+16,768+64)`，即 `[784,832)`。
- 相对映射指针 `p`：`[784-512,832-512)`，即 `[272,320)`。

所以，按字节寻址时，写入位置是 `p + 272`，不是 `p + 16`，也不是 `p + 784`。但填写 `VkMappedMemoryRange.offset` 时，又不能使用 272：这个字段从**内存对象的起点**计数，不是从映射窗口起点计数。`vkMapMemory` 返回映射区间的起始指针，缓冲区绑定偏移也有自己的含义，三者要分别记住。[1][2]

## 刷新范围不一定就是刚写过的48字节

非 coherent 内存需要显式处理主机写入的刷新。`VkMappedMemoryRange.offset` 必须是 `nonCoherentAtomSize` 的倍数；显式大小也有粒度条件及分配末尾例外，而且范围必须落在当前映射内。[3]

对本例，记录 A 的分配范围 `[784,832)` 向外扩到 256 字节边界，得到：

```text
起点：向下取整到 768
终点：向上取整到 1024
刷新范围：[768,1024)
offset = 768，size = 256
```

这组值落在映射 `[512,1024)` 内。直接填写 `offset=784, size=48` 并不满足这里的要求；误把映射窗口当原点填写 `offset=256`，不仅不是同一片内存，而且起点已落在当前映射之外。此处是在推导合法范围，不是在报告某次调用成功。

现在只改一个条件：当前映射到 944 就结束，变成 `[512,944)`。它虽然仍包含记录 A，却不包含扩展后的完整范围 `[768,1024)`。不能为了凑进映射窗口，把刷新范围裁成 `[768,944)`：176 既不是 256 的倍数，944 也不是这块 4096 字节分配的末尾。

`VK_WHOLE_SIZE` 不是忽略对齐的通行证。对于 `VkMappedMemoryRange`，它延伸到当前映射的末尾；规范仍要求该末尾相对内存对象对齐到 atom 边界，或者恰好是整个内存对象的末尾。[3] 因此，在 `[512,944)` 这个例子里也不能靠它补救。

实际设计映射窗口时，应让所需刷新范围能合法包含在内。若必须调整现有映射，应先按项目的资源与同步规则完成相应收尾，不能对同一内存直接叠加第二次映射。本文不提供在途映射替换流程。

## 相邻记录没有被改写，也可能需要一起等待

回到合法映射 `[512,1024)`。假设记录 B 位于同一分配的 `[896,944)`，GPU 尚未完成对它的旧读取。A 与 B 没有一个字节重叠，却都落在 `[768,1024)` 这个 atom 内。

固定规范的主机访问要求明确指出：非 coherent 内存的相关完成保证必须扩大到 atom 边界。[4] 因此，准备写 A 时，不能仅凭“A 自己已经不用了”就排除 B 的旧访问。问题在 **CPU 开始写之前**就要处理，不是写完以后再用一次 flush 补救。flush 负责让主机写入可用于后续内存域操作，不负责等待旧 GPU 工作结束。[5]

这不表示程序主动把 B 的字节重新写了一遍，也不表示每条逻辑记录必须独占一次内存分配。分配器可以让需要独立推进的区域不共享相应 atom，也可以把同一 atom 中记录的使用归到共同的完成条件。前者可能增加填充，后者可能增加等待；选择取决于实际上传模式。其他绑定与用途对齐要求仍要同时满足，不能只按 256 划格子就算全部合法。

完成旧访问的确认、主机写入、合法刷新，以及后续提交之间仍要有正确顺序。这里仅把“需要考虑哪片内存”算清楚，不替代完整的跨队列同步、设备写回主机、失败恢复或分配器实现。
