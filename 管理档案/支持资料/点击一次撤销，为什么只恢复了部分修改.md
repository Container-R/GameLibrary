# 点击一次撤销，为什么只恢复了部分修改

一个批处理工具可以同时改名称、调整层级，却只在菜单里留下一个“整理门对象”。如果撤销后名称回去了，父子关系却没有恢复，先别急着让使用者多按几次。需要先检查：**这次操作改变了什么，其中哪些变化真的被记录了？**

下面用一个原创、未执行的工具设想说明。场景里已有门对象 A、B，分别属于走廊组 P、Q。TA 准备做一个按钮，给两扇门加上检查后的名称，并把它们移到已有的整理组 R 下。使用者希望一次撤销回到原名称及原父级，再重做时恢复整理结果。

对使用者而言，这是一次工作；对工具而言，却包含多项状态变化。撤销记录解决“能恢复哪些变化”，撤销分组解决“这些记录怎样成为一次操作”。先把后者做漂亮，不能补齐前者遗漏的内容。

## Unity 6000.0 的例子：记录对象，也要选对操作

在 Unity 中，门的名称属于 `GameObject.name`，父子关系由它的 `Transform` 表达。只把 GameObject 交给记录接口，不能因此假定所有组件或整棵层级都已被记录。先分清实际修改的是哪个对象，是工具作者的基本工作。

但即使对象找对，也还没检查完。假设本例脚本在修改前，已经分别对相关 GameObject 和 Transform 调用了 `Undo.RecordObject`，随后改名称、直接设置父级。Unity 6000.0 文档明确说明，RecordObject 可以记录大多数属性变化，却不记录 Transform 父级改变。[1] 所以“每个相关对象都记过了”仍不足以说明这次整理可以完整撤销。

对于这项父级操作，同版本提供 `Undo.SetTransformParent`：它在设置父级时记录对应撤销。[2] 因而本例的实现思路应是，名称修改按对应对象记录，父级修改使用支持该操作的记录途径。这里不是给普通父级赋值再套一个相同标题，而是改变操作本身进入撤销系统的方式。

这是按文档范围推导的缺口，不是本库观察到的一组固定运行结果。例子只涉及同一场景中已有的普通对象，不涉及 Prefab、创建或销毁；其他版本应核对各自文档。

## 合成一步之前，先确认没有漏掉变化

要把这次整理设计成一次撤销，先确认名称和父级变化都有相应的记录途径。Unity 的 `Undo.CollapseUndoOperations` 按组索引合并已有撤销操作；它没有替未记录变化补写历史的职责。[3] 因此，给刚才那段只做通用属性记录的脚本加一次合并，不能据此宣称父级问题已经修好。

显示标题也不能代替分组。RecordObject 的 `name` 参数是历史中的操作名称；两条记录都叫“整理门对象”，不等于它们具有同一组身份。[1] 工具应依据实际组索引界定这次命令的范围，避免顺手把此前或期间的无关编辑一起合进去。分组的目标是符合使用者的一次工作，而不是让历史条目越少越好。[3]

## 在副本上对照状态，不只看菜单

验收这类工具时，可以先用隔离的场景副本完成一次有限检查。下面是建议的检查过程，不是已经执行的测试：

1. **留下初态。** 记下 A、B 的实际对象身份、原名称及各自父对象 P、Q；另选一个不参与整理的对象作对照。对象随后会改名，不能只凭新旧名称猜它是不是同一个对象。
2. **执行整理。** 检查 A、B 是否得到预定名称，并确实归到 R 下；对照对象不应被一起修改。
3. **撤销一次。** 分别核对两扇门的名称和父子关系是否回到初态。出现一个历史条目、按钮没有报错，都不能代替这两项检查。
4. **重做一次。** 再核对名称与父级是否恢复到整理后的预定状态，并检查无关对象仍未改变。

如果工具实际还会影响位姿、层级顺序或其他字段，也要把这些变化纳入对照，不能因为本例只追踪名称和父级，就默认其余状态都正确。检查发现遗漏时，应回到“修改了哪个对象、用了哪种记录操作”，而不是先继续合并历史。

这次检查只回答正常操作中的撤销与重做。批处理中途失败怎样恢复、取消后留下什么、已经保存到磁盘或写出的外部文件如何处理，都需要另外设计；不能仅凭撤销分组，就认定这些副作用已有原子回滚或恢复保证。
