# 已经减去相机位置，为什么大坐标仍会丢失细节

对象和相机都离世界原点很远，彼此却只差一个位置单位。着色器里明明写了“对象位置减相机位置”，得到的差值为什么仍可能是零？关键在于减法之前：如果两个绝对位置已经被转换成同一个数，后面的减法便无从知道它们原来不同。

本文面向负责位置数据上传与坐标变换的图形程序员，用一个可以逐步推导的例子说明转换顺序。这里的位置单位只是算例单位，不代表米或厘米，也不据此规定游戏世界能做多大。

## 先看输入能不能保留这一个单位

本文明确采用 IEEE 754 的 **binary32 单精度**与 **binary64 双精度**，而不是只凭程序里的类型名称判断精度。binary32 正规数有 23 个显式小数位，加上隐含的首位，共有 24 位有效二进制精度；binary64 对应为 53 位。[1]

有效位数固定，意味着数值变大时，相邻可表示值之间的间隔也会变大。在半开区间 `[2^24, 2^25)` 内，binary32 的间隔为 `2^(24−23)=2`。因此，16,777,216 和 16,777,218 都可精确表示，夹在中间的 16,777,217 却不能。

现在只看一个坐标分量，设相机位置为 `C=16,777,216`，对象位置为 `P=16,777,217`。两者最初由 binary64 保存，这两个整数都能精确表示，真实差值为 1。

下面所有舍入均约定为**舍入到最近值，恰在中间时取保留有效数末位为偶的候选**，即 round-to-nearest, ties-to-even。[2] 这项约定不能省略：P 正好位于两个相邻 binary32 值的中间；较低候选 16,777,216 的有效数末位为 0，所以 P 转成 binary32 后成为 16,777,216。C 转换后也仍是这个数。

## 两条顺序，得到两个差值

用 `Q32(x)` 表示按上述方式将 x 转成 binary32。现在比较两条明确的计算路径：

| 路径 | 计算步骤 | 结果 |
| --- | --- | ---: |
| 先转换绝对位置 | 分别求 `Q32(P)`、`Q32(C)`，再用 binary32 相减 | 0 |
| 先求相对位置 | 先用 binary64 计算 `P−C`，再将差值转成 binary32 | 1 |

第一条路径的减法没有算错。它拿到的两个输入已经相同，因此精确地得到零。原来相差一个单位的信息，丢在了此前的类型转换中。

第二条路径在输入仍保留差别时相减，得到整数 1；这个结果也能由 binary32 精确表示。它避免的是把两个很大的绝对位置分别压进较粗的表示，而不是给最终减法增加了某种特殊能力。

将第一条路径中的两个单精度值再转回双精度，也无法补救：它们只会成为两个精确的 16,777,216，差值仍为零。更宽的类型能保存更多信息，但不能从相同的输入中猜回已经丢失的那一个单位。

作为对照，保持 C 不变，只将 P 改为 16,777,218。此时两个绝对位置都能由 binary32 精确表示，两条顺序都会得到差值 2。因此，并非所有大坐标都会出错；能否保留差值，取决于具体数值、表示和计算顺序。

这些都是基于指定格式和舍入规则的原创推导，不是着色器或引擎运行结果。

## 把转换位置放回真实的数据路径

排查时，可以沿着一个对象的位置逐段写清：世界位置怎样保存，在哪一步转换类型，何时形成相对位置，上传给着色器的究竟是什么。只看最后一行已经减了相机，或者 CPU 变量使用 double，都不足以确认前面的信息仍在。

如果输入还保留所需差值，一种做法是先以足够精度形成相对平移，再将较小的结果转成单精度。另一种做法则把额外信息一起传过去，在目标侧用配套运算形成相对结果。它们的共同要求是：所需细节必须保留到相对量形成的那一步。

Unreal Engine 5.6 的渲染文档提供了后一类表示与相对坐标配合的例子：DoubleFloat 用 High、Low 两个单精度分量保存较高精度的信息，Low 保留 High 舍入误差中的一部分；文档同时建议尽早进入 translated world space，例如相机相对世界空间。[3] 这不是“所有路径都改用硬件双精度”的承诺，也不是把两个分量随意相加回一个大 float 就能保留原精度。

Godot 4.6 的说明也提醒我们检查具体路径：其双精度构建中的 3D 渲染仍借助单精度表示与配套运算模拟更高精度，并非着色器全面采用双精度类型；`skip_vertex_transform`、`world_vertex_coords` 等模式有明确限制。[4] 这里借它确认范围需要逐项核对，不据此比较两种引擎或给出现成迁移方案。

## 相机附近的坐标，仍有自己的边界

**相机相对世界坐标**可以只改变平移参照，继续沿用世界坐标轴。完整的视空间变换通常还要按相机朝向旋转，不能把“已经减去相机位置”理解为“已经完成所有视变换”。

渲染入口采用相对坐标，也不等于整个世界已经迁移原点。原点迁移还需要相关系统一致处理自己的位置与状态；仅改变渲染输入，不会自动改变独立物理系统的输入和求解过程。因此，CPU 使用双精度或画面采用相对坐标，都不能单独成为物理问题已经解决的证据。

先相减同样有前提。如果位置在读入时已经丢失细节，或者相减后的范围仍大到单精度不能满足需求，这个顺序也不能保证结果足够精确。模型局部顶点本身过大、投影深度不足等问题，也需要分别检查。

回到开头，最有用的问题是：“P 和 C 在第一次降精度之前，是否仍保留了我们需要的差别？”先找到那一步，再决定在哪个空间、用什么表示完成转换。本文没有运行引擎、测试物理或测量画面抖动；实际项目仍须核对自己的数据路径与目标精度。
