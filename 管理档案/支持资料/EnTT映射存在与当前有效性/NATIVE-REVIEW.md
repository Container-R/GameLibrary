## 实际观察及解释

声明记录为 EnTT 3.13.2、C++17，默认20位索引/12位版本。技术编译宏只是本次构建自报，不是官方工具链认证。归档三项依次为 uint32计数1、uint32活跃数1、entity来源完整值0。

| 阶段 | map完整值（索引/版本） | contains | 目标 valid(map) | 活跃数 | 保存的旧 initial 是否有效 |
|---|---|---|---|---|---|
| before_load | null哨兵4294967295（1048575/4095） | false | false | 1 | 尚无 initial |
| loaded | 1（1/0） | true | true | 2 | true |
| externally_destroyed | 1（1/0） | true | false | 1 | false |
| reloaded | 1048577（1/1） | true | true | 2 | false |

source 与 seed 的完整值在各自注册表中均为0、均一直有效。数值相同不表示跨注册表是同一个对象。首次加载产生的本地1不同于目标 seed；销毁后，loader 中的映射仍返回完整值1，contains与非空均不能替代目标 registry.valid。第二次 get 消费同一归档的全新游标，恰好3项；恢复后 map 变为1048577，索引仍1而版本为1，旧完整值1仍无效。两次加载的 input_consumed 均为3，未加载阶段为 null，不冒充累计次数。

这与固定源码的 map 查询保留映射、不再次验证本地有效性，以及 restore 在同一来源映射的本地实体无效时创建新实体的路径一致。它不是“map 调用本身修复实体”，不是 EnTT 出错，也不是可永久使用裸索引的依据。输出中的具体0/1来自本次记录，不能升级为所有分配序列的固定承诺。

本项实际为 **2次构建入口、2次原生 fixture、2组相同四阶段记录**；每 fixture 包含2次 continuous_loader.get。它们是同环境、同 runner、同输入的重复，不是两种配置。编译器内部可能产生其他进程，以上不是系统总进程计数。本审查新增编译/原生调用均为0。
