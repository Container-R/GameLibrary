# EnTT 连续加载映射的四阶段观察

`continuous_loader.map` 找到了本地句柄，是否就能直接使用它？本例把两个动作分开观察：加载器还保存着对应关系，以及该句柄在目标注册表里当前有效。

固定 EnTT v3.13.2 的同一流程，在同一环境下用两个新副本各构建、执行一次。两份输出相同。这是同一操作者的一次 runner 调用内的重复，不是另一操作者独立执行，也不是跨机器验证。本页为既有记录的公开整理，没有重跑。

> **执行准备限定：** 发表后核对发现，冻结 v2 没有落实当时规范要求的 HOME 与三个 XDG 目录准备。原始观察保留，但不能据此声称流程符合该规范。见[具体缺口与后续处理](WORKFLOW-LIMITATION.md)。

## 后续补齐环境准备的执行

[v3 新执行与复现入口](v3/README.md)按新协议补齐五个运行位置的准备和启动前检查，并另外完成两次构建、两次原生执行。技术输出与下表一致。v2 与 v3 合计四次原生调用，仍只有同一个实体映射条件；v3 不追认旧 v2 流程合规，也不是不同操作者的独立复跑。以下旧流程材料继续保留，便于区分两次协议与各自证据。

## 实际做了什么

来源注册表只创建一个实体。目标注册表先创建另一个实体，使目标不是空的，再创建连续加载器。夹具用 EnTT 自己的 snapshot writer 生成内存归档，由同一个 loader 读取；随后外部逻辑销毁映射到的本地实体，最后从头重读相同归档。

| 阶段 | 加载器知道来源实体 | map 返回非空句柄 | 该句柄在目标中有效 | 目标活跃实体数 |
|---|---|---|---|---:|
| 加载之前 | 否 | 否 | 否 | 1 |
| 第一次加载后 | 是 | 是 | 是 | 2 |
| 外部销毁后 | 是 | 是 | 否 | 1 |
| 相同归档再次加载后 | 是 | 是 | 是 | 2 |

外部销毁后，map 仍返回第一次保存的完整句柄；再次加载后，map 返回另一个有效完整句柄，原句柄仍无效。来源实体和目标预先创建的实体始终有效。两次读取各消费同一份归档的三个有类型条目：总数、活跃数、来源实体。

这里观察的是映射与当前有效性的区别，不是库故障，也不是“有映射就有权限”的业务判断。没有加载组件、迁移组件内部引用、发送网络消息、测试代次绕回，或验证产品存档兼容性。两个独立注册表中的相同整数也不自动代表同一业务对象。

## 怎样查看证据

- 两份原始八行输出：[第一次](observations/repeat-1/native.stdout)、[第二次](observations/repeat-2/native.stdout)。声明行记录编译宏：C++ 201703、GCC 14.2.0、EnTT 3.13.2；这些是构建中的技术声明，不认证完整工具链来源。
- [公开回执投影](receipt-projection.json)保留两个构建与两个原生调用的返回状态、空诊断、无超时、源输入前后关系和内容检查结果。构建输出和两种 stderr 均为空，原文件保存在对应 observations 目录。
- [执行前独立字面预期](independent-oracle.json)、[协议审查](PROTOCOL-REVIEW.md)、[初次代码审查](CODE-REVIEW.md)及[v2差异闭合](CODE-REVIEW-v2.md)说明预期与执行前检查范围。[原生记录独立审查](NATIVE-REVIEW.md)核对了原始输出和原回执；它没有另行运行原生程序。代码审查也不是独立原生复跑。

公开回执省略两个副本各自的编译产物摘要，共四个字段；只保留原记录中产物前后相等的判断，不能用这个判断重新认证被省略的身份。源代码、夹具、协议和输出的摘要仍保留，用于核对公开技术材料。投影的新增说明明确它不是新运行；原始回执没有被改写，其整体身份仅在本地审查记录中保存，不纳入公开投影。

## 执行前修正了什么

最初协议把 initial 的存在时点写得含糊，之后明确：只有加载前没有 initial，第一次加载后便记录实际句柄。三处代码问题也都在原生执行前修正：

1. 不再因入口进程已经退出就跳过拥有的进程组收尾；清理错误不能覆盖首错。
2. 每阶段先输出真实观察，再检查并立即停止，不能在已偏离预期后继续下一次加载。
3. 回执先写入并正常关闭非权威 pending 文件，再发布正式 receipt；不能把写到一半的 PASS 当结果。

这些是执行前发现，不是 EnTT 原生失败。清理与回执的十个纯 Python 测试在普通和优化模式通过，进程与信号全部使用 mock；另有独立消费者合成反例检查，见审查记录。它们不增加本例的原生条件数，也不证明断电持久性、所有后代的系统调用或完整网络隔离。

## 复现材料与前提

本目录保留冻结 v2 的原创 [fixture.cpp](fixture.cpp)、[runner.py](runner.py)、[checker.py](checker.py)、[测试](test_runner_cleanup.py)、[协议](PROTOCOL-v2.md)及[输入清单](INPUT-MANIFEST.json)，字节与本次执行输入相同。协议中的“尚未执行/待授权”描述的是冻结时点，不能当成本页记录了额外一次运行。审查文件提到的早期工作目录和历史副本不是这里必须准备的依赖。

为避免重复分发约3.1MB的第三方单头，本目录不包含 EnTT 源文件。希望复现的开发者须先按 [UPSTREAM-SOURCE.json](UPSTREAM-SOURCE.json) 从官方固定提交取得 `single_include/entt/entt.hpp` 和 `LICENSE`，分别放到此目录的 `source/entt.hpp`、`source/LICENSE`，并核对大小与摘要。固定来源是 [EnTT v3.13.2 提交](https://github.com/skypjack/entt/tree/78213075654a688e9da6bc49f7f873d25c26d12c)，[上游许可证](https://github.com/skypjack/entt/blob/78213075654a688e9da6bc49f7f873d25c26d12c/LICENSE)仍适用。没有自动下载器、安装步骤或第三方字体/游戏数据。

还需要可用的 Python 3、C++17 编译器和标准库。runner 使用固定 `c++` 命令、POSIX 进程组及文件操作；不承诺 Windows 等其他运行环境直接可用。以下命令描述旧 v2 的复现条件，不是已满足上述目录准备规范的新实验推荐入口。源码准备齐全、核对冻结输入后，可从本目录复查旧流程：

```text
python3 -B runner.py fresh-observation
```

`fresh-observation` 必须不存在，父目录必须已存在。一次调用最多两次构建、两次原生执行；首个失败即停止，不自动修改警告门槛或重试。编译器可以有内部子进程，所以这不是“系统总共四个进程”的声明。流程没有网络调用需求，不等于已经测量过零网络系统调用。

另外附有未改字节的[独立消费者合成检查](independent-consumer-check.py)，其中一个正例和25个反例都是合成记录，不是额外原生观察。它是审查工具副本，不加入原执行输入清单。准备并核对上述源文件后，可从本目录分别复查：

```text
python3 -B independent-consumer-check.py
python3 -B -O independent-consumer-check.py
```

本次公开整理没有重新执行这些命令。

缺少上游源文件时输入检查应失败，不能为了让检查通过而删除清单项。本目录的 `INPUT-MANIFEST.json` 仍是原执行输入绑定，包含需要另行准备的两个上游文件；`PUBLIC-PACKAGE-MANIFEST.json` 则只是本公开包现有文件的字节清单，二者不能互换。新运行自行生成的原回执包含构建产物身份，不自动成为可直接发布的安全投影。
