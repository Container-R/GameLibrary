# 两个构建目标都要武器数据，为什么不能各自生成同一份文件

[返回构建工程师正文](../../GameLibrary/引擎与工具/构建发布/岗位与协作/构建工程师如何交付可用的游戏版本.md)

客户端和规则测试程序都要读取一份转换后的武器数据。于是两边的构建步骤都写了：“先运行转换工具，生成 `weapons.bin`，再继续。”单独构建任意一边看起来都合理；两边同时构建时，却可能出现两个工作同时写同一文件。

这是一个原创假设，不是已经观察到的项目事故。它比“工具有没有编好”多了一个问题：**这份共享文件究竟由哪个构建步骤负责产生？** 两个消费者需要它，不意味着应该给它安排两个独立生产者。

## 先画文件关系，再决定谁负责生成

在这个例子里，我们希望的关系是：

```text
武器规则表 + 转换工具
          ↓
   唯一的武器数据生成规则
          ↓
      weapons.bin
       ↙       ↘
客户端的后续步骤   规则测试程序的后续步骤
```

这里说“唯一”，是指这次构建图中这一个输出文件有明确生产归属，不是说整个团队只能有一个构建进程，也不是要求所有工作串行。两边等到共享数据就绪后，仍可开展各自互不冲突的工作。

如果确实需要两种不同格式，例如客户端使用压缩版、测试程序使用便于检查的展开版，那就应明确为两份不同产物及其转换关系。不能因为文件名相同就把它们当成相同内容，也不能因为内容目前相同，就忽略两个写入者的冲突可能。

## CMake 的例子为什么同时写文件和目标依赖

CMake 3.31.12 文档明确提醒：不要把同一自定义命令的输出列到可能并行构建的多个独立目标中；它给出的多目标示例，把共享 `table.csv` 的生成接到一个单独的 `generate_table_csv` 自定义目标，再让两边的后续生成命令依赖它。[1]

这个例子中的消费者还保留了对 **`table.csv` 文件本身**的依赖。这不是无意义地写两遍：

- 文件依赖表达“生成内容变化后，我的派生结果可能需要重做”。
- 对负责生成的目标建立依赖，表达“先让负责这份共享文件的工作就绪，再轮到我”。

单独保留其中一种，不能随意推断另一种关系已经完整表达。原正文讨论的“转换工具已先编好，不代表工具重编会让数据失效”，也属于应把顺序与失效分开看的情况；这里进一步要求共享输出有一个明确的生产入口。

还有一个容易误解的细节：`add_custom_target` 创建的目标本身没有输出文件，总被视为过期；但官方共享文件例子把生成命令放在 `add_custom_command(OUTPUT ...)` 中，自定义目标只依赖该输出。[1][2] 因此，不能仅看到“自定义目标总是构建”，就断言转换程序每次都必然重新执行。反过来，若把转换命令直接放进这个总会执行的目标，那又是不同安排，不能借用原例的增量行为解释它。

这段说明限于官方示例所表达的关系，并不是一份完整的游戏构建脚本。具体接入还要核对目录、输出路径、工具和其他实际输入；跨目录、多配置、远端缓存或多个外部构建同时写同一目录，都不因加上一个目标依赖自动得到保证。

## 不用“这次没撞上”代替检查

针对假设中的武器数据，可以先检查实际生成图：到底有几条规则会写 `weapons.bin`？客户端和测试程序引用的是否真是同一个输出路径？是否另有打包脚本会在构建系统之外改写它？然后再安排有限项目检查：

1. 单独构建客户端、单独构建测试程序，都应能从缺失的共享数据开始得到各自所需结果。
2. 两者一起构建时，检查共享输出的生产归属，不以“这一次文件看起来完整”证明没有竞争。
3. 只改武器表，再只改转换工具，分别检查共享数据及受影响的后续产物是否按约定更新。
4. 无相关输入变化时，检查是否存在意外重复转换；不要为了省一次工作而删掉必要依赖。

这些是待执行的检查建议。本文没有运行 CMake、制造并发写入或测量构建时间，也没有证明某种生成器在任意项目中都不会竞争。能从文档确定的是应明确表达哪些关系；实际项目还需要用自己的构建配置与文件结果核实。

共享文件的问题不一定靠一个锁或“构建前全部删除”解决。先把生产者、消费者、失效原因与先后顺序写清楚，才知道剩下的冲突属于构建图、外部脚本，还是本来就不该共享的两种产物。
