# 纹理每行字节数正确，为什么上传后仍会错行

预算表算清了纹理有多少数据，上传时却还可能把第二行放错位置。原因是：**一行要复制多少字节，与下一行从哪里开始，是两个数字。** 来源图像和上传缓冲区，还可能各用一种行跨度。

这份说明面向渲染与平台程序，是纹理预算书的可选延伸。我们只看 D3D12 常规上传布局中的一小步：把已有的 CPU 图像数据放进上传缓冲区。例子是纸面地址推演，没有调用设备、编译 helper 或运行 GPU。

## 同样的两行内容，可以有不同的排列间隔

Microsoft 的 `GetCopyableFootprints` 文档用32像素宽、每像素4字节的图像说明：一行有效数据为128字节，而上传布局的行跨度可以是256字节。[1] 后者意味着相邻两行的**起点**相距256字节，不意味着一行有256字节图像内容。

沿用这个区别，假定我们要放入两行数据：

- 来源紧密排列，每行128字节，总共256字节，来源行跨度也是128。
- 本例选定的目标布局行跨度为256，子资源起点是上传缓冲区中的偏移 `O`。
- 来源和目标区域不重叠，格式一致，目标有足够空间容纳这两行。

这里的目标布局是教学假设，不是本次取得的 API 返回值。实际程序应根据资源描述取得可复制布局，使用其中的偏移和行跨度，而不是把例子的256写成所有纹理的规则。

| 行 | 来源中的有效字节区间 | 目标中应写入的区间 | 本次复制长度 |
|---|---|---|---:|
| 第一行 | `[0,128)` | `[O,O+128)` | 128字节 |
| 第二行 | `[128,256)` | `[O+256,O+384)` | 128字节 |

区间右端不包含在内。目标第一行之后留有间隔；第二行从 `O+256` 开始，而不是紧接着第一行的有效数据。`O+384` 是本例最后一个有效区间的结束位置，不是对整个上传缓冲区分配大小的结论；实际容量仍需按 API 给出的总空间及所用区域确定。

## 两种看似省事的复制，错在不同地方

第一种做法是从来源一次复制256字节到目标 `O`。来源没有读越界，但第二行会落在 `[O+128,O+256)`，占用了目标两行之间的间隔。目标布局约定的第二行位置并没有因此得到正确内容。**总字节数正确，不能抵消行起点错误。**

第二种做法是看到目标行跨度为256，就复制 `256×2=512` 字节。这也不是修正：本例来源只有256字节，按这个长度读会超出来源范围。目标需要较大的排列间隔，并不意味着来源自动多出了可供读取的数据。

正确的判断是分开保留三个量：来源下一行按128前进，目标下一行按256前进，每次复制128。固定版本的官方 `MemcpySubresource` helper 正是分别使用来源与目标的 `RowPitch` 定位，再以 `RowSizeInBytes` 作为每行复制长度；`UpdateSubresources` 则把映射地址加上返回布局中的 `Offset`，作为该子资源的目标起点。[2]

这不意味着“一次 memcpy 永远错误”。如果来源已经按与目标完全匹配的布局准备好，而且各行、切片、偏移和可读写范围都满足要求，就可能采用整块搬运。这里反对的是：**明知来源紧密排列、目标有不同间隔，却仍把两者当成同一种布局。**

## 回到纹理预算与实际上传

BC纹理也有行，但那是**块行**。预算书的60×40 BC1顶层，每块覆盖4×4纹素，每块8字节，因此紧密来源有120字节一块行、共10块行；不能拿40个纹素的高度当作40次块行复制。来源跨度按实际来源布局确定，目标行数、有效行字节和放置位置应与目标格式及 API 布局相符。[1][2][3]

若离线文件能读、数据量也正确，而自写上传代码得到错行，先比较来源与目标的行起点及复制长度，不要立即更改纹理格式或要求美术重做素材。文件里某个 pitch 字段也不能未经核对就当作可靠布局：DDS 官方指南特别提醒过历史工具写入该字段不一致的问题，并建议按行复制。[3]

本文只解释二维、单切片、正行跨度的例子。多切片还要分别处理来源与目标的 `SlicePitch`；多个子资源也各有自己的布局和起点。官方 helper 的少量检查不是完整的文件安全校验，调用者仍需确认来源范围、目标容量及计算不会溢出。

把字节放到正确位置之后，还没有完成整个上传流程。资源状态、命令提交与同步，以及 GPU 使用期间上传缓冲区的寿命，仍需另外处理。CPU 复制结束或 helper 返回，不等于纹理已经可安全使用，也不证明图像或性能已在设备上验证。这里不把256或512概括成所有 D3D12 新特性、所有复制方式或其他图形 API 的统一要求。
