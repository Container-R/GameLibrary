# 没拆开字，为什么右括号还是跑到了下一行

奖励提示写着“获得（宝石）”。程序没有拆坏任何一个汉字，却把右括号单独留在下一行。问题不一定是字体宽度算错了：**一个完整字符的后面，并不一定允许换行。**

界面排版至少要分开回答两个问题：哪些位置可以断开；这些位置里，哪个适合当前行的宽度。字素簇边界帮助避免拆开一个组合字符，但不能代替换行规则。Unicode 的换行算法给出候选位置，最终选哪一个还需要排版程序结合可用宽度决定。[1]

## 六个字符，不一定排成两行

先不测真实字体，做一个可以手算的例子。字符串只包含以下六码点，没有空格或隐藏控制字符：

```text
获 得 （ 宝 石 ）
```

这里的空隙只是为了展示各字符，实际字符串仍是“获得（宝石）”。固定采用 Unicode 16.0.0 的默认换行规则，不加语言定制：四个汉字的换行类别为 ID，全角左括号 U+FF08 为 OP，全角右括号 U+FF09 为 CL。[2]

| 相邻字符之间 | 本例是否允许换行 | 原因 |
|---|---|---|
| 获｜得 | 允许 | 前序规则没有禁止，适用 LB31 |
| 得｜（ | 允许 | 本例没有适用的前序禁止条件，适用 LB31 |
| （｜宝 | 不允许 | LB14 不允许在开括号之后断开 |
| 宝｜石 | 允许 | 前序规则没有禁止，适用 LB31 |
| 石｜） | 不允许 | LB13 不允许在闭括号之前断开 |

规则按顺序处理，不能只拿最后的“其他位置允许”覆盖前面的限制。文本起点不换行，结尾按 LB3 结束；结尾不是与表中三个内部候选完全相同的可选机会。[1]

再人为规定每个字符占一格、每行最多三格，每次选择当前行能容纳的最远合法位置，不压缩或悬挂标点，也不采用紧急断行。结果是：

```text
获得
（宝
石）
```

第一行原本能塞下“获得（”，但不能在左括号后断，于是退到“得”后。第二行能塞下“（宝石”，但不能把闭括号留到下一行，于是又退到“宝”后。最后一行放“石）”。

这不是对中文排版美观程度的推荐，更不是游戏界面的实测截图。它只是说明：**六个字符、三格宽度，不足以推出恰好两行。** 原因既可能是实际字形宽度，也可能是合法断点的位置；这次纸面例特意排除了前一种因素。

## 排查时保留“候选位置”和“最终选择”两份信息

遇到标点落在不合适的位置，可以先看排版组件提供的换行机会，再看它如何按宽度选行。

如果“石”和“）”之间已经被当成普通候选，先检查所用规则、Unicode 数据版本和语言定制，而不是只改文本框宽度。如果候选位置正确，却仍在这里断开，再确认是否启用了紧急换行，以及组件在没有可容纳候选时采用什么退路。这类额外策略不能悄悄混同于默认换行机会。

如果断点合法，但结果仍溢出，则回到塑形、字体回退和实际宽度测量。上面的“一字符一格”是假设，不适用于一般的比例字体。也不要为了让这个例子变成两行，给所有中文词语盲目插入空格：中文没有空格，并不意味着没有换行机会。[1]

最后，还要用目标语言和产品风格检查结果。Unicode 允许规则定制，紧急换行也不属于这份算法负责的默认机会计算。不同组件不一定采用同一套语言策略；本文没有核验任何游戏引擎、浏览器或 ICU 版本的实际断行输出，也没有实现完整换行器。
