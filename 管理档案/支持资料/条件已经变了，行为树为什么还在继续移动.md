# 条件已经变了，行为树为什么还在继续移动

这份说明面向已经使用过行为树的 AI 程序员。假设巡逻机器人开始移动前，要先检查“通道仍允许进入”。检查通过，移动开始；稍后通道被关闭，机器人却还在继续。先不要认定条件读取错误：也可能是这一轮根本没有再次执行那个条件节点。

下面只分析 **BehaviorTree.CPP 4.6.2** 的普通 `Sequence` 与 `ReactiveSequence`，不是所有行为树的统一规则。例子是纸面推演，没有运行机器人或引擎；也不是 Killzone 3 的内部实现。

## 开始时通过，不等于运行中一直检查

每次让节点推进一次检查或执行，本文称为一次 **tick**。动作返回 `RUNNING`，表示它还未结束，并把控制权交回行为树；这不要求另开线程，也不意味着动作一直占住程序不返回。

先给序列两个子节点：前面是一个没有副作用的同步条件，读取通道是否允许进入；后面是跨多次 tick 的 `Move` 动作。条件只返回成功或失败。Move 使用库的 `StatefulActionNode`：首次启动走 `onStart()`，处于 RUNNING 时再次收到 tick 则走 `onRunning()`，让项目查询或推进这次移动。[1][3]

第一次实际 tick 时，条件成功，Move 启动并返回 RUNNING。普通 Sequence 会记住当前子节点的位置。下一次执行这个序列时，它从仍在运行的 Move 继续，而不是先回到已经成功的条件。[1]

因此，如果两次 tick 之间通道变为禁止，Move 自身又没有检查这个条件，第二次仍可以进入 `onRunning()`。黑板里的值已经变了，不代表前面的条件回调已经重新读取过它。这里的条件是一个已成功的子节点，而不是自动持续监视世界的守卫。

## 从头检查，会改变第二次 tick 的去向

把同样两个子节点放在本版本的 ReactiveSequence 下，第二次实际 tick 会从第一个子节点开始。假设条件这时读到禁止并返回失败，序列便不会先去调用 Move 的 `onRunning()`，而是重置子节点；对于仍处于 RUNNING 的 Move，这条路径会触发停止处理。[2]

区别发生在**下一次实际 tick**，不是通道值刚改变的瞬间。若上层没有继续 tick 这棵子树，或者条件拿到的仍是旧感知数据，换成 ReactiveSequence 也不能凭空及时发现变化。

本例还假定没有额外的前置脚本、注入回调或外部停止操作。库本身提供其他影响执行的机制，例如运行中的 `_while` 脚本条件可以触发 halt；所以不能把普通 Sequence 的子节点位置记忆，扩大成“它下面任何条件都不可能重新检查”。[4]

## 收到了停止处理，不等于移动系统已经停好

在这条固定源码路径中，ReactiveSequence 的失败处理会重置子节点，对 RUNNING 子节点调用 `haltNode()`，再进入动作的 `halt()`。对于 StatefulActionNode，这会调用项目实现的 **`onHalted()`**，随后重置节点状态。[2][3][4]

`onHalted()` 是项目接入停止与清理工作的地方，不是库替移动系统完成的通用取消协议。若 Move 早先发出了寻路或移动请求，怎样让执行器停止、何时确认停止，仍由该请求接口与动作实现负责。节点回到未运行状态，不能单独证明角色已不再移动；已经发生的位移也不会因此自动撤销。

排查时可以把过程连起来看：第二次 tick 有没有到达条件，条件返回了什么，Move 是否仍为 RUNNING，停止钩子是否被调用，以及移动执行器随后实际做了什么。只记录帧末的通道值，或者只看到节点状态重置，都不足以回答整条问题。

## 先决定条件的用途，再选择重评估方式

如果通道条件只用于决定是否允许开始，之后移动允许完成，普通 Sequence 的行为可能正符合设计。若要求观察到通道关闭后开始终止正在执行的移动，则需要持续检查的安排，并实现相应的停止路径。换节点会改变规则，不只是修一个通用库错误。

也不要把所有前置动作都搬进反应式序列。它在运行期间重新从头 tick，并会重置其他兄弟节点；把扣资源、发请求这样的副作用放在前部，可能使它们再次执行。这里刻意只用一个纯条件和一个长动作，不推广到多个异步子节点或更复杂的嵌套树。

先找出“这一轮从哪里继续”，再判断“条件是否应该再次检查”，最后追踪“停止通知怎样落到执行器”，比只盯着条件值更能分清是执行结构、设计选择，还是动作停止实现的问题。
