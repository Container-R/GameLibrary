## 必须保留的精确前提

**FT_Get_Char_Index 的输入是当前 charmap 所解释的字符码，不是无条件 Unicode 码点。** FT_CharMap 的说明虽然记载新 face 会尝试自动选 Unicode 映射，但这不证明任意现存 face 当前仍使用它。若正文以 Unicode 覆盖清单举例，宜直接限定“已成功选择 Unicode 字符映射”，例如说明 FT_Select_Charmap(FT_ENCODING_UNICODE) 的成功前提，而不写成无需检查的固定操作。没有对应 charmap 时选择会失败。这里无需给读者加入完整 C 调用流程。

在此限定内，非零索引仅支持所查询映射有相应条目，不包含当前整串所需的上下文替换或相对位置。A 与组合标记 M 的示意有效：两个索引本身不提供标记应相对基字符放在哪里的信息。不能反向说每一对 A/M 都必定替换成一个字形，或必定产生特定偏移；也不能用非零索引证明最终轮廓质量、图集上传或屏幕显示成功。A/M 必须持续标为抽象符号，不是拉丁字母 A/M 的实际字体输出。

固定 HarfBuzz 接口的一次调用接收一个 font 与 buffer，配合手册的片段属性/上层分段说明，足以支持“该调用本身不证明项目已正确组织多字体回退”。这不等于证明所有自定义字体回调都只能访问一个底层文件，更不支持逐码点换字体后拼接一定正确。建议正文只问实际文本组件如何选择字体、保持所需上下文并输出整串，不给通用 fallback 算法。

手册明确区分可选拉丁连字与其他必需操作；没有 fi 连字不是一般错误判据。双向顺序、塑形和最终绘制不是同一验证，既有双向索引文章/旧 ICU 格式结果不能移作本项证明。无需重复手册对阿拉伯形式的简化概括，或把介绍页关于不负责其他功能的措辞扩为所有 API 的永久能力清单。
