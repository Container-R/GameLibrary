## 完整性与生产价值

本文解决快速设置操作中“最终截图正确却漏掉中间错误提交”的实际测试设计困难。它不是单项 API 提醒：阶段契约、真实受理、先后/相邻/完成交错、请求与视图身份、布局输入、检查点和旧工作观察段首尾衔接，读者可以据此构造回归并区分加载、绑定、布局与画面证据。

全文通读后独立检查关闭起点的 L→S→P：L/S 只改变设置目标并回读；P 分配新界面代次并以当前目标发起内容请求，成功时再等该 token 的真实提交和匹配布局。因而没有要求关闭界面等待不存在的布局。异步双请求另从已打开且初始就绪的预览开始，不偷换同一条轨迹。

作者对同值合并、同步完成、失败、取消、关闭重开和提交重入均给出必要前提。核心推理在正文内，管理材料只承担来源与有限复现。布局坐标、裁剪和字形判据明确属于项目输入，本文没有假装交付通用排版检查器。

## 反例与实际复跑

除枚举先后和双请求交错，本轮完整阅读已发表模型源码和说明，执行原始 settings_model.py。退出码0，15个固定案例，实际输出与远端 results.json 逐字节相同，见本目录验证记录。三请求排列仅穷举“请求全部先受理”后的六种完成顺序。

自主核对的高风险反例是新请求 pending 时旧内容布局回执仍可有效：模型 operation_ready 同时核对 current、committed_token、status 和 layout_done，旧样本不能替新请求证明完成。完成时重新给旧 payload 贴 current 的错误反例，以及缩放按目标重建的假设反例，均只有最终快照通过，提交历史检出违规。

模型 complete 对过期请求只记录 ignored_completion，并未将旧记录 settled 置真。因此复跑支持“旧提交被拒绝”，不支持“生产加载器旧工作已终态清算”。正文已要求项目观察真实完成/失败/取消终态，附录也明示未验证底层停止或资源释放。无需为了督导制造另一个模型来扩大主张。

有限模型没有几何、字形、真实帧和平台调度；三个层次必须分别报告：原始接口/源码分析，有限状态模型结果，待接入真实项目的适配方案。当前正文区分清楚。
